## 连接池

### 普通连接

客户端连接池。 主要是java客户端每次和mysql服务端交互 都需要经历：

1.tcp三次握手 建立网络连接

2.mysql协议层的握手与认证 校验账号密码权限

3.执行实际的sql语句

4.tcp 4次挥手断开连接

124的开销很大 非常消耗cpu。 如果每次普通很短的crud操作 都需要走一次这个流程 高并发场景下 cpu时间和网络带宽会被浪费在建立和销毁连接上 mysql端的线程资源也会因频繁的创建和销毁崩溃。



### 池化技术

以空间换时间 应用启动的时候 提前建立好一批连接放在池子里 线程需要执行sql 直接从池里拿一个建立好的连接 用完在归还。 而不是关闭连接



### 连接池

常用的有 HikariCP Druid

核心机制：

- 初始化： 系统启动的时候 按照配置的最小空闲连接数 提前与 mysql建立好连接
- 分配与回收： 业务线程请求连接的时候 连接池优先分配空闲连接 如果连接池满了 并且所有连接都在使用中 新请求的线程 会被阻塞等待 直到超时触发异常 业务执行完毕后 连接标记为free 归还给池
- 探活与保活： 网络是不稳定的 mysql有 wait_timeout机制 (默认8h空闲 自动断开) 。连接池会定期发送类似select 1 的心跳 sql 确保池子的老连接正常存活 避免业务拿到死连接。
- 连接淘汰：超过 `maxLifetime`（最大生命周期）的连接会被强制平滑关闭并重建，防止长连接导致的内存泄漏或隐蔽状态残留。

### HikariCP

在 Spring Boot 开发中，数据源（DataSource）的底层实现就是连接池。HikariCP 之所以成为 Spring Boot 的默认选择，是因为它极简且性能极高（号称 Java 史上最快连接池）

配置：

​	核心是 控制 **连接数** 与 **超时** 的阈值

- 最大连接数 不是越大越好 连接数目过大会导致mysql线程上下文切换开销急剧上升 降低吞吐量
- 最小空闲数 池中始终保持的最小连接数。通常建议将其设置得和最大连接数 这样可以避免高峰期动态创建连接的性能抖动，追求极致的稳定。
- 超时连接时间 业务线程从池中借用连接时，最多等待多久。超过这个时间拿不到连接就会抛出异常 这往往是高并发压垮系统的第一个报警信号。

### 线程上下文切换

#### mysql里的案例

**cpu核心数目core** 就是线程工作的环境 一个线程需要一个cpucore作为环境 类似于灶台。

mysql 工作线程 对应 连接上mysql的连接数 类似于厨师

连接池小：

如果二者数目是1对1的 厨师处理完一件事就可以立刻做下一件事 产出效率 也就是吞吐量达到了极致。

连接池大：

一般cpu核心数目比较少 通常是 4、8、10 。如果连接池很大 100 。为了保证绝对公平 操作系统会规定 每个连接只能占用cpu0.1s处理自己的sql语句 时间到就得换下一个连接。

上下文切换开销： 一个连接处理一半sql 就被切换 他必须保存自己的线程状态 并且加载新的连接的线程状态 ... 大量的时间没有在处理sql语句 而是在切换线程 保存线程 加载线程状态上

#### 底层

在计算机底层，一颗单核 CPU 在同一个纳秒内，**绝对只能执行一个线程的指令**。

当并发连接数（线程数）远大于 CPU 核心数时，操作系统 OS 为了让所有线程看起来都在“同时”运行，会采用时间片轮转（Time-Slicing）机制。它会频繁地暂停当前线程，切换到另一个线程。

这个“切换”动作极其昂贵，它包含：

- **寄存器保存与恢复：** 把当前线程在 CPU 寄存器里的所有临时数据、程序计数器（记录代码跑到哪一行了）全部打包存到内存里；然后再把下一个线程的数据从内存里读出来塞进 CPU。
- **CPU 缓存失效（Cache Miss）：** 每个线程在运行时，CPU 的 L1/L2 缓存里存的都是它需要的数据。一旦切换线程，缓存里的数据就没用了，必须重新去慢速的主内存中读取，这会导致极大的延迟。

当连接数过大时，CPU 的使用率可能飙升到 100%，但其中 80% 的算力都在做上下文切换，只有 20% 的算力在真正执行 SQL。系统陷入了所谓的“抖动/颠簸（Thrashing）”状态，外部表现就是：**吞吐量断崖式下跌，响应时间飙升至几秒甚至超时。**

### 主从架构与读写分离的连接池

单体应用 一般只需要配置一个connect pool 指向一台mysql。 主从架构下 一般是一主多从  主库负责写 从库负责读。 

此时 一般会引入类似于 **ShardingSphere-JDBC** 或 **MyBatis-Plus 动态数据源 (Dynamic DataSource)** 的中间件。

本质逻辑： 应用内部会维护多个独立的连接池。

1.Master Pool：指向主库 只配置少量的核心连接 就处理insert update delete

2.Salve Pools ：一般是多个池 配置比较大的最大连接数  通过负载均衡算法（如轮询、随机）分发大量的 `SELECT` 查询。



当业务代码加上类似 `@Transactional` 注解，或者执行写操作时，动态数据源框架会拦截请求，智能地从 Master Pool 中借出连接；而对于普通的查询逻辑，则从 Slave Pool 中借出连接。

 是java端 也就是客户端配置的 客户端连接服务端时需要的。

## 连接层

mysql的连接层有三大职责。

### 连接处理与线程分配

每当springboot的HikariCP发来一个建立连接的请求的时候 

1.客户端每进来一个tcp连接 mysql连接层就会分配一个后台的物理线程伺候这个连接 负责接收它的sql并返回结果

2.避免频繁创建和销毁这个专属线程  连接层内部维护了一个线程缓存 连接断开的时候 连接不销毁 放回缓存 新连接进来 直接从缓存里拿 此时类似于Hikaricp的pool技术。

3.高并发情况下 不可能为每个连接分配一个线程 会导致mysql 内存暴涨 cpu上下文切换瘫痪。 所以mysql企业版 在连接层会引入线程池插件 采用半同步/异步的多路复用极致 类似于reactor模型 young少量的活动线程处理大量的并发连接。



### 授权认证

线程接待后 连接层继续做安全校验

1.鉴权 校验ip在白名单 账号密码是否正确 如果错误 连接层直接打回 报`Access denied`

2.权限加载：鉴权通过后 连接层去查系统表 把用户的权限查出 加载到当前线程的内存上下文 比如有没有insert权限 能不能访问特定的database 供后续的sql执行做权限管理



### 连接管理与限制

控制最大连接数  以及监控连接状态 踢掉坏连接。

也就是一个看门的作用。 处理外部与mysql的连接。

## 比喻总结



**Spring Boot（HikariCP）** 是一家公司的外联部（客户端连接池），提前雇好了 10 个业务员（10 个 TCP 连接），随时准备去办事，省去了每次现招业务员的时间。

**MySQL（连接层）** 是政务大厅。大厅有前台保安（负责**授权认证**），大厅内部有办事窗口的公务员（**分配的 Thread**）。为了提高效率，政务大厅不允许公务员办完一个事就下班辞职，而是让他们在大厅休息区待命（**内部维护的线程池/Thread Cache**）。

## 案例

3000个用户并发产生http请求

springboot 内置的Tomcat服务器开始处理请求 默认有200个核心线程 开始处理这些请求

tomcat执行到需要查db的时候 去HikariCP里借连接 假如连接池大小为20

只有20个java线程借到连接 其他180个阻塞等待

由于sql执行很快 干完活就归还给池子 其他线程继续借用干活。



一个用户的一个事务 里面有5个sql语句 mysql连接层只需要分配一个后台线程 在线程池里也只需要一个连接。

tomcat从HikariCP拿出一个连接 对应mysql的一个处理线程 然后串行执行5条sql。 



如果5条sql语句显示开启多线程并发查询 则就回去连接池里拿5个连接 mysql服务端就会分配5个线程去处理5条sql。



## 总结

连接池 是 java应用层和mysql的连接  线程池是mysql内部真正允许执行 sql操作的线程数目。

都是一个漏斗设计 多对少的设计 一时间只能进去一部分  其他都会阻塞等待 为了削峰填谷。

第一个漏斗为了保护mysql 一时间不让太多的连接 连接mysql

第二个漏斗保护mysql所在服务器的cpu和内存。 控制mysql内部真正参与cpu调度的物理线程数量 避免频繁的上下文切换。 一次建立200个连接 也只让几十个线程活跃 其他短暂阻塞 保证cpu能专心完成部分任务 吞吐量反而更高



加上用户就是三个漏斗【  多对少 阻塞等待逻辑】

从 Java 代码到 MySQL 磁盘的脉络。

1. 用户的 HTTP 请求要在 Tomcat 线程池里排队（多对少）。
2. Tomcat 线程要在 HikariCP 连接池里抢连接（多对少）。
3. 拿到的网络连接，到了 MySQL 端，还要在服务端线程池里排队等待 CPU 执行（多对少）。
