## 连接池

### 核心本质

连接池池化的是网络连接对象 TCP Socket。

是java端 也就是客户端配置的 客户端连接服务端时需要的。 

在这里客户端就是后端程序 服务端就是mysql 。提前建立好一批tcp长连接

### 普通短连接

客户端连接池。 主要是java客户端每次和mysql服务端交互 都需要经历：

1.tcp三次握手 建立网络连接
2.mysql协议层的握手与认证 校验账号密码权限
3.执行实际的sql语句
4.tcp 4次挥手断开连接

124的开销很大 非常消耗cpu。 如果每次普通很短的crud操作 都需要走一次这个流程 高并发场景下 cpu时间和网络带宽会被浪费在建立和销毁连接上 mysql端的线程资源也会因频繁的创建和销毁崩溃。


### 池化技术
以空间换时间 应用启动的时候 提前建立好一批连接放在池子里 线程需要执行sql 直接从池里拿一个建立好的连接 用完在归还。 而不是关闭连接

### 连接池

常用的有 HikariCP 、Druid

核心机制：

- 初始化： **系统启动**的时候 按照配置的**最小空闲连接数** 提前与 mysql建立好连接
- 分配与回收： 如果连接池满了（无法创建新的连接） 并且所有连接都在使用中 （旧连接忙碌）新请求的线程 会被阻塞等待 直到超时触发异常 业务执行完毕后 连接标记为free 归还给池
- 网络是不稳定的 定期会发送select1的请求 确保连接是健康的
- 单条连接是有最大生命周期的，超过后会被强制平滑关闭并重建，防止长连接导致的内存泄漏或隐蔽状态残留。

### HikariCP

在 Spring Boot 开发中，数据源（DataSource）的底层实现就是连接池。HikariCP 之所以成为 Spring Boot 的默认选择，是因为它极简且性能极高（号称 Java 史上最快连接池）

配置：

​	核心是 控制 **连接数** 与 **超时** 的阈值

- 最大连接数 不是越大越好 连接数目过大会导致mysql线程上下文切换开销急剧上升 降低吞吐量
- 最小空闲数 池中始终保持的最小连接数。通常建议将其设置得和最大连接数 这样可以避免高峰期动态创建连接的性能抖动，追求极致的稳定。
- 超时连接时间 业务线程从池中借用连接时，最多等待多久。超过这个时间拿不到连接就会抛出异常 这往往是高并发压垮系统的第一个报警信号。



### 主从架构与读写分离的连接池

单体应用 一般只需要配置一个connect pool 指向一台mysql。 主从架构下 一般是一主多从  主库负责写 从库负责读。 

此时 一般会引入类似于 **ShardingSphere-JDBC** 或 **MyBatis-Plus 动态数据源 (Dynamic DataSource)** 的中间件。

本质逻辑： 应用内部会维护多个独立的连接池。

1.Master Pool：指向主库 只配置少量的核心连接 就处理insert update delete

2.Salve Pools ：一般是多个池 配置比较大的最大连接数  通过负载均衡算法（如轮询、随机）分发大量的 `SELECT` 查询。



当业务代码加上类似 `@Transactional` 注解，或者执行写操作时，**动态数据源框架**会拦截请求，智能地从 Master Pool 中借出连接；而对于普通的查询逻辑，则从 Slave Pool 中借出连接。



## 连接层

mysql的连接层有三大职责。

### 连接处理与线程分配

每当springboot的HikariCP发来一个建立连接的请求的时候 

1.客户端每进来一个tcp连接 mysql连接层就会分配一个后台的物理线程伺候这个连接 负责接收它的sql并返回结果。（是1:1的模型）

2.避免频繁创建和销毁这个专属线程  连接层内部维护了一个线程缓存 连接断开的时候 连接不销毁 放回缓存 新连接进来 直接从缓存里拿 此时类似于Hikaricp的pool技术。



### 授权认证

线程接待后 连接层继续做安全校验

1.鉴权 校验ip在白名单 账号密码是否正确 如果错误 连接层直接打回 报`Access denied`

2.权限加载：鉴权通过后 连接层去查系统表 把用户的权限查出 加载到当前线程的内存上下文 比如有没有insert权限 能不能访问特定的database 供后续的sql执行做权限管理

### 连接管理与限制

控制最大连接数  以及监控连接状态 踢掉坏连接。

也就是一个看门的作用。 处理外部与mysql的连接。

## 总结

连接池 是 java应用层和mysql的连接  连接层里的最大连接数是mysql内部真正允许执行 sql操作的线程数目。

都是一个漏斗设计 多对少的设计 一时间只能进去一部分  其他都会阻塞等待 为了削峰填谷。

第一个漏斗为了保护mysql 一时间不让太多的连接 连接mysql

第二个漏斗保护mysql所在服务器的cpu和内存。 控制mysql内部真正参与cpu调度的物理线程数量 避免频繁的上下文切换。 一次建立200个连接 也只让几十个线程活跃 其他短暂阻塞 保证cpu能专心完成部分任务 吞吐量反而更高



加上用户就是三个漏斗【  多对少 阻塞等待逻辑】

从 Java 代码到 MySQL 磁盘的脉络。

1. 用户的 HTTP 请求要在 Tomcat 线程池里排队（多对少）。
2. Tomcat 线程要在 HikariCP 连接池里抢连接（多对少）。
3. 拿到的网络连接，到了 MySQL 端，能拿到mysql的线程的数量 也是多对少
