

iInnoDB 的整体设计思想是：尽可能将随机磁盘 I/O 转换为**内存操作**和**顺序磁盘 I/O**，通过缓存、延迟写、批量刷盘等机制提升数据库吞吐量。

因为不管是 buffer pool 、change buffer 、RedoLog 都是 随机IO->内存->顺序IO


## Buffer Pool

内存中最大的区域 作用主要是 缓存磁盘上的各种Page 比如数据页 索引页  Undo页

查询数据的时候 会先去bufferpool里面看有没有  有的话直接返回 走内存读。 没有的话 去disk读取 并且加载到 buffer pool里。

修改数据的时候 也是先修改buffer pool里的数据 此时变成脏页 再由后台线程定期刷入磁盘。如果数据不在buffer pool里 也必须去磁盘加载到buffer pool里 才能修改。 不能直接改磁盘数据

数据结构： 按Page 默认16KB 为单位进行管理

### 内存管理算法



 使用改进后的LRU 最近最少使用

传统LRU 问题： 如果发生全盘扫描 大量冷数据会瞬间塞满 把热点数据挤出去 导致缓存污染

冷热分离方案： 把LRU按比例分为两部分 : New Sublist 热数据区 默认5/8   Old Sublist 冷数据区 3/8

运行机制：

**新读取的页 先放在old区的头部 在old区停留超过一定阈值 且再次被访问 就会移动到new区的头部** 



## change buffer

写缓冲区。

实际上优化的是一段时间内的多次update 、delete操作、insert操作。 

**总结：优化非唯一二级索引页的插入、删除和更新操作。**

由于二级索引树一般是在磁盘里，不在bufferpool里。修改了索引值，更新的是二级索引树叶子结点的页面，会把本来的索引值+主键（二级索引树叶子结点存的一行数据就是索引值+主键）在叶子结点页面的一行**标记**为删除，再插入新的数据。

由于在磁盘里一次修改是一次随机I/O ，多次修改就是多次随机IO。 
当需要更新一条数据，并且不在bufferpool里的时候，innodb不会去disk里读取这个页面在更新，而是把更新操作记录在写缓冲区changepool里。

当该 **页面被访问**的时候 或者**后台线程任务定期执行** 或者**数据库关闭**(要求所有数据都正常落盘。) innodb就会把changebuffer里关于这个非唯一索引的操作和合并到页面里。
把多次随机IO 立即执行 变成 延迟执行 一次批量合并。

核心目的是优化  **非唯一 普通索引**的写入性能。 也就是二级索引树


只适用于 非唯一普通索引 。 因为唯一索引 在写入的时候 必须把数据页读入内存 来校验是否冲突。 页面都读入内存 直接修改buffer pool就行了 change buffer失去了意义。





## Adaptive hash index AHI

自适应哈希索引   

B+树再快 查询的时候 也会经过几层节点的寻路 查询效率是logn。 

- 工作机制：
  - InnoDB 会持续监控表上各索引页的查询频率。如果它发现某些确定的值被极度频繁地访问（比如相同的等值查询），它就会在内存中基于 B+ 树的这一部分**自动构建**一个哈希索引。

- 特性：

  - 它是“自适应”的，由数据库内部隐式创建，外部无法手动干预（只能选择开启或关闭）。

  - 它**只支持等值查询**（如 `=`, `IN`），不支持范围查询（`>`, `<`）。



## log buffer

日志缓冲区 崩溃恢复的缓冲区。

为redo log 重做日志服务。 为了保证事务的持久性 又不能让每次修改都同步刷盘 开销巨大。  

意义是减少刷盘 还可以批量刷盘

innodb采用WAL write-ahead logging 日志先行技术

### WAL

修改数据 先在buffer pool里修改 产生 脏页

然后把修改的物理页修改日志 redolog  写入内存的log buffer

**事务提交**（取决于刷盘策略）的时候 再把log buffer里的日志 顺序io的方式 快速刷入disk里的redo log。(实际上中间还有一步内核存储区oscache)

只要日志落盘 就算db宕机 重启后也能恢复。

方案，MySQL 挂了数据不丢，只有服务器所在操作系统宕机或断电才会丢失约 1 秒的数据）。


## 总结：

执行一条update 先看buffer pool里有没有该数据页 

没有并且是非唯一索引 就把修改先记入change pool。等待后续merge到磁盘

有的话 就在内存里修改 同时生成redolog放入log buffer

如果该数据频繁的被等值查询 就使用ahi进行加速。

并且change buffer 和redolog也不是二选一是协同工作 本身changebuffer里的修改操作也会记录到redoLog里 。所以即使数据库崩溃 changebuffer里的数据也不会丢
