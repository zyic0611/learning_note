离线评测集只能覆盖已知的问题 但是线上输入会不断变化。
如果线上问题不进入评测集 只是修改程序 后续版本可能还会出现。

所以核心目的是 **把一次线上失败转换为以后每个版本都通过的测试**

## 线上问题的来源

一般是三个
- evaluator评价任务失败
- metric指标：成功率下降 token 延迟异常
- 用户反馈：投诉、重新提问、人工接管

## 人工确认

线上异常必须人工确认 进行故障归因（失败run或者metric）和人工复核 代表是一个真实的 值得长期预防的失败模式

人工确认的点：
- 是agent真的失败
- evaluator 是否误判
- 用户提问本身有问题
- 外部系统 依赖服务 临时故障

## trace---case

失败的trace要具备下列其中一种特性 才值得提炼为case
- 新的失败类型
- 高频
- 高风险
- 以前修复 但是再次出现
- 可以稳定复现的问题 也就是不要偶然

trace不是直接变成case  他包含大量细节和偶然数据 从中提炼出case必备的那些信息
- 输入
- 成功标准
- 判断证据
- 分类标签

## 修改后验证

修复badcase后 回放整个baseline 要先保证baseline不被破坏 然后保证新badcase是否修复
最后看质量、成本、延迟有没有退化


然后灰度上线 继续监控metric和失败trace。

## 完整闭环
```text
线上运行
→ Metric / Evaluator / 用户反馈发现异常
→ 找到对应 Trace
→ 故障归因并确认真实失败
→ 提炼成评测 Case
→ 修改 Agent
→ 对比 Baseline 做回归
→ 灰度上线
→ 继续观测
```
