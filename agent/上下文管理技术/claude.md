## 上下文管理什么？
区分三类 ：
- session记录 ：会话记录，比如llm、用户、工具调用等完整消息历史 用于持久化 恢复 追溯
- runtimeState与外部文件：主要存外部的真实状态（比如计划、已使用的skill、工具状态）和具体的文件，用于记录当前的工作状态
- context：交给模型完成一次推理的全部信息

上下文管理的工作**就是从前两类信息中 构造第三类信息 并且控制context的大小**。

## 完整链路
1. 用户的输入 - 上一轮的工具结果
2. 写入session 并且更新runtime state
3. 取出工作消息
4. 构造本轮消息视图
	- 大工具结果外置
	- 历史消息剪裁
	- 清理旧的工具结果 同时考虑前缀缓存
	- 投影视图
	- 自动压缩 两种路径
5. 结合系统指令 工具定义 项目信息等 最后构造context

## 大工具结果外置

主要是在tool result很大的情况 可以把它写入disk 然后模型收到一个
**预览+完整的结果路径**

这一步并非做语义总结 主要是把结果用 预览和地址替代。 

主要是在构造context的时候 进行一个tool result侧的 压缩

## 历史剪裁 history snip

大工具结果外置只能处理单条结果过大的情况 但是小结果还在。 所以多条小结果的存在仍会导致context过大。

这一步就是从当前工作信息里裁掉部分历史片段。

  

这一步主要就是剪裁 并不是做摘要。 这部分不仅是处理工具 还会处理别的消息 核心聚焦于移除历史片段。

  

## microCompact

核心处理的问题是 以前读过的文件、搜索结果、命令输出等信息 是否还值得每轮完整的携带。

处理的是tool result 核心聚焦于工具正文是否要存在。

原本 toolcall-toolresult. 处理后 变为 toolcall-摘要/地址引用 都有可能 需要正文的时候可能需要重新读取。

  

这一步就要看缓存是否过期。

如果间隔时间比较长 基本上 前缀缓存过期了 那么直接替换正文、清理旧工具结果。

如果缓存还有复用价值的时候 也就是不能影响前缀缓存的时候 可以用API清理。

  

API清理： 工具正文不变 但是在最后加上编辑字段。 也就是让模型仍然命中前缀缓存 但是模型读到编辑字段 就知道该工具正文可以忽略。 也就是context不变 变的是让服务端忽略那部分。

  

## Context collapse 读时投影

前面几步都是在构造上下文的时候针对历史消息进行一个处理。

这一步会保留完整历史 并且把部分历史的摘要存到独立的 collapase store里。

当构造context的时候 不全量注入完整历史 **而是用store里的摘要历史替换部分历史信息 相当于对本来的信息做了折叠 再结合未折叠信息 构造新的context。**

模式需要显式开启 但是主动自动压缩会被抑制。

开启后大概在context达到90%的时候使用读时投影。 具体阈值不一定。

  

## Auto-Compact

这一步是自动触发和调度的一个机制 并不是具体压缩的实现方法。

当context达到某个阈值的时候 优先启用 **session memory conpact：**

有已有会话摘要就用 然后再保留部分原始消息的尾部。 作为新的context。

如果摘要不可用、边界消息太大、摘要后还是太大。就回退 不用这个。

他并不是对context切分后再对历史消息做摘要 一般优先用已有的session compaction
