
## 检索的时机

最简单的方案是在会话开始时加载用户的全部记忆。
当记忆很少时，这可以工作。随着记忆增长，更合理的做法是区分预加载和按需检索。

### 预加载稳定背景
会话开始时加载少量、高频且相对稳定的信息，例如：

```text
默认回答语言
当前项目技术栈
长期有效的协作偏好
```
预加载可以减少每一步重复查询，但必须严格控制数量。

### 按需检索具体信息
只有当前任务明确需要历史事实或经验时才检索：

按需检索可以节省 Context，并降低无关记忆干扰。

实际系统通常混合使用：

```text
会话开始加载少量稳定背景
任务执行中按需检索具体记忆
```

## 构造检索

检索不能只用用户最后一句输入作为检索条件   Runtime 应结合当前**任务**构造检索需求：

目标+实体+用户、租户、作用于+所需要的记忆类型+时间范围

目标作为语义条件 所有加起来可以构成精确匹配的结构化条件。

## 检索策略
检索这一步最好宽一些 避免重要记忆过早遗漏。
所以可以组合

语义向量检索+关键词检索

检索回来需要重排 因为进入context的空间有限
需要考虑
- 与目标的相关性
- 实体和属性匹配程度
- 信息来源与置信度
- 时效
- 重复性
重排依据 可以是业务规则和加权分数 如果候选规模和语义复杂度上去 就需要引入重排模型

并且也要受token预算约束  memory的目标是用尽可能少的信息 帮助llm作出更好的决策

并且memory检索出来的信息 注入context 要注明来源于历史记忆。
