## 1. 为什么风险会被放大

拆分 Agent 缩小了单个职责，却增加了模型调用、数据传递、权限组合和独立失败点。并行与嵌套委派还可能造成资源竞争、循环和任务爆炸。

因此设计重点不只是让每个 Agent 能工作，还要限制它出错时能影响多大范围。

## 2. 权限从全局向下收缩

Specialist 只应获得当前子任务需要的工具、数据、资源范围和操作类型。

```text
Agent 的长期能力边界
∩ 当前子任务的临时授权
∩ 具体工具调用的参数规则
= 本次真正可执行的动作
```

代码分析 Agent 可以读仓库，但不能发布；发布 Agent 即使拥有发布工具，本次只被批准测试环境，也不能切换到生产环境。

> 委派任务不等于继承 Orchestrator 的身份和全部权限。

高风险凭证由 Runtime 在执行时注入，不能作为文本放进 Handoff，也不能暴露给模型。

## 3. 局部失败不等于全局失败

分发任务时，需要先明确它对总目标的重要性：

- **required**：失败后总目标无法完成；
- **degradable**：可以切换到较弱方案；
- **optional**：失败后允许跳过。

子 Agent 失败后，Orchestrator 才能有依据地选择有限重试、备用能力、跳过、转人工或终止。

重试、Fallback、Checkpoint 和幂等仍由第五部分的 Orchestration 机制实现。Multi-Agent 只额外决定失败发生在哪个职责边界，以及是否影响依赖它的其他任务。

持续失败的 Agent 或下游服务应停止接收新任务，但隔离范围要准确。某类输入失败不代表整个 Agent 不可用，一个工具故障也不代表所有能力都应关闭。

## 4. 预算也从全局向下分配

如果每个 Agent 独立决定调用次数，局部行为合理，整体成本仍可能失控。

Orchestrator 应维护端到端预算，再为子任务分配时间、Token、模型与工具调用次数、并发和委派深度。子任务预算不能超过全局剩余预算。

预算不足时，应先保证 required 任务，而不是平均分配后让所有分支都无法完成。

## 5. 防止循环与任务爆炸

最简单的控制方式仍是禁止 Specialist 直接相互调用，所有新增任务回到 Orchestrator 审批。

如果允许嵌套委派，还需要：

- 限制最大深度和可调用 Agent；
- 用“目标 + 关键输入版本 + 作用域”识别重复任务；
- 已完成的结果直接复用，执行中的相同任务只等待一次；
- 所有分支共享同一全局预算和终止条件。

这样可以阻止 Agent A 和 B 以相同目标反复委派，也能避免并行创建大量等价任务。

## 6. 最后判断是否值得

Multi-Agent 应与单 Agent、Tool 或 Subflow 比较：

```text
收益：成功率、专业质量、权限与 Context 隔离、并行效率
成本：延迟、Token、工具调用、Handoff 失败、冲突和人工介入
```

如果只是把一个 Prompt 拆成多个 Prompt，没有提高质量或隔离能力，却增加了协调成本，就应该回退到更简单的结构。

> Multi-Agent 的价值不由 Agent 数量决定，而由分工收益是否超过协作成本决定。
