## 1. 为什么 Prompt 写清楚了仍然会失败

Prompt 已经说清楚任务，模型还是可能回答错误：

- 没拿到当前订单状态；
- 使用了已经过期的历史信息；
- 缺少上一轮工具结果；
- 同时看到两个版本的退款规则；
- 被大量无关对话干扰。

这些问题不是“指令怎么写”，而是“这一轮模型看到了什么”。

> Prompt Engineering 负责表达任务，Context Engineering 负责构造模型本轮可见的信息。

Prompt 是 Context 的一部分，但 Context 还包括用户输入、历史、业务 State、工具结果和外部资料。

---

## 2. Context 是本轮决策的工作视图

模型不能直接读取 Runtime 中的完整世界。

Runtime 需要从系统拥有的信息里，选出当前判断真正需要的部分：

```text
用户请求
历史对话
任务 State
工具定义与结果
文件、RAG、数据库
长期 Memory
      ↓ 选择、过滤、压缩、组织
本轮 Context
      ↓
模型判断
```

所以 Context 不是“所有可用信息”，而是：

> Runtime 为模型当前**这一步决策构造的最小工作视图。**

“提取订单号”和“判断能否退款”属于同一个任务，但需要的 Context 不一样。前者只需要用户表达，后者需要订单状态和退款规则。

如果不先明确本轮要做什么判断，就无法判断哪些信息应该进入 Context。

---

## 3. Context 随任务复杂度逐步升级

### 只用 Prompt 和当前输入

```text
任务说明 + 当前用户请求
```

适合分类、抽取和改写。如果一次调用就能完成，不需要历史、记忆和检索。

### 出现跨轮信息后，加入必要历史

用户说“帮我退掉刚才那个订单”时，模型需要知道“刚才那个”指什么。

但这不代表必须放入全部聊天记录。旧消息可能已经失效，也可能属于另一个任务。

### 模型内部知识不够时，加入外部资料

例如查询当前退款政策、产品文档或数据库。

此时不能只看“有没有检索结果”，还要判断：

- 是否与当前问题**相关**；
- 来源是否**权威**；
- 内容是否已经**过期**；
- 用户是否**有权访问**。

### 进入 Agent Loop 后，加入 State 和工具结果

模型需要知道任务已经进行到哪一步、工具刚返回什么、接下来允许做什么。

Runtime 应提供必要的 State 投影，而不是把完整数据库对象和全部执行日志交给模型。

具体的意思就是 runtime具有完整的 权威的业务 state 。 这个state就是业务信息 比如数据库查询出来的对象信息 全部的执行日志。 但是模型本轮可能不需要全量信息  

选择：只需要部分字段 或者一些敏感信息 
隐藏：比如手机号 身份证号 不能给模型 需要过滤
转换：底层字段要组合成模型直接理解的业务语义 比如对某些字段做一个计算、聚合等等 处理后再给模型。

不同节点需要的投影不同 并且模型拿到的只是只读信息 。

### 信息过多后，开始选择和压缩

当候选信息超过本轮真正需要的内容时，重点不再是继续增加，而是删除噪声：

```text
按需召回
→ 权限和版本过滤
→ 去重与冲突处理
→ 摘要或结构化压缩
→ 按用途组织
```

---

## 4. 怎样构造一轮 Context

第一步先**定义本轮决策**，例如“识别退款意图”或“判断当前订单能否退款”。

第二步从历史、State、工具结果和外部资料中**召回候选信息**。

第三步执行**硬过滤**。无权访问、版本失效、租户不匹配的内容，不应进入模型。权限检查必须发生在输入模型之前，不能指望模型看见秘密后自行保密。

第四步按相关性、权威性和新鲜度**排序**。文本相似不代表真正有用，旧订单状态与当前问题高度相似，也不应该覆盖实时结果。

第五步**压缩成最小充分信息**，例如：

- 删除无关历史；
- 把长对话压缩成任务状态；
- 从工具原始响应中提取稳定字段；
- 合并重复事实；
- 只保留当前步骤需要的规则。

压缩不是单纯减少 Token，而是在不丢失决策信号的前提下降低噪声。

最后按**用途组织**，让模型能区分：

```text
Instructions：应该怎样行动
Current Task：这一轮要解决什么
State：任务进行到哪里
Evidence：判断依据是什么
Available Actions：可以提议哪些动作
Output Contract：结果如何返回
```

调用结束后，Runtime 根据新状态**重新构造**下一轮 Context，而不是永远在旧消息后面追加内容。

## 5. 三种常见的控制方式

### 按需获取

只在当前步骤需要时获取详细信息。

先识别订单号，再查询该订单；不要任务一开始就加载用户全部订单。

### 渐进披露

先提供高层信息，确定进入某个分支后再加载细节。

例如先告诉模型有哪些工具，选中某个工具后再提供它的详细参数或相关资源。

### 历史压缩

长任务中把执行轨迹压缩成稳定状态：

```text
当前目标
已确认事实
已完成步骤
未解决问题
下一步约束
```

这不是普通聊天摘要。它只保留未来决策仍然需要的信息。

## 6. 为什么 Context 不是越长越好

内容越多，模型越可能遇到：

- 无关信息争夺注意力；
- 新旧事实互相冲突；
- 重要规则被埋没；
- 原始工具结果大量膨胀；
- 成本延迟
- 不好的信息进入

信息虽然还“在上下文里”，不代表模型能稳定使用。

因此 Context 的目标不是尽可能完整，而是提高：

```text
有效决策信息 / Context 成本
```

高质量 Context 应该是最小充分集。

## 总结

prompt 只表达 这个模型节点  任务是什么 需要什么输入输出  相关的一些任务定义
而context 包括了prompt 。多出来的部分 主要是给这个模型工作 提供充足的信息 

但是context不是越大越好。
首先是随着任务复杂度 开始加入东西 升级。
只有一轮对话 context基本和prompt差不多。 只有任务定义 输入是什么
多轮对话就需要提供历史信息
需要外部信息的时候 就需要工具调用的信息 或者接入知识库
context太长的时候 就需要合理的压缩策略。

而构造context 肯定是runtime执行的 确定性的程序执行的。
首先定义本轮决策 也就是这一轮的核心任务是什么
然后根据决策 拿到所需要的相关信息
必须做一层过滤 过滤掉冲突、没权限、过期等信息
再对信息做一个排序 按照优先级
然后压缩成最小充分信息 比如有重复的信息 一些废话等等 压缩一下
最后做一个架构化 让模型可以充分理解。

并且react循环中 每一轮任务不一样 所以每一轮构造的context是不一样的。
