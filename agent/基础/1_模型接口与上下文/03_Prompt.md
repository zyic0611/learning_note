## 1. 解决什么问题

Runtime 决定在**某个节点调用模型**，但模型还不知道：

- 任务是什么
- 参考那些信息
- 完成条件
- 遇到模糊情况时如何判断；
- 结果输出

**核心定义Prompt**  就是对当前模型节点的行为说明。 在一个节点开始调用模型的时候 定义上述内容 但是模型真正需要工作 需要的是全部context 也就是上下文 上下文粒度更粗 包括prompt 以及历史消息 业务状态 参考资料等等所有的的东西。 prompt聚焦于行为界定。

---

## 2. 最小 Prompt 

最小版本通常只需要三件事：

```text
任务：模型这次只负责做什么
输入：它可以依据什么信息
输出：结果以什么形式返回
```

如果这个版本已经稳定，就不需要继续加入角色设定、长规则和大量示例。

Prompt 的升级路线应该是：

```text
写出最小版本
→ 用真实输入测试
→ 找到具体失败
→ 只增加解决该失败的约束
→ 再次测试
```

不是先想象所有风险，再写一份几千字的万能 Prompt。 是针对具体失败 增加行为约束。

---

## 3. 真实失败会推动 Prompt 逐步升级

### 目标太模糊：增加成功标准

```text
判断用户是否想退款。
```

这句话没有说明“咨询退款政策”算不算退款意图。模型可能把咨询和执行混在一起。

可以改为：

```text
区分 policy_query、refund_request 和 unknown。
只提取用户明确表达的意图。
```

“准确、专业、全面”不是成功标准，因为程序无法判断它是否满足。成功标准要尽量能被观察或校验。

### 模型做了多余的事：增加职责边界

模型可能不仅识别意图，还开始判断退款资格，甚至提议直接退款。

此时需要说明：

```text
负责：识别订单号和意图。
不负责：判断退款资格、执行退款、猜测缺失订单号。
```

角色设定真正有价值的地方也是限定任务语境和责任，不是写一句“你是世界顶级专家”就让模型获得新能力。

### 模糊输入处理不稳定：增加判断策略

```text
订单号缺失时，返回 need_clarification。
存在多个订单号时，返回候选列表，不自行选择。
用户只询问订单状态时，不推断为退款请求。
```

判断策略适合处理需要语义理解的分支。

但重试次数、审批状态、金额限制和事务流转是确定性规则，不应让模型仅凭 Prompt 维护。

### 定义仍然讲不清：加入少量示例

Few-shot 示例适合展示难以用一句规则讲清楚的决策边界。

通常只需要覆盖不同模式：

- 一个正常案例；
- 一个信息不足案例；
- 一个容易误判的边界案例。

示例不是越多越好。大量相似示例只会增加 Token 和干扰。

---

## 4. 区分

系统要求可以按强制方式分成三层。

### 软约束：主要由 Prompt 引导

例如表达风格、信息组织方式、开放语义判断。

模型偶尔偏离不会直接破坏系统状态。

### 可校验约束：Prompt 加程序校验

例如 JSON Schema、字段类型、枚举值和引用格式。

Prompt 告诉模型怎么输出，Runtime 检查输出是否真的符合要求。

### 硬约束：必须由系统强制

例如用户权限、退款金额、工具访问范围、审批和幂等。

这些规则一旦失效就会产生真实副作用，所以不能依赖模型自觉遵守。

> 能被程序明确验证，并且失败代价较高的规则，不应该只存在于 Prompt 中。




## 总结

prompt 属于context 但是它主要是行为方面的界定。
最小prompt 就是说明任务、输入、输入。
然后使用真实的测试用例 针对真实失败的情况进行增强。
增强手段： 增加成功标准、增加职责边界、增加路由判断、增加few-shot。
最后软约束 比如风格 写在 prompt里
可校验的约束，比如输出格式写在prompt里做软约束 然后也要用确定性的程序补充校验。
