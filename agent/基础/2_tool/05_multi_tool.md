## 1. 多tool 


 Runtime 不只是在“重复调用模型”，还要处理：

- 工具之间是否存在依赖；
- 哪些调用可以并行；
- 部分工具失败时保留哪些结果；
- 什么错误值得重试；
- 写操作是否被重复执行；
- 循环什么时候必须停止。

> 多工具可靠性的核心，是 Runtime 把一串概率性行动建议约束成有依赖、有预算、有终态的执行过程。

---

## 2. 先判断工具之间的依赖

### 有依赖时必须串行

后一步需要使用前一步结果：

在不知道 需要的信息 之前，第二个调用无法正确生成。

### 没有依赖时可以并行

三者互不依赖，可以并行降低总延迟。

但“模型一次生成多个 Tool Call”不等于这些调用一定能并行。Runtime 还要检查：

- 是否读写同一资源；
- 是否存在隐含顺序；
- 一个调用会不会改变另一个调用的前提；
- 并发写入是否产生冲突；
- 工具后端是否允许当前并发量。


## 3. 多个结果什么时候交回模型

并行调用后，Runtime 有三种常见策略。

### 等待全部结果

```text
所有工具完成
→ 一次性构造完整 Context
→ 再调用模型
```

优点是模型看到的信息完整、模型调用次数少，适合需要综合判断的任务。

缺点是整个流程会等待最慢的工具。

### 每个结果返回后立即继续

某个结果一到就重新调用模型。

这可以更快推进部分任务，但模型调用次数更多，而且模型可能在信息不完整时过早得出结论。

### 关键结果到达后继续

先等待决定主路径的关键结果，低优先级调用继续执行。

这种方式适合长任务，但要求 Runtime 明确哪些结果已经到达、哪些仍在运行，并避免模型重复发起相同调用。

复杂度不值得时，优先选择等待全部结果。只有延迟确实成为问题，才升级成更细粒度的调度。


## 4. 部分失败不能抹掉已经成功的结果


Runtime 不应该因为一个服务超时，就把整个批次都表示成“什么都没有得到”。

应该把成功与失败分别保留：

模型需要知道证据缺口，才能判断：

- 现有信息是否足够回答；
- 是否值得重试；
- 是否请求用户稍后再试；
- 是否转人工处理。

但真正采取哪种恢复策略，由 Runtime 根据错误类型、预算和业务风险决定。

---

## 5. 重试只解决暂时性执行错误

不是所有失败都应该重试。

通常不重试：

```text
参数错误
业务规则拒绝
权限不足
资源不存在
用户没有确认
```

这些错误不会因为再次调用就自动消失。

可以有限重试：

```text
网络超时
临时限流
服务暂时不可用
可恢复的连接错误
```

重试需要同时限制：

- 最大次数；
- 退避等待时间；
- 单次超时；
- 总时间预算；
- 总调用成本。

模型可以在结果中看到“该错误可能暂时可恢复”，但不能自行无限重试。

---

## 6. 写操作最关键的是幂等和结果未知

查询工具重复执行通常只增加成本，写工具重复执行可能产生真实损失。

可靠处理通常需要：

```text
同一业务意图使用同一个幂等键
→ 重试时仍携带同一个幂等键
→ 工具后端识别重复请求
→ 返回第一次操作的已有结果
```

幂等键应该由 Runtime 根据业务意图生成和保存，不能让模型随意生成。

如果工具不支持幂等，还可以先查询操作状态，再决定是否补偿或人工处理。

> 写操作超时后最危险的不是失败，而是不知道是否已经成功。

---

## 7. Runtime 必须识别无效循环

Agent Loop 可能出现：

- 相同工具和相同参数被反复调用；（防重）
- 工具持续失败，模型仍然重复尝试；（重试次数）
- 连续多轮没有获得新事实；（任务没有取得进展）
- 模型在两个工具之间来回切换；（2个反复）
- 已经获得答案，却仍继续调用；（停止）
- 调用数量、Token 或时间不断增长。（预算控制）

Runtime 应检测：

```text
相同调用是否已经成功执行
本轮是否产生了新的有效信息
相同错误是否连续出现
任务 State 是否实际推进
```

并设置硬预算：

```text
最大模型调用次数
最大工具调用次数
单工具和总任务超时
Token 预算
费用预算
```

达到预算后，应保留已经得到的结果，并进入明确终态，而不是继续让模型尝试。


## 8 可靠性必须能通过 Trace 回放

当任务失败时，只看最终回答无法判断问题出在哪里。

一次工具任务至少要通过 `trace_id` 关联：

```text
模型看到了哪些 Context 和工具
模型生成了哪些 Tool Call
每次调用经过了什么校验
产生了哪些 execution_id
工具怎样返回、是否重试
最终使用了哪些 Tool Result
任务为什么进入当前终态
```

这样才能区分：

```text
没有调用必要工具
选择了错误工具
参数生成错误
Runtime 校验拒绝
工具后端失败
重复调用或循环
最终回答没有基于 Tool Result
```

Trace 服务于排错、回放和后续评测，但不应该把内部令牌、敏感参数和完整私有数据直接写入日志。日志同样需要脱敏和访问控制。
