## 1. 为什么模型需要工具

语言模型接收 Context，然后生成下一段输出。
模型需要的信息，要处理的信息存在数据库、业务服务或外部系统中，不在模型参数里。模型生成一句“已经退款”，也不会让真实订单发生变化。

所以任务一旦依赖**外部真实状态**或需要产生**真实副作用**，就需要工具。 简单来说就是读写操作。

工具可以封装数据库查询、HTTP API、本地函数、浏览器、文件系统、MCP Server 等确定性能力。

> Tool Calling 解决的核心问题，是把模型的语义判断连接到真实系统。

## 2. Tool Calling 不等于模型直接执行工具

通常情况下，模型不会自己连接数据库或者调用接口。

完整过程是：

```text
用户提出目标
→ Runtime 构造 Context 和可用工具
→ 模型生成结构化 Tool Call
→ Runtime 校验并执行工具
→ Tool Result 返回模型
→ 模型根据新信息继续判断
```

因此 Tool Calling 可以定义为：

> 模型根据当前 Context 生成结构化的调用意图，Runtime 校验并执行真实工具，再把执行结果放回 Context，让模型继续决策的闭环机制。

这里最重要的边界是：

```text
模型负责提出下一步行动
Runtime 负责决定是否真的执行
工具负责查询或改变真实世界
```

模型输出的是**候选行动**，不是命令。

## 3. 四个参与者分别负责什么

### 用户

用户提供最终目标，同时用户会关联权限等东西 给runtime提供权限信息。 runtime根据用户的权限 判断能否执行工具。

### 模型

模型负责需要**语义理解**的判断：

- 用户真正想做什么；
- 是否需要工具；
- 应该选择哪个工具；
- 从用户表达中提取哪些候选参数；
- 如何理解工具结果；
- 下一步继续调用工具还是生成回答。

模型不负责鉴权、事务、幂等和真实执行，因为这些工作需要确定性保证。

### Runtime

Runtime 是模型和真实工具之间的控制层，负责：

- 决定本轮向模型提供哪些工具；
- 解析模型生成的 Tool Call；
- 校验工具、参数、业务规则和权限；
- 注入用户身份、租户、令牌等可信参数；
- 执行工具并处理超时和异常；
- 保存任务状态和调用预算；
- 把结果转换成稳定的 Tool Result；
- 决定继续循环、请求澄清还是结束任务。

### 工具

工具是被 Runtime 调用的具体能力。


## 4. 三个边界

### Tool Call 不等于真实执行

Tool Call 是模型提出的**结构化候选调用**。只有 Runtime 校验通过并调用工具后，外部世界才可能发生变化。

### Tool Result 不等于执行成功

`role = tool` 只表示这条消息对应某次工具调用。结果可能是成功、空结果、业务失败、权限拒绝或系统异常。

### 工具执行成功不等于用户任务成功

可能还有下次tool call 或者缺少信息 或者还在思考
