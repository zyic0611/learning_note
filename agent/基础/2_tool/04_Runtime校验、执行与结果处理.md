## 1. 为什么 Tool Call 不能直接执行

模型生成的 Tool Call 可能**结构正确**，但仍然存在很多问题：

- 工具名称不存在；
- 参数缺失或类型错误；
- 模型猜测了用户没有提供的信息；
- 订单已经退款，不能重复执行；
- 当前用户无权操作该订单；
- 删除、转账等高风险行为没有经过确认；
- 相同调用已经执行过。
总结就是只能保证json结构 没办法保证 语义、业务、权限、幂等、风险等特性。
因此 Tool Call 必须被当作不可信的**候选输入**。

Runtime 的执行链可以概括为：

```text
解析 Tool Call
→ 查找工具
→ Schema 校验
→ 注入可信参数
→ 业务校验
→ 权限与风险校验
→ 必要时用户确认
→ 执行工具
→ 标准化 Tool Result
```

业务、权限和风险校验 是runtime的核心校验。
## 2. Runtime 先完成四层校验

### 第一层：协议与结构校验

检查：
格式是否完整、参数是否合法、工具名是否存在、必填字段是否缺失、枚举值是否符合、类型是否符合、范围是否符合、是否有未知字段。
这一层只证明调用能够被程序解析。

### 第二层：业务校验

检查当前业务状态是否允许操作：

业务规则依赖真实业务 State，不能只写进 Prompt 或 Schema。

### 第三层：权限与数据范围校验

检查：
- 当前用户身份
- 是否具有工具权限
- 是否有权操作该资源 可能是读操作 也可能是写操作。
- 用户是否符合该租户空间。
模型不能通过生成另一个 `user_id` 或 `tenant_id` 改变权限。

Runtime 应从**可信会话中注入**这些参数，而且工具后端仍要再次执行鉴权和租户隔离。
Agent Runtime 的检查不能代替数据服务自身的权限控制。

**核心** 后端服务的鉴权和数据隔离应作为兜底 。不能被runtime替代。

### 第四层：风险与副作用校验

读取类工具通常风险较低，写入和不可逆操作需要更强控制：

普通操作 ------- 基础鉴权后执行
可逆操作 -------  展示操作结果
高风险写 -------  确认关键参数
不可逆操作  -------   人工介入审批

所以不产生副作用的话 鉴权 
产生副作用  看可逆 就展示结果 可以给用户确认 不可逆/高风险 最好人工介入审批

## 3. 校验失败后不是直接拒绝

Runtime 要根据**错误性质**选择处理方式。

### 可以自动修复

只适合低风险且语义唯一的情况：
	简单的参数问题 比如去除空格、日期格式转换、大小写归一化、基础类型转换 安全的前提下
	但是这些都需要提前定义好规则 runtime不能乱做。

不能自动修复：
	帮用户修改参数

### 需要用户澄清

当关键业务参数缺失或存在多个合理解释时，应向用户一次询问最关键的信息。

### 直接拒绝

越权、违反业务规则或高风险且无法确认的请求，应由 Runtime 直接拒绝，不需要让模型反复修改参数尝试绕过。

## 4. Registry 和 Dispatcher 

Runtime 通常可以拆成两个关键组件：

```text
Tool Call
   ↓
Dispatcher ──查找──> Tool Registry
   ↓                    ↓
执行与异常处理        工具实现和元数据
   ↓
统一 Tool Result
```

### Tool Registry

Registry 保存：

```text
工具名称 → 真实可执行实现
工具 Schema
权限和风险元数据
超时与调用限制
```

比较核心的是 要注意 工具注册的时候就**写好权限、风险元数据、 超时和调用的限制。**
### Dispatcher

Dispatcher 接收已经通过校验的调用，负责：

- 从 Registry 找到真实实现；
- 注入可信运行时参数；
- 调用本地函数、RPC、HTTP API 或 MCP Server；
- 处理超时、取消和服务异常；
- 记录一次 `execution_id`； runtime一次执行就对应一次execution_id 执行id
- 把原始结果转换成统一 Tool Result。 适配层功能 统一结果协议

Dispatcher 负责单次执行，Agent Loop 决定执行后任务是否继续。

---

## 5. 高风险操作冻结参数后确认


正确过程是：

```text
生成候选参数
→ Runtime 校验
→ 冻结待执行参数
→ 向用户展示影响
→ 用户确认
→ 使用同一份冻结参数执行
```

确认是对具体操作的授权，不是对模型未来任意行动的授权。

冻结参数就是为了防止模型再生产新的参数

## 6. 原始工具结果做统一处理

第三方 API 或数据库可能返回：

无关信息、调试信息、敏感字段、每个模型厂商返回的格式不一样

Runtime 应在结果进入 Context 前做确定性处理：

- 权限和敏感信息过滤
- 选择本轮需要的信息
- 做分页、聚合等处理
- 标明结果状态

结构可以参考：
- status 执行状态
- data 需要的业务数据
- error 错误
- metadata 辅助元信息
- warnings： 结果可用 但需要注意的问题


这本质上也是一种 State 投影：真实全量工具结果由 Runtime 保存，模型只看到当前决策所需的最小视图。

---

## 7. 模型回答必须基于真实 Tool Result

工具执行后，模型负责把结果解释给用户，但不能脱离结果继续猜测。

Prompt 可以要求模型遵守，但 Runtime 仍应保留来源、校验引用，并避免把未验证的模型推断写回业务 State。

runtime作为信息来源 可以做校验

---


## 总结

由于tool call提出的只是候选行为 不一定合规。
所以需要runtime校验等等。
校验失败 根据不同的情况 做不同的处理 并非直接拒绝。
并且runtime是负责拿着候选行为去找真正工具执行的角色。
也负责对工具执行结果处理后交给runtime。
所以它持有原始工具执行结果 可以做溯源、再次校验。
