
## 1. 先判断：这个任务真的需要 Agent 吗

设计 Agent 的起点不是选框架，而是判断任务中的**不确定性来自哪里**。

- 路径和规则都确定：写普通程序。
- 只需要理解或生成语言：调用一次模型。
- 需要读取外部信息：增加工具。
- 下一步必须根据工具结果临时决定：才需要 Agent Loop。

因此，Agent 最有区分度的特征不是“使用了 LLM”，而是：

> 系统需要不断观察环境，并根据新的观察动态决定下一步。

```text
目标
 ↓
观察当前情况
 ↓
决定下一步行动
 ↓
执行并获得新结果
 ↓
目标未完成则继续
```

这就是 Agent 的核心。Prompt、Tool Calling、Memory、Planning 都是在增强这个闭环，而不是 Agent 本身。

## 2. 从简单方案逐级长成 Agent

不要一开始就设计完整 Agent。正确路线是从最低复杂度出发，遇到解决不了的问题再升级。

### L0：确定性代码

如果输入、规则和执行路径都明确，直接使用普通代码。

```text
输入 → if/else 或规则 → 执行 → 输出
```

例如根据订单状态码判断能否退款，不需要模型参与。

### L1：单次模型调用

当规则难以穷举，但任务可以一次完成时，引入模型处理开放语义。

```text
输入 → Model → 输出
```

适合分类、抽取、改写、总结。此时仍然不是典型 Agent，因为模型没有与环境形成行动闭环。

### L2：模型加工具

模型内部知识不够新、不够准，或者任务需要操作真实系统时，引入 Tool。

```text
用户目标 → Model 提出 Tool Call → 程序执行 Tool → Model 生成结果
```

这一步出现了重要边界：

> Model 只提出行动，Runtime 才决定是否执行。

因为模型是概率性的，不能让它直接掌握数据库连接、用户身份、权限和真实副作用。

如果一次工具调用就能完成任务，到这里停止，不需要循环。

### L3：受限 Agent Loop

当下一步取决于上一轮工具结果，预先无法确定完整路径时，才增加循环。

```text
Context
   ↓
Model 提出行动
   ↓
Runtime 校验并执行
   ↓
Observation 更新任务
   ↓
继续或终止
```

循环一出现，系统自然需要解决三个问题：

1. **当前做到哪里了？**  
   需要 State，由 Runtime 在模型之外保存。

2. **这一轮模型需要看到什么？**  
   Runtime 从 State、History、Memory 和外部资料中选择信息，组成 Context。

3. **什么时候停止？**  
   必须定义验收标准、最大步数、预算和失败条件，不能以“模型没再调用工具”作为完成依据。

所以 State、Context 和终止控制不是要提前背的组件，而是 Agent 进入循环后必然出现的工程问题。

### L4：Workflow 加局部 Agent

真实业务通常不是整条链路都不确定。

例如退款流程中的鉴权、规则检查、用户确认和退款执行都有固定顺序；只有意图理解、资料收集等局部节点需要模型判断。

```text
确定性 Workflow
├─ 权限检查
├─ Agent：理解意图、收集信息
├─ 业务规则校验
├─ 人工确认
└─ 执行与结果验证
```

因此生产系统通常不是“全自动 Agent”，而是：

> Workflow 控制主干，Agent 处理局部不确定性。

### L5：Multi-Agent

只有出现以下问题时，才考虑拆成多个 Agent：

- 单个 Context 太大，需要隔离信息；
- 不同角色需要完全不同的工具和权限；
- 子任务可以真正并行；
- 不同领域需要独立评测和维护。

Multi-Agent 的价值是**隔离和分工**，不是让多个模型自由讨论。没有这些需求，单 Agent 更简单、更可靠。

### 复杂度升级原则

```text
确定性代码
  → 单次模型
  → 模型 + 工具
  → 受限 Agent Loop
  → Workflow + 局部 Agent
  → Multi-Agent
```

> 只有当前一级无法以可接受的质量、成本和风险完成任务，才升级到下一级。

## 3. Runtime 为什么是 Agent 的核心

进入 L2 以后，就需要一个普通程序把模型和真实世界连接起来，这个程序就是 Runtime。

Runtime 的控制逻辑是确定性的，主要负责：

```text
保存 State
→ 组装 Context
→ 调用 Model
→ 校验 Model 提出的行动
→ 执行 Tool
→ 记录 Observation
→ 判断继续还是终止
```

其中 Model 和外部环境都可能产生不确定结果，但 Runtime 必须用确定规则约束它们。

最重要的分工只有一句：

> 不确定的语义决策交给 Model，确定的状态、权限、执行和终止交给 Runtime。

这条边界比具体使用 ReAct、LangGraph 或某个 Agent 框架更重要。

## 4. 用退款任务推导一次架构

需求：“查询订单状态，如果还没发货就帮我退款。”

不要直接套 Agent 框架，先逐步判断：

1. 需要理解自然语言订单信息，所以需要 Model。
2. 需要查询实时订单，所以增加查询 Tool。
3. 查询结果决定下一步是解释、补充信息还是退款，所以需要有限循环。
4. 退款涉及权限、业务规则和副作用，必须放进确定性 Workflow。
5. 退款前需要用户确认，执行后需要验证结果。
6. 任务不需要上下文或权限隔离，因此不需要 Multi-Agent。

最终架构自然变成：

```text
用户请求
→ Model 提取订单与意图
→ Runtime 校验参数并查询订单
→ Model 根据查询结果提出下一步
→ 业务代码检查退款规则和权限
→ 用户确认
→ Runtime 使用幂等键执行退款
→ 查询退款结果并判断任务完成
```

这里不是先设计组件再拼装，而是每个组件都由一个真实问题推导出来。

## 5. 设计 Agent 时只问五个问题

1. **路径是否可以提前确定？**  
   可以就用代码或 Workflow。

2. **是否需要模型处理开放语义？**  
   不需要就不要引入模型。

3. **是否需要读取或改变外部世界？**  
   需要才增加 Tool。

4. **下一步是否依赖刚得到的 Observation？**  
   依赖才增加 Agent Loop 和 State。

5. **是否真的需要上下文、能力或权限隔离？**  
   需要才升级为 Multi-Agent。

这五个问题基本决定了 Agent 的架构复杂度。

---

## 6. 最后记住三句话

1. Agent 的核心是“观察—决策—行动”的动态闭环。
2. Model 负责不确定判断，Runtime 负责确定性控制。
3. 设计时从最低复杂度开始，只为真实问题增加结构。
