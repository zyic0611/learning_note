## 1. 复杂模式不是默认答案

更多规划、循环和模型调用，会同时增加成本、延迟、状态以及失败入口。

选择架构时真正要问的是：

> 当前任务最少需要哪种决策能力，才能以可接受的质量、成本和风险完成？

---

## 2. 从简单方案逐级升级

### 直接回答

一次模型调用即可完成，不依赖实时状态，也没有真实副作用。

### 单次工具调用

任务只缺一个外部事实，或者只需执行一个明确动作：

```text
模型生成 Tool Call
→ Runtime 校验并执行
→ 模型解释结果
```

### ReAct

下一步取决于刚获得的 Observation，无法提前确定完整路径。

### Plan-and-Execute

任务较长，存在需要持续维护的步骤、依赖和全局目标。

升级关系是：

```text
直接回答
→ 单次工具调用
→ 局部 ReAct
→ 全局 Plan-and-Execute
```

只有前一级无法可靠完成任务时，才继续升级。

---

## 3. Workflow 和 Verifier 是横向能力

Workflow 不属于上面的升级链。它负责固化确定的业务路径、权限和审批关卡。
它负责节点的编排 属于orchestration层面。
从编排的角度 react和plan-execute也是编排层面 把整体作为一个节点 就是节点层面
workflow也可以是一个节点层面。 所以取决于任务大小吧或者任务定义。

Verifier 也不是独立推理模式。它负责检查关键产物是否满足完成条件。

它们可以与不同模式组合：

```text
固定 Workflow
├─ 权限检查
├─ 动态计划节点
│  └─ 局部 ReAct
├─ Verifier
└─ 人工审批
```

确定部分交给 Workflow，路径不确定的局部才交给模型，高风险或可验证结果增加 Verifier。

---

## 4. 模式组合后谁控制全局

复杂模式可以组合，但全局状态只能由一个 **Controller** 维护：

```text
Planner：生成候选计划
Controller：维护计划状态并选择下一步骤
Executor：执行当前步骤
ReAct：解决某个步骤内部的路径不确定
Verifier：验证关键结果
```

局部 ReAct 完成后必须把结果交回 Controller，不能自行修改全局目标或宣布整个任务完成。

---

## 5. 用几个问题完成选择

```text
一次模型调用能完成吗？
→ 直接回答

只需要一个确定性工具调用吗？
→ 单次工具调用

下一步是否依赖新的 Observation？
→ 局部 ReAct

是否需要长期维护步骤、依赖和全局目标？
→ Plan-and-Execute
```

最后再判断：

```text
业务路径是否固定？
→ 用 Workflow 固化确定部分

关键结果是否高风险或可以明确检查？
→ 增加 Verifier 或人工审批
```

如果升级后没有提高任务成功率，也没有降低风险，就应该退回更简单的方案。
