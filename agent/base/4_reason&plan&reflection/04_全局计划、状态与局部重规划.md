## 1. 为什么长任务不能只靠逐步反应

ReAct 擅长根据最新 Observation 解决当前问题，但没有天然的全局结构。

任务较长时，Agent 容易忘记最终目标、重复工作、跳过依赖，或者在某一步失败后不知道哪些后续步骤受到影响。

所以长任务需要：

```text
先形成全局计划
→ 逐步执行
→ 记录每一步的实际结果
→ 环境变化时只修改受影响部分
```

这就是 Plan-and-Execute 要解决的问题。

---

## 2. 计划也是状态

计划不能只保存“准备做什么”，还要保存“实际发生了什么”：

```text
步骤定义：目标、输入、输出、依赖、完成条件
执行状态：待执行、执行中、完成或阻塞
实际结果：工具结果、产物或失败原因
```

状态名称可以按系统需要设计。真正重要的是：

> 计划必须区分预期路径与实际执行结果。

否则任务中断后无法恢复，后续步骤也无法判断前置条件是否真的满足。

---

## 3. 三个逻辑职责

### Planner

根据目标生成候选步骤和依赖，不执行真实操作。

### Executor

执行当前已经批准的步骤，并返回结构化结果。它不能擅自修改总目标或跳过依赖。

### Controller

维护计划状态，根据执行结果决定：

```text
更新当前步骤
→ 选择下一个就绪步骤
→ 继续、重规划或结束
```

三者是逻辑职责，不代表必须使用三个模型或部署三个服务。通常 Planner 可能由模型承担，Controller 和状态维护由 Runtime 实现。

---

## 4. 什么时候需要局部重规划

只有现实变化使原计划失效时，才需要重规划，例如：

- 执行结果推翻了原计划假设；
- 某一步失败且原路径无法继续；
- 用户修改了目标或约束；
- 已完成结果使后续步骤不再需要。

重规划不等于推倒重来。

假设原计划是：

```text
A 读取数据
→ B 转换数据
→ C 写入目标库
→ D 校验结果
```

如果 C 因权限不足失败，A 和 B 的结果仍可能有效。此时只需增加权限处理步骤，再重新执行 C 和 D。

> 局部重规划保留仍然有效的事实和结果，只修改受影响的未完成步骤及依赖。

## 5. 全局计划与 ReAct 如何组合

两者解决的问题不同：

```text
Plan-and-Execute：维护全局目标、步骤和依赖
ReAct：在局部路径未知时，根据 Observation 选择下一步
```

例如：

```text
全局计划
├─ 确认故障范围
├─ 定位根因
│  └─ 使用 ReAct 动态查询监控和日志
├─ 生成修复方案
└─ 验证结果
```

局部 ReAct 完成后，要把结构化结果交回 Controller，由 Controller 更新全局计划。

计划只能让过程可控，不能证明结果正确。步骤是否真正完成，还需要验证机制。
