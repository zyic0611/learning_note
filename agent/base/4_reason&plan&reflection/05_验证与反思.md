## 1. 生成结果不等于完成任务

模型生成了答案，或者工具返回执行成功，都不能单独证明用户目标已经完成。

关键结果之后需要独立判断：

> 当前产物是否满足目标、约束和完成条件？

---

## 2. 先定义完成条件，再验证

验证闭环应该是：

```text
定义完成条件
→ 生成或执行
→ 按条件验证
→ 根据失败证据修正
```

没有明确完成条件，Reflection反思节点 往往只是让模型重新阅读自己的输出，不能证明它发现了真实错误。

---

## 3. 确定性验证优先

能用程序、规则或权威状态验证的内容，不应只询问模型“是否正确”：

```text
JSON → Schema Validator
代码 → 编译、静态检查、测试
SQL → Parser、Schema、只读规则、试运行
外部操作 → Tool Result 和业务状态回查
```

模型评审适合表达是否清楚、论证是否遗漏等难以完全规则化的问题，但不能替代硬性校验。

---

## 4. 验证与修正怎样分工

完整闭环有三个逻辑职责：

1. 判断哪些错误/没完成（验证）
2. 定位原因（反思）
3. 根据原因修正


这三个职责不一定由三个模型承担。确定性检查可以同时完成验证和错误定位，模型只处理需要语义判断的修正。

---

## 5. 为什么修正必须有限

模型可能在修复一个问题时引入另一个问题，所以不能无限重新生成。

Runtime 至少需要限制：

- 最大修正次数；
- 总时间和 Token 预算；
- 同一错误是否重复出现；
- 高风险结果是否需要人工确认。

每次修正后必须重新验证。多次失败后应保留证据，并选择请求补充信息、更换方案、升级人工或明确失败。

> Reflection 的价值不是让模型“再想一次”，而是根据可验证的失败证据进行有限修正。
