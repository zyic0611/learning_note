## 1. 为什么无法总是提前写出完整计划

有些任务的下一步取决于刚获得的外部结果。

例如排查接口延迟：

```text
错误率升高
→ 查询异常日志

错误率正常但下游耗时升高
→ 查询下游依赖
```

在看到监控结果前，无法判断哪条路径正确。此时强行生成完整计划，只会写入大量未经验证的假设。

更合适的方式是：

> 每获得一次新的 Observation，再决定下一步行动。

---

## 2. ReAct 是一个决策循环

ReAct 的核心不是“模型会调用工具”，而是决策与观察交替进行：

```text
读取目标和当前状态
→ 模型选择下一步行动
→ Runtime 校验并执行
→ 获得 Observation
→ 更新状态
→ 继续行动或结束
```

新的 Observation 必须能够改变后续判断。

如果无论工具返回什么，系统都走同一条路径，就不需要 ReAct，固定 Workflow 更直接。

---

## 3. 每轮需要保留什么

每轮决策至少需要看到：

```text
当前目标
已确认事实
尚未解决的问题
已完成的关键行动
剩余预算
```

这些信息分别用于防止目标漂移、重复查询和无限探索。

完整工具历史不必一直原样放入 Context。较早结果可以压缩成结构化状态，但精确 ID、错误码和关键证据不能丢失。

---

## 4. 怎样决定继续还是停止

一次新行动至少应该带来一种进展：

- 获得完成目标所需的新事实；
- 排除一个候选假设；
- 缩小尚未解决的问题。

如果连续行动没有带来这些变化，就已经进入无效循环。

ReAct 通常在以下情况结束：

- 目标已经完成；
- 信息不足，需要用户补充；
- 权限、资源或预算不允许继续；
- 继续行动也无法有效降低不确定性。

模型停止生成 Tool Call，不代表任务必然成功。Runtime 仍需根据目标和当前状态判断真实终态。

---

## 5. 什么时候值得使用

ReAct 适合路径依赖外部结果的探索、诊断和检索任务。

它不适合替代确定性的业务 Workflow，也不适合独自维护很长的依赖链。Runtime 仍要限制模型轮数、工具次数、总时间和 Token 预算。

对于长任务，更可靠的方式是维护全局计划，只在局部路径不确定的步骤中使用 ReAct。
