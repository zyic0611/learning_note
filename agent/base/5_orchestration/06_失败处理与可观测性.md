## 1. 为什么失败后不能统一重试

网络超时可能重试后恢复，权限不足、资源不存在和业务条件不满足则不会。

如果所有失败都再试一次，只会增加成本、掩盖原因，还可能重复产生副作用。

> 失败处理的第一步是识别失败性质，再选择匹配的控制策略。

---

## 2. 六种控制策略

```text
Retry：暂态错误，有限重试同一动作
Fallback：主方案不可用，切换已定义的备用方案
Skip：非必要步骤失败，记录后继续
Replan：原计划前提失效，修改后续步骤
Escalate：自动处理风险过高或无法继续，转人工
Fail：无法安全完成，终止任务
```

典型判断是：

```text
网络抖动 → Retry
权限不足 → Escalate 或 Fail
辅助数据缺失 → Skip 或 Fallback
执行结果推翻计划假设 → Replan
```

这些策略不能互相替代。

---

## 3. Retry 和 Fallback 的边界

Retry 必须明确可重试错误、最大次数、超时、退避方式和副作用幂等。

还要统一整条链路的重试预算。SDK、工具节点和 Workflow 如果各自无感重试三次，最坏可能放大成 27 次调用。

Fallback 必须是提前定义的备用路径，并明确损失了什么：

```text
实时数据不可用
→ 使用带时间标记的缓存
→ 告知结果可能不是最新
```

如果降级结果已经不能满足用户核心目标，就应该失败，而不是为了返回内容强行降级。

---

## 4. 为什么需要可观测性

端到端失败时，只看到“Agent 回答错误”无法定位问题。错误可能来自路由、节点输入、模型输出、工具调用、State 更新、Join 或恢复。

因此需要一个 `trace_id` 贯穿：

```text
Workflow
→ 节点与子流程
→ 模型调用
→ 工具调用
→ Checkpoint 和最终终态
```

关键事件至少要记录身份、状态变化、尝试次数、耗时、错误类型和采用的处理策略。输入输出保存安全摘要或引用，不能为了调试泄露敏感内容。

---

## 5. 指标应该帮助发现什么

先观察少量能指导改进的指标：

- 端到端任务完成率；
- 各节点和分支失败率；
- Retry、Fallback 和人工介入比例；
- 恢复成功率与重复副作用；
- 延迟以及模型、工具成本。

完成率高但持续依赖重试或人工介入，说明系统虽然能完成任务，却没有稳定、低成本地完成。

Orchestration 不会让模型更聪明，但它能限制错误影响范围，并让失败可以被发现、解释和恢复。
