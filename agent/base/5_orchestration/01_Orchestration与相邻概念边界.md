## 1. 为什么有模型和工具还不够

简单 Agent 可以这样运行：

```text
用户请求
→ 模型选择工具
→ Runtime 执行
→ 模型回答
```

任务变长后，还要处理步骤依赖、状态保存、失败恢复、人工审批和任务终止。

这些不是模型是否聪明的问题，而是流程控制问题。

> Orchestration 负责**把模型、工具、规则和人工节点组织成可控制、可恢复的执行流程**。

---

## 2. 为什么不能只写进 Prompt

Prompt 可以告诉模型“付款前确认”或“最多重试三次”，但不能提供硬保证。

模型可能遗漏规则，Context 可能被压缩，服务重启后模型也不知道之前执行到了哪里。

所以 Runtime 必须保存并强制执行：

```text
当前节点和任务状态
权限与审批状态
重试次数和预算
超时与终止条件
副作用操作的幂等标识
```

Prompt 负责指导模型行为，不能代替状态机、权限校验和持久化。

---

## 3. 与推理、规划和执行的边界

```text
推理：根据当前信息形成判断
规划：生成候选步骤和依赖
执行：完成当前动作
编排：控制整个流程怎样推进
```


## 4. Runtime、Orchestration 与 Workflow

三者的关系是：

```text
Runtime：Agent 的整体运行环境
Orchestration：Runtime 中的流程控制机制
Workflow：流程控制的一种结构化表达
```

固定 Workflow 适合稳定业务路径和强制安全关卡。Agent Loop 适合局部路径依赖 Observation 的任务。

二者可以组合 agent loop可以是workflow的一个节点。
## 5. 它能保证什么

Orchestration 能保证流程按规则推进、状态可追踪、失败进入规定路径、中断后可以恢复。

它不能保证模型理解正确、计划合理、外部数据真实或业务规则本身没有错误。

稳定 Agent 需要模型负责语义判断，工具连接真实系统，Verifier 检查关键结果，Orchestration 控制执行过程。
