## 1. Router 解决什么问题

同一个入口可能对应不同能力：

```text
查询订单 → 查询流程
申请退款 → 退款流程
投诉商家 → 客服流程
```

> Router 在有限、已注册的候选路径中选择下一条路径。

它只回答“去哪里”，不负责执行具体业务。

---

## 2. Router、Planner 与 Subflow

```text
Planner：复杂目标需要哪些步骤
Router：当前目标应该进入哪条已知路径
Subflow：这条路径内部怎样执行
```

如果业务步骤固定，Workflow 可以直接路由到对应 Subflow，不需要 Planner。

---

## 3. 确定性规则优先

State 中已有明确字段时，应直接使用规则：

```text
amount > 10000 → 人工审批
permission = denied → 拒绝执行
```

只有路径选择依赖自然语言语义时，才需要模型路由。例如把“钱还没回来”识别为退款进度查询。

模型也只能从 Runtime 提供的白名单中选择。结果置信不足或语义有歧义时，应请求澄清；超出能力或风险过高时，应转人工或停止。

错误做法是把未知请求强行分配给最相近路径。

---

## 4. 分支只保留会改变控制流的结果

一个工具结果不只有成功和失败。例如订单查询可能是：

```text
found → 继续处理
not_found → 检查输入或告知用户
permission_denied → 停止
temporarily_unavailable → 重试或降级
```

无需枚举所有技术异常。只要一种结果会改变后续路径，就应有明确 Edge；不会改变控制流的细节留在节点结果中。

---

## 5. 什么时候值得抽取 Subflow

一组节点满足以下条件时，可以封装为 Subflow：

- 有独立输入和输出；
- 有明确终态和失败语义；
- 会被多个流程复用，或者内部复杂度需要隔离。

父流程只依赖 Subflow 契约：

```text
输入
输出
允许的终态
权限和预算
失败如何返回
```

不要只为了减少主流程节点数量而抽取 Subflow。

路由进入某条路径，不代表权限和业务条件已经满足。目标 Subflow 内仍要执行参数、权限、审批和结果验证。
