## 1. Workflow 最少需要什么

Workflow 要回答：

```text
当前执行什么
→ 结果保存在哪里
→ 接下来进入哪里
```

因此最小结构是：

```text
Node：执行一个明确职责
Edge：定义节点之间如何流转
State：保存流程推进需要的任务事实
Entry / End：定义入口和终态
```

---

## 2. Node 为什么要职责清楚

节点可以由模型、工具、规则或人工执行。

一个节点最好只产生一种可判断的结果。例如不要把“生成 SQL、校验、执行和解释”放进同一节点，否则无法定位失败，也无法只重试其中一步。

更合理的是：

```text
生成 SQL
→ 校验 SQL
→ 执行 SQL
→ 解释结果
```

拆分标准不是越细越好，而是节点能否独立执行、记录结果和处理失败。

能用确定性规则完成的权限、Schema 和金额检查，不应交给模型判断。

---

## 3. Edge 定义合法流转

Edge 不只是连接线，它说明节点在什么结果下进入哪个已注册节点：

```text
permission.status = passed
→ 执行工具

permission.status = denied
→ 结束或转人工
```

模型可以生成分类结果，但不能随意创造节点名称或绕过未注册路径。

---

## 4. State 是节点之间的数据契约

State 保存当前任务的权威执行事实，例如：

```text
workflow_id
当前节点和节点状态
订单 ID 等业务字段
审批状态
工具结果或结果引用
错误与最终结果
```

每个节点应明确读取哪些字段、写入哪些字段，以及可能产生什么结果。Runtime 才能校验节点输入，而不是让节点通过自然语言猜测彼此输出。

精确状态应使用结构化字段。自然语言摘要可以帮助模型理解，但不能代替权威状态。

---

## 5. State、Context 与 Memory

```text
State：当前任务的权威执行事实
Memory：跨任务复用的信息
Context：本轮模型实际看到的信息
```

Runtime 从 State 中选择当前决策必需的字段放入 Context，不需要把全部内部状态交给模型。

任务结束后 State 通常归档或清理，其中少量具有长期价值的信息经过判断后才能进入 Memory。

---

## 6. Entry 和 End 必须明确

Workflow 必须有入口和有限终态，例如：

```text
succeeded
failed
cancelled
waiting
escalated
```

`waiting` 是可恢复的暂停，不等于失败。

节点没有报错，也不代表任务成功。只有最终目标和必要完成条件满足后，Workflow 才能进入成功终态。
