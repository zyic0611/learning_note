## 1. 为什么长任务需要 Checkpoint

长任务可能等待工具、用户或审批，也可能遇到服务重启和外部系统暂时不可用。

如果进度只存在内存中，中断后只能从头执行。之前完成的工作会被重复，已经发生的副作用甚至可能再次发生。

所以需要在节点完成、进入等待以及关键副作用前后保存 Checkpoint。

> Checkpoint 的目标不是保存所有运行细节，而是让系统知道哪些结果仍然有效，以及应该从哪里安全继续。

---

## 2. Checkpoint 需要保存什么

最少需要：

```text
任务与 Workflow 版本
关键 State
节点执行状态和有效结果
恢复位置
尝试次数
正在等待的事件
```

普通 State 描述当前任务事实；Checkpoint 是能够恢复这些事实和执行位置的持久化记录。

---

## 3. 恢复不是直接重跑

Runtime 发出退款请求后、收到响应前崩溃，外部系统可能已经退款，但本地节点仍显示执行中。

恢复时不能直接再执行一次，而要先核对：

```text
Checkpoint 记录了什么
外部系统当前是什么状态
上一次动作能否安全重试
输入、权限和审批是否仍然有效
```

恢复的目标不是回到某一行代码，而是让 Workflow State 与真实业务状态重新一致。

---

## 4. 副作用为什么需要幂等

查询和纯计算通常可以重跑，付款、退款、发邮件和创建资源则可能造成重复业务结果。

一次业务动作应使用稳定的幂等标识，例如：

```text
workflow_id + node_id + action_version
```

恢复和重试继续使用同一个标识，并结合外部状态回查。

分布式系统很难仅靠一次网络调用保证“恰好执行一次”。更现实的目标是：即使请求被重复投递，也只产生一次业务结果。

---

## 5. Human-in-the-loop 也是暂停与恢复

人工确认的完整过程是：

```text
持久化待处理动作和当前状态
→ Workflow 进入 waiting
→ 用户或审批人提交决定
→ 校验身份、内容和有效期
→ 重新检查外部状态
→ 恢复或终止
```

等待期间环境可能变化，所以人工批准的是某个具体动作版本。金额、对象或关键参数变化后，需要重新确认。

---

## 6. 取消不等于删除状态

取消后，尚未开始的节点可以停止调度，但已经发生的外部副作用不会因为修改 Workflow 状态而自动回滚。

系统仍要记录：

- 哪些动作已经发生；
- 正在运行的动作能否撤销；
- 是否需要执行明确的补偿动作；
- 最终应向用户报告什么。

Checkpoint 解决“从哪里继续”，不能决定失败后应该重试、降级还是终止。
