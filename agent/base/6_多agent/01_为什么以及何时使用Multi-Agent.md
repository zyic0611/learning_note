## 1. 为什么会需要多个 Agent

单个 Agent 也能调用多个工具、执行多步 Workflow。任务变复杂时，首先应该增强单 Agent，而不是直接增加 Agent。

真正的问题出现在多个职责被塞进同一个执行者后：

- 不同领域需要不同知识和判断方式；
- 无关 Context 相互干扰；
- 高低风险工具共享同一权限边界；
- 独立子任务无法清楚分工和并行。

Multi-Agent 的思路是：

```text
总目标
→ 拆成边界明确的子任务
→ 交给拥有对应 Context、能力和权限的 Specialist
→ 由控制层验证并汇总结果
```

> 它的核心价值是职责、Context 和权限隔离，不是让多个模型自由讨论。

## 2. 先用最低复杂度的方案

系统应沿复杂度阶梯逐级升级：

```text
单次模型调用
→ 单 Agent + Tool
→ Workflow + 专用节点或 Subflow
→ Multi-Agent
```

工具太多，可以按节点动态暴露工具；流程太长，可以拆成 Subflow。它们都不必引入新的 Agent 身份。

只有一个执行单元确实需要独立地理解局部目标、根据局部信息做判断，并且需要自己的 Prompt、Context 或权限边界时，才适合成为 Specialist Agent。

## 3. 什么时候值得拆分

### 能力边界不同

例如代码分析、安全审查和发布执行依赖不同知识、工具和判断标准。拆分后，每个 Agent 可以专注于稳定职责。

### 权限必须隔离

代码分析 Agent 只需读仓库，不应自动获得生产发布权限。独立 Agent 能让 Runtime 按职责授予最小权限。

### Context 应该隔离

代码细节、业务规则和发布信息都放进同一个 Context，不仅增加 Token，也会让无关信息影响判断。拆分后，每个 Agent 只接收完成子任务所需的信息。

### 子任务能够独立完成

输入、输出和完成条件清楚的子任务可以并行执行。若子任务边界模糊、频繁依赖彼此的中间结论，拆分只会增加 Handoff。

## 4. Agent、Tool 与 Subflow 的边界

- **Tool**：封装一个确定性动作，不理解完整目标，也不自主决定下一步。
- **Subflow**：封装一段主要由 Workflow 定义的可复用流程。
- **Specialist Agent**：在明确领域内进行语义判断、选择工具，并按契约返回结果。

是否需要 Agent，关键不是模型调用次数，而是是否形成了独立职责边界。一个 Agent 可以调用多个模型；多个模型调用也不等于 Multi-Agent。

## 5. 一个受控的结构

以代码发布为例：

```text
Orchestrator
├─ 代码分析 Agent：识别变更影响
├─ 测试 Agent：验证关键行为
├─ 安全 Agent：检查安全风险
└─ 发布 Agent：审批通过后执行发布
```

每个 Specialist 只接收必要子任务和 Context，只拥有必要工具，并返回结构化结果与证据。

Multi-Agent 只解决分工问题，不自动保证协作正确。接下来还需要回答：谁拆分任务、如何选择 Agent，以及谁维护全局目标。
