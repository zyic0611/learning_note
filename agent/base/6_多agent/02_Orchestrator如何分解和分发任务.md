## 1. 为什么需要一个控制者

如果每个 Agent 都能修改总目标、继续拆分任务并相互调用，局部决策很快会失去全局约束：

```text
重复执行
循环委派
权限和预算扩散
局部目标取代总目标
无人判断何时结束
```

默认应使用中央 Orchestrator：

```text
接收总目标
→ 确认子任务和依赖
→ 选择 Specialist
→ 分发并跟踪执行
→ 验证、汇总并判断终态
```

Orchestrator 可以调用模型做规划和路由判断，但 State、权限、预算与调度必须由 Runtime 强制控制。

点对点协作或多层 Orchestrator 只有在中央控制成为真实瓶颈时才值得引入，否则只会扩大协调难度。

## 2. Orchestrator 与 Specialist 的边界

Orchestrator 维护全局：

- 总目标、约束和任务依赖；
- 可用 Agent、权限与预算；
- 子任务状态和结果有效性；
- 失败、冲突与最终完成条件。

Specialist 只负责局部：

- 在自己的能力边界内完成子任务；
- 使用本次授权的工具；
- 按契约返回结果、证据或失败原因。

Specialist 不能擅自改变总目标，也不能因为局部任务完成就宣布整个任务成功。

## 3. 任务怎样产生

任务拆分属于 Planning，不是 Multi-Agent 特有机制。

固定流程直接由 Workflow 定义，例如并行执行质量、安全和测试审查。路径不固定时，Planner 可以生成候选任务，但 Runtime 仍要检查：

- 子目标是否必要且不重复；
- 输入、输出和完成条件是否明确；
- 依赖能否执行；
- 所需能力、权限和预算是否合法。

不能把模糊总目标原样广播给多个 Agent，再期待它们自行协商出可靠分工。

## 4. 怎样选择 Specialist

Agent 必须先注册能力契约，说明它能处理什么、需要什么输入、返回什么结果，以及工具和权限边界。

路由遵循两个原则：

1. 能用确定性规则判断时，直接按规则选择；
2. 需要语义判断时，模型只能从符合条件的 Agent 白名单中选择。

模型可以选择已注册能力，不能临时创造一个 Runtime 无法验证的 Agent。

## 5. 并行与委派边界

子任务只有在输入已准备、互不依赖、不会冲突写入同一资源且结果可独立验证时，才适合并行。代码质量和安全审查可以并行，发布则必须等待前置结果。

默认不允许 Specialist 任意调用其他 Agent。它需要协作时，应向 Orchestrator 返回请求，由 Orchestrator 判断是否创建新任务。

确实需要嵌套委派时，Runtime 必须限制 Agent 白名单、委派深度、重复任务、全局超时和总预算。这样才能防止两个 Agent 相互转交同一个目标。

## 6. 调度结果要进入全局 State

协作进度不能只存在于聊天记录。Runtime 至少要知道：

```text
子任务是谁、依赖什么
由谁执行、当前是什么状态
使用哪个输入版本
结果在哪里、是否通过验证
```

这样重启、重试或局部失败后，Orchestrator 才能判断哪些结果仍有效。

任务分发之后，下一个关键问题是 Handoff：怎样只把完成局部任务所需的信息交给 Specialist。
