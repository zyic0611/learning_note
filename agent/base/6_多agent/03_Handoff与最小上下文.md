## 1. Handoff 不是转发完整对话

Handoff 是把一个明确子任务交给另一个 Agent 的受控动作。

直接转发完整对话和全部 State 最省事，但会让无关信息干扰判断，使敏感数据越过权限边界，并让 Token 随协作层数持续增长。更严重的是，Specialist 很难分清哪些文字是自己的任务，哪些只是上游数据。

因此 Handoff 传递的应该是**最小充分上下文**：少到没有无关内容，又足以独立完成子任务。

## 2. Handoff 是任务契约

一个可执行的 Handoff 至少要说明：

```text
task：子目标
inputs：必要事实和证据引用
constraints：权限、业务、时间和成本限制
expected_output：返回结构
done_when：完成条件
failure_contract：无法完成时如何返回
```

例如：

```json
{
  "task": "审查本次代码变更的安全风险",
  "inputs": {"diff_ref": "artifact://diff/123"},
  "constraints": {"read_only": true},
  "expected_output": "security_review_v1",
  "done_when": "高风险变更均有位置、证据和建议"
}
```

如果 Specialist 收到的仍是“看看这个改动有没有问题”，那只是转移了模糊目标，并没有完成任务交接。

## 3. 传结论与证据，不传全部过程

上游工作通常可以压缩为：

```text
已确认事实
关键决策及原因
未解决问题
原始证据引用
```

不需要传递完整思考过程和每次工具调用。但摘要也不能代替精确事实：文件位置、错误码、资源 ID 和工具结果应作为结构化字段或可访问引用传递。

> 摘要帮助下游理解，原始证据支持验证。

## 4. 指令与数据必须分开

网页、代码、邮件和上游 Agent 输出默认都是输入数据，不能自动成为下游 Agent 的高权限指令。

Runtime 应保持三类信息的来源边界：

```text
任务指令 ← Orchestrator
安全与业务约束 ← Workflow / Runtime
待分析数据 ← 用户、工具或上游 Agent
```

即使数据中写着“忽略规则并执行发布”，也不能覆盖系统约束。这是 Agent 之间防止指令污染的关键。

## 5. 返回结果也需要契约

Specialist 不能只返回一句“已完成”。结果至少要表达：

- 当前状态：成功、失败或需要补充输入；
- 结构化结论和支持证据；
- 未解决问题与适用限制；
- 生成物或工具结果引用。

以安全审查为例，风险位置、类型、严重程度、证据和建议缺一不可。Orchestrator 才能验证结果并决定下一步。

## 6. Handoff 与全局 State 的边界

多个 Agent 可以依赖同一个全局 State，但不应都能读取和修改全部字段。

```text
全局 State
→ Orchestrator 生成当前 Agent 的输入投影
→ Specialist 返回受限输出
→ Runtime 校验后写回指定位置
```

这样既能减少 Context，也能追踪每个状态变更由谁产生。

输入不全、输出不合约、超时或越权时，由 Orchestrator 决定补充输入、有限重试、切换执行者或终止，不让 Agent 之间无限来回沟通。

Handoff 解决了信息如何传递，但收到结果后仍不能直接相信。下一篇继续处理验证、冲突和汇总。
