## 1. 子 Agent 输出只是候选结果

Specialist 仍可能格式错误、遗漏证据、使用过期信息或超出职责范围。多个 Agent 还可能给出互相矛盾的结论。

因此协作结果要经过：

```text
子 Agent 输出
→ 契约校验
→ 关键事实验证
→ 冲突处理
→ 围绕总目标汇总
```

未经验证的输出不能直接写成全局事实。

## 2. 先验证契约，再验证事实

第一层是确定性校验：状态和必填字段是否合法、类型是否符合 Schema、Artifact 是否可访问。格式不合约时，应返回明确错误让原 Agent 有限修正，而不是由汇总层猜测自然语言。

第二层验证结论依据。能用确定性方法检查时，优先使用权威来源：

```text
代码行为 → 编译、测试、静态检查
数据事实 → 权威接口或数据库
业务状态 → 状态查询工具
结构格式 → Schema Validator
```

例如“没有高风险漏洞”必须说明检查范围、依据和未覆盖部分。模型评审可以判断软性质量，但不能替代权威事实。

## 3. 冲突不能简单投票

多数 Agent 给出同一答案，不代表答案正确。它们可能依赖同一个错误来源、拥有相同模型盲点，或者观察的是不同时间和范围。

处理冲突时先问：

1. 是否在讨论同一对象和同一问题；
2. 数据范围和时间是否一致；
3. 哪个来源更权威，证据能否复现；
4. 哪个 Agent 对该问题负有明确职责。

只有候选相互独立、信息范围相同、判断标准一致时，投票才有意义。

## 4. 冲突怎样收敛

优先级从低成本到高成本：

```text
按权威来源裁决
→ 补充证据或重新调用确定性工具
→ 保留分歧及各自依据
→ 高风险问题转人工
```

证据不足时，正确结果不是强行选边，而是明确说明当前无法判断。汇总文本不能通过润色隐藏分歧。

## 5. 汇总围绕总目标

汇总不是把多份回答拼接起来，而是重新回答：

- 哪些子目标已经完成；
- 关键结论及证据是什么；
- 有哪些限制、风险和未解决问题；
- 总目标的完成条件是否满足。

重复结论应合并，冲突应显式保留，汇总者不能补充无证据的新结论。

Orchestrator 负责判断流程终态：继续执行、降级、转人工、失败或完成。可以让专门的汇总 Agent 负责表达，但它不能绕过 Orchestrator 宣布成功。

## 6. 一个代码审查案例

```text
质量 Agent：发现重复查询
安全 Agent：发现权限校验缺失
测试 Agent：关键回归用例通过
```

“测试通过”和“存在安全风险”并不冲突，因为它们检查的是不同维度。Orchestrator 需要确认测试是否覆盖权限场景，并根据发布规则决定阻止发布还是转人工审批。

不能用“三个 Agent 中两个认为没问题”做结论。验证解决了结果可信度，但 Multi-Agent 还会扩大权限、故障和成本风险，最后一篇继续处理这些系统边界。
