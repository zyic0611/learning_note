## 1. 为什么 Agent 需要 Memory

语言模型的一次调用只会看到 Runtime 本轮提供的 Context。

一次调用结束后，模型不会自动保留刚才看过的用户偏好、项目背景和历史经验。下一次调用如果没有再次提供这些信息，模型就无法使用它们。

最简单的办法是每次都把完整聊天记录放进 Context。

但对话变长后会出现三个问题：

- 历史记录持续消耗 Token；
- 大量临时信息会干扰当前任务；
- 跨会话、跨任务真正有价值的信息很难稳定复用。

所以 Runtime 需要把未来仍可能有用的信息保存到模型之外，并在后续任务需要时重新取回。

> Memory 解决的不是“让模型内部永久记住”，而是让 Runtime 能跨调用**保存、选择并重新提供**信息。

---

## 2. 持久化是memory的写入环节

系统把用户说的话写进了数据库，只说明数据已经持久化。

今天模型回答问题时，只有经过下面的链路才能使用这条信息：

```text
用户提出新问题
→ Runtime 检索到对应的信息
→ Runtime 将它作为背景信息放入当前 Context
→ 模型基于这条信息生成回答
```

如果检索失败、权限过滤错误或者没有注入 Context，这条记忆对本次模型调用就不存在。

因此 Memory 至少包含两个方向：

```text
写入：从当前交互中形成可复用信息
读取：为当前任务找回真正需要的信息
```

存储介质只是中间环节，不是 Memory 的全部。

---

## 3. Memory 与 Context 的边界

Context 是**当前这次模型调用能看到的全部输入**，生命周期通常只有一次调用。

其中可以包含：

- 当前用户请求；
- 系统和开发者指令；
- 最近对话；
- Runtime State 的必要投影；
- Tool Result；
- 从长期 Memory 中检索出的信息。

Memory 则位于模型之外，用来跨调用保存可能复用的信息。

两者的关系是：

```text
Memory --检索与选择--> 当前 Context --> 模型
```

所以“长期记忆”不是一种特殊的模型输入格式。它只有被选中并放入 Context 后，才会参与本轮推理。

有时会把当前 Context 中正在使用的信息称为 Working Memory。这个说法可以帮助理解，但不要误以为模型内部存在一个可以独立读写的工作记忆数据库。

所以context和memory是相交的关系 context中使用的历史信息 来源于memory

## 5. Memory 与 Runtime State 的边界

Runtime State 保存的是程序推进任务所需的确定性事实，例如：

- 当前执行到第几步；
- 订单 ID；
- 审批状态；
- 已完成和未完成的动作；
- 重试次数；
- 工具调用结果。

它回答的是：**这个任务现在处于什么状态。**

Memory 保存的是跨任务仍可能复用的信息，例如：

- 用户稳定偏好；
- 项目长期约束；
- 已确认的实体事实；
- 可复用的历史经验。

订单退款任务中的 `order_id=A1024` 应该进入 Runtime State，因为程序必须精确读取它。用户偏好“退款前先展示金额并确认”才可能进入长期 Memory。

> 必须精确、可校验、可恢复的执行事实，优先由 Runtime State 管理，不能让模型从长期记忆或对话摘要中猜。

任务结束后，State 通常可以清理。只有其中少量对未来有价值的信息，才经过判断转成 Memory。

## 6. Memory 与 Cache、RAG 的边界

Cache 的目标是减少重复计算、降低延迟或成本。

它可以缓存模型结果、Embedding 或工具响应。缓存内容是否保留，通常取决于性能策略，而不是未来是否具有认知价值。

RAG 的目标是为当前问题检索外部知识，例如产品文档、公司制度或技术资料。这些知识通常面向一批用户，而不是从某个用户的历史交互中形成。

Memory 更关注具有主体和作用域的信息：

```text
这个用户偏好什么
这个项目已经做过什么决定
过去处理相似任务得到过什么经验
```

三者可以使用相似的向量检索技术，但解决的问题不同：

| 机制 | 核心问题 |
| --- | --- |
| Memory | 哪些历史信息值得在未来任务中复用 |
| RAG | 当前问题需要哪些外部知识 |
| Cache | 哪些计算结果可以直接复用 |

不能因为底层都用了向量数据库，就把它们当成同一个系统。

---

## 7. 一条完整的 Memory 链路

Memory 的端到端链路是：

```text
当前交互产生信息
→ 提取候选记忆
→ 判断价值、来源和权限
→ 与已有记忆比较并写入
→ 后续任务构造检索需求
→ 召回、过滤和重排
→ 选择少量相关记忆
→ 注入当前 Context
→ 模型使用
→ 根据新信息继续更新或遗忘
```

模型可以参与候选提取、语义匹配和内容归纳，但 Runtime 必须控制权限、作用域、持久化和最终注入。

因此职责边界仍然是：

```text
模型负责理解和生成候选判断
Runtime 负责管理生命周期与访问边界
存储系统负责可靠保存和查询
```

Memory 让 Agent 具有连续性，但它不能保证记忆一定正确，也不能代替权威业务数据。后续真正困难的问题是：面对当前交互产生的大量信息，究竟什么值得记。
