## 1. 全量保存history

最简单的 Memory 方案是保存完整聊天记录，需要时再做语义检索。

这个方案容易实现，但会把四类内容混在一起：

- 对未来有用的稳定事实； （长期价值）
- 只对当前任务有效的临时要求； （短期价值）
- 模型的猜测和错误结论； （错误信息）
- 重复、敏感或不允许长期保存的信息。（不合规）

保存得越多，后续检索不一定越好。错误和过时信息也会被反复召回，占用 Context 并影响模型判断。

## 2. 判断一条信息是否值得记

一条信息进入长期 Memory，通常需要同时满足几个条件。

### 相对稳定

未来一段时间仍然可能成立。

### 能够复用

未来任务确实可能再次需要。


### 对决策有影响

如果是否提供这条信息不会改变后续判断，就没有必要让它长期占据检索空间。

### 来源足够可信

用户明确表达、系统确认和工具返回的权威事实，可以具有不同可信度。

llm推测信息不准入

### 允许保存

信息即使有用，也可能因为敏感性、权限或保留规则不能进入长期 Memory。


## 3. 记忆应该保存结论，而不是整段过程

用户可能在一次长对话中逐步确认：

```text
项目早期考虑过 PostgreSQL
→ 现有团队更熟悉 MySQL
→ 线上基础设施也主要支持 MySQL
→ 最终确定这个项目使用 MySQL
```

长期 Memory 不需要复制整段讨论，只需要保存最终可复用事实：

```text
项目 A 的数据库选型为 MySQL。
```

但压缩过程不能丢掉来源和适用范围。否则以后无法判断：

- 这是用户明确决定，还是模型总结；
- 只适用于项目 A，还是用户的所有项目；
- 现在仍然有效，还是已经被新决定替代。

所以高质量记忆不是单独一段文本，而是一条带证据和边界的记录。 可以是压缩后的文本 但是内容要可用

## 4. 一条记忆至少需要什么

最小记忆单元可以表示为：

```text
内容 + 来源 + 时间 + 置信度 + 作用域
```

这些字段分别解决不同问题：

- `content`：未来要复用什么信息；
- `source`：这条信息从哪里来，能否回溯；
- `created_at`：系统什么时候记录了它；
- `confidence`：它是确认事实还是推断结果；
- `scope`：谁可以使用，它适用于哪里。

只有内容而没有这些元数据，系统很难可靠处理冲突、权限和失效。

## 5. 复杂度升级

当系统只保存少量独立偏好时，文本加基础元数据就够了。

但只要开始出现更新和冲突，就需要更明确地回答：

```text
谁的什么属性，在什么时间范围内是什么值
```


因此可以按复杂度逐步升级：

```text
少量独立偏好
→ 文本 + 基础元数据

需要精确更新和冲突判断
→ 增加实体、属性、值和有效时间

需要保留变化历史
→ 增加状态与替代关系
```



## 6. 语义、情景和程序性信息怎么理解

有时会按内容把长期 Memory 分成三类。

### 语义信息：是什么

```text
用户主要使用 Java。
项目 A 使用 MySQL。
```

它通常是实体事实、属性或偏好。

### 情景信息：发生过什么

```text
上次排查连接超时时，根因是连接池配置过小。
```

合格的情景信息至少要保留场景、行动和结果，否则未来无法判断是否真的相似。

### 程序性信息：以后可以怎么做

```text
排查这个项目的数据库连接问题时，先检查 Hikari 连接池指标。
```

这种经验仍可能演化，可以先存在 Memory 中。

如果一条方法已经稳定、通用而且必须严格执行，就不应该继续只依赖动态记忆。它应当固化到代码、Prompt 或 Skill 中。

> Memory 适合积累仍在变化的经验；代码、Prompt 和 Skill 负责固化稳定能力。

这三类只是在回答“记忆表达什么”，并不决定底层必须使用哪种数据库。

---


## 重点

判断 Memory 的关键不是识别关键词，而是判断信息的**稳定性、复用价值、证据和作用域**。

即使候选已经值得保存，也不能直接插入数据库。Runtime 还需要把它与已有记忆比较，决定是新增、更新、替代还是保留冲突。
