## 1. 存储选型应该从查询问题出发

Memory 系统最终需要保存内容、元数据和变化历史，也需要支持后续检索。

但数据库不能替 Runtime 决定：

- 什么信息值得记；
- 新旧记忆是并存、更新还是替代；
- 当前用户有权读取哪些记录；
- 哪些记忆应该进入本轮 Context。

这些属于 Memory 的业务规则。

存储系统解决的是：

```text
数据如何可靠保存
→ 系统需要按什么条件找到它
→ 更新、删除和审计要达到什么保证
```

所以选型不能从“哪种数据库更适合 AI”出发，而要先问：Memory 最常见的查询是什么。

---

## 2. 最简单的方案：先用关系数据库

大多数 Memory 都有明确的结构化字段：

```text
memory_id
tenant_id
user_id
project_id
subject
predicate
content
source
confidence
valid_from
valid_to
status
```

系统通常需要按用户、项目、实体、状态和时间精确查询，也需要可靠地更新、替代和删除记录。

这些需求天然适合 MySQL、PostgreSQL 等关系数据库：

- 精确条件查询；
- 事务和唯一约束；
- 更新与删除可靠；
- 容易实现租户隔离；
- 能保留来源和替代关系；
- 便于审计。

如果 Memory 规模不大，或者主要保存稳定偏好和结构化事实，关系数据库加普通索引通常已经足够。

> 不要因为 Memory 会被模型使用，就默认先上向量数据库。

---

## 3. 关系数据库什么时候开始不够

用户查询不一定使用存储时的原话。

Memory 中保存：

```text
连接池耗尽导致请求排队。
```

用户后来问：

```text
之前数据库连接卡住是怎么解决的？
```

普通字段和关键词检索可能无法稳定识别两句话的语义关系。

当系统需要在大量非结构化经验、摘要和历史案例中按含义找相似内容时，可以增加向量索引。

升级后的链路是：

```text
文本生成 Embedding
→ 向量检索召回候选 memory_id
→ 回关系库读取完整记录和权威状态
→ 做权限过滤、重排和 Context 选择
```

这里向量索引负责“帮忙找到可能相关的记录”，关系库仍然负责事实源和生命周期管理。

---

## 4. 为什么向量数据库不能单独承担 Memory

向量检索擅长语义召回，但相似度不能回答：

- 两条信息是否描述同一个实体；
- 当前用户是否有权读取；
- 记录是否已经被替代；
- 哪条事实当前有效；
- 删除是否已经覆盖全部派生数据；
- 相似案例的结论是否适用于当前任务。

因此一条向量记录不能只有 Embedding，至少需要关联：

```text
memory_id
tenant_id / user_id / project_id
文本或文本引用
记忆类型
状态
时间
```

文本更新后，Embedding 也需要重新生成。删除主记录时，对应向量索引也必须清理。

更准确的定位是：

> 向量库是语义召回索引，不是记忆正确性的来源。

如果数据库本身已支持满足规模需求的向量扩展，也可以先在同一个关系数据库中完成，不必为了架构形式额外拆出独立系统。

---

## 5. KV 存储解决的是快速已知键查询

如果系统已经知道准确 Key，例如：

```text
user_7 的会话偏好
session_123 的临时摘要
memory_456 的检索缓存
```

Redis 等 KV 存储可以提供低延迟读写。

它适合：

- 当前 Session 的临时状态；
- 高频读取的少量用户配置；
- 检索结果和 Embedding 缓存；
- 有明确 Key 和过期时间的数据。

但 KV 不擅长复杂条件查询、实体关系和完整审计。

因此 KV 通常作为关系库旁边的性能层，而不是长期 Memory 的唯一事实源。

还要继续区分：

```text
存在 Redis 里，不代表它就是 Cache
存在 MySQL 里，也不代表它就是 Memory
```

概念由数据用途决定，存储产品只决定实现方式。

---

## 6. 什么时候才值得引入图数据库

如果核心查询变成：

```text
用户参与哪些项目
→ 这些项目依赖哪些服务
→ 服务又使用哪些数据库
→ 哪些历史故障可能沿依赖关系传播
```

系统需要频繁做多跳关系遍历，实体之间的连接本身成为主要信息。

这时图数据库可以自然表达：

```text
用户 --参与--> 项目
项目 --依赖--> 服务
服务 --使用--> 数据库
```

但如果系统只是查询“项目 A 的数据库是什么”，关系表已经足够。为了少量一跳关系引入图数据库，只会增加建模、同步和运维成本。

升级条件应该是：

- 多跳查询是核心业务路径；
- 关系类型多且持续演化；
- 关系遍历使用频繁；
- 关系表和递归查询已经难以满足复杂度或性能。

图数据库解决关系遍历，不解决自然语言语义召回，也不会自动保证记忆正确。

## 7. 一个常见的混合架构

当需求确实同时包含精确管理、语义检索和高频读取时，可以形成：

```text
                 ┌→ 向量索引：召回相似内容
记忆写入 → 关系库
                 └→ KV：缓存热点数据和检索结果
```

读取时：

```text
当前任务构造查询
→ 结构化条件与向量索引召回 memory_id
→ 关系库读取权威内容、状态和权限字段
→ Runtime 过滤、重排并注入 Context
```

如果多跳实体关系后来成为核心需求，再增加图索引：

```text
关系库：事实源、事务、权限、生命周期
向量索引：语义召回
KV：快速状态与缓存
图索引：复杂关系遍历
```

多个存储同时存在会带来新的成本：

- 数据同步；
- 一致性；
- 删除传播；
- 索引重建；
- 故障恢复；
- 可观测性和运维。

只有单一存储无法以可接受的质量和成本支持查询时，才值得升级为混合架构。

---

## 8. 用查询需求完成选型

可以按下面的顺序判断：

```text
是否主要按用户、项目、实体和状态精确查询？
→ 是：先使用关系数据库

是否需要按自然语言含义检索大量非结构化记忆？
→ 是：在事实源之外增加向量索引

是否存在明确 Key 的高频、低延迟或临时数据？
→ 是：增加 KV 层

是否频繁查询复杂的多跳实体关系？
→ 是：再评估图数据库
```

最终要记住的不是“Memory 应该使用哪种数据库”，而是：

> 先确定记忆怎样被查询和治理，再选择最低复杂度、能够满足需求的存储组合。
