## 1. 为什么工具调用需要专门协议

模型、Runtime 和工具是三个不同角色：

```text
模型：我建议调用哪个工具，候选参数是什么
Runtime：我是否允许执行，怎样执行
工具：执行后得到什么结果
```

三者需要交换结构化信息，并且要知道每个结果对应哪次调用。

所以 Tool Calling 不只是“模型输出一个 JSON”，而是一套请求与响应协议：

```text
Model → Runtime：Tool Call
Runtime → Model：Tool Result
```

它与 HTTP 请求响应有些相似：
区别是 Tool Call 由概率模型生成。协议结构合法，只能说明 Runtime 可以解析它，不能说明调用在业务上正确。

---

## 2. Tool Call 表达模型的候选行动

模型决定使用工具时，会生成结构化调用：

```json
{
  "tool_call_id": "call_123",
  "tool_name": "query_order",
  "arguments": {
    "order_id": "A1024"
  }
}
```

它表达三件事：

```text
调用标识：这是哪一次调用
工具名称：模型希望使用哪个能力
候选参数：模型认为这次调用需要什么输入
```

Runtime 收到后不能立即执行，而要继续完成工具存在性、Schema、业务、权限和风险校验。

因此：

> Tool Call 是模型发给 Runtime 的结构化提案，不是已经发生的工具执行。

---

## 3. Tool Result 表达一次调用的观察结果

Runtime 执行工具后，需要把结果转换成模型能够稳定理解的结构：

```json
{
  "tool_call_id": "call_123",
  "status": "success",
  "data": {
    "order_id": "A1024",
    "shipping_status": "shipped"
  },
  "error": null
}
```

Tool Result 应该让模型区分： 

```text
success          执行成功并获得结果
error            执行失败
partial_success  只获得部分结果
accepted         异步任务已经受理，但还没有完成
cancelled        调用被取消
unknown          当前无法确认最终结果
```


## 4. tool_call_id

一次模型响应可能同时提出多个调用：

```text
call_1 → query_order(A1024)
call_2 → query_order(B2048)
```

两个工具可能并行执行，而且完成顺序不确定：

```text
先返回 call_2
后返回 call_1
```

如果只依赖消息顺序，模型和 Runtime 就无法可靠知道结果属于哪个请求。

`tool_call_id` 用于把协议中的 Tool Call 和 Tool Result 关联起来：

```text
Tool Call(call_1)   ↔ Tool Result(call_1)
Tool Call(call_2)   ↔ Tool Result(call_2)
```

这个 ID 通常由**模型接口**产生。Runtime 应把它当作不透明标识保存并原样返回，不需要解释或修改其内部格式。

它和其他 ID 的作用不同：

```text
tool_call_id  关联模型协议中的调用与结果
execution_id  标识 Runtime 的一次真实执行尝试
trace_id      关联整个用户任务的完整链路
```

同一个 Tool Call 可能因为网络错误重试多次，因此可以对应多个 `execution_id`，但面向模型仍然形成一个最终 Tool Result。

---

## 5. 为什么 Tool Call 也要写入消息历史

工具执行后，不能只把 Tool Result 单独塞给下一轮模型。

逻辑上应该保留
- 用户提问
- assistant发出的tool call
- tool result

这样模型才能知道：

- 自己刚才提出了哪个调用；
- 当前结果为什么会出现在 Context 中；
- 结果对应哪组参数；
- 任务已经进行到哪一步。

无论历史由应用自己保存，还是由模型服务端通过会话 ID 恢复，这组逻辑关联都不能丢失。

但是消息历史只**帮助模型理解轨迹**。真实执行次数、权限结果、预算和任务状态仍然要由 Runtime 单独维护。

---

## 6. Runtime 不能假设模型只返回一种结果

一次模型调用可能返回：

- 最终自然语言；
- 一个 Tool Call；
- 多个 Tool Call；
- 文本和 Tool Call 同时出现；
- 请求补充信息；
- 拒绝或无法完成。

如果文本和 Tool Call 同时出现，文本通常只是过程说明。Runtime 不应该因为看见文本就直接结束，而应先检查是否仍有待处理的 Tool Call。

可以按下面的顺序分类：

```text
存在 Tool Call
→ 校验并处理调用

不存在 Tool Call
→ 判断是最终回答、澄清、拒绝还是失败
```

任务是否完成不能只看响应中有没有文本。

---

## 7. 流式 Tool Call 要先拼接再解析

模型采用流式输出时，一个 Tool Call 可能被拆成多个片段：

```text
chunk 1: {"order_
chunk 2: id":"A
chunk 3: 1024"}
```

Runtime 不能把每个片段都当成完整 JSON，也不能一边接收参数一边执行。

正确流程是：

```text
按 call index 或 call id 分组
→ 累积工具名称和参数片段
→ 等待 Tool Call 完成事件
→ 解析完整 JSON
→ 执行 Schema 和业务校验
→ 最后才允许执行
```

Tool Call 尚未完成时，只能缓冲，不能产生真实副作用。

---

## 8. 不同模型协议需要适配层

不同模型厂商对工具定义、Tool Call、Tool Result、流式事件和结束原因的字段设计可能不同。

如果 Runtime 直接依赖某个厂商的原始结构，切换模型时业务代码会大面积修改。

更稳定的方式是：

```text
模型厂商协议
→ Provider Adapter
→ 内部统一 Tool 协议
→ Agent Runtime
```

适配层负责字段和事件翻译，不负责业务权限、用户确认和真实工具执行。

统一协议也不能假装所有模型能力完全相同。共同语义可以统一，是否支持并行 Tool Call、严格 Schema 或某种流式事件，应作为能力差异明确暴露。

## 总结

tool_call tool_result 都需要制定协议 
tool_call 协议 是为了让runtime能稳定使用 去调用工具
tool_result 是让模型能够稳定理解工具调用结果 并且知道状态
两者必须通过一个tool_call_id 连接一起 是一对 都需要写入消息历史 模型才能充分理解历史执行轨迹 因为模型是无状态的
runtime要对多种tool_result的情况都能处理 tool_result的情况有很多 协议要制定好
流式输出tool_call 需要先拼接 再解析
不同模型的tool_call不一样 可以构建统一适配层 转换为统一协议 给runtime。 runtime只消费制定好的协议。
