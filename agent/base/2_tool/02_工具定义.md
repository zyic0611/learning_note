## 1. 模型为什么需要 Tool Definition

模型不会天然知道 Agent 系统里有哪些工具。

即使系统中已经实现了订单查询 API，如果 Runtime 不把它描述给模型，模型也不知道：

- 工具叫什么；
- 它能解决什么问题；
- 什么时候应该使用；
- 调用时需要哪些参数；
- 参数允许什么类型和取值。

因此 Runtime 每次调用模型时，会根据当前任务选择一部分工具，并提供对应的 Tool Definition。

一个最小定义通常包含：

```text
name：工具名称
description：用途、适用条件和边界
input_schema：模型需要生成的参数结构
```

> Tool Definition 是模型认识外部能力的说明，也是模型生成 Tool Call 的输入契约。

它只是告诉模型“有哪些能力可以提议”，不代表模型获得了真实执行权限。

---

## 2. Tool Definition 同时服务模型和 Runtime

### 对模型来说，它像一段能力说明

模型主要通过工具名称、描述和参数语义判断：

- 当前任务是否需要这个工具；
- 它和用户目标是否匹配；
- 应该生成哪些参数。

例如：

```text
name: query_order
description:
  查询当前用户有权访问的单个订单实时状态。
  只用于查询，不创建退款，也不修改订单。
```

高质量描述不只写“查询订单”，还要写清适用场景和不负责什么。否则多个相似工具同时出现时，模型容易误选。

### 对 Runtime 来说，它是稳定接口

Runtime 根据工具名找到真实实现，并根据 Schema 校验模型生成的参数。

只要对模型暴露的定义保持稳定，底层可以从一个订单服务切换到另一个服务，而不要求模型理解内部 API、服务地址和数据库结构。

因此 Tool Definition 位于模型语义和真实系统之间：

```text
模型理解的业务能力
        ↓
Tool Definition
        ↓
Runtime 中注册的真实实现
```

---

## 3. 工具设计

模型会结合用户目标和 Tool Definition 选择工具，但 Runtime 简化这个选择 则

设计工具时优先遵守：

- 读优先于写
- 工具能力粒度尽量越小越好
- 不要提供语义重复的工具
- 只提供模型当次可能用到的工具

减少候选工具可以降低 Token、选择歧义和误调用风险，也限制模型当前能够提议的行动范围。

但工具列表缩小只是第一层限制，真正权限仍由 Runtime 和工具后端执行。

---

## 4. Input Schema 约束候选参数

Tool Schema 通常采用类似 JSON Schema 的结构：

```json
{
  "type": "object",
  "properties": {
    "order_id": {
      "type": "string",
      "description": "用户要查询的订单号"
    }
  },
  "required": ["order_id"],
  "additionalProperties": false
}
```

它告诉模型：

- 参数整体必须是对象；
- 允许字段是 `order_id`；
- 该字段必须是字符串；
- 它是必填项；
- 不能添加其他未知字段。

常用约束还包括：

```text
enum                 限制有限取值
minimum / maximum    限制数值范围
minItems / maxItems  限制数组数量
format               描述日期、邮箱、UUID 等格式
```

Schema 的价值是降低生成歧义，并给 Runtime 提供确定性的结构校验标准。

但 Schema 通过只代表参数**结构上合法**，不能证明：

- 订单真实存在；
- 订单属于当前用户；
- 当前状态允许退款；
- 这次操作没有越权。

这些属于业务和权限校验。

---

## 5. 参数不都应该由模型生成

工具需要的参数通常有三种来源。

### 模型生成

需要从用户自然语言中理解出来的业务参数：

```text
order_id
查询日期
退款原因
目标城市
```

### Runtime 注入

来自可信运行环境、不允许模型猜测或修改的参数：

```text
user_id
tenant_id
permission
access_token
trace_id
idempotency_key
当前可信时间
```

这些字段可以存在于工具真实接口中，但不应该全部暴露在模型可生成的 Input Schema 里。

### 工具内部派生

工具根据已有参数自行转换的内部字段：

```text
城市名称 → city_code
商品名称 → 内部商品 ID
业务类型 → 下游服务路由
```

如果 Runtime 或工具能够确定性获得，就不要增加模型的生成负担。

> 模型只生成必须依赖语义理解的参数；可信身份由 Runtime 注入；内部实现细节由工具自己派生。

---

## 总结

模型需要工具定义 才能知道有什么工具可以用。 
最小工具定义包含name、description、schema。
工具定义还服务于runtime runtime根据工具定义中的工具名 去执行对应的工具。
工具设计是有原则的 简单说越简单越好 并且每次只给模型提供需要的工具 tool的schema类似于json schema 参数约束提前定义好 保证工具调用的稳定性。 
工具参数不一定都是模型侧给 还有默认值 runtime注入 工具内部派生计算。
