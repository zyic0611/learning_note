
## 1. 为什么不能只给模型一大段文本

最简单的模型调用可以只有一段字符串：

```text
请回答：我的订单为什么还没发货？
```

当任务只有一个问题时，这已经足够。

但 Agent 很快会同时拥有：

- 业务规则；
- 当前任务
- 历史对话和历史回答
- 工具调用结果
- 可用工具及其参数

如果把这些内容直接拼成一段文本，模型很难稳定判断：

- 这句话是谁提供的；是LLM还是工具还是用户
- 它是在下指令，还是提供数据；
- 新信息是否覆盖旧信息；
- 工具结果对应哪一次调用。

因此模型接口需要消息协议。

> 消息协议的作用，是把不同来源、不同用途的信息组织成模型可以理解的**有序输入**。

---

## 2. 一条消息主要表达什么

消息不只是“聊天记录中的一句话”。从系统角度看，一条消息至少表达四件事：

```text
来源：谁提供了这段内容
内容：具体文本、图片或结构化数据
顺序：它在上下文中的位置
关联：它是否对应某次工具调用或其他对象
```

常见消息角色包括：

- `system`：应用级的指令 最高 提供的一般是整个运行环境的全局规则
- `developer`：高优先级的业务规则 面向的是某个具体的功能场景
- `user`：当前用户请求以及用户提供的数据；
- `assistant`：模型之前生成的回答或行动提议；
- `tool`：工具执行后返回的观察结果。


---


## 3. 一次完整模型请求包含什么

从概念上看，一次请求通常包括：

```text
Model Request
├─ 模型与生成配置
├─ 消息
├─ 工具信息
└─ 结构化输出
```

### 模型与生成配置

决定使用哪个模型以及生成行为，例如温度、最大输出长度等。

这些配置影响生成分布，但不能代替任务指令。

这个一般在调用某个具体的模型的时候 可以顺便配置好。

### 消息

承载当前任务需要的指令、用户输入、必要历史、状态摘要和工具结果。

Messages 是本轮 Context 的主要表达形式，但 Context 还可能包含图片、音频、缓存引用等其他输入。

消息的粒度比较小 上下文的粒度比较大。

### 工具定义

告诉模型本轮可以提议哪些工具，以及参数应该采用什么结构。

工具定义只是提供给模型的能力说明，真正权限仍由 Runtime 决定。

### 结构化输出

规定模型应该返回自然语言、结构化数据，还是工具调用提议。

它解决输出如何被下游消费，不保证业务内容一定正确。

---

## 4. 模型返回值

一次的模型响应 可能是 自然语言回答、结构化输出、一个或多个toolcall、拒绝/无法完成、需要补充信息。

runtime是确定性的程序 理解为外部框架 要对模型输出进行分类处理。

决定下一步做什么 是结束循环输出答案 还是再次组装消息 进入模型 还是找用户补充信息。

一次模型响应不应被假设成“必然返回一段文本”。常见结果包括：

所以 Runtime 校验并执行后，外部世界才真正发生变化，模型改变不了外部世界。

---

## 5. 消息历史不等于真实状态

Assistant 历史消息的价值是帮助模型保持语义连续，但它可能包含：

- 模型的错误输出
- 过期的信息；
- 用户后来纠正的事实；
- 对工具结果的错误解释。

所以：

> 历史消息 用于帮助模型理解上下文业务，业务 State 用于系统控制。 以业务state为基准


## 总结

就是模型的一次输入 包含了模型配置、消息（系统、用户、工具调用结果、历史模型输出）、工具定义信息、结构化输出协议要求。
消息只是一次输入的一部分 并且消息要区分4个结构。
模型的返回值有几种 runtime确定性程序根据不同的返回值做出不同的行为。
并且消息历史不一定是真相
