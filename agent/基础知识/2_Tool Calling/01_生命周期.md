
一轮用户对话可能调用多次模型 多次工具

## 轮次的区分

### 对话轮次

指的是用户发送消息一次 assistant最终回复一次。

从用户视角来看 这是一个对话轮次。

## 模型调用轮次

因为react流程是一个循环 所以可能调用多次llm思考输出

### 工具调用轮次

一次llm输出可以包含一个或多个tool call。

并且可以输出多个并行的工具调用。

## 生命周期中的五个核心对象

完整生命周期中会不断传递五类对象。

1. tool definition： 告诉llm有哪些工具可以用 一般是json格式的工具定义

2. message history：llm可以看到的历史消息 包括：system、developer、user、assistant、tool。 工具定义通常作为llm请求中的独立配置传入 但是从llm的语义来看 也属于当前上下文的一部分。

3. tool call：llm生成的候选调用。 tool schema形式。

4. tool result：runtime执行tool后的结果 会传回上下文

5. execution state： **是runtime在llm上下文自在维护的确定性状态** 执行状态是给程序可靠的控制任务用的。一般包括 执行的任务id 现在执行到第几步了 调用了几个工具 执行状态是什么 超时时间是多少

## 阶段0 runtime接收用户请求

用户请求首先是到达应用程序 不是直接进入工具

runtime会创建或者加载任务状态

- task id

- 会话id

- 任务状态

- 执行步骤

- 累计工具调用数量

Runtime还可能会获取：

- 当前用户身份

- 时间

- 时区

- 会话历史

- 用户权限

- 可用工具列表

- token预算

- 最大调用轮次

## 阶段1 组装第一次llm上下文

runtime负责构造第一次llm请求

概念上包括： system developer user 、runtime context、tools

有三个重要的概念

**1 runtime决定模型能看到什么**

模型不是自己拥有当前时间 用户 历史消息 数据库状态 工具 长期记忆 这些都是需要runtime 动态选择并且注入

因此上下文构建是runtime的能力 责任 不是llm自动完成的能力

**2 不一定把所有的工具都给llm**

一次可能只给几个

- 降低token

- 减少工具选择歧义

- 限制模型能力范围

- 降低错误调用风险

**3 当前时间 属于运行时事实**

明天不能靠llm的内部知识计算 应该由runtime提供可信的当前时间

## 阶段2 第一次llm调用

runtime把消息和工具定义交给llm

llm 需要完成三个判断

1. 用户最终目标是什么

2. 是否需要调用工具

3. 如果需要 先调用哪个工具

## assistant tool call 必须写入消息历史

runtime收到模型输出后 也就是受到tool call 应该保存斤历史消息。

因为下一次llm调用必须知道

- 自己用了哪些工具

- tool result哪里来的

- tool rusult对应哪个请求

- 执行到哪一步了

## 阶段3 runtime解析tool call

llm输出tool call ，runtime 不会立即执行

需要完成检查：

- 工具是否存在

- 是否允许使用当前工具

- 参数是否可以解析

- 参数是否符合 schema

- 参数是否符合业务规则

- 用户是否有权限

- 是否需要用户确认

- 是否超出调用预算

- 是否重复调用

## 阶段4 工具执行

工具底层可能是

- 本地函数

- HTTP API

- 数据库查询

- MCP server

- 微服务RPC

执行期间 runtime还得处理

- 超时

- 取消

- 限流

- 网络错误

- 服务异常

- 日志

## 阶段5 runtime标准化 tool result

第三方api的原始返回可能非常复杂 不一定可以直接给llm

runtime可以通过 **工具适配层** 转换成 统一结果

标准化的好处：

- 减少模型理解负担

- 屏蔽第三方api差异

- 降低上下文token

- 方便自动测试

- 提供稳定错误结构

- 后续可以随便更换服务供应商

## 阶段6 tool result写入历史消息

runtime把tool result 作为 tool message写入历史

并且根据tool_call-id 把结果跟之前的调用关联起来

## 任务什么时候算完成

不是llm没有生成tool call就算完成

因为可能是

- 任务完成

- 模型认为不用tool

- 模型错误的没用tool

- 模型无法继续

- 模型在请求用户补充信息

- 模型拒绝任务

- 模型错误的认为工具已经执行完

所以runtime需要区分 状态

- completed

- waiting_user_input

- failed

- denied

- cancelled

- budget_exhausted

- unknown
