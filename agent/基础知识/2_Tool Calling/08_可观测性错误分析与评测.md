不只知道 Agent “答错了”，还要能定位它在哪一步、为什么错，并用数据持续改进。

## 可观测性

一次任务必须能追踪全链路

核心id：
- `trace_id`：串起一次用户任务的全部链路
- `conversation_id`  : 标识会话
- `tool_call_id` : 关联模型调用与工具结果
- `execution_id`：标识一次真实工具执行尝试

一次trace需要记录

用户输入
→ 模型输入与版本
→ 可用工具
→ 模型输出的 tool call
→ 校验 / 鉴权结果
→ 工具耗时、重试、结果
→ 最终回答
→ Token、延迟、成本


## 核心指标

质量、成本、延迟、安全

- 任务质量： 任务成功率 用户澄清率 人工接管率
- 工具质量： 工具选择准确率 参数准确率 工具成功率
- 可靠性： 超时率 重试率 循环终止率
- 效率：平均工具调用次数、模型轮次、延迟、token消耗
- 安全：越权拒绝率 高风险确认覆盖率 敏感信息泄漏数量

## 构建评测集

需要覆盖真实工作流 应该覆盖

- 正常成功路径
- 缺少参数 需要澄清
- 无权限
- 工具无结果
- 工具超时
- 多工具串行 并行
- 高风险副作用确认
- 提示注入 于越权请求
- 重复调用 预算终止

## 离线评测 于线上监控

**离线评测**：发布前，固定案例集跑回归测试。

适合发现：

- 改了 Prompt 后工具选择是否退化；
- 新工具是否导致旧工具被误选；
- 规则、模型或 Schema 改动是否破坏旧能力。

**线上监控**：发布后，观察真实 Trace 与指标。

适合发现：

- 某个下游服务突然变慢；
- 特定用户意图成功率下降；
- 新型用户表达导致参数提取失败；
- 异常成本或循环激增。

两者缺一不可：

> 离线评测防回归，线上监控发现真实世界问题。


## 评测顺序

先确定性 后主观质量

确定性指标：
```
工具是否正确？
参数是否正确？
是否发生越权？
是否超预算？
最终答案是否引用真实 Tool Result？
```

主观：
```
回答是否清晰？
是否完整？
语气是否合适？
```

## 总结：

我会从完整轨迹而非只看最终文本来评估。每次任务用 trace_id 串起模型决策、工具调用、参数校验、执行结果与最终回答；指标覆盖工具选择准确率、参数正确率、任务成功率、延迟、成本和安全拒绝率。失败时按工具漏调、选错、参数错误、下游失败、权限拒绝、循环和结果未 Grounding 等标签归因。上线前跑离线回归集，上线后监控真实 Trace 和异常指标，并将线上高频失败样例持续回流到评测集。
