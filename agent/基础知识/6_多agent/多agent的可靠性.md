## 错误分类与处理策略

首先保证单agent发生错误了 要采取对应的处理策略

网络异常 网络超时 ：   指数退让重试 并且设置上限

参数格式错误： 修正参数后重试 

输出不符合预期： 重新生成或者降级

权限不足、资源不存在： 终止 报错

参数不足：返回澄清信息



## 幂等设计

agent会重试 重试就要保证幂等性。 保证重试安全



## 检查点与状态持久化

agent的长任务全部跑在内存里 那么中途失败 全部丢失。

所以每写完一个子任务 就要保存checkpoint 出现问题 从checkpoint断点续跑 不用重头。



## 循环检测和步数限制

agent可能陷入死循环 

设置最大循环次数

调用工具去重 比如用历史 (tool,args) 哈希

递归深度限制 但是最好子agent不能继续调用agent

全局超时时间：整个任务的时间上限



## 输出校验

sub-agent的输出不能盲从 orchestrator必须校验

三层校验：

1. 格式校验  json schema是否符合预期结构
2. 语义校验 内容是否合理 可以使用llm as judge
3. 一致性校验 多个agent输出是否矛盾



## 人工介入

agent 输出置信度过低

涉及高危 不可逆操作 

连续失败n次

任务偏离原始目标太远



## 超时与熔断器

每层设置超时：

- 单词tool call 5-30s
- 单个sub-agent 任务 2-5min
- 整体任务 设置硬上限



熔断器模式：

比如某个sub-agent连续失败n次 直接标记为不可用 走备用方案

降级 或者跳过



## 总结：

预防： 幂等 输出校验

检测： 步数、循环、超时 检测

恢复：checkpoint机制

降级： 熔断 fallback 高风险人工介入



## fallback

是回退 降级。 使用备用方案 返回降级结果



多 Agent 场景的具体例子

  场景 1：子 agent 失败
  主方案：调用"高精度分析 agent"处理数据
  失败后 fallback：改用"简单规则引擎"处理，结果精度低一点但有结果

  场景 2：外部 tool 不可用
  主方案：调用实时搜索 tool 获取信息
  失败后 fallback：用本地缓存的历史数据回答

  场景 3：LLM 输出不符合预期
  主方案：让 agent 生成结构化 JSON
  校验失败后 fallback：用正则从文本里提取关键字段
  再次失败：返回"无法处理，请人工介入"

---
  Fallback 的层级设计

  好的 fallback 是多层的，不是一下子就放弃：

  第 1 层：重试（参数不变，重试 3 次）
  第 2 层：修正重试（修正参数或 prompt，再试）
  第 3 层：换备用方案（降级到更简单的实现）
  第 4 层：跳过该步骤（如果该步骤非必须）
  第 5 层：人工介入（实在处理不了，报给人）
