

长期记忆只有被 **召回-过滤-重排-选择-注入context** ，模型才能使用。

完整链路：
当前任务
-> 构造查询
-> 召回候选
-> 硬过滤
-> 重排
-> 选择少量记忆
注入context

## 两种检索时机
### 预加载

任务开始前，根据当前用户和任务加载稳定背景：

```text
语言偏好
项目技术栈
当前项目配置
```

适合少量 稳定 高频使用的信息。
### 按需检索

推理过程中 遇到需要历史经验或旧事实的步骤时（也就是相关步骤），再调用记忆检索工具。

可以解决context 并且避免不管记忆干扰

### 混合使用

两者可以混合：

```text
会话开始加载少量稳定背景
任务过程中按需检索具体历史
```

## 查询构造

检索query 不能只用用户最后一句话 需要结合
**当前任务+目标实体+用户作用域+所需记忆类型**

好的查询需要明确
- 查什么
- 关于什么
- 范围：租户、会话、项目
- 需要哪类记忆：事实、案例、经验

## 召回

优先保证候选不漏选 把候选都召回
可以使用
- 语义相似度
- 关键词匹配
- 精确实体匹配
- 元数据条件。

召回阶段通常取较多候选
候选Top-K. 追求的是较高的Recall。 该阶段解决可能相关 重排才决定谁最值得。

## 硬过滤

先排除不可能使用的记忆。
过滤规则一般有：
- 租户/用户 是否匹配
- 权限
- 是否被删除 or 替代 or 国旗
- 实体是否匹配

过滤是硬约束 即使语义分数最高 也需要顾虑


## 重排

最终排序需要考虑
- 相关性
- 时效性
- 置信度
- 重要性
- 实体匹配度 
可以采用简单加权来计算得分 重排。

权重不是固定答案。 需要根据业务调整。

最后去除冗余信息。 

## 最终选择：

Top-k 重排后 去除冗余信息、冲突信息、符合token预算 的记忆 注入 context。

并且应该作为带边界的背景信息注入 不应该默认放进高权限的system prompt里。

注入的时候 保留 内容 来源 时间 置信度 作用域 。

并且可以设置 最大记忆条数、最大tokne数目、单条最大记忆长度、最低得分阈值 再筛查一部分。
