ReAct的核心是 不假设一开始就知道完整路径。 而是每次在获取工具结果后 再决定下一步 


ReAct 将决策和行动交替进行：

```text
根据当前状态决定行动
→ 执行工具
→ 获得 Observation
→ 更新判断
→ 继续行动或结束
```

Runtime 视角：

```text
Model Decision
→ Tool Call
→ Tool Result
→ Model Decision
```

它不提前固定完整计划，每一步根据最新结果调整，适合流程不完全确定、需要使用工具的中等复杂任务。

主要风险：

- 长流程中忘记初始目标；
- 重复调用相同工具；
- 遇到错误后陷入无效循环；
- 上下文持续增长并发生目标漂移。

## ReAct的状态

必须包含是那个字段：
- goal：目标 防止偏移
- current_state 让模型知道已经完成了什么
- unresolved_questions 没解决的问题 让next action 始终服务于未解决问题

所以ReAct的关键不是llm会use tool 而是把目标、历史观测、未解决目标 作为每轮决策输入 使Observation可以改变后续行动。

## 观测结果影响下一步

循环内需要对Observation做分类

- 得到预期数据：基于结果推进到下一个未解决问题
- 结果为空调整查询范围、检查前提，或说明无数据
- 参数错误：修正参数后有限重试
- 工具暂时失败：按规则重试或等待
- 权限不足/资源不存在：换数据源、请求用户授权或停止
- 已有证据足够：汇总并结束

关键是判断下一步是否带来新消息 推进目标 降低不确定性 如果否 就应该结束
## 循环护栏

1. 最大步骤数
2. 调用预算
3. 明确终止条件
4. 重复调用检测 看是否用了同一个工具
5. 无进展阈值 看是否连续几轮没有增加事实或者缩小问题范围 也就是看未解决的问题是否没有看花

## 总结：
ReAct 在每次工具调用后将 Observation 重新输入决策，因此能根据最新环境信息调整路径，适合信息不完整、行动路径不确定的任务。但它没有天然的全局保证：长链路容易重复调用、上下文膨胀、目标漂移和成本失控。所以生产中必须显式维护目标与未解决问题，并设置最大步骤、调用预算、重复调用检测、无进展阈值和终止条件。

## 推理脚手架和react

推理脚手架是planning阶段 更像是任务开始的时候的“分析模板”。帮助识别目标、约束、缺失信息，并把复杂问题转成可执行子目标。

React 是 推理 reasoning和 action执行阶段 更像任务运行中的“逐步决策循环”。每次拿到工具结果后，决定继续、换方法、提问还是结束。
