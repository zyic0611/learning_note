反思是：Agent 已经生成答案或执行结果后，如何判断它是否可靠；不可靠时，如何有限地修正，而不是无限“自我反思”。

Reflection 不是独立的完整 Agent 流程，而是一段可插入生成或执行后的质量控制闭环。

核心闭环

```text
生成
→ 检查 verifier 判断是否明确满足标准
→ 定位问题 给出建议 critic 解释哪里不好 给初修改建议
→ 修正 corrector 根据反馈 最小化修改
→ 再验证
```

所以会有四个角色 

## 确定性验证 优于模型自评

对于不同的结果 应该使用不同的验证期 verifier

能用代码、规则、事实验证 不要给llm感觉

- json 给schema validator 验证
- sql /代码： 给parser、compiler、单元测试、静态检查
- 金额、库存、审批：给业务规则和健全
- 外部操作是否成功：给工具返回结果 和状态查询
- 回答完整性、质量：给规则审查 和引入另一个模型

llm自评：
- 同一模型常会保留同一个盲点
- 模型说“正确”不是可证伪的事实
- 它可能为错误结果编造合理解释
- 高风险任务需要可审计的通过标准

## 验证标准来自完成条件

需要确定的完成条件 才能对应的去验证。

没有完成条件的 Reflection，通常会退化为模型重复润色。


## 总结

如果被问“为什么 Agent 自我反思不能保证正确？”：

> 自我反思本质上仍是模型生成，模型可能重复同一个错误或为错误结果提供看似合理的解释。因此我会先把任务完成条件转成可执行的确定性验证，例如 Schema、编译、单元测试、业务规则和权限检查。模型 Critic 只负责解释软性缺陷或生成修正建议；Corrector 根据明确错误做最小修改；每次修改后重新验证，并限制修正次数。若仍无法通过，就保留证据并升级人工或向用户澄清。
