# 评测、项目与面试复习

## 已有项目知识整理

现有 NL2SQL 项目可以按下列方式分析：

```text
固定节点流程
    属于 Workflow，由 Orchestration 实现。

SQL Query Plan
    属于任务拆解和 Plan-and-Execute。

工具结果驱动下一步
    具有 ReAct 式自适应决策。

SQL Parser、Schema 和规则检查
    属于 Verifier。

根据明确错误重新生成 SQL
    属于有限 Self-Correction。

Schema 检索
    属于 RAG，不等于推理模式本身。

Redis 保存上下文和槽位
    属于 Memory，不等于推理模式。
```

项目表达可以总结为：

> 系统使用 Workflow 控制主流程，在 SQL 子任务中通过结构化 Query Plan 完成任务拆解，使用工具执行查询，并通过 Parser、Schema 和业务规则进行确定性验证；验证失败时根据明确错误进行有限修正。

## 还需要学习

### 计划质量

- 步骤是否必要、可执行。
- 依赖是否正确。
- 是否覆盖用户目标。
- 是否有明确完成条件。

### 执行决策质量

- 下一步选择是否正确。
- 是否出现无效或重复工具调用。
- 失败后策略是否合理。
- 是否保持初始目标。

### 修正质量

- 是否发现真实错误。
- 是否误报或把正确结果改坏。
- 修正是否最终通过验证。
- 增加的成本是否换来实际提升。

### 核心指标

```text
Task Completion Rate
Plan Success Rate
Average Steps
Repeated Action Rate
Loop / Timeout Rate
Verification Pass Rate
Correction Success Rate
Latency and Cost
```

## 项目验收标准

- 能画出推理、执行和验证节点。
- 每个节点职责唯一，不重复控制同一决策。
- 有最大循环和修正次数。
- 关键结果使用确定性验证。
- 有一组简单任务、失败任务和边界任务评测。

## 面试需要能回答

- ReAct 与 Plan-and-Execute 有什么区别？
- 什么情况下应该先规划？
- Reflection 为什么不能保证正确？
- 如何防止 Agent 无限循环？
- 为什么固定 Workflow 在很多生产场景更可靠？
- 如何评测一次推理架构改动是否有效？
