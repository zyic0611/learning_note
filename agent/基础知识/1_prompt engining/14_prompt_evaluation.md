prompt engineering 并不能单纯的凭借经验修改 

必须定义成功标准

1. 构建测试集
2. 对多个版本的prompt进行评测
3. 分析失败模式
4. 修改prompt或系统
5. 继续回归测试

## 评测对象

不能只看最终答案 来评价prompt的好坏

需要同时评测
- 最终答案
- 工具调用轨迹
- 工具选择
- 工具参数
- 中间状态
- 澄清问题
- 错误处理
- 停止条件
- 权限和安全行为
- 成本和延迟

因为最终答案回答正确 不代表中间过程正确。

## 成功标准的维度

需要多维度的评测。

任务完成： 是否正确回答问题 正确执行操作

正确性： 结果是否 事实正确 业务正确

可靠性：答案是否基于可靠来源

工具选择：是否选择了正确工具

参数正确：工具参数是否正确完整

安全性：是否拒绝危险或越权操作

澄清品质：是否在真正需要的时候澄清 而不是过度询问

稳定性： 重复运行是否得到稳定结果

效率：工具调用的次数 token消耗 延迟 成本

用户体验：回答是否清晰 错误是否可以理解 是否给出下一步

## 评测集如何设计

至少包括 
- 正常样例
- 边界样例
- 异常样例
- 缺少信息
- 歧义输入
- 对抗输入
- 提示词注入
- 工具错误
- 空结果
- 冲突结果
- 权限不足
- 高风险操作
- 多论对话
- 长上下文

## 离线 在线评测

offline eval: 上线前使用固定数据集进行评测

优点：
- 可重复
- 便于比较版本
- 适合回归测试
缺点：
- 不能覆盖所有真实输入
- 可能与线上分布不一样

online eval： 在真实流量或者灰度流量中测试
- 用户是否重新提问
- 人工接管率
- 任务完成率
- 投诉率
- 工具错误率
- 成本和延迟
线上评测必须注意隐私和数据安全

## 评测方法

### 代码评测 

适合评测
- json schema
- sql语法
- 字符串匹配
- 函数调用参数
- 状态转移
- 权限检查
优点： 
- 快
- 稳定
- 可重复

### 人工评测

适合： 
- 回答质量
- 语气
- 复杂业务判断
- 用户体验
缺点：
- 成本高
- 速度慢
- 主观性很强


### LLM as Judge

让另一个llm 根据rubric（评分标准）打分

适合：
- 相关性
- 完整性
- 风格
- 解释质量
- 复杂问题比较

需要注意：
- model可能判断错误
- 可能更偏好长答案
- 可能被表面格式影响
- 需要和人工评分校准
- 不能只用同一个模型生成和评价 起码两个

## agent Trajectory evaluation

评估 也要看完整的agent 轨迹

要检查
- 是否调用了正确工具
- 是否出现了不必要调用
- 是否重复调用
- 参数是否来自用户或可信上下文
- 是否在工具失败后正确回复
- 是否在高风险操作前请求确认
- 是否超过最大步数
## 回归测试

prompt修改后 **必须保证旧能力没有退化**

因此测试集必须包含 
- 正例
- 反例
- 边界例
- 之前修复过的失败样例

## 线上监控

生产环境必须记录：
- 提示词版本
- 模型版本
- 输入类型
- 输出状态
- 工具调用轨迹
- 错误类型
- token消耗
- 延迟
- 用户是否重试
- 是否人工介入
- 是否发生安全事件

必须注意：
- 脱敏
- 隐私保护
- 访问权限
- 日志保存周期
- 敏感内容隔离

## 完整闭环

1. 定义成功标准
2. 构建代表性数据集
3. 定义自动和人工 grader
4. 运行基线测评
5. 分析失败轨迹
6. 修改 prompt/tool/context/runtime
7. 运行回归测评
8. 灰度发布
9. 线上监控
10. 补充新的失败样例

## 总结
Prompt Evaluation 不是只看最终回答是否正确，而是要评测完整 Agent 轨迹，包括工具选择、参数、澄清、错误处理、权限、安全、成本和延迟。Prompt 的优化应当是 Eval-driven，而不是凭感觉修改。
