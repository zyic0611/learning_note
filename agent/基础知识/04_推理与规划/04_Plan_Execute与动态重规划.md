Plan-and-Execute（规划—执行）适合复杂、长链路任务。它的核心思想是：

> 先维护一个可见的全局计划，再逐步执行；环境变化时，修改尚未完成的部分，而不是推倒重来。


```text
Planner 制定计划
→ Executor 执行步骤
→ Controller 更新状态并选择下一步
```

Plan-and-Execute 针对 ReAct 长任务容易局部漂移的问题：

## 三个角色的边界

- Planner 
	- 将目标转换为步骤、依赖、完成条件 
	- 不执行外部操作
- Executor
	- 只执行当前已经批准的步骤 并且返回结果 
	- 不擅自修改总目标 或跳步
- Controller
	- 只维护计划的 **状态** 决定下一个步骤或是否重新规划
	- 不能代替具体的工具执行

## 计划是状态对象

计划并不是一个步骤列表 而是一个json 结构化的 状态对象  里面列出正在执行的任务 未开始的任务  。

常见的状态：
```
pending      未开始
in_progress  执行中
completed    已完成
blocked      缺少条件，暂不能执行
failed       已失败
skipped      不再需要执行
```

一个步骤只有其依赖全部完成 结果仍然有效的时候 才可以进入执行。


## contrller的决策核心

Controller 每次收到 Executor 的结果后，主要做四件事：

1. 更新步骤状态和输出；
2. 检查依赖是否已满足；
3. 判断当前计划是否仍然有效；
4. 选择下一个可执行步骤，或触发局部重规划。

所以就是一个计划控制器

## 重规划

不要“每一步执行完就重规划”，那会退化成高成本的 ReAct；也不要坚持旧计划到底。

触发条件：
- 步骤失败 比如哪个工具调用失败
- 前置条件缺失 阻塞并向用户澄清
- 环境变化： 用户修改query 删除或者调整无关步骤
- 结果推翻假设： 调整分析路径
- 用户修改总目标：重新评估计划 必要时重建

经常是局部重规划： 保留已经完成有效的步骤。

## 区别于ReAct

R：
- 核心机制：每轮观察后决定下一步
- 全局视图：较弱，主要面向当前状态
- 变化应对：灵活性高
- 适合：路径不确定的中等复杂探索
- 主要风险：上下文膨胀、循环、目标飘逸

P：
- 核心机制：维护全局计划后逐步执行
- 全局视图：较强，明确步骤和依赖
- 变化应对： 通过局部重规划应对
- 适合：多步骤、依赖清晰的长任务
- 主要风险：初始计划过时、状态管理复杂

实际工程中常组合：**Planner 提供全局骨架，Executor 内部可用轻量 ReAct 处理某一步的不确定性。**

## 模型选用

模型分层是成本和质量权衡，不是架构必需品。我会通过端到端成功率、平均调用成本、延迟和重规划率来验证是否值得分层。

## 计划某一步失败 如何处理


我会先由 Controller 判断失败类型：暂态错误可有限重试，工具或路径不适配则寻找替代步骤，缺少关键前提则请求用户澄清。若失败影响后续依赖，就触发局部重规划：保留已完成且仍有效的步骤，只重建受影响的未完成步骤和依赖关系。Executor 只负责执行当前批准步骤，不能自行修改总目标，从而保证整个任务仍然可控、可审计。
