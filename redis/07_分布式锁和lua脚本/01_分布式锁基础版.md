并发竞争、在同一个JVM内部 多个线程竞争一个资源 使用java的synchronized or reentrantlock就可以搞定。  

当应用部署为集群（多个 JVM / 多个实例）后，本地锁只能约束当前 JVM 内部线程，无法协调不同 JVM 之间的资源竞争，因此需要引入分布式锁。

此时需要一个外部的仲裁者 redis就是最常见的

## setnx

Redis 最早期也是最简单的实现方式。

实现：

​	使用`setnx lock_key 1` 返回1 就说明抢锁成功   

​	执行后 调用 `DEL lock_key` 释放锁

问题：

​	如果拿到锁的线程 在执行业务时 崩溃 或者服务被强制重启

​	del没有执行 那么锁永远在redis里 所有线程都被死锁。

## setnx+expire

为了解决死锁问题 为锁加上过期时间

`setnx`后加上`expire lock_key 10`

问题：

​	这两条命令不是原子操作 中间有间隙 

​	如果setnx成功后 执行expire之前 客户端异常退出 则依旧没成功执行expire 锁还是永远存在



## set nx ex

`SET lock_key 1 NX EX 10`

NX代表not exist 代表是否存在 不存在才创建锁

EX代表expire   设置过期时间

一条命令 包括 判断是否存在 和设置过期时间 上锁。 **是原子操作**。

为什么是原子操作 因为redis是单线程的 一个set命令不会被其他命令打断

问题：

​	误删别人的锁。

1.如果线程a拿到锁 业务执行的很慢 执行时间超过expire过期时间 

2.则锁会自动释放 

3.此时线程b进来 成功获取锁

4.此时a终于执行完了 把锁释放

5.此时把b获取的锁给释放了

6.c线程又可以进来获取锁 彻底失控

**主要是因为 锁到期自动释放 但是业务代码顺序执行 不知道锁被释放了 所以还是会手动释放一次锁 **
## 引入唯一标识

锁的key-value结构 key是锁名字 value不能简单的只存放1 也要存放当前现成的唯一标识 一般使用UUID或UUID+ ThreadID

释放锁的时候 先get判断一下是不是自己的标识 如果是 再del

问题：

​	判断是不是自己的锁 和删除 这两个操作 依旧不是原子操作。

极端情况下：

1.a准备删除锁 先get 发现是自己的

2.此时java发生STW 比如 full gc 线程a停止了2s

3.在这2s内 锁a超时 自动释放 b就拿到了锁

4.gc结束 a还是执行了del 

5.把b的锁释放了 依旧有问题

## lua脚本

解决 判断+删除 也就是`get set的`原子性问题 引入lua脚本。 因为没有一条原子命令可以实现判断+删除的原子操作。

因为redis处理网络请求是单线程的 执行lua脚本 不会被插队 符合原子性。

## 演进路线

`SETNX
        ↓
SETNX + EXPIRE
        ↓
SET NX EX
        ↓
SET NX EX + UUID
        ↓
SET NX EX + UUID + Lua（Redis官方推荐）`
