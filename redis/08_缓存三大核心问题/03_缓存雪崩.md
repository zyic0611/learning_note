击穿是一个点导致数据库宕机 雪崩是一个面 :大面积key同时过期或者redis集群宕机  ，整个面都被打穿。


1. 大面积key同一时间集中过期
   - 大量的key的过期时间相同 则在这在过期的瞬间 查询流量全部砸向mysql
   - 解法：采用过期时间打散 （TTL Jitter) 不用固定值设置ttl 在基础时间上加上随机数
   - 在随机数区间内就会陆续过期 把同时打向数据库的流量平摊薄了
2. redis节点宕机【物理毁灭
   - 物理机断电 或者大key导致oom redis服务直接失效
   - 主从切换失败 redis内存耗尽

## 预防策略

### 随机TTL

事前预防：

预防同时过期  在过期时间上加上一个随机扰动函数

### 建立高可用集群

事前预防：

建立集群 保证redis节点宕机 自动发送故障转移 保证reids高可用性

### 多级缓存结构

事前预防：

不能把所有缓存都放在redis里。

采用 **`本地缓存 (Guava / Caffeine)` + `分布式缓存 (Redis)`** 的双层架构。

**执行流程：** 请求进来时，先查操作系统的进程内缓存（Caffeine），如果命中直接返回。Caffeine 没命中，再查 Redis。Redis 没命中，才走 DB。

**对雪崩的防御：** 即使 Redis 整个集群挂了，或者成批 Redis Key 过期，本地的 Caffeine 还能帮你顶住最核心的一波流量，不至于让数据库直接裸奔。

### 熔断 限流 降级

事后兜底：

如果前两道防线全被冲破，流量已经大到快把数据库压垮了，必须立刻启动自保机制。

- **实战做法：** 利用 Sentinel 或 Spring Cloud Circuit Breaker。一旦监控到数据库响应变慢，立刻开启**限流**，每天只放行 20% 的核心请求，其余请求直接走**降级**（比如返回“服务器拥挤，请稍后再试”或走静态兜底数据）。宁可让部分用户体验受损，也要死死保住数据库不宕机。

## 击穿引起雪崩

缓存击穿会引起服务雪崩。

1.触发： 热点key过期 没做互斥锁 缓存击穿

2.蔓延 请求到达mysql 连接池打满 并且mysql宕机

3.灾难 不仅热key请求卡死 所有有关db的业务都报错 

**缓存雪崩 (Cache Avalanche)：** 侧重于描述**缓存层**发生的大面积灾难（大面积 Key 同时过期，或者 Redis 集群宕机）。它是“起因”。

**服务雪崩 (Service Avalanche)：** 侧重于描述你说的**系统全面瘫痪**（MySQL 挂了，导致服务 A 挂了，接着调用服务 A 的服务 B 也挂了，最终整个微服务链条全线崩溃）。它是“结果”
