

HTTPS = HTTP + TLS：先用TLS保证安全通道，再传输 HTTP 数据。



## RSA密钥交换

当客户端浏览器要请求服务端域名的时候。流程为：

1. 服务器发送证书 证书中包含RSA公钥
2. 客户端验证证书 
3. 证书如果合法 也就是符合CA和服务端私钥签名 就生成一个随机密钥 用于对称加密
4. 然后用RSA公钥 也就是锁 堆随机密钥加密
5. 服务器用私钥解密
6. 双方基于这个密钥 双向传递http数据。

### 问题

没有前向安全性。 

就算攻击者现在无法解密https 但是它只需要把所有密文都保存下来。

某一天以后 偷到了RSA私钥 就可以解密出当时客户端传的随机密钥 用密钥就可以解密出所有数据。 

所以私钥一旦泄漏 就会导致过去的信息可能被解密。

## ECDHE

现代TLS不直接传输对称加密的密钥。

而是 相互提供临时参数 双方在本地计算 得到共同的秘密。 根据共同的秘密 派生出对称加密的密钥。

就算服务器私钥被获取 也无法根据旧流量 恢复过去的对称加密密钥。

所以现代TLS 服务器私钥主要用于签名 堆本次证书进行签名。 保证了证书没有被修改。所以ECDHE 协商会话密钥

## TLS 握手做了什么

以现代 TLS 1.3 为例，可以简化为四步

1. 客户端向服务端提供临时密钥参数
2. 服务端 选择参数 返回临时密钥参数 证书 和数字签名
3. 客户端验证证书和签名 确认服务器身份
4. 双方通过ECHDE计算出对称加密的密钥

保证了密钥不会在网络传输握手完成后，双方使用会话密钥进行高速的对称加密通信。

## HTTP 与 HTTPS 对比

| 对比项 | HTTP | HTTPS |
|---|---|---|
| 传输方式 | 明文 | TLS 加密传输 |
| 身份认证 | 没有 | 通过数字证书认证服务器 |
| 完整性保护 | 没有 | 能检测数据篡改 |
| 默认端口 | 80 | 443 |
| 建连成本 | TCP 握手 | TCP 握手 + TLS 握手 |

## 总结

> HTTPS 使用证书和数字签名认证服务器，通过 ECDHE 协商会话密钥，再使用对称加密保护 HTTP 数据的机密性与完整性，从而防止窃听、篡改和大多数中间人攻击。
