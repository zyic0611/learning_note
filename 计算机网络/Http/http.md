

http的特点就是无状态  协议本身不会保存状态

所以发明了 cookie 和session 每次发送http请求 都会在请求头【header里加入cookie 相当于是身份证。

但是cookie不是每次请求都要携带 有条件的。





http1.0:

默认使用短连接 

问题：每次发送一个http请求 都必须tcp三次握手 请求完毕都得四次挥手断开连接

如果网页里有100张图片 就必须经历100次tcp握手 网络开销大



http1.1:

引入了长连接 只要建立了一次tcp三次握手 就可以在这个连接上发送多个http请求  节省了握手时间

问题： 队头堵塞 服务器按照请求顺序返回响应 如果第一个请求很慢 后面的小请求也必须阻塞等待 整个通道卡死



http2.0:

1. 引入了多路复用 在一个tcp连接上 并发多个http请求 和响应
1. 但是多个stream 共享一个TCP连接 一旦TCP发生丢包 所有Stream都可能等待重传
2. 二进制分帧 把数据打碎成了很多小的二进制帧 并且打上Stream ID 交替写入TPC字节流  浏览器收到后 再根据编号拼接 消灭了http层的队头阻塞
3. 头部压缩  之前每次请求头部都带几百字节重复的cookie和header  客户端和服务端共同维护一个表 用索引等编码 压缩重复请求头 这样只需要发送压缩后的就行



http3.0:

抛弃了TCP

TCP的问题：绝对保证顺序 底层网络丢了一个包 TCP协议栈就会强制把后面的数据扣下 等待丢失的包重传 意思就是 TCP层丢了一个包 http2.0所有并发的请求都卡死

HTTP/3 基于 UDP 上的 QUIC。QUIC 在用户态实现可靠传输、拥塞控制和 TLS 加密。不同 Stream 独立处理丢包，从而解决 TCP 队头阻塞。



总结： 1.0解决通信 1.1复用连接 引入长连接 2 并发复用stream 3 用QUIC解决stream的TCP队头阻塞。
