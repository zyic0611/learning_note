# DDH Multi-Agent 智能助手平台 — 技术文档

> 本文档基于项目内部设计文档（`docs/` 目录）与源码审计报告重新整理，技术论断以代码实现为准，设计文档仅作为补充说明。

## 一、项目概述

DDH（Data-Driven Hardware）Multi-Agent 是面向汽车芯片硬件团队（ADCU 部门）的企业级多入口 AI 助手平台。系统以 **Claude Agent SDK** 为底层运行时，构建了"意图路由 + 专家并行"的多 Agent 架构，接入 4 个飞书机器人与 Web 端两条入口，覆盖器件硬件设计（CHD）、硬件项目交付管理（HPD）、测试验证（HTV）、通用问答（General）四大业务域，并在 HPD 域上实现了一套支持全局知识库与用户级临时文档融合检索的 **Agentic RAG** 系统。

项目由本人主导完成的核心工作包括：**用户级临时 PDF 上传全链路**（上传/解析/建索引/检索/删除的完整生命周期管理）、**飞书与 Web 双入口统一执行链**、**基于 ContextVar 的用户身份隔离机制**、**混合检索与多轮 Agentic 检索策略**、**文档状态机与并发安全设计**，并配套 111 个单元测试覆盖关键路径。

## 二、技术栈

| 层级 | 技术选型 |
|------|---------|
| AI 运行时 | Claude Agent SDK（`claude-agent-sdk`）、Anthropic API（`claude-sonnet-4-6`） |
| MCP 协议 | 本地 stdio MCP Server（`create_sdk_mcp_server`） + 远端 HTTP MCP Server（项目/风险/OKR API、联网搜索） |

| RAG 检索 | Docling（PDF 解析+VLM 图片描述）、BAAI/bge-m3（向量嵌入）、ChromaDB（向量库）、rank_bm25（稀疏检索）、RRF 融合排序 |
| 结构化查询 | SQLite（表格参数库 `table_facts`/`table_cells`、文档目录状态机） |

| 鉴权 | Keycloak OAuth2（Authorization Code Flow）、飞书 Device Flow |
| 基础设施 | Docker + docker-compose、asyncio 单事件循环、Python 3.11 |

## 三、系统架构

### 3.1 总体架构

```
用户接入层：飞书 P2P/群聊(@机器人) + Web/HTTP API
        ↓
接入与路由层：WebSocket 长连接管理，多个飞书 Bot 共用单一事件循环
        ↓
智能路由层 — LeadAgent（DDH 机器人）
  ├─ 关键词快速路由：零 AI 开销，毫秒级响应
  ├─ AI 智能路由：复杂/跨域任务，输出结构化 JSON 路由指令
  └─ Python 层确定性分发（非 AI 执行）→ 任务并行调度
        ↓
专家 Agent 层（各自独立 SDK query() 会话，工具权限物理隔离）
  ├─ CHD Agent — 器件硬件设计专家（本地 Datasheet 解析 + 五维度评分）
  ├─ HPD Agent — 硬件项目交付专家（项目管理 + 飞书生态 + Agentic RAG）
  ├─ HTV Agent — 测试验证专家
  └─ General Agent — 通用兜底（无独立机器人身份，借用发起方身份回复）
        ↓
基础设施层：LLM Gateway、Redis 会话存储、飞书生态 MCP、Delivery Center API
```

四个飞书机器人（DDH/CHD/HPD/HTV）中，DDH 是路由入口，用户消息先经 LeadAgent 理解意图再确定性分发；CHD/HPD/HTV 三个专家机器人被 @ 提及时则直接进入各自专家 Agent，无需二次路由。

### 3.2 设计核心原则

| 原则 | 说明 |
|------|------|
| LeadAgent 零业务工具 | LeadAgent 的 `allowed_tools=[]`，不持有任何数据库/飞书操作能力，只输出路由 JSON |
| 子 Agent 工具最小化 | CHD 只有硬件工具，HPD 只有项目+RAG工具，权限物理隔离，不是靠 Prompt 约束 |
| 默认上下文隔离 | 每个子 Agent 独立会话（`resume=session_id`）、独立工具集，互不污染 |
| 显式共享 | 需要共享的资源（LLM Client、Redis 连接池）必须显式 opt-in，不隐式复用 |
| 失败关闭 | 子 Agent 失败不拖垮主流程，向上返回错误结果供 LeadAgent/上层决策，而非崩溃 |
| 文件系统是大脑 | 业务知识（评分规则、操作指南）以 `SKILL.md` 文件存储并按需懒加载，不硬编码进 Prompt 常驻 |

这套原则的落地方式是**用 Python 代码做确定性路由分发，而非依赖 SDK 内置的 Agent 工具调用**。这是本项目相对于"单体 Agent 全部工具塞一起"或"依赖 LLM 自主决定调用哪个子 Agent"的关键架构选择：LeadAgent 输出结构化 JSON 路由指令后，由 Python 层的 `agents/router.py` 做 BFS 拓扑分层调度——同层任务 `asyncio.gather` 并行执行，有依赖关系的任务串行执行并把前置结果注入 context，整个路由过程不依赖 LLM 二次判断，避免了模型可能出现的路由幻觉。

## 四、核心模块能力

### 4.1 LeadAgent — 中枢路由大脑

- **关键词快速路由**：识别"器件/芯片/datasheet"等关键词直接分发 CHD，识别"项目/OKR/飞书"等分发 HPD，命中时完全跳过 LLM 调用，零延迟响应
- **AI 智能路由**：意图模糊或跨域请求时，才发起一次 `allowed_tools=[]`、`max_turns=3` 的纯 LLM 调用，输出结构化 JSON 路由计划（`{"tasks":[{"to_agent":..., "task":...}], "parallel": true}`）
- **并行任务调度**：同一条消息可以同时拆解给多个专家并行处理（如"查器件评分 + 看项目风险"），各专家独立执行，最终耗时取决于最慢的专家而非累加
- LeadAgent 本身完全无状态，不保存对话历史，多轮记忆完全交给各子 Agent 自行维护

### 4.2 CHD Agent — 器件硬件设计专家

聚焦本地 PDF 数据手册解析与五维度器件评分：
- **数据手册解析**：本地 Datasheet 库文件名/目录匹配（`glob` + 型号规范化正则），定位到对应 PDF 后用 PyMuPDF 子进程提取文本/图片
- **五维度评分**：性能匹配度、认证完整性（AEC-Q/ISO26262）、成本优势、供应链稳定性、项目时间窗口，输出结构化评分报告
- **器件对比推荐**：多器件并行评分后表格对比，给出推荐结论
- 之所以不需要 Agentic RAG：CHD 面对的是"型号→文件"的确定性查找问题，文件系统目录结构本身就是现成索引，glob 匹配足够，不存在检索质量不确定性，因此没有引入向量检索或迭代改写机制

### 4.3 HPD Agent — 硬件项目交付专家（系统最复杂节点）

- **项目管理查询**：项目进度、OKR 完成度、风险列表、质量准出计划，通过远端 MCP 直连 Delivery Center API
- **飞书生态全操作**：文档创建/追加/搜索、Wiki 读取、云盘、日历、任务、会议，支持以用户真实身份或机器人身份执行
- **Agentic RAG 知识检索**：详见第五章
- **HSI 自动化流水线**：驱动 Allegro 网表解析、Excel 模板填充、飞书上传、染色校验等硬件自动化脚本
- **审批网关**：高风险写操作（如量产问题单创建）需人工在飞书卡片上确认后才真正执行
- `max_turns=100`，是所有子 Agent 中轮次上限最高的，用于支撑复杂多步骤流水线任务

### 4.4 HTV Agent — 测试验证专家

结构与 CHD 类似（`max_turns=15`），通过远端 MCP 对接 HTV 业务 API，同样具备飞书生态操作能力，但不涉及 RAG。

### 4.5 General Agent — 通用兜底

不是独立机器人身份，而是被 CHD/HPD/HTV/Lead 共用的兜底逻辑层，承接三类场景：
1. LeadAgent 路由判断为非专业域的请求（闲聊、天气、新闻）
2. 专家 Agent 主动判定超出能力范围时吐出 `__GENERAL_FALLBACK__` 哨兵
3. 专家 Agent 运行异常时的兜底转接
4. 飞书群聊消息分析与摘要生成（接入火山引擎联网搜索）

任何专家 Agent 故障都不会让用户看到技术报错：哨兵机制 → 自动转 General → 固定友好文案，三层兜底保障体验；网络抖动导致的 Session 失效会自动清除重试一次，用户无感知。

## 五、Agentic RAG 知识库系统

### 5.1 设计理念：为什么是"Agentic"而不是固定流水线

HPD 面对的是"项目文档/Datasheet 里写了什么内容"这类语义层面的自然语言问题，必须把文档切成语义片段建立向量+关键词混合索引，天然存在召回率和排序质量的不确定性。因此设计上没有做成"查一次、直接用结果生成答案"的固定 RAG Pipeline，而是把**检索封装成 Agent 可反复调用、按结果质量动态调整的工具**，检索策略、改写重试逻辑完全由 Agent 在 ReAct 循环中自主驱动：

| 维度 | 固定 RAG Pipeline | 本项目 Agentic RAG |
|------|-------|-------|
| 检索策略 | 查一次，用结果直接生成 | Agent 自主决定查几次、怎么改写查询 |
| 结果不好时 | 直接输出或拒答 | 分析原因（词汇不匹配/范围过窄），改写重试 |
| 工具选择 | 路由规则预先决定 | ReAct 循环中实时决策（语义检索 vs 表格精确查） |
| 置信度 | 不透传 | `rrf_score` + `no_answer_guard` 信号驱动决策 |

核心转变：不引入额外的 Agent 框架或 Query Router 代码模块，而是让 Claude Agent SDK 原生的 ReAct 循环本身承载这套"评估-重试"逻辑，业务决策树完全写在 `SKILL.md` 里，由模型在对话中自主读取遵循。

### 5.2 离线构建管线

一键脚本 `build_index.sh` 串起三步，把非结构化 PDF 转成两种可检索形态：

**Step 1 — Docling 解析 PDF → blocks**：解析成有序 `text`/`table`/`image` 三类 block；可选开启 VLM（Claude）对内嵌图片生成中文描述，描述文字写入 block 正文使图片也能被语义检索命中。

**Step 2 — 分块 + 建索引 → chunks.pkl + ChromaDB**：
- **标题路径回填**：按文档/页顺序维护"页面祖先标题 + 当前小节标题"，拼成 `title_path`，解决同页多级标题互相覆盖导致上下文丢失的问题
- **长表格切分**：超过 token 阈值的表格按 `<tr>` 行边界拆分为多个 part，每片重复表头，不破坏行完整性
- **产物字段**：每个 chunk 含 `chunk_id/doc_id/file_name/page_num/chunk_type/section_title/title_path/text/image_path`
- 用 `BAAI/bge-m3` 对 `searchable_text` 编码写入 ChromaDB 持久化 Collection

**Step 3 — 表格参数结构化库 → SQLite**：把 Datasheet 里"型号 × 参数"表格转成两张可精确查询的表——`table_facts`（型号-参数事实，主查询）和 `table_cells`（全量单元格兜底）。型号列识别用正则统计命中率（≥60% 判定为型号列），参数名通过 `parameter_norm` 归一化（如"额定电流/rated current/current rating"统一映射到 `rated_current`），解决中英文别名不一致问题。

离线解析全程配置为离线模式（`TRANSFORMERS_OFFLINE=1`、HF 镜像、本地模型缓存路径），避免生产环境无外网时构建失败。

### 5.3 在线混合检索引擎

`rag/retriever.py` 职责边界严格：只做在线检索，不重复解析、不写索引。

```
查询 query
├─ 同义词扩展（rated current ↔ idc ↔ 额定电流）
├─ BM25 排序（现场内存构建，不落盘）─┐
├─ BGE-M3 dense 排序（ChromaDB 查询）─┼─ RRF(k=60) 融合
├─ 型号精确/前缀命中加权，纯表头零头块降权
└─ 按 rrf_score 降序 → 可选 doc_filter 过滤 → 返回 top_k
```

**no-answer 守护**（`is_no_answer`）：强规则——查询点名了具体型号/实体但全库找不到，判定"查无此物"；弱规则——BM25 top1 精确匹配分低于阈值（8.0），同样判定。命中守护时即便有 chunks 返回，也会标记 `no_answer_guard=true`，交给 Agent 决定改写还是如实拒答，不会用不相关结果硬答。

**单例加载与优雅降级**：`get_retriever()` 进程内单例 + 线程锁，避免重复加载耗时的向量模型；重依赖（`chromadb`/`sentence_transformers`/`rank_bm25`）延迟到函数内导入，模块导入本身不因缺依赖失败；轻量 `readiness()` 探活支持在正式检索前判断依赖/索引是否就绪，返回结构化降级响应而非抛异常。

### 5.4 Agent 接入与迭代检索决策树

检索能力通过本地 MCP Server `hpd-tools` 注册为两个工具，与远程业务 MCP 并列挂载：

| 工具 | 用途 | 关键返回字段 |
|------|------|------|
| `rag_search` | 语义检索（主路径） | `available`/`found`/`no_answer_guard`/`top_rrf_score`/`chunks[]` |
| `rag_sql_query` | 表格参数精确查/反查型号（补充路径） | 精确查 `table_facts`；反查将自然语言条件解析为 `(参数, 运算符, 值)` 拼 SQL（白名单过滤防注入） |

两个工具之间**没有代码层的 Query Router**——路由决策 100% 交给 LLM，依据是 `datasheet-rag/SKILL.md` 定义的迭代检索决策树：

1. **边界判断**：文档正文内容问题走 `rag_search`；结构化字段（OKR/风险/负责人）走项目 API 工具，不走 RAG
2. **每轮必评估**：拿到 chunks 后 LLM 自行判断是否真支撑问题，警惕大表格块靠体量堆高 `rrf_score` 却不含答案
3. **`top_rrf_score` 阈值驱动**：>0.02 进入充分性评估；0.01~0.02 偏低，即使可答也要标注置信度较低；<0.01 大概率词汇不匹配，改写重试
4. **迭代纪律**：`rag_search` 总调用 ≤5 次，达上限立即停止、如实告知，不编造答案
5. **回答规范**：强制来源归因 `(文档 doc_id, 第 N 页)`，命中图片 chunk 时必须附图展示

对于"对比两个项目质量准出差异"这类多跳查询，Agent 会先规划检索步骤，每步检索后只在思考链中保留"子问题+结论+来源"，不把整段原文带入后续轮次，控制 token 消耗在有限 `max_turns` 内完成多跳推理。

### 5.5 用户级临时文档 RAG（HPD Agent Harness）

原有 HPD Agent 只能检索预置的 10 份全局 Datasheet，本人主导设计并实现了让用户在飞书和 Web 两个入口上传自己的临时 PDF，与团队共享知识库融合检索，同时保证多用户数据互不可见。

**身份隔离（LLM 物理不可伪造）**：`current_owner_id` 是请求级 `ContextVar`，唯一写入点在 `HpdAgent._run_inner()`（`try/finally` 保证 `reset`），`rag_search` 的工具 Schema **不声明 `owner_id` 参数**——LLM 在工具调用参数里根本没有这个字段可以填，从物理层面杜绝越权检索。真正的 owner 授权执行点在 `rag/catalog.py` 的 SQL `WHERE owner_id=?` 查询，而不是 ContextVar 本身（ContextVar 只是把值从入口搬运到工具函数，不做判断）。

**混合检索融合**：`search_merged(query, owner_id, top_k, doc_filter)` 不是索引层合并，而是"多路独立检索 + 结果层合并重排"——全局库走标准 `Retriever`，用户每份 `ready` 状态的上传文档各自构造一个独立 `Retriever`（复用全局单例的 BGE-M3 模型对象避免重复加载），所有路的 `(chunk, rrf_score)` 塞进同一列表按分数统一排序。个人库命中时不受全局库 `no_answer_guard` 拖累——即便全局库判定"查无此物"，只要用户自己的文档有命中就能正常回答。

**文档生命周期状态机（9 态 + CAS 乐观锁）**：

```
queued → downloading → parsing → describing → indexing → ready
  ↓         ↓             ↓          ↓            ↓
 failed ←───┴─────────────┴──────────┴────────────┘
  ↓ (同sha重传requeue)
queued
ready → expired（到期）
{queued, ready, failed} → deleted（终态，用户主动删除）
```

核心防复活机制：`catalog.compare_and_set_status(doc_id, expected_status, new_status)` 用 `UPDATE ... WHERE doc_id=? AND status=?` 做乐观锁。用户删除文档后状态被置为 `deleted`（除自身外任何状态都可迁入的终态），异步解析流水线下一步 CAS 时 `expected_status` 与实际值不匹配，`rowcount=0` 触发中止并清理已生成产物，绝不会把已删除文档重新写回 `ready`。`reserve_upload` 用 `BEGIN IMMEDIATE` 把"SHA256 去重 + 每用户最多 2 份上传上限校验 + 插入排队记录"合并进单事务，避免并发绕过上限。

**引用治理**：上传文档磁盘统一落盘为 `source.pdf`，但 chunk 元数据里原始记录的也是这个内部文件名——`rag_search` 返回给 Agent 前，用 catalog 记录的真实 `file_name`/`doc_id` 覆盖 chunk 自身取值，保证引用展示的是用户上传时的原始文件名而非内部落盘名（这是一个真实修复过的 bug：`fix(rag): preserve original upload filename in citations`）。图片访问 `GET /web-docs/{doc_id}/images/{image_id}` 做身份+状态+路径穿越三重校验（`real_path.is_relative_to(imgs_dir)`），且只暴露文件名给 LLM，不透传服务器绝对路径。

**双入口统一执行链**：飞书私聊/群聊 @机器人 或 Web 悬浮窗上传 PDF，两条路径最终都进入同一个 `HpdAgent.run()`，身份来源不同（飞书 `sender_id.open_id` 不经 LLM 解析 / Web `Authorization: Bearer` → Keycloak userinfo 在线校验得到 `web:{sub}`），但执行链、检索逻辑、多轮记忆完全复用同一套代码，解决了此前"同一问题在不同入口得到不一致答案"的问题。

**Web 端一次性问答验证**：`query_service.py` 提供无状态、无工具、`max_turns=3` 的轻量问答服务，强制模型输出结构化 `{"answerable": bool, "answer": str}`，来源（`sources`）由后端代码基于检索元数据拼装而非让模型自由生成，避免编造页码/文件名。

## 六、隔离与安全机制

### 6.1 四维隔离机制

| 维度 | 实现方式 |
|------|---------|
| 知识隔离 | 每个 Agent 的 System Prompt 各自独立加载，互不感知彼此的业务规则 |
| 工具隔离 | 物理限定 `allowed_tools` 列表（如 CHD 只有 `datasheet_search/extract`，HPD 才有 RAG 与 Skill/Bash/Read），不依赖 AI 自律 |
| 会话隔离 | 群聊内按 `open_id` 分隔 session_key，同一群内不同用户对话历史完全独立存储 |
| 并发隔离 | 同用户消息串行（`asyncio.Lock`）保序，不同用户完全并行，互不阻塞 |

四维隔离均在代码层面物理实现，不依赖 AI 自律或 Prompt 约束。

### 6.2 双系统鉴权机制

系统同时维护两套独立鉴权，服务不同场景：

| 鉴权体系 | 用途 | Token 存储 | 自动续期 |
|---------|------|-----------|---------|
| 飞书 Device Flow | 操作飞书文档/云盘/Wiki | 服务器本地文件（`lark-users/{open_id}/`） | 不支持，过期需重新走流程 |
| Keycloak OAuth2（Authorization Code Flow） | 调用 Delivery Center 项目管理 API | Redis（`keycloak:token:{union_id}`） | 剩余不足 1 天自动 refresh，30 天内用户无需重复授权 |

飞书授权流程：用户触发写操作 → Bot 调 `lark-cli auth login --no-wait` 拿到 `verification_url` + `device_code` → 发授权链接给用户 → 用户扫码完成授权 → Bot 静默检测授权完成 → **自动重放之前挂起的任务**，用户点一次链接后续操作无感知。Keycloak 流程走标准 Authorization Code Flow，回调换取 access+refresh token 存入 Redis。

### 6.3 敏感操作审批网关

对高风险写操作（如量产问题单创建）实现"预览 → 人工确认 → 执行"的挂起流，基于 SDK `PreToolUse` Hook：首次调用 `defer`（暂停执行），生成预览卡片推送到飞书，用户点击"确认/取消"后写入 Redis，`resume` 同一 SDK session 恢复执行，Hook 根据 Redis 结果 allow/deny。整个过程无需重放之前已完成的 ReAct 步骤，对用户透明。

### 6.4 命令执行白名单

所有 Agent 的 Bash 工具通过 `PreToolUse` Hook 物理拦截：
- 允许 `lark-cli <任意子命令>`（含用户身份前缀 `LARKSUITE_CLI_CONFIG_DIR=...`）
- 禁止 `lark-cli auth ...` / `lark-cli config ...`（鉴权配置由系统层管理，AI 不得干预）
- 禁止所有其他 Shell 命令（`ls`/`cat`/`python` 等），违反即拒绝执行
- HPD 额外白名单 HSI 工作目录下的 `python3 scripts/<白名单脚本>.py`，且检测危险字符（`;`、`|`、反引号、`$()`、`&`）
- Cron 相关工具（`CronCreate`/`CronDelete`/`CronList`/`ScheduleWakeup`）全局禁用，统一改用业务自研的 `set_reminder`

安全边界在代码层面落地，不依赖 Prompt 约束模型自觉遵守。

## 七、并发与容错

### 7.1 三层并发控制

- **第一层 全局限流**：每个 Agent 独立 `Semaphore(5)`，超出自动排队，避免并发过高压垮 LLM 网关
- **第二层 用户级串行锁**：同一用户快速连发消息时排队串行执行，保证会话文件不被并发写入损坏
- **第三层 跨 Agent 并行**：不同用户、不同 Agent 完全并行；LeadAgent 调度多个专家时也并行执行，总耗时取决于最慢的专家而非累加

### 7.2 超时与降级

各 Agent 设置独立超时（HPD 1800 秒最长，支持复杂 HSI 流水线；CHD/HTV/General 3-5 分钟），超时后移除思考态、回复友好提示，不暴露技术细节。任何子 Agent 异常都会自动转交 General Agent 兜底，兜底也失败才返回固定友好文案，用户永远看不到技术报错。Session 失效（网络抖动/服务重启后旧 session_id 失效）会被自动检测、清除后重试一次，重试成功用户无感知。

### 7.3 会话与记忆分层

会话记忆（Redis 存 SDK `session_id`，TTL 7 天，SDK 自管 JSONL 历史）与业务知识（`SKILL.md`，服务启动时读入内存缓存，修改后需重启生效）是两套本质不同的机制——前者随对话动态积累会自动过期清除，后者是静态配置随代码版本管理。每个用户、每个 Agent、每种场景（P2P/群聊）的 session key 互相独立，杜绝群聊场景下多用户上下文互相污染。

## 九、技术亮点

**① 确定性路由替代 LLM 自主调度**：路由分发在 Python 层硬编码完成，未知 `to_agent` 直接报错不 fallback，杜绝了让 LLM 自主决定调用哪个子 Agent可能引入的路由幻觉与权限逃逸风险。

**② ContextVar 实现 LLM 物理不可伪造的身份隔离**：`rag_search` 工具 Schema 不声明 `owner_id` 参数，用户身份通过请求级 `ContextVar` 传递而非函数参数——LLM 在工具调用层面根本没有篡改身份的入口，这是比"信任 LLM 传入正确参数再校验"更强的安全设计。

**③ Agentic RAG：检索质量信号驱动的自主迭代**：不引入额外 Query Router 模块，而是把 `rrf_score`/`no_answer_guard` 透传给 Agent，由 SKILL.md 定义的决策树驱动模型自主判断"要不要改写查询重试"，在有限调用次数（≤5 次）内平衡准确率与成本。

**④ CAS 乐观锁防止异步任务复活已删除资源**：文档生命周期状态机用 `UPDATE ... WHERE doc_id=? AND status=?` 做版本校验，异步解析流水线的每一步推进前都做 CAS 校验，用户删除文档后任何仍在跑的后台步骤都会因状态不匹配而自动中止，不会产生"已删除但仍可查到"的数据不一致。

**⑤ 双入口统一执行链**：飞书机器人与 Web 悬浮窗两个前端入口最终复用同一个 `HpdAgent` 类与 SDK 工具循环，避免了"同一问题不同入口给出不一致答案"的常见多入口架构缺陷。

**⑥ 引用治理与图片访问防护**：来源文件名以数据库记录覆盖磁盘内部落盘名，保证用户看到的引用是自己上传时的原始文件名；图片访问接口做身份+状态+路径穿越三重校验，防止跨用户访问与目录穿越攻击。

**⑦ 离线优先的生产可靠性设计**：Docling 解析与 BGE-M3 嵌入模型全程配置离线模式，解决生产环境无外网导致解析失败的真实问题（对应真实修复记录 `c1ecd3b`/`799716f`）。
