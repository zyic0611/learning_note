# DDH Multi-Agent 业务背景与案例说明

## 背景：这是什么公司、什么团队

这是一家自动驾驶公司（Momenta），团队是负责**车载计算单元（ADCU）的硬件部门**。他们的日常工作是：选芯片、设计硬件电路板、管理项目进度、做硬件测试。

团队成员大概这样分工：**硬件工程师**选芯片做设计，**项目经理**跟进交付进度，**测试工程师**做硬件验证。DDH Multi-Agent 平台就是给这三类岗位都用的 AI 助手，接在飞书机器人和 Web 悬浮窗上，每天有百余名工程师在用。

---

## 四个子 Agent 各负责什么

### CHD Agent — 器件硬件设计专家

**服务对象：硬件工程师**

硬件工程师每天要做的事之一：给某个功能模块选一颗合适的芯片或电子元器件（电容、电感、MCU 等）。选型流程很繁琐——要找到这个器件的规格书（Datasheet PDF），看懂里面密密麻麻的技术参数，再判断它是否符合车规要求（比如 AEC-Q 认证、-40°C 到 125°C 工作温度、能不能稳定量产供货）。

以前这个流程要工程师自己下载 PDF、翻找参数、对照车规标准逐项核查，一颗器件评估下来要花不少时间。

**用户会问的典型问题：**

| 场景 | 示例问题 |
|------|---------|
| 查参数 | "帮我查一下 MCU-NXP-S32K344 的工作电压范围和工作温度" |
| 查规格 | "LQG15HH 系列电感的额定电流和自谐振频率是多少？" |
| 器件评估 | "帮我评估这颗电容，看看车规认证和供应链情况怎么样" |
| 器件对比 | "这两颗 MCU 哪个更适合我们项目，帮我对比一下" |
| 评分报告 | "给 MCU-NXP-S32K344 出一份五维度评分报告" |

**CHD Agent 怎么做到的：**
本地存了一批 Datasheet PDF，接到问题后去文件库找到对应 PDF，用 PyMuPDF 提取相关页面内容，然后按**五个维度**（性能匹配度、车规认证、成本优势、供应链稳定性、项目时间窗口）给出评分和推荐结论。

### HPD Agent — 硬件项目交付专家

**服务对象：项目经理 + 技术负责人 + 所有需要操作飞书的用户**

这是整个系统里功能最复杂的 Agent，对应三类完全不同的日常工作：

#### 场景一：项目管理数据查询

ADCU 部门同时在推进多个车型项目（比如 ADCU-MBv3、ADCU-MBv4），每个项目都有进度报告、OKR、风险列表、质量准出计划。这些数据存在公司内部的 Delivery Center 项目管理系统里，以前要打开浏览器登录系统才能查。

**用户会问的典型问题：**
- "ADCU-MBv3 项目现在 OKR 完成度怎么样？"
- "上周新增了哪些风险项，责任人是谁？"
- "这个项目的质量准出计划里，硬件验证部分还有哪些没完成？"
- "量产阶段有没有未关闭的问题单？"

#### 场景二：飞书生态操作

硬件部门的日常协作高度依赖飞书——文档、云盘、Wiki、日历、任务、会议都在飞书上。工程师经常需要在几个场景之间切换，比如开完项目会议马上要把纪要写进 Wiki，还要在任务系统里给相关人创建跟进任务。

**用户会问的典型问题：**
- "帮我把这份测试报告上传到飞书云盘的 ADCU-MBv3 目录下"
- "帮我在 Wiki 里建一个页面，整理一下今天的评审会结论"
- "帮我给张三发消息，告诉他风险评审会改到周五下午两点"
- "帮我在飞书上创建日程，下周三 15:00，拉上项目组所有人"
- "帮我把这个 Excel 表格的数据写入飞书多维表格"

#### 场景三：文档内容检索问答（RAG）

工程师手上经常有一些临时收到的规格书、供应商报告、项目文档，想快速从里面找到某个具体信息，但 PDF 动辄几十上百页，人工翻阅效率极低。

**用户会问的典型问题：**
- "我刚上传的这个供应商 PDF，里面写的存储温度范围是多少？"
- "根据项目文档，ADCU-MBv3 的硬件验证流程是怎样的？"
- "这份接口规格书里，SPI 总线的最大时钟频率是多少？"
- "帮我从这个 Datasheet 里找一下额定电流超过 500mA 的型号有哪些？"

**HPD Agent 怎么做到的：**
后台同时连接三套系统：Delivery Center 项目管理 API（查项目数据）、lark-cli 飞书命令行工具（代用户操作飞书）、RAG 知识库（检索文档内容）。用户说什么类型的问题，Agent 在 ReAct 循环里自主判断调用哪个工具。

---

### HTV Agent — 测试验证专家

**服务对象：测试工程师**

硬件测试工程师的日常：对硬件板子做各类验证测试（EMC 电磁兼容、电气特性、环境可靠性、协议兼容性），在内部测试系统里管理测试用例和问题单，跟踪测试进展。

**用户会问的典型问题：**
- "ADCU-MBv3 的 EMC 测试现在进展怎么样？"
- "这个版本有哪些测试项还没通过？"
- "帮我在飞书上创建一个测试问题单，关联到 MBv3 项目"
- "上周提交的测试报告审批状态怎么样了？"

**HTV Agent 怎么做到的：**
连接内部 HTV 测试管理系统 API，同样具备飞书生态操作能力。HTV 和 HPD 用的是不同的业务系统，所以是独立的 Agent，工具权限互相隔离，不会误操作对方的数据。

---

### General Agent — 通用兜底

**服务对象：所有用户（处理前三个 Agent 都不擅长的问题）**

不是独立机器人，是一个"接盘侠"角色。当用户的问题明显跟硬件选型、项目管理、测试验证都没关系时，就交给它。也负责飞书群聊消息的提取和知识整理。

**用户会问的典型问题：**
- "今天深圳天气怎么样？"
- "帮我把这段技术描述翻译成英文"
- "上午群里讨论了什么，帮我总结一下关键结论"
- "帮我把这次评审会的讨论内容整理成一篇会议纪要，发到 Wiki 上"

**General Agent 怎么做到的：**
接入了火山引擎联网搜索能力（查实时信息），以及飞书群聊消息读取和飞书文档写入能力。

## 一个完整的用户对话场景

### 场景：跨域复合请求（体现多 Agent 并行调度的价值）

> 用户在飞书群里 @DDH机器人：  
> **"帮我查一下 S32K344 的工作电压，另外看看 ADCU-MBv3 项目最近有没有新增风险"**

**系统内部发生了什么：**

```
用户消息
  ↓
LeadAgent 识别出两个问题：
  ├─ "S32K344 工作电压" → 器件参数查询 → 分配给 CHD Agent
  └─ "ADCU-MBv3 新增风险" → 项目管理查询 → 分配给 HPD Agent
  ↓
Python 路由层同时启动两个 Agent（asyncio 并行）
  ├─ CHD Agent：查本地 Datasheet 文件 → 提取参数 → 返回结果
  └─ HPD Agent：调 Delivery Center API → 查风险列表 → 返回结果
  ↓
LeadAgent 汇总两个结果 → 整合成一条完整回复 → 发给用户
```

**用户感受到的：** 发一条消息，几秒内同时得到两个方向的答案。

**如果没有多 Agent 并行：** 先查器件（等待），再查项目（等待），总耗时是两个等待的累加。有了并行调度，总耗时只取决于两个 Agent 里较慢那个，速度提升约一倍。

---

### 场景：需要用户鉴权后才能执行的飞书操作

> 用户私聊 HPD 机器人：  
> **"帮我在飞书云盘的 ADCU-MBv3 目录下新建一个文档，标题是《硬件验证报告 v1.0》"**

**系统内部发生了什么：**

```
用户消息 → HPD Agent 判断需要操作飞书（写操作）
  ↓
检查用户的飞书授权状态 → 未授权
  ↓
发送授权引导卡片给用户（包含飞书 Device Flow 授权链接）
  ↓
用户点击链接，手机上完成飞书账号授权
  ↓
系统检测到授权完成，自动重新执行之前挂起的任务
  ↓
以用户自己的飞书身份调用 lark-cli → 创建文档 → 返回文档链接
```

**为什么要以用户自己的身份执行，而不是机器人身份？**  
创建的文档、日历、任务等需要有明确的所有者和操作记录，用机器人身份创建的内容归属不清晰，也无法满足公司审计要求。所以系统要求用户完成飞书 OAuth 授权，后续操作都以用户自己的账号身份执行。

---

### 场景：用户上传 PDF，对内容提问（用户级 RAG）

> 用户私聊 HPD 机器人，发送一个供应商规格书 PDF：  
> **（发送 PDF 文件）"这个传感器的接口协议支持哪些？存储温度范围是多少？"**

**系统内部发生了什么：**

```
用户发送 PDF 文件
  ↓
系统后台异步处理：
  1. Docling 解析 PDF → 提取文字、表格、图片
  2. BGE-M3 嵌入模型 → 把每个文段转成向量
  3. 存入用户专属的 ChromaDB Collection + BM25 索引
  （处理完成后推送状态卡片给用户）
  ↓
用户提问 "接口协议支持哪些？存储温度范围是多少？"
  ↓
HPD Agent 调用 rag_search 工具：
  1. 同时检索全局知识库 + 该用户刚上传的 PDF
  2. BM25 关键词匹配 + BGE-M3 语义匹配 → RRF 融合排名
  3. 评估检索结果质量（rrf_score）：分数高 → 直接作答；分数低 → 改写查询重试
  ↓
生成带来源引用的回答：
  "根据您上传的《供应商规格书》第 12 页：
   接口协议：SPI、I2C、UART（最高 10Mbps）
   存储温度：-55°C 至 +150°C
   来源：[您的文件名.pdf，第 12 页]"
```

**关键点：用户 A 上传的 PDF，用户 B 看不到，也检索不到。** 身份隔离在代码层面实现（不依赖 AI 自律），保证多用户之间数据完全隔离。

### 场景：量产问题单创建（高风险操作审批流）

> 用户对 HPD 机器人说：  
> **"帮我创建一个量产问题单：项目 ADCU-MBv3，问题描述：电源模块在高温环境下电压纹波超标"**

**系统内部发生了什么：**

```
用户发送请求
  ↓
HPD Agent 在 ReAct 循环中决定调用"创建量产问题单"工具
  ↓
系统检测到这是高风险写操作（Hook 拦截）
  ↓
暂停执行，生成问题单预览卡片，推送给用户：
  ┌─────────────────────────────────┐
  │ 即将创建量产问题单              │
  │ 项目：ADCU-MBv3                 │
  │ 问题：电源模块高温电压纹波超标  │
  │ [确认创建]    [取消]            │
  └─────────────────────────────────┘
  ↓
用户点击"确认创建"
  ↓
系统恢复执行，真正创建问题单 → 返回问题单编号和链接
```

**为什么要这一步？** 量产问题单一旦创建会触发一系列下游流程（通知相关方、启动处理流程），写错了回滚成本高。让用户在执行前确认，把误操作的影响降到最低。

## 理解技术选择的出发点

有了上面这些业务背景，技术上的每个选择就有了具体的理由：

| 技术选择 | 对应的业务问题 |
|---------|--------------|
| CHD 用文件 glob 定位 PDF，不用向量检索 | 器件查找是"型号→文件"的确定性映射，文件名本身就是索引，不存在语义模糊性 |
| HPD 用 Agentic RAG + 多轮迭代检索 | 文档内容问答是"自然语言→片段"的语义匹配，召回质量有不确定性，需要 Agent 自主判断是否够用、要不要改写重试 |
| 飞书操作要用用户真实身份（Device Flow） | 文档/任务需要有归属人，机器人账号操作不符合审计要求 |
| 高风险写操作加审批网关 | 量产问题单创建后会触发下游流程，误操作回滚成本高 |
| 用户 A 的 PDF 对用户 B 不可见 | 不同工程师的临时资料（供应商 NDA 文件、未公开规格书）不应该互相泄露 |
| LeadAgent 零工具，路由在 Python 层完成 | AI 做路由决策有幻觉风险，"A 的问题发给 B 去处理"这种路由错误在生产中不可接受，所以路由逻辑用确定性代码实现 |
