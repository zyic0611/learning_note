## 一、主导设计 Multi-Agent 确定性执行架构

**① 简历写法**

> 主导设计 LeadAgent 统一规划、多专家 Agent 协同执行的架构，将任务规划与执行解耦，按依赖关系并行/串行调度、上游失败阻断下游；并在结果聚合前引入仲裁校验，检测跨 Agent 输出矛盾，避免"各自正确、联合冲突"的结论被直接呈现。复杂任务平均耗时由 **60 秒降至 35 秒（降低 42%）**。

**② 深挖准备**

- **核心实现**：LeadAgent 输出的不是图，而是"任务节点 + 依赖关系"的声明式列表（JSON）；服务端把它解析成 DAG，并做 schema 校验 + 环检测 + 引用校验（LLM 可能生成 A→B→A 这类环，不能信任）。调度用 asyncio.TaskGroup 按拓扑排序执行——同层无依赖的节点并行、跨层有依赖的节点串行等待上游输出。节点状态机 PENDING/RUNNING/SUCCESS/FAILED/SKIPPED；节点状态持久化到 PostgreSQL，崩溃后从 checkpoint 断点恢复、已成功节点复用缓存。
- **仲裁校验（跨 Agent 一致性检测）**：多个专家 Agent 的输出可能"局部正确、联合矛盾"——例如选型 Agent 推荐某型号，测试 Agent 同时标记该型号存在已知问题；或项目 Agent 查到的交期与项目截止日期冲突。结果聚合前增加一层仲裁校验，专门检测这类跨 Agent 矛盾；发现矛盾时触发局部 replan，或将矛盾原样呈现给用户由其判断，而不是静默选择其中一个结论、掩盖冲突。
- **幂等怎么落地**：工具调用携带幂等键/自然键，重试不产生重复副作用——这是"写了 retry"和"真 durable"的分界。
- **可观测**：OpenTelemetry 把 LeadAgent/专家 Agent/检索/工具调用统一建模为 span，看关键路径、大模型延迟、token 成本（这条不单列，挂在本条里）。
- **降级链路**：计划生成失败 → 降级单 Agent 直接回答；某专家 Agent 失败 → 阻断下游 + 返回"部分结果"；跨 Agent 输出矛盾 → 触发局部 replan 或原样呈现矛盾，不静默丢弃；成本超限 → 预算熔断降级。
- **必被追问的 5 个点**：
  1. 为什么 Multi-Agent 而不是单 Agent + 一堆工具？→ 异构专家域（选型/项目/测试三套知识域）、状态隔离、可审计的显式计划。
  2. 计划"结构合法但拆解错"怎么办？→ 执行中发现偏离 → 局部 replan。
  3. 用户中途取消/刷新页面？→ 取消传播 + 已执行节点副作用清理。
  4. 成本怎么控？→ 单请求 token/成本预算熔断。
  5. 多个 Agent 输出互相矛盾怎么办？→ 仲裁校验检测冲突，触发局部 replan 或原样呈现给用户，不静默选择其中一个。

## 二、深挖：LeadAgent 怎么把用户请求转成"任务节点 + 依赖关系"的声明式列表

### 1. 输入不只是用户那句话，还有"专家能力清单"

LeadAgent 的上下文里必须包含**专家 Agent 能力清单（capability manifest）**——每个专家 Agent 声明"我是谁、能做什么、需要什么输入、会产出什么"。LeadAgent 只能在清单里存在的 Agent 之间做任务分配，这也是后续服务端能做"引用校验"的前提（计划里出现清单里不存在的 Agent，直接判非法）。

**好处（可扩展性）**：新增一个专家 Agent，只是往清单里注册一条描述，不用改 LeadAgent 的核心逻辑。

### 2. 分解：识别子目标，路由到最合适的专家

第一步是把用户请求拆成若干子目标，每个子目标匹配到清单里能力最贴合的专家——本质是"意图分解 + 路由"，是 LLM 比较擅长的任务。

### 3. 依赖判断的核心标准（真正的难点）

> **判断标准只有一句话：任务 B 需要的输入，是"计划阶段就已知的"，还是"必须等任务 A 真正跑完才知道"？**

- 已知（用户请求里直接给的参数、常量）→ B 不依赖 A，可并行；
- 未知，要等 A 的执行结果（比如具体选中的型号）→ B 依赖 A，必须串行。

### 4. 输出结构：受限结构化输出，不是自由 JSON

LeadAgent 通过 tool-calling / 结构化输出，被**强制**只能吐出符合 schema 的结构——任务字段、agent 枚举值、依赖边格式都在 schema 层面锁死。这一层直接消灭一整类错误（字段名瞎写、结构不完整），比"生成完再校验"更严格。

### 5. 依赖怎么表达：两种设计，推荐更严谨的一种

**方案 A（简单）**：LLM 直接声明 `dependencies: [{from: "A", to: "B"}]` 边列表。缺点：正确性全靠 LLM"自己意识到"该不该连边，容易漏连或瞎连。

**方案 B（更严谨，推荐）**：每个任务声明**符号化的 `produces`（我会产出什么）和 `consumes`（我需要什么）**，依赖边由**服务端匹配 produces/consumes 自动推导**，不由 LLM 直接声明边。

```json
{
  "tasks": [
    {"id": "A", "agent": "selection", "goal": "筛选满足功耗要求的候选型号", "produces": ["selected_part_number"]},
    {"id": "B", "agent": "test",      "goal": "列出该型号需要的测试验证项",  "consumes": ["selected_part_number"]},
    {"id": "C", "agent": "project",   "goal": "查询项目当前进度",          "produces": [], "consumes": []}
  ]
}
```

服务端发现 B 消费的 `selected_part_number` 正好是 A 产出的 → 推导出 `A→B`；C 无消费无生产 → 独立，可并行。

**为什么这个设计更强**：它把"LLM 要不要正确连边"这个易错动作，换成了"LLM 要不要正确描述每个任务的输入输出"——后者更贴近 LLM 描述任务时的自然语言习惯，更不容易漏。而且它带来一个方案 A 做不到的校验：**数据流完整性检查**——如果某任务 `consumes` 了一个占位符，但没有任何上游任务 `produces` 它，也不在用户原始请求里，这就是"缺失依赖/幻觉输入"，可以在执行前直接拒绝或打回重规划。这比单纯的环检测更深一层。

### 6. 具体例子（含依赖 + 并行分支）

用户问："帮我选一个满足项目功耗要求的 MOSFET，告诉我这个项目现在的进度，并列出选出来的型号要做哪些测试。"

```
Task A（selection）：筛选候选型号        —— 不依赖任何任务，参数在原始请求里已知
Task B（test）     ：列出该型号的测试项  —— 依赖 A（要等 A 选出具体型号才知道测什么）
Task C（project）  ：查询项目当前进度    —— 完全独立
```

调度结果：**第一层并行 {A, C}，第二层串行 {B}（等 A 完成）**。

### 7. 这一步的失败模式

| 失败模式 | 描述 | 兜底 |
|---------|------|------|
| **漏依赖** | LLM 忘了 B 其实需要 A 的输出 | produces/consumes 匹配发现 B 消费了一个没人产出的占位符 → 拒绝/重规划 |
| **假依赖** | LLM 过度保守，把不需要串行的任务也串起来了 | 不是正确性问题，是效率问题；可作为质量指标（不必要边比例）持续观测优化 prompt |
| **过度拆分** | 拆出过多细粒度节点，计划失控 | 节点数/拆解深度上限 |
| **循环依赖** | A 依赖 B，B 又依赖 A | 环检测拒绝 |

### 8. 为什么必须是"声明式"，不是 LeadAgent 自己排执行顺序

LeadAgent 只回答"谁需要谁的产出"，**从不**回答"先跑谁、等多久、怎么并行"——那是纯粹的拓扑排序，一个确定性算法，交给服务端做。**LLM 只声明关系，调度逻辑完全在 LLM 能力之外、由代码保证正确**。这正是"规划与执行解耦"在最细颗粒度上的体现。

### 9. 模型选型：这一步该用什么档次的模型

这一步的任务性质是**"结构化任务路由 + 浅层依赖推理"**，不是"深度创造性推理"，选型要按这个性质来判断，不是"越强越好"：

- **不推荐用旗舰级推理模型（如 Opus 档）**：这一步在每个请求的关键路径上都会走一次，用最强模型会显著拖慢首次响应延迟、拉高单请求成本；而且规划任务本身的推理深度需求，远低于专家 Agent 里"复杂选型权衡""长文档理解"这类真正需要深度推理的环节——把预算花在这里性价比低。
- **不推荐用最小档模型（如 Haiku 档）**：结构化输出的可靠性可能没问题，但多步依赖推理、歧义处理能力不足，容易出现"漏依赖/假依赖"这类语义错误——这一步毕竟要做"谁需要谁的产出"这种因果推断，太弱的模型会拖累整条计划的正确性。
- **推荐用中档、强 tool-calling 可靠性的模型（如 Sonnet 档）**：结构化输出稳定、有足够的多步推理能力做依赖判断，同时延迟和成本适合"每个请求都会调用一次"的关键路径场景。这是"够用且经济"的选择，而不是"能力天花板"的选择。
- **可选的自适应设计（加分项）**：对绝大多数请求用中档模型规划；如果请求被判断为异常复杂（子目标数多、存在歧义），再动态升级到更强模型重新规划——这是"按复杂度分层路由"的思路，和亮点里已有的"成本预算熔断"是同一套工程哲学：不为简单请求多花钱，只在真正需要时才加大投入。

**必被追问**：为什么规划步骤不用最强模型？→ 规划是结构化路由 + 浅层依赖推理，不是深度推理；用旗舰模型会拖慢关键路径延迟、增加成本，而收益（依赖判断的正确率）边际提升有限；把预算留给真正需要深度推理的专家 Agent 环节。

## 三、深挖：局部 replan 机制——"结构合法但拆解错"怎么办

### 1. 怎么发现"拆解错了"——靠契约不匹配，不靠 LLM 主观判断

结构校验（schema/环检测）只能挡住"格式非法"的计划，挡不住"格式合法但和现实脱节"的计划。真正的信号来自**执行结果和"计划时的预期"发生了不匹配**，而这个不匹配要尽量靠**确定性检查**，不是再找一个 LLM 去"感觉哪里不对"（那样又贵又不稳）。

两类信号，对应两种检测方式：

- **契约不匹配（确定性检查，不用 LLM）**：每个任务声明的 `produces` 可以再带一个**期望形状**——比如"selection 任务声明它产出一个**单值** `selected_part_number`"。如果实际跑完返回的是**3 个候选**，这就是"声明单值、实际多值"的结构性不匹配，代码直接能判断，不需要理解语义。这一层抓的是"**形状不对**"。
- **自报低置信度（复用该 Agent 自身已有的质量信号，不是新发明一个打分机制）**：这一层抓的是"**形状是对的，但底下的证据很薄**"——比如选型 Agent 确实吐出了一个型号（单值、不为空，形状完全合规），但这个答案是自纠错循环挣扎几轮后勉强给出的低分结果。

  **关键设计原则：不是"每个 Agent 每次都强制吐一个置信度分数"**——让 LLM 自己给自己打分（"我这次 60% 确定"）是不可靠的，业内已知 LLM 自报置信度校准很差，会被面试官直接问穿。正确做法是**看这个 Agent 本身是什么类型**：
  - **检索型 Agent（如选型 Agent）**：亮点 3 的质量感知自纠错闭环本身就在算一个真实数字——融合得分 + 有效命中数。如果闭环跑完仍落到 abstention，这是一个**确定性计算出来的终态**，直接复用这个已有的内部状态即可，不是新增机制。
  - **确定性查询型 Agent（如项目管理 Agent）**：查项目进度这类任务本质是"查到/没查到/数据是否过期"的分类状态，不是连续置信度；这类情况往往已经被"契约不匹配"检查覆盖（声明会有输出、实际为空），不需要再单独发明置信度概念。
  - **纯 LLM 判断、没有天然量化信号的节点**：不让它自报数字，改用**自洽性检测（self-consistency）**——跑 2~3 次或轻微扰动输入，看结果是否一致；结果不稳定本身就是"低置信度"的证据，比 LLM 自己说的数字可信。代价是要多跑几次，成本更高，只用于真正高风险的关键节点，不能所有任务都这么跑，否则和成本熔断哲学冲突。

这两类信号合起来才是"该不该触发 replan"的判断依据——**不是每次结果和 LLM 预想有点不一样就重规划**，只在这两类明确信号出现时才触发，避免滥触发。

### 2. "局部"局部到哪——只重规划受影响的下游子图

当任务 A 的输出被标记异常时，只暂停"消费了 A 的输出"的下游任务（DAG 上 A 的后继子图），和 A 无关的分支继续跑，不受影响。

然后重新调用 LeadAgent，但给它的不是整个原始请求，而是一个**收窄后的上下文**：原始目标 + A 的实际结果（哪里和预期不一样）+ 等着消费 A 输出的下游任务原本的目标。让它只针对这个子图产出一份修订版子计划，走一遍和原计划一样的校验流程（schema/环检测），再拼回 DAG，替换掉原来的下游节点。

**为什么不是整个计划推倒重来**：已经跑完且仍然有效的上游工作不该被浪费，也不该因为重新规划一次而莫名其妙变了结论——只动"确实被污染"的那一小块。

### 3. 具体例子

用户问："帮我选一个满足功耗要求的 MOSFET，并列出需要的测试项。"

计划：`A(selection, produces: selected_part_number[单值]) → B(test, consumes: selected_part_number)`

执行：A 跑完发现有 3 个候选同样满足约束，没有唯一最优解——声明是单值，实际返回 3 个，**契约不匹配** → 标记 `AMBIGUOUS`，B 暂停。

重规划时，可选的修订策略应该是**几条预先设计好的策略**，不是让 LLM 天马行空：

- **扇出**：把 B 拆成 B1/B2/B3，分别对应 3 个候选各查一次测试项，最后聚合呈现"这三个型号分别要测什么"；
- **转人工澄清**：3 个候选无法自动收敛时，直接把选择权交还用户（"以下 3 个型号都满足要求，你想选哪个？"），呼应"助手要能多轮澄清"这个语义；
- **补充判据收敛**：如果上下文里有其他可用的次级筛选条件（比如"优先选库存多的"），重新调用一次 A 加上这个判据，把 3 个收敛成 1 个。

这三种策略该怎么选也要有明确的默认规则，不能随意——"多个同样有效的候选"默认走**扇出**（信息没丢，只是变多了）；"完全没有候选/查不到"默认走**转人工澄清**（不能瞎猜一个）。

### 4. 怎么保证不死循环

- **重规划预算**：单个请求最多重规划 N 次，超过预算就转成"部分结果 + 说明哪里不确定"，不无限重试；
- **范围只收缩不扩大**：每次 replan 只处理"当前受影响的子图"，不会让受影响范围越滚越大——这个单调收缩的性质本身就保证了整个过程一定会终止；
- **成本联动**：重规划本身要消耗 token，和已有的成本熔断是同一个预算池，不是单独开一个无限额度的口子。

### 5. 必被追问的标准答案

1. **怎么判断该不该重规划，不是每次都触发？** → 只有"produces 声明的形状和实际不匹配"或"Agent 自报低置信度"两类明确信号才触发，不靠 LLM 主观判断。
2. **是不是每个 Agent 都要输出一个置信度分数？** → 不是，LLM 自报置信度数字不可靠；检索型 Agent 复用自纠错闭环已有的融合得分/命中数，确定性查询型靠契约不匹配兜底，纯 LLM 判断且无天然信号的关键节点用自洽性检测（多次采样看结果是否一致）代替。
3. **重规划会不会死循环？** → 有限预算 + 范围单调收缩，两条保证终止。
4. **为什么不是整个计划从头重来？** → 避免浪费已完成且仍然有效的上游工作，也避免无关结论被莫名改变。
5. **重规划期间用户体感是什么？** → 无关分支正常展示完成结果，受影响分支标"重新规划中"；如果走"转人工澄清"策略，直接把问题抛给用户，不让用户干等。

### 6. replan 这一步用什么模型——和初始规划的选型逻辑一样，但有一个额外考量

**结论先说**：同样推荐 Sonnet 档，不推荐在 replan 时升级到旗舰模型。

**推理过程**：

replan 的问题性质和初始规划完全相同——"结构化任务路由 + 浅层依赖推理"——但它的**输入范围更窄、问题更具体**：我们已经知道"哪里出了什么问题"（契约不匹配的具体信号或低置信度的具体表现），LeadAgent 只需要针对这个收窄后的子图产出修订方案，不是从头规划整个请求。问题更具体 + 范围更小，意味着对模型推理深度的要求**不高于**初始规划，用同等档次模型完全够用。

**反对"replan 时升级模型"的理由**：

1. **成本叠加**：replan 本身就是额外支出，已经在从成本预算里扣钱；如果再用更贵的模型来 replan，成本叠加会很快触发预算熔断，让 replan 这个机制变成一个"用了就会让整个请求快速超预算"的负担，与成本熔断哲学冲突。
2. **初始规划用旗舰模型也没用**：如果初始规划任务真的难到 Sonnet 档答不好，那它 replan 时也会遇到同样的困难——用更强的模型做 replan，本质是在用贵的方式重试一个不靠谱的前提，不如把问题归因到"问题本身有歧义 → 走转人工澄清策略"，收益更确定。
3. **范围收窄带来的天然加成**：replan 时上下文更丰富（原始结果 + 具体的不匹配信号），Sonnet 档在具体、清晰的问题定义下表现本来就更稳定；旗舰模型的额外推理能力在这里不是瓶颈，瓶颈是"问题是否描述清楚"，而这一点两个档次的模型面对同样的问题。

**一个可选的"最后一搏"设计（加分项，不是必须）**：如果要在"最后一次重规划机会"（预算耗尽前的最后一次）上用更强模型，逻辑上也能自洽——毕竟已经是最后一次了，多花一点钱换一个更好机会说得通。但这是"锦上添花"的设计细节，不是基础架构。如果面试官问到可以提，但不要主动把它当主卖点。

**必被追问**：replan 时要不要用更强的模型，毕竟出错了说明上次模型能力不够？→ replan 范围更窄、问题更具体，原因不是模型能力不够，而是"计划时无法预见执行结果"——这是规划本身的局限，不是模型档次的问题；用更强模型 replan 成本叠加快，且收益不可靠；真正能力不足的情况（歧义问题）应该走"转人工澄清"，不是升级模型。

## 四、深挖：降级链路展开——四条"→"背后的机制

### 1. 计划生成失败 → 降级单 Agent 直接回答

**"失败"要先分三类，不是一失败就退化**：
- 结构性失败：LLM 输出没通过 schema 校验（字段缺失、格式不对）；
- 语义性失败：结构合法但环检测/引用校验/契约不满足（某任务 consumes 一个没人 produces 的占位符，且原始请求里也没有）；
- 调用性失败：规划这一步的 LLM 调用本身超时/报错。

**退化前先有一次补救**：结构性/语义性失败，先做一次**validation-feedback 重试**——把校验报错原样喂回给 LLM（"你生成的计划里 B 消费了一个不存在的产出，请修正"），让它自己修一次。只有这次重试预算也用尽了，才真正降级——不能一点小错就整个退化。

**降级具体做什么**：绕开 LeadAgent/DAG 整条链路，用一个**轻量分类器**（不是完整规划）判断这句话最贴近哪个专家域，直接单 Agent 执行，不做任务拆解。这样即使退化了，也尽量保住"领域匹配度"——退化的是复杂度，不是准确性方向。

**用户感知**：必须明确告知"本次未能生成完整执行计划，以下是简化处理的回答"，不能让用户误以为这是正常的完整多 Agent 答案。

### 2. 某专家 Agent 失败 → 阻断下游 + 返回"部分结果"

**先厘清一个容易混的点：abstention（查不到/不确定）不算这里说的"失败"。**

- abstention 是任务的**正常终态**——状态是 SUCCESS，只是内容层面标了低置信度，走的是"自报低置信度"那条线，可能触发 replan 评估，但**不会直接阻断下游**；
- 这里说的"失败"专指**工具调用异常、超时且重试预算耗尽、外部系统报错**——任务是真的没有产出，不是"产出了一个不确定的答案"。

**阻断下游怎么落地**：某任务标记 FAILED，它声明的 `produces` 值根本不存在；消费这个值的下游任务发现"契约无法满足"（找不到有效的 producer），调度器**根本不会派发它执行**，直接标记 SKIPPED——这正是"核心实现"里那套状态机（PENDING/RUNNING/SUCCESS/FAILED/SKIPPED）里 SKIPPED 状态存在的意义，不是另加逻辑。

**阻断范围只限于依赖它的子图**，和 A 无关的兄弟分支照常跑——同一个"局部"哲学。

**"部分结果"具体呈现**：聚合阶段收集所有 SUCCESS 任务的输出，对 FAILED/SKIPPED 的分支，在最终回复里**明确标注哪部分没完成、为什么**——不是静默裁掉让用户以为答案就这么少，而是让用户清楚看到"缺了什么"。

**阻断是最后手段**：标 FAILED 之前，Agent 自己的工具调用要先走完"有限重试 + 指数退避"，阻断下游只在这个重试预算也耗尽之后才发生。

### 3. 跨 Agent 输出矛盾 → 局部 replan 或原样呈现

**检测时机**：受影响范围内所有任务都到达终态之后，聚合前。

**检测机制，同样是"确定性优先、LLM 兜底"**：
- 第一层（便宜可靠）：针对已知冲突模式做**确定性规则检查**——比如"选型 Agent 推荐了型号 X，但测试 Agent 返回的该型号 `known_issues` 字段非空"，或"项目 Agent 查到的截止日期早于该型号的交期"，这些都是可以硬编码判断的规则；
- 第二层（兜底）：一次轻量的仲裁 LLM 调用，抓规则没覆盖到的矛盾类型——这一层贵、也不如规则可靠，只作为补网，不是主力。

**replan 还是原样呈现，取决于矛盾的性质，不能一刀切**：
- 如果矛盾是"**可以通过调整参数重新求解的事实冲突**"（比如选型没考虑交期约束，加上这个约束重选一次就能收敛）→ 走局部 replan；
- 如果矛盾本质是"**价值权衡，没有唯一正确答案**"（更便宜的型号交期更长 vs 更贵的型号更快，选哪个是业务判断）→ 不该让系统自己瞎选，直接把两个事实原样呈现给用户，让用户决策。

这个区分本身是判断力的体现——展示"什么时候该自动化、什么时候该交还人"。

### 4. 成本超限 → 预算熔断降级

**计量粒度**：单请求维度累计 token/成本，规划、专家执行、replan、仲裁调用**共享同一个预算池**，不是每个 Agent 各自配额——这也是为什么 replan 本身要消耗 token、和成本熔断是同一个池子。

**熔断检查点，不是中途硬掐**：熔断主要发生在"**是否派发下一个任务 / 是否允许再来一轮 replan**"这个调度边界上，而不是在某次 LLM 调用中途打断——中途打断已经花掉的 token 也拿不到可用结果，纯粹浪费。真正防止单次调用无限超支的手段，是给**每次调用单独设一个 max token 硬上限**（前置约束），预算熔断负责的是"还能不能再来一轮"，两者分工不同。

**熔断后怎么处理**：已完成的任务结果保留，未派发的任务标 SKIPPED（原因是 budget-exhausted），聚合阶段同样要在回复里说明"由于资源限制，以下部分未能完成"——和 Agent 失败那条一样，不能静默截断。

**预算怎么定**：可以按请求复杂度分级配置（简单查询给小预算，复杂多 Agent 请求给大预算），呼应"模型分层路由"那条思路——不为简单请求多花钱。

### 5. 四条路径最终会收敛，不需要各自发明出口

值得一提的设计洞察：**触发原因不同，退化终点可能是同一个**。比如"计划生成的 validation-feedback 重试烧光了预算"，根本原因是预算熔断，但落地效果和"计划生成失败"一样——都是降级单 Agent。系统不需要给每种失败原因发明一个独一无二的出口，**收敛到少数几个成熟的退化路径上，本身就是好设计，不是偷懒**。

### 6. 必被追问

1. **abstention 算失败吗，会阻断下游吗？** → 不算，是正常终态，只会触发潜在的 replan 评估，不会直接阻断。
2. **阻断下游具体怎么实现？** → 状态机层面：FAILED 节点的 produces 值缺失，下游 consumes 匹配不到 → 标记 SKIPPED，调度器天然不会派发它，不是额外写的判断逻辑。
3. **仲裁矛盾检测会不会又是一次不可靠的 LLM 判断？** → 规则优先（已知冲突模式做确定性检查），LLM 只兜底覆盖规则没识别到的类型。
4. **预算熔断为什么不是中途打断？** → 中途打断浪费已花的 token 又拿不到可用结果，改用"单次调用输出上限"硬约束 + "调度边界处的预算检查"组合。
5. **部分结果会不会让用户觉得答案很奇怪/不完整？** → 不会静默裁剪，聚合阶段明确标注哪部分没完成、为什么。

## 五、模拟面试记录：亮点一连环拷打

> 记录格式：面试官问题 → 最终正确答案（已修正）→ 踩过的坑（如果第一次答的时候有偏差，记下来提醒自己）。

### Q1. 为什么一定要用 Multi-Agent，而不是单 Agent 挂一堆工具？

**答案**：这个 Agent 服务于硬件部门的三个子部门——硬件选型、项目交付、测试验证，职责需要区分开。系统是双入口设计：用户可以直接对话某个子 Agent（退化成单 Agent 模式），也可以走统一入口，由 LeadAgent 处理跨部门的复合需求（比如"选个型号，同时看看项目进度和需要的测试项"）。多 Agent 架构还能把工具调用的权限和资源访问隔离开，避免跨权限、调错工具，把错误范围控制在一个 Agent 内。

### Q2. 单 Agent 用现在大模型支持的"一次 turn 内并行发起多个 tool_use"，不也能并行吗？

**答案**：DAG 可以实现"有依赖串行、无依赖并行"，响应时间大幅降低；而且某一步执行出错，可以只对受影响的子图做局部 replan，不会牵连其他并行分支——单 Agent 一次性并行发起工具调用，出错之后很难做到这种精确的局部隔离。

### Q3. 单 Agent 一次性并行发起多个 tool_use，跟你的多 Agent 并行调度，本质区别是什么？

**答案**：每个 DAG 节点不是单纯的一次工具调用，而是子 Agent 自己内部一个完整的推理循环——判断工具调用结果是否合理、要不要重试、要不要换一种查法，错误处理都在 Agent 内部自己完成。而单 Agent 并行发起工具调用之后，必须把所有结果汇总到一起，在一个节点里让 LLM 统一判断"合不合理、要不要重来"——这是本质区别：一个是"每个分支各自有独立的多轮推理深度"，一个是"扁平并行 + 事后统一判断"。

### Q4. 每个子 Agent 内部都是完整循环，成本和延迟岂不是更高？怎么说服我这不是过度设计？

**答案**：两层保障。一是工程上有全局 token 熔断，也可以对每个子 Agent 设置循环次数上限，双重控成本。二是业务本身决定了这个设计是必要的——这套系统主要在做 RAG 查知识库，检索本来就不是一次能查准的，每个子 Agent 可能要查多次。**关键洞察是**：如果用单 Agent 做法，多个域的检索结果要汇总到一个上下文里做统一判断，上下文变得很长，成本反而更高，而且判断更容易被无关信息干扰；子 Agent 各自在窄上下文里判断自己的检索结果，速度快、成本低，判断也更聚焦。

### Q5. 子 Agent 重试到上限还是没查到好结果，会发生什么？

**踩过的坑**：第一次答成"走降级策略，下游节点标 SKIP，该节点返回降级信息告知用户查询失败"——这是把 **abstention（查不到/低置信度）当成了 FAILED** 来处理。

**修正后的答案**：重试到上限仍不理想，属于 abstention，是任务的**正常终态**（状态是 SUCCESS，只是内容置信度低），不应该直接判失败、阻断下游。应该走"自报低置信度 → 触发下游 replan 评估"这条线——可能让下游换一种方式处理这个不确定性，也可能带着这个不确定性继续往下走，不是无脑判失败。

### Q6. 那什么才是真正的"失败"？

**踩过的坑**：第一次答成"超出 token 限制、依赖关系错误、产生环"——这里混淆了三个不同阶段的问题：产生环是**计划校验阶段**的问题（走"计划生成失败 → 降级单 Agent"，根本不会进入执行阶段）；超出 token 限制是**全局调度层面**的预算熔断（影响的是"还要不要派发新任务"）；这两个都不是"一个正在执行中的子 Agent 任务，它自己内部的失败"。

**修正后的答案**：执行阶段真正的 FAILED，是指工具调用异常/超时，或者 LLM 调用异常/超时——这才是"任务已经在跑，但真的没有产出"的情况，跟 abstention（有产出、只是置信度低）和计划/预算层面的问题都不是一回事。

### Q7. 工具调用超时重试，如果调用本身有副作用，会不会导致重复执行？怎么防？

**踩过的坑**：连续两次答成"幂等性，重试带幂等键，插入数据库时按唯一 ID 校验是否插入过"/"工具调用时携带幂等键，用幂等键去判断"——这个答案默认**下游系统自己会检查幂等键**。但如果下游是老旧的内部系统，压根没有这个去重能力，"携带幂等键"就是自说自话，下游根本不认。

**修正后的答案**：幂等键放在哪不重要，**谁来检查它才是关键**。既然不能指望下游，检查逻辑必须在自己控制的编排层做：调用之前先把"我要发起这次调用，幂等键是 K"这条记录持久化下来（这是 checkpoint 机制的自然延伸），重试之前先查自己的记录，如果已经标记"已发送/已成功"，就不再发起。

### Q8. 如果调用已经发出去，下游可能已经处理了，但网络在返回响应前断了——这种"结果未知"的情况怎么处理？

**答案**：如果下游支持查询验证，可以先去下游核验这次操作到底有没有真的发生，再根据核验结果回来标记状态、决定要不要重试——这是一种叫"**结果核验**"的技术，跟"写时幂等"是不同的另一条路，只在下游支持"查询"这个能力时才成立。

### Q9. 如果下游连查询验证能力都没有，真正最坏情况怎么处理？

**答案（面试官给出，需要记住）**：

- 把这次调用的结果标记成**第三种状态**——不是 SUCCESS，也不是 FAILED，是"**结果未知，存在重复风险**"；
- **不自动重试**，因为重试的下行风险（真的造成重复副作用，比如给人发了两条一样的通知）比"这次可能没成功"的风险更大，两害相权取其轻；
- **显式呈现给人**："系统尝试执行了 XX 操作，但受下游系统限制，无法确认是否成功，请手动核实"——把不确定性说清楚，不硬编一个确定的成功/失败状态糊弄过去；
- **系统化**：不要每次遇到新工具都临时判断。在工具接入的能力清单里，强制每个工具声明三个属性——`有没有副作用`、`支持不支持幂等去重`、`能不能查询核验结果`。调度层的重试策略完全由这三个声明驱动，不是每次现场分析。

### Q10. 崩溃恢复——DAG 执行到第 5 个节点崩溃重启，怎么知道执行到哪一步，会不会重复执行已成功节点？

**答案**：每个节点的 checkpoint 持久化到 PostgreSQL，每个节点有状态（PENDING/RUNNING/SUCCESS/FAILED/SKIPPED），重启后找到最近状态为 SUCCESS 的节点，恢复 checkpoint，继续向后执行。

**遗漏的点**：这个答案没有覆盖崩溃那一刻正好在跑的**RUNNING 状态节点**——它既不是 SUCCESS 也不是 FAILED，直接当"没跑过"重新执行,如果它调用的工具有副作用，就正好踩进 Q7/Q8 讨论的"重复执行"的坑里。

### Q11. RUNNING 状态的节点，崩溃后具体怎么处理？

**踩过的坑**：第一次答成"回滚里面的操作"——"回滚"对自己控制的 Postgres checkpoint 数据库很自然（事务本身支持撤销），但对外部系统的副作用操作（比如已经发出去的飞书通知），"回滚"往往做不到，而且如果连"有没有真的执行"都不知道，也不知道该不该回滚。

**修正后的答案**：这跟"工具调用超时后重试要不要防重复"是**同一类问题**，只是触发原因从"网络中断"变成了"进程崩溃"，可以套用同一套框架——先判断这个 RUNNING 节点有没有调用有副作用的工具；如果有，判断该工具调用是已完成还是进行中；如果进行中，判断支不支持核查结果——支持就核查后决定要不要重新执行，不支持就转人工确认。

### Q12. 用户取消（关闭浏览器/点取消）——正在执行有副作用工具调用时怎么处理？会不会遇到同样的"副作用已发生但不确定"问题？

**答案（面试官给出，需要记住）**：取消不是"立刻杀掉所有正在跑的东西"，而是"停止调度新任务 + 对已经在跑的任务按有无副作用分类处理"：

- **还没开始跑的（PENDING）**：直接不派发，标 CANCELLED，零风险；
- **正在跑、无副作用的**：直接打断，停止等待结果，没有风险；
- **正在跑、有副作用的**：**不强行打断**——强行打断只会制造"结果未知"的不确定状态，比让它自然跑完更糟。让这一个调用自然跑完，再走 Q7/Q8/Q11 那套核验/转人工的逻辑处理；
- **已经跑完（SUCCESS）**：结果保留，不受影响。

**本质原则**：取消传播控制的是"要不要开始新的工作"，而不是"强行终止正在发生的、有真实后果的操作"——这跟崩溃恢复、网络中断重试，是**同一个通用的不确定结果处理框架**在三种不同触发场景下的应用，不是三个孤立的机制。

### Q13. 规划这一步（LeadAgent 生成任务列表）为什么不直接用最强的旗舰模型？

**答案**：规划步骤的任务性质是"结构化任务路由 + 浅层依赖推理"，不是"深度创造性推理"或"长文档理解"。旗舰模型（如 Opus 档）的额外能力，在这个任务上**边际收益很低**，但代价很明确：

1. **延迟**：规划是每个请求关键路径的第一步，旗舰模型的输出延迟更高，直接拖慢用户感知到的"首次响应时间"；
2. **成本**：这一步在每个请求都要走一次，用最贵的模型意味着每个请求的基础成本大幅上升——即使是最简单的请求，也要为规划步骤付旗舰价格；
3. **预算应该留给真正需要的环节**：三个专家 Agent 才是真正做"复杂权衡""长文档理解""多跳推理"的地方，那里才是旗舰模型能力能发挥作用的场景。

**类比**：这就像在工厂里把最贵的精密仪器用在"分拣传送带决定往哪个方向送货"这一步——传送带的选择不需要那个精度，精密仪器应该留在精加工环节。

**必被追问**：那规划出错怎么办，不就是因为模型不够强？→ 规划出错的原因不是"模型推理不够深"，而是"计划时无法预见执行结果"（这是所有规划系统的固有局限，不是档次问题）；出错靠局部 replan 兜底，不靠升级模型。

---

### Q14. 那为什么不用最便宜的最小档模型（如 Haiku 档）做规划，把成本压到最低？

**答案**：最小档模型在这一步有两个明确的能力风险，不是"凑合能用"：

1. **多步依赖推理不可靠**：判断"任务 B 需要的输入是计划时已知的，还是必须等任务 A 跑完才知道"，本质上是因果推断。最小档模型在这类需要保持多步推理链条的任务上，容易出现"漏依赖"（该串行的误判为可并行）或"假依赖"（该并行的过度保守串起来），这两类错误会直接影响执行结果的正确性和效率；
2. **歧义处理能力不足**：用户的请求往往不是整洁的标准句，包含省略、歧义、多重目标混在一句话里——最小档模型在这种情况下容易产生结构上合法但语义上已经跑偏的计划，而这种错误要到执行阶段才会暴露，代价比"规划阶段多花一点钱"高得多。

**选型结论**：推荐中档、强 tool-calling 可靠性的模型（如 Sonnet 档）——结构化输出稳定、依赖推理够用、延迟和成本适合"每个请求都调用一次"的关键路径。这是"够用且经济"的选择，不是"能力天花板"的选择。

**踩过的坑**：不要说"越强越好所以用旗舰"，也不要说"成本优先所以用最便宜的"——两个极端都是没有工程判断的答案。面试官想听到的是"按任务性质选"：这一步的任务性质不需要最深的推理，但也有具体的多步推理和歧义处理门槛，Sonnet 档刚好跨过这个门槛且成本/延迟在可接受范围内。

### Q15. 你说仲裁校验用"实体中心规则"，规则写在共享实体上而不是 Agent 对上。一条规则长什么样？它挂在哪里、谁来触发它、触发条件是什么？

**答案**：

一条规则的伪 YAML：

```yaml
entity: component          # 规则挂在"器件"这个共享实体上

rules:
  - id: known_issue_vs_recommendation
    condition:
      field_a: selection.recommended_part    # 选型 Agent 输出的字段
      field_b: test.known_issues[*].part_number  # 测试 Agent 输出的字段
      conflict_if: field_a IN field_b        # 确定性判断
    action: trigger_replan                   # 冲突时 → 局部 replan

  - id: delivery_vs_deadline
    condition:
      field_a: selection.delivery_date       # 选型 Agent 输出
      field_b: project.deadline              # 项目 Agent 输出
      conflict_if: field_a > field_b         # 交期晚于截止日
    action: present_to_user                  # 价值权衡 → 交给用户
```

- **挂在哪**：规则文件按实体类型组织（`component.yaml`、`project.yaml`），与具体 Agent 代码解耦，新加规则只改配置，不动 Agent 代码
- **谁来触发**：编排层在聚合前统一触发，不是某个 Agent 顺带跑，是独立校验步骤
- **什么时候触发**：不等全部任务完成；一条规则涉及的所有字段的贡献 Agent **都到达终态**时即可检查，不阻塞无关分支

**为什么"实体中心"比"Agent 对规则"好**：现有 3 个 Agent 新加第 4 个——Agent 对规则要补 3 条新规则（O(n²) 增长）；实体中心规则只需第 4 个 Agent 声明"我输出 component 实体的哪几个字段"，已有规则自动对它生效，O(1) 扩展。

**action 怎么选**：可以自动收敛的事实冲突（加约束重选就能解决）走 replan；本质是价值权衡没有唯一解的冲突交给用户——规则里声明好，不是运行时临时判断。

### Q16. DAG 校验里有环检测——LeadAgent 生成了 A→B→C→A 这样的循环依赖，代码里怎么检测？用什么算法？

**答案（第一次答"直接 BFS 遍历 DAG 判断是否有环"——方向对但不够精确）**：

正确算法是 **Kahn's 算法（拓扑排序的 BFS 版）**：
1. 计算所有节点的入度
2. 把入度为 0 的节点加入队列
3. 每次取出一个节点，把它所有出边邻居的入度 -1；邻居入度变为 0 就入队
4. 最后如果处理过的节点数 < 总节点数，说明有节点始终入度无法归零 → **存在环**

**为什么不只说"BFS"**：纯 BFS 在有向图里遇到"已访问"节点，可能只是汇聚点（A→C、B→C，不是环），判断不了。Kahn's 的入度机制才是有向图环检测的标准做法。

**一举两得的加分点**：调度执行本来就需要拓扑排序（决定哪些节点先跑），Kahn's 算法跑完**环检测和拓扑序同时拿到**，复杂度 O(V+E)，不需要跑两次。

### Q17. 节点状态持久化到 PostgreSQL——具体存什么？表结构大概长什么样？崩溃重启后怎么决定从哪个节点继续跑？

**答案（第一次答"从最近状态为 RUNNING 的节点开始跑"——关键错误，RUNNING 节点是最危险的，不能直接重跑）**：

**表结构**（面试说出来即可）：

```
execution_runs:  run_id, request_id, status, plan_json, created_at
dag_nodes:       node_id, run_id, agent_type, goal, status,
                 produces_schema, consumes_keys, updated_at
node_outputs:    node_id, run_id, output_json, confidence_signal
tool_calls:      call_id, node_id, tool_name, input_json, output_json,
                 status, idempotency_key, has_side_effects, started_at
```

工具调用单独一张表：idempotency_key 和 has_side_effects 存在这里，崩溃后判断"要不要重发这个调用"靠的就是它。

**崩溃恢复顺序（不是"从最近 RUNNING 节点开始跑"）**：
1. **SUCCESS 节点**：复用 node_outputs 缓存，不重新执行
2. **FAILED / SKIPPED 节点**：维持原状，下游继续阻断
3. **RUNNING 节点**：查 tool_calls 表，判断有无副作用调用已发出 → 走 Q11 框架（核验/转人工），不能无脑重发
4. **PENDING 且上游全是 SUCCESS 的节点**：这才是"继续跑"的起点，重新入调度队列

**一句话**：SUCCESS 复用缓存，PENDING 接着跑，RUNNING 先查副作用状态，不能直接重发。

### Q18. 一个节点有两个上游，一个 SUCCESS、一个 FAILED，这个节点应该怎么处理？

**答案**：直接 SKIPPED，不是"用已有的那个上游结果凑合跑"。

这个节点在 `consumes` 里声明了两个字段，调度器派发前检查所有 `consumes` 字段是否都有有效 producer 输出——只要有一个缺失（对应上游 FAILED，produces 值不存在），契约无法满足，直接标 SKIPPED，不派发。**契约是全有或全无。**

**为什么不需要额外写判断逻辑**：FAILED 节点的 produces 值在 node_outputs 里根本没有记录，匹配时找不到，SKIP 是 produces/consumes 机制的自然结果，不是另加的 if 判断。

### Q19. LeadAgent 是每次请求都重新生成完整计划，还是有缓存/复用机制？

**答案（Plan 这一层不应该缓存）**：

LeadAgent 生成的计划里包含从用户请求提取出的**具体参数**（功耗 ≤ 2W、截止日期 XX 等）。两个问题"长得很像"但参数值不同，计划就不同；如果按相似度复用了旧计划，执行的是上次的参数，用户拿到错误答案且**没有任何报错**——静默错误比慢一点更危险。

**真正该缓存的是节点结果这一层**：如果某个节点的 `goal` + `consumes 的具体输入值` 和上一次完全一致，可以直接复用 node_outputs，跳过执行。这是 checkpoint 机制（崩溃恢复时 SUCCESS 节点复用缓存）的自然延伸，把"同一请求内复用"扩展为"跨请求复用"，同一套逻辑。

### Q20. 节点缓存的范围——是只在本次会话内，还是同一用户跨会话，还是所有用户共享？

**答案**：按数据的**时效性 × 归属性**两个维度分层，不是一刀切。

| | 时效性高 | 时效性低 |
|---|---|---|
| **用户私有** | none（不缓存） | scope: user，短 TTL |
| **公共数据** | scope: session（本次用完就丢） | scope: global，长 TTL |

具体例子：
- "查 XX 项目当前进度"→ 实时 + 用户相关 → none，不缓存
- "查用户负责的项目列表"→ 慢变 + 用户相关 → user scope，小时级 TTL
- "查某型号 MOSFET 规格参数"→ 静态 + 公共 → global scope，长期缓存，跨用户共享

**缓存键**：`node_goal + consumes 的具体输入值` 完全一致才命中，不是"同类型 Agent"就命中。

**最干净的设计**：复用已有 node_outputs 表，加两列 `cache_scope` 和 `user_id`，查询时按 scope 决定过滤条件（global 只按 cache_key，user 加 user_id，session 加 run_id）——**不引入额外存储**，PostgreSQL 加索引够用。

**和工具能力清单的一致性**：在已有三个属性（`has_side_effects`、`supports_idempotent_dedup`、`supports_result_verification`）基础上加 `cache_scope` + `cache_ttl`，声明式驱动，不是运行时临时判断——和整个系统"声明 → 调度层执行"的工程哲学一致。

**和多租户隔离的连接**：global scope 缓存需要过租户访问控制，不能让用户 A 查到用户 B 私有项目的缓存——缓存设计和亮点四（多租户资源治理）的隔离机制是同一套，不是两套独立逻辑。
