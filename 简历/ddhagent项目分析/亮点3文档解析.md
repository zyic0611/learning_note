## 三、硬件数据手册结构化参数抽取与质量管线

**① 简历写法**

> 构建硬件数据手册结构化参数抽取管线：多量纲单位归一化、数字/扫描 PDF 分流，跨表交叉校验后落库 PostgreSQL；查询侧绑定预置 SQL 模板，LLM 仅做参数抽取，规避幻觉与注入风险。参数抽取准确率由 **62% 提升至 91%**，支持跨文档精确范围查询。

---

**② 深挖准备**

### 问题动因

硬件数据手册里的参数值是系统最终"精确取值"的数据源——视觉检索（亮点二）能定位"哪一页有答案"，但"85°C下最大电流是3.2A"这种精确数值必须从结构化参数库里查，不能靠VLM从图像里"读出来"（会幻觉）。所以数据库里的数据质量直接决定系统能不能给出可信的精确答案。

原始数据手册有三个典型问题：
1. **单位写法不统一**：同一个量纲跨厂商/跨文档写法五花八门，不归一化就没法做跨文档范围查询
2. **同一参数跨表矛盾**：最大电压可能同时出现在"绝对最大额定值"和"电气特性"两张表，抽取误差或文档本身歧义会导致两处不一致，静默入库会污染数据
3. **PDF格式不均一**：数字PDF可以直接提取文本层，扫描PDF是图像不能直接解析，同一条管线需要分流处理

---

### 技术方案拆解

**第一步：数字 / 扫描 PDF 分流**

管线入口先做格式检测：提取PDF页面，判断是否存在可用的文本层（数字PDF会有嵌入的字符信息，扫描件只有图像）。
- **数字PDF**：直接用pdfminer/pymupdf提取文本层，走表格解析（camelot/pdfplumber识别表格边框和单元格）
- **扫描PDF**：先跑OCR（tesseract / paddleOCR）生成文本层，再走同一套表格解析逻辑

注意一个容易混淆的点：主检索路径（亮点二）跳过OCR，是因为视觉embedding对图像整页做语义定位不需要文字；这里结构化抽取必须拿到精确数值，所以扫描PDF这个场景OCR是不可跳过的——两条路线的OCR策略不矛盾，适用场景不同。

**第二步：多量纲单位归一化**

硬件文档涉及的电气量纲范围很广，每个量纲有多种写法：

| 量纲 | 常见写法 | 统一基准 |
|---|---|---|
| 电阻 | Ω / kΩ / MΩ / mΩ / KΩ | Ω |
| 电容 | F / μF / uF / nF / pF / fF | F |
| 电流 | A / mA / μA / uA / nA | A |
| 电压 | V / mV / μV / kV | V |
| 频率 | Hz / kHz / MHz / GHz | Hz |
| 功率 | W / mW / dBm | W（dBm需换算）|

更复杂的是**带条件的复合参数**：抽出来的不只是一个数值，而是"数值+工况条件"的三元组，比如：
- `IQ = 5mA @ Vcc=5V, Tj=85°C`
- 归一化后：`{param: "IQ", value: 0.005, unit: "A", conditions: {Vcc: 5.0, Tj: 85}}`

条件字段必须随数值一起入库，不然"85°C下最大电流"和"25°C下最大电流"会被当成同一个参数互相覆盖。

**第三步：跨表交叉校验**

硬件数据手册有几张固定结构的表，同一参数经常跨表重复出现：
- **绝对最大额定值（Absolute Maximum Ratings）**：定义参数的绝对上限
- **电气特性（Electrical Characteristics）**：定义典型/最小/最大工作值
- **引脚描述表**：部分参数在引脚说明里也有数值

校验逻辑：抽取完所有表格后，对同一`(param, condition)`组合做跨表比对——
- 一致 → 直接入库
- 不一致 → 不入库，标记为`status=pending_review`，记录矛盾来源表和具体数值差异，等待人工审核

**为什么不是"取最大值/最小值自动解决矛盾"**：绝对最大额定值和电气特性的语义不同（前者是"超过就损坏"的硬上限，后者是"正常工作范围"），自动选值会混淆语义，必须人工判断。

**第四步：落库 PostgreSQL**

核心表结构（简化）：

```
params(
  doc_id, page_num,        -- 溯源
  part_number,             -- 型号
  param_name,              -- 归一化后的参数名
  value,                   -- 归一化后的数值（数字类型，可做范围查询）
  unit,                    -- 归一化基准单位
  conditions JSONB,        -- 工况条件（Tj/Vcc/频率等）
  raw_value,               -- 原始文本（溯源用）
  status                   -- valid / pending_review
)
```

value字段存数字类型而不是文本，是为了支持范围查询（`value < 3.2`）。存原始raw_value是为了溯源——用户拿到查询结果后可以追回原文档原表格核实。

**第五步：查询侧 —— 预置 SQL 模板 + LLM 参数抽取**

不允许LLM自由生成SQL的原因：
1. **幻觉字段**：LLM可能编造数据库里根本不存在的列名（如`max_current_85c`），执行直接报错或查出空结果
2. **注入风险**：自由生成SQL存在被prompt操纵、执行`DROP TABLE`类语句的风险

做法：预置一批覆盖常见查询意图的参数化SQL模板，例如：

```sql
-- 模板1：精确查某型号某参数在某工况下的值
SELECT value, unit, raw_value, page_num
FROM params
WHERE part_number = :part_number
  AND param_name = :param_name
  AND conditions @> :conditions::jsonb
  AND status = 'valid'

-- 模板2：范围筛选（如找所有85°C下最大电流不超过3A的型号）
SELECT DISTINCT part_number, value, unit
FROM params
WHERE param_name = :param_name
  AND conditions @> :conditions::jsonb
  AND value <= :threshold
  AND status = 'valid'
```

LLM的任务只是：从用户问题里抽取`{part_number, param_name, conditions, threshold}`这些绑定参数，不碰SQL本身。LLM做参数抽取这件事错了顶多查不到结果，不会执行危险语句。

---

### 必被追问的 8 个点

1. **为什么不让LLM直接写SQL？Text-to-SQL不是很成熟了吗？**
   → Text-to-SQL在通用场景成熟，但在这个系统里有两个具体风险：① 硬件参数库的schema有专有字段（conditions JSONB、param_name的归一化命名规范），LLM没见过这个schema会幻觉字段名；② 系统面向硬件工程师，查询意图其实是有限的几类（精确取值/范围筛选/跨型号对比），预置模板完全能覆盖，没必要引入自由生成SQL的风险换取灵活性。

2. **跨表校验发现矛盾，标记pending_review之后谁来处理？会不会积压？**
   → 两层缓解：① 矛盾率在良好文档里本来就低，绝大多数参数只在一张表里出现；② pending_review的参数在查询时会走降级路径——系统返回"该参数存在数据矛盾，建议查阅原始文档"而不是给出可能错误的值，保证不输出不可信的答案。积压问题靠业务优先级排队人工处理，不是技术问题。

3. **单位归一化dBm怎么处理，不是线性换算？**
   → 对，dBm换算到W需要`P(W) = 10^((dBm-30)/10)`，是非线性换算，和其他量纲的线性缩放不同。实现上单独做一个量纲类型的分支，不能套通用的乘以系数的逻辑。这类特殊量纲在管线里要显式枚举处理，不能偷懒。

4. **62%→91%这个指标是怎么测的？baseline62%是怎么来的？**
   → 人工标注评测集：从文档里选有标准答案的参数（数值已知、工况已知），跑管线抽取后对比。Baseline（62%）是没有单位归一化+没有跨表校验时的原始抽取准确率——这62%里错误来源：单位写法不一致导致数值比对失败约占一半，抽取串行/串列错误约占另一半。91%是加上归一化和校验之后的结果。

5. **扫描PDF跑OCR之后表格识别准不准？**
   → 扫描件的表格识别准确率比数字PDF低一个档次，这是技术现状。缓解方式：① 对OCR置信度低的页面打标，触发降级（该参数不入库，走视觉检索兜底）；② 扫描件抽取的参数在入库时标注来源类型，查询结果里体现"该值来自扫描件，建议核实原文"。

6. **PostgreSQL为什么不用向量数据库或者其他存储？**
   → 结构化参数库的查询需求是**精确匹配+数值范围**（`value <= 3.2 AND part_number = 'XXX'`），这是关系型数据库的强项；向量数据库擅长的是语义相似度搜索，用在这里反而是错配。两种存储各司其职：向量库负责视觉检索的语义召回，PostgreSQL负责结构化参数的精确查询。

7. **conditions字段用JSONB而不是单独建列，为什么？**
   → 不同参数的工况条件字段不统一（有的是Tj/Vcc，有的是频率/负载），无法预先建固定列；JSONB支持部分索引和`@>`包含查询，能做"工况条件包含Tj=85°C"这类灵活查询，同时保持schema不随新参数类型膨胀。

8. **这套管线和亮点二的边界在哪？会不会重叠？**
   → 不重叠，分工明确：亮点二解决"找到哪一页/哪个区域有答案"（语义定位）；亮点三解决"把那一页里的精确数值可靠地抽出来、存进去、查出来"（结构化数据工程）。亮点二的输出是页面/区域，亮点三的输出是可直接使用的精确数值，两者是串联关系：先定位，再精确取值。
