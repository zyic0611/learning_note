## 二、多阶段检索 + 质量感知自纠错

**① 简历写法**

> 针对硬件术语中英混合、同义表达导致的检索召回率低问题，构建关键词 + 语义双路融合、二次精排的检索链路，并将质量信号反馈给自纠错闭环，证据不足时明确拒答、绝不编造。评测集 Recall@5 由 **58% 提升至 82%**，无答案场景误答率控制在 **6%** 以内。

**② 深挖准备**

- **完整检索链路总览（分层视角，新增视觉优先层）**：整条链路实际上是四层级联，不是单一路径。
  - **L0 视觉原生（默认优先尝试）**：对有视觉索引覆盖的文档，先走"池化向量ANN粗排 + MaxSim多向量精排"，直接对页面图像定位答案区域（数据侧怎么建这条索引、成本怎么摊平，属于亮点三"多模态文档建库"的范畴，这里只讲检索侧怎么用它）。
  - **L1 文本双路召回 + reranker（视觉链路不可用时的熔断替代，也是无视觉索引文档的默认路径）**：BGE-M3密集向量 + BM25稀疏关键词，RRF融合后接Cross-Encoder Reranker二次精排——下面"核心实现"及后续几条讲的都是这一层的细节。
  - **L2 质量感知自纠错（在L1结果基础上判断是否需要升级重试）**：融合得分+有效命中数低于阈值 → 触发术语转换/改写/拆分的升级阶梯，重新检索。
  - **L3 Abstention（预算耗尽仍不达标的终态）**：明确拒答，不呈现低置信度内容，绝不编造。

- **为什么视觉原生排在最前面，不是"文本搜不到再补救"**：如果反过来做成"text-first，搜不到再升级视觉"，会踩一个根本性的坑——BM25/dense对"答案其实在图表里"的query，通常不会返回空结果（明确失败信号），而是返回一堆语义相关但答案错误/不完整的候选（比如命中了讨论某参数的文字段落，但具体数值只在旁边的曲线图里），系统看到的是"有结果、置信度还不算低"，根本不会触发升级——这是**静默错误，不是可检测的失败**，没法用"搜不到才升级"的阈值机制兜底。只要语料里图表/曲线/复杂表格类内容占比不可忽略，text-first在架构上就存在这类系统性覆盖盲区。视觉原生设为默认优先路径，能保证这类内容从一开始就有被正确召回的机会；而"贵不贵"这个顾虑已经被数据侧的池化向量粗排+MaxSim精排两阶段设计压平到跟普通向量检索同量级，不再是"只能当补救手段"的理由。

- **核心实现（L1层细节）**：双路召回 = BGE-M3 密集向量 + BM25 稀疏关键词，RRF 融合后接 Cross-Encoder Reranker 二次精排。两阶段分工：first-stage 召回负责"别漏"，second-stage 精排负责"排对"。
- **查询侧增强**：短问题/口语化问题先用 LLM 生成"假设答案"（HyDE）或改写为检索友好形式再召回，解决查询-文档词汇不对齐的问题。
- **自纠错闭环（正名为 Corrective RAG / CRAG）**：检索评估器用"融合得分 + 有效命中数"判断质量，低于阈值则触发纠错动作（术语转换/改写/拆分 → 重新检索），预算耗尽或仍无效则 abstention。这不是"随手拍的 retry"，而是"评估 → 纠错 → 再检索"的显式控制环。
- **完整降级链路（四层）**：视觉原生超时/成本超限 → 熔断降级到文本双路召回+reranker（L0→L1，依据可用性/成本指标，不是质量判断）→ 该层召回质量低 → 自纠错升级阶梯（改写/拆分，L1→L2，依据融合得分+有效命中数）→ 仍低 → abstention（L2→L3，不确定回复，绝不编造）。**注意L0→L1和L1→L2这两次降级的判断依据本质不同**：前者是系统可用性熔断（超时/GPU队列/预算，运维指标，不需要跨模态置信度校准），后者是检索质量判断（融合得分+有效命中数，需要在评测集上校准阈值）。
- **必被追问的 8 个点**：
  1. 怎么判断"低质量召回"？→ 融合得分 + 有效命中数的阈值，在评测集上校准（拒绝率与漏答率的 trade-off）。
  2. RRF 的 k、BM25/向量各取多少？→ 消融实验定。
  3. 为什么需要 reranker？→ 召回与精排分工，cross-encoder 精度高于双塔，但慢、只对候选集用。
  4. HyDE 会不会引入幻觉、把检索带偏？→ 假设答案只用于召回、不参与最终回答，且只在词汇失配时启用。
  5. Recall@5 的 ground truth 怎么做？→ 固定评测集人工标注，分八类题型。
  6. 视觉优先会不会导致每次查询都多付一次视觉的开销，最后还是走文本兜底？→ 视觉层的粗排（池化向量ANN）本身很轻，触发熔断的判断点在粗排/超时检测阶段就介入，不是等整条视觉链路（包括精排）跑完才发现不行，不会重复付两遍精排级别的成本。
  7. L0→L1和L1→L2的降级判断依据是不是同一套？→ 不是，前者是可用性/成本熔断（超时、预算），后者是质量信号判断（融合得分+有效命中数），两层性质不同，混着讲会被追问出漏洞。
  8. 加了视觉优先层之后，这条链路自己的Recall@5指标（58%→82%）还成立吗，是不是两个亮点在打同一个指标？→ 成立，两者评测集不重叠。这条指标测的是"术语中英混合/同义表达导致的文本检索失效"这一类问题，ground truth本身就是答案在文本段落里、只是词面难匹配的题，跟视觉层要解决的"答案在图表里、文本解析读不出来"是完全不同的失效模式和评测集，互不覆盖。这条链路在真实流量里也不是摆设——它是无视觉索引文档的默认路径，也是视觉链路熔断后的兜底路径，两种场景加起来在实际流量里占比可观，指标提升是实打实生效的。

## 模拟面试记录：亮点二连环拷打

> 记录格式同 multi.md：面试官问题 → 最终正确答案（已修正）→ 踩过的坑（第一次答偏了的地方）。

### Q1. 关键词召回和语义召回各自的失效模式是什么？举硬件场景的例子。

**答案**：BM25（关键词）对同义词/别名效果差——比如用户说芯片的别名，字面对不上就漏检；向量（语义）对精确数值/型号这类"精确匹配"效果差——比如查"电阻 25Ω 下最大电流"，语义相近但数值不对的文档也会被判定"相似"，精确取值容易查偏。两者失效模式正好互补，这是双路召回的存在依据。

### Q2. 为什么用 RRF 而不是直接把 BM25 分数和向量相似度分数加权平均融合？

**答案**：两个系统的分数不可比——BM25 无上界，向量相似度有界（如 -1~1 或 0~1），量级和分布完全不同，直接加权平均没有意义。RRF 只依赖**排名**（ordinal position），不依赖原始分数量级，天然系统无关。公式：`RRF_score(d) = Σ 1/(k + rank_i(d))`，对文档 d 在每个检索系统 i 里出现过的排名求和。

**踩过的坑**：第一次答成"一个文档如果在向量里出现、在 BM25 没出现，那么在 BM25 里就是 0 分"——不准确。准确说法是：该文档在 BM25 里**根本没有排名**（未被召回），对 BM25 那一项的求和贡献为 0（缺失这一项，不是"BM25 给了 0 分"），这个区别看似小，但容易被追问"BM25 怎么算出 0 分的"而答不上来。

### Q3. RRF 公式里常数 k（常取 60）的作用是什么？k 取很小/很大分别有什么后果？

**答案**：k 是平滑参数，控制排名靠前/靠后之间的分数落差。**k 小**（如 k=1）：落差大，"只在一个系统里排第一"的文档会远超"两个系统里都排第五"的文档，融合结果容易被某一路的偶然高排名带偏。**k 大**（如 k=1000）：落差几乎消失，排名先后基本不影响分数，丢失排序信息本身的价值。取 60 是经验平衡点，鼓励"两路都认可、排名都不错"的文档（共识）赢过"只有一路排第一、另一路完全没召回"的文档。面试诚实答法：默认 60，最终值在评测集上消融实验确定。

**踩过的坑**：第一次表示完全不了解这一点，是被直接讲解的，没有自己推出来。

### Q4. RRF 融合完已经排好序了，为什么还需要 Cross-Encoder Reranker 二次精排？本质区别是什么？

**答案**：双路召回（尤其向量部分）是 bi-encoder——query 和 doc 各自独立编码成向量，再比较相似度，编码阶段两者互不感知；reranker 是 cross-encoder——把 query 和 doc 拼在一起联合编码，做 token 级的交叉 attention，能捕捉更细粒度的语义交互，精度更高。

### Q5. 既然 cross-encoder 精度更高，为什么不直接用它做第一阶段召回，对全库跑？

**答案**：cross-encoder 成本高、耗时长；第一阶段的目标是"别漏"（尽量召回所有相关文档），第二阶段的目标才是"排对"（在小范围内精确排序）。对全库跑 cross-encoder 会导致延迟爆炸、显存溢出。更本质的原因是**架构上决定了它不能被索引化**：bi-encoder 的文档向量可以离线预计算、建 ANN 索引（如 HNSW），查询时只需编码一次 query 做近似搜索（亚线性）；cross-encoder 的文档表示依赖具体是哪个 query（query+doc 联合编码），没法离线预计算，每来一个新 query 都要对候选集里每个 doc 重新跑一次完整前向传播——所以它天生只能对一个已经缩小的候选集做精算，不是"贵和慢"这么简单，是没法被索引化。

### Q6. 检索评估器用"融合得分 + 有效命中数"判断质量，为什么需要两个信号，只看 top-1 融合得分够不够？

**答案**：只看 top-1 分数会漏掉两类问题——① **假阳性风险**：top-1 分数高不代表真的相关，可能只是偶然字面命中（比如命中了数字/型号但主题不相关）；② **绝对分数不可比**：不同查询类型（短查询/生僻词/长查询）的分数分布本身不一样，用同一个绝对阈值卡 top-1 不稳定。"有效命中数"抓的是**证据的收敛程度/共识**——如果 top-K 里有多条都超过阈值、互相印证，说明不是偶然命中；如果只有 1 条勉强过线，即便分数不低，整体证据强度也薄。融合得分卡"最强证据够不够强"，有效命中数卡"证据是不是孤证"，两者都不达标才判定"低质量召回"。这跟系统里"不信任单一 LLM 自报置信度、要用多个独立信号交叉验证"的设计哲学是同一套逻辑。

**踩过的坑**：第一次表示不了解，是被直接讲解的。

### Q7. 阈值太严格 / 太宽松分别导致什么问题？（用"拒绝率"和"漏答率/误答率"说）

**答案**：阈值太严格 → 拒绝率升高 → **漏答率**升高（本来证据够、能答对的问题被误判"证据不足"，触发降级甚至 abstention，可用性变差）；阈值太宽松 → 拒绝率降低，但**误答率**升高（证据其实不充分，系统却当作够格直接生成答案，可能给出看似合理但错误的答案）——这正是简历里"无答案场景误答率由 A% 降至 B%"对应的风险点。

**踩过的坑**：第一次把宽松阈值的后果笼统答成"回答偏离用户问题核心"，没有点出"误答率"这个和简历指标直接对应的关键词。

### Q8. 面向硬件工程师的场景，阈值该往严格还是宽松偏？为什么？

**答案**：往严格偏。硬件设计对参数精确性要求极高，给错参数（如电流上限）可能直接导致器件损坏或设计缺陷，后果远比"没查到、需要人工确认"严重；召回的数据也要求可溯源。本质是"宁可漏答不可误答"，和系统"绝不编造"的设计主线一致。

### Q9. 术语转换 / 查询改写 / 问题拆分，这三种纠错动作各自对应什么样的召回质量低的原因？

**答案**：**术语转换**对应"词汇不匹配但意思对"——比如用户用别名/中文说法，文档里是官方型号/英文术语，字面对不上导致 BM25 漏检，此时把查询词替换/映射成文档实际使用的标准术语（同义词典/术语表），不用改写整句、也不用拆分；**查询改写**对应问题太简短/口语化，词汇信息量不够，用 LLM 补全/重写成检索友好的形式（含 HyDE）；**问题拆分**对应问题过长、一句话涉及多个独立子目标，需要拆成多个子问题分别检索。

**踩过的坑**：第一次把"术语转换"错答成了"指代消解"（解析代词"它/这个型号"），这是一个真实存在但**不在简历声明的三个动作范围内**的概念，漏答了"术语转换"真正对应的场景（词汇/别名/中英文不匹配）。

### Q10. 系统怎么判断该用三种纠错动作里的哪一种，而不是随便选或者都试一遍？

**答案**：**核心设计不是精准诊断，而是一个"由便宜到贵"的升级阶梯（escalation ladder）**，按固定顺序依次尝试：① 先试术语转换（最便宜，查词表，不用调 LLM）；② 不行再试查询改写（中等成本，一次 LLM 调用）；③ 还不行才试问题拆分（最贵，每个子问题都要单独走一遍检索），且"是否值得拆分"可以靠一个便宜的规则在检索前先判断（是否有并列连词、多个独立实体）。判断线索方面，词汇不匹配可以靠"BM25 命中少、向量命中多"这个不对称信号识别；问题模糊对应两路都召回不少候选但分数分布很平、没有明显头部结果。设计哲学：不信任一个不可靠的诊断判断，用有限预算的升级阶梯兜底，即使诊断不准，最坏情况也只是多花一轮便宜的尝试，不会导致闭环失控。

**踩过的坑**：第一次能答对"词汇不匹配"的判断信号（BM25 少、向量多），但"问题模糊"的信号描述成"两路召回数量都多"（不够精确，应该是"分数分布平、无明显头部"），"问题太复杂需要拆分"完全答不上来——这条是被直接讲解的。

### Q11. 5 轮纠错预算耗尽、召回质量仍低于阈值，系统该给用户返回什么？

**答案**：**明确拒答**——"该信息未能在知识库中找到可靠依据"，不展示任何检索到的低质量内容，不给"答案+低置信度标签"这种模式。原因：宁可漏答，也不给可能被误用的错误信息，严谨精确优先，这正对应系统三级降级链路里的 L3（abstention，绝不编造）。可以附带说明"已尝试术语转换/改写等方式仍未找到"以体现透明度，但不代表要展示不确定的候选内容。

**踩过的坑**：第一次答成"输出结果，并标明低置信度"——这恰好是简历里要避免的反模式："答案+置信度标签"本质上还是在呈现一个答案，用户容易忽略标签直接采信，不是真正意义上的降级；正确终态应该是不呈现内容的明确拒答。

### Q12. HyDE（生成假设答案再检索）本身可能幻觉，会不会把检索结果带偏？怎么保证风险可控？

**答案**：三层保障。① **假设答案只用于检索、不参与最终生成**——全程不展示给用户，检索完即丢弃，最终回答只用真实检索到的文档作证据，幻觉内容不会流入最终答案；② **本质原理**：检索只需要语义/主题层面相似，不需要内容事实正确——假设答案哪怕具体数字编错，用词和表达方式通常仍贴近真实文档风格（比原始短问题更接近），这是 HyDE 有效的根本原因；③ **风险面被收窄**：只在已诊断为"词汇失配"的场景触发，不是无条件使用，本来就是检索已失败的场景，用了顶多没帮上、不会把能查对的场景搞坏；且 HyDE 产出结果依然要过同一个质量评估器（融合得分+有效命中数），不会被特殊豁免验证。

**踩过的坑**：第一次表示不了解，是被直接讲解的。

### Q13. 为什么评测集要分八类题型分别测，而不是直接算一个总的 Recall@5？

**答案**：总分会被样本量大的题型平均掉，掩盖某个具体题型（哪怕是关键场景）表现很差的问题。更进一步，分题型评测能定位到底是哪个机制在拖后腿——比如"精确数值查找"类一直上不去，就该去调 BM25 权重/阈值，而不是笼统地"整体优化"；如果所有题型均匀提升，说明双路融合/reranker 本身起了作用。分类型本质是给"该调哪个组件"提供归因依据。

### Q14. 八类题型具体怎么分？能否对应前面讨论的召回失效模式？还缺哪一类？

**答案**：可对应：① 词汇不匹配类（别名/中英混合）→ 测术语转换+双路融合；② 精确数值/型号查找类 → 测 BM25 精确匹配+结构化参数库；③ 模糊/笼统类 → 测改写/HyDE+阈值判断；④ 复合多子问题类 → 测问题拆分；⑤ 图表/曲线类 → 测视觉原生检索（亮点三）；⑥ 跨段落综合类 → 测 reranker+多候选聚合；⑦ 口语化/短查询类 → 测 HyDE/改写。

**关键缺失的一类**：⑧ **无答案/知识库外类**——问题问的信息压根不在库里，正确答案本身就应该是"查不到"。这一类必须单独存在的原因：**"误答率"这个指标的分母就是这类题**——本该拒答的问题里有多少被系统自信地给出了错误答案。前 7 类都是测"该答对时有没有答对"（Recall 维度），第 8 类是反过来测"该拒答时有没有老实拒答"（abstention 准确性维度），没有这一类根本没法算出"无答案场景误答率"这个简历指标，两个维度混在一起算总分同样会互相掩盖。

**踩过的坑**：第一次表示不了解，是被直接讲解的。

### 本轮复盘小结

- **答得扎实的**：设计原则/权衡类判断题——双路失效模式对应关系、阈值方向选择（严格 vs 宽松）、abstention vs 误答的取舍、总分 vs 分题型评测的意义。这类问题背后是"工程判断力"，回答时逻辑链条基本没断。
- **答得薄弱、需要回去补的**：机制细节类——RRF 的 k 常数作用、"有效命中数"信号的存在意义、三种纠错动作各自的判定信号（尤其"问题太复杂"这条完全没有思路）、abstention 终态的正确呈现方式（第一次想成"降级但仍给内容"，混淆了"降级"和"仍然编内容"的边界）、HyDE 风险控制的具体机制、评测集分类的完整性（漏了"无答案类"这个和核心指标直接挂钩的类别）。
- **共性问题**：容易把"给一个打了折扣/标了低置信度的答案"当成"合理的降级"——这是本系统设计主线里最容易被面试官抓住的薄弱点，回去要把"abstention = 不呈现内容的明确拒答"这条边界刻死。
