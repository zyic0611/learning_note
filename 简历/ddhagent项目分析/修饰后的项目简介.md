# DDH Multi-Agent 项目 · 修饰后简历亮点 + 面试深挖手册

> 每条亮点分两层：
> **① 简历写法** —— 给面试官一眼看懂的，结构为"主导设计了X"或"针对问题→采取了什么→指标从多少到多少"，少用专有名词，指标留空。
> **② 深挖准备** —— 这条背后具体用了什么技术、有哪些边界，供你应对面试官多轮深入追问。

## 贯穿全系统的设计主线：三级降级链路

> 面试官最看重"边界考量"——LLM 系统最大的风险不是性能不够，而是**不可控地返回错误答案**。本系统设计上有一条显式的降级链路，任何一层失败都不会输出错误答案，最坏情况是明确告诉用户"查不到"。

```
用户问题
  │
  ▼
L1 结构化参数查询（预置模板，最精确）
  │  模板未覆盖 / 单位解析失败
  ▼
L2 视觉原生召回 + 多路检索 + reranker（RAG）
  │  召回质量低 → 自纠错(改写/拆分) → 仍低
  ▼
L3 明确拒答 / "该信息在库中未找到"（abstention）
      —— 绝不编造，返回不确定回复
```

| 组件 | 主路径 | 兜底路径 |
|------|--------|---------|
| 检索 | 视觉原生（ColPali） | 超时 / 成本超限 → 降级 BM25 + dense 文本检索 |
| 结构化 | 预置模板精确查询 | 字段缺失 / 模板未覆盖 → 降级 RAG 从原文定位 |
| 规划 | LeadAgent 生成完整 DAG | 计划生成失败 → 降级单 Agent 直接回答 |
| 执行 | 多专家并行/串行调度 | 某 Agent 失败 → 阻断下游 + 返回"部分结果" |
| 聚合 | 仲裁校验多 Agent 一致性 | 发现矛盾 → 触发局部 replan 或原样呈现矛盾，不静默丢弃 |
| 生成 | 高质量回答 | 无证据 → abstention，绝不编造 |

## 一、主导设计 Multi-Agent 确定性执行架构

**① 简历写法**
> 主导设计 LeadAgent 统一规划、多专家 Agent 协同执行的架构，将任务规划与执行解耦，按依赖关系并行/串行调度、上游失败阻断下游；并在结果聚合前引入仲裁校验，检测跨 Agent 输出矛盾，避免"各自正确、联合冲突"的结论被直接呈现。复杂任务平均耗时由 **X 秒降至 Y 秒（降低 Z%）**。

**② 深挖准备**
- **核心实现**：LeadAgent 输出的不是图，而是"任务节点 + 依赖关系"的声明式列表（JSON）；服务端把它解析成 DAG，并做 schema 校验 + 环检测 + 引用校验（LLM 可能生成 A→B→A 这类环，不能信任）。调度用 asyncio.TaskGroup 按拓扑排序执行——同层无依赖的节点并行、跨层有依赖的节点串行等待上游输出。节点状态机 PENDING/RUNNING/SUCCESS/FAILED/SKIPPED；节点状态持久化到 PostgreSQL，崩溃后从 checkpoint 断点恢复、已成功节点复用缓存。
- **仲裁校验（跨 Agent 一致性检测）**：多个专家 Agent 的输出可能"局部正确、联合矛盾"——例如选型 Agent 推荐某型号，测试 Agent 同时标记该型号存在已知问题；或项目 Agent 查到的交期与项目截止日期冲突。结果聚合前增加一层仲裁校验，专门检测这类跨 Agent 矛盾；发现矛盾时触发局部 replan，或将矛盾原样呈现给用户由其判断，而不是静默选择其中一个结论、掩盖冲突。
- **幂等怎么落地**：工具调用携带幂等键/自然键，重试不产生重复副作用——这是"写了 retry"和"真 durable"的分界。
- **可观测**：OpenTelemetry 把 LeadAgent/专家 Agent/检索/工具调用统一建模为 span，看关键路径、大模型延迟、token 成本（这条不单列，挂在本条里）。
- **降级链路**：计划生成失败 → 降级单 Agent 直接回答；某专家 Agent 失败 → 阻断下游 + 返回"部分结果"；跨 Agent 输出矛盾 → 触发局部 replan 或原样呈现矛盾，不静默丢弃；成本超限 → 预算熔断降级。
- **必被追问的 5 个点**：
  1. 为什么 Multi-Agent 而不是单 Agent + 一堆工具？→ 异构专家域（选型/项目/测试三套知识域）、状态隔离、可审计的显式计划。
  2. 计划"结构合法但拆解错"怎么办？→ 执行中发现偏离 → 局部 replan。
  3. 用户中途取消/刷新页面？→ 取消传播 + 已执行节点副作用清理。
  4. 成本怎么控？→ 单请求 token/成本预算熔断。
  5. 多个 Agent 输出互相矛盾怎么办？→ 仲裁校验检测冲突，触发局部 replan 或原样呈现给用户，不静默选择其中一个。

## 二、多阶段检索 + 质量感知自纠错

**① 简历写法**
> 针对硬件术语中英混合、同义表达导致的检索召回率低问题，构建关键词 + 语义双路融合、二次精排的检索链路，并将质量信号反馈给自纠错闭环，证据不足时明确拒答、绝不编造。评测集 Recall@5 由 **X% 提升至 Y%**，无答案场景误答率控制在 **B%** 以内。

**② 深挖准备**
- **核心实现**：双路召回 = BGE-M3 密集向量 + BM25 稀疏关键词，RRF 融合后接 Cross-Encoder Reranker 二次精排。两阶段分工：first-stage 召回负责"别漏"，second-stage 精排负责"排对"。
- **查询侧增强**：短问题/口语化问题先用 LLM 生成"假设答案"（HyDE）或改写为检索友好形式再召回，解决查询-文档词汇不对齐的问题。
- **自纠错闭环（正名为 Corrective RAG / CRAG）**：检索评估器用"融合得分 + 有效命中数"判断质量，低于阈值则触发纠错动作（术语转换/改写/拆分 → 重新检索），预算耗尽或仍无效则 abstention。这不是"随手拍的 retry"，而是"评估 → 纠错 → 再检索"的显式控制环。
- **降级链路**：召回质量低 → 自纠错（改写/拆分）→ 仍低 → abstention（不确定回复），绝不编造。
- **必被追问的 5 个点**：
  1. 怎么判断"低质量召回"？→ 融合得分 + 有效命中数的阈值，在评测集上校准（拒绝率与漏答率的 trade-off）。
  2. RRF 的 k、BM25/向量各取多少？→ 消融实验定。
  3. 为什么需要 reranker？→ 召回与精排分工，cross-encoder 精度高于双塔，但慢、只对候选集用。
  4. HyDE 会不会引入幻觉、把检索带偏？→ 假设答案只用于召回、不参与最终回答，且只在词汇失配时启用。
  5. Recall@5 的 ground truth 怎么做？→ 固定评测集人工标注，分八类题型。

## 三、多模态文档检索 —— 视觉原生 + 结构化双轨设计

**① 简历写法**
> 主导设计"视觉原生召回 + 结构化参数抽取"的双轨检索方案：视觉语言模型对页面图像直接 embedding 定位答案，结构化参数库负责精确取值，解决图表类信息在文本解析下丢失的问题。图表类问题回答准确率由 **X% 提升至 Y%**。

**② 深挖准备**
- **核心实现——视觉原生检索（ColPali / ColQwen2）**：视觉语言模型对"页面图像"直接做 patch 级多向量 embedding，用 MaxSim late-interaction 检索，**跳过 OCR、布局解析、图片 caption 生成**。中英混合场景选 ColQwen2（Qwen2-VL 基座，天然吃中文 + 高分辨率）。
- **为什么做这个技术选型（含金量所在）**：旧路线"布局解析 → 文本向量化 + 图片 VLM 描述 + bbox 关联"环节多、每层丢信息；视觉原生把整页图像作为一个检索单元，图表/曲线/pin 图这类"纯文本解析救不回来"的内容召回明显更优。结论不是"我用了 ColPali"，而是"我做过技术选型与对比实验"。
- **第二轨——结构化抽取（老实的支撑细节，不过度包装）**：PDF 表格值抽取 → 单位归一化到统一基准（如电阻统一用 Ω）→ 校验入库，供后续精确查询。这条轨道价值在于"抽得全、抽得准"，是必要的数据工程，不是模型层面的创新点。
- **查询侧防护**：结构化参数库的查询不由大模型自由生成 SQL，而是选定预置模板 + 绑定参数执行，避免幻觉字段与注入风险——这是工程细节，不作为独立卖点。
- **双轨如何共存**：视觉原生解决"哪一页/哪个区域能回答"（召回侧），不做精确取值；结构化抽取解决"精确取值"，不做语义召回。两条轨互补，各司其职。
- **降级链路**：视觉原生超时 / 成本超限 → 降级 BM25 + dense 文本检索；结构化抽取字段缺失 / 模板未覆盖 → 降级 RAG 从原文定位。
- **必被追问的 4 个点**：
  1. 视觉原生贵/慢吗？→ 只用于召回阶段、对候选页精排，控制成本；召回提升的收益 > 多花的算力。
  2. 为什么不直接用视觉原生取代结构化抽取？→ 它做召回、不做精确取值，"85°C 下最大电流 = 3.2A"要落到结构化参数库才准。
  3. caption 还做吗？→ 视觉原生路线下不再依赖 caption，避免"描述丢细节"的老问题。
  4. 公共文档离线建库 vs 用户上传在线增量？→ 复用同一条管线，只是触发方式不同。

## 四、主导设计多租户资源治理层

**① 简历写法**
> 针对多名工程师同时使用系统时，不同用户的多 Agent 任务竞争同一批模型调用与外部系统资源、复杂任务容易挤占简单任务响应时间的问题，主导设计多租户资源治理层：按模型调用、数据库连接、下游系统调用等不同资源类型分别设置并发上限，请求间按公平轮转分配执行槠位而非先进先出，避免单个复杂任务独占资源；同时补齐跨请求的成本预算核算与限流。高并发场景下简单请求的 P95 延迟由 **X 秒降至 Y 秒**，资源利用率提升 **Z%**。

**② 深挖准备**
- **核心实现——两层调度模型**：单请求内的拓扑排序只决定"哪些节点依赖已满足、有资格执行"，这是"资格"不是"时机"；真正决定"这一刻谁能实际拿到执行槠位"的，是一个**全局共享资源池**——所有用户所有 DAG 里已具备执行资格的节点，向这个全局池申请槠位，池子容量对应真实基础设施承载力（模型 API 并发上限、数据库连接池大小、下游系统承受能力）。
- **公平排队，不是先进先出**：如果只是 FIFO，一个用户的复杂任务（一次性产生多个就绪节点）会把队列前排占满，导致另一个用户的简单查询排在后面——正确做法是按用户/请求做**轮转分配**，即使某用户同时有多个节点就绪，也不会一次性把所有空闲槠位分给他，简单请求不会被复杂任务"因为节点多"而挤占。
- **按资源类型分别设限，不是一个笼统数字**：模型 API 调用、数据库连接、下游系统调用的承载力完全不同，分别注册容量上限，而不是共用一个总闸门。
- **重试风暴防护**：单个任务的失败重试（亮点一里的机制）同样要走这个全局资源池申请槠位，不能绕过限流直接打——否则高负载下大量并发重试会互相叠加，把资源池冲垮，需要给重试设置比新请求更低的抢占优先级，防止级联放大。
- **与亮点一的边界**：亮点一管"单个请求内部怎么编排对"（依赖解析、状态机、局部 replan、仲裁）；本条管"多个请求之间怎么公平分资源"——调度器向全局资源池申请执行槠位这个动作，是两者的接口，责任不重叠。
- **降级链路**：资源池满 → 排队等待，明确告知预计等待时间，不是直接拒绝服务；排队时间超过阈值 → 可选择走"降级单 Agent"的更快路径，而不是让用户无限等待。
- **必被追问的 5 个点**：
  1. 为什么不是先进先出？→ 复杂任务多节点会占满队列前排，公平轮转按请求而不是按节点分配槠位。
  2. 不同资源类型的限制怎么定？→ 按真实基础设施承载力配置，分别设限，不是一个笼统数字。
  3. 和亮点一的预算熔断什么关系？→ 亮点一是单请求内"还能不能再来一轮"，本条是跨请求的资源分配/限流，两个层次，不重叠。
  4. 大量重试会不会把资源池冲垮（重试风暴）？→ 重试同样要走全局资源池申请槠位，且优先级低于新请求，防止级联放大。
  5. 系统繁忙时用户体验是什么？→ 排队 + 预计等待时间提示，超时可降级到更快路径，不是直接报错。

## 结构总览

| 亮点 | 级别 | 定位 |
|------|------|------|
| 一 · 确定性执行架构（含跨 Agent 仲裁校验） | S | 灵魂，Agent Infra 深度 |
| 二 · 多阶段检索 + 自纠错 | A | 检索深度 |
| 三 · 多模态检索（视觉原生双轨） | 收敛 | 支撑，别抢戏 |
| 四 · 多租户资源治理（全局并发 + 公平调度 + 成本核算） | A | 后端工程深度，区别于纯 AI/Agent 视角 |

> 四条都"看得懂、有亮点、有核心技术、指标留空"，底下每条都有"具体技术 + 边界追问 + 降级链路"的弹药，能扛住面试官连问几轮。
