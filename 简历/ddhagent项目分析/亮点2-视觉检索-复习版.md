## 〇、30 秒故事线（🔴 开场怎么讲）

```
硬件文档（图表/曲线/复杂表格为主）
   │  整页渲染成高分辨率图像（跳过 OCR/布局解析）
   ▼
ColQwen2：页 → ~1024 个 patch → 每个 patch 一个 128 维向量（不做整页池化）
   ▼
双层存储：①粗排层 = mean pooling 单向量 → HNSW ANN 索引（快）
          ②精排层 = 原始 1024×128 多向量全量存储（准）
   ▼
查询：query → 同一 ColQwen2 编码成多个 token 向量
   ANN 粗排 Top-200 页 → MaxSim 精排打分（late interaction）
   ▼
Cascade 降级：MaxSim 最高分 < 阈值 → 自动降级 BM25 + dense + Reranker 文本双路
   ▼
定位答案区域（max 索引反查 patch 坐标）→ 返回
```

**一段话版本**（开场直接背这个）：

"硬件文档里大量信息在图表、曲线、复杂表格里，纯文本检索对这种内容是**系统性静默盲区**——不是搜不出结果（空结果反而是可检测的失败），而是返回一堆语义相关但答案错误的候选，系统看到'有结果、置信度还不低'，不会触发任何补救。我们的方案：跳过 OCR 和布局解析，整页 PDF 渲染成图像，用 ColQwen2 做 patch 级多向量 embedding——每页约 1024 个 128 维向量，保留每个局部区域的独立语义。建库时存两层：单向量进 ANN 索引做粗排，全量多向量留给精排。查询时 ANN 粗排到 Top-200 页，MaxSim 精排打分，分数不足自动降级文本双路。图表类问题准确率从 35% 提到 73%。"

## 一、必背核心（🔴 面试 80% 问题从这出）

### 1. 问题动因：为什么文本检索对图表是"系统性静默盲区"

关键不是"文本检索效果差"，而是**检测不到自己错了**：

- BM25/dense 对"答案其实在图表里"的 query，通常**不返回空结果**（空结果是可检测的明确失败），而是返回一堆**语义相关但答案错误/不完整**的候选——比如命中了讨论某参数的文字段落，但具体数值只在旁边的曲线图里；
- 系统看到"有结果、置信度还不算低"，不会触发任何升级机制；
- **这是静默错误，没法靠"搜不到才补救"的机制发现。**

### 2. 技术方案五步（背诵骨架）

1. **不做 OCR，直接渲染成图**：整页 PDF → 高分辨率图像作为检索单元。OCR 读不出曲线/形状、读出乱码；布局解析搞错阅读顺序；caption 化又是一次有损压缩。
2. **ColQwen2 patch 级多向量 embedding**：页 → ~1024 个 patch → 每个 patch 一个 128 维向量；**不做整页池化**，保留每个 patch 的独立语义（多向量表征，思想来自 ColBERT）。
3. **双层存储**：粗排层 = mean pooling 单向量 → HNSW ANN 索引；精排层 = 原始多向量全量存储。建库时两份都算好，不在查询时现场算。
4. **ANN 粗排 + MaxSim 精排**：粗排快速缩到 Top-200 页；精排对候选页用 MaxSim 逐页打分。
5. **Cascade 分数驱动降级**：MaxSim 最高分低于阈值 → 自动降级文本双路（BM25 + dense + Reranker）兜底。

### 3. 三个关键设计决策（🔴 被追问的核心）

**决策 1：为什么跳过 OCR？**

- 图表/曲线/pin 图上 OCR 要么读不出来、要么读出乱码；布局解析会搞错阅读顺序；caption 是有损压缩（"曲线在 80°C 之后斜率骤降"这种细节很容易丢）；
- **最深的洞察（⚪加分）**：OCR 的根本问题不是"读不出文字"，而是"**读出来之后丢失了结构**"——OCR 读出"3.2A"和"85°C"，但不知道它们在同一行表格里；视觉方案的 patch 向量过完 self-attention 天然知道这种上下文关系。OCR 能读出的文字，视觉方案一样能处理，还额外保留位置关系和上下文语义。

**决策 2：为什么两阶段，不全库 MaxSim？**

- 对全量 300 万页做完整 MaxSim ≈ **614 亿次点积**，线上实时不可接受；
- 粗筛到 Top-200 后降到 **410 万次**，差 **4 个数量级**；
- 不是省钱优化，是"**不做就跑不起来**"的必要设计。

**决策 3：为什么 Cascade 而不是路由（Query 意图分类）？**

- 路由需要提前判断 query 类型，但意图往往模糊——"85°C 下最大电流"答案可能在表格也可能在文字段落，光看 query 分不清，分类器容易判断错；
- 而且路由判断后，**每条路径后面还是要挂分数阈值做兜底**——多了一层判断，但没减少任何兜底逻辑；
- Cascade 让分数说话：MaxSim 分数低就是"视觉路径没搜到什么"的直接信号，比任何分类器可靠；
- 路由只在有标注数据证明分类器准确率达标时才值得加——**锦上添花，不是基础设计**。

### 4. 结果与评估口径（🔴 数字必被问）

- **35% 基线怎么来的**：针对图表/曲线类问题单独建评测子集——选"答案只在图表里、文本段落里找不到"的问题，人工标注正确答案和答案所在页码。Baseline 是原方案（OCR + 布局解析 + 文本向量化）的准确率——OCR 只能读出轴标签、孤立数字，读不出曲线形状/走势，文本向量也没有对应的视觉信息可检索，答案准确率本来就低。
- **73%**：视觉原生方案在同一评测集上的准确率。评测同时验证"回答对了"和"定位到了正确页面"两个维度。
- **口径要点（防被问倒）**：这是**图表类问题子集**的准确率，不是全量。被问"总体准确率多少"时可以说："整体更高，但 35%→73% 这个数字针对的是图表类子集——因为那才是这个方案要解决的问题。"

## 二、深挖弹药库（🟡 被追问才展开）

### 2.1 ColQwen2 原理（四个"为什么"）

**Q1：为什么不压成一个向量（整页池化）？**
压成一个向量 = 表格里的"3.2A"、曲线斜率、大段说明文字全部稀释进同一个点。核心是**粒度问题，不是位置问题**——丢的不是位置（位置编码在 ViT 阶段就带上了），是"细粒度区分能力"：一个向量承载不了几十个不同语义的局部信息点。

**Q2：为什么过完视觉编码器还要过 Qwen2 LLM backbone？**
ViT 输出的 patch 特征是**孤立的**——每个 patch 只看到自己格子里的像素。过 self-attention 后，每个 patch 向量融入整页上下文：只写"3.2A"的 patch，过完后知道自己在表格里、旁边是"85°C"那一行。**为什么必须过 LLM**：query 词是带语言理解的语义向量，patch 向量也必须带语义才能匹配得上——两种模态要活在同一个坐标系，点积才有意义。

**Q3：为什么压缩到 128 维？**
MaxSim 是 query 每个 token × 候选页每个 patch 的点积，对多个候选页反复做——维度越高，每次点积越贵，总成本线性放大；存储同理。ColBERT 验证过 128 维足够表达单个语义单元，继续加维收益不大。

**Q4（⚪理论辨析，被追才展开）：压向量数量（1024→1）和压向量维度（几千→128）有什么本质区别？**
两个完全不同的轴：
- **压数量**：丢的是"区分能力"本身——"3.2A"、曲线斜率、文字段落是性质不同的东西，池化后身份搅在一起，再也无法单独指向任何一个——**范畴性损失**；
- **压维度**：丢的是"描述单个东西的冗余维度"——每个 patch 只负责一个很窄的语义单元，几千维里大量方向是冗余的，砍掉损失小。
类比：100 个文件夹合并成 1 个 = 从此分不清"财务"和"合同"；每个文件夹的标签从一段话精简成一句摘要 = 只要还能认出是谁，没真丢信息。

**Q5：query 侧怎么处理？（对称设计）**
query 文本 → tokenizer 切 token → 过**同一个** Qwen2 LLM backbone（"最大"和"电流"互相"看到"对方，融合成组合语义）→ **同一个** 128 维线性投影层 → 每 token 一个向量，不池化。

**最关键的共同设计**：图片 patch 和文字 token 走**同一套 backbone、同一个投影层**——两者的向量活在同一个坐标系里，点积才有意义。如果各用各的模型，向量空间不对齐，点积算出的数字毫无意义。这不是"VLM 更聪明"，是"两种模态被映到同一个可比较的空间"。

**对称性**：query 在两阶段用两种形态——粗排 mean pooling 成 1 个向量去 ANN，精排保留多 token 向量做 MaxSim；和文档侧"双层存储"完全对称。

### 2.2 MaxSim 精排

```
score(Query, Page) = Σ_i  max_j ( q_i · d_j )
```

**侦探类比（照这个跟面试官说）**：把 query 拆成几个词，每个词是一个独立侦探，拿着自己的向量去这一页所有 patch 里逐一比对"像不像"（点积），只汇报自己找到的最高分；所有侦探的最高分加起来，就是这一页的总分。

- `q_i`：第 i 个侦探（query 第 i 个 token 的向量）；
- `max_j(q_i · d_j)`：侦探 i 扫完页面所有 patch，只留自己的最高分；
- `Σ_i`：所有侦探的最高分加总。

**核心：每个词各自找自己的落点，不要求所有词落在同一个地方。** "85°C"命中页顶的 patch，"最大电流"命中底部表格的 patch，物理位置隔得再远照样各自命中——这叫 **late interaction（晚期交互）**：细粒度单元保留身份，打分那一刻才逐一比对，不提前糊在一起。

**为什么取 max 不取平均**：取平均，空白 patch、曲线 patch 的低分会把真命中 patch 的高分拉低——和"整页池化成一个向量"犯的是**同一种稀释错误**。取 max = 明确说：不相关 patch 存在与否根本不影响这个词的得分。

**变长天然支持**：max 和 Σ 对集合大小不敏感——800 个 patch 和 1200 个 patch 操作方式一样；query 3 个 token 加 3 次，15 个加 15 次。不需要 padding/对齐/归一化，这是 late interaction 的副产品优势。

**🟡 归一化的坑（细节深挖）**：Σ 是求和不是平均——**长 query 天然算出更高的绝对分数**（词多、加的项多）。对"同一个 query 比不同页面"没影响，但 Cascade 的降级阈值如果是固定数值，不同长度 query 越过阈值的难度不一样。工程上要在**阈值比较前按 query token 数归一化**，或评测集校准时控制 query 长度分布。注意：归一化出现在**阈值比较**这一步，不是 MaxSim 计算本身。

**粗排 vs 精排一句话区分**：
- 粗排 = **页面主动被召回**（ANN 搜索，页面是主体，速度优先）；
- 精排 = **query 的每个词主动去页面里找最佳落点**，落点分数加总 = 页面总分（query token 是打分主体，精度优先）。patch 是被动被挑选的，不是"每个 patch 打分再加总"。

### 2.3 双层存储与成本

**为什么建库时存两份**：全量多向量存储 ≈ **750GB**，是单向量 dense 索引的 25~30 倍；查询时现场池化 = 把离线成本推到在线路径上，直接拖延迟。所以离线建库时两份都算好。

**750GB 徒手推导**（面试官爱考，记步骤）：
- 1 个向量：128 维 × 2 字节（fp16）= 256 字节
- 1 页：256 字节 × 1024 patch = 256 KB
- 300 万页：256 KB × 300 万 ≈ **750 GB**
- 300 万页怎么来的：约 1 万份硬件 PDF × 每份平均 300 页（业务量级估算，不是精确数字——面试官问这个是想看你清不清楚数字背后的推导逻辑，不是考背诵）

**回答分两层**：① 750GB 离线存储可接受（一次性建库，增量更新，新文档触发不必重跑全库）；② 查询时靠双层存储控成本——单向量 ANN 索引不到 1GB，全量多向量只在精排候选 200 页时用。

**🟡 踩坑题：粗排用 mean pooling 压成一个向量，你不是刚批评"压成一个向量丢细节"吗？自相矛盾？**
答法：粗排的目标不是精确匹配，而是**不漏掉真正相关的页面**——mean pooling 的单向量仍能反映整页整体语义方向，真相关页大概率进候选 200；细节的精确匹配交给 MaxSim 精排。
**一句话记住：粗排负责"不漏"，精排负责"不错"，分工不同，不矛盾。**

### 2.4 降级与阈值

**降级阈值怎么定**：评测集上校准，观察**降级率**和**图表类准确率**的 trade-off：
- 阈值太高 → 频繁降级，视觉路径优势发挥不出来；
- 阈值太低 → 视觉分数低但没触发降级，强行用了质量较差的视觉结果，图表类准确率下降。
**硬件文档场景宁可多降级（文本路径随时能兜底），不用低置信度视觉结果。**

**⚠️ 措辞注意（踩坑）**：不要说"阈值低会导致错误信息被召回"——应该说"视觉路径置信度不够但没触发降级，强行用了**定位不精准**的视觉结果"。**不是召回了错误信息，是定位不精准。**

**⚠️ 纯文本 query 会不会更差？（踩坑）**：
**不能说"不会更差，因为 patch 粒度更细"——这个逻辑是错的**（切得细不代表对纯文字更好，很多 patch 是空白/边距，对文字 query 没贡献）。
正确答法：视觉路径对纯文字 query 确实稍弱（不如 BM25 精确关键词匹配、BGE 语义向量）。但这正是 Cascade 的用武之地——纯文字 query 对应的 MaxSim 分数大概率不高，自动降级到文本路径。**两条路径不是互斥，是互补。**

## 三、面试连环追问速查（🟡 含踩坑记录）

**Q：为什么不直接给图表加 caption，让文本检索能找到？**
caption 是有损压缩，细节容易丢；而且生成 caption 本身要一次 VLM 推理，成本不比视觉 embedding 低，还多一道"图→文字描述→文字向量"的有损链路。不如直接用 VLM 做视觉 embedding——输出直接编码视觉形状的向量，没有中间转换损失。

**Q：视觉原生检索贵不贵？怎么控成本？**
贵在两处：① 建库（离线一次性，约 250 GPU 小时量级，新文档增量触发，不重跑全库）；② 查询时精排——两阶段设计已把查询成本压到和普通向量检索同量级（ANN 粗排极快，MaxSim 只对候选 200 页跑）。

**Q：MaxSim 和普通余弦相似度的本质区别？**
余弦：整页池化成 1 个向量，一次点积出分数，细粒度对应关系丢失；MaxSim：query 每个 token 分别去页面所有 patch 找最佳匹配——"85°C"精确命中表格里写着 85°C 的那个 patch，"最大电流"命中旁边那列的 patch，两个词在图里空间不相邻也能各自精准匹配。

**Q：patch 之间的关联关系怎么解析的？**
不是单独设计的——patch 向量过 Qwen2 LLM backbone 时 **self-attention 自然完成**，每个 patch 的最终向量融合整页上下文，不是孤立的局部特征。

**Q：如果让你重新设计，有什么改进点？（⚠️ 陷阱题）**
**坑：不能说"加路由，根据 query 类型提前决定走哪条路"**——这就是 Cascade 方案里已经分析并否定过的方向（意图模糊、分类器易错、兜底逻辑没少）。
可以说的真实改进方向：
1. **阈值自适应**：根据 query 特征（是否含数值/单位关键词）动态调整降级阈值，而不是全局一个静态值；
2. **两路并行 + 分数融合**：视觉和文本路径同时跑、加权融合——代价是查询成本翻倍，适合延迟敏感度低的场景；
3. **建库增量更新优化**：文档更新频繁时，异步队列减少新文档进库延迟。
**答题结构**：先说一个改进点，再主动说"我们当时也考虑过 X，但因为 Y 没选"——显得思考过多种可能性，不是只会背一个方案。

## 四、新增补强（原文档没有，面试必被问）

### 4.1 答案区域定位怎么做（🔴 简历写了"定位答案区域"，必须能答）

- MaxSim 给页面打分后，对胜出页面：把 query 每个 token 的**最高分 patch** 收集起来——每个 patch 有空间坐标（max_j 的索引 j 对应页面上的位置）；
- 按空间位置聚类/取包围盒，得到"答案区域"，返回时标注页码 + 区域；
- **一句话背**：粗排选页，精排打分，**MaxSim 的 max 索引反查 patch 坐标定区域**。

### 4.2 ColPali vs ColQwen2（🟡 被懂行面试官追问时的准备）

- **ColPali**（2024）：VLM 直接做文档检索的**开创者**——页面渲染成图 → patch 级多向量 → late interaction 打分。"免 OCR、免布局解析"这条技术路线是它确立的；
- **ColQwen2**：同一技术路线、视觉编码器换成 **Qwen2-VL** 的版本——Qwen2-VL 支持**原生动态分辨率**（不强制 resize 到固定尺寸，保留表格小字/细节），中文语料充分，中英夹杂的硬件文档（中文说明 + 英文型号/单位）吃得住；
- 为什么选 ColQwen2 不选 ColPali：同路线新一代，**动态分辨率对文档小字更友好** + 中文语料更匹配业务文档；
- ⚠️ 被问"你对比过 ColPali 吗"：诚实答"调研过同路线，ColQwen2 在动态分辨率和中文文档上更合适"即可，**不编造评测数字**。

### 4.3 文本双路具体是什么（🟡 被追问"降级到哪"）

- **BM25**：精确关键词匹配——型号、编号、参数值这类高精度 token 的场景；
- **dense（BGE）**：中文语义向量——召回语义相关段落，弥补 BM25 对同义表达的盲区；
- **Reranker**：交叉编码器重排（如 BGE-Reranker）——对双路召回结果融合后重排 Top-K；
- 一句话：**BM25 保精度、dense 保召回、Reranker 做融合重排**——这条链路随时在线、随时能接管。

### 4.4 ANN 选型（🟡 为什么 HNSW）

- **HNSW**（Hierarchical Navigable Small World）：图结构索引，**高召回、低延迟**，内存占用较高——粗排单向量只有 ~1GB，内存压力可控，选它；
- IVF（倒排 + 量化）：省内存、召回略降、需要训练聚类中心——数据量大到内存装不下时才考虑；
- 暴力搜索：召回 100% 但延迟不可接受——只作离线评测基准；
- 一句话：粗排向量规模小（单向量 × 300 万页 ≈ 750MB），HNSW 的内存代价完全可接受，换取高召回低延迟。

### 4.5 与亮点 1 / 3 的联动（呼应亮点1复习版 4.3）

- **与亮点 1**：视觉检索的"MaxSim 分数低 → 降级文本双路"，正是亮点1 replan 的"低置信度触发信号"之一——检索型 Agent（选型 Agent）的融合得分/命中数复用自这条链路，作为"自报低置信度"的确定性信号；
- **与亮点 3**：亮点3 的"数字/扫描 PDF 分流"——扫描 PDF 正是视觉检索的天然应用场景（无文本层可走抽取）；两条管线一个管"查"（亮点2）、一个管"抽"（亮点3），数据同源（硬件知识库）。

### 4.6 讲法建议（包装感防御）

- **数字口径**：35%→73% 是**图表类子集**评测，别被"总体多少"问倒；750GB 是业务量级估算（1 万份 × 300 页）；
- **模型细节别过度展开**：被问 ColQwen2 参数量/训练方式，答"基于 Qwen2-VL 的文档检索专用变体，patch 级多向量 + late interaction"即可，**不编造细节**；
- **第一人称工程叙述**：多用"我们当时先试了 OCR 方案，发现读出来丢结构……所以改成视觉原生"——原文件的踩坑记录就是现成素材。
