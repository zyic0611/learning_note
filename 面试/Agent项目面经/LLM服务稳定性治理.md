

**LLM 服务稳定性治理**：构建 LLM 调用异常分类、指数退避与随机抖动重试、**失败率熔断及半开探测机制**，结合连接、读取、请求级超时和全链路重试预算，避免模型服务抖动引发重试风暴与故障级联；为 SSE 流式链路增加**心跳保活、总时长控制和客户端断连取消**，提升长耗时 Agent 任务的可用性与资源回收能力。

---

## 一、90 秒项目总述

### Q：请介绍一下你是怎么做 LLM 服务稳定性治理的。

### A：

Agent 一次请求可能调用模型多次，比如先理解问题、再生成查询计划、再生成 SQL。如果模型服务发生短暂超时，完全不重试会影响成功率；但所有失败都立即重试，又可能在模型故障时把请求量成倍放大，形成重试风暴。

所以我做了四部分治理。

第一是异常分类。连接超时、限流以及网络异常 属于暂时性故障，可以有限重试；参数错误、鉴权失败、上下文超长和内容安全拒绝这类问题，重试也不会恢复，直接返回或进入降级流程。

第二是有节制地重试。可重试错误采用指数退避，每次失败后等待时间逐渐增加，并加入随机抖动，避免多个实例在同一个时间点一起重试。同时设置单次调用的最大尝试次数，以及整个 Agent 请求共享的重试次数和时间预算，防止工作流里的多个节点各自无限重试。

第三是熔断。当最近一段时间内模型调用达到一定请求量，并且失败率超过阈值时，熔断器从关闭状态进入打开状态，新请求先快速失败。等待一个冷却时间后进入半开状态，只允许少量探测请求；探测成功再恢复，失败则重新打开。

第四是 SSE 流式治理。Agent 长时间没有输出时，服务端定期发送心跳，防止网关把空闲连接关闭；同时设置整个流的最长持续时间。检测到用户关闭页面或网络断开后，会取消模型流、后续节点和数据库任务，并在 `finally` 中释放连接等资源。

整体目标不是保证模型永远不失败，而是在模型抖动时控制重试规模、快速止损，并确保用户离开后后台任务不会继续白白消耗资源。

## 二、为什么需要稳定性治理

### Q1：LLM 调用和普通接口调用相比，有什么特殊之处？

### A：

主要有三个特点。

第一，单次调用时间更长，受到模型排队、生成长度和网络流式传输影响。

第二，一次 Agent 请求通常不止调用一次模型。

第三，模型输出具有随机性作用。

所以重试必须结合错误类型、工作流状态和剩余时间，不能简单套一个装饰器就结束。

### Q2：什么叫模型服务抖动？

### A：

就是模型服务没有完全宕机，但短时间内出现不稳定，例如：

- 偶发连接失败；
- 响应突然变慢；
- 网络异常
- 限流
- 流式输出到一半长时间没有新数据。

这种情况适合“有限重试加熔断”，因为少量故障可能自己恢复，持续故障则需要尽快停止施压。

### Q3：什么叫重试风暴？

### A：

假设模型服务变慢时，原来有 100 个请求，每个请求都立刻重试 3 次，短时间内就可能变成 300 个额外请求。模型越慢，重试越多；重试越多，模型又越难恢复。

如果应用有多个实例，而且大家都按固定间隔重试，还会在同一个时间点再次集中请求。

指数退避、随机抖动、重试预算和熔断，就是分别从“降低频率、打散时间、限制总量、持续故障时停止调用”四个角度解决这个问题。

### Q4：什么叫故障级联？

### A：

模型服务变慢以后，应用线程或异步任务一直等待，连接池和内存逐渐被占满；随后其他正常请求也拿不到资源，最后原本只是模型接口的问题扩大成整个 Agent 服务不可用。

---

### Q6：哪些异常通常可以重试？

### A：

通常是暂时性故障，例如：

- 连接建立失败或连接超时；
- 连接被远端临时重置；
- 读取超时；
- 429 限流；
- 502、503、504 等网关或服务暂时不可用；
- 服务端明确返回可以稍后重试的错误。

即使能重试，也必须受到最大次数、剩余时间和熔断状态限制。429 如果带有服务端建议等待时间，应优先参考它。

### Q9：结构化输出解析失败要不要重试？

### A：

要看原因。

如果模型只是偶发没有按照要求返回 JSON，可以在预算内做一次受控修复，把解析错误和格式要求重新提供给模型。

如果输出规则本身配置错误，或者上下文字段互相矛盾，继续调用模型没有意义，应该修复程序或进入澄清。

它属于业务层重试，和网络超时重试要分别计数，但都要消耗同一个全链路预算。


## 四、指数退避与随机抖动

### Q11：什么是指数退避？

### A：

就是每次失败后不要立刻重试，而是越往后等待越久。

例如基础等待时间是半秒，大致可以是：

```text
第一次失败：最多等0.5秒
第二次失败：最多等1秒
第三次失败：最多等2秒
第四次失败：最多等4秒
```

同时会设置最大等待上限，不能无限增长。

这样可以给下游服务恢复时间，也避免应用不断发送请求。


### Q13：随机抖动是什么？

### A：

就是在等待时间里加入随机性，把原本集中在同一个时间点的重试打散。

例如第二次重试最多等待两秒，不是所有请求都固定等两秒，而是在零到两秒之间随机选择。

可以简单记成：

```text
指数退避负责越失败等得越久
随机抖动负责大家不要一起醒来
```

### Q14：重试多少次比较合适？

### A：

没有所有项目通用的数字，要结合接口耗时、用户可接受等待时间和错误类型。

通常只做少量重试

### Q15：为什么重试前要看剩余时间？

### A：

假设整个 Agent 请求只剩两秒，但下一次模型调用通常需要五秒，这时即使还有重试次数，继续尝试也没有意义。


### Q16：为什么不能在 SDK、业务封装和 LangGraph 节点里都各自重试？

### A：

因为多层重试可能叠加。

例如底层 SDK 重试三次，外层节点又重试三次，实际模型请求可能远超我们以为的三次。Agent 又有多个模型节点时，总调用量会进一步放大。

所以要明确只有哪一层负责网络重试，并让所有节点共享一个全链路重试预算。

## 五、全链路重试预算

### Q18：什么是全链路重试预算？

### A：

可以把它理解成整个 Agent 请求的一张“重试储值卡”。

一次请求可能经过：

```text
意图理解 → 查询计划 → SQL生成 → 结果解释
```

每个节点都可能调用模型。如果每个节点都只看自己的重试上限，整条链路可能调用太多次。

所以请求开始时就设置总次数和总时间，各节点每重试一次都要消耗同一份预算。预算用完后，即使当前节点自己的次数还没用完，也不能继续。

### Q19：单次超时和全链路预算有什么区别？

### A：

单次超时限制某一次模型调用最多等多久；全链路预算限制整个 Agent 请求最多为重试额外付出多少时间和次数。

例如一次模型调用最多30秒，不代表四个节点都可以各等30秒再重试多次。整条链路还需要一个更外层的总截止时间。

### Q20：重试预算里通常记录什么？

### A：

至少包括：

```text
请求总截止时间
已经尝试的模型调用次数
已经发生的重试次数
各错误类型的重试次数
当前剩余时间
是否已经向用户输出内容
客户端是否仍在线
```

最后两项很重要，因为已经流式输出或者用户已经离开时，重试策略会不同。

### Q21：为什么要把截止时间向下传递？

### A：

否则下游节点不知道上游已经花了多久。

例如整个请求最多允许60秒，上游已经用了45秒，下游模型调用就不能再设置30秒超时。它应该根据剩余15秒决定是否调用，并把单次超时压到剩余预算以内。

### Q22：网络重试和业务反思是不是同一种重试？

### A：

不是。

网络重试是因为模型接口暂时不可用，通常使用相同请求再次尝试。

业务反思是模型返回了结果，但格式、SQL或者计划不符合要求，需要携带明确错误重新生成。

两者原因和次数上限可以不同，但都会增加调用量和延迟，所以都应该消耗全链路预算。

## 六、熔断器

### Q23：熔断器是什么？

### A：

它和家里的空气开关比较像。

下游只是偶发失败时，正常调用加有限重试就可以；如果最近请求持续大量失败，说明服务可能已经出问题，这时继续调用只会增加压力。熔断器会暂时切断调用，让新请求快速失败或走降级逻辑。

等待一段时间后，它再放少量请求试探服务是否恢复。

### Q24：熔断器的三个状态是什么？

### A：

三个状态是：

```text
关闭：正常放行请求并统计结果
打开：暂时不调用模型，直接快速失败
半开：只放少量探测请求判断是否恢复
```

这里“关闭”代表电路接通、正常调用；“打开”代表电路断开、停止调用。这个名字第一次听容易反。

### Q25：熔断器什么时候从关闭变成打开？

### A：

通常不是失败一次就打开，而是在一个滚动时间窗口内：

1. 请求数量先达到最小统计量；
2. 可计入的失败率超过阈值；
3. 才进入打开状态。

设置最小请求量是为了避免样本太少。例如只有一个请求且失败率100%，不能据此判断整个模型服务不可用。

### Q26：哪些失败应该计入熔断失败率？

### A：

应该计入真正代表下游服务不稳定的错误，例如连接失败、读取超时、部分服务端错误。

不应该计入：

- 用户主动取消；
- 请求参数错误；
- 鉴权配置错误；
- 内容安全拒绝；
- 本地业务校验失败。

否则熔断器反映的不是模型健康度，而是把用户和程序错误也混了进去。

### Q27：打开状态下为什么要快速失败？

### A：

因为已经有足够证据说明下游暂时不可用。继续让每个请求等待连接超时、再重试，只会占用应用资源并加重模型压力。

快速失败可以及时释放线程、协程和连接，把系统容量留给仍然可用的功能。

### Q28：什么是半开探测？

### A：

熔断器打开一段冷却时间后，不会一下子恢复全部流量，而是进入半开状态，只放少量请求。

如果这些请求连续成功，说明模型基本恢复，熔断器回到关闭状态；如果探测仍然失败，就重新打开并继续等待。

### Q29：为什么半开状态不能一下子放开所有请求？

### A：

模型服务可能只是刚恢复，还比较脆弱。如果所有积压请求同时涌入，很可能再次把它压垮。

半开阶段只允许少量探测，相当于先试水，再逐步恢复。

### Q30：失败率阈值和冷却时间应该怎么设置？

### A：

要根据真实流量、正常错误率、模型恢复时间和用户等待要求来定。

阈值太低会频繁误熔断，太高又不能及时止损；冷却时间太短会反复探测，太长会延迟恢复。

项目中应该通过监控和故障演练调参。面试时必须回答真实配置，没有确认时不要现场编造百分比和秒数。

### Q31：有了熔断器，还需要重试吗？

### A：

需要，两者解决的层次不同。

重试解决偶发失败，熔断解决持续失败。正常情况下先做有限重试；当整体失败率过高时，熔断器阻止更多请求和重试继续打向下游。

### Q32：多实例部署时，每个实例自己熔断有什么问题？

### A：

每个实例只能看到自己的请求样本，可能出现一部分实例已经熔断，另一部分仍在持续调用；实例重启后本地状态也会丢失。

流量较小时本地熔断简单、故障隔离好；如果希望所有实例共享模型健康状态，可以通过网关、服务网格或者共享状态协调，但会增加复杂度。

面试时按项目真实实现回答。如果只是进程内熔断，就不要说成全局分布式熔断。

### Q33：熔断打开后，用户怎么办？

### A：

不能一直转圈等待。可以根据业务能力：

- 快速返回“模型服务暂时繁忙，请稍后重试”；
- 对已有结果型追问使用缓存结果；
- 对非实时任务转成异步任务；
- 如果确实接入了兼容的备用模型，可以受控降级。

备用模型的能力、上下文长度和结构化输出可能不同，不能简单切换后假装完全等价。没有真实实现备用模型时，只能把它说成改进方向。

## 七、分层超时

### Q34：为什么要区分连接超时、读取超时和请求级超时？

### A：

因为它们对应不同阶段：

```text
连接超时：多久还没和模型服务建立连接就放弃
读取超时：连接建立后，多久没有收到新数据就放弃
请求级超时：一次完整模型调用最多允许持续多久
```

只设置一个超时，很难区分是连接不上、生成过程中卡住，还是整体时间太长。

### Q35：连接超时应该很长吗？

### A：

通常不应该太长。

连接阶段没有开始模型计算，长时间连不上往往代表网络或服务入口有问题。尽早失败后做有限重试，比长期占住资源更合理。

具体秒数要根据网络环境和监控数据设置。

### Q36：读取超时在流式调用里是什么意思？

### A：

流式调用可能持续很久，但只要模型不断返回数据，就不应该因为总耗时稍长而被“读取超时”误杀。

读取超时关注的是：连接已经建立，但连续很长时间一个新数据块都没有收到。这可能说明上游连接卡住。

它和整个请求的总时长限制不是一回事。

### Q37：请求级超时和 Agent 总时长有什么区别？

### A：

请求级超时限制一次模型调用；Agent 总时长限制从用户发起请求到整个工作流结束。

一个 Agent 可能调用模型三次，每次都没有超过单次超时，但加起来仍然超过用户可以接受的时间，所以还需要最外层的总截止时间。

### Q38：超时后只是给用户返回错误就行吗？

### A：

不够。

还要取消正在运行的模型流、数据库查询和后续任务，并释放连接。如果只是接口不等了，后台任务仍然继续跑，资源还是会被消耗。

## 八、SSE 流式链路

### Q39：SSE 是什么？为什么适合大模型？

### A：

SSE 是基于 HTTP 长连接的服务器单向推送。

模型生成一点，服务端就可以推送一点，前端边接收边展示。它主要改善首段内容到达时间和用户等待感，不一定缩短完整回答总时间。

聊天场景主要是服务端持续向客户端输出，因此 SSE 比需要双向高频通信的 WebSocket 更简单。

### Q40：SSE 心跳是什么？解决什么问题？

### A：

Agent 可能在执行 SQL 或等待模型，几十秒没有正文输出。网关、代理或者客户端可能把这个连接当成空闲连接关闭。

服务端可以每隔一段时间发送一条不影响正文的心跳，告诉链路“这个连接还活着”。SSE 常用注释行做心跳，例如：

```text
: ping

```

心跳主要防止空闲断开，也让服务端有机会检查客户端是否还在线。

### Q41：有心跳是不是就不需要超时了？

### A：

不是。

应用自己可以一直发送心跳，但上游模型可能早就卡住了。如果心跳无限续命，连接反而永远不结束。

所以心跳负责保活，读取超时负责发现上游长时间没数据，总时长负责限制整个任务最多运行多久。这三者职责不同。

### Q42：SSE 总时长控制怎么做？

### A：

请求开始时记录总截止时间。每个Agent节点、模型重试和心跳循环都检查剩余时间。

到达截止时间后，如果连接还在，可以先发送一个明确的超时结束事件，然后取消下游任务、关闭生成器并释放资源。

不能只停止向前端输出，却让后台工作流继续执行。

### Q43：如何知道客户端已经断开？

### A：

在 FastAPI 流式处理里，可以定期检查请求是否已经断开；向客户端写数据失败或者协程收到取消异常，也说明连接已经结束。

发现断开后设置取消信号，并向下传播到模型流、工具调用和工作流。

不同服务器和代理对断开的感知可能有延迟，所以心跳和定期检查可以帮助更快发现。

### Q44：客户端断开后具体要取消什么？

### A：

根据当前执行位置，可能包括：

- 模型流式读取；
- 后续 Agent 节点；
- 尚未开始的重试和退避等待；
- 正在执行的数据库查询；
- 心跳任务；
- 内存队列和临时结果。

最后在 `finally` 中关闭HTTP响应、数据库连接和异步生成器等资源。

### Q45：取消本地任务后，模型供应商一定停止计费吗？

### A：

不一定。

本地取消可以停止继续等待和处理，但如果请求已经到达模型服务，供应商是否立即停止计算取决于对方接口是否支持取消以及取消信号有没有及时传到。

所以客户端断连取消主要保证本地资源回收，也尽量减少无效下游消耗，但不能绝对承诺已经产生的费用全部取消。

### Q46：流式输出到一半失败，能不能自动从头重试？

### A：

通常不能直接偷偷重试。

因为前半段内容已经发给用户，新一次模型输出可能不同，直接拼接会重复或前后矛盾。如果中间还产生了工具调用，还可能重复执行工具。

更安全的做法是：在输出前发生的暂时错误可以有限重试；一旦已经向客户端发送业务内容，失败后发送明确的错误结束事件，让用户主动重试，或者使用真正支持断点续传和事件去重的协议。

### Q47：SSE 自动重连会不会导致整个 Agent 再执行一次？

### A：

有这个风险。

如果客户端重连时重新提交同一个业务请求，服务端需要使用请求 ID 做幂等判断，不能直接重新执行工具和 SQL。

如果实现事件编号和短期事件缓存，可以根据客户端最后收到的事件编号补发；如果没有实现，就应该明确告诉前端重新发起的是新请求还是恢复旧请求，不能把浏览器重连等同于业务断点续传。

### Q48：如果客户端接收特别慢怎么办？

### A：

服务端不能无限把模型输出堆在内存里。

可以使用有容量上限的缓冲队列，并设置写入等待时间。如果客户端长期消费不过来，就取消任务或主动断开，避免一个慢客户端占用越来越多内存。

这叫背压控制，面试时知道它是在解决“生产速度大于消费速度”即可。

## 九、完整故障案例

### Q49：举一个模型服务抖动时的完整处理过程。

### A：

假设模型接口开始间歇性返回 503。

请求第一次失败后，系统把它识别成可重试的服务端暂时故障。然后检查客户端仍在线、熔断器仍关闭，并且全链路还有次数和时间预算。

满足条件后，系统按指数退避加随机抖动等待，再发起下一次调用。连续请求的结果同时进入熔断统计窗口。

如果达到最小请求量后失败率超过阈值，熔断器打开。后续请求不再等待连接和反复重试，而是快速返回服务繁忙，避免继续给下游加压。

经过冷却时间后进入半开状态，只允许少量探测。探测成功后恢复正常流量；如果仍然失败，就再次打开。

整个过程中，单个请求不能超过自己的截止时间，所有节点共享重试预算。用户关闭页面后，当前调用和后续重试都会被取消。

### Q50：举一个长时间 Agent SSE 任务的处理过程。

### A：

用户发起一个需要多步分析的任务，服务端建立 SSE 连接并开始运行工作流。

模型或数据库有内容时正常发送事件；没有正文输出的间隔由独立心跳任务发送保活消息。每个节点都检查总截止时间和客户端连接状态。

如果用户关闭页面，服务端发现断连后设置取消信号，停止模型流、SQL和后续节点，并释放资源。

如果用户一直在线但达到任务总时长，则发送超时结束事件并取消任务。心跳不会把总时长无限延长。

## 十、监控与效果验证

### Q51：这套治理应该监控哪些指标？

### A：

我会关注：

- 模型调用总量和第一次调用成功率；
- 各类错误数量，尤其是限流、连接和读取超时；
- 平均重试次数和重试后的成功率；
- 最终失败率；
- P50、P95模型调用耗时；
- 熔断打开次数和持续时间；
- 半开探测成功率；
- 因重试预算耗尽而结束的请求数；
- SSE当前连接数、平均持续时间和异常断开数；
- 客户端断开后的任务取消成功率；
- 断开后仍继续运行的孤儿任务数。

不能只看“重试成功了多少”，还要看重试增加了多少延迟和额外模型调用。

### Q52：怎么测试熔断器？

### A：

可以用可控的假模型服务模拟：

- 全部成功；
- 偶发503；
- 持续503；
- 响应超时；
- 冷却后恢复。

验证熔断器是否按照预期从关闭变打开，再进入半开；半开只允许规定数量的探测；恢复后能关闭；用户错误不会错误计入失败率。

### Q53：怎么测试重试不会形成风暴？

### A：

在并发请求下让下游统一失败，观察：

- 重试时间是否被随机打散；
- 总调用量是否受预算限制；
- 熔断后新增调用是否快速下降；
- SDK、封装层和工作流是否出现重复重试；
- 应用连接池和内存是否稳定。

只测试单个请求重试成功不够，重试风暴是并发情况下的问题。

### Q54：怎么测试 SSE 资源能正确回收？

### A：

可以模拟用户在不同阶段断开：

- 模型调用前；
- 流式输出中；
- SQL执行中；
- 退避等待中；
- 心跳空闲阶段。

然后检查模型任务、数据库查询、心跳协程和连接是否结束，当前任务数和连接数是否回落，不能只看前端页面是不是关闭了。

## 十一、高压追问

### Q55：为什么不把所有失败都重试三次？

### A：

因为参数错误和鉴权失败重试没有意义；流式内容已经发出后从头重试会重复；持续故障时所有请求都重试还会造成重试风暴。

正确做法是先分类，再受次数、时间、熔断状态和输出状态共同限制。

### Q56：重试和幂等有什么关系？

### A：

重试意味着同一个逻辑操作可能执行多次。

纯模型生成虽然通常不修改业务数据，但模型可能返回工具调用。如果失败点发生在工具执行之后，再重试整段工作流可能重复查询、重复写状态甚至重复产生副作用。

因此请求要有唯一 ID，Checkpoint 要记录执行到哪个节点，有副作用的工具也要支持幂等。稳定性重试不能脱离工作流状态单独考虑。

### Q57：熔断和限流有什么区别？

### A：

限流是“不管下游好不好，我都限制进入的请求速度”，用于保护容量。

熔断是“发现下游已经大量失败后，暂时停止调用”，用于故障止损。

两者可以同时存在：平时限流控制正常容量，故障时熔断快速减少无效调用。

### Q58：熔断和降级有什么区别？

### A：

熔断决定“暂时不再调用这个不健康的下游”；降级决定“不调用以后给用户什么替代结果”。

例如熔断模型调用后，结果型追问可以尝试返回已有缓存，这是降级；没有可用替代能力时就明确提示稍后重试。

### Q59：SSE 心跳能判断模型服务是健康的吗？

### A：

不能。

心跳是我们自己的应用发给客户端的，只能说明应用和客户端之间的连接还在。上游模型是否卡住，要靠模型读取超时和调用监控判断。

### Q60：客户端断开后，为什么后台任务可能还在运行？

### A：

因为HTTP连接断开不一定会自动取消已经创建的模型任务、数据库任务和子协程。

应用必须主动检测断连、传播取消信号，并在清理代码中关闭资源。否则用户已经离开，服务器仍然在调用模型和执行SQL。

### Q61：这个方案最大的代价是什么？

### A：

主要是状态和边界变多了：要维护错误分类、每类重试策略、全链路预算、熔断状态、超时层级和取消传播。

规则太保守会降低可用性，太激进又会放大故障。因此需要用监控数据和故障演练持续调整，不能只写完代码就认为稳定性治理结束了。

## 十二、容易说错的地方

### 错误说法1

> 只要调用失败，就统一重试三次。

正确说法：只有暂时性错误才重试，并受到次数、时间、熔断状态和输出状态限制。

### 错误说法2

> 指数退避就是每次固定多等一秒。

正确说法：等待上限通常按倍数增长，并加入随机抖动分散并发重试。

### 错误说法3

> 有重试就不需要熔断。

正确说法：重试解决偶发故障，熔断解决持续故障；持续失败时重试反而会放大压力。

### 错误说法4

> 熔断器打开就是恢复正常调用。

正确说法：打开表示暂时切断调用；关闭才表示正常放行。

### 错误说法5

> 失败一次就应该打开熔断器。

正确说法：通常需要达到最小请求量，并且滚动窗口内失败率超过阈值。

### 错误说法6

> 半开状态可以恢复全部流量试一下。

正确说法：半开只允许少量探测，避免刚恢复的服务再次被压垮。

### 错误说法7

> 所有错误都应该进入熔断失败率。

正确说法：用户取消、参数错误和本地业务错误不代表模型服务不健康。

### 错误说法8

> 有读取超时就不需要请求总时长。

正确说法：模型可能持续返回少量数据而永不触发读取超时，所以还需要完整调用和Agent总时长限制。

### 错误说法9

> SSE有心跳就可以一直运行。

正确说法：心跳只负责保活，不能代替上游读取超时和任务总时长。

### 错误说法10

> 流式输出中断后，服务端从头重试就可以。

正确说法：已经输出后自动重试可能造成重复内容和重复工具调用，需要明确失败或实现真正的事件恢复机制。

### 错误说法11

> 客户端关闭页面，后台任务一定会自动停止。

正确说法：必须检测断连并主动取消模型流、工具和子任务，再通过清理逻辑释放资源。

### 错误说法12

> 本地取消模型请求后，供应商一定不会计费。

正确说法：是否停止远端计算取决于供应商能力，本地取消首先保证的是本地资源回收。

## 十三、面试前必须确认的真实信息

- [ ] 使用的模型SDK和HTTP客户端；
- [ ] 实际定义了哪些可重试与不可重试错误；
- [ ] 429是否读取服务端建议等待时间；
- [ ] 指数退避的基础时间、最大等待和抖动方式；
- [ ] 单次调用最大尝试次数；
- [ ] 整个Agent请求的总重试次数和时间预算；
- [ ] SDK自身是否也开启重试，是否与应用重试叠加；
- [ ] 连接超时、读取超时、单次请求超时和Agent总时长；
- [ ] 熔断统计窗口、最小请求量和失败率阈值；
- [ ] 熔断冷却时间、半开探测数量和恢复条件；
- [ ] 熔断状态是单实例还是多实例共享；
- [ ] 熔断后真实采用快速失败、缓存回答还是备用模型；
- [ ] SSE心跳间隔和实际事件格式；
- [ ] 代理层是否关闭响应缓冲并允许长连接；
- [ ] 客户端断连使用什么方式检测；

- [ ] 流式输出到一半失败时的真实产品策略；
- [ ] 是否使用请求ID、事件ID或短期事件缓存支持重连；
- [ ] 当前监控了哪些重试、熔断、超时和SSE指标；
- [ ] 是否做过持续503、429、读取卡死和客户端断连故障演练。
