

## 简历表述

**会话状态持久化与一致性**：基于 MySQL LangGraph Checkpoint 构建可恢复的会话状态存储，持久化 AgentState、结构化业务槽位、待澄清信息及执行进度；结合 **Redis 热点会话与查询结果缓存、结果引用及三级命名空间**，实现多实例状态共享、服务重启后的会话恢复及跨轮结果复用；针对同一会话的并发更新，引入**状态版本号、乐观锁和请求幂等机制**，避免状态覆盖与重复执行。改造后会话恢复成功率达到 **99.9%**，重复数据库查询减少 **65%**，结果型追问的 P95 响应时间降低 **70%**。

## 一、90 秒项目总述

### Q：请介绍一下你是如何实现会话状态持久化与一致性的。

### A：

这个项目是一个面向环卫业务的数据分析 Agent。改造前，会话状态主要依赖应用实例内存和历史消息：实例切换或服务重启后，上下文容易丢失；用户对上一轮结果做解释、筛选或图表转换时，也可能重新生成 SQL、重复查询数据库；同一会话并发提交时，还可能出现后一个请求覆盖前一个请求状态的问题。

我的改造分为四部分。

第一，使用 MySQL LangGraph Checkpoint 持久化完整 AgentState。除了最近消息和结构化业务槽位，还保存待澄清问题、最后一次有效 QueryPlan、结果引用、当前节点和执行状态。MySQL 是会话状态的唯一权威数据源，服务重启或请求被路由到其他实例后，都可以从最新已提交的 Checkpoint 恢复。

第二，使用 Redis 缓存**热点会话**和**完整查询结果**。AgentState 不保存大结果，只保存 j结果引用指针和结果元数据。**结果型追问**到达后，系统先检查结果是否属于当前租户、用户和会话，再校验查询指纹、数据完整性和过期时间；满足条件就走快路径，不再经过 NL2SQL 和数据库查询。

第三，所有状态、缓存和结果引用都放在 `tenant_id + user_id + session_id` 三级命名空间下，并由认证上下文确定租户和用户，避免跨租户、跨用户或跨会话串数据。

第四，同一会话的更新通过 `state_version` 做乐观并发控制。提交时版本不一致，不会直接覆盖最新状态，而是重新读取状态并重放本轮状态增量。每个请求还有唯一 `request_id` 和幂等记录，相同请求重试时复用原执行状态或原结果，避免重复推进工作流和重复查询。

改造后，会话恢复成功率达到 99.9%，重复数据库查询减少 65%，结果型追问的 P95 响应时间降低 70%。

## 二、整体架构与核心概念

### Q1：你所说的“会话状态”具体包含什么？

### A：

会话状态不只是聊天记录，而是工作流继续运行所需的最小完整信息，主要包括： 最近消息与历史摘要 业务槽位 带澄清字段 执行状态 最后一个queryplan、查询指纹，结果引用，消息轮数，版本号。


### Q2：AgentState、业务槽位和 Checkpoint 是什么关系？

### A：

业务槽位不是单独的一套状态，而是 AgentState 中的结构化字段。AgentState 还包含消息摘要、待澄清信息、执行进度、QueryPlan 和结果引用等。

### Q3：为什么不能只把全部历史消息重新放进 Prompt？

### A：

历史消息只能说明“用户说过什么”，不能稳定表达“当前有效状态是什么”，主要有四个问题：

1. 会持续增加 Token、延迟和成本；
2. 每轮都让模型重新抽取条件，容易漏继承或错误覆盖；
3. 待澄清状态和工作流进度无法仅靠自然语言可靠恢复；
4. 并发请求对同一段历史做不同推断时，没有可用于冲突检测的版本。也就是做不了版本管理

因此我只保留必要的最近消息和摘要用于语言理解，

把时间、地域、指标、待澄清项、执行进度和结果引用保存为结构化状态。

### Q4：为什么选择 MySQL 保存 Checkpoint，而不是只使用 Redis？

### A：

MySQL 负责正确性和可恢复性，Redis 负责性能。

MySQL 具有事务、持久化、唯一约束和版本条件更新能力，适合做权威状态源。

Redis 适合保存带 TTL 的热点状态和查询结果，但缓存可能过期、淘汰或短暂不可用，不能单独承担会话恢复责任。

所以 Redis 丢失后，AgentState 可以从 MySQL 恢复；结果缓存丢失后，可以根据已保存的 QueryPlan 重新查询。系统允许缓存暂时不可用，但不能因此使用错误状态。

### Q5：Checkpoint 表的核心字段是什么？

### A：



`state_json` 保存序列化后的 AgentState，`state_version` 用于乐观锁，`request_id` 用于关联本轮请求和幂等记录。

查询索引围绕 `tenant_id + user_id + session_id` 建立；

## 三、可恢复状态与工作流恢复

### Q6：为什么要持久化待澄清信息？

### A：

因为澄清是一个跨请求的等待状态。

例如用户问“统计今年项目数量”，但系统需要确认是招标项目还是中标项目。第一轮生成：


如果不持久化这部分信息，服务重启后用户只回复“中标”，系统无法判断这是在回答哪个问题。恢复后系统会先识别当前存在待澄清项，将用户答案合并到对应槽位，再清除 `pending_clarification` 并继续工作流。

### Q7：执行进度保存到什么粒度？

### A：

我在具有明确业务语义、可以安全恢复的节点边界保存，而不是在每一行代码后保存。

checkpoint需要保存状态  `current_node`、`request_id`、输入摘要、QueryPlan、重试次数和已有结果引用。恢复时从最近一个已提交的安全节点继续。

不能只保存一个模糊的“执行中”，也不能看到 `EXECUTING` 就无条件重复调用工具。系统必须结合幂等记录判断原请求是否已经完成、正在执行还是可以安全重试。

### Q8：服务重启后是从断点继续，还是整轮重新执行？

### A：

取决于最近一个已提交 Checkpoint 和节点的幂等性。

主要看checkpoint里的状态

- 如果处于 等待用户澄清，恢复待澄清信息，继续等待用户回答；
- 如果 QueryPlan 已生成但 SQL 尚未执行，可以从执行前节点继续；
- 如果幂等记录显示原请求已经成功，则直接返回原结果；
- 如果记录停留在 `执行中`，需要先查询原任务或结果是否已经落库，不能直接重复执行；
- 如果结果缓存已过期，但状态和 QueryPlan 仍有效，可以重新查询并生成新的结果引用。

本项目的数据查询工具是只读的，重试不会修改业务数据库，但仍可能造成重复查询和状态重复推进，所以仍然要通过 `request_id` 控制，而不能依赖“只读就随便重跑”。

### Q9：什么叫“会话恢复成功”？

### A：

不是只要能重新加载聊天记录就算成功。一次恢复至少要满足：

1. 最新会话版本
2. 结构化业务槽位与重启前一致；
3. 待澄清信息没有丢失或串到其他请求；
4. 执行状态能够进入正确的后继节点；
5. 有效结果引用可以继续使用，失效引用能够安全降级重查；
6. 不重复提交状态，也不重复执行已成功的请求。

任何一项不满足，都应记为恢复失败。

## 四、Session Slot 与状态增量

### Q12：如何判断继承、覆盖、清空和新话题？

### A：

基本规则是：

- 本轮没有提及某个槽位：继承；
- 本轮明确给出同类型新值：覆盖；
- “不限地域”“去掉企业条件”：清空指定槽位；
- “重新开始”“清除之前条件”：创建新的业务上下文；
- 完全独立的新话题：递增 会话轮次，隔离旧槽位和旧结果引用；
- 无法可靠判断：保存 等待澄清状态，不猜测。

`context_epoch` 用于隔离同一 session 内的不同业务任务。聊天记录可以继续保留，但新任务不会默认继承旧任务的业务槽位和结果引用。

### Q13：候选状态为什么不能在业务执行前直接覆盖正式状态？

### A：

状态合并后先形成 `CandidateFrame`，**经过完整性和一致性校验**，再决定是否提交。

如果 SQL 生成失败、权限校验失败或结果执行失败，却已经把候选槽位提交为“最后一次成功状态”，后续追问就可能引用一份从未成功执行过的条件。

因此，成功执行后才提交最后一次有效 QueryPlan 和 result_ref；如果需要澄清，只提交待澄清所需的最小状态；如果执行失败，则保留错误和重试信息，不用失败结果污染最后一次有效结果。

## 五、Redis 缓存、结果引用与三级命名空间

### Q14：热点会话缓存和查询结果缓存有什么区别？

### A：

热点会话缓存保存近期频繁访问的 AgentState 或结构化摘要，**用于减少 MySQL 读取和反序列化开销，缓存中必须带 `state_version`。**

查询结果缓存保存完整 rows、columns、QueryPlan 指纹、结果能力、数据版本、生成时间和过期时间，用于跨轮结果复用。

热点会话缓存失效时回源 MySQL；结果缓存失效时根据 QueryPlan 重查。两种缓存不能混成一份数据。

### Q15：三级命名空间具体是哪三级，为什么要这样设计？

### A：

三级是 `tenant_id + user_id + session_id`。

- `tenant_id` 隔离不同客户或组织；
- `user_id` 隔离同一租户内的不同用户；
- `session_id` 隔离同一用户同时进行的不同会话。

这三个字段同时进入 MySQL 查询条件、Redis Key、结果注册表和权限校验。`tenant_id` 和 `user_id` 必须从认证上下文获得，不能信任前端任意传值。

`result_id` 即使使用不可预测的随机值，也不能替代所有者校验。读取结果时仍要验证它属于当前三级命名空间。

### Q16：Result Reference 有什么作用？

### A：

完整查询结果可能很大，不适合写入 AgentState，更不适合每轮放入 Prompt。因此结果存放在 Redis 或结果注册表中，AgentState 只保存轻量引用：

用户说“把刚才的结果做成柱状图”时，系统通过 result_ref 精确读取对应结果，而不是读取一个全局 `latest`。这样既减少上下文体积，也支持同一会话内引用多份历史结果。

### Q17：如何判断一次追问可以复用旧结果？

### A：

不能只靠 LLM 判断“看起来相关”，必须做确定性校验：

1. 结果属于当前 `tenant_id + user_id + session_id`；
2. 缓存未过期；
3. QueryPlan 指纹和业务过滤条件兼容；
4. 结果包含追问所需的指标、维度和字段；
5. 结果范围足够且排序规则一致；
6. 数据版本和权限范围仍然有效；
7. 结果是完整结果，而不是被截断后无法支持当前操作。

只有全部通过才走结果快路径。否则重新查询，宁可多一次查询，也不能错误复用。

### Q18：哪些追问通常可以直接复用结果？

### A：

常见可复用操作包括：

```text
解释当前结果
表格改为柱状图或折线图
导出当前结果
对已有完整结果做本地排序、筛选、单位换算
在缓存覆盖范围内缩小 TopK
询问当前结果中的某一名或某个对象
```

时间、地域、指标口径、聚合粒度、权限范围或数据新鲜度要求发生变化时，一般需要重新查询。

### Q19：“Top5 改成 Top3”是否一定不查数据库？

### A：

不一定。

如果缓存保存的是相同指标、过滤条件和排序规则下的完整有序 Top5，Top3 可以直接截取。如果缓存只有摘要、排序规则变化、企业别名需要重新归并，或结果本身被截断且无法证明前三名正确，就必须重查。

相反，Top5 扩大为 Top10 时，原缓存通常不覆盖新增候选，也需要重查。

### Q20：结果引用过期了怎么办？

### A：

不能返回空结果，也不能改用其他会话的“最近结果”。系统保留 QueryPlan、查询指纹和必要槽位，重新执行查询，生成新的 `result_id`，再通过版本控制更新 AgentState。

如果原数据版本已经变化，还要明确这是基于最新数据重算的结果；不能假装它与旧结果完全相同。

## 六、MySQL 与 Redis 的一致性

### Q21：MySQL 和 Redis 同时存在，会不会有双写一致性问题？

### A：

会，所以设计前提是两者职责不对等：MySQL 是权威状态源，Redis 是可丢失、可重建的缓存。

对于热点状态，先在 MySQL 事务中提交新 Checkpoint 并递增 `state_version`，再更新或失效 Redis。读取缓存时必须校验版本；缓存缺失或版本不可信时回源 MySQL。

对于查询结果，先将结果写入 Redis 并获得 `result_id`，再提交引用它的新 Checkpoint。这样 Redis 写入失败时，不会把无效引用写进权威状态；如果 MySQL 提交失败，只会留下没有 Checkpoint 引用的孤儿缓存，由 TTL 清理。

### Q22：为什么不用分布式事务让 MySQL 和 Redis 强一致？

### A：

Redis 保存的是可重建缓存，不值得为它引入高成本的跨存储分布式事务。分布式事务会增加延迟、组件耦合和故障恢复复杂度。

这里采用的是“权威存储 + 版本校验 + 缓存失效/重建”：

- MySQL 事务保证状态版本和幂等记录正确提交；
- Redis 失败时允许回源或重新查询；
- TTL 负责清理孤儿和长期旧缓存，但 TTL 只是兜底，不是一致性机制；
- 若项目实际实现了 Outbox，可用它保证缓存失效事件最终送达；如果没有实现，面试时不要把它说成已落地能力。

### Q23：数据库查询成功，但 Redis 结果写入失败怎么办？

### A：

本轮查询结果仍可直接返回给用户，但不能把不存在的 `result_ref` 提交到 AgentState。

后续结果型追问只能根据已保存的 QueryPlan 重新查询。可以对 Redis 做有限次数的指数退避重试，但不能因为缓存写失败就伪造一个有效引用。

### Q24：Redis 结果写入成功，但 MySQL Checkpoint 提交失败怎么办？

### A：

这份结果没有被任何已提交状态引用，是孤儿缓存，不会成为会话事实。请求应按幂等策略重试状态提交，或明确判定本轮提交失败。

孤儿缓存最终由 TTL 清理。读取结果必须从已提交 AgentState 中的 result_ref 出发，不能扫描 Redis 猜测“最新结果”。

### Q25：MySQL 成功，但热点会话缓存更新失败怎么办？

### A：

权威状态已经成功，不会丢失。下一轮缓存未命中时直接回源 MySQL。

如果旧缓存仍存在，必须防止它长期返回旧状态。工程上可以采用删除缓存优先、缓存版本校验和 Outbox 异步重试等方案。核心原则是：不能仅凭 Redis 中存在一个值，就认为它一定是最新状态。

### Q26：读取 Redis 后还查 MySQL 版本，会不会让缓存失去意义？

### A：

如果每次都同步查询 MySQL 当前版本，确实会削弱缓存价值。因此实现上通常把版本随缓存一起写入，并结合缓存失效通知、较短 TTL 或当前状态指针控制。

对于强一致要求高的状态更新路径，可以回源确认；对于普通只读路径，在缓存更新协议可靠的前提下直接使用带版本缓存。版本号的价值不仅是读时对比，也用于写入时的 CAS 条件和故障排查。

面试时要基于项目真实实现说明版本校验发生在哪个环节，不能笼统地说“每次都查 MySQL 后再用 Redis”。

## 七、并发控制与请求幂等

### Q27：同一会话同时到达两个请求，如何防止状态互相覆盖？

### A：

使用 `state_version` 做乐观并发控制。请求读取版本 V，提交时对会话的“当前版本指针”执行乐观锁sql更新

如果 Checkpoint 采用追加式保存，则“插入新 Checkpoint”和“按预期版本推进当前版本指针”放在同一个 MySQL 事务中；这里的 SQL 是乐观锁语义示例，并不要求直接覆盖 LangGraph 的历史 Checkpoint 表。

如果受影响行数为 0，说明版本 V 已被其他请求更新。事务回滚，当前请求不能直接覆盖，而是：

1. 重新读取最新状态；
2. 判断当前请求与已提交请求是否仍可合并；
3. 把本轮 Delta 重放到最新状态；
4. 重新执行受状态影响的校验或 QueryPlan 生成；
5. 使用新版本再次提交。

如果两个请求语义冲突且无法安全重放，则返回冲突或要求用户确认，不能无限自动重试。

### Q28：为什么不用 MySQL 行锁串行处理整个会话？

### A：

LLM、工具调用和数据库查询可能持续数秒甚至更久。如果整个执行期间持有行锁，会造成锁等待、连接占用和超时，吞吐量也会明显下降。

因此长耗时计算在事务外完成，只在提交阶段通过版本条件更新做短事务。必要时可以增加带租约的会话级锁来减少冲突，但会话锁是性能优化，最终正确性仍由 MySQL 的版本检查保证。

### Q29：版本冲突后为什么不能直接重试原来的完整 AgentState？

### A：

因为原完整状态基于旧版本生成，可能不包含另一个请求刚提交的修改。直接重试等于再次尝试覆盖最新状态。

正确做法是保存本轮的原始意图和状态 Delta，将 Delta 重新应用到最新版本，并重新验证路由、QueryPlan 和结果引用是否仍成立。这也是采用“增量合并”而不是每轮重写整个状态的重要原因。

### Q30：请求幂等具体怎么实现？

### A：

利用一张请求处理表 使用requestid作为唯一索引 请求到来的时候 先尝试插入表 也就是检查是否来过 由于唯一索引 第二个请求到来的时候 因为插不进去 根据状态 返回前端 是处理中、已完成、失败。

### Q31：乐观锁和幂等机制分别解决什么问题？

### A：

两者解决的问题不同：

- 乐观锁处理**不同请求并发修改同一会话**，防止旧版本覆盖新版本；
- 幂等机制处理**同一个逻辑请求被重复投递或重试**，防止重复执行和重复提交。

只有乐观锁时，相同请求仍可能在不同版本上执行两次；只有幂等键时，两个不同 request_id 的并发请求仍可能相互覆盖，所以两者都需要。

### Q32：如果两个请求内容相同但 request_id 不同，会被视为幂等吗？

### A：

不会仅凭文本相同就判定为同一请求。用户可能确实希望刷新数据或重新执行一次。

幂等语义由 `request_id` 表达。查询指纹可以用于结果缓存和重复查询识别，但不能替代请求幂等键。一个解决“是否是同一逻辑请求”，另一个解决“是否可以复用相同查询结果”。

### Q34：服务在向用户提问澄清后重启，会发生什么？

### A：

澄清节点已经把 `pending_clarification` 和 `WAITING_CLARIFICATION` 保存到 MySQL。重启后，新实例根据三级命名空间恢复最新 Checkpoint。

用户回复“中标”时，系统优先把它识别为当前待澄清字段的答案，写入 `metric_scope`，清除待澄清信息，再从后续节点继续，而不是把“中标”当成一个孤立的新问题。

### Q35：SQL 已执行成功，但服务在返回答案前宕机，用户重试怎么办？

### A：

先根据相同 `request_id` 查询幂等记录和已提交结果：

- 如果结果和状态已提交，直接返回原 response_ref 或 result_ref；
- 如果结果已缓存但状态未提交，不能直接把孤儿结果当作正式结果，需要按原请求恢复提交或重新执行安全流程；
- 如果执行状态不确定，先检查任务记录和结果登记，再决定是否重试。

目标是做到“即使网络层没有收到响应，也不会因为用户重试而把工作流推进两次”。

### Q36：并发请求“换成广东”和“改成前三名”同时到达，会怎样？

### A：

假设两者都基于 V1：

1. “换成广东”先提交，生成 V2；
2. “改成前三名”提交 V1 时乐观锁失败；
3. 系统读取 V2，把 `limit=3` 的 Delta 重放到“广东”的最新状态；
4. 重新判断 V2 结果是否覆盖 Top3；
5. 安全时复用并提交 V3，否则重新查询后提交 V3。

最终状态同时包含广东和 Top3，不会被旧的上海状态覆盖。

### Q37：如果 Redis 整体不可用，系统还能工作吗？

### A：

核心会话可以工作，但性能会下降。

AgentState 从 MySQL 加载；新查询结果可以本轮直接返回，但不能保存无效 result_ref；结果型追问需要根据 QueryPlan 重新查询。系统应监控缓存降级比例，避免 Redis 故障把重复查询压力全部打到业务数据库。

因此“可降级”不等于“没有容量风险”，还要配合限流、熔断和恢复后的缓存预热策略。

## 九、三项核心指标怎么回答

### Q38：会话恢复成功率 99.9% 是怎么定义和测量的？

### A：

口径是：

```text
会话恢复成功率
= 恢复后所有关键状态均正确且没有重复执行的会话数
 / 会话恢复尝试总数
```

测试会覆盖**服务重启**、**实例切换**、**Redis 缓存未命中**、**待澄清等待**、**QueryPlan 已生成未执行**、**结果已提交未返回等场景。**

每次恢复会校验槽位、待澄清项、执行节点、版本号、结果缓存指针、所有权以及最终响应，不能只以“接口返回 200”作为成功。

### Q39：重复数据库查询减少 65% 是怎么计算的？

### A：

先通过标准化 QueryPlan 生成查询指纹。相同租户权限、数据版本、指标、维度、过滤条件、排序和结果范围下，在规定窗口内再次访问数据库，才计为一次可避免的重复查询。

计算公式是：

```text
重复查询下降率
=（改造前重复查询次数 - 改造后重复查询次数）
 / 改造前重复查询次数
```

改造前，图表转换、结果解释、TopK 缩小等追问仍可能重新进入 NL2SQL；改造后通过 result_ref 和结果能力校验走快路径。

统计时必须排除数据版本变化、缓存过期、权限变化、TopK 扩大等必须重查的情况，否则会为了指标而错误复用旧结果。

### Q40：结果型追问具体指什么？

### A：

结果型追问是以已有结果为输入、且经过能力校验后不需要重新访问业务数据库的追问，例如：

- 解释刚才结果；
- 把刚才结果改成图表；
- 导出或转换格式；
- 在完整结果范围内排序、筛选、截取；
- 查询上一结果中的某个对象或排名。

改变时间、地域、指标口径或统计粒度的请求不是结果型追问，应进入重新查询路径。

### Q41：结果型追问 P95 响应时间降低 70% 是怎么测的？

### A：

在相同模型版本、并发压力、结果规模和统计窗口下，分别统计改造前后结果型追问的端到端延迟：

```text
P95 降低比例
=（改造前 P95 - 改造后 P95）
 / 改造前 P95
```

改造前链路通常是：

```text
上下文理解 → NL2SQL → SQL 校验 → 数据库执行 → 答案生成
```

改造后命中快路径时变为：

```text
上下文理解 → 结果引用与能力校验 → Redis 读取 → 答案或图表生成
```

下降主要来自跳过 NL2SQL、SQL 治理和数据库执行。

我们统计的是结果型追问从服务端收到请求，到生成完整响应的端到端时间。在相同模型、相近并发量和结果规模下，改造前 P95 大约是 5.2 秒，改造后大约是 1.6 秒，降低了接近 70%。

改造前，即使用户只是说“做成柱状图”或者“解释一下刚才的结果”，请求仍可能重新经过意图理解、Schema Linking、SQL 生成与校验、数据库执行等完整链路。改造后通过 result_ref 直接读取 Redis 中的历史结果，只需要做结果权限和完整性校验，再进行图表生成或结果解释，因此减少了大约 3.6 秒。

### Q42：如何证明三个指标不是偶然波动？

### A：

要固定测试集、模型版本、Prompt、数据库快照和负载条件，并进行多轮重复测试。线上指标还应使用相同业务类型和相同时间窗口做前后对比。

分别做分层统计：

```text
恢复：按重启、实例切换、缓存丢失、待澄清、执行中断分层
重复查询：按解释、图表、筛选、TopK、缓存过期分层
延迟：按缓存命中/未命中、结果大小、并发量分层
```

同时报告失败样本和 P50/P95，而不是只展示一个最好的百分比。

## 十一、开放性追问

### Q46：这个方案最大的代价是什么？

### A：

状态链路更复杂了，需要同时管理 Checkpoint、热点状态、结果缓存、版本冲突、幂等记录和缓存失效。

此外，结果快路径并不是命中缓存就直接返回，还要验证所有权、查询指纹、结果完整性、数据版本和能力范围。这会增加工程复杂度，**但它把原来依赖模型临场判断的行为变成了可验证的确定性逻辑。**

### Q47：为什么使用乐观锁，而不是所有请求都强制串行？

### A：

同一会话的真实并发冲突比例通常低于读取比例，乐观锁在无冲突时没有锁等待，更适合包含 LLM 和工具调用的长链路。

代价是冲突后要保存并重放 Delta，且对有副作用的工具需要更严格的幂等控制。如果监控发现某些会话冲突非常高，可以增加短租约会话锁做削峰，但不改变数据库版本控制这一最终正确性边界。


### Q49：如果重新设计，还会做哪些改进？

### A：

1. 用 Transactional Outbox 提高 Redis 失效与异步任务投递的可靠性；
2. 定期进行 MySQL、Redis、实例重启和网络超时故障演练；
3. 将线上恢复失败和缓存误判样本沉淀为回归测试集。

## 十二、容易说错的地方

### 错误说法 1

> Redis 和 MySQL 都是会话状态的数据源。

正确说法：MySQL 是权威状态源，Redis 是可重建缓存。

### 错误说法 2

> LangGraph Checkpoint 保存聊天记录，所以服务重启后一定能恢复。

正确说法：恢复还依赖业务槽位、待澄清项、执行节点、版本和幂等状态；只恢复消息不等于会话正确恢复。

### 错误说法 3

> Redis 有缓存就可以直接复用结果。

正确说法：还要校验 **三级命名空间、查询指纹、结果完整性、数据版本、权限和能力范围。**

### 错误说法 4

> Result Reference 保证结果永远存在。

正确说法：result_ref 只是引用；缓存过期后要使用 QueryPlan 重查并生成新引用。

### 错误说法 5

> Redis 锁保证并发绝对安全。

正确说法：会话锁只能减少冲突，最终并发正确性依靠 MySQL 状态版本和乐观锁。

### 错误说法 6

> 有乐观锁就不需要请求幂等。

正确说法：乐观锁防止不同请求相互覆盖，幂等机制防止同一个请求重复执行。

### 错误说法 7

> 版本冲突后，把原来的 AgentState 再提交一次就行。

正确说法：应读取最新状态，将本轮 Delta 重放并重新校验，不能用旧完整状态覆盖新版本。

### 错误说法 8

> TTL 能保证 MySQL 和 Redis 一致。

正确说法：TTL 只负责最终清理，是安全兜底；权威源、事务边界、版本控制和缓存失效协议才是一致性设计。

### 错误说法 9

> 只读 SQL 可以随意重试，不需要幂等。

正确说法：虽然不会修改业务库，但可能造成重复查询、重复计费、重复状态推进和结果覆盖，仍需 request_id 控制。

### 错误说法 10

> 会话恢复成功率 99.9%，就是服务可用性 99.9%。

正确说法：前者是会话状态恢复的业务指标，后者是系统可用性指标，两者分母和判定条件不同。
