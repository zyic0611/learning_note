我这个项目采用了两层 LangGraph 架构，分别是主 Agent 图和 NL2SQL 专用子图。

主图主要负责对话理解、业务路由、工具编排和记忆管理。用户问题进入系统后，首先进行指代消解，然后更新结构化的 ConversationFrame。这个 Frame 会保存时间、地域、指标、企业和业务口径等槽位，并判断本轮是新话题、条件修改还是纯展示变化。

之后系统会识别是否属于基于历史结果的追问，并检查查询口径是否完整。如果缺少关键条件，就进入澄清节点；如果条件完整，再进行领域分类。域外问题走直接回复，环卫招投标领域的问题则进入主 Agent。

主 Agent 采用 Tool Calling 和 ReAct 循环。涉及金额、数量、排名、趋势等结构化数据时，会调用 query_data 工具；工具返回结果后，系统先更新结构化查询上下文，再压缩体积较大的工具消息，然后重新进入 Agent，由 Agent生成最终的业务解释。

query_data 内部不是直接拼接 SQL，而是调用一个独立的 NL2SQL 子图。子图首先进行 Query Understanding 和 Schema Linking，提取相关表、字段以及 Join 路径，并生成结构化 QueryPlan。QueryPlan 相当于 SQL 的业务合同，明确指标、维度、时间范围、过滤条件、排序和限制条数。

SQL 生成后，系统会检查 SQL 是否符合 QueryPlan，并通过治理层完成只读校验、风险判断和成本控制，通过后才执行数据库查询。如果出现错表、错列、语法错误或计划不一致，系统会对错误进行分类，并携带原 QueryPlan、上一次 SQL 和错误信息进入 reflect_sql 节点进行定向修复，然后重新校验和执行。

在记忆方面，我使用 LangGraph Checkpoint 持久化 AgentState，同时使用独立的 Session Cache 保存完整查询结果。AgentState 主要保存消息、摘要、结构化业务槽位、上一轮查询意图和结果引用。这样既能支持多轮条件继承和图表追问，也能避免把大量原始数据反复放入模型上下文。
