
我把多轮上下文理解设计成主业务工作流之前的独立子图。它采用规则、结构化意图相似度和 LLM 组成的三级漏斗完成话题检测；通过历史槽位信息和候选约束完成指代消解；基于字段级合并策略完成业务槽位继承最终生成不可变的 ContextDecision，主业务工作流只消费这个契约。所有状态采用版本控制、延迟提交和全链路审计，避免模型判断直接污染会话状态。


Schema Linking 解决的是：用户使用自然语言提问后，系统应该把哪些表、字段、业务口径和 Join 关系提供给 SQL 生成模型。
项目早期主要依赖字段名关键词匹配，或者把大量表结构直接放进 Prompt。前者遇到业务同义词时容易漏召回，也就是用户用词和数据库字段名不一样；后者虽然降低了漏表概率，但会占用大量 Token，无关字段还会干扰模型。跨表查询中，如果只召回业务起点表和目标表，中间桥接表也容易遗漏，模型甚至会编造 Join 条件。
优化分为五层。

第一，建设 Schema 语义层。检索对象不是原始 DDL，而是加工后的表、字段和指标语义文档，包含中文说明、业务同义词、指标口径、所属表、数据类型以及关联 Tag。
第二，将用户问题解析成结构化 QueryIntent，识别查询类型、指标、维度、时间、过滤条件、排序和 TopK。除了用原问题检索，还使用这些槽位扩展检索词，**减少自然语言省略带来的漏召回。**
第三，采用 BM25 和 Vector 双路召回。BM25 负责**字段名、业务术语和编码等精确匹配**，Vector 负责“成交额—中标金额”这类语义匹配。两路候选合并后归一化打分，得到初始候选 Schema。
第四，对于指标依赖字段、时间字段、地域外键、租户字段等不能遗漏的内容，通过规则 Tag 强制召回，不让它们被 TopK 截断。
第五，把已验证的表关联关系构造成 Join Graph。如果召回结果包含两个业务表，系统在图中搜索合法路径，补全中间桥接表、Join Key 和关联条件，避免模型自己猜 Join。
最后只把经过权限过滤和裁剪后的相关表、字段、业务口径与 Join 路径注入 SQL 生成 Prompt。



状态设计上：
改造前，会话状态主要依赖应用实例内存和历史消息：实例切换或服务重启后，上下文容易丢失；用户需要上一轮的数据的时候 也可能重新生成 SQL、重复查询数据库；同一会话并发提交时，还可能出现后一个请求覆盖前一个请求状态的问题。

我的改造分为四部分。
第一，使用 MySQL LangGraph Checkpoint 持久化完整 AgentState。除了最近消息和结构化业务槽位，还保存待澄清问题、最后一次有效 QueryPlan、结果引用指针、执行状态。MySQL 是会话状态的唯一权威数据源，服务重启或请求被路由到其他实例后，都可以从最新已提交的 Checkpoint 恢复。

第二，使用 Redis 缓存**热点会话**和**完整查询结果**。AgentState 不保存大结果，只保存结果引用指针和结果元数据。**结果型追问**到达后，系统先检查结果是否属于当前租户、用户和会话，再校验查询指纹、数据完整性和过期时间；满足条件就走快路径，不再经过 NL2SQL 和数据库查询。

第三，所有状态、缓存和结果引用都放在 `tenant_id + user_id + session_id` 三级命名空间下，并由认证上下文确定租户和用户，避免跨租户、跨用户或跨会话串数据。

第四，同一会话的更新通过 `state_version` 做乐观并发控制。提交时版本不一致，不会直接覆盖最新状态，而是重新读取状态并重放本轮状态增量。每个请求还有唯一 `request_id` 和幂等记录，相同请求重试时复用原执行状态或原结果，避免重复推进工作流和重复查询。


在NL2SQL中，仅保证SQL语法正确和能够执行是不够的。业务上可能发生错误。

因此我在Query Understanding和SQL生成之间增加了结构化QueryPlan。QueryPlan相当于SQL生成阶段的执行契约，显式记录分析类型、招标或中标口径、指标物理列、聚合方式、维度、过滤条件、时间边界、排序、TopK、必需表、Join路径和去重粒度。

生成SQL前先校验QueryPlan自身是否完整，例如排名是否有排序和TopK、趋势是否有时间粒度、企业分析是否声明去重及联合体口径。SQL生成后使用SQLGlot解析AST，检查SQL实际使用的表、列、状态条件、时间范围、分组、排序、Limit和Join是否符合计划。治理层注入逻辑删除、Limit等策略后还会再次校验，防止策略改写破坏原有语义。

如果失败，系统先分类错误。对于错列、未知Schema、语法、时间粒度、地域编码或Join重复等可修复错误，会保留原QueryPlan，并把上一版SQL、受控错误、相关DDL和语义上下文注入反思Prompt，限次重试；对于危险SQL、成本过高、指标口径不明和空结果则直接终止或澄清，不允许模型绕过规则。

LLMAgent 一次请求可能调用模型多次，比如先理解问题、再生成查询计划、再生成 SQL。如果模型服务发生短暂超时，完全不重试会影响成功率；但所有失败都立即重试，又可能在模型故障时把请求量成倍放大，形成重试风暴。

所以我做了四部分治理。

第一是异常分类。连接超时、限流以及网络异常 属于暂时性故障，可以有限重试；参数错误、鉴权失败、上下文超长和内容安全拒绝这类问题，重试也不会恢复，直接返回或进入降级流程。

第二是有节制地重试。可重试错误采用指数退避，每次失败后等待时间逐渐增加，并加入随机抖动，避免多个实例在同一个时间点一起重试。同时设置单次调用的最大尝试次数，以及整个 Agent 请求共享的重试次数和时间预算，防止工作流里的多个节点各自无限重试。

第三是熔断。当最近一段时间内模型调用达到一定请求量，并且失败率超过阈值时，熔断器从关闭状态进入打开状态，新请求先快速失败。等待一个冷却时间后进入半开状态，只允许少量探测请求；探测成功再恢复，失败则重新打开。

第四是 SSE 流式治理。Agent 长时间没有输出时，服务端定期发送心跳，防止网关把空闲连接关闭；同时设置整个流的最长持续时间。检测到用户关闭页面或网络断开后，会取消模型流、后续节点和数据库任务，并在 `finally` 中释放连接等资源。

整体目标不是保证模型永远不失败，而是在模型抖动时控制重试规模、快速止损，并确保用户离开后后台任务不会继续白白消耗资源。
