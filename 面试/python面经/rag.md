Q：为什么 RAG 需要 Chunk？Chunk 大小如何选择？

A：因为文档长度通常很长，<mark>整篇文档可以生成向量，但受 Embedding 模型输入上限限制，而且整篇一个向量会压缩、混合多个主题，导致检索粒度太粗</mark>。 chunk<mark>切分方式可以按标题、段落、句子等语义边界，过长时再按 token 数递归切分，并保留适当 overlap。Chunk 大小要结合 Embedding 输入上限、语义完整性、检索精度和最终上下文预算通过评测选择</mark>。



Q：Chunk 太大和太小分别有什么问题？

A：chunk太大的话 每次召回的文档很长 塞入上下文 占token多。 并且可能不需要这么多文档 干扰llm思考。 太小的话 可能只召回了局部信息 不完整 llm同样容易自己瞎猜。 并且太小的话 关键信息可能被截断。



Q：Embedding 模型为什么能够表示语义？它本质学习了什么？

A：是因为它通过大量文本数据训练，学习了词语、句子、文本之间的语义关系，将离散的文本信息映射到连续的高维向量空间中。

在这个向量空间里，语义相近的文本经过模型编码后，其向量距离会更接近；语义差异较大的文本，向量距离会更远。

本质上，Embedding模型学习的是文本中的语义特征表示，包括词语之间的关系、上下文信息以及不同表达方式之间的关联，而不是简单的关键词匹配。



Q：向量检索为什么使用余弦相似度？

A：余弦相似度<mark>衡量两个向量夹角方向的一致性，不是通常意义上的空间距离；值越大（越接近 1）表示方向越相似</mark>，<mark>在所用 Embedding 模型中通常意味着语义越接近。它对向量模长不敏感；向量归一化后，按余弦相似度排序与按欧氏距离排序等价</mark>。



Q：BM25 的原理是什么？为什么它可以和 Embedding 结合？

A：BM25的原理是 <mark>基于词频 TF、逆文档频率 IDF 和文档长度归一化的词项匹配评分函数；倒排索引是常见的高效实现方式，不是 BM25 本身</mark>。 它对文本长度进行归一化，降低<mark>长文档仅因词更多而得分偏高</mark>的情况，并且对词频<mark>做饱和处理</mark>，词频大到一定程度 权重增长比较慢。 然后<mark>通过 IDF 提高稀有查询词的权重</mark>。 因为<mark>它</mark>在关键字检索表现好 但是对近义词 同语义的词 表现不好。 <mark>Embedding</mark>在语义表现好 对精确关键字表现<mark>可能</mark>不好 可以结合二者的优缺点。



Q：**Hybrid Retrieval 如何融合 BM25 和向量召回结果？**

A：混合检索就是兼顾二者的召回结果。 <mark>可以先分别召回候选集，再用 RRF（按排名融合）；也可以先把量纲不同的 BM25 分数和向量相似度归一化，再加权融合</mark>。 然后取前<mark>top-k</mark> 并且过滤重复、分数阈值以下的<mark>结果；阈值和权重应通过验证集评测调整</mark>。



Q：Rerank 模型为什么比 Embedding 更准确？

A：因为<mark>Rerank（如 Cross-Encoder）会对“问题—候选文本”进行联合编码并直接预测相关性，而双塔 Embedding 通常分别编码后只做向量相似度计算，交互较弱。因此 Rerank 通常排序更准确，但计算成本更高，适合对召回后的少量候选进行二次排序</mark>。



Q：RAG效果不好，你怎么定位问题？

A：

先判断用户本身的问题适合检索吗 。 比如是否存在指代 是否表达清晰 是否需要改写。 

再看召回阶段 ：去观察召回率 准确率 。 正确文档是否被召回。 判断是不是chunk切分的问题  调整chunk 大小 overlap大小 

再看embedding问题 如果语义相似但是就是没有被召回 那可能是embedding模型不合适 或者是专业词汇表达能力不足 可能需要领域微调过的模型

再看检索策略  是语义出问题 还是关键词出问题 可以使用混合检索 

再看rerank阶段 如果正确文本被召回了 但是排名靠后 就调整权重 更换rerank模型 修改top k 修改阈值

再看context构造 如果检索到了正确的文本 llm却没用 那就是上下文可能太大 文档重复 或者提示词有问题 就压缩context 提取关键片段 调整to p-k

最后判断llm生成的结果 如果检索没问题 回答出问题 那就是优化提示词 要求必须基于context回答 引用溯源 不确定时候不能乱回答。
