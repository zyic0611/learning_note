
## 简历表述

**Schema Linking 优化**：建设业务同义词、指标口径和表字段语义层，采用 **BM25 + Vector 混合检索**，叠加规则 Tag 强制召回与 QueryIntent 槽位增强，并通过 Join Graph 补全跨表关联路径；在固定金标集上，核心表与字段的样本级完整召回率由 **71% 提升至 95% 以上**，按需注入 Schema 上下文后，平均 Prompt Token 消耗降低 **17.3%**。

---

## 一、90 秒项目总述

### Q：请整体介绍一下你是如何优化 Schema Linking 的。

### A：

Schema Linking 解决的是：用户使用自然语言提问后，系统应该把哪些表、字段、业务口径和 Join 关系提供给 SQL 生成模型。

项目早期主要依赖字段名关键词匹配，或者把大量表结构直接放进 Prompt。前者遇到业务同义词时容易漏召回，例如用户说“成交额”，数据库字段可能叫 `win_amount`；后者虽然降低了漏表概率，但会占用大量 Token，无关字段还会干扰模型。跨表查询中，如果只召回业务起点表和目标表，中间桥接表也容易遗漏，模型甚至会编造 Join 条件。

我的优化分为五层。

第一，建设 Schema 语义层。检索对象不是原始 DDL，而是加工后的表、字段和指标语义文档，包含中文说明、业务同义词、指标口径、所属表、数据类型以及关联 Tag。

第二，将用户问题解析成结构化 QueryIntent，识别查询类型、指标、维度、时间、过滤条件、排序和 TopK。除了用原问题检索，还使用这些槽位扩展检索词，减少自然语言省略带来的漏召回。

第三，采用 BM25 和 Vector 双路召回。BM25 负责字段名、业务术语和编码等精确匹配，Vector 负责“成交额—中标金额”这类语义匹配。两路候选合并后归一化打分，得到初始候选 Schema。

第四，对于指标依赖字段、时间字段、地域外键、租户字段等不能遗漏的内容，通过规则 Tag 强制召回，不让它们被 TopK 截断。

第五，把已验证的表关联关系构造成 Join Graph。如果召回结果包含两个业务表，系统在图中搜索合法路径，补全中间桥接表、Join Key 和关联条件，避免模型自己猜 Join。

最后只把经过权限过滤和裁剪后的相关表、字段、业务口径与 Join 路径注入 SQL 生成 Prompt。固定金标集上，核心表与字段的样本级完整召回率从 71% 提升到 95% 以上，平均 Prompt Token 降低 17.3%。

## 二、核心概念

### Q1：Schema Linking 到底是什么？

### A：

Schema Linking 是把用户问题中的业务概念映射到数据库 Schema 的过程。

例如用户问：

```text
查询去年上海各区中标金额最高的企业。
```

Schema Linking 需要识别：

```text
“中标金额” → 中标事实表.win_amount
“企业”     → 企业维表.enterprise_id / enterprise_name
“上海各区” → 地域维表.region_code / region_name
“去年”     → 中标日期字段.win_date
```

如果这些表和字段没有被召回，后面的模型再强也无法生成正确 SQL；如果召回了大量不相关表，模型又容易选错字段或 Join。

### Q2：Schema Linking 在 NL2SQL 链路中的位置是什么？

### A：

整体链路是：

```text
用户问题
  ↓
Query Understanding
  ↓
QueryIntent
  ↓
Schema Linking
  ↓
相关表、字段、业务口径、Join 路径
  ↓
QueryPlan
  ↓
SQL 生成与校验
```

QueryIntent 描述“用户想查什么”，Schema Linking 寻找“数据库中用什么实现”，QueryPlan 再把业务语义和 Schema 选择固化成 SQL 必须遵守的计划。

### Q3：为什么不能直接把全部 DDL 放进 Prompt？

### A：

主要有四个问题：

1. 表和字段增多后，Prompt Token、延迟和调用成本持续上升；
2. 大量无关字段会稀释真正相关的信息；
3. 不同表存在 `amount`、`status`、`date` 等相似字段，模型更容易选错；
4. 仅有 DDL 通常缺少业务指标口径和经过验证的 Join 语义。

所以目标不是“给模型越多 Schema 越好”，而是“召回完成当前查询所需的最小充分 Schema”。

### Q4：为什么又不能只做关键词匹配？

### A：

因为用户语言和数据库命名经常不一致：

```text
用户说法       数据库表达
成交额         win_amount
供应商         enterprise
去年           win_date 的时间范围
环卫车         product_category_code
上海各区       region_code + region_level
```

关键词检索擅长精确名称，但无法稳定解决同义词、简称和语义改写；所以需要 Vector 语义召回和业务同义词层进行补充。

### Q5：Schema Linking 的输出只有表名和字段名吗？

### A：

不止。完整输出通常包括：

候选表和相关证据
候选字段和所属表
指标的定义
时间字段和语义
维度字段和编码字段
过滤字段
主键、外键、joinkey
经过验证的join路径
权限范围
召回来源： bm25/vector/rule/joingraph


记录召回来源有利于离线评测和排查：可以知道某个字段是被语义检索召回，还是被指标规则或 Join Graph 补全。

## 三、Schema 语义层

### Q6：为什么需要建设 Schema 语义层？

### A：

原始 DDL 主要描述物理结构，例如字段名、数据类型和约束，不一定包含业务人员使用的语言。Schema 语义层是在物理 Schema 之上补充可检索的业务信息。

例如原始字段只有：

```text
win_amount DECIMAL(18, 2)
```

加工后的字段语义文档可以包含：

```text
字段：win_amount
所属表：fact_project_win
中文名：中标金额
同义词：成交金额、成交额、合同中标金额
业务口径：按中标结果记录汇总，不等于招标预算
聚合方式：SUM
数据类型：金额
Tags：metric:win_amount, scope:win
```

这样 BM25、Vector 和规则系统都能使用同一份业务语义。

### Q7：语义层通常包含哪些类型的文档？

### A：

我会至少区分三类：

1. **表语义文档**：表名、中文说明、业务主题、粒度、主键和常见用途；
2. **字段语义文档**：字段名、中文说明、同义词、所属表、数据类型和业务 Tag；
3. **指标语义文档**：指标名称、口径、聚合方式、依赖字段、过滤条件、去重粒度和适用时间字段。

表、字段和指标不宜全部拼成一个超长文档，否则字段级命中会被长表描述稀释，也不方便按不同粒度控制 TopK。

### Q8：业务同义词是怎么建设的？

### A：

来源主要包括：

- 业务口径文档；
- 数据字典和字段注释；
- 产品页面上的展示名称；
- 历史查询和参考 SQL；
- 线上失败问题中的真实用户表达；
- 业务人员确认的简称和别名。

同义词需要绑定到明确的业务实体或指标，不能只维护一张没有上下文的全局词表。例如“金额”可能是预算金额、中标金额或合同金额，不能统一映射到一个字段；信息不足时应该依赖 QueryIntent 的业务口径或向用户澄清。

### Q9：指标口径和普通字段说明有什么区别？

### A：

字段说明回答“这个字段存什么”，指标口径回答“这个指标怎么算”。

例如“中标项目数”可能需要：

```text
事实表：fact_project_win
统计字段：project_id
聚合方式：COUNT(DISTINCT project_id)
时间字段：win_date
状态过滤：只统计有效中标记录
去重粒度：项目
```

如果只召回 `project_id`，模型仍可能使用 `COUNT(*)` 造成重复统计。因此指标语义层必须同时描述依赖字段、过滤条件、聚合方式和去重粒度。

### Q10：语义层如何保持与数据库 Schema 同步？

### A：

需要将物理 Schema 版本和语义层版本关联起来。表或字段发生新增、重命名、删除时，触发语义文档重建和索引更新。

至少应该检查：

```text
语义文档引用的表字段是否真实存在
字段所属表是否正确
指标依赖字段是否被删除
Join Graph 的边是否仍然有效
Embedding 与 BM25 索引是否使用同一语义层版本
```

如果语义层长期不同步，检索效果再高也可能给模型提供已经不存在的字段。

## 四、BM25 与 Vector 混合检索

### Q11：BM25 主要解决什么问题？

### A：

BM25 擅长词法和稀有关键词匹配
它会综合词频、逆文档频率和文档长度：稀有词更有区分度，同一个词反复出现时收益逐渐饱和，长文档也不会天然获得过高分。

### Q12：Vector 主要解决什么问题？

### A：

Vector 将用户问题和 Schema 语义文档编码成向量，通过相似度召回语义接近但字面不同的内容，例如：

```text
成交额       ↔ 中标金额
供应商       ↔ 企业
项目走势     ↔ 按时间维度统计项目数量
哪个公司最多 ↔ 企业维度降序排名
```

它能弥补关键词不重合的问题，但也可能召回“语义上相近、业务口径不同”的字段，例如把招标预算和中标金额混在一起，因此不能单独依赖 Vector。

### Q13：为什么 BM25 和 Vector 要同时使用？

### A：

两者错误类型互补：

- BM25 精确但可能漏掉同义表达；
- Vector 泛化强但容易混淆相近业务概念。

例如用户直接说 `win_amount` 时，BM25 非常可靠；用户说“成交额”时，Vector 和同义词层更有价值。混合召回能兼顾精确匹配和语义泛化。

### Q14：混合检索的具体流程是什么？

### A：

流程可以概括为：

```text
原问题 + QueryIntent 扩展词
        ├── BM25 TopK
        └── Vector TopK
                 ↓
            候选集合并
                 ↓
          两路分数归一化
                 ↓
            加权融合排序
                 ↓
        规则强召回与图补全
                 ↓
          权限过滤和上下文裁剪
```

两路应该先各自取候选再合并，不能先把某一路截断得过小，否则另一种信号无法弥补漏召回。

### Q15：BM25 和 Vector 的分数能直接相加吗？

### A：

不能直接相加，因为两种分数的取值范围和分布不同。需要先做归一化，再计算融合分数，例如：

```text
hybrid_score
= α × normalized_bm25
 + β × normalized_vector
 + business_boost
```

`α`、`β` 和 TopK 应该在开发集上调优，不能凭感觉固定。也可以使用 RRF 等只依赖排名的融合方式，但面试时要说清项目实际使用的是哪一种，不要把备选方案说成已实现。

### Q16：为什么不只维护同义词词典，省掉 Vector？

### A：

词典适合高频、确定性的业务表达，精度高且可解释，但无法覆盖所有长尾改写，维护成本也会随业务增长。

Vector 能处理没有进入词典的自然语言表达；同义词层则为核心指标提供确定性映射。两者关系不是替代，而是“确定性知识 + 语义泛化”。

### Q17：Vector 会不会把相近但不同口径的字段召回来？

### A：

会。例如“招标预算”和“中标金额”在语义空间中都与“金额”接近。

所以我的处理不是直接取 Vector Top1，而是：

1. 同时使用 BM25、指标 Tag 和 QueryIntent 口径；
2. 保留候选及召回证据；
3. 对核心指标使用确定性指标映射；
4. 口径仍不明确时进入澄清；
5. 在 QueryPlan 阶段再次校验指标口径。

Vector 负责扩大候选，不负责最终决定业务口径。

## 五、QueryIntent 槽位增强

### Q18：QueryIntent 槽位增强是什么意思？

### A：

不是只拿用户原问题做检索，而是先提取结构化意图，再把槽位中的标准业务概念加入检索查询。

例如：

```text
用户问题：去年上海哪个区项目最多？
```

QueryIntent 可能是：

```json
{
  "metric": "project_count",
  "dimension": "region",
  "time_range": "last_year",
  "filters": {"city": "上海"},
  "sort": "desc",
  "limit": 1
}
```

检索时除了原问题，还会加入：

```text
项目数量、项目ID、COUNT DISTINCT、地域维度、
地域编码、项目日期、降序排名
```

这样即使用户没有明确说“地域编码”或“项目日期字段”，系统也能召回完成查询所需的 Schema。

### Q19：槽位增强会不会把 QueryIntent 的错误进一步放大？

### A：

会有这个风险，所以槽位增强不是无条件替换原问题，而是增加一组有来源和置信度的检索信号。

- 高置信度的规则或实体链接结果可以强增强；
- 模型推断的低置信度槽位只用于扩展候选；
- 与用户原话冲突时以用户明确表达为准；
- 指标口径不确定时不做强映射，而是保留多个候选或澄清。

同时保留原问题的 BM25 和 Vector 召回，防止 QueryIntent 单点错误导致全部候选偏离。

### Q20：QueryIntent 和规则 Tag 有什么区别？

### A：

QueryIntent 描述本次查询的结构化业务需求；规则 Tag 描述某种业务需求必然依赖哪些 Schema。

例如 QueryIntent 中出现：

```text
metric = win_amount
dimension = region
```

规则 Tag 可以展开为：

```text
metric:win_amount
→ fact_project_win.win_amount
→ fact_project_win.win_date
→ 有效中标状态字段

dimension:region
→ region_code
→ dim_region.region_name
→ 合法地域 Join Key
```

QueryIntent 是输入，规则 Tag 是由输入触发的确定性 Schema 依赖规则。

## 六、规则 Tag 强制召回

### Q21：为什么混合检索之后还需要规则强制召回？

### A：

因为 TopK 检索本质上是相关性排序，不保证业务必需字段全部出现。

例如“中标金额趋势”最显眼的是金额字段，但正确 SQL 还必须有时间字段；“各区项目数”除了地域名称，还需要地域编码和项目去重字段。这些字段在文本相似度上未必排得高，却是生成正确 SQL 的必要条件。

因此核心业务依赖不能完全交给相似度排序。

### Q22：哪些字段适合强制召回？

### A：

通常包括：
- 去重字段
- 指标计算需要的字段
- 时间范围字段
- 维度字段、编码字段
- 租户和权限过滤字段


这些内容由 QueryIntent 和业务规则触发，不受普通 TopK 截断。


## 七、Join Graph

### Q25：Join Graph 是什么？

### A：

Join Graph 把数据库中经过验证的关联关系表示成图：

```text
节点：表
边：允许使用的 Join 关系
边属性：左右 Join Key、Join 类型、基数、业务条件和可信度
```

例如：

```text
fact_project_win
  -- enterprise_id -->
dim_enterprise

fact_project_win
  -- region_code -->
dim_region
```

Schema Linking 召回起始表和目标表后，系统从图中寻找合法关联路径，并补充路径上的表和字段。

### Q26：Join Graph 解决了什么问题？

### A：

主要解决三个问题：

1. 召回了起点表和目标表，但遗漏中间桥接表；
2. 数据库中存在多个名称相似的 Join Key，模型容易关联错误；
3. 模型根据字段名猜测不存在或业务不允许的 Join 关系。

**Join Graph 将 Join 从“模型自由生成”变成“从已验证候选路径中选择”**。

### Q27：Join Graph 的边从哪里来？

### A：

来源包括：

- 数据库外键；
- 数据模型文档；
- 已验证的参考 SQL；
- 业务人员确认的逻辑关联。

不能只依赖数据库外键，因为很多业务库或数仓没有完整声明外键；也不能只根据同名字段自动建边，因为 `id`、`code` 等同名字段不一定具有相同业务含义。

### Q28：如果两张表之间存在多条路径，怎么选择？

### A：

路径评分通常考虑：

- 路径长度；
- 边是否经过业务验证；
- 是否包含不必要的多对多关系；
- 路径与 QueryIntent 业务主题是否一致；
- 是否满足权限范围；
- 是否存在推荐或禁用路径。

优先选择较短、可信度高、业务粒度匹配的路径。如果多条路径代表不同业务口径，不能只靠最短路径决定，应由 QueryPlan 明确口径或向用户澄清。

### Q29：最短 Join 路径就是执行成本最低的路径吗？

### A：

不是。图上的最短路径只表示经过的表或边较少，不等于数据库执行代价最低。

真正的执行成本还取决于数据量、索引、过滤选择性、分区和数据库优化器。Join Graph 主要保证关联关系合法并减少无关表，不替代 SQL 的 EXPLAIN 和成本治理。

### Q30：Join Graph 会自动补全哪些内容？

### A：

会补充：

```text
中间桥接表
路径上需要的主键和外键
经过验证的 Join 条件
必要的业务过滤条件
表之间的粒度和基数提示
```

补全后的路径仍要经过权限过滤和 QueryPlan 校验，不能因为图中存在一条边就无条件允许用户访问对应表。

## 八、上下文裁剪与 Prompt Token

### Q31：最后如何把召回结果注入 Prompt？

### A：

不会直接把候选文档原样全部拼进去，而是按当前 QueryPlan 需要组装最小充分上下文：

```text
相关表名称、业务说明和粒度
必要字段、类型和简短语义
指标口径及聚合方式
过滤与去重规则
合法 Join 路径
必要的枚举或编码说明
```

候选中与本次指标、维度和 Join 路径无关的字段会被裁掉；主键、外键、权限字段和规则强召回字段不会因普通 TopK 被误删。

### Q32：Token 减少为什么不会造成召回率下降？

### A：

因为减少的是无关和重复上下文，不是简单把 TopK 调小。

完整性由混合召回、QueryIntent 增强、规则强召回和 Join Graph 保证；裁剪阶段再删除未参与本次指标、维度、过滤和 Join 的内容。

目标是：

```text
先保证必要 Schema 全部进入候选集
再从候选集中删除无关 Schema
```

如果先为了省 Token 截断候选，再尝试补救，容易降低召回率。

### Q33：为什么平均 Prompt Token 只降低 17.3%，而不是更多？

### A：

这个指标统计的是 SQL 生成阶段的完整输入 Prompt，不只有 Schema，还包含用户问题、QueryIntent、QueryPlan、业务规则和输出约束。

即使 Schema 部分明显缩短，其他固定部分不会同步减少，所以总 Prompt Token 的降幅会小于 Schema 文本本身的降幅。此外，规则 Tag 和 Join Graph 会主动保留正确性所需的字段，不会为了追求更大的 Token 降幅而激进裁剪。

### Q34：Prompt Token 降低 17.3% 是怎么计算的？

### A：

对固定金标集中的每个问题，分别统计改造前后 SQL 生成请求的 `input_tokens`，再计算平均值：

```text
Token 降低比例
=（改造前平均 input_tokens - 改造后平均 input_tokens）
 / 改造前平均 input_tokens
```

必须保证两组使用相同 Tokenizer、模型版本、系统 Prompt、输出约束和测试问题，仅改变 Schema Linking 与上下文注入策略。

如果真实记录接近“平均 6,350 降到 5,250”，降幅约为：

```text
(6350 - 5250) / 6350 ≈ 17.3%
```

这组数字只能在与真实日志一致时使用；否则面试前应替换为项目实际的前后 Token 数。

### Q35：只看平均 Token 是否足够？

### A：

不够。平均值可能被少数超长 Schema 场景影响，还应报告：

- 中位数；
- P95；
- Schema 上下文单独占用的 Token；
- 按单表、双表、多表查询分层后的 Token；
- 超过模型上下文预算的比例。

简历可以写平均降幅，但面试时要知道分布和测试口径。

## 九、完整召回率与金标评测

### Q36：71% 提升到 95% 以上具体是什么指标？

### A：

是核心表和字段的**样本级完整召回率**，不是单个字段 Recall，也不是最终 SQL 执行准确率。

对于一条问题，只有生成正确 SQL 所需的核心表和字段全部被召回，才算该样本成功：

```text
样本级完整召回率
= 完整召回全部必要表和字段的样本数
 / Schema Linking 金标样本总数
```

例如某问题需要：

```text
表：fact_project_win、dim_enterprise
字段：win_amount、win_date、enterprise_id、enterprise_name
```

即使只漏掉 `win_date`，表级 Recall 看起来很高，这条样本仍然判定失败，因为无法正确实现时间过滤。

### Q37：为什么使用样本级完整召回率，而不是字段平均 Recall？

### A：

字段平均 Recall 可能掩盖关键字段遗漏。

假设一个样本需要 10 个字段，召回 9 个，字段 Recall 是 90%；但如果漏掉的是金额字段或 Join Key，SQL 仍然无法正确生成。

样本级完整召回率更严格，更接近“当前 Schema 上下文是否足以支持正确 SQL”。同时我也会拆分统计表 Recall、字段 Recall、Join 路径正确率，用来定位具体问题。

### Q38：Join Graph 补全的桥接表是否进入完整召回率？

### A：

如果桥接表和 Join Key 是正确 SQL 的必要条件，就应该进入金标依赖集合。

不过最好将指标拆开报告：

```text
核心业务表和字段完整召回率
Join 必需表和 Join Key 完整召回率
合法 Join 路径命中率
```

这样能区分“检索没有找到业务 Schema”和“Join Graph 没有补出合法路径”。

### Q39：95% 以上是怎么测出来的？

### A：

项目中维护了约 550 条 NL2SQL 综合用例，其中约 160 条完成了专门的 Schema Linking 标注，作为核心回归集。每条至少包含：

```text
自然语言问题
业务场景标签
期望核心表
期望核心字段
必要 Join 表与 Join Key
期望 Join 路径
```

Baseline 使用原有关键词或基础检索方案，优化版本使用语义层、BM25 + Vector、QueryIntent 增强、规则 Tag 和 Join Graph。两组逐条比较完整召回结果。

如果固定集确实为 160 条，那么：

```text
114 / 160 = 71.25%
152 / 160 = 95%
```

这只是与简历百分比相符的换算示例。面试前必须以真实评测报告确认总数和通过数，不能看到百分比后倒推并当作真实结果。

### Q40：这套金标集是谁标注的？

### A：

现有数据主要根据数据库 Schema、业务口径文档和已有参考 SQL 整理。对每条问题，从经过验证的 SQL 反推必要表、字段和 Join 路径，再执行检查结果。

如果当前没有严格的双人独立标注和业务专家仲裁，就应该称为“内部自建金标集”或“核心回归集”，不能包装成专家双标数据集。

### Q41：固定金标集如何避免调参泄漏？

### A：

理想流程是：

1. 按查询意图族分组，例如排名、趋势、地域、企业和多表聚合；
2. 按组划分开发集、验证集和冻结测试集，避免相同问题的改写进入不同集合；
3. BM25/Vector 权重、TopK、同义词和规则只在开发集调整；
4. 验证集选择最终配置；
5. 配置冻结后，测试集只运行一次；
6. 记录数据集、Embedding、模型和检索参数版本。

新增线上失败样本先进入候选池，标注后只能进入下一版本数据集，不能加入当前测试集后重新计算并继续声称是同一组结果。

### Q42：项目早期没有严格划分开发集和测试集，应该怎么回答？

### A：

应该如实说明：

> 早期这批数据主要用于持续回归，并没有从第一天起严格冻结测试集。因此 71% 到 95% 能证明优化后在这批核心业务场景上的完整召回明显改善，但不能完全等价于未知问题上的泛化准确率。后续更规范的做法是按意图族拆分开发、验证和冻结测试集，并对数据集和参数版本化。

这比把内部回归结果说成严格学术评测更可信。与此同时，简历既然写了“固定金标集”，就必须能说明最终用于前后对比的具体数据集版本在比较期间没有变化。

### Q43：如何证明提升来自 Schema Linking，而不是其他模块？

### A：

Schema Linking 指标直接比较召回集合与金标集合，不依赖最终模型生成结果。

同时做消融实验：

```text
Baseline
+ Schema 语义层与 BM25
+ Vector
+ QueryIntent 槽位增强
+ 规则 Tag
+ Join Graph
```

每一步比较表、字段和 Join 路径的错误变化。端到端 SQL 执行准确率可以作为下游指标，但不能用它单独证明 Schema Linking 的提升。

### Q44：95% 召回率是不是越高越好？

### A：

召回率高是必要条件，但不能无上限地扩大候选集。如果把全库 Schema 全部返回，召回率可以接近 100%，却会导致 Token 增加和模型干扰。

因此需要同时关注：

- 样本级完整召回率；
- 无关表和字段比例；
- Prompt Token；
- SQL 字段选择错误率；
- Join 路径正确率；
- 端到端执行与结果正确率。

这个亮点有意义的地方正是：完整召回率提升的同时，Prompt Token 还下降了 17.3%。

## 十、典型案例

### Q45：用一个例子说明完整召回过程。

### A：

用户问题：

```text
统计去年上海各区中标金额最高的三家企业。
```

第一步，QueryIntent 提取：

```text
metric_scope = win
metric = win_amount
dimension = region, enterprise
time_range = last_year
region_filter = 上海
sort = win_amount desc
limit = 3
```

第二步，混合召回：

```text
BM25：
中标金额 → win_amount
企业     → dim_enterprise

Vector：
去年     → 业务时间字段
上海各区 → 地域维度
```

第三步，规则 Tag 补全：

```text
metric:win_amount
→ win_amount、win_date、有效中标状态字段

dimension:region
→ region_code、region_name、region_level

dimension:enterprise
→ enterprise_id、enterprise_name
```

第四步，Join Graph 生成合法路径：

```text
fact_project_win
  ├── enterprise_id → dim_enterprise
  └── region_code   → dim_region
```

第五步，裁剪后向 SQL 生成模型注入必要表、字段、指标口径和上述 Join 路径，不注入其他无关事实表和维表。

### Q46：如果混合检索没有召回中间桥接表怎么办？

### A：

Join Graph 会根据已召回的起点表和目标表寻找合法路径，把中间桥接表及 Join Key 加入 Schema 上下文。

如果图中不存在经过验证的路径，系统不能让模型自由猜测。可以扩大受控召回范围、返回 Schema 不完整错误，或者进入人工维护流程。

### Q47：如果 BM25 和 Vector 给出了冲突候选怎么办？

### A：

先结合 QueryIntent、指标 Tag 和业务口径重新排序。例如 BM25 命中“预算金额”，Vector 命中“中标金额”，而 QueryIntent 明确是中标口径，那么指标 Tag 应使 `win_amount` 获得确定性优先级。

如果用户只说“金额”，QueryIntent 也无法确定口径，就不应由融合分数替用户做业务决定，而应该询问是招标预算、中标金额还是合同金额。

### Q48：如果召回了正确表，但同名字段选错了怎么办？

### A：

字段文档必须带所属表、业务说明和粒度，不能只返回裸字段名。

后续 QueryPlan 与 SQLGlot AST 校验还会检查 SQL 使用的字段是否与计划中的指标、时间和维度一致。Schema Linking 负责提供正确候选，QueryPlan 和 AST 校验负责防止模型在候选中选错。

## 十一、开放性追问

### Q49：这套方案最大的缺点是什么？

### A：

主要是知识维护成本增加了。业务同义词、指标口径、规则 Tag 和 Join Graph 都需要随 Schema 和业务变化更新。

此外，混合检索参数、Embedding 模型和语义文档结构也会影响效果。因此必须对语义层、索引和金标集进行版本管理，不能把它当作一次性建设。

### Q50：为什么不用 LLM 直接从全库 Schema 中选择相关表？

### A：

全库较小时可以这样做，但 Schema 增长后会带来 Token、延迟、成本和稳定性问题；模型选择结果也不容易复现和调试。

混合检索负责快速缩小候选，规则与 Join Graph 保证关键依赖，LLM 只在受控 Schema 范围内生成计划或 SQL，整体更可控。

### Q51：为什么没有使用 Cross-Encoder Reranker？

### A：

如果项目没有真实落地 Reranker，就不要说已经使用。

合理的改进方向是对 BM25 和 Vector 合并后的少量候选进行 Rerank，提高复杂业务语义下的精排能力。但要额外评估推理延迟、成本以及它对完整召回率的真实收益。

### Q52：如果重新设计，还会做哪些改进？

### A：

1. 严格建立开发、验证和冻结测试集；
2. 引入双人标注与业务专家仲裁；
3. 对融合候选增加轻量 Reranker；
4. 学习化调整不同 QueryIntent 下的检索权重和 TopK；
5. 为语义层、Embedding 索引和 Join Graph 建立自动一致性检查；
6. 记录每个召回候选的来源和贡献，完善错误归因；
7. 将线上失败样本按版本进入下一轮金标集；
8. 将结果正确率与 Schema Linking 错误建立可追踪的因果链路。

## 十二、容易说错的地方

### 错误说法 1

> Schema Linking 准确率从 71% 提升到了 95%。

正确说法：固定金标集上，核心表和字段的样本级完整召回率从 71% 提升到 95% 以上。

### 错误说法 2

> 95% 是最终 SQL 的准确率。

正确说法：这是 Schema Linking 召回指标；最终 SQL 和业务结果正确率需要单独评测。

### 错误说法 3

> Vector 能直接确定正确的业务指标。

正确说法：Vector 用于扩大语义候选；核心指标由 QueryIntent、指标语义层和规则共同约束，口径不清时需要澄清。

### 错误说法 4

> BM25 和 Vector 的原始分数直接相加。

正确说法：两路分数尺度不同，需要归一化或使用基于排名的融合方法。

### 错误说法 5

> 规则 Tag 就是在代码里硬编码字段名。

正确说法：规则 Tag 是稳定业务语义到版本化 Schema 依赖的映射。

### 错误说法 6

> 强制召回的字段也会被统一 TopK 截掉。

正确说法：业务必需字段、权限字段和 Join Key 不受普通相关性 TopK 截断。

### 错误说法 7

> Join Graph 通过字段同名自动生成关联关系。

正确说法：图中的边来自外键、数据模型、参考 SQL 或业务验证；字段同名不能证明可以关联。

### 错误说法 8

> Join Graph 找到的最短路径就是执行成本最低的路径。

正确说法：Join Graph 保证路径合法和业务粒度匹配；执行成本仍需 EXPLAIN 和数据库优化器判断。

### 错误说法 9

> 为了降低 Token，把召回 TopK 调小就可以。

正确说法：先通过多路召回和规则补全保证必要 Schema，再按 QueryIntent 和 Join 路径裁剪无关上下文。

### 错误说法 10

> 全量 DDL 的完整召回率一定最高，所以应该作为最终方案。

正确说法：全量注入虽然不容易漏表，但 Token 高、干扰大，而且原始 DDL 仍可能缺少业务口径和合法 Join 语义。

### 错误说法 11

> 内部回归集达到 95%，说明未知问题也有 95% 的泛化准确率。

正确说法：它证明固定核心场景上的回归效果；未知问题泛化需要严格冻结测试集或独立线上评测。

### 错误说法 12

> Prompt Token 降低 17.3%，说明整个请求成本和延迟也降低 17.3%。

正确说法：17.3% 是 SQL 生成阶段平均输入 Token 的降幅；总成本和端到端延迟还受其他模型调用、输出 Token 和数据库执行影响。

## 十三、面试前必须确认的真实信息

- [ ] Baseline 到底是关键词检索、基础 BM25，还是全量 DDL 注入；
- [ ] Schema Linking 金标集的准确总数、版本和冻结时间；
- [ ] 71% 和 95% 以上分别对应多少通过样本；
- [ ] 金标中是否包含中间 Join 表、Join Key 和完整路径；
- [ ] 约 160 条是否为最终实际评测数量；
- [ ] 表、字段、指标语义文档的真实结构和索引粒度；
- [ ] 使用的中文分词器、Embedding 模型和向量距离；
- [ ] BM25 与 Vector 的实际 TopK、归一化方式和融合权重；
- [ ] QueryIntent 中哪些槽位参与了检索增强；
- [ ] 已落地的规则 Tag 数量及两个真实例子；
- [ ] Join Graph 的边来源、路径搜索方法和冲突处理方式；
- [ ] 权限过滤发生在召回前、召回后还是两者都有；
- [ ] SQL Prompt 中实际注入哪些 Schema 内容；
- [ ] Token 指标统计的是哪一个模型调用和哪一种 Token；
- [ ] 改造前后平均 input_tokens 的真实数值；
- [ ] 17.3% 是否使用相同模型、Tokenizer 和 Prompt 固定部分；
- [ ] 数据集是否严格拆分；若没有，需要按内部回归集如实表述；
- [ ] 是否真正做过消融实验及每一步的真实数据；
- [ ] 是否使用 Reranker；没有实现时只能作为改进项。
