当用户提交一个问题后，请求首先进入多轮上下文理解层，而不是直接进入主业务 LangGraph。

系统首先根据 `session_id` 加载当前会话的结构化状态，包括上一轮有效问题、`ConversationFrame`、待澄清信息和最近查询结果的元数据。如果这是会话中的第一次提问，则跳过历史关联判断，但仍然需要提取本轮业务意图并创建初始 `ConversationFrame`。

如果会话中存在历史信息，系统首先进行话题关联初判。话题检测采用三级关联漏斗：

- 第一层使用确定性规则，识别“换个问题”“重新开始”“刚才的”“第一名”“那上海呢”等明确的新话题、重置或追问信号。
- 第二层比较本轮意图与上一轮结构化意图各个维度上的相似性。 使用的向量
- 当前两层无法形成高置信度结论时，再使用低温度 LLM 进行边界判定，并通过结构化输出返回话题关系、置信度和判定依据。

此阶段只产生话题关联候选结论，不会立即清空上下文，避免“那上海呢”“第二名呢”等省略表达在指代消解前被误判为新话题。

随后进行指代消解。指代消解会从当前 `ConversationFrame`、最近查询结果、图表元数据和结果注册表中召回候选对象，解析一些指代词。
- 能够通过规则确定的指代直接解析
- 涉及企业简称、地域别名等情况时，通过实体词典、维表、模糊检索或向量检索完成实体链接；
- 仍存在多个候选时，可以由 LLM 在受约束的候选集合中进行选择。
- 如果无法可靠消解，则生成澄清需求，而不是猜测对象。

再系统判断本轮的追问类型。追问类型描述用户相对于上一轮任务执行了什么操作 ，并且一个问题可能进行了多个操作。

在指代消解和追问类型判断完成后，系统进行**话题关联终判**。终判会结合原始问题、解析后的问题、追问类型和历史结构化状态，决定本轮属于同一任务、同主题新任务、独立新话题、主动重置或仍需澄清。

如果判定为新话题，系统不会物理删除原始聊天记录和审计记录，而是创建新的 `context_epoch`，建立新的业务上下文，并隔离上一轮的业务槽位、查询结果引用和临时状态。

如果判定为同一任务的追问，系统进入槽位合并阶段。

本轮用户明确表达的内容优先级最高，其次是澄清回答、确定性规则、指代消解结果、上一轮结构化槽位、LLM 推断和系统默认值。每个槽位还应记录数据来源、置信度和所属轮次，便于审计与问题排查。

槽位合并后不会立即覆盖正式会话状态，而是先生成候选 `CandidateFrame`。系统会对候选状态进行**一致性校验**，
- 有没有冲突的地方
- 有没有缺少的信息
- 新话题是否错误继承了旧结果引用

随后系统进行追问快路径判断。快路径不只用于图表展示，而是根据用户需求和上一轮结果的能力决定本轮执行方式。

快路径不能只由 LLM 决定。系统必须检查上一轮结果是否包含所需指标和维度、结果是否完整、缓存是否过期，以及当前用户和租户是否有权访问该结果。

完成上述步骤后，多轮上下文理解层生成一份不可变的 `ContextDecision`。

进入主业务 LangGraph 后，系统首先根据 `ContextDecision` 进行路由。

如果需要澄清，则进入澄清节点，向用户询问缺失的指标口径、时间范围、对象或其他关键条件，并保存 `PendingClarification`，等待下一轮用户回答。

如果执行模式为 直接回答、结果解释、结果转换、图表生成等等。 也就是走快路径。则直接读取经过权限校验的结果缓存，完成图表生成、结果转换或结果解释，不再重新生成 SQL。


如果执行模式为 重新查询，系统继续判断问题是否属于当前支持的环卫业务领域。如果不属于当前数据查询领域，则根据产品策略进入通用 LLM 回答、能力提示或拒绝流程。如果属于环卫业务领域，则进入 ReAct 主循环。

ReAct Agent 根据 `ContextDecision` 和当前业务状态选择合适的工具。对于数据查询需求，Agent 调用查询数据工具。查询数据工具本质上是一个独立的 NL2SQL LangGraph 子图。

进入 NL2SQL 子图后，系统首先进行 Query Understanding，将最终有效问题解析为结构化 `QueryIntent`，识别查询类型、指标口径、指标、维度、时间范围、筛选条件、排序和数量限制。

随后进行 Schema Linking。系统根据 `QueryIntent` 从当前用户有权访问的 Schema 范围中召回相关表、字段、业务规则和 Join 路径。权限过滤应在 Schema Linking 阶段提前执行，避免把用户无权访问的表和字段提供给模型。

完成 Schema Linking 后，系统生成结构化 `QueryPlan`。`QueryPlan` 用于固化本次查询必须遵守的业务语义，包括目标指标、统计粒度、过滤条件、去重方式、时间边界、所需表、Join 关系、排序方式和返回数量等。

生成 `QueryPlan` 后，需要执行确定性计划校验，检查关键业务槽位是否缺失、指标口径是否冲突、计划是否自相矛盾，以及是否需要向用户澄清。如果计划本身不完整，则返回主图进入澄清流程，而不是继续生成 SQL。

计划校验通过后，LLM 根据用户问题、`QueryIntent`、`QueryPlan`、精简后的 Schema 和业务规则生成 SQL。

SQL 生成后，系统首先使用 SQL Parser 构建 AST，确认 SQL 能够被正确解析，并识别语句类型、访问的表和字段、过滤条件、Join、排序、聚合、子查询和 Limit 等结构。

随后执行 SQL 与 `QueryPlan` 的一致性校验，检查生成的 SQL 是否真正实现了计划中要求的指标口径、过滤条件、统计粒度、去重方式、时间范围和排序要求。

通过计划一致性校验后，SQL 进入治理层。治理层采用纵深防御机制，依次完成：

- 只读校验，禁止 INSERT、UPDATE、DELETE、DROP、ALTER 等写操作；
    
- 多语句和危险函数检测；
    
- 表级、字段级和行级权限校验；
    
- 强制租户或数据范围过滤；
    
- SQL 复杂度和风险检查；
    
- 通过 EXPLAIN 或数据库估算进行扫描量与成本控制；
    
- 超时、最大返回行数和资源配额控制。
    

权限越界、危险操作、不可接受的高成本查询和违反安全策略的 SQL 属于不可修复错误，不能交给模型通过反思尝试绕过，而应直接拒绝或返回安全提示。

SQL 语法错误、字段别名错误、可修复的 Join 错误、可调整的计划不一致等问题，可以进入受控反思流程。反思节点会携带原始问题、`QueryIntent`、`QueryPlan`、上一版 SQL、错误类型和数据库错误信息重新生成 SQL。

反思必须按照错误类型设置独立的最大重试次数，并防止相同 SQL 和相同错误不断循环。只有被标记为可修复的错误才能进入反思；权限错误、危险操作、资源超限和治理策略拦截不得通过反思重试。

SQL 通过全部校验后，系统使用只读数据库连接执行查询，并设置查询超时、最大行数和资源限制。

执行成功后，查询结果被写入结果注册表和结果缓存。结果元数据至少包含 `result_id`、查询指纹、指标、维度、筛选条件、字段列表、结果完整性、数据版本、过期时间、用户和租户信息。这样后续追问才能确定性判断是否可以复用结果。

查询工具将结构化结果摘要返回 ReAct 主图。为了避免把大量数据直接写入 Agent 上下文，可以只向 Agent 返回结果摘要、字段信息、关键统计和 `result_id`，完整结果保存在结果缓存中。

Agent 根据工具返回结果判断是否还需要调用其他工具。如果不再需要工具，则组织最终答案，并按需要生成表格、图表、解释或报告。

当本轮业务执行成功后，系统将候选 `CandidateFrame` 提交为正式 `ConversationFrame`，更新最后一次有效查询计划和结果引用，并递增状态版本。若本轮失败或需要澄清，则只保存必要的待处理状态，避免不完整或错误的业务状态污染后续会话。

最后，系统以流式方式向用户输出最终答案，同时记录本轮 `ContextDecision`、模型调用、规则命中、槽位变化、工具调用、SQL 治理结果、错误分类、缓存使用情况和 Token 消耗，用于审计、监控和离线评测。


### Q：请介绍一下你是怎么做 LLM 服务稳定性治理的。

### A：

Agent 一次请求可能调用模型多次，比如先理解问题、再生成查询计划、再生成 SQL。如果模型服务发生短暂超时，完全不重试会影响成功率；但所有失败都立即重试，又可能在模型故障时把请求量成倍放大，形成重试风暴。

所以我做了四部分治理。

第一是异常分类。连接超时、限流以及网络异常 属于暂时性故障，可以有限重试；参数错误、鉴权失败、上下文超长和内容安全拒绝这类问题，重试也不会恢复，直接返回或进入降级流程。

第二是有节制地重试。可重试错误采用指数退避，每次失败后等待时间逐渐增加，并加入随机抖动，避免多个实例在同一个时间点一起重试。同时设置单次调用的最大尝试次数，以及整个 Agent 请求共享的重试次数和时间预算，防止工作流里的多个节点各自无限重试。

第三是熔断。当最近一段时间内模型调用达到一定请求量，并且失败率超过阈值时，熔断器从关闭状态进入打开状态，新请求先快速失败。等待一个冷却时间后进入半开状态，只允许少量探测请求；探测成功再恢复，失败则重新打开。

第四是 SSE 流式治理。Agent 长时间没有输出时，服务端定期发送心跳，防止网关把空闲连接关闭；同时设置整个流的最长持续时间。检测到用户关闭页面或网络断开后，会取消模型流、后续节点和数据库任务，并在 `finally` 中释放连接等资源。

整体目标不是保证模型永远不失败，而是在模型抖动时控制重试规模、快速止损，并确保用户离开后后台任务不会继续白白消耗资源。
