# SQL 安全与成本治理

> 这份材料对应简历中的“SQL 安全与成本治理”亮点。回答时抓住一条主线：**模型生成的 SQL 不能直接执行，必须先判断能不能执行，再判断执行起来贵不贵，最后还要为判断失误准备运行时兜底。**

## 简历表述

**SQL 安全与成本治理**：构建基于 SQLGlot AST 的多层 SQL 治理链路，实现只读语句校验、表白名单、危险操作拦截及 LIMIT 策略注入；结合**规则化风险评分与 EXPLAIN 扫描行数评估**，并通过执行超时和数据库只读权限兜底，在查询执行前拦截高风险、高成本 SQL。

---

## 一、90 秒项目总述

### Q：请介绍一下你是怎么做 SQL 安全和成本治理的。

### A：

这个项目里 SQL 是模型动态生成的，所以我不会把生成结果直接交给数据库。模型可能生成写操作、访问不允许的表，也可能生成语法正确但要扫描几百万甚至几千万行的查询。因此我在真正执行前增加了四层治理。

第一层是**结构解析**。我用 SQLGlot 按 MySQL 方言把 SQL 解析成语法树，不依赖字符串和正则判断。解析后确认只有一条语句，并且只允许查询语句；像新增、修改、删除、删表以及写文件这类操作直接拦截。

第二层是**访问控制和策略注入**。我会遍历语法树中的所有表，确认都在当前用户允许访问的白名单里，同时检查危险函数、无条件大表查询、过多关联和大偏移分页等风险。对于普通明细查询，如果没有返回条数限制，会通过语法树安全地补一个 LIMIT；但我不会把 LIMIT 当成成本治理的全部，因为聚合和排序可能在 LIMIT 之前就已经扫描了大量数据。

第三层是**成本预估**。静态检查通过后，对 SQL 执行 EXPLAIN，重点看数据库选择了什么索引、访问方式以及预计扫描多少行。再把扫描量、关联表数量、是否缺少时间条件、是否全表扫描、是否需要临时表和额外排序等信号组合成规则化风险分数。命中明确危险规则的直接拒绝，综合风险过高的也不进入真实执行。

第四层是**运行时兜底**。因为 EXPLAIN 是估算，不可能百分之百准确，所以执行连接使用数据库只读账号，并设置查询超时、最大返回行数和并发限制。这样即使前面的判断出现偏差，也尽量把影响控制住。

所以这套方案不是靠某一个规则保证安全，而是“语法树检查、白名单、风险评分、执行计划、超时和数据库权限”共同形成纵深防御。

## 二、先建立整体认识

### Q1：为什么模型生成的 SQL 不能直接执行？

### A：

主要有三类风险。

第一类是安全风险，比如模型生成了删除、修改、写文件或者访问系统表的语句。

第二类是权限风险，比如当前用户只能查询环卫项目表，模型却访问了财务表或者其他租户的数据。

第三类是成本风险。SQL 可能完全合法，也确实是查询语句，但没有时间范围、关联太多大表或者需要扫描全表，最后把数据库拖慢。

所以“SQL 能执行”和“SQL 应该执行”是两回事。

### Q2：你这套治理链路可以简单概括成什么？

### A：

我一般概括成四句话：

```text
先解析：SQL到底写了什么
再授权：这些表能不能访问
再估价：执行起来会不会太贵
最后兜底：真执行时最多允许消耗多少资源
```

对应的技术分别是：

```text
SQLGlot语法树
表白名单和危险规则
风险评分与EXPLAIN
超时、行数限制和只读账号
```

### Q3：SQL 安全治理和 QueryPlan 语义校验有什么区别？

### A：

QueryPlan 语义校验关注：

> 这条 SQL 有没有正确回答用户的问题？

例如有没有用对中标金额、时间范围、地域和去重方式。

SQL 安全与成本治理关注：

> 即使业务语义正确，这条 SQL 是否有权限执行，执行成本是否可以接受？

例如是不是只读、有没有访问白名单外的表、预计扫描量是否过高。

两者不能互相替代。一条 SQL 可能业务语义正确，但成本太高；也可能执行很快，但查错了指标。

### Q5：为什么不用正则或者字符串包含判断？

### A：

因为 SQL 有大小写、换行、注释、别名、子查询和字符串内容。


危险操作也可能藏在子查询、函数或者多语句里。正则很容易误判或漏判。语法树能识别这个词到底是字符串，还是一个真正的操作节点。

### Q6：SQLGlot 在治理里主要检查什么？

### A：

主要检查：

- 能否按照 MySQL 方言正确解析；
- 是否只有一条语句；
- 是否属于允许的查询类型；select
- 访问了哪些表和字段；
- 有没有子查询、关联、排序、分组和分页；
- 有没有危险函数或危险语法；
- 是否已经存在 LIMIT；
- LIMIT 的值是否超过系统上限；
- 有没有明显的笛卡尔积或者无条件大表查询。
- 符合版本吗

SQLGlot 负责看清结构，但它不知道表里有多少数据、索引怎么建，所以成本还要结合 EXPLAIN。


### Q9：SELECT 语句也可能有危险吗？

### A：

会。

例如它可能：

- 调用休眠函数长期占用连接；
- 读取数据库服务器上的文件；
- 把查询结果写入文件；
- 查询系统库中的敏感信息；
- 返回海量数据；
- 通过复杂笛卡尔积耗尽资源。

所以“只允许 SELECT”只是第一步，不等于所有 SELECT 都放行。

### Q10：如何防止多语句攻击？

### A：

例如：

```sql
SELECT * FROM project;
DROP TABLE project;
```

即使第一条是查询，第二条仍然危险。

系统会检查解析结果只能包含一条语句，数据库驱动层也关闭一次执行多条语句的能力。应用检查和数据库连接配置同时存在，避免只靠一层。

### Q11：为什么数据库账号还要设置成只读？

### A：

因为应用规则可能写错，也可能出现没有覆盖到的新语法。只读账号是最后的权限边界。

即使一条修改语句意外绕过应用层，数据库也会因为当前账号没有写权限而拒绝。

这叫纵深防御：上层负责尽早发现并给出友好错误，底层权限负责最后兜底。

### Q12：只读账号是不是就绝对安全了？

### A：

不是。只读账号解决的是“不能修改业务数据”，但它仍然可能：

- 查询不该看的表；
- 扫描大量数据；
- 占满连接；
- 消耗 CPU 和磁盘；
- 返回敏感字段。

所以还需要表白名单、行级权限、成本评估、查询超时和结果行数限制。

---

### Q15：只做表白名单够不够？

### A：

不一定。

同一张表里可能同时有普通字段和敏感字段，因此更严格的场景还需要：

- 字段白名单；
- 租户条件；
- 敏感字段脱敏；
- 逻辑删除条件。

表白名单解决“能不能访问这张表”，行列权限解决“能看到表里的哪些数据”。

### Q16：租户过滤为什么不能完全交给模型生成？

### A：

因为模型可能漏掉，也可能在修复 SQL 时把它删掉。

租户条件属于安全边界，应该由系统根据认证信息确定，再通过确定性策略检查或注入。认证上下文中的租户 ID 不能直接相信用户在问题里提供的值。

策略注入之后还要重新解析和检查，确认没有破坏原查询结构。

## 六、LIMIT 策略

### Q17：为什么要强制加 LIMIT？

### A：

主要是防止模型生成无上限的明细查询，一次返回几十万行。

如果普通列表查询没有 LIMIT，系统可以补一个默认上限；如果原 SQL 的 LIMIT 超过系统允许值，就压到最大值；如果用户只要求较小数量，则保留用户的较小值。

### Q18：为什么不能直接在 SQL 字符串末尾拼 LIMIT？

### A：

因为原 SQL 可能：

- 已经带 LIMIT；
- 结尾有分号或注释；
- 外面还有子查询；
- 是 UNION；
- LIMIT 位于不应该修改的层级。

直接拼字符串容易得到错误 SQL。更稳妥的方式是在语法树的最外层查询节点上增加或修改 LIMIT，再重新生成 SQL。

### Q19：有 LIMIT 就能说明成本很低吗？

### A：

数据库可能要先扫描大量明细、完成分组和排序，最后才取 10 行。

LIMIT 主要控制返回量，不一定控制扫描量，所以后面仍然要做 EXPLAIN。

## 七、规则化风险评分

### Q21：什么是规则化风险评分？

### A：

可以理解成给 SQL 做一张风险检查表。

例如：

```text
大事实表没有时间条件：增加风险
出现全表扫描：增加风险
关联表太多：增加风险
出现笛卡尔积：直接高风险
大Offset分页：增加风险
预计扫描行数很大：增加风险
有明确租户和时间过滤：降低部分风险
```

最后根据总分分成低、中、高风险。低风险允许执行，中风险可以告警或进一步检查，高风险直接阻断。

### Q22：为什么不只用一条“扫描超过多少行就拒绝”的规则？

### A：

因为成本不是只由扫描行数决定。

扫描十万行后直接过滤返回，和扫描十万行再做多表关联、分组、排序，成本不一样。几十行的小维表全表扫描也不一定有问题。

所以会综合考虑：

- 表的大小和类型；
- 是否缺少时间、租户等关键条件；
- 预计扫描量；
- 关联数量和中间结果放大；
- 分组、去重和排序；
- 子查询复杂度；
- 返回结果量；
- 当前用户的资源额度。

### Q23：哪些规则应该直接阻断，不参与累计打分？

### A：

明确的安全红线应该直接阻断，例如：

- 写操作；
- 多语句；
- 白名单外表；
- 危险函数；
- 文件读写；
- 明确的笛卡尔积；
- 缺少租户隔离；
- 超过硬性成本上限。

风险评分更适合处理“单看一项不一定危险，但多项叠加后风险很高”的灰色情况。



### Q25：规则会不会把正常 SQL 误拦截？

### A：

会，所以规则要区分硬规则和软规则。

明确危险的用硬阻断；不确定的先记录告警、观察执行结果，再决定是否升级为阻断。上线前还要准备合法 SQL 正例和危险 SQL 反例做回归。

每次拦截记录规则编号和原因，才能分析误拦截并调整规则。

## 八、EXPLAIN 与查询计划

### Q26：EXPLAIN 是做什么的？

### A：

可以把 EXPLAIN 理解成让数据库提前告诉我们：

> 如果执行这条 SQL，我准备先查哪张表、用哪个索引、大概要看多少行、需不需要额外排序。

它主要给出执行计划和估算，不会替我们证明真实耗时一定是多少。

### Q27：看 EXPLAIN 时重点看什么？

### A：

我主要看五项：

1. **访问方式**：是按主键找、按索引范围找，还是全表扫描；
2. **实际索引**：数据库最终选了哪个索引；
3. **预计扫描行数**：大概要检查多少行；
4. **过滤比例**：读到的数据最终能留下多少；
5. **额外操作**：是否需要临时表和额外排序。

面试官如果问英文字段，可以对应：

```text
访问方式：type
实际索引：key
预计扫描行数：rows
过滤比例：filtered
额外操作：Extra
```

### Q28：访问方式 type 怎么看？

### A：

通俗理解就是数据库“怎么找数据”。

比较常见的顺序是：

```text
直接定位一行
→ 通过唯一索引关联
→ 普通索引等值查找
→ 索引范围扫描
→ 扫完整个索引
→ 扫全表
```

对应常见英文大致是：

```text
const → eq_ref → ref → range → index → ALL
```

通常越往后扫描范围越大，但不能机械判断。几十行的小维表全表扫描可能完全合理，还是要结合表大小和预计行数。

### Q29：rows 是真实扫描行数吗？

### A：

不是，`rows` 是数据库根据统计信息估算出来的。

它适合执行前筛查，但数据分布不均、统计信息过期时可能估错。所以即使 EXPLAIN 通过，仍然需要执行超时和慢查询监控。

### Q30：filtered 是什么意思？

### A：

它表示读取这些行以后，预计有多少比例能通过当前过滤条件。

例如：

```text
预计读取100万行
过滤后保留1%
```

最后可能只剩1万行，但数据库仍然可能检查了100万行。结果少不等于扫描成本低。

### Q31：possible_keys 有索引，但 key 为空，说明什么？

### A：

说明数据库知道有一些候选索引，但最后认为不值得使用。

常见原因包括：

- 条件能筛掉的数据太少；
- 表很小，扫全表更便宜；
- 在索引字段上做了函数计算；
- 字段类型不一致发生隐式转换；
- 使用前导模糊查询；
- 联合索引没有从最左侧开始；
- 返回数据太多，频繁回表反而更贵；
- 统计信息不准确。

不能看到没走索引就立即强制加索引。

### Q32：Using temporary 和 Using filesort 是什么意思？

### A：

`Using temporary` 表示数据库可能为了分组、去重等操作使用临时表。

`Using filesort` 表示不能直接利用索引顺序得到最终排序，需要额外排序。它名字里虽然有 file，但不代表一定写磁盘。

这两个信号不是出现就必须拦截。小数据量完全可以接受，真正要关注的是它们是否和大量扫描、复杂聚合同时出现。

### Q33：为什么不能只看 EXPLAIN 的一个字段？

### A：

因为每个字段只反映一部分情况。

例如访问方式是范围扫描，看起来不错，但范围可能覆盖几百万行；也可能出现全表扫描，但表总共只有几十行。

所以需要把访问方式、索引、扫描量、过滤比例、表大小、关联顺序和额外排序放在一起判断。

### Q34：MySQL 5.7 没有 EXPLAIN ANALYZE，怎么知道真实成本？

### A：

执行前使用普通 EXPLAIN，必要时使用 JSON 格式查看更完整的估算信息。

执行后再结合：

- 慢查询日志；
- Performance Schema；
- 应用链路耗时；
- 实际检查行数和返回行数；
- 测试环境或只读副本上的真实执行。

MySQL 5.7 不能直接使用 MySQL 8.0 的 `EXPLAIN ANALYZE`，面试时不要混在一起说。

## 九、索引与常见慢 SQL

### Q35：什么是索引？为什么能加快查询？

### A：

可以把索引理解成书的目录。

没有目录时，为了找到某个内容可能要从第一页翻到最后一页；有合适目录后，可以先定位到较小范围，再读取对应数据。

但索引也有存储和维护成本，新增、修改数据时还要同步更新索引，所以不是越多越好。

### Q36：什么是覆盖索引？

### A：

如果查询需要的过滤字段和返回字段都能直接从索引里拿到，就不用再回到数据表读取完整记录，这就是覆盖索引。

它可以减少回表次数，但索引包含的字段越多，索引也越大，所以应该针对稳定、高频查询设计。

### Q37：联合索引的最左前缀是什么意思？

### A：

例如索引顺序是：

```text
地域、项目状态、中标日期
```

它最适合先按地域，再按状态，最后按日期查找。如果查询完全跳过地域，只按状态和日期过滤，通常不能像从索引开头查找那样高效。

联合索引像电话号码或字典排序，前面的字段决定后面的字段能不能被快速定位。

### Q38：为什么通常把等值条件放在范围条件前面？

### A：

例如：

```text
地域 = 上海
状态 = 有效
日期在2025年范围内
```

地域和状态是确定值，日期是一个范围。索引可以先用等值条件把范围缩小，再在这个范围里扫描日期。

遇到日期这样的范围后，后面的字段通常很难继续用于确定索引的起止位置，所以索引顺序要结合实际查询设计。

### Q39：什么情况下索引可能没有被有效使用？

### A：

常见情况有：

- 对索引列使用函数；
- 字段类型不一致发生隐式转换；
- `LIKE` 前面带百分号；
- 联合索引跳过最左列；
- 查询返回了表中大部分数据；
- 条件区分度太低；
- 使用过多 OR；
- 排序和索引顺序不匹配。

最终仍然要用 EXPLAIN 确认，不能只根据SQL长相判断。

### Q40：为什么 YEAR(日期)=2025 可能比较慢？

### A：

这种写法需要对很多记录先计算年份，普通日期索引不容易直接定位范围。

更好的写法是：

```sql
win_date >= '2025-01-01'
AND win_date < '2026-01-01'
```

数据库可以直接按日期索引找这一段范围。使用左闭右开的时间条件，也能避免遗漏12月31日带时分秒的数据。

### Q41：为什么 SELECT * 不推荐？

### A：

因为它会读取和传输不需要的字段，增加网络和序列化开销，也更难使用覆盖索引。

在 Agent 项目中还会把无关内容带入模型上下文，既增加 Token，也可能暴露敏感字段。所以 QueryPlan 应该明确真正需要返回的列。

### Q42：为什么 GROUP BY 和 ORDER BY 容易慢？

### A：

数据库可能需要先读取大量数据，再建立临时结果、完成分组和排序。

尤其是：

```sql
ORDER BY SUM(金额)
```

这个排序值是聚合后才计算出来的，普通明细索引通常不能直接给出最终顺序。

优化方向通常是先缩小时间和地域范围、减少参与聚合的数据、使用合理索引，或者对高频统计建立预聚合表。

### Q43：LIMIT 10 为什么仍然可能是慢 SQL？

### A：

因为执行顺序上可能要先完成过滤、关联、分组和排序，最后才取前10行。

所以 Top10 聚合查询虽然只返回10条，但底层仍然可能扫描几百万条明细。

### Q44：深分页为什么慢？

### A：

例如：

```sql
LIMIT 100000, 20
```

数据库通常仍然要找到并跳过前10万行，再返回20行。页数越深，成本越高。

如果业务允许，可以记住上一页最后一个排序值，然后从它后面继续查，这叫游标分页或者Keyset分页。

## 十、慢 SQL 怎么排查

### Q48：如果面试官给你一条慢 SQL，你会怎么排查？

### A：

我会按这个顺序说：
1. 首先定位 通过慢查询日志 或者监控 找出慢sql 看 发生频率 sql执行时间 哪个接口触发
2. 拿到真实sql和参数后  看看真实的参数 因为不同时间范围的参数返回的数据量差距很大
3. 看是不是扫描数据量很大 存在深分页 有没有存在行锁竞争的关系 
4. 然后explain查询计划分析 看查询类型 千万不能死all 然后看 用到了哪些索引 再看过滤比例 返回行数目 然后看额外信息 有没有用到文件排序或者临时表
5. 检查 有没有导致索引失效的问题
6. 做有针对性的优化； 比如做联合索引 走覆盖索引 等等
7. 用相同参数重新测试；
8. 确认新索引或改写没有让其他高频查询变慢。

不能一看到慢 SQL 就直接加索引。

### Q49：数据库 CPU 不高，SQL 为什么还可能很慢？

### A：

因为它可能在等待：

- 等行锁或元数据锁；
- 等磁盘读取；
- 等数据库连接；
- 等网络传输大量结果；
- 临时表落盘；
- 被长事务阻塞；
- 应用拿到结果后处理很慢。

所以排查时不能只看 CPU，还要看锁、磁盘、连接池、网络和应用链路。


### Q52：慢 SQL 优化通常有哪些方向？

### A：

可以从几方面考虑：

- 缩小时间、地域等查询范围；
- 删除不需要的返回字段；
- 避免在索引列上做函数或类型转换；
- 调整联合索引；
- 在关联前先过滤、去重或聚合；
- 优化深分页；
- 对高频聚合建立汇总表；
- 把大查询改成异步任务；
- 将分析查询路由到只读副本或分析库。

具体选择取决于慢在哪里，不能所有问题都靠SQL改写解决。

## 十一、运行时保护

### Q53：为什么 EXPLAIN 已经通过，还需要执行超时？

### A：

因为 EXPLAIN 是估算。统计信息可能过期，真实参数也可能命中特别大的数据范围。

执行超时是为了防止估算错误后，查询无限占用数据库连接和资源。

### Q54：执行超时应该在哪些层设置？

### A：

最好不只一层：

- 应用调用数据库的超时；
- 数据库查询执行时间限制；
- 连接池等待超时；
- 上游接口整体超时；
- 异步任务的最大运行时间。

任何一层超时后都要正确取消或释放数据库资源，不能只是接口不等了，数据库里的查询还继续跑。

### Q55：最大返回行数和执行超时有什么区别？

### A：

最大返回行数控制“最多拿多少数据回来”，执行超时控制“最多允许运行多久”。

一条SQL可能只返回10行，但为了得到这10行扫描了大量数据；也可能执行很快，却一次返回几十万行。因此两个限制都需要。

### Q56：如果用户确实需要一个很大的查询怎么办？

### A：

不能为了成本治理直接改变用户问题，也不能无条件占用在线数据库。

可以：

- 请用户缩小时间或地域范围；
- 转成异步分析任务；
- 使用只读副本或分析库；
- 查询完成后通过结果引用通知用户。

治理的目标不是禁止所有大查询，而是让不同规模的查询走合适的执行通道。

### Q57：成本过高时，为什么不直接让模型自动优化？

### A：

模型为了让 SQL 变快，可能偷偷删除关联、缩小时间范围或者改变统计口径。SQL 虽然变快了，却回答了另一个问题。

只有不改变 QueryPlan 语义的确定性改写才能自动进行，例如把年份函数改成日期范围、删除无用返回列、在关联前预聚合。

改写后还要重新做语义校验和 EXPLAIN。无法安全降低成本时，应要求用户缩小范围或改成异步执行。

## 十二、典型完整案例

### Q58：举一个从 SQL 生成到治理执行的完整例子。

### A：

用户问：

```text
统计2025年上海各区中标金额，并按照金额从高到低排序。
```

模型生成SQL后，治理过程是：

第一步，用 SQLGlot 解析，确认只有一条查询语句，没有写操作和危险函数。

第二步，提取事实表和地域表，确认都在当前用户白名单中，并确认存在租户、上海地域和2025年时间条件。

第三步，检查返回字段和分组，给无上限的明细结果注入合理 LIMIT；这个例子属于区县聚合，LIMIT 只控制最终返回，不能替代成本分析。

第四步，计算静态风险。检查关联表数量、有没有笛卡尔积、是否使用日期函数以及是否缺少重要过滤。

第五步，执行 EXPLAIN。重点看事实表是否使用地域和时间相关索引、预计扫描多少行，地域表是否通过主键关联，以及分组排序的数据量是否过大。

如果模型写的是：

```sql
WHERE YEAR(win_date) = 2025
```

可以在不改变业务语义的前提下改成：

```sql
WHERE win_date >= '2025-01-01'
  AND win_date <  '2026-01-01'
```

然后重新做语义检查和 EXPLAIN。

最后使用只读账号执行，并设置超时和结果上限。任何硬性安全规则或成本上限不通过，都不会进入真实执行。

### Q59：如果模型生成了危险 SQL，或者应用层校验被绕过，只读权限有什么意义？

### A：

它保证即使上层生成或传入了危险 SQL，查询账号也没有权限修改业务数据。

但它只能限制数据库权限，不能代替应用治理。攻击者仍可能尝试读取敏感表或制造高成本查询，所以白名单、危险函数和成本限制仍然要存在。

## 十三、高压追问

### Q60：你能保证所有危险 SQL 都被拦住吗？

### A：

不能绝对承诺。

我的设计目标是降低单点失误：语法树规则可能漏掉一种写法，但数据库账号没有写权限；EXPLAIN可能估算不准，但执行还有超时和行数限制。

安全不是一个百分之百正确的判断函数，而是多层防线共同把风险降下来。

### Q61：风险评分会不会被模型绕过？

### A：

模型不能看到完整内部阈值，也不能决定自己是否放行。生成SQL之后，由独立治理模块重新解析并评分。

明确的写操作、白名单越界和危险函数属于硬规则，不会因为综合分数低而放行。

### Q62：为什么不让数据库自己决定是否执行？

### A：

数据库优化器负责寻找它认为比较合适的执行方式，不负责理解我们的租户权限、业务资源配额和接口响应时间要求。

数据库认为“可以执行”不代表产品侧可以接受，所以应用层仍要做安全和成本准入。

### Q63：如果规则误拦了正常查询怎么办？

### A：

每次拦截都要记录：

```text
SQL结构
命中的规则
风险分数
EXPLAIN摘要
最终处理结果
```

通过人工复核和回归集判断是不是误拦。对没有把握的规则可以先告警、灰度，再决定是否硬阻断。

### Q64：怎么证明这套治理有效？

### A：

可以准备安全正反例和成本分层测试集：

- 合法查询应该通过；
- 写操作、危险函数和越权表必须拦截；
- 大表无时间条件、笛卡尔积和超高扫描量应该拦截；
- 小表正常查询不能因为全表扫描被误杀。

线上关注：

- 高风险 SQL 拦截数；
- 误拦截率；
- 放行后超时率；
- 放行 SQL 的预计与实际扫描量；
- 慢 SQL 数量；
- 数据库只读权限拒绝次数；
- P95 查询耗时。

## 十四、容易说错的地方

### 错误说法1

> 只要是 SELECT 就是安全 SQL。

正确说法：SELECT 仍可能读取敏感数据、调用危险函数或消耗大量资源。

### 错误说法2

> SQLGlot 可以保证 SQL 绝对安全。

正确说法：SQLGlot负责结构化解析；安全还依赖规则、白名单、执行超时和数据库权限。

### 错误说法3

> 有 LIMIT 就不会扫描大量数据。

正确说法：聚合、关联和排序可能在LIMIT之前已经处理大量数据。

### 错误说法4

> EXPLAIN 的 rows 就是真实扫描行数。

正确说法：它是统计信息基础上的估算，运行时仍需监控和超时兜底。

### 错误说法5

> Using filesort 表示一定发生磁盘排序。

正确说法：它表示不能直接利用索引顺序完成排序，不一定写磁盘。

### 错误说法6

> 查询没有使用索引，就一定要给它加索引。

正确说法：小表或低选择性查询全表扫描可能更合理，必须结合数据量和真实计划分析。

### 错误说法7

> 索引越多，查询就越快。

正确说法：索引会增加存储和写入成本，需要围绕真实高频查询设计。

### 错误说法8

> 一对多关联后金额重复，使用SUM DISTINCT即可。

正确说法：不同项目可能金额相同，应按业务主键和QueryPlan粒度先去重或聚合。

### 错误说法9

> MySQL 5.7可以使用EXPLAIN ANALYZE查看真实耗时。

正确说法：MySQL 5.7主要使用EXPLAIN做估算，再结合慢日志、Performance Schema和受控真实执行。

### 错误说法10

> 成本过高时让模型多优化几次就行。

正确说法：任何自动改写都必须保持QueryPlan语义；无法安全优化时应缩小范围、异步执行或切换分析存储。

### 错误说法11

> 数据库账号只读后，应用层就不需要治理。

正确说法：只读账号不能防止越权读取和资源耗尽，应用层仍需白名单和成本治理。
