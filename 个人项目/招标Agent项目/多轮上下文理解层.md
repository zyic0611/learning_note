
该层的内部顺序是：
1. 做话题初判
2. 做指代消解
3. 追问类型判断
4. 槽位继承、覆盖、清除（槽位合并）
5. 追问快路径判断
6. 生成 ContextDecision
7. 进入主业务 工作流

## 话题检测

倾向于业务意图是识别

不应该作为一个LLM的 true/false判断  ，话题检测只负责生成证据，不直接修改状态。真正是否切换上下文，由后面的 `ContextDecision` 统一决定。

**目标是判断 本轮和历史任务的关系：**

是同一任务 还是 显示开启新的话题。 要输出具体的关系是同话题的追问 还是部分同话题的分析之类的。

该层的输出不是只输出 related=t/f 而是一个结构化的。
比如
- related: 关系为
- score：置信度
- reason_code：这么认为的原因

技术上：话题关联漏斗式三层判断：

### 第一层 确定性规则

处理高置信度情况：

用户明确换一个话题、一些明显的引用代词。 参数明显的修改。 展示方式的修改。  用户给出的是澄清话术。


实现方式：  正则表达式、关键字词典、有限状态机（比较槽位）。


直接判定 稳定 成本低

### 第二层 结构化语义相似度

不能直接去计算两个问题的文本相似度 效果差。

要比较二者的结构化意图。 并且可以对结构化意图里的每个维度加权。

embedding可以作为辅助证据 但不能独立决定是否清空上下文。

### 第三层 LLM边界判定

只有前两层无法确定的时候 才会调用。

让模型通过json schema输出
- relation：相关类型
- 置信度
- 相关原因
- 可以继承的槽位

技术上使用：
- structured Output
- json schema 校验
- 枚举值约束


## 指代消解

目标是把 一些指代词 解析为明确对象

技术实现：

### 第一步 候选对象生成

从以下位置召回候选
- 当前结构化业务槽位
- 最近几轮的结构化意图
- 最近的查询结果
- 带澄清问题

不能把全量结果都给llm 也是要建立一个结构化格式交给llm

### 第二步 确定性解析

优先走规则解析 明确一些规则：
比如第一名 就是最近排名结果里的第一名等等

### 第三步 实体链接

对于公司简称、地域简称、业务类型别名 使用别名字典、数据库维表

使用
- 别名字典
- 数据库维表
- 模糊匹配
- BM25
- 向量召回

### 第四步 LLM候选选择

LLM可以从候选ID中选择 不允许自由编造对象

### 降级策略

- 如果没有候选 保持原问题 不进行继承
- 多个候选无法区分 直接询问用户澄清

## 追问类型判断

目标

判断用户本轮对上一轮任务做了什么操作。它是“操作意图分类”，不同于业务意图识别。 聚焦于操作。

一些分类体系：
- 回答系统的澄清问题
- 解释上一轮的结果
- 修改某些条件 
- 重试或重新执行
- 同主题下的新任务
- 独立新话题
- 主动重置

可能的执行模式：
- 无需查询即可直接回答；
- 直接基于上一轮结果回答；
- 对已有结果进行排序、筛选、单位转换或截取；
- 复用结果，仅重新生成图表或表格；
- 需要重新查询数据库；
- 信息不足，需要用户补充；
- 请求越权或不受支持。


技术实现：

### 决策规则优先

用户的问题命中了决策规则 就直接映射到对应的类型。

### 多标签或层级分类

一个query 可能包含多个变化

同时包含很多类型 所以底层最好输出 多分类结果 而不是强制单分类。

### LLM结构化分类

负责识别自然语言里面的操作 。输出还是结构化形式。


## 槽位修改

技术核心是 定义一个类 ConversationFrame 也就是session slot的具体实现。 使用 Pydantic定义 强类型状态来约束

并且建立槽位优先级

1. 用户本轮显示表达
2. 用户本轮明确清除
3. 澄清回答
4. 确定性业务规则
5. 指代消解结果
6. 上一轮结构化槽位
7. LLM推断
8. 默认值

每个槽位都需要标记来预案。

根据上一轮不同的追问类型 采取不同的追问策略。


## 追问快路径判定

快路径不能只让llm决定 llm可以识别用户意图 但是必须由确定性代码判断缓存结果是否足够。

对缓存结果进行安全判定
- TTL
- 数据版本
- 租户、用户权限
- 缓存里数据可能不够


## 生成ContextDecision

是多轮上下文层 和主工作流之间 唯一契约。

主业务图不再随便读取历史信息 自己猜测上下文。


ContextDecision 将概率性的语言理解与确定性的业务执行隔离。上游可以使用规则、向量和 LLM，但下游只消费经过 Schema 校验的稳定契约，因此模型升级不会直接破坏 SQL 和业务节点。

内容：
- 原始问题 指代消解后的问题 最终有效问题
- 话题关系 以及置信度
- 追问类型 和结构化操作
- 槽位操作记录
- 是否需要查询
- 是否可以快路径
- 是否有可以引用的查询结果
- 是否需要澄清


## 总结：

我把多轮上下文理解设计成主业务工作流之前的独立子图。它采用规则、结构化意图相似度和 LLM 组成的三级漏斗完成话题检测；通过结果注册表和候选约束完成指代消解；将追问解析为 SET、CLEAR、KEEP 等结构化操作；基于字段级合并策略完成业务槽位继承；再通过结果能力校验决定复用、转换、重查或澄清。最终生成不可变的 ContextDecision，主业务工作流只消费这个契约。所有状态采用版本控制、延迟提交和全链路审计，避免模型判断直接污染会话状态。
