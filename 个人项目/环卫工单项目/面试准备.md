# 城市应急调度平台——面试准备

## 1. 项目定位

这是一个面向突发事件的人员调度项目。重点不是普通 CRUD，而是解决三件事：

1. 如何从大量人员中快速找到位置、技能和负载都合适的候选人。
2. 多人并发争抢有限名额时，如何保证不超卖、一人不重复抢。
3. Redis 已经预占、MySQL 尚未落库的异步链路中，如何处理重复消息、服务宕机和数据不一致。

如果这是个人项目，面试时应明确说“我在项目中设计并实现/压测了”，不要暗示存在真实生产流量或线上事故。

## 2. 一分钟项目介绍

> 我做的是一个城市应急调度平台，用于暴雨防汛、大型活动等场景。一个事件可能同时需要多名、不同技能的人员，系统先通过 Redis GEO 按距离粗筛，再结合技能、在线状态和负载做候选人排序；待调度事件用 ZSet 按事件等级和等待时长排序，避免普通事件长期饥饿。
>
> 我主要负责的是并发抢单和可靠落库。抢单时由 Redis Lua 在一次原子操作里检查工单状态、技能名额、人员容量和重复抢单，并生成带 Token 的短时技术预占。接口先返回 PROCESSING，再通过 RabbitMQ 异步落 MySQL；超过落库截止时间的迟到消息不能创建有效 assignment。落库成功后才开启完整的 5 分钟确认租约。消息链路采用 outbox、Publisher Confirm、手动 ACK 和数据库唯一键，目标是至少一次投递下的业务幂等。对于 Redis 成功但 outbox 尚未写入就宕机的空窗，我额外记录 Redis 待确认事件，由定时任务补写或条件回滚。确认超时通过延迟队列释放，同时用 Token 和状态校验防止旧消息误操作新租约。

这段控制在 60～90 秒。讲完停住，让面试官选择深入 Redis、MQ 还是调度算法。

## 3. 三分钟展开版

### 背景和难点

一个应急工单可能需要 10 人，而且有技能配额。热点事件会让大量人员同时点击，普通的“查剩余数再更新”会发生超卖。另一方面，如果同步完成所有数据库写入再返回，高峰时接口延迟和数据库压力都会上升。因此我把实时预占放在 Redis，把持久化通过 RabbitMQ 异步削峰。

### 核心链路

请求到达后，workerId 从登录态获取，应用生成 requestId 和 leaseToken。Lua 原子检查工单、对应技能名额、人员负载以及一人一单，成功后扣减 available、增加 reserved，记录 `PENDING_PERSISTENCE` 租约、短时 `persistExpireAt` 和 Redis 待确认事件。客户端得到 requestId 和 PROCESSING，通过查询接口获知最终结果。

应用随后写入 outbox。投递任务发送消息并等待 Confirm；消费者先通过 Lua 校验 requestId、Token、状态和 `persistExpireAt`，迟到消息不能创建有效 assignment。仍有效时，消费者生成 `confirmExpireAt = 当前服务端时间 + 5 分钟`，在一个 MySQL 事务内插入消费记录、assignment、更新工单计数并写确认超时 outbox。提交后 Redis 转为 `RESERVED` 并保存同一个 confirmExpireAt，最后手动 ACK。即使 Confirm 后状态更新失败导致重复发送，或数据库提交后 ACK 丢失导致重复消费，eventId 和 `(orderId, workerId)` 唯一键都能使处理幂等。

### 异常闭环

最关键的异常是 Redis 成功后应用立即宕机，可能还没来得及写 outbox。仅靠 outbox 解决不了这次双写，所以 Lua 同时写一个 pending event。扫描器发现它长期未确认后，检查 MySQL：已有记录就修正状态，没有记录且租约有效就补写 outbox，已经过期就条件回滚。

落库成功后，人员获得完整的 5 分钟确认时间。TTL+DLX 产生到期消息，消费者必须比较 requestId、Token、租约状态和 `confirmExpireAt` 才释放；如果人员已经确认或产生了新租约，迟到的旧消息不会生效。RabbitMQ 故障时还有 Redis deadline ZSet 扫描兜底。

## 4. 为什么这样设计

### 为什么用 Lua，不用分布式锁

抢单逻辑本质上是对少量 Redis Key 的条件判断和修改，Lua 能一次原子完成，网络往返少，也没有锁续期、误释放和锁粒度问题。分布式锁只会增加复杂度。数据库唯一键仍是最终防线。

### 为什么不是只用 Redis `DECR`

`DECR` 只能避免单个总数的并发问题，不能在同一个原子边界里处理工单状态、技能名额、一人一单、人员容量、租约和请求幂等。只扣库存后再写其他 Key，进程在中间宕机会留下半完成状态。

### 为什么用 RabbitMQ

这个场景重视可靠投递、路由、ACK、死信和延迟处理，RabbitMQ 的能力与需求匹配。它让抢单接口不必同步等待数据库，并吸收瞬时峰值。代价是系统只能做到最终一致性，并且必须建设幂等、补偿和监控。

### 为什么还要 outbox

如果业务提交后直接发 MQ，数据库成功但 MQ 发送失败会丢事件。先在本地数据库事务里保存业务变更和 outbox，再异步发送，能用数据库记录补发。本项目第一步先写 Redis，所以还需要 pending event 补 Redis→MySQL 之间的空窗。

### 为什么不能说 Confirm 保证消息不丢

Confirm 只说明 Broker 接收消息，不说明消费者处理成功；Broker 的持久化、集群故障策略也影响可靠性。Confirm ACK 后，本地状态更新前仍可能宕机而重复发送。因此准确表述是“持久化配置 + Confirm + 补发降低丢失风险，至少一次投递，消费端幂等”。

### 为什么接口返回 PROCESSING

Redis 预占成功时 MySQL 还未提交，立即返回 SUCCESS 会向客户端承诺一个尚未持久化的结果。返回 PROCESSING 更符合最终一致性语义。若产品必须同步返回确定成功，就应该走同步数据库事务，而不是在话术上把异步说成强一致。

## 5. RabbitMQ 高频追问

### 1）消息从生产到消费，哪里可能丢？

- 发送前应用宕机：outbox 或 Redis pending event 补偿。
- 应用到 Broker 途中丢失：Publisher Confirm 未 ACK，后台重发。
- Routing Key 错误：`mandatory + Return` 发现不可路由。
- Broker 重启：durable exchange/queue + persistent message；仍需结合实际集群策略说明边界。
- 消费者拿到消息后宕机：手动 ACK，未 ACK 消息重新投递。
- 数据库提交后 ACK 丢失：消息重复，数据库唯一键幂等。

### 2）Confirm 和消费者 ACK 有什么区别？

Confirm 是 Broker 对生产者的确认，覆盖“消息是否被 Broker 接收”；consumer ACK 是消费者对 Broker 的确认，覆盖“消息是否可以从队列删除”。两者解决的是不同阶段的问题。

### 3）为什么不 `requeue=true`？

持续失败的消息会被立即重新投递，形成 CPU 和网络热循环，阻塞正常消息。临时失败应进入有延迟的重试队列，达到次数后进入 DLQ；永久异常直接 DLQ。

### 4）如何判断临时异常和永久异常？

- 临时：数据库连接失败、锁超时、下游暂时不可用，可重试。
- 永久：消息格式错误、必要字段缺失、无法识别的业务版本，重试不会改变结果。
- 业务幂等冲突不是异常，应读取已有结果后 ACK。

### 5）DLQ 中的消息怎么处理？

DLQ 消费者先将消息、异常原因、重试次数写入补偿表，事务成功后 ACK。后台根据类型自动重放或人工处理。必须有告警、积压年龄监控和重放审计，不能把消息放进 DLQ 就算结束。

### 6）如何保证消息顺序？

该项目不依赖整个队列的全局顺序，而依赖 assignment 状态机和 version 拒绝非法转换。如果某些事件必须按工单有序，可按 orderId 计算分片路由到固定队列，并让单分片内串行消费；但重试会打乱顺序，因此最终仍需版本校验。

### 7）消息积压怎么办？

先判断是突发流量还是单条消息变慢；看 ready、unacked、消费速率和最老消息年龄。消费者无共享状态时可水平扩容；同时批量写库、优化索引和缩短事务。若数据库已到瓶颈，盲目加消费者只会把压力转移到数据库，需要限流和按容量消费。

### 8）5 分钟延迟如何实现？

固定延迟采用 TTL 队列 + DLX：消息进入无人消费的 5 分钟队列，到期后死信到实际处理队列。不要给同一个队列混放大量不同 TTL 的消息，否则队头长 TTL 可能阻塞后面的短 TTL。业务正确性依靠 Token 和状态校验，不依赖消息准时到达。

### 9）RabbitMQ 自己挂了怎么办？

抢单落库事件留在 outbox，恢复后补发。租约到期还有 Redis ZSet 扫描兜底。接口是否继续开放取决于积压阈值：短时可继续 Redis 预占，超过阈值应限流或暂时关闭抢单，避免制造过多未持久化状态。

### 10）prefetch 和消费者并发怎么设？

不背一个固定答案，先按消费事务耗时、数据库连接池和可接受积压时间压测。可以从每消费者 prefetch 10～20 开始观察 ready/unacked、数据库连接等待和 P99，再调整。消费者数量受数据库容量约束，不是越多越好。单条消息处理很慢时，小 prefetch 也能减少消息长期压在某个消费者内存中。

### 11）消息体如何设计？

放事件发生时落库所需的最小快照，至少包含 eventId、eventType、schemaVersion、occurredAt、requestId、orderId、workerId、技能和 traceId。不要只传 orderId 后再回 Redis 拼装关键事实，否则缓存变化会让同一事件重放出不同结果；也不要塞入无关大对象。新增字段保持向后兼容，破坏性变更提升 schemaVersion。

### 12）落库消息超过截止时间才被消费，还能写 MySQL 吗？

不能创建有效 assignment。消费者先用 Lua 原子比较 Redis 当前的 requestId、Token、`PENDING_PERSISTENCE` 状态和 `persistExpireAt`。Token 不匹配说明消息不属于当前租约；时间已过说明技术预占失效，应条件释放名额。可以落一条消费审计，但不能记成抢单成功。校验通过时先把状态改成 `PERSISTING`，再写数据库，避免校验与落库之间被超时任务并发释放。数据库临时失败且尚未到期时条件恢复为 `PENDING_PERSISTENCE` 后重试；消费者宕机或重投遇到 `PERSISTING` 时，先查 MySQL，再决定修成 `RESERVED` 还是回滚。

## 6. Redis 高频追问

### 1）Lua 会阻塞 Redis 吗？

会。Redis 单线程执行脚本期间不能处理其他命令，所以脚本不能访问外部系统，避免遍历大集合，只做固定数量的判断和写入，并监控脚本 P99。数据结构按城市/工单拆分，避免超大 Key。

### 2）Token 为什么能防止旧消息误删？

同一人员再次获得租约时会生成新 Token。延迟消息携带旧 Token，回滚 Lua 先比较当前 Token；不一致说明租约已经变更，旧消息直接返回，不做任何修改。它是租约的“世代身份标识”；严格意义上的 fencing token 通常还要求单调递增，本项目需要比较先后时使用单独的 version。

Token 只能判断“是不是当前这一轮”，不能判断 UUID 的大小顺序。Token 不同通常是旧消息，也可能是错误消息，总之不能操作当前租约；Token 相同也可能是 RabbitMQ 对同一消息的重复投递，所以不能用 Token 代替消息幂等。

### 3）requestId、eventId、Token 和 version 有什么区别？

| 标识 | 解决的问题 |
| --- | --- |
| `requestId` | 客户端同一次抢单的网络重试和异步结果查询 |
| `eventId` | RabbitMQ 重复投递；由数据库唯一键防重复消费 |
| `leaseToken` | 当前这一轮租约身份；旧租约不能操作新租约 |
| `version` | 单调递增，用于判断状态事件的严格先后 |

同一次请求重试必须继续使用相同 requestId；同一消息重复投递仍携带相同 Token，因此消费幂等依靠 eventId 和业务唯一键，而不是 Token。

### 4）为什么租约 Key 不直接设置 TTL 后什么都不管？

TTL 只删除 Key，不会原子恢复 available、技能名额和人员负载；Key 消失后也无法比较旧 Token。明确保存 `persistExpireAt/confirmExpireAt`，由消息或扫描器执行条件回滚，才有完整业务语义。

### 5）缓存和数据库谁是准的？

实时抢占阶段 Redis 是并发闸门，MySQL 是最终、可审计事实。短暂不一致通过 request 状态、事件版本和对账修复。查询长期结果以 MySQL 为准，不能一句“数据库永远为准”就忽略 Redis 已成功但数据库尚未落库的中间态。

### 6）Redis Cluster 下 Lua 跨 Key 怎么办？

本项目采用 Sentinel，因为脚本会同时修改工单和全局人员负载。Cluster 要求脚本 Key 同槽，单纯给工单 Key 加 hash tag 解决不了 worker 全局 Key。迁移 Cluster 时需要缩小原子边界，或按调度分区重新设计数据归属。

### 7）主从切换会不会丢数据？

异步复制下极端情况下可能丢失尚未同步到从库的写。该项目不把 Redis 当最终持久化事实，通过 MySQL、outbox 和对账修复；抢单核心链路在 Redis 不确定时采用保守策略，避免继续放大错误。若业务要求金融级零丢失，需要重新评估一致性模型，而不是只调 Redis 参数。

## 7. MySQL 与一致性追问

### 1）数据库如何幂等？

`event_id` 防同一消息重复消费，`request_id` 防同一请求重复落库，`(order_id, worker_id)` 防业务上的一人一单。不能只先查再插，因为两个事务可能同时查不到；最终要靠唯一约束。

### 2）唯一键冲突都当成功吗？

不能盲目当成功。冲突后要读取已存在记录并核对 orderId、workerId、请求状态是否与当前消息一致。一致才是幂等重放，不一致说明 requestId/eventId 复用或数据污染，需要告警。

### 3）本地消息表为什么要定时扫？

发布可能失败，Confirm 回调也可能因进程重启丢失。扫描 `PENDING/RETRY_WAIT` 且到达 `nextRetryAt` 的记录可以补发。多实例使用行锁跳过或抢占字段，防止同批事件被大量重复发送；即便少量重复，消费者仍须幂等。

outbox 建议使用 `PENDING -> SENDING -> SENT`，失败进入 `RETRY_WAIT`，业务已经过期进入 `CANCELLED`，达到最大生产重试次数进入 `DEAD`。`SENDING` 保存 `senderId/sendLeaseUntil`，投递器宕机后可以重新取得发送权。必须强调：`SENT` 只表示 Broker 已接收且可路由，不代表 assignment 已落库。

### 4）对账时发现 outbox 是 SENDING 怎么办？

不能立即判定成功或失败。先看 assignment：存在就说明业务已落库并修复 Redis；不存在时再看 `sendLeaseUntil`。发送租约尚未到期就等待，已经到期则转为 `RETRY_WAIT` 并允许重发。若抢单的 `persistExpireAt` 也已到期，则通过 Lua 在 `PENDING_PERSISTENCE` 状态下竞争回滚；如果消费者已经抢到 `PERSISTING`，不能回滚，要等消费者提交或由扫描器结合 MySQL 修复。

### 5）对账会不会把新数据覆盖掉？

补偿必须带 requestId、Token 或 version 做条件更新，不允许读出旧值后无条件覆盖。大批对账要分页、限速，先记录差异和告警，再按可证明的规则修复。

## 8. 面试官可能指出的设计挑战

### “为什么 Redis 预占后才写 outbox，这不还是双写吗？”

回答重点：是的，outbox 只能解决 MySQL 业务事务到 MQ 的可靠发布，不能天然解决 Redis 到 MySQL。项目明确承认这个空窗，并用 Lua 同步记录 pending event、定时对账和条件回滚闭环。如果一致性要求更高，也可以改为数据库先写、Redis 只做缓存，但会牺牲热点抢单性能和即时库存判断。

### “异步落库失败，用户不是白抢了吗？”

用户最初看到的是 PROCESSING，不是最终成功。可恢复异常会自动重试；确认无法落库时释放租约并返回失败。产品上通过短轮询/推送呈现结果。系统在低延迟和同步确定性之间做了明确取舍。

### “为什么一个工单要多人抢，不直接由系统派单？”

突发场景中，系统先筛选和推送合适候选人，但人员是否可立即响应仍需本人确认。抢单不是完全无约束的公开竞争，而是候选范围内的快速确认机制。对于必须强制指派的岗位，可以复用同一租约和确认状态机，由调度员创建预占。

### “人员确认后退出怎么办？”

确认后的退出不是预占超时，而是可审计的 WITHDRAWN 状态。它释放一个名额、降低人员负载并触发补位，必要时通知调度员。把两条链路拆开可以避免用同一个 5 分钟 Token 管理整个救援生命周期。

## 9. 一个故障案例的 STAR 讲法

如果没有真实线上事故，请明确说这是故障演练。

> **S（场景）**：我在故障演练中发现，只使用 outbox 仍有一个缺口：Lua 已经扣了 Redis 名额，但服务可能在插入 outbox 前宕机。
>
> **T（任务）**：需要保证这个窗口不会永久占用名额，同时不能因为粗暴回滚而误删已经落库的成功记录。
>
> **A（行动）**：我在 Lua 中同步记录 requestId、事件快照和 pending 时间。扫描器只处理超过阈值的记录，先按 requestId 查询 MySQL；有记录就修正 Redis 状态，没有记录且租约仍有效就幂等补写 outbox，租约过期才用 Token 条件回滚。我还注入了进程终止、MQ 停机和 ACK 丢失三类故障。
>
> **R（结果）**：用实际压测结果填写，例如“在 X 次注入中，没有出现永久占位；恢复时间 P95 为 X；重复消息均被唯一键拦截”。没有测量前不要填数字。

## 13. 面试表达红线

- 不说“RabbitMQ 保证消息绝不丢失”，说清可靠性措施和边界。
- 不说“实现 exactly once”，说“至少一次投递 + 业务幂等”。
- 不说“用了 Lua 所以整个系统强一致”，Lua 只保证 Redis 内的原子性。
- 不把 outbox 说成自动解决 Redis 与 MySQL 双写。
- 不把 5 分钟说成救援完成时限，它是确认接单租约。
- 不说“用了分布式锁防超卖”，如果实现实际采用的是 Lua。
- 不报未经压测的数据，不把个人故障演练说成线上事故。
