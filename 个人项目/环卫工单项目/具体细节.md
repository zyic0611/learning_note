# 城市应急调度平台——详细设计

> 本文统一项目的业务口径和技术实现。面试讲法、追问清单见《面试准备.md》。

## 1. 先统一业务语义

一个工单代表一个应急事件，例如“XX 小区地下车库积水”。一个工单可以有多个、甚至多种技能的人员名额，例如需要 5 名排水人员、3 名交警和 2 名医护。

- 一名人员对同一工单只能占一个名额。
- 点击抢单后先进入短时的 `PENDING_PERSISTENCE` 技术预占，要求在 `persistExpireAt` 前完成 MySQL 落库；示例可先设 30 秒，最终以压测结果配置。
- MySQL 落库成功后才进入正式的 `RESERVED`，并从此时开始计算 5 分钟的人工确认期限 `confirmExpireAt`；5 分钟不是要求完成救援。
- 确认后进入正式执行阶段，完工时更新该人员的执行记录，不再恢复名额。
- 技术预占未及时落库，或者正式预占后 5 分钟未确认，系统都会按各自状态和截止时间释放名额与人员负载。
- 如果已确认的人员后来退出，这是另一条“退出并补位”业务，不和 5 分钟预占超时混用。
- 所有必需名额均已确认后，工单进入 `EXECUTING`；所有名额均已完工后，工单进入 `COMPLETED`。

### 为什么要拆成“技术预占、正式预占、确认、完工”四步

旧设计把“5 分钟未完成”和“执行完成”混为一谈，也通过 `workers` 集合是否为空判断整个工单是否完成。这会产生歧义：人员完成后被移出集合，但名额并没有恢复；此时另一人超时，又可能把工单改回待抢状态。

拆分后，每个数字都有唯一含义：

| 字段 | 含义 |
| --- | --- |
| `requiredCount` | 工单最初需要的人数，创建后通常不变 |
| `availableCount` | 还能被抢的名额数 |
| `reservedCount` | 已扣减名额但尚未确认的人数，包含待落库和已落库待确认 |
| `confirmedCount` | 已正式确认接单的人数 |
| `finishedCount` | 已完成任务的人数 |

始终满足：`availableCount + reservedCount + confirmedCount = requiredCount`。`finishedCount` 是 `confirmedCount` 的子集，不参与恢复名额。

## 2. 状态机

### 工单状态

```text
CREATED -> RECRUITING -> EXECUTING -> COMPLETED
   |           |             |
   +-----------+-------------+----> CANCELLED
```

- `RECRUITING`：仍有可抢名额，或者仍有人处于预占待确认状态。
- `EXECUTING`：全部名额都已确认。
- `COMPLETED`：`finishedCount == requiredCount`。
- `CANCELLED`：管理员取消；取消操作需与抢单脚本互斥地校验状态。

### 单个人员的名额状态

```text
NONE -> PENDING_PERSISTENCE -> RESERVED -> CONFIRMED -> FINISHED
                    |              |           |
                    v              v           v
                 EXPIRED        EXPIRED     WITHDRAWN -> 重新开放一个名额
```

- `PENDING_PERSISTENCE`：Redis 已暂扣名额，等待 RabbitMQ 消费者在 `persistExpireAt` 前完成落库。
- `RESERVED`：MySQL 已落库，人员须在 `confirmExpireAt` 前确认。
- 租约 Token 保护的是“这一次租约”相关的条件转换；完工接口依据数据库中的 assignmentId 和状态做幂等，不继续复用预占 Token。

## 3. 一条完整的业务故事

1. 调度中心创建工单，配置位置、事件等级、所需技能和各技能人数。
2. 系统用 Redis GEO 找到附近在线人员，过滤技能、班次、当前负载等硬条件，计算候选人得分并推送。
3. 工人点击抢单。应用从登录身份中取得 workerId，在应用层生成 `requestId` 和候选 `leaseToken`，调用 Lua 原子完成校验和预占。同一 requestId 重试时，Lua 返回第一次保存的 Token，不能用新的候选 Token 覆盖原租约。
4. Lua 写入短时 `persistExpireAt`，接口返回 `requestId + PROCESSING`。客户端轮询查询接口，或由推送通知最终结果。
5. 应用将“预占成功事件”写入本地消息表；投递任务可靠发送到 RabbitMQ。
6. 落库消费者先原子校验 requestId、Token、`PENDING_PERSISTENCE` 状态和 `persistExpireAt`。已经超时或 Token 不匹配的消息不能创建有效 assignment；仍有效才幂等写入 MySQL。
7. 数据库落库成功后，请求状态变为 `RESERVED`，生成 `confirmExpireAt = 落库成功时间 + 5 分钟`，人员获得完整的 5 分钟确认时间。
8. 确认接口使用 Lua 比较 workerId、requestId 和 Token，将该名额从 `RESERVED` 改为 `CONFIRMED`。
9. RabbitMQ 中的 5 分钟确认延迟消息到期。它只有在“Token 仍相同、状态仍为 RESERVED、当前时间已到 confirmExpireAt”时才能释放名额，因此迟到的旧消息不会误删新租约。
10. 全部名额确认后工单进入 `EXECUTING`。每名人员独立提交完工；数据库原子增加 `finishedCount`，达到需求人数后工单进入 `COMPLETED`。

## 4. 候选人匹配和优先级调度

### GEO 粗筛

- 工人的在线位置存入 `worker:geo:{cityId}`。
- 工单按事件类型设置搜索半径，例如先搜索 3 公里，不足时扩大到 5 公里、10 公里。
- GEO 只做空间粗筛，避免直接扫描整座城市的人员。
- 对结果再检查技能、在线状态、班次和负载。workerId 必须来自服务端登录态，不能相信客户端传入值。

### 候选人排序

面试中可用下面的可解释模型，不需要声称用了复杂机器学习：

```text
score = 距离分 * 0.45 + 技能匹配分 * 0.30
      + 空闲度 * 0.15 + 历史响应分 * 0.10
```

硬条件先过滤，软条件再排序。权重配置化，避免写死。对位置长时间未上报的人员直接过滤，防止使用陈旧定位。

### 工单优先级与防饥饿

待调度工单放入按城市或区域拆分的 ZSet：

```text
priorityScore = 事件等级基础分 + 等待分钟数 * agingFactor
```

调度器周期性取最高优先级的一批工单。等待时间会不断抬高分数，使普通事件也能最终被处理。不要高频重写全量 ZSet；可在取出候选工单时计算动态分，或按时间桶批量刷新。

## 5. Redis 数据模型

以下是一种面试时能够解释清楚的模型，并不要求每个字段都真的拆成单独 Key：

| Key | 类型 | 作用 |
| --- | --- | --- |
| `order:{orderId}:meta` | Hash | 状态、总名额、available/reserved/confirmed/finished、version |
| `order:{orderId}:skill_slots` | Hash | `DRAINAGE -> 5` 等各技能剩余名额 |
| `order:{orderId}:workers` | Set | 已预占或已确认的 workerId，用于一人一单 |
| `order:{orderId}:lease:{workerId}` | Hash | requestId、token、state、persistExpireAt、confirmExpireAt、version |
| `order:{orderId}:lease_deadlines` | ZSet | score 为当前阶段截止时间，用于落库和确认超时兜底扫描 |
| `order:{orderId}:pending_events` | ZSet | Redis 成功但尚未确认写入 outbox 的请求 |
| `request:{requestId}` | Hash | PROCESSING/RESERVED/FAILED、orderId、workerId、失败原因 |
| `worker:{workerId}:load` | String | 当前预占及执行中的任务数 |

`lease` 记录不能只依赖 TTL 自动消失。超时回滚需要读取并比较旧 Token；如果 Key 先过期，处理器反而无法判断它是否对应当前租约。这里分别保存 `persistExpireAt` 和 `confirmExpireAt`，由消息消费者或 ZSet 扫描器在 Lua 中做条件回滚。

### Redis 部署口径

抢单 Lua 同时访问工单 Key 和人员负载 Key。Redis Cluster 要求脚本涉及的 Key 位于同一 hash slot，而不同工单和人员很难同时满足这一点。本项目口径采用主从 + Sentinel，在当前规模下保留跨 Key 原子脚本能力。

如果将来必须迁移 Cluster，有两种选择：

1. 缩小 Lua 原子边界，只原子维护工单名额；人员全局容量改由数据库唯一约束/事务或独立服务控制。
2. 按业务分片使同一调度分区落到同一槽位，并接受跨分区不能由一个 Lua 保证原子性。

不能只说“Key 都加 `{orderId}`”来回避问题，因为全局的 `worker:{workerId}:load` 不可能同时跟每个 orderId 共槽。

## 6. 抢单 Lua 的原子边界

`requestId` 和 Token 由 Java 应用提前生成并作为 `ARGV` 传入。Redis Lua 没有可靠的 UUID 生成能力。

脚本内按以下顺序执行：

1. 检查工单必须为 `RECRUITING`，且未取消。
2. 检查 worker 是否已经存在于 workers 集合。若同一个 requestId 重试，直接返回原结果；若是另一次请求，返回“已经抢过”。
3. 检查该 worker 的技能对应名额是否大于 0。
4. 检查 worker 当前负载是否低于上限。
5. `availableCount - 1`、`reservedCount + 1`，对应技能名额减 1，worker 负载加 1。
6. 写入 workers、lease=`PENDING_PERSISTENCE`、request=`PROCESSING`，并把 requestId 加入 `pending_events`。
7. 将 workerId/lease 标识加入 `lease_deadlines`，score 为短时的 `persistExpireAt`。
8. 返回预占成功及 requestId。

所有判断和写操作在一次脚本中完成，因此不会出现“先查询还有名额，随后两个线程都扣减”的竞态，也不需要分布式锁。脚本只做内存操作，不访问网络或数据库，并控制执行时间。

### 接口幂等

- 客户端每次业务意图携带唯一 requestId；网络重试继续使用同一个 requestId。
- 同一 requestId 返回相同结果。
- 同一 worker 换 requestId 再抢同一工单，由 workers 集合拒绝。
- 数据库仍建立 `(order_id, worker_id)` 唯一索引，形成最终防线。

### 四个标识不要混用

| 标识 | 作用 |
| --- | --- |
| `requestId` | 标识客户端的一次业务意图；同一请求网络重试时返回原结果，也用于查询异步状态 |
| `eventId` | 标识一条消息事件；数据库 `UNIQUE(event_id)` 防 RabbitMQ 重复消费 |
| `leaseToken` | 标识当前这一轮租约；与 Redis 当前 Token 不同就不能操作当前租约 |
| `version` | 单调递增的状态版本；需要判断事件严格先后时使用 |

随机 Token 只能判断“相同/不同”，不能像数字 version 一样比较谁更新。Token 不同通常表示旧消息，也可能是错误消息；无论哪种情况都必须拒绝操作当前租约。Token 相同也不能证明消息没有被消费过，因为同一条重复消息携带的仍是同一个 Token，重复消费必须依靠 eventId 唯一键和业务状态机。

## 7. 抢单接口与异步落库

### 正常路径

```text
客户端 -> 抢单服务 -> Redis Lua 预占
                    -> MySQL outbox 写 PENDING
                    -> 返回 requestId/PROCESSING

outbox 投递器 -> RabbitMQ -> 消费者事务落库 -> Redis 标记 RESERVED
```

接口返回 `PROCESSING`，是因为 Redis 成功不等于 MySQL 已成功落库。查询接口：

1. 优先读 Redis 的 request 状态。
2. Redis 不可用或长期 PROCESSING 时，以 MySQL assignment/outbox 记录兜底。
3. MySQL 已成功但 Redis 未更新时，返回成功并触发/等待修复任务回填缓存。

### Redis 成功、outbox 写失败

如果应用仍存活并明确收到数据库失败，立即调用补偿 Lua。补偿脚本只有在 requestId 和 Token 均匹配、lease 仍为 `PENDING_PERSISTENCE` 时才执行，恢复名额、技能名额与人员负载，删除人员标记，并把请求置为失败。

### Redis 成功、写 outbox 前宕机

这是最容易被追问的“空窗期”。预占脚本已经把 requestId 写入 `pending_events`。对账任务扫描超过短阈值仍未确认的记录：

1. 先查 assignment。存在说明业务已经落库，根据数据库状态修正 Redis，并移除 pending 标记。
2. assignment 不存在，再查 outbox。outbox 也不存在且尚未超过 `persistExpireAt`，根据 Redis 事件快照幂等补写 outbox；requestId/eventId 唯一键可以处理与原请求并发插入的情况。
3. assignment 不存在且已经超过 `persistExpireAt`，不能只看 outbox 是否存在。对 Redis 执行条件 Lua：只有 requestId、Token、version 仍相同且状态仍为 `PENDING_PERSISTENCE` 才回滚。若消费者已把状态抢占为 `PERSISTING`，则等待短保护期后结合数据库结果修复。
4. 即使回滚后迟到的 outbox 消息又被发送，落库消费者也会看到 lease 已是 `EXPIRED`，不会创建有效 assignment。

因此 outbox 并没有单独消灭 Redis 与 MySQL 的双写问题；真正补上空窗的是 Redis 待确认事件 + 定时对账。

## 8. RabbitMQ 设计

RabbitMQ 在这里承担两类职责，不要混成一个队列：

1. **抢单事件异步落库**：削峰并缩短抢单接口耗时。
2. **正式租约延迟检查**：MySQL 落库成功后开始计时，5 分钟后检查人员是否确认。

### 建议拓扑

| 用途 | Exchange | Queue | Routing Key |
| --- | --- | --- | --- |
| 抢单落库 | `dispatch.claim.x`（direct） | `dispatch.claim.persist.q` | `claim.reserved` |
| 临时失败重试 | `dispatch.claim.retry.x` | `dispatch.claim.retry.5s.q` | `claim.retry` |
| 最终死信 | `dispatch.claim.dlx` | `dispatch.claim.dlq` | `claim.dead` |
| 租约延迟 | `dispatch.lease.delay.x` | `dispatch.lease.delay.5m.q` | `lease.delay` |
| 租约到期执行 | `dispatch.lease.x` | `dispatch.lease.expire.q` | `lease.expire` |

项目不依赖 RabbitMQ 延迟插件：固定 5 分钟可通过“TTL 队列 + DLX”实现。延迟队列不设消费者，消息到期后死信转发到真正的到期处理队列。若需要大量不同延迟时间，才考虑延迟插件或按时间分桶。

### 生产端可靠性

#### outbox 状态机

```text
PENDING -> SENDING -> SENT
              |
              v
          RETRY_WAIT -> SENDING

PENDING / RETRY_WAIT -> CANCELLED
多次发送失败          -> DEAD
```

| 状态 | 含义 |
| --- | --- |
| `PENDING` | 已写本地消息表，等待投递 |
| `SENDING` | 某个投递器已取得发送权，正在等待 Broker Confirm |
| `RETRY_WAIT` | NACK、Confirm 超时或不可路由，等待 `nextRetryAt` 后重试 |
| `SENT` | Broker 已 ACK 且消息可路由；不代表消费者已完成 assignment 落库 |
| `CANCELLED` | 业务技术预占已经过期，尚未发送的事件停止投递 |
| `DEAD` | 超过生产端最大重试次数，需要告警、回滚或人工处理 |

`SENDING` 需要附带 `senderId` 和短时 `sendLeaseUntil`。投递进程可能在 Broker 收到消息后、更新 SENT 前宕机；其他实例等发送租约过期后把它改成 `RETRY_WAIT` 并重发。这里的 `sendLeaseUntil` 只控制“哪个投递器负责发送”，与抢单业务的 `persistExpireAt` 不是同一个时间。

- Exchange、Queue、Binding 声明为 durable。
- 消息 delivery mode 设为 persistent。
- 开启 Publisher Confirm，并设置 `mandatory=true` 和 Return 回调。
- 只有 Confirm ACK 且消息可路由时，outbox 才可标记为 `SENT`。
- NACK、Confirm 超时或 Return 将状态改为 `RETRY_WAIT`，后台按 `nextRetryAt` 指数退避重投。
- 多实例投递器使用 `SELECT ... FOR UPDATE SKIP LOCKED` 或抢占字段，避免同一实例批次内重复发送。

Confirm 只表示 Broker 接收了消息，不表示消费者业务成功。即使 Confirm 成功后服务在更新 outbox 前宕机，消息仍会重发，所以整个系统目标是“至少一次 + 业务幂等”，不宣称 exactly once。

### 消费端事务与 ACK

消费者关闭自动 ACK。落库之前不能只看消息自己的时间，也不能只比较 Token；需要以 Redis 当前租约为准，原子检查：

```text
requestId 相同
&& Token 相同
&& state == PENDING_PERSISTENCE
&& now < persistExpireAt
```

条件不满足时，不创建有效 assignment：Token 不同表示它不属于当前租约；已经超过 `persistExpireAt` 则由 Lua 原子释放技术预占并把请求置为 `EXPIRED`。可以写消费审计记录，但不能写成抢单成功。

为了避免“校验通过后、数据库写入前又被超时任务释放”的检查—执行竞态，校验 Lua 先把状态从 `PENDING_PERSISTENCE` 条件转换为 `PERSISTING`，相当于取得本轮落库资格。消费者此时用服务端时间计算 `confirmExpireAt = now + 5 分钟`，随后处理顺序如下：

1. 开启 MySQL 事务。
2. 按 eventId 插入 `consumed_event`。唯一键冲突时读取已有 assignment 并核对业务字段，一致才按幂等成功处理。
3. 插入带 `confirmExpireAt` 的 assignment、更新工单持久化计数，并在同一事务中写入“5 分钟确认超时”outbox；`(order_id, worker_id)` 再设唯一索引。
4. 提交事务。
5. 通过 Lua 把 Redis lease 改为 `RESERVED`，写入与数据库及超时事件相同的 `confirmExpireAt`，并更新 deadline ZSet；失败则交给修复任务，不回滚已提交数据库。
6. 手动 ACK。对于重复消息，读取已有 assignment 后也要尝试修复 Redis 状态，再 ACK。

若数据库提交后、ACK 前连接断开，Broker 会重新投递；`event_id` 和 `(order_id, worker_id)` 两层唯一键保证不会多生成 assignment。

数据库事务失败时，消费者根据当前时间执行条件 Lua：还没到 `persistExpireAt`，就把本事件占有的 `PERSISTING` 恢复为 `PENDING_PERSISTENCE` 后进入延迟重试；已经到期则释放技术预占。不能让一次临时数据库异常把租约永久卡在 `PERSISTING`。

如果消费者在 `PERSISTING` 后宕机，或者消息重投时发现同一个 eventId/requestId 仍处于 `PERSISTING`，扫描器或重投消费者先按 requestId 查询 MySQL：已经提交就将 Redis 修成 `RESERVED`，没有记录且保护期已过才回滚。所有修复都比较 Token/version，不能无条件覆盖后来状态。

### 重试和 DLQ

- 数据库短暂不可用、锁等待超时等临时错误：投到 5 秒重试队列，最多 3 次。
- 数据格式错误、必要字段缺失等永久错误：直接进最终 DLQ。
- 重试次数可从自定义 header 或 `x-death` 读取；达到上限后路由 DLQ，避免 `requeue=true` 形成热循环。
- 若采用“重新发布到重试队列再 ACK 原消息”，重新发布也必须等待 Confirm；发布失败则不 ACK 原消息。
- DLQ 独立消费者先把消息写入 MySQL 补偿表，提交成功再 ACK。后台可重放或人工判定。

### 租约延迟消息的正确性

消息体至少包含 `orderId、workerId、requestId、leaseToken、confirmExpireAt、version`。到期消费者调用 Lua：

1. 当前 lease 不存在：说明已处理，直接幂等成功。
2. 当前 Token/requestId 与消息不一致：旧消息，直接忽略。
3. 当前状态不是 `RESERVED`：已经确认或释放，直接忽略。
4. 当前时间早于 confirmExpireAt：异常提前到达，重新安排剩余延迟或交由 ZSet 扫描。
5. 条件均满足：释放名额、恢复技能名额、减少 reservedCount 和人员负载，移除 workers，并把请求置为 `EXPIRED`。

RabbitMQ 延迟消息可能迟到，所以它只是触发器，业务正确性必须由 Token + 状态 + `confirmExpireAt` 条件保证。延迟事件由 assignment 落库事务中的 outbox 可靠投递；即使消息投递失败，`lease_deadlines` ZSet 扫描器也会按绝对 `confirmExpireAt` 兜底，不能因为消息晚发送就从发送时刻重新计算 5 分钟。

### 消费并发参数

- `prefetch` 不能盲目设大，应结合单条事务耗时和数据库连接池设置，例如先从每消费者 10～20 条开始压测。
- 消费者并发数不能超过数据库可承受范围；队列积压时盲目扩容，可能把 RabbitMQ 压力转成数据库雪崩。
- 消息体只放落库所需快照和标识，不放大对象；包含 `eventId、eventType、schemaVersion、occurredAt、traceId`，便于幂等、演进和排障。
- 如果演示环境是单节点 RabbitMQ，要如实说明 durable/persistent 只能应对进程重启，不能应对节点磁盘损坏；生产高可用还需要多节点和复制型队列，并经过故障演练。

## 9. MySQL 核心表和约束

### assignment（人员工单关系）

关键字段：`id、event_id、request_id、order_id、worker_id、skill_type、status、lease_token_hash、reserved_at、confirmed_at、finished_at、version`。

关键索引：

- `UNIQUE(event_id)`：消费事件幂等。
- `UNIQUE(request_id)`：接口请求幂等。
- `UNIQUE(order_id, worker_id)`：一人一工单。
- `INDEX(worker_id, status)`：查询人员当前任务及负载修复。
- `INDEX(order_id, status)`：统计工单各阶段人数。

Token 不建议明文长期保存，可保存摘要，日志中也必须脱敏。

### outbox_event

关键字段：`event_id、aggregate_id、event_type、payload、status、retry_count、next_retry_at、created_at、sent_at`。

索引：`UNIQUE(event_id)` 和 `INDEX(status, next_retry_at)`。

### consumed_event

关键字段：`event_id、consumer_group、consumed_at`，唯一键为 `(event_id, consumer_group)`。如果未来同一事件有多个不同业务消费者，它们可以各自消费一次。

## 10. 确认、完工和退出补位

### 确认接单

确认接口校验 Token 后原子执行：`reservedCount - 1、confirmedCount + 1`，lease 状态改为 `CONFIRMED`，移出 deadline ZSet。若确认后 `availableCount == 0 && reservedCount == 0`，工单进入 `EXECUTING`。重复确认返回原成功结果。

确认结果也要通过事件同步到 MySQL。Token 超时与确认并发时，由同一 Lua 串行决定：谁先满足状态转换谁成功，另一方读取到终态后幂等退出。

### 人员完工

完工以 MySQL 为最终事实，在事务内将 assignment 从 `CONFIRMED` 条件更新为 `FINISHED`，只有更新行数为 1 时才增加 `finishedCount`。重复请求更新行数为 0，直接返回已有结果。达到 requiredCount 后工单完成，再发布“工单完成”事件更新缓存和下游；人员负载通过同一事件幂等减一。已完工人员仍保留在工单人员关系中，不能靠删除 workers 成员表示完成。

### 已确认人员退出

退出需要权限和原因审核。事务内把 assignment 改为 `WITHDRAWN`，并通过补偿事件将 Redis 的 `confirmedCount - 1、availableCount + 1、workerLoad - 1`，工单回到 `RECRUITING`。这条链路与预占超时分开，便于审计。

## 11. 对账与补偿

对账不做无条件覆盖，而是根据 requestId/eventId/version 修复：

- Redis 有预占、MySQL 无 outbox：补写 outbox 或在超时后释放。
- outbox 长期 PENDING：重新投递。
- MySQL 有 assignment、Redis request 仍 PROCESSING：回填成功状态。
- Redis 计数与 MySQL assignment 汇总不一致：先告警和记录差异，再依据事件版本修复。
- `persistExpireAt` 已过但 lease 仍为 `PENDING_PERSISTENCE/PERSISTING`：先查 MySQL，再完成落库状态修复或释放技术预占。
- `confirmExpireAt` 已过但 lease 仍为 `RESERVED`：执行与确认超时消费者相同的条件 Lua。

修复任务分片、限批、带游标运行，避免一次全表扫描冲击数据库。所有补偿操作本身也必须幂等。

## 12. 关键并发场景

| 场景 | 结果 |
| --- | --- |
| 最后一个名额被多人同时抢 | Lua 串行执行，只有一人扣减成功 |
| 同一人员连续点击 | 相同 requestId 返回原结果；不同 requestId 被 workers 拒绝 |
| 确认与超时同时发生 | 同一 Lua 状态机只允许一个状态转换成功 |
| 旧延迟消息遇到新租约 | Token/requestId 不同，旧消息跳过 |
| 抢单落库消息超过 persistExpireAt 才消费 | 不创建有效 assignment，条件释放技术预占并记录审计结果 |
| 同一落库消息重复投递 | Token 可能仍相同，由 eventId 唯一键和状态机防重复落库 |
| Confirm ACK 后 outbox 状态没更新 | 生产端重发，消费端 eventId 幂等 |
| 数据库提交后 ACK 丢失 | RabbitMQ 重投，数据库唯一键幂等 |
| Redis 预占后服务宕机 | pending_events 对账补写 outbox 或超时释放 |
| RabbitMQ 停机超过技术预占期限 | persist deadline 扫描器释放未落库预占；已落库租约由 confirm deadline 扫描器兜底 |
| Redis 故障转移丢失极少量最新写 | MySQL/outbox/对账修复；接口在恢复前降级为不可抢或走保守策略 |

## 13. 可观测性

至少准备以下指标，面试时能说明“如何知道系统真的可靠”：

- 抢单请求量、成功率、P95/P99 延迟、Lua 执行耗时。
- 名额不足、重复抢单、人员超负载等拒绝原因分布。
- outbox PENDING 数量、最老事件停留时间、重试次数。
- RabbitMQ ready/unacked 消息数、消费速率、积压时长、Confirm NACK/Return 数。
- DLQ 消息数与最老消息年龄。
- 超时释放数量、延迟消息实际到达偏差、ZSet 兜底命中数。
- Redis/MySQL 对账差异数、自动修复成功率。

日志统一带 `traceId、requestId、eventId、orderId、workerId`，但不记录明文 Token。告警重点看“积压时长”而不只是队列长度，因为不同流量下相同长度的意义不同。

## 14. 压测与故障演练

不要在面试中编造生产数据。应实际做一次可复现压测，再把结果填入《面试准备.md》：

1. 一个工单 10 个名额，使用 100/500/1000 个并发人员争抢，验证成功数永远为 10。
2. 同一 worker 使用相同和不同 requestId 连续请求，验证数据库最终只有一条记录。
3. 在 Redis 成功后主动终止应用，验证 pending_events 能补写或释放。
4. 关闭 RabbitMQ 后恢复，验证 outbox 补发、无数据丢失且可能重复。
5. 在数据库提交后模拟 ACK 丢失，验证重复消费不会生成重复记录。
6. 暂停超时消费者，验证 ZSet 扫描能够释放过期租约。
7. 记录机器配置、数据规模、并发数、测试时长、P95/P99、吞吐量和错误率。

## 15. 明确边界，避免过度设计

- Redis 负责高并发实时预占，MySQL 保存最终可审计事实。
- RabbitMQ 保证至少一次传递，业务唯一键和状态机保证重复消息无副作用。
- 系统实现的是最终一致性，短时间内查询到 PROCESSING 是正常状态。
- 不宣称 exactly once、不宣称绝对不丢、不把分布式锁当成万能方案。
- 若业务要求“接口返回成功时数据库必须已经提交”，就应改为同步数据库事务；不能同时追求异步返回又声称强一致。
