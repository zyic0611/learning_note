# 抢单接口（旧版描述，仅供对照）

> 新的业务口径和实现以《具体细节.md》为准。本文件保留用于对比，不再作为面试讲稿。

抢单链路采用 Redis 原子预占、RabbitMQ 异步落库、生产端本地消息表补发、消费端数据库幂等以及定时对账补偿的最终一致性方案，整体保证至少一次投递和业务结果幂等，不宣称消息只投递一次。

请求进入后，先获取工人和任务的基础信息。热点信息采用旁路缓存，但任务状态、剩余名额和一人一单标记由 Lua 脚本在 Redis 中一次性完成校验和修改，避免校验与扣减之间产生竞态。Lua 成功后会扣减名额、写入工人抢单标记，并生成带有 requestId 的 PROCESSING 状态记录。

Redis 预占成功后，应用向 MySQL 本地消息表插入一条 PENDING 记录。插入失败时，通过 Lua 根据 requestId 条件回补库存并删除抢单标记，确保补偿幂等。考虑到 Redis 成功后应用可能在写消息表前宕机，Lua 还会把请求加入待处理集合，定时任务扫描超时的 PROCESSING 请求，根据数据库记录决定补写消息或回补库存。

消息由独立投递任务发送到 RabbitMQ，交换机和队列设置为持久化，消息设置为 persistent，并启用 Publisher Confirm、mandatory 和 Return 回调。Confirm ACK 且消息可路由后，将本地消息状态更新为 SENT；如果出现 NACK、超时或者不可路由，状态保持 PENDING，由后台任务重新投递。即使 Confirm 成功后状态更新失败导致重复发送，消费端也可以幂等处理。

消费端采用手动 ACK。在一个 MySQL 事务中，先根据 eventId 插入消费幂等记录，再插入抢单记录并更新任务数据；eventId 以及 taskId、workerId 建立唯一索引。事务提交成功后更新 Redis 请求状态为 SUCCESS，Redis 更新失败则由状态修复任务补写，查询接口在缓存异常时回源 MySQL。最后进行 ACK。数据库提交后如果 ACK 丢失，消息会重新投递，但唯一索引可以保证不会生成重复抢单记录。

对临时异常，消息进入 5 秒延迟重试队列，达到 3 次后通过 DLX 路由到最终 DLQ；永久性异常直接进入 DLQ。独立消费者将 DLQ 消息写入本地补偿表，写入成功后再 ACK，由后台任务执行补偿。同时通过定时对账检查 Redis 预占记录、本地消息表和 MySQL 抢单记录，修复长期处理中、漏投递和库存不一致问题。

接口返回的是 requestId 和 PROCESSING，客户端通过查询接口获取最终结果；查询优先读取 Redis，必要时回源 MySQL。
