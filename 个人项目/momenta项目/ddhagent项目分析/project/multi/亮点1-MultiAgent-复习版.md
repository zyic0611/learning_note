# Multi-Agent 确定性执行架构 

> **一句话定位**：LeadAgent 只做"声明式规划"，执行交给确定性调度器；规划与执行解耦，正确性由代码保证，LLM 只管它擅长的。

---

## 〇、30 秒故事线

```
飞书消息 → 统一入口 → LeadAgent（中档模型）
   │  输出：{tasks:[{id, agent, goal, produces, consumes}]}（受限结构化输出）
   ▼
服务端解析成 DAG → 三层校验：①schema ②环检测(Kahn's) ③数据流完整性
   ▼
拓扑排序调度：asyncio.TaskGroup 同层并行、跨层串行；节点状态持久化 PostgreSQL
   ▼
专家 Agent 各自闭环执行（内部独立多轮推理：查→判→重试→换路）
   ▼
聚合前仲裁校验（确定性规则优先 + LLM 兜底）
   ▼
最终回复（明确标注部分完成情况）｜异常走四条降级路径
```

**一段话版本**（开场直接背这个）：

"用户请求进来后，LeadAgent 把它拆成任务清单——每个任务声明自己产出什么、消费什么，依赖关系由服务端从 produces/consumes **自动推导**，而不是让 LLM 连边。服务端把计划解析成 DAG，做三层校验：结构、环、数据流完整性，全过才执行。执行按拓扑序，无依赖的节点并行、有依赖的等上游输出；节点状态持久化到 PostgreSQL，崩溃能恢复。最后聚合前有仲裁层检测跨 Agent 矛盾。整体设计原则一句话：**LLM 只声明关系，正确性交给确定性代码**。"

## 一、一级核心

### Q1 为什么 Multi-Agent，不是单 Agent 挂一堆工具？

三个理由，按优先级说：

1. **异构专家域 + 权限隔离**（业务层）：选型/项目/测试是三个子部门的知识域，工具和权限不同。多 Agent 把错误范围控制在单个 Agent 内，不会跨权限调错工具。
2. **可审计的显式计划**（工程层）：LeadAgent 产出的是人可读的 DAG，用户能看到"系统打算怎么做、做到哪了"；单 Agent 是黑盒。
3. **状态隔离**（架构层）：每个 Agent 上下文独立，一个 Agent 的上下文污染不会传染其他分支。

**加分细节**：系统是**双入口设计**——用户可以直接对话某个子 Agent（自动退化成单 Agent 模式），也可以走统一入口由 LeadAgent 处理跨部门复合需求（"选个型号，同时看看项目进度和需要的测试项"）。多 Agent 不是强制所有人走一条路的架构，而是"简单问题不付出多 Agent 代价"。

### Q2/Q3 单 Agent 也能一次并行多个 tool_use，区别到底在哪？

**本质区别：每个 DAG 节点不是一次工具调用，而是一个子 Agent 完整的独立推理循环。**

- 多 Agent：每个分支**内部自己**判断"结果合不合理、要不要重试、要不要换查法"，错误处理在分支内闭环；
- 单 Agent 并行 tool_use：所有结果汇总到一个上下文里统一判断——是"**扁平并行 + 事后统一判断**"。

**配套论据（Q4 的答案也在这）**：本项目以 RAG 为主，检索天然要查多次。多 Agent 各自在**窄上下文**里判断自己的检索结果——上下文短、成本低、判断聚焦；单 Agent 把多域检索结果塞进一个**长上下文**，成本反而更高、还容易被无关信息干扰。

**被追问：成本/延迟不更高吗？** → 两层保障：工程上有全局 token 熔断 + 每个子 Agent 循环次数上限；业务上窄上下文判断本身就是省成本的手段。不是过度设计——是"业务需要多次检索"决定了这个架构。

### Q4 计划怎么生成？

LeadAgent 只输出**声明式任务清单**（每个任务声明 `produces`/`consumes`），依赖边由服务端匹配自动推导。LLM 从不说"谁依赖谁"——它只说"我需要什么、产出什么"，**关系是算出来的，不是编出来的**。

### Q5 计划怎么保证正确？（三层校验）

1. **Schema 校验**：tool-calling/结构化输出强制，字段名、枚举、结构在生成层就锁死（不是"生成完再校验"，是生成时就不允许错）；
2. **环检测**：Kahn's 算法（拓扑排序 BFS 版），顺便拿到拓扑序，O(V+E) 一次搞定；
3. **数据流完整性检查**（最深的一层）：每个任务的 `consumes` 必须有 producer——要么上游 `produces` 匹配，要么来自用户原始请求/常量。有占位符没人产出 → 计划非法，拒绝或打回重规划。**这层能抓"幻觉输入"，比环检测更深。**

### Q6 节点失败怎么处理？（状态机语义）

- **先分清两件事**：abstention（查不到/低置信度）**≠** FAILED（工具/LLM 调用异常、超时且重试耗尽）。
- **abstention 是正常终态**（状态 SUCCESS），走"低置信度 → 触发 replan 评估"，**不阻断下游**；
- **真 FAILED**：produces 值不存在 → 消费它的下游契约不满足 → 调度器**自然标记 SKIPPED、不派发**（不是额外 if 判断）；
- 只阻断依赖它的子图，兄弟分支照跑；
- 聚合时**明确标注哪部分没完成、为什么**，绝不静默裁剪。

### Q7 崩溃恢复 + 幂等 + 副作用？

**四张表**（PostgreSQL）：执行计划表、DAG节点图表、节点输出表、工具调用表

**恢复顺序**：SUCCESS 复用缓存 → PENDING 且上游全成功才重新入队 → **RUNNING 不能无脑重跑**（先查 tool_calls 有没有发出有副作用的调用）→ FAILED/SKIPPED 维持原状。

**幂等核心**：幂等键放在哪不重要，**谁来检查它才关键**。下游老系统不认幂等键 → 检查逻辑必须在**自己控制的编排层**做：调用前先持久化"我要调用，幂等键 K"，重试前先查自己的记录，已标记就不再发起。

**结果未知**（调用发出但网络断了）：下游支持查询 → 先"**结果核验**"再决定；不支持 → 标记**第三态 UNKNOWN**，**不自动重试**（重试的下行风险 > 不成功的风险），显式呈现给用户人工核实。

**工具接入时强制声明三属性**：有副作用、可以查询章台、不可查询状态

### Q8 用户中途取消？

"取消 = 停止调度新任务 + 对在跑的按副作用分类处理"，**不是强杀**：

| 节点状态 | 处理 |
|---|---|
| PENDING（还没跑） | 标 CANCELLED，零风险 |
| RUNNING、无副作用 | 直接打断，停止等结果 |
| RUNNING、**有副作用** | **不强行打断**——让它自然跑完，再走核验/转人工逻辑 |
| SUCCESS（已跑完） | 结果保留，不受影响 |

**本质**：取消控制的是"要不要开始新的工作"，不是"强行终止正在发生的、有真实后果的操作"——和崩溃恢复、网络中断重试是**同一个框架**在三种场景下的应用。

### Q9 降级链路（四条）

| 触发 | 降级动作 |
|---|---|
| 计划生成失败 | 先 **validation-feedback 重试一次**（把校验报错喂回让 LLM 自修），再降级单 Agent（轻量分类器选最贴合的域，不做任务拆解）|
| 专家 Agent 失败 | 阻断下游（SKIPPED）+ 聚合时标注部分结果 |
| 跨 Agent 矛盾 | 仲裁检测 → 可收敛的事实冲突走局部 replan；价值权衡原样呈现给用户 |
| 成本超限 | 预算熔断（调度边界检查），未派发标 SKIPPED，回复说明 |

**加分洞察（⚪）**：触发原因不同，但退化终点收敛到少数几条成熟路径——不是每种失败发明一个独一无二的出口，这本身就是好设计。

## 二、模型选型

**结论**：规划（LeadAgent）和 replan 都用**中档、强 tool-calling 的模型（Sonnet 档）**，不用旗舰也不用最小档。

**三段论**：

1. **任务性质**：规划是"结构化任务路由 + 浅层依赖推理"，不是深度创造性推理；
2. **排除旗舰**：规划在关键路径第一步，每个请求都走。旗舰拖慢首次响应 + 抬高每个请求的固定成本。预算该留给真正需要深度推理的环节（专家 Agent 的复杂选型权衡、长文档理解）。**类比**：最贵的精密仪器不该用在"分拣传送带决定往哪送"这一步，应留在精加工环节；
3. **排除最小档**：多步依赖推理不可靠（漏依赖/假依赖）+ 歧义处理不足（结构合法但语义跑偏，到执行才暴露）——两类错误的代价都比"规划阶段多花一点钱"高得多。

**被追问 1：规划出错是不是模型不够强？** → 不是。是"计划时无法预见执行结果"——所有规划系统的固有局限，不是档次问题；出错靠局部 replan 兜底，不靠升级模型。

**被追问 2：replan 时要不要升级强模型？** → 不升级。replan 输入范围更窄、问题更具体（已经知道哪里出问题），推理需求**不高于**初始规划；升级 = 成本叠加，很快触发预算熔断。真正能力不足的情况（歧义）该走"转人工澄清"。可选（⚪）：最后一次 replan 用强模型"最后一搏"，逻辑自洽但只是锦上添花。

**被追问 3（⚪ 加分）**：按复杂度分层路由——普通请求中档规划，判断为异常复杂时动态升级重规划。与"预算分级配置"是同一套工程哲学：不为简单请求多花钱。

## 三、深挖弹药库

### 3.1 LeadAgent 怎么生成计划

- **输入不只是用户的话**，还有**专家能力清单（capability manifest）**：每个专家 Agent 声明"我是谁、能做什么、需要什么输入、会产出什么"。LeadAgent 只能在清单内分配 → 这是服务端引用校验的前提 → 新增 Agent 只注册一条描述，不改核心逻辑。
- **分解**：子目标识别 + 路由到最贴合的专家——"意图分解 + 路由"，是 LLM 擅长的。
- **依赖判断的唯一标准**："任务 B 需要的输入，是计划阶段就已知的（请求参数/常量），还是必须等任务 A 真正跑完才知道？" 已知 → 可并行；未知 → 串行。
- **方案 B（produces/consumes）> 方案 A（LLM 直接声明边）**：
  - 方案 A 一句话带过：LLM 直接声明 `dependencies: [{from, to}]` 容易漏连/瞎连，正确性全靠 LLM 自觉；
  - 方案 B：LLM 只描述"我产出什么、需要什么"，服务端匹配**自动推导边**——把易错的"连边"换成贴近自然语言的"I/O 描述"，更不容易漏；
  - **换来方案 A 没有的校验**：数据流完整性检查——某任务 `consumes` 的占位符没人 `produces`、也不在用户请求里 → 缺失依赖/幻觉输入，执行前拒绝。
  - 记忆锚点 JSON：
    ```json
    {"tasks":[
      {"id":"A","agent":"selection","goal":"筛满足功耗的候选","produces":["selected_part_number"]},
      {"id":"B","agent":"test","goal":"列出该型号测试项","consumes":["selected_part_number"]},
      {"id":"C","agent":"project","goal":"查项目进度","produces":[],"consumes":[]}
    ]}
    ```
    服务端发现 B 消费的恰好是 A 产出的 → 推导出 A→B；C 无消费无生产 → 独立，可并行。
- **为什么"声明式"**：LeadAgent 只答"谁需要谁的产出"，从不答"先跑谁、等多久、怎么并行"——那是拓扑排序，一个确定性算法，交给服务端。**LLM 只声明关系，调度逻辑完全在 LLM 能力之外、由代码保证正确**。
- **失败模式表**：

  | 失败模式 | 描述 | 兜底 |
  |---|---|---|
  | 漏依赖 | 该串行误判为可并行 | 数据流检查发现无 producer → 拒绝/重规划 |
  | 假依赖 | 过度保守，该并行的串起来 | 效率问题非正确性；作为指标（不必要边比例）观测优化 prompt |
  | 过度拆分 | 节点过多，计划失控 | 节点数/拆解深度上限 |
  | 循环依赖 | A 依赖 B，B 又依赖 A | 环检测拒绝 |

### 3.2 replan 机制（局部重规划）

- **触发信号（两类，确定性优先，不靠 LLM 主观判断）**：
  1. **契约不匹配**：`produces` 声明"单值"，实际返回 3 个候选 → 形状不对，**代码直接判断**，不需要语义理解；
  2. **自报低置信度**——关键设计：**不是每个 Agent 都强制吐置信度分数**（LLM 自报分数校准差，会被问穿）。按 Agent 类型复用已有信号：
     - 检索型 Agent：复用亮点3 自纠错闭环已有的融合得分/命中数（本来就是确定性算出来的终态）；
     - 确定性查询型 Agent：靠契约不匹配兜底；
     - 纯 LLM 判断的关键节点：用**自洽性检测**（跑 2~3 次看结果是否一致），不一致本身就是低置信度的证据。代价高，只用于高风险关键节点。
- **局部范围**：只暂停"消费了 A 的输出"的下游子图，无关分支照跑；重规划时给 LeadAgent **收窄后的上下文**（原始目标 + A 的实际结果 + 待消费目标），产出修订子计划，走同样校验流程后拼回 DAG。
- **修订策略（预先设计，不是让 LLM 天马行空）**：
  - **扇出**：多个候选同样有效 → 拆成多个下游各查一次再聚合；
  - **转人工澄清**：查不到/无法收敛 → 把选择权交还用户（"3 个型号都满足，你选哪个？"）；
  - **补充判据收敛**：有次级筛选条件（"优先库存多的"）→ 加判据重算收敛成 1 个。
  - 默认规则：多有效候选走**扇出**（信息没丢）；无候选走**转人工**（不能瞎猜）。
- **终止保证**：重规划有限预算（N 次封顶）+ **范围单调收缩**（每次只处理受影响子图，只缩不扩）+ 成本与熔断同一预算池。
- **例子**：`A(selection, produces: selected_part_number[单值]) → B(test)`；A 跑完返回 3 个候选 → 契约不匹配，标记 AMBIGUOUS，B 暂停 → 扇出为 B1/B2/B3。

### 3.3 降级链路细节

- **计划失败先分三类**：结构性（schema 不过）/ 语义性（环/数据流/契约不满足）/ 调用性（LLM 调用超时报错）。结构/语义失败**先做一次 validation-feedback 重试**——把校验报错原样喂回给 LLM 让它自修，预算用尽才真正降级，不能一点小错就退化。
- **降级动作**：轻量分类器判断这句话最贴近哪个专家域 → 单 Agent 直接执行，不做任务拆解；**必须告知用户**"本次未生成完整执行计划，以下是简化处理的回答"。
- **abstention ≠ 失败**（重复强调）：abstention 是正常终态，只触发 replan 评估，不阻断下游；FAILED 专指工具/LLM 调用异常、超时且重试耗尽。
- **仲裁检测**：受影响任务都到终态后、聚合前触发。第一层**确定性规则**（硬编码冲突模式：选型推荐型号 ∈ 测试 Agent 的 known_issues 列表；交期 > 项目截止日）；第二层轻量仲裁 LLM **兜底**规则没覆盖的类型。→ 冲突可收敛（加约束能重算）走局部 replan；本质是价值权衡（便宜慢 vs 贵快）→ 原样呈现给用户，不替用户做业务判断。
- **预算熔断**：单请求累计 token/成本，规划 + 专家执行 + replan + 仲裁**共享同一预算池**；检查点在"是否派发下一个任务 / 是否允许再来一轮 replan"的调度边界，**不中途硬掐**（中途打断已花的 token 拿不到结果）；单次调用用 **max_tokens 硬上限**做前置约束——两者分工：前者管"还能不能再来一轮"，后者管"单次不能无限超支"。预算可按请求复杂度分级配置（⚪）。

### 3.4 缓存设计（Q19/Q20）

- **Plan 层不缓存**：计划含从请求提取的具体参数（功耗 ≤ 2W、截止日期等），参数不同计划就不同；按相似度复用旧计划 = 执行上次的参数 + **无任何报错的静默错误**，比慢更危险。
- **节点结果层缓存**：`goal + consumes 具体输入值` 完全一致才命中，跨请求复用（checkpoint 的自然延伸）。
- **四象限**（时效性 × 归属性）：

  | | 时效性高 | 时效性低 |
  |---|---|---|
  | 用户私有 | none 不缓存 | scope: user，短 TTL |
  | 公共数据 | scope: session 用完即丢 | scope: global，长 TTL |

  例子："查项目进度"→ 实时+私有 → 不缓存；"查型号规格"→ 静态+公共 → global 长期缓存跨用户共享。
- **实现**：复用 node_outputs 表加 `cache_scope` + `user_id` 两列，查询按 scope 决定过滤条件——不引入额外存储。
- **与多租户隔离联动**（呼应亮点4）：global 缓存要过租户访问控制，不能让用户 A 查到用户 B 私有项目的缓存。

### 3.5 调度器并发模型

- 拓扑排序后，所有依赖已满足的节点组成同一"层"，层内并发：`asyncio.TaskGroup`（结构化并发，作用域内任一失败可取消兄弟任务）。
- **细节深挖点 1**：TaskGroup 是 Python 3.11+ 特性；更早版本用 `asyncio.gather` + 手动 cancel。**要能接住这一问**（一句话：部署环境 3.11+ 或说明替代方案）。
- **细节深挖点 2**：TaskGroup 不等于无限并发——还要套**信号量/并发池**限制同时跑的节点数，呼应亮点4（按资源分类限流）。
- **细节深挖点 3（抢跑保护）**：派发前检查所有 `consumes` 字段是否已有 SUCCESS 的 producer 输出——下游只在上游落库后才入队，跨层串行是"契约就绪检查"天然实现的，不是 sleep 等。

### 3.6 仲裁校验落地（Q15 提炼）

- **实体中心规则**（不是"Agent 对规则"）：规则挂在共享实体上（component/project），声明式 yaml：

  ```yaml
  entity: component
  rules:
    - id: known_issue_vs_recommendation
      condition:
        field_a: selection.recommended_part
        field_b: test.known_issues[*].part_number
        conflict_if: field_a IN field_b
      action: trigger_replan
    - id: delivery_vs_deadline
      condition:
        field_a: selection.delivery_date
        field_b: project.deadline
        conflict_if: field_a > field_b
      action: present_to_user
  ```

- **为什么实体中心 > Agent 对规则**：加第 4 个 Agent 时，Agent 对规则要补 O(n) 条；实体中心只需新 Agent 声明"我输出 component 的哪几个字段"，已有规则自动生效——**O(1) 扩展**。
- **谁触发**：编排层聚合前统一触发，是独立校验步骤，不是某个 Agent 顺带跑。
- **何时触发**：一条规则涉及的所有字段的贡献 Agent 都到达终态即可检查，不阻塞无关分支。
- **action 在规则里声明**（trigger_replan / present_to_user），不运行时临时判断。

### 3.7 环检测算法（Q16）

Kahn's 算法（拓扑排序的 BFS 版）：计算入度 → 入度 0 的节点入队 → 出队时把邻居入度 -1、归零再入队 → 最后处理节点数 < 总数 = 存在环。

**为什么不能只说"BFS 判重"**：有向图里"已访问"可能只是汇聚点（A→C、B→C），不是环，判断不了。Kahn's 的入度机制才是有向图环检测的标准做法。

**加分点**：调度本来就需要拓扑序，Kahn's 跑完**环检测和拓扑序同时拿到**，O(V+E)，不用跑两次。

### 3.8 特殊场景：一成功一失败的上游（Q18）

节点两个上游，一个 SUCCESS 一个 FAILED → **直接 SKIPPED**，不是"用已有的那个上游结果凑合跑"。

**为什么不需要额外写判断逻辑**：节点 `consumes` 声明了两个字段，调度器派发前检查所有字段都有有效 producer 输出——FAILED 节点的 produces 值在 node_outputs 里根本没有记录，匹配时找不到 → SKIP 是 produces/consumes 机制的自然结果。**契约是全有或全无。**

## 四、增强

### 4.1 评估口径：60s → 35s（↓42%）怎么来的

面试官必问"数字怎么测的"，准备自洽口径（不能只有数字没有方法）：

- **评测方式**：从线上真实请求抽样 + 构造典型跨部门复合任务集（如"选型号 + 查项目进度 + 列测试项"这类 N 条），记录端到端耗时；
- **对比基线**：改造前的实现（串行/单 Agent 顺序执行全部子任务）；
- **统计口径**：说清楚是 P50 还是 P95——和简历数字对齐，被追问能对上；
- **加速分解**：①并行化——第一层 {A, C} 并行、第二层 {B} 串行，砍掉了串行等待；②局部 replan——避免了整个计划推倒重来。
- ⚠️ **别和亮点4 的数字混**：亮点4 的 P95 15s→5s 是**多用户并发排队**维度，亮点1 的 60s→35s 是**单请求执行**维度——一个管并行调度，一个管资源治理。

### 4.2 恢复的并发安全（深挖点）

"崩溃恢复"如果部署多进程/多实例，**两个 worker 同时恢复会重复执行**。被问到这个：

- 答案：恢复流程要保证**单实例执行**——用分布式锁（PostgreSQL advisory lock / Redis SETNX）只让一个 worker 执行恢复和调度；或调度器设计为单 worker（DDH 内部场景可接受）。
- 这一步把"checkpoint 持久化"从单机健壮性提升到分布式健壮性，是深挖时的关键一问。

### 4.3 四亮点联动主线（被问"这不是一个系统吧"时的回答）

一句话主线：**亮点1 是骨架，亮点2/3 是肉，亮点4 是运行环境。**

- 亮点1 的 DAG 节点 = 专家 Agent 内部跑的就是亮点2 的多模态 RAG（选型 Agent 查图表类问题走视觉检索）+ 亮点3 的结构化查询（项目/测试 Agent 走 SQL 模板）；
- 亮点2 的"分数不足降级文本双路"和亮点3 的 abstention 信号，正好是亮点1 replan 的"低置信度触发信号"——**三个亮点在质量信号上闭环**；
- 亮点4 的并发上限按"模型调用/DB/下游服务"分类，DAG 调度器的并发池就是消费这些资源的主体；
- 面试时能画这张联动图，比单独讲任何一点都加分。

### 4.4 讲法建议（防"包装感"——对你尤其重要）

- **颗粒度对齐**：简历一句话 → 面试先讲"设计选择 + 理由"（30 秒），被追问才展开"表结构/算法/伪代码"（弹药库）。**深度是挤出来的，不是倒出来的**——主动一次性倒完所有深度，反而像背稿。
- **第一人称 + 踩坑**：多用"我们最初想……后来发现……所以改成……"（下文速查表里标"踩过坑"的条目就是现成素材，背下来当真实感来源）。
- **数字口径一致**：60s→35s（亮点1）、35%→73%（亮点2）、62%→91%（亮点3）、15s→5s（亮点4）——四个数字分别对应哪条、什么口径，考前写在一张纸上过一遍。
- **诚实收口**：被追问到没做过的细节时，用"当时我们还讨论过……后来因为 XX 没做"收口，比硬编一个细节安全得多。
