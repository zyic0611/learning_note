# DDH 记忆系统设计(面试用)

> 定位:面试回答口径。重心放在"从约束推导出设计"的推理链,落地说"设计 + 部分落地/原型",不夸大实现范围。

---

## 一、先讲约束:为什么这个项目的记忆系统不是普通聊天记忆

面试答法的核心开头:好的记忆设计都是从**业务约束**推出来的,不是抄别人的。DDH 的约束有五条:

1. **群聊而非 1v1**:飞书群是多用户、多话题交错的消息流。用户 A 问选型、用户 B 在聊排期,消息互相穿插。"按群记记忆"会把无关信息混进上下文,还造成用户间偏好串扰。
2. **多域切换**:同一个群里器件选型 / 项目管理 / 测试验证交替出现,记忆必须按话题(topic)切分,而不是按时间线性累积。
3. **高频引用消解**:工程师常问"和刚才那颗比怎么样""你上次查的那份 datasheet"——需要线程内的实体锚点(型号、参数)。
4. **跨周时间跨度**:选型 → 验证 → 量产跟踪横跨数周,会话窗口关闭当天就丢,必须有小粒度的长期记忆。
5. **百余人 × 高频消息**:记忆写入/召回都要花钱花时间,必须有过滤和批处理,否则成本和噪音双双爆炸。

这五条直接决定了四层结构:每条约束映射到一层。

---

## 二、四层架构总览

```
┌─────────────────────────────────────────────────────────┐
│ L3 知识层(边界声明:不是记忆)                              │
│    器件结构化库(PG)+ 视觉库(ColQwen2 向量 + ANN/MaxSim)   │
│    全局、静态、只读优先;记忆是动态、个体、易变 —— 分开管    │
├─────────────────────────────────────────────────────────┤
│ L2 长期记忆(跨会话)      PostgreSQL + pgvector            │
│    Episodic 经历记忆(历史 thread 摘要,向量化)              │
│    Semantic 语义记忆(事实/偏好条目, JSONB + 向量双存)      │
│    三层 scope: user / group / global                      │
├─────────────────────────────────────────────────────────┤
│ L1 会话记忆(线程内)      PG(线程元数据)+ Redis(热上下文)   │
│    单元 = topic 线程;压缩摘要 + 锚点实体集                 │
│    滑动 TTL(如 30 分钟沉寂后转冷)                          │
├─────────────────────────────────────────────────────────┤
│ L0 工作记忆(Agent 执行态)  Redis, 任务级 TTL               │
│    LeadAgent 的 DAG 节点状态、子任务中间产物、Schema 校验结果 │
└─────────────────────────────────────────────────────────┘
```

## 三、分层详解

### L0 工作记忆(执行态)

- **职责**:Multi-Agent 执行中的共享状态——LeadAgent 规划出的 DAG(pending/running/done/failed)、各专家 Agent 的中间产物(候选器件列表、归一化后的参数、查询计划)、Schema 校验通过的计划 JSON。
- **存储**:Redis,Hash 结构以 `task_id` 为 key,任务级 TTL(任务时长 + 缓冲,聚合完成后清理)。
- **面试点**:这层回答"为什么专家 Agent 能无状态"。专家 Agent 只负责执行,状态全部上移到底座——这是编排架构能并行、能重试、能水平扩的前提。**记忆系统与 Multi-Agent 架构在这里咬合**,面试时主动点出这个闭环。

### L1 会话记忆(线程内)

- **单元是 topic 线程,不是群**。入场先做话题归属:对飞书消息做轻量分类(规则 + LLM 小模型),归属到当前活跃线程或开新线程。
- **每个线程维护两样东西**:
  - digest(压缩摘要):超过窗口阈值(如 8k token)触发 rolling summarization,而不是简单截断——截断会丢型号这种关键锚点,摘要保语义;
  - anchor 实体集:对话中出现过的器件型号、关键参数、议题,额外用白名单保真,服务于"刚才那颗"这类引用消解。
- **存储**:线程元数据(thread_id、参与用户、话题标签、时间窗)存 PG;热态上下文放 Redis 滑动 TTL。
- **面试点**:为什么压缩而不是截断。截断的失败模式是丢锚点、答非所问;压缩的失败模式是细节丢失,可被锚点白名单兜底。两个失败模式不对称,选不对称性更小的那个。

### L1 深挖:无限消息流里的会话切分(私聊场景)★★★

**问题**:私聊里 user → bot 是唯一且永不结束的消息流(没有"开新窗口"的说法),如何在流里识别"新会话"?

**重新定义**:短期记忆的单元不是物理会话,而是**话题线程**。于是"检测新会话"= "判定新消息归属哪个线程"(含"新建线程"选项)。私聊与群聊统一为同一抽象:两者都是无限消息流,群聊只多一个 user 维度,一套机制两个频道复用。

**归属判定,三层信号从强到弱**:
1. **强信号(零成本零误判)**:飞书引用回复 → 继承被引用消息的 thread_id(平台协议级信号);显式指令 `/new`、"换个问题" → 开新线程。
2. **中信号(便宜)**:时间间隔——距线程最后消息 > T_idle(约 30min)即软关闭候选;新消息默认只与最近活跃线程比较。
3. **弱信号(花钱,最后裁决)**:embedding 相似度三段论——高于高阈值并入、低于低阈值新建、**落在模糊带交给小模型 LLM 裁决(继续前文/新话题/引用前文)**。只有模糊带花 LLM 的钱(通常仅占 1~2 成 case)。

**线程生命周期:边界是软的**

```
新建 → 活跃 → 软关闭(idle)→ 复活 → 归档(closed)
              ↑______________________|
```

- 软关闭:gap > T_idle,摘要与锚点实体冻结但保留;
- 复活:后续"继续刚才那颗芯片"经锚点命中重新挂 active;
- 归档:超过一天无复活,摘要异步进入 L2 长期记忆提取管线,热上下文清理。
- 核心理由:硬切的失败模式是"用户说接着刚才的,助手失忆"——客服助手最常见差评;软边界 + 锚点保留把误切代价压到近零。

**核心取舍:误切 vs 漏切,漏切更贵**。误切=上下文缺失,可被引用复活兜底;漏切=上下文噪音,会把上一话题结论带进新话题回答,模型被无关上下文带偏。RAG 场景噪音比缺失更危险 → **宁可多切,不可误并**:合并走保守阈值,切分走激进阈值。

**阈值从哪来**:T_idle 取历史消息间隔分布的分位点(如 P90)再人工回放校准;相似度阈值在人工标注的话题边界集上离线调 precision/recall;线上看下游代理指标(引用复活成功率)。

**追问预案**:
- Q:为什么模糊带才用 LLM?→ 每条都判是每轮一次 LLM 调用的固定税;强信号已覆盖大半;模糊带恰是 embedding 最不可靠的区间,正好把 LLM 用在刀刃上。
- Q:怎么评估切分质量?→ 人工标注真实流的话题边界算切分准确率 + 引用复活成功率("继续刚才的"答对率)。

### L2 长期记忆(跨会话)

- **两类记忆**:
  - **Episodic(经历记忆)**:历史线程结束后生成的"事件记录"——谁、何时、讨论了什么、结论是什么。向量化存 pgvector,服务"上次我们讨论过 X"类召回。
  - **Semantic(语义/偏好记忆)**:抽取的事实条目——"张工负责域控制器 XX 项目""部门常用连接器是 JST/Amphenol""B 项目的 PMU 需求是 3A"——JSONB(结构化,可过滤)+ 向量(可召回)双存。
- **三层 scope(群聊场景的关键设计)**:
  - `user`:个人偏好、个人项目——**召回时按提问者过滤,用户 A 的记忆绝不进用户 B 的上下文**;
  - `group`:群内共享的项目事实、部门约定;
  - `global`:通用知识(一般归入知识层,记忆里只留指针)。

- **写入管线(全部异步,thread 关闭或沉寂 N 小时后触发)**:
  1. LLM 记忆提取 prompt → 候选条目 {类型、主体、内容、重要性、有效期};
  2. 重要性阈值过滤(一条垃圾记忆的代价 > 十条无用文档——它的位置在 system prompt 里,是每轮都花钱的);
  3. 与已有记忆做向量相似度去重(> 0.9 走更新而非新增);
  4. 冲突处理:同一事实多条 → 新胜旧,旧条目降权软删,保留审计痕迹;
  5. 写入。

- **读取管线(同步,对话开场 / 话题切换时)**:
  - 多路召回:提问者的 semantic 条目 + 话题相关 episodic(top-k)+ 时间衰减重排(如半衰期 30 天);
  - 注入方式:作为 system prompt 的"用户与项目上下文"独立段——**不和知识库检索结果混在一起**,两者来源、置信度、作用域都不同。

- **面试点**:
  - 为什么不同步写入?对话有延迟预算(编排省下的 35s 不能还给记忆链路),提取是离线 LLM 调用,失败可重试不影响在线上。
  - 为什么记忆和知识库分开?更新频率不同(知识库跟着 datasheet 版本走,记忆跟着人走)、作用域不同(全局 vs 个体)、错误代价不同(记忆错一条直接污染每次回答)。

### L3 知识层(边界声明)

严格说不是记忆,是全局知识(结构化器件库 + 视觉索引),面试时要主动划这条线,防止面试官把"记忆"和"RAG 知识库"混为一谈。两者的交互是一个加分点:**长期记忆反哺检索**——用户常用某品牌 → 提升该品牌结果的排序权重,即记忆作为检索的偏好先验。

## 四、技术选型表(贴合现有栈,不引入新组件)

| 层 | 存储 | 关键操作 | 生命周期 | 访问形式 |
|---|---|---|---|---|
| 工作记忆 | Redis | task_id Hash | 任务级 TTL | 编排底座内部 |
| 会话记忆 | PG + Redis | 话题归属、滚动摘要 | 分钟 ~ 小时 | thread 内 |
| 长期记忆 | PG + pgvector | 异步提取、去重、衰减召回 | 天 ~ 月,软删 | 对话开场 / 话题切换 |
| 知识 | PG + pgvector + ANN/MaxSim | 已有 RAG 管线 | 静态(随版本更新) | 检索时 |

**MCP 形态**:记忆能力包装成一个 MCP server,暴露 `memory.search / memory.record / memory.forget` 三个工具,三个子 Agent(测试 / 项目 / 硬件选型)统一经 MCP 访问,权限按 `user_id + scope` 过滤。子 Agent 即插即用,不感知底层存储。

## 五、评估方法(硬问题,要能答)

1. **贡献度评估**:构造历史问题集,做 A/B——带记忆 vs 不带记忆,LLM-judge 打分,看有没有增益(防线:记忆必须证明自己有用,否则就是纯成本)。
2. **锚点保持率**:摘要压缩后,关键型号/参数的保留率(这条直接量化"压缩 vs 截断"的设计决策)。
3. **写入精确率**:人工抽查提取条目,错一条就删一条并回灌 case 给提取 prompt。
4. **成本卡点**:召回 top-k 和注入 token 预算设上限。
- 诚实口径:长尾效果无法全自动化,靠部门内测 + 人工 review——4 人团队的现实选择,不丢分。

## 六、口播模板(约 60 秒)

> 我们的记忆系统按生命周期分了四层,每一层都是被业务约束逼出来的。
>
> 最底层是工作记忆,Multi-Agent 执行时的任务状态——LeadAgent 规划出的 DAG、各专家 Agent 的中间产物,放 Redis 带任务级 TTL。这层的价值是让专家 Agent 保持无状态,重试、并行、水平扩展才好做。
>
> 往上是会话记忆,单元是群里的一个话题线程,不是整个群——因为飞书群是多用户多话题交错的,我们会先做话题归属,每个线程维护滚动摘要和锚点实体。这里一个关键决策是压缩而不是截断:截断会丢型号这种锚点,压缩保语义,再用实体白名单兜底。
>
> 再往上是长期记忆,跨会话的,分经历记忆和偏好事实两类,异步从关闭的线程里提取,过重要性过滤和向量去重,按 user/group/global 三层 scope 隔离存储,召回时按提问用户过滤、时间衰减重排。记忆和知识库是分开的,知识库跟着资料版本走,记忆跟着人走。
>
> 整套记忆能力包装成 MCP server,三个子 Agent 统一调用。设计上最关键的两个决定:一是按话题而不是按群记,二是按用户隔离、和知识库划清边界。

## 七、追问链预案

**Q1:为什么不把所有历史都塞进上下文?现在长上下文不是很能打吗?**
→ 三个理由:成本(每轮全量重算,百人 × 高频消息下不可控);精度(长上下文存在 lost-in-the-middle,相关段被稀释后召回质量反而下降);隔离(群聊场景无法区分记忆归属,串味)。分层本质是"按生命周期和访问模式,把状态放进对它有意义的介质"。

**Q2:记忆冲突和遗忘怎么处理?**
→ 写回侧:同一事实向量相似度超过阈值走更新,新胜旧,旧条目降权软删留审计。召回侧:重要性 × 时间衰减打分,长期不衰减的条目自然沉底;提供显式 `memory.forget`。两条腿一起走,优先保证召回精度,再谈存量。

**Q3:群聊里用户 A 提问,会不会把用户 B 的偏好带进来?**
→ 不会,这是三层 scope 的动机:semantic 按 user_id 维度存,召回按提问者过滤;episodic 按线程归属,线程记录参与用户列表;只有群内共享的项目事实在 group scope。跨用户污染在这里是设计上被排除的,不是靠 prompt 祈祷。

**Q4:为什么写入异步、读同步?**
→ 延迟预算:一个对话回合的在线链路已经很紧(多 Agent 编排并行才压到 35s),记忆提取是一场额外 LLM 调用,必须挪出在线路径。异步还带来好处:批处理摊薄成本、失败可重试不脏在线。

**Q5:记忆写回的成本怎么控?**
→ 三重:触发条件(只对关闭线程、且含高重要性候选的才跑提取)、批处理(离线批量抽取,非逐条实时)、去重防堆积(相似条目更新而非新增,控制存量增长)。

**Q6(可能的冷门追问):记忆系统和多模态 RAG 是什么关系?**
→ 责任不同:RAG 管"知识在哪",记忆管"和谁有关、聊到哪了"。交集在偏好先验——长期记忆里"用户常选某品牌"这类事实可以调高检索排序权重。回答时用一个具体例子闭环:怎么把"张工的项目域控制器需求 3A"这件事,变成检索 PMU 器件时的排序信号。

## 八、诚实表述策略

- 话术结构:**"设计上我们这么做……实际落地重点先做了 L0/L1,L2 长期记忆做完了方案设计和原型验证,是在后续迭代计划里。"** —— 关键是把每个设计决策的"为什么"讲扎实,AI 应用岗的面试官听的是推理,不是验收单。
- 任何一层被深追实现细节时,承认工程现状 + 补一句"这个坑我在设计方案时怎么考虑的"(即本文档内容),比现编一个精细实现更安全;编的实现经不起第三句追问。
- 如果面试官问"为什么没做完",标准答案:**优先级**——百人部门的实际痛点是检索准确率和任务时延,记忆的收益是渐进抬升的,排在稳线上线和数据效果之后。
