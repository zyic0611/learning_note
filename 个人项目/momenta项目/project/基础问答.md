# 基础问答（框架选型与工程判断）

这类问题不属于某一个具体亮点，而是面试官对整个项目底层技术选型/工程判断力的追问，容易在自我介绍之后作为第一轮追问出现。

**问答地图**：
- Q1 底层用的什么框架：Claude Agent SDK 提供了什么、自己封装了什么
- Q2 为什么不用 LangGraph/LangChain
- Q3 怎么检测（观测/验证）整条 Agent 链路
- Q4 用了哪些模型、为什么这么选型：哪些节点用哪些模型、哪些可以本地部署
- Q5 这个 Agent 有必要部署多实例吗
- Q6 具体到 LLM 节点：多人同时用是部署多个 LLM 节点吗

---

## Q1：底层用的是什么框架？是基于 Claude Agent SDK 实现的吗？

**标准答案**（口播约 50 秒）：

> 底层执行引擎用的是 Claude Agent SDK，它提供的是基础的 agent loop（模型调用循环）、MCP client 接入能力、内置工具执行的脚手架和权限确认的 hooks 机制——我们对接公司内网的 MCP server（streamable HTTP）就是走这层能力连上去的。
>
> 但整个系统真正的工程量在于我们在这之上自研的编排层，SDK 本身并不提供：LeadAgent 的 DAG 规划与四层校验（结构校验→能力权限校验→数据流唯一产出校验→拓扑排序构图）、Skill 系统（两级层级、元数据向量匹配、误选安全网、版本管理）、按资源类型分类的并发治理调度器（分类限流、公平轮转、重试降权老化、三层嵌套超时）、多模态 RAG 的检索融合链路（三路并行、MaxSim 精排、RRF 融合、降级机制）——这些都是根据硬件研发这个具体场景从零设计的。

**要点**：
- SDK 提供的部分（老实认）：agent loop、MCP client 接入、工具执行脚手架、权限 hooks
- 自研的部分（真正的工程亮点，要具体）：LeadAgent DAG 四层校验、Skill 系统、并发资源治理、多模态 RAG 全链路
- 别用"大部分自己封装，只用了SDK一些东西"这种含糊说法——精确说清楚"SDK 给的是底层胶水层，自研的是编排层"更有技术深度

**易错点**：
- 含糊回答"用得少"会被追问"那具体自己写了什么"打穿，一定要能精确列出自研模块
- 不要低估或回避 SDK 的作用——诚实说清楚 SDK 提供了什么，比回避更显得对系统边界有清晰认知

## Q2：为什么不用 LangGraph/LangChain？

**标准答案**（口播约 50 秒）：

> 不管选哪个框架，系统里真正的技术含量——Skill 匹配安全网、DAG 四层校验、资源治理调度器——这些领域规则任何通用框架都不会替你写，都得自己搭。所以框架选型比的不是"谁帮你把核心逻辑写好了"，而是"谁把底层的模型调用胶水层做得更贴合、更省心"。
>
> Claude Agent SDK 是 Anthropic 官方维护的，工具调用格式、MCP 接入、hooks 权限机制都是原生适配 Claude 模型的，模型侧一有新能力基本同步跟上；LangChain/LangGraph 是多供应商抽象层，为了兼容不同模型的接口差异，中间有一层通用化转译，功能跟进往往有滞后、抽象也更重。
>
> 而且我们的 DAG 需要特定的四层校验和节点状态机（含 abstained/blocked/skipped 这种业务语义状态），如果硬套进 LangGraph 的通用图抽象里，还要多一层"把自己的语义翻译成 LangGraph 图概念"的适配成本，不如直接在更底层的 SDK 上按自己的语义设计执行引擎，链路更短，调试也更直接。

**要点**：
- 核心论证：领域核心逻辑不管选哪个框架都得自研，所以比的是底层胶水层和模型的贴合度、抽象层数，不是"谁帮你写了编排逻辑"
- Claude Agent SDK 优势：官方维护、原生适配模型新能力，无需等第三方框架跟进
- LangGraph 通用图抽象和自定义 DAG 语义（四层校验、abstained/blocked 状态）有错位，硬套会多一层翻译成本

**易错点**：
- 别把答案说成"LangChain 不好用"这种主观吐槽，要落到抽象层数、和模型贴合度、领域逻辑归属这几个具体维度
- 避免暗示"用了SDK就什么都不用做"——问题1 已经说清楚自研范围，这里重点是选型逻辑不是重复自研内容

## Q3：怎么检测（观测/验证）整条 Agent 链路？

**标准答案**（口播约 50 秒）：

> 分两层：运行时怎么看得见、效果怎么测得准。
>
> 运行时可观测性上，每个 DAG 节点都维护显式状态机（pending→ready→running→{succeeded/failed/abstained/blocked/skipped}），每次工具调用信息落 PG、可复用结果缓存进 Redis——任何一次请求的完整执行链路，包括每个节点最后落到什么状态、调用了什么工具、参数是什么，都可回放可追溯，出问题能直接定位到具体哪个节点、哪次调用。
>
> 效果验证上，延续项目里统一的方法论：评测集用 6:3:1 构建（60% 线上真实流量、30% 自建、10% AI 增强），关键机制上线前做消融测试和负样本集回归，验证通过后走灰度上线、和线上真实流量做对照，而不是直接全量替换。

**要点**：
- 两层拆分：运行时"看得见"（节点状态机+全链路留痕）+ 效果"测得准"（6:3:1 评测集+消融+灰度）
- 节点状态机是结构化观测手段，不是简单的日志堆砌
- 效果验证方法论和其他亮点（Skill、资源治理、RAG）保持一致，是项目统一的工程规范

**易错点**：
- 只说"有日志"太单薄，一定要点出节点状态机这个结构化观测手段
- 别漏掉效果验证这一层——面试官问"怎么检测"往往既想听可观测性，也想听怎么验证做得对不对

## Q4：用了哪些模型？为什么这么选型？哪些节点用哪些模型？哪些可以本地部署？

**标准答案**（口播约 60 秒）：

> 项目里的模型分两类，选型逻辑完全不同。
>
> 第一类是负责"智能"的推理型 LLM——LeadAgent 结构化规划、专家 Agent 内部的判断节点、仲裁层冲突检测、多路检索融合后的最终答案生成，这几个节点复用同一个主力纯文本 LLM。这几处的共同点是：需要强推理、强指令遵循、输出要对用户最终负责，所以选能力最强的闭源模型走 API 调用，不追求本地部署——这类顶尖推理模型自己训练或本地化部署门槛极高，不划算也不现实。
>
> 第二类是负责"表示"和"翻译"的小模型，清一色本地部署的开源模型：知识库建库和检索阶段，文本向量用 BGE，图表页面的 Patch 级视觉向量用 ColQwen2；视觉候选命中后，裁剪出的图像区域交给一个多模态小模型做"图像→文字"翻译，不负责回答，只描述这个区域画的是什么。这几个节点选本地开源小模型，是因为任务本身很窄——生成向量、描述一张图，不需要通用推理能力，但调用量极大，建库阶段要给每页每个 Patch 都编码，检索翻译层每次命中视觉候选都要跑一次，如果都走 API 调用，成本和延迟都撑不住，本地部署的小模型刚好胜任这种"高频、任务单一"的活。
>
> 所以选型的核心逻辑是：按节点的任务性质分层——需要强推理、对最终结果负责的节点上最强模型、走 API；高频、职责单一的表示层和翻译层，上开源小模型、本地部署，省成本、控延迟。

**要点**：
- 两层划分：推理层（规划/判断/仲裁/生成答案）→ 主力 LLM，API 调用；表示/翻译层（BGE 文本向量、ColQwen2 视觉向量、多模态小模型图像翻译）→ 本地开源小模型
- 选型依据不是"哪个准"，而是"任务性质匹配"：强推理不可本地化替代 vs 窄任务+高频调用不需要强推理
- 本地部署的三个具体模型点名：BGE（文本 embedding）、ColQwen2（视觉多向量）、多模态小模型（图像翻译层）
- 强调"多模态模型不负责回答"——翻译和生成职责分离，主力 LLM 永远保持纯文本、不受视觉能力天花板约束

**易错点**：
- 别笼统说"都用的开源模型"或"都用的大模型"——这题就是考察分不分得清"每个节点为什么用这个模型"，笼统回答等于没答到点子上
- 别把 Skill 匹配用的元数据 embedding 漏掉——它和 BGE/ColQwen2 是同一类"表示层"模型，也是本地部署逻辑的延伸
- 如果追问"主力 LLM 具体型号"，如实说是 Claude 系列即可，不需要回避，但重点要落在"为什么这个节点必须用最强模型"而不是纠结型号本身

## Q5：这个 Agent 有必要部署多实例吗？

**标准答案**（口播约 55 秒）：

> 有必要，而且系统的架构本身就是按多实例设计的，不是"要不要"的问题，是"设计时就假定了会有多个"。
>
> 两个理由。第一是吞吐：百余名研发人员同时在飞书群聊里用，一个复杂请求内部会扇出几百个调用，单实例的连接数、内存、事件循环撑不住这个并发量级，必须水平扩展多个实例分摊流量。第二是可用性：专家 Agent 被设计成无状态的——所有执行状态（DAG 节点状态、专家 Agent 的输入输出、仲裁中间结果）都上移到 Redis 的工作记忆里，不留在进程内存里，这个设计本身就是为多实例存在的：一个实例挂了，换另一个实例从 Redis 里读状态接手，断点续跑，不用整个任务重来。如果只有单实例，这套"无状态可替换"的设计就没有意义了。
>
> 但多实例部署会给已有的资源治理机制提一个新要求：分类并发限流（LLM/DB/下游各自的上限计数）和用户级公平轮转，如果计数状态是进程内内存态，多个实例各算各的，总并发会超出真实上限——比如 LLM 上限 40 是按全局 RPM 600 推出来的，如果每个实例都各开 40，实例一多总并发直接击穿 rate limit。所以这些计数状态本身也得跟着无状态化的逻辑走，放到共享存储里做全局协调，这是"专家 Agent 无状态"这个设计原则在多实例场景下的必然延伸。

**要点**：
- 两个理由：吞吐（百人级并发扇出）+可用性（无状态设计本身就是为实例可替换、故障转移准备的）
- 关键论证方式：不是从零发明"要多实例"，而是从已有的"专家Agent无状态"设计倒推出"这本来就是为多实例准备的"
- 主动抛出追问点：多实例下分类限流计数器和公平轮转状态必须全局共享，不能是单实例内存态，否则会被击穿——这是原有设计原则的自然延伸，不是新发明的机制

**易错点**：
- 别只说"用户多所以要多实例"，要点出"无状态设计"这个已有证据，答案才有项目细节支撑，不是泛泛而谈的分布式系统常识
- 抛出"计数状态要全局共享"这个点时，措辞要克制——说成"这是设计原则的延伸，如果被问起会这样处理"，不要说成"我们已经实现了分布式限流器"这种没有文档依据的具体实现细节，避免被追问细节时穿帮

## Q6：具体到 LLM 节点，多人同时用 Agent，是部署多个 LLM 节点吗？

**标准答案**（口播约 55 秒）：

> 要分两种模型说，因为它们的部署形态完全不同。
>
> 主力推理 LLM（负责规划、判断、仲裁、生成答案的那个）是走 API 调用的闭源模型，对我们来说它不是"我们部署的东西"，是外部的一个黑盒服务。所以"给它部多个实例"这个问题本身不成立——多个用户同时用，本质就是我们的 Agent 服务并发地往外发多个 HTTP 请求，谁来处理这些请求、怎么扩容，是模型供应商那边的事，不是我们要解决的部署问题。我们唯一要管的是"自己这边发出去的并发量不能超过供应商给的配额"，这就是分类限流里 LLM 上限=40 的来源——按 RPM 反推出的并发上限，不是"实例数"，是"允许同时飞在外面的请求数"。
>
> 本地部署的那几个小模型——BGE 文本向量、ColQwen2 视觉向量、多模态图像翻译小模型——情况正好相反。这些是我们自己托管的推理服务，单个推理进程/单张卡的吞吐是有限的，百人并发一起检索、一起建库，单实例肯定扛不住，所以这几个才是真正需要水平扩展、部多个副本、前面挂负载均衡来分流的对象。
>
> 所以准确的说法是：主力 LLM 没有"我们部署的实例"这个概念，只有"并发配额"要管；本地小模型才是真正要考虑多实例部署的对象。这也是为什么分类限流要按资源类型分开设计的原因之一——LLM 侧限流管的是"对外配额"，本地模型侧要管的是"自己有几个副本能扛多少"。

**要点**：
- 核心区分：API 型 LLM（黑盒外部服务，不谈"部实例"，只谈"并发配额"）vs 本地开源小模型（自己托管，真正需要多副本+负载均衡）
- 呼应已有机制：LLM 并发上限=40 本质是"对外配额"而不是"实例数"，这是对之前 Little's Law 推导的再利用，不是新发明
- 本地模型才是"该不该多实例"这个问题真正成立的地方——因为只有自己托管的东西才有"实例"这个概念

**易错点**：
- 别把"LLM 节点"和"本地小模型"混为一谈笼统回答"都要多实例"——面试官问这个问题很可能就是想看你是否清楚哪些模型是自己托管、哪些是纯 API 消费
- 如果被继续追问"本地模型具体几个副本、怎么做负载均衡"，如实说这是合理的架构推断、没有具体数字，不要编造实例数或负载均衡组件名称
