## Q1：完整介绍一下"多模态 RAG"这个亮点——问题、解法、效果？

**标准答案**（口播约 55 秒）：

> 问题是硬件工程师查的 Datasheet 里，效率曲线、波形图这类图表信息，文字层根本没有——图注只有标题，没有数据点、趋势、拐点，传统文本 RAG 完全答不出这类问题，准确率只有 35%。
>
> 方案是三路并行检索，不做路由、全部跑：BM25 做型号精确匹配（向量会把"TPS54331"模糊掉，BM25 不会）、BGE 文本向量做语义召回、视觉向量专门处理图表。视觉这一路是核心创新：直接把 PDF 每页渲染成图像，用 ColQwen2 编码成 Patch 级多向量，不压缩成单一向量，保留空间信息；检索时先 ANN 粗排从海量页里捞出候选，再用 MaxSim 精排——拿 query 和页内每个 Patch 算相似度，取最大值当页面分，天然定位到"这页最相关的区域"，而不是整页笼统打分。视觉分低于阈值就在融合前降级为纯文本两路。三路结果用 RRF 按排名融合，解决不同检索方式分数量纲不一致的问题。
>
> 融合后，视觉命中的候选区域再送一个多模态小模型翻译成文字描述，和文本候选一起交给主力纯文本 LLM 生成答案——多模态模型只做"翻译"，不负责真正的理解和回答，这样主力 LLM 可以用最强的纯文本模型，不受视觉能力限制。
>
> 最终图表类问题准确率从 35% 提升到 73%。

**要点**：
- 完整故事要三路都提到：BM25（精确匹配）+ 文本向量（语义）+ 视觉向量（图表），不能只讲视觉这一路
- 视觉路两阶段：ANN 粗排收窄候选 → MaxSim 精排定位答案 Patch（不是整页平均）
- 降级机制：视觉分低于阈值，融合前就退化为两路文本
- RRF 融合：解决三路分数量纲不同的问题
- 翻译层：多模态模型只做"图→文字"，不做最终回答，主力 LLM 保持纯文本最强模型
- 收尾效果数字：35%→73%

**易错点**：
- 开场整体介绍漏掉"三路并行"框架，会让面试官误以为这只是个图表检索小功能，体会不到系统完整度
- "因为不知道怎么召回所以用 ColQwen"这句因果要调整：是"直接把每页图像都送多模态模型成本太高，所以需要先用轻量检索（ANN+MaxSim）缩小候选，再对命中的候选做多模态理解"

## Q2：三路都全跑，成本和延迟不会很高吗？为什么宁可付出代价也不做路由？"路由判错代价是整条路漏掉"举个例子？

**标准答案**（口播约 55 秒）：

> 硬件问答精度优先，这是前提。但更关键的论证是路由本身也不便宜、还多一个出错点：路由需要一次 LLM 调用去猜"这个问题要不要走视觉路"，这次调用本身的延迟不比 ANN+MaxSim 检索快多少；而且它是纯猜——只看 query 文字，猜错了会直接漏掉整条视觉路。
>
> 举个例子：用户问"TPS54331 在 3A 负载下效率大概多少"，文字上看就是个普通规格问题，路由很可能判成"纯文本、不需要视觉"，但这个效率值只在效率曲线图里，文字层压根没有——路由错判，视觉路整个不跑，答案要么是空、要么模型编一个数字回复用户，这次提问直接白问，用户还要重新追问，反而更费成本，提问的意义也丧失了。
>
> 真正该控制成本的地方不是"要不要检索"，而是检索之后最贵的那一步——多模态模型翻译。这一步已经有门控了：只有 MaxSim 精排分数过阈值的 Patch 才会送进去翻译，分数不够直接跳过、退化成文本两路。这是用检索出来的真实证据（MaxSim 分）做门控，而不是用 LLM 事前瞎猜做门控——同样是省成本，门控放在有真实证据之后，永远比放在检索之前更准。至于 ANN+MaxSim 本身，虽然比纯文本检索慢一点，但量级上远比一次 LLM 调用便宜，三路都跑换来零漏检，这笔账划算。

**要点**：
- 领域前提：硬件问答精度优先
- 路由不是免费的：也要一次 LLM 调用，延迟不比检索省多少，还多一个"猜错"的失败点
- 具体例子：效率曲线类问题文字上像纯规格问题，路由易误判成纯文本，视觉路被跳过，答案错误或为空
- 核心洞察：成本控制点不该放在"检索前用 LLM 猜"，该放在"检索后用真实证据（MaxSim 分）门控"——即翻译层的置信度门控才是真正省钱的地方
- 收尾：三路全跑本身增量成本可控（ANN+MaxSim 远比一次 LLM 调用便宜），换来零漏检

**易错点**：
- 别停在"精度优先"就结束——面试官要听到"为什么路由本身也不划算"的具体论证
- 被要求举例子时一定要给（效率曲线类问题最典型），空对空的论证说服力弱

## Q3：MaxSim 精排具体怎么算？为什么取最大值不用平均？一页里两个不相关图表会不会误打高分？具体裁哪个 Patch？

**标准答案**（口播约 60 秒）：

> 先纠正一个细节：MaxSim 不是"query 整体和所有 Patch 比一次取最大值"这么简单，它是 token 级的后期交互（late interaction）。query 编码后也是多个向量——每个 token 一个；一页有 N 个 Patch 向量。计算方式是：对 query 的每一个 token 向量，单独去和这一页所有 Patch 向量算相似度，取这个 token 自己的最大值——也就是给这个 token 在页面里找到"最匹配它的那个区域"；然后把 query 所有 token 的这些最大值加总（或取平均），作为这一页的最终得分。公式是 `score = Σ_i max_j (q_i · d_j)`，i 遍历 query token、j 遍历页面 Patch。
>
> 为什么不用平均值：如果直接对所有 Patch 相似度求平均，答案区域的高分会被页面里大量无关区域（空白、图例边框）的低分拉低，真正相关的信号被稀释；取最大值，是让每个语义点（query token）去页面里挑它自己最匹配的区域，不受其他无关区域打分低的拖累。
>
> 一页两个不相关图表会不会误打高分：不会造成实际问题，原因有两层。第一，即便是 sum-of-max，得分反映的是"query 的每个语义点能不能在页面某处找到匹配"，如果两个图表主题完全不同，query 的 token 通常也只会匹配其中一个图表对应的 Patch，不会两个图表都被"蹭分"；第二，更关键的是下游用的是 Patch，不是整页——MaxSim 精排选出的是"这页里得分最高的具体 Patch 坐标"，后续裁剪、送多模态翻译的也是这个坐标框出来的区域图，不是把整页图像原样甩给翻译层。所以哪怕这一页确实有一半内容不相关，也不影响最终喂给 LLM 的内容——MaxSim 的职责只是"判断这页存不存在答案"和"答案具体在哪个区域"，不是"评价整页内容的相关度"，这正是不做物理切块、改用多 Patch 向量的设计初衷。

**要点**：
- MaxSim 精确定义：query 多 token 向量，每个 token 对页面所有 Patch 取最大相似度，再对 query 所有 token 的最大值求和/平均 = 页面得分（late interaction，不是单一全局最大值）
- 为什么最大值不用平均：平均会被无关区域低分稀释，最大值让每个语义点各自找匹配区域
- 两个不相关图表的顾虑：①query token 通常只匹配到其中一个图表，不会两边都蹭分 ②关键防线是下游只用"最高分 Patch 坐标裁剪出的区域图"，不是整页——MaxSim 只负责"存在性判断+定位"，不负责"整页相关度评价"
- 具体裁剪哪个 Patch：先定位锚点（全局相似度最高的 token-Patch 对），再以定位点为中心扩窗，裁出**覆盖完整视觉元素的区域**，而非死抠单个 Patch（单 Patch 大概率裁不出完整图表）；若 query 涉及页内多个不同区域，可按坐标聚类裁多个区域分别翻译
- 分数量纲延伸：MaxSim 用 sum-of-max，长 query token 多分数天然更大；同一 query 内比较候选页不受影响（token 数量对所有候选一致），但跨 query 或跨检索路直接比较分数不安全——这也是用 RRF 按排名融合而非原始分数加权的原因，和"三路量纲不同不能直接加权"同一道理

**易错点**：
- 只重复"取最大值当页面得分"不算讲透，必须说出 token 级 late interaction 的计算步骤（每 token 各自 max，再求和）
- 防守"两个图表"问题时，光说"不会"没用，要落到"下游只用裁剪出的 Patch，不用整页"这个具体机制上

## Q4：ANN 粗排召回 top-50 这个数怎么定的？降级阈值怎么定的？定高了/定低了分别有什么问题？

**标准答案**（口播约 55 秒）：

> 两个数值都是从"召回率 vs 延迟"曲线上找拐点，做法和资源治理里压测找拐点是同一套方法论，只是这次测的对象是检索召回而不是下游服务：内部搭了一套专门针对 Patch 检索的评测集，固定 query 集合，扫不同 top-k 值观察召回率和 MaxSim 精排延迟——k 小于 50，召回率明显下降（真正相关的页有一部分排不进候选）；k 大于 50，召回率提升很小，但精排是要对每个候选页算 token 级相似度，候选数一涨，计算量跟着线性涨，延迟明显变差。50 就是那个召回够、延迟还可控的拐点。
>
> 降级阈值的设定思路则是风险不对称：定高了，一部分真正该走图表检索的问题会被误判成"低置信度"，退化成纯文本，直接答不出来——这是漏检，漏检的代价是这次提问白问了；定低了，顶多是多送几个其实不太相关的 Patch 去多模态翻译，多花一点翻译成本。硬件问题经常依赖图表，漏检比多余的翻译成本贵得多，所以阈值故意设得偏低，默认更相信要走视觉路，只有 MaxSim 分明显差才降级——本质上和前面"三路都全跑不做路由"是同一个风险不对称逻辑：宁可多花一点成本兜底，不要因为误判漏掉答案。
>
> 这两个数值都不是钉死的，会随评测集和线上反馈迭代调整，重要的是这套"曲线找拐点+风险不对称"的推导方法。

**要点**：
- top-50 推导：专门的 Patch 检索评测集 + 扫 k 值观察召回率-延迟曲线，50 是拐点（同资源治理"压测拐点"方法论的迁移）
- 降级阈值推导：风险不对称——漏检（该用图表却退化成文本）代价 > 多余多模态翻译成本，所以阈值故意设低，默认偏向信任视觉路
- 跨亮点呼应可以主动说出来：这和"三路全跑不做路由"是同一套"宁可多花成本、不可误判漏答案"的风险不对称原则，贯穿了整个 RAG 设计
- 收尾：数值本身可迭代，方法论（曲线拐点+风险不对称）才是重点

**易错点**：
- 只说"经验值加测试"太空，要具体到"扫 k 值看召回率-延迟曲线"这个方法
- 阈值设定别只说"避免误判"，要点出风险不对称这个决策依据（漏检代价远高于多余翻译成本）

## Q5：跳过 OCR 是为了避免信息损失，但检索命中后又把图像翻译成文字——这不是同一种损失又发生了一遍吗？跳过 OCR 的意义何在？

**标准答案**（口播约 60 秒）：

> 先纠正问题里隐含的等价假设：这两步根本不是同一件事重复了一遍。OCR 是字符识别，只能认出图像里印刷体的文字和数字，它对曲线本身没有任何理解能力——"3A 负载下效率约 87%"这句话，曲线图上根本没有印这行字，它是要看懂 X 轴代表电流、Y 轴代表效率、曲线在 3A 位置的高度对应哪个刻度，推理出来的。OCR 结构上就做不出这种推理，它只会把图注标题那几个字抠出来。而多模态小模型做的是视觉语义理解，能读轴、读曲线位置、做推理描述——这是 OCR 完全不具备的能力，不是同一种操作的重复，是两种本质不同的操作。
>
> 第二个关键是顺序和信息损失发生的时机：如果一开始就全量 OCR，是在完全不知道哪页、哪个区域重要之前，就把图像信息破坏掉了，而且不可逆——错了没法挽回。我们的设计是反过来：检索阶段全程用图像原生的 Patch 向量，不损失任何信息；等 ANN+MaxSim 已经精确定位到答案具体在哪个区域之后，才对这一个小区域做"转文字"这一步操作，而且做的是有视觉理解的语义翻译、不是字符识别。同样是有损的最后一步，发生在你已经知道该看哪之后，信息含量天差地别。
>
> 成本上也要澄清：不是"OCR 本身贵"，OCR 引擎其实很便宜；真正的成本账是——把最贵的能力（多模态语义理解）只用在检索精确命中的那一小撮候选上，而不是全量跑在万级页面上。全量 OCR 便宜但信息破坏不可逆；全量多模态理解信息保真但太贵跑不起；我们的方案是检索阶段用便宜且不损失信息的方式（Patch 向量）撑住全量规模，只在真正需要理解的那一步，花贵的成本用对地方。所以两次"转文字"不是重复，是能力不同+时机不同+成本分配不同。

**要点**：
- 核心反驳：OCR（字符识别）≠ 多模态翻译（视觉语义理解），不是同一操作重复，后者能做前者结构上做不到的推理
- 关键论证：损失发生的时机不同——OCR 上前破坏信息且不可逆；多模态翻译发生在已经精确定位之后，只对一个小区域做，而且是语义理解而非识字
- 成本论证修正：不是"OCR 贵"，是"全量多模态理解贵"，设计精髓是"检索用便宜不损失信息的方式撑全量，理解只用在精确命中的候选上"——这是资源分配的问题，不是二选一避免损失的问题

**易错点**：
- 别接受面试官"这不就是同一步重复了"的预设，先拆穿"OCR≈多模态翻译"这个等价假设不成立
- "OCR 成本太高"这个说法不准确，OCR 通常很便宜——真正该强调的是"全量多模态理解才贵，所以只用在精确命中之后"

## Q6：图表类问题准确率 35%→73%，这个数字怎么测出来的？评测集怎么构建、标准答案谁定、数值题误差怎么判、有没有做消融证明每个组件都有必要？

**标准答案**（口播约 55 秒）：

> 评测集延续同一套 6:3:1 构建方式（60% 线上真实流量、30% 自建、10% AI 增强），但专门筛出图表类问题这个子集，针对性测视觉链路。
>
> 标准答案的来源是从原始 Datasheet 的图表里人工核实读出真实数值，不是模型自己判断对错；数值类问题的判分容忍一定误差范围（落在真值某个百分比区间内算对），纯定性问题（比如趋势上升还是下降）才用精确匹配。
>
> 消融是分层做的：文本两路基线是 35%；只加视觉检索但不做 MaxSim 精排（粗排后直接拿整页或随便一个 Patch 去翻译）——提升有限，因为翻译内容不精确，可能把无关区域也翻译进去，稀释正确信号；接入 MaxSim 精确定位到答案 Patch 之后，准确率有一次明显跃升——证明真正带来提升的不是"有没有视觉能力"，而是"能不能精确定位到答案区域"；降级机制对图表类问题准确率本身影响不大，它的价值主要在纯文本问题不被视觉路误伤、以及成本延迟的控制上——不加降级，纯文本问题也会跑视觉翻译，浪费成本、拉长延迟，但不见得拉低图表题这个指标。最终三路+MaxSim+降级的完整链路，图表类问题准确率到 73%。

**要点**：
- 评测集延续 6:3:1，但专门筛"图表类问题"子集——和资源治理、Skill 两个亮点的评测方法论保持一致，可主动点出这种跨亮点一致性
- 标准答案来源：人工核实原始图表真实数值，不是模型自判
- 判分标准：数值题按误差区间容错，定性题精确匹配——不能说成"精确对答案"
- 消融按组件拆开：文本基线 35% → 加视觉但无 MaxSim（提升有限，翻译不精确）→ 加 MaxSim（明显跃升，证明"精确定位"才是核心贡献）→ 加降级（不直接提升图表题准确率，价值在纯文本问题不被误伤+成本延迟控制）
- 结论：73% 是完整链路结果，但消融揭示了精确定位（MaxSim）才是最大功臣

**易错点**：
- "标准答案是老办法去 PDF 库拿"太模糊，要落到"人工核实图表真实数值+数值题容错区间"
- 消融别笼统说"都提高了"，要按组件拆开说清楚谁贡献了多少、贡献的性质是什么（准确率 vs 成本延迟）

## Q7：混合问题（既有纯文字部分又有明确图表需求，比如"封装是什么，效率曲线在3A下大概多少"）怎么处理？降级判断是对整个 query 判一次，还是要拆开来看？

**标准答案**（口播约 50 秒）：

> 混合问题不拆分，整体当一个完整 query 去做三路检索——这和"不路由、全跑"的设计一致，不需要先判断这个 query 里哪部分是文字、哪部分是图表。
>
> 关键在于 MaxSim 本身是 token 级的：query 会被拆成多个 token，"封装是什么"和"效率曲线在3A下"对应不同的 token，每个 token 各自独立去页面里找它自己最匹配的 Patch，再把所有 token 的最大值求和作为最终分数。只要"效率曲线"这部分 token 真的在某个图表 Patch 上找到强匹配，它贡献的高分会被加进总分，不会因为"封装"那部分 token 匹配度低就被平均拉低——这跟当初"取最大值不用平均"是同一个道理。所以混合问题不需要额外拆分或者用关键词硬判"这个问题一定是图表类"，MaxSim 的 sum-of-max 设计天然就能让"哪怕只有一部分 query 是图表相关"也把总分顶到阈值以上，正常走三路融合而不会被误判降级。

**要点**：
- 混合问题整体当一个 query 做三路检索，不拆分——和"不路由"设计保持一致
- 核心机制：MaxSim 是 token 级 late interaction，每个 token 独立找最佳匹配再求和，图表相关的子问题只要有 token 强匹配就能把总分顶高，不会被文字部分的低分拉低
- 不需要引入关键词硬编码判断（比如"看到'曲线'就绝对判图表类"）——这类关键词表既没有依据、也和"不路由"的设计哲学相矛盾，还容易漏掉没提关键词但确实是图表问题的表达

**易错点**：
- 不要为了"图表类问题不能漏检"而引入关键词白名单强判——这是重新造了一个脆弱的路由分支，站不住脚
- 回答"混合问题怎么处理"时不能只说"当一个 query 处理"，要说清楚 MaxSim 的 token 级机制为什么天然能处理混合场景，这才是问题的核心

## Q8：视觉候选翻译成文字之后，这段翻译文字和 BM25/文本向量召回的原始文字候选，喂给主力 LLM 时是同等对待混排，还是要做区分？为什么？

**标准答案**（口播约 50 秒）：

> 需要区分，而且要标注来源，不能混排。原因分三层：
>
> 第一，可信度不对等——文本路召回的是文档原文，是准确引用；多模态小模型翻译图表得到的文字，本质是从曲线位置反推出来的近似值，存在读图误差。不加区分混在一起，主力 LLM 没法判断哪句该原样引用、哪句该带不确定性表述，比如输出"效率约为 87%"还是"效率为 87%"，语气上应该不一样。
>
> 第二，这和聚合层的复合置信度是同一套逻辑——聚合节点算置信度要看证据是否充分、推理占比多少，翻译内容的"推理成分"更高，如果不标注来源，聚合阶段没法把这个因素纳入打分，最终答案的可信度评估会失真。
>
> 第三，可追溯可验证——硬件场景对准确性要求高，如果标注了"这个数值来自第 X 页效率曲线图翻译"，用户发现数字可疑时能自己回原图核实；混在一起看不出出处，用户没法验证，这在硬件选型这种高风险场景是不可接受的。理想情况下标注要带着来源页码/区域坐标一起传下去，方便引用也方便复盘。

**要点**：
- 结论：必须区分标注，不能同等混排
- 三层原因：①可信度不对等（原文引用 vs 推理转述）②和聚合层复合置信度是同一逻辑，翻译内容推理占比需要被纳入打分 ③可追溯可验证，标注来源页码/坐标，方便用户核实、方便复盘
- 理想标注粒度：不只是贴标签，带着来源页码/区域坐标一起传递

**易错点**：
- 只说"需要区分"不够，容易被面试官追问"具体因为什么"——必须落到可信度、复合置信度、可追溯这三层
- 别忘了复合置信度这一层——这是和 Multi-Agent 高亮点"证据充分性、推理占比"同一套评估逻辑的跨亮点呼应

## Q9：这些向量和倒排索引数据都放在 PostgreSQL 里吗？HNSW、BM25 这些检索方式是数据库自带的，还是应用层自己实现的？

**标准答案**（口播约 70~80 秒）：

> 存储位置：向量数据（文本向量、视觉 Patch 向量）和倒排索引数据都在同一个 PostgreSQL 实例里，没有拆成专用向量库+专用搜索引擎+关系库三套系统。这不是没想清楚，是主动选择——全库量级估算下来是 75~90GB，单机 PG 完全扛得住，引入多套专用系统只会增加不必要的运维复杂度。
>
> HNSW 不是应用层写的算法，是装了 **pgvector** 这个开源扩展。PG 本身不自带向量能力，pgvector 给它加了向量类型（比如 halfvec 存 float16 省一半空间）和新的索引方式，`CREATE INDEX ... USING hnsw` 建出来的图结构、插入、遍历，核心算法全部是 pgvector 扩展的 C 代码实现的，不是我们自己写的近邻搜索引擎。应用层真正做的是：选类型、建索引时调参数（比如 m、ef_construction 控制图的连接度和构建质量）、查询时调 ef_search 控制召回率和速度的权衡，以及把三路结果做 RRF 融合和降级判断——这些编排逻辑才是自己写的代码，向量索引算法本身没有重新发明轮子。
>
> BM25 这个命名要澄清一下，严格来说不完全准确。真实情况是用 PG 原生全文检索能力：`tsvector` 分词 + `GIN` 索引做倒排存储，这部分没问题；但排序打分用的是 PG 内置的 `ts_rank`/`ts_rank_cd` 函数，这两个函数思路上和 BM25 同源，都是基于词频、文档长度做归一化打分，但不是逐公式一致的标准 Okapi BM25——PG 原生排序函数没有 BM25 那套 k1、b 可调的饱和函数。要做到严格 BM25，需要额外引入类似 pg_search（ParadeDB）这样的扩展，或者自己在统计信息上手写打分函数。所以更准确的说法是：这一路承担的是 BM25 的角色（词项精确匹配，比如"TPS54331"差一个字就要精确区分），用的是 tsvector+GIN+ts_rank，概念同源但不是严格实现。
>
> 总结一下分工：三路检索没有一条是从零手写检索算法，都是用 PG 生态里现成的能力——pgvector 给向量检索、tsvector+GIN 给全文检索；自己写的是 schema 设计、索引参数调优、三路并行查询组装、RRF 融合、降级判断这些业务编排逻辑。

**要点**：
- 存储位置：向量+倒排全在一个 PG 实例，不拆多套专用系统——依据是数据量级（75~90GB）单机可控，见 `数据.md`
- HNSW = pgvector 扩展提供的索引类型，核心图算法是扩展的 C 代码实现，应用层只做类型选择、参数调优（m/ef_construction/ef_search）
- "BM25"命名不严谨：PG 用的是 tsvector+GIN+ts_rank，思路同源（词频+长度归一化）但不是标准 Okapi BM25 公式，被追问要诚实澄清
- 分工总结：检索算法用现成的（pgvector/tsvector），自己写的是编排逻辑（schema、参数、融合、降级）——这个分工讲清楚比含糊说"我们实现了 BM25 和 HNSW"更真实也更专业

**易错点**：
- 别说成"自己实现了 HNSW/BM25"——会被顺着问算法细节问倒，正确说法是"用的是 pgvector/PG 原生全文检索，自己做的是参数调优和查询编排"
- 被追问"这是标准 BM25 吗"不要硬撑说是，如实说"概念同源但不是逐公式一致的 Okapi BM25，PG 用的是 ts_rank"
- 别把这个"实现边界"问题和前面 Q1-Q8 的检索设计混为一谈——设计思路（三路并行、MaxSim、降级）是自己的判断，但落地这些判断用的底层算法是数据库生态现成的，这是两个不同层面的问题
