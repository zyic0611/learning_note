# 知识库检索

## 三路并行（不做路由，全跑）

| 路 | 召回什么 | 技术 |
|---|---|---|
| BM25 | 型号精确匹配（"TPS54331"差一个字是另一颗芯片） | PG tsvector |
| 文本向量 | 语义段落（规格描述、工作条件） | BGE + pgvector |
| 视觉向量 | 图表曲线（文字层里根本没有数据点） | ColQwen2 + pgvector |

为什么不路由：路由判断需要一次 LLM 调用；硬件问题经常同时涉及文字和图表；路由判错代价是整条路漏掉。

---

## 三路的索引实现：HNSW × 2 + GIN

| 路 | 索引类型 | 说明 |
|---|---|---|
| BM25 | PG tsvector + GIN 倒排 | 词项 → posting list，和向量索引无关 |
| 文本向量 | BGE + pgvector，HNSW | 与视觉路统一用 HNSW |
| 视觉向量 | ColQwen2 + pgvector，HNSW | ANN 粗排用的就是 HNSW，不是 IVF |

为什么两个向量表统一 HNSW 而不是 IVF：

- **无训练步骤**：HNSW 直接增量插入，新增 PDF 随时入库不用重建；IVF 要先对数据分布聚类训练分出 lists，增量数据进来会让列表结构劣化，需要定期重聚类——和"用户增量上传"的场景冲突
- **召回质量不依赖聚类**：HNSW 是图遍历，对数据分布不敏感；IVF 的召回高度依赖"查询落在哪个 list 附近"的聚类质量，分布一变精度就掉，要靠加大 probe 数量去补，多出要调的参数
- **代价可接受**：几十 GB 的 HNSW 索引基于 pgvector 的按需加载方案落地，不用全量塞进内存；构建虽然慢，但离线跑一次即可（见 数据.md）

## 视觉路内部：两阶段精排

```
query → ColQwen2 编码
          │
        ANN 粗排（HNSW）
        万页里快速捞出候选 top-50
          │
        MaxSim 精排
        每页有 N 个 Patch 向量
        取 query 与所有 Patch 相似度的最大值作为页面得分
        → 找到"这页最相关的区域"，不是整页平均
          │
        top-k 页（带最高分 Patch 坐标）
```

MaxSim 的意义：平均分会把无关区域的低分稀释答案区域；MaxSim 只看最相关的那个 Patch，天然完成答案定位。

不加 Reranker：MaxSim 本身已是精排，再叠一层收益边际递减。

---

## 降级判断：在融合前

```
视觉路 MaxSim 最高分
  ├─ 高于阈值 → 三路正常融合
  └─ 低于阈值 → 视觉路降权，退化为文本两路融合
```

在融合前判，不是融合后补救。MaxSim 分是视觉路最直接的置信度信号。

---

## RRF 融合

三路分数量纲不同（TF-IDF / 余弦 / MaxSim），不能直接加权。

RRF 只用排名：`score = Σ 1/(60 + rank_i)`，三路都靠前的候选自然胜出，量纲问题消失。

## 图像翻译层：多模态模型只做"图像→文字"

```
视觉候选（Patch 区域裁剪图）
        │
   多模态小模型（只做一件事：描述这个区域的内容）
        │
   文字描述（"在3A负载下效率约为87%"）
        │
        └─ 和文本候选合并
                │
          主力纯文本 LLM 生成最终答案
```

多模态模型不负责回答，只负责把图像翻译成文字。主力 LLM 永远是纯文本的，不受视觉能力约束，可以用最强的文本模型。

降级时直接跳过翻译层，只走文本两路，一个开关，干净。

---

## 完整链路

```
用户 query
    │
  三路并行检索
    │
  视觉 MaxSim 分 < 阈值？→ 是：视觉降权，两路融合
                          → 否：三路 RRF 融合
    │
  视觉候选 → 多模态小模型翻译 → 文字描述
  文本候选 → 直接取文字
    │
  合并 context → 主力纯文本 LLM → 答案
```

## 耗时分析（查询链路）

**口径**：检索段数字是按 数据.md 的规模（160 万文本向量 / 1.02 亿 Patch / 2 亿词项）推的工程量级估计；模型推理段的 10ms / 4s 与资源治理亮点里的基准值同源（DB 查询 10ms、LLM 调用平均 4s）。

### 分层结论：检索毫秒级，模型推理才是大头

| 阶段 | 典型耗时 | 依据 |
|---|---|---|
| BM25 GIN 查询 | ~10ms 量级 | 与"DB 查询 10ms"同量级，倒排直接命中 posting list |
| 文本向量 HNSW（160 万 × 1024 维） | ~ms 级 | 图遍历对数级扩张 |
| ColQwen2 query 编码 | ~50~150ms（GPU） | 一次文本编码器前向，产出 token 级 query 向量组 |
| 视觉 HNSW 粗排（1.02 亿 × 128 维，top-50） | ~10~30ms | 对数级扩张，输出只有 50 个候选页 |
| MaxSim 精排（50 页 × 256 Patch） | ~几 ms | 50×256×query-token 次 128 维点积，百万级浮点运算，GPU 亚毫秒级 |
| 三路并行 + 降级判断 + RRF 融合 | **~200ms 以内**（视觉路是关键路径） | 三路并行，关键路径 = query 编码 + 视觉 HNSW |
| 多模态小模型翻译（视觉命中时） | 秒级（1~3s 量级） | 全链路除最终答案外最慢的一步 → 超时阈值单独放宽到 60s |
| 主力 LLM 生成最终答案 | ~4s（平均基准） | 与资源治理里 Little's Law 推导（RPM 600 × 4s = 并发 40）同源 |
| **端到端（视觉命中路径）** | **~5~7s 量级** | 检索 ~0.2s + 翻译 1~3s + 生成 ~4s |
| 端到端（纯文本路径） | ~4~5s 量级 | 跳过翻译层，检索 ~0.1s + 生成 ~4s |

### 三个推导结论

1. **优化检索段没有意义**：三路检索全加起来 ~200ms，占端到端 <5%，真正的成本永远在模型前向（翻译 + 生成）。所以 RAG 侧的成本优化点从来不是"少跑一路检索"，而是"门控翻译层"——MaxSim 分不过阈值就不翻译。"不路由、三路全跑"在延迟账上几乎是免费的。
2. **降级机制省的是翻译的 1~3s，不是检索时间**：文本类问题跳过多模态翻译层，端到端直接 ~4~5s；视觉命中路径多出的 1~3s 就是那一次"看图说话"的钱。阈值设低（偏向走视觉路）在延迟上的代价也仅仅是这 1~3s，风险不对称的判断和延迟账对得上。
3. **复杂任务 60s→35s 的收益不来自检索也不来自单次推理，来自编排**：单次调用的耗时分布没有变，变的是墙钟时间——DAG 无依赖节点并行执行、失败分支局部恢复（不再"一出错全部重来"）。检索链路在这套体系里始终是廉价环节，重头戏在编排层的并行度和失败路径设计。

**建库侧（离线）**：40 万页的 ColQwen2 编码是全库最重的成本（万级页面的 GPU 编码任务），但只发生一次；增量入库只需编码新增页面，索引直接增量插入（HNSW 无训练步骤的好处再次兑现）。

## 一句点睛

从跳过 OCR 开始，ColQwen2 直接吃图像；ANN 粗排压候选量；MaxSim 精排定位答案 Patch；裁剪区域送多模态翻译层输出文字；最终主力 LLM 只看文字。**视觉信息从进库到翻译全程保真，翻译层之后和文本信息对齐**。
