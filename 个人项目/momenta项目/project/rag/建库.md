

## 文档池

| 类型 | 处理路径 |
|---|---|
| Datasheet / 测试规范 / 测试报告 | 进知识库（三路索引） |
| BOM / 器件清单 | 结构化抽取 → PostgreSQL 普通表，**不进知识库** |

规模：万级文档，基本全是数字 PDF（无扫描）。

---

## 入库流程

```
文档进来（初始批量 / 用户增量上传）
  │
  ├─ 结构化数据 → 结构化抽取管线（另一条线，此处不展开）
  │
  └─ 非结构化文档
        │
        ├─ 数字PDF → 直取文字层
        └─ 扫描PDF → OCR 先出文字         ← 这个项目基本不走这条
              │
        ┌─────┴──────────────────────┐
        │                            │
   文字层处理                    图像层处理
   分块（按页/段）               每页渲染成图像
   ↓            ↓                    ↓
  BGE 文本向量  tsvector 倒排      ColQwen2 Patch 向量
  pgvector 表A  PG 全文索引         pgvector 表B
                （BM25，不用ES）     （HNSW 索引）
```

---

## 三个索引各管什么

- **BM25（tsvector）**：型号精确匹配，"TPS54331" 差一个字就是另一颗芯片，向量会把它模糊化，BM25 不会
- **文本向量（BGE）**：语义召回，规格描述、工作条件等文字段落
- **视觉向量（ColQwen2）**：图表曲线，文字层里根本没有数据点，只有图注标题

---

## 关键决策

**为什么 BM25 用 PG tsvector 不用 ES**
万级文档 PG 够用；已经用 PG 存向量，同一个库同一个连接池，不引入额外运维。

**为什么视觉检索跳过 OCR**
OCR 把图表转成文字本身就是有损的，曲线数据点、颜色、趋势全部丢失；ColQwen2 直接吃图像，Patch 级多向量保留空间信息。

**为什么索引单元是"页"而不是切块**
曲线图的 X 轴/Y 轴/曲线是一个整体，切开即废；一页出多个 Patch 向量，用多向量覆盖页内不同区域，等价于"切"但不破坏视觉连续性。
