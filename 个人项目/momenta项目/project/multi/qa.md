# Multi-Agent 任务编排 · 面试问答复盘

**问答地图**：
- Q1【最难的问题】失败节点的重规划范围：整体重来 vs 确定性分类 + 局部子图补丁
- Q2 依赖边谁定、为什么不让 LLM 连边、唯一生产者校验
- Q3 仲裁层三层结构、复合置信度五要素、为什么不能只让 LLM 打分
- Q4 Worker 崩溃恢复：PG 事实源恢复粒度、工具调用幂等性、Redis 为什么只需重建不需强一致双写
- Q5 用户确认节点回调链：状态落库、飞书异步确认、回调权限+幂等校验、超时降级

## Q1：项目里遇到最难的一个问题是什么？怎么解决的？

**标准答案**（口播约 90~100 秒，可根据反应掐到 70 秒）：

> 最难的问题不是某个具体算法，是 Multi-Agent 执行失败之后，"要不要重新规划、重新规划多大范围"这件事，比听起来复杂得多。
>
> 最直觉的做法是：DAG 里任何一个节点失败，就整体打回去让 LeadAgent 重新规划一遍。我们最初就是这么设计的，但压测和实际跑下来，发现有三个问题。第一是浪费：一个任务往往只有一个节点出错，其余节点早就成功产出了，整体重规划等于把已经算完的结果全部推倒重来。第二个问题更隐蔽，也更危险：让 LLM 重新规划整个任务，它很可能顺手"优化"了原本运行正常的分支，一次局部失败反而引入了一次全局的不稳定，这比"没修好"更糟——它把好的地方也改坏了。第三是可能不收敛：像网络抖动、限流这类瞬时性错误，根本不需要重新规划，原地重试就能过，但如果不加区分地一律触发重规划，同类瞬时错误反复出现时，每次都要重新出一版计划，等于在烧预算做无意义的重复劳动，而且每次新计划长得都差不多，容易陷在原地打转出不来。
>
> 想清楚这件事之后，我们把"要不要重规划"从一次临时的 LLM 判断，改成一套确定性的分类策略：先看失败原因属于哪一类，每一类对应固定的处置方式，不再交给 LLM 临场决定。网络错误、限流、偶发超时——原节点直接重试，不触发重规划；节点正常跑完但没找到可行结果（abstained）——判断是否存在替代检索路径或者能放宽约束，而不是无脑重来；上游没有产出、真正阻塞了下游——才从最初失效的那个节点重新规划；仲裁层发现跨节点事实冲突——只替换冲突的候选或重跑相关分支；缺用户关键信息——不重规划，直接向用户澄清；预算或时间不够——也不重规划，诚实返回部分结果。这一步的关键洞察是：重规划不是一个"失败了就兜底触发"的动作，而是要先分类失败原因，再决定动不动、动多大范围。
>
> 即便真的要重规划，我们也不让 LeadAgent 从头理解整个请求，只把失败原因和已有的产物喂给它，让它输出一个"计划补丁"——只重新生成受影响的局部子图，这个子图照样要过完整的四层校验，不能绕过。同时为了防止真的陷入死循环，设了硬上限：单任务最多重规划两次，新计划不能和上一次完全相同，至少要在工具、约束、执行路径里改变一项，并且全程卡在 token 和端到端超时的预算线内——真收敛不了就诚实止损，返回部分结果，不做无限重试。
>
> 这一套走通之后，"失败分支局部恢复"才从简历上的一句话变成真正能跑的能力——这也是复杂任务平均耗时从 60 秒降到 35 秒里很关键的一部分贡献：省下来的不是正常路径的时间，是原来"一出错就全部重来"浪费掉的那部分时间。
>
> 这道题真正难的地方，是它没有唯一正确答案——正确性、成本、收敛性这三个目标互相牵制，不能只优化其中一个，得靠一套分类清楚的确定性策略把它们同时兼顾住。

**要点**：
- 弧线结构：朴素做法（整体重规划）→ 三个具体代价（浪费 / 引入新错误 / 不收敛）→ 洞察（先分类失败原因，再决定处置策略）→ 落地机制（局部子图补丁 + 四层校验 + 重规划上限）→ 量化收尾（60s→35s 的关键贡献之一）
- "浪费"和"引入新错误"要分开讲，后者更少人会想到，是这题的亮点——不是"没修好"，是"把好的地方也改坏了"
- 一定要点出重规划上限（2 次、不能重复计划、预算内）——这是防止方案本身反而不收敛的关键，面试官大概率会追问"如果一直失败怎么办"
- 收尾一句"三个目标互相牵制，没有唯一答案"直接回答了"为什么难"，不是只讲了"怎么解决"

**易错点**：
- 别把这题讲成"我们设计了重规划机制"的单纯介绍——重点是"朴素方案为什么不行"这个转折，少了这段就没有"最难"的味道
- 如果面试官追问"具体怎么判断该走哪条处置路径"，如实说是确定性策略/规则判断，不要说成"让 LLM 自己判断"——这会自相矛盾，核心就是"确定性策略判断是否值得重规划"
- 别漏掉"局部子图仍要过四层校验"这句——否则听起来像是给补丁开了绿色通道，反而暴露一个安全隐患

## Q2：节点之间的依赖边是谁确定的——LLM 直接输出，还是服务端算出来的？为什么不让 LLM 连边？"唯一生产者"校验是什么？

**标准答案**（口播约 55 秒）：

> 依赖边是服务端推导的，不是 LLM 输出的。LeadAgent 只输出结构化计划：每个节点声明自己的目标、要消费什么数据（consumes）、成功后产出什么数据（produces），但不画边。服务端拿每个节点的输入，去其它节点的输出里按产物名和类型匹配，匹配上就生成一条"生产者→消费者"的边，整张 DAG 是从数据契约推导出来的。
>
> 为什么不让 LLM 连边：连边是全局拓扑推理，LLM 可能幻觉出不存在的依赖、漏掉真实依赖、甚至连出环；而且它不可复现——同一个请求两次规划，依赖结构可能都不一样，这种产出没法测、没法验证。反过来，让每个节点只声明自己的输入输出，是局部描述，比描述全局拓扑简单得多，出错率天然低。原则还是那句：LLM 只声明关系要素，正确性交给确定性代码。
>
> 推导完之后还有一道关键校验：唯一生产者。每个输入必须有明确来源，而且生产者只能有一个——如果两个节点都产出同名字的数据，下游就面临消费谁的歧义。服务端不做任何选择，直接判计划非法，退回 LeadAgent 重新生成。这样做的价值是：把歧义消灭在规划期，而不是拖到执行期才暴露，那时再解决要么引入复杂的运行时仲裁，要么结果不可复现。
>
> 从工程视角看，这层设计本身就是解耦：节点之间只有数据契约，没有对彼此身份或实现的直接引用，谁都能被替换、被复用、被并行调度。

**要点**：
- 流程：LLM 输出节点（目标+consumes+produces），不画边 → 服务端按产物名/类型匹配推导边 → 校验（来源明确+唯一生产者）
- "为什么不让 LLM 连边"三连：幻觉/漏依赖/成环 + 不可复现没法验证 + 局部声明比全局拓扑简单
- 唯一生产者的价值：数据歧义消灭在规划期，服务端"不选择、判非法、退回重生成"
- 收尾升华：数据契约 = 解耦，节点可替换/复用/并行调度——对字节 JD 语言

**易错点**：
- 别说"校验数据流完整性得出边"——推导和校验是两步，顺序错了会被当成没想清楚
- "为什么唯一生产者"要主动讲"两个生产者会带来什么坏处"（下游不知道消费谁、运行时数值歧义），不能只停留在"规则就是这么定的"
- 如果被追问"唯一生产者会不会限制太死"：产物用名字+类型区分，真需要同样的数据就由下游明确引用指定的产物；消不掉歧义就退回重规划——宁可在规划期卡住，不在执行期拍脑袋

## Q3：聚合前的仲裁层怎么检测跨 Agent 输出冲突？为什么置信度不能只让 LLM 打个分？复合置信度由什么构成？

**标准答案**（口播约 80~90 秒）：

> 仲裁分三层，不是一层。第一层是硬约束：提前写好的业务规则，比如某个温度区间不能选某类器件、参数不能超过某个上限，这一层是确定性代码判断，不涉及语义理解。第二层是跨节点事实冲突：各专家节点的输出都能抽取出实体，先用结构化规则比对不同节点的实体是否直接冲突，这一步能覆盖大部分情况；剩下那些藏在自然语言表述里、需要理解语义才能发现的隐性矛盾，才交给 LLM 过一遍。第三层是价值权衡：如果分歧本身没有对错，只是成本、性能、时间这类主观取舍，系统不替用户做决定，直接把候选选项交出去让用户选。这三层的顺序不是随便排的：能用确定性规则解决的先解决，实在解决不了、又必须做判断的才用 LLM，LLM 兜底判断不了的分歧交回用户——每一层都是把"不该由谁做的判断"往外推。
>
> 至于置信度，不能只让 LLM 输出一个分数，因为 LLM 自评的分数反映的是"这句话说得有多确定、多流畅"，跟"这句话背后有多少真实证据支撑"没有必然关系——模型完全可能对一个证据单薄的结论说得斩钉截铁，这种自信是没有意义的。所以我们把置信度做成一个复合值，由五个可计算的信号构成，不问 LLM 的主观感受。
>
> 第一是检索分数是否达到阈值，直接复用文本路的向量相似度和视觉路的 MaxSim 值，这个信号在检索链路里已经用来做过一次降级判断，这里是第二次复用。第二是证据是否充分，这里的关键是"密度"不是"数量"——同样返回 top-k 篇文档，如果大多数都指向同一个结论、相互印证，证据就充分；如果只是勉强达标凑数、真正相关的只有一两篇，即便用了 k 篇文档证据也不算充分。第三是数据是否过期，这个领域的特殊性是版本一旦更新，旧版本的参数就是错的，不是打折可信，所以更适合按版本号做硬性截断，而不是常规的连续时间衰减。第四是推测的比例，这个不能问 LLM 自己承认编了多少，而是拿生成的结论文本去和检索到的原文做重叠度比对——能在原文里找到直接依据的算摘录，找不到对应支撑、是模型自己补出来的内容算推测，这是一个确定性的文本比对，不是自评。第五是数据来源是否一致，这里容易理解反的一点是：同一个分片被反复引用不算一致，因为那只是同一份证据的重复计入，真正有意义的是**不同**文档、不同分片之间的结论是否互相印证、没有矛盾。
>
> 这五个信号的共同点是：每一条都能被算出来，没有一条是靠问 LLM"你有多确定"得到的——这和仲裁三层里"能用规则解决的不问 LLM"是同一个设计哲学，只是分别用在了"检测冲突"和"评估可信度"这两件事上。

**要点**：
- 仲裁三层完整顺序：硬约束(规则引擎) → 跨节点事实冲突(结构化优先+LLM兜底隐性冲突) → 价值权衡(交给用户选)，三层都是"能确定性解决的不问 LLM，LLM 解决不了的交回用户"
- 复合置信度五要素：检索分数阈值 / 证据充分性(密度非数量) / 数据时效性(硬截断非线性衰减) / 推测比例(文本重叠度比对非LLM自评) / 来源一致性(不同来源间比对，同源去重)
- 核心论证：LLM 自评分数衡量的是"表达自信度"，不是"证据支撑度"，两者不等价
- 跨亮点呼应(主动说出来加分)：检索分数阈值信号和 RAG 里 MaxSim 降级判断是同一个信号的复用；复合置信度机制和 RAG 里"翻译层推理成分要不要区分对待"是同一套底层逻辑的落地

**易错点**：
- 别把"证据充分性"讲成"用了几篇文档"——topk 数量是固定的，充分性衡量的是这些文档里有效、相互印证的证据密度，这个是可变的
- 别把"推测比例"讲成"让 LLM 自己说他编了多少"——这和"不能只让 LLM 打分"的原则自相矛盾，正确做法是生成内容和原文做重叠度比对
- 别把"来源一致性"讲成"同一分片来源多就是一致性高"——同源重复不是交叉验证，真正的一致性检查是不同独立来源之间是否矛盾
- 别漏掉仲裁的第三层"价值权衡"——只讲硬约束和事实冲突两层，会显得对架构理解不完整

## Q4：Worker 崩溃后怎么恢复？会不会重复执行、会不会丢数据？Redis 里的热态数据需要强一致双写保证吗？

**标准答案**（口播约 70~80 秒）：

> Worker 崩溃恢复完全依赖 PG 这个事实源，PG 里有四类表：任务表、节点执行表、产物表、工具调用记录表。新 worker 接手后，先按节点执行表判断每个节点的终态：成功的节点直接跳过，产物从产物表里取，不重跑；真正需要处理的是崩溃时正在跑的那个节点。
>
> 关键是节点内部可能不止调了一次工具，所以恢复粒度要精确到工具调用记录表这一级：这个节点里哪些工具调用已经有明确成功结果——直接复用结果，不重跑；哪个工具调用没有明确结果——先看这个操作有没有副作用，没有副作用就直接重试；有副作用的操作，比如已经触发了外部下单或者发送，就不能无脑重试，得先看能不能反查到执行结果，查得到就按查到的结果继续，查不到就必须转人工确认，因为有副作用的操作重复执行是不可逆的，宁可停下来等人确认，不能猜。
>
> Redis 那边只存热态数据，比如限流计数、实时进度展示这类高频读但允许短暂不准的数据，任何真正影响正确性的判断都只读 PG，不读 Redis。所以 Redis 丢了不需要做数据恢复，直接重建就行——这不是妥协，是设计上它从一开始就不是权威数据源，所以不需要强一致双写或者两阶段提交，也就没有"两份数据谁准"这个一致性问题需要解决。

**要点**：
- 恢复粒度：节点级别定终态，工具调用记录级别定幂等性——因为一个节点可能内部多次调用工具
- 幂等性判断三分支：有结果复用 / 无结果无副作用直接重试 / 无结果有副作用查不到就转人工
- PG=唯一权威源，Redis=派生缓存，崩了直接重建，没有强一致双写的必要——这是"只有一个真源"带来的解耦收益
- (可选追问点，需标注为推测)任务级恢复的并发安全靠归属锁/租约机制防止多 worker 重复认领

**易错点**：
- 别把幂等性检查的粒度讲成"节点级别"——正确粒度是工具调用记录，否则会暴露"节点内部工具重复调用"的漏洞
- 别把"Redis 重建"讲成"因为来不及做一致性方案的权宜之计"——要讲成"设计上它本来就不是权威源，所以不需要一致性方案"，这是主动设计不是妥协
- 如果被追问"两个 worker 抢同一个任务怎么办"，如实说"这是合理推测，文档没展开"，不要编成项目已实现的细节

## Q5：用户确认节点的回调链是怎么走的？长时间没人确认会怎样？

**标准答案**（口播约 75~85 秒）：

> 用户确认节点是特殊节点类型，它到达时的"等待用户确认"状态必须先落库到 PG，再等外部输入——这一步不能省，如果只在内存里挂起，worker 一崩溃这个上下文就丢了。落库之后这个等待状态就变成了任何 worker 都能接手恢复的持久化终态，这跟前面讲的崩溃恢复是同一套体系。
>
> 确认请求通过飞书发出去，不占用一个阻塞连接死等。用户在飞书上选完之后，触发一个回调事件打到服务端，这个回调必须过两道校验：第一是权限校验，确认发起回调的确实是这个任务被授权的用户；第二是幂等性校验，因为网络重试可能让同一个确认回调打进来两次，服务端要能识别"这个确认已经处理过了"，第二次进来直接返回成功但不重复执行，否则轻则重复副作用，重则节点被恢复执行两次。
>
> 校验通过后，用户的选择作为这个节点的输入上下文注入，节点状态从"等待确认"切回运行态继续往下跑，激活的是这一条分支，不是整个任务重来。
>
> 长时间没人确认这块，文档没有写死具体策略，我按已有的失败分类原则去推：这本质上和"缺用户关键信息"是同一类问题，应该同样处理——不重规划、不无限等待，超过一个最大等待窗口就判超时，返回明确的部分结果或提示，不让任务无限期占着资源。这是基于现有原则的合理推断，不是文档写死的具体数值。

**要点**：
- 等待确认必须先落 PG 再等外部输入，是可崩溃恢复的持久化状态，不是内存挂起——和 Q4 是同一套体系，要主动联动
- 飞书异步发出确认请求，worker 不阻塞占用资源
- 回调两道校验：权限（谁能确认）+ 幂等性（重复回调不能重复触发）——分布式系统经典考点，对应 JD 高并发方向
- 确认结果作为节点输入上下文注入，恢复的是该节点/该分支，不是整个任务重触发
- 超时策略文档未写死，合理推断为与"缺用户关键信息"同类处理，需诚实标注为推断

**易错点**：
- 别漏"落库到 PG"——讲成纯内存等待会被追问"这时候 worker 崩了怎么办"，而且暴露没把这题和崩溃恢复联系起来
- 别漏幂等性校验——这是最容易被单独拎出来拷问的点
- 超时降级部分别说成文档写死的机制，要老实说是自己的推断
