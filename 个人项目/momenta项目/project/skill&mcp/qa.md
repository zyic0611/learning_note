# Skill & MCP · 面试问答复盘

**问答地图**：
- 定义与动机：Q1 为什么需要 Skill 层

- 权衡与效果：Q7 灵活性 vs 固化 → Q8 量化效果 → Q9 版本与可观测 → Q10 复盘改进

## Q1：Skill 是什么？为什么不直接让 LLM 拿着工具列表自己规划？

**标准答案**（口播约 30~40 秒）：

> Skill 是把部门沉淀的硬件研发 SOP 固化成可复用的执行单元。为什么需要这一层：如果让 LLM 拿着工具列表即兴规划，同样的请求每次跑出的步骤可能不一样，而且像"国产替代验证"这类部门强制的必查项，纯靠提示词提醒可能被跳过；另外工程师积累的选型经验散落在一段段 prompt 里，无法沉淀复用。所以 Skill 的做法是：步骤顺序和必查项由确定性代码固化、强制执行，LLM 只出现在需要语义判断的节点，比如候选筛选和报告生成，其余全是确定性逻辑。这样同一个流程谁用、什么时候用，执行路径和输出质量都是一致的，新人用和老工程师用结果一样。最终我们沉淀了 10 多个这样的标准化工作流。

**要点**：
- 一句话定义：SOP → 可复用的确定性执行单元
- 对比开放式工具调用：即兴规划 → 流程不稳定、漏必查项、不可复现
- 核心机制：代码固化步骤 + 必查项，LLM 只在语义判断节点介入
- 收益：一致性、经验沉淀、新人可用（"流程质量一样"）

**易错点**：
- 不要说"Skill 是提示词形式的"——会引出"prompt 凭什么强制"的追问。Skill 的价值恰恰在于：它不止是 prompt，步骤执行是确定性代码，LLM 只占判断节点。

## Q2：一个 Skill 在工程上具体长什么样？步骤由谁驱动执行？代码步骤和 LLM 判断怎么区分？

**标准答案**（口播约 40 秒）：

> 一个 Skill 分四部分：元数据（名称、适用场景、输入输出 schema，用于匹配和规划）、SOP 步骤清单、资源和脚本。核心在 SOP：它是一个有序的步骤列表，每一步声明自己的类型——是确定性步骤还是判断节点。
>
> 运行时由 Skill 执行器驱动这个列表：确定性步骤直接调用绑定的脚本或 MCP 工具执行，完全不经过 LLM；只有标记为判断节点的步骤才调 LLM，而且输出被 schema 约束，通常是从枚举候选里做选择，而不是开放生成。
>
> 必查项就实现为确定性步骤——比如"国产替代验证"本身就是一个 MCP 工具调用步骤，执行器保证它一定会跑到，LLM 没法跳过。
>
> 所以 LLM 在整个 Skill 里只出现在两类位置：入口匹配时（决定用哪个 Skill、传什么参数）和 SOP 内的判断节点。步骤先后、调用什么工具，由 SOP 定死。

**要点**：
- Skill 四组成：元数据 / SOP 步骤清单 / 资源 / 脚本
- SOP = 有序步骤 + 每步类型声明（code 步 / judge 步）→ 这就是"执行区分"的答案
- 驱动者是确定性执行器，不是 LLM；code 步不经过 LLM
- judge 步也要上约束：输出 schema、枚举候选里选，不做开放生成
- 必查项 = code 类步骤 → 天然不可跳过

**易错点**：
- "由 LLM 驱动执行"的说法会让"必查项由代码保证"自相矛盾——标准表述：LLM 是被分派的参与者之一，驱动者是执行器。

## Q3：入口怎么匹配到正确的 Skill？拿什么信息匹配？选错了怎么办？和 LeadAgent 规划是什么关系？

**标准答案**（口播约 45 秒）：

> 匹配是两段式的：离线把每个 Skill 的元数据（适用场景、能力描述、输入输出 schema）做 embedding 建索引；在线接到节点目标后，先做向量相似度召回 top-k 候选——只用轻量元数据，不全量加载，省上下文；然后才把候选的完整描述交给 LLM 从里面拍板选定一个并输出调用参数，结构化输出、必须附置信度和依据。
>
> 为什么不纯靠 LLM 读一遍自己选：Skill 多了描述塞不进上下文，纯靠印象选不稳定，所以用召回收窄候选 + LLM 拍板，各取所长。
>
> 选错了的兜底是四道闸：第一，输入 schema 校验，参数不合法直接拦；第二，有副作用的操作先返回工作流描述给用户确认再执行，无副作用的不造成外部损失；第三，执行结果照常过仲裁层，低置信会被拦；第四，重规划时强制更换 Skill。场景真重叠时，元数据里设优先级，仍无法裁决就升级为用户确认。
>
> 另外这步和编排的分层：LeadAgent 规划时只到 agent 粒度，不分派 Skill；Skill 匹配发生在专家 Agent 节点内——编排层完全不感知 Skill 内部，两边解耦。

**要点**：
- 两段式匹配：元数据 embedding 建索引 → 向量召回 top-k → LLM 拍板 + 结构化参数输出
- "需要时再加载完整 Skill"是亮点细节：检索轻量、执行才全量
- 兜底四道闸：schema 校验 / 副作用事前确认 / 仲裁层 / 重规划强制换
- 重叠处理：优先级字段 + 升级用户确认（不能只说"尽量避免"）
- 分层：LeadAgent 规划不分派 Skill，匹配下沉到专家 Agent 节点内

**易错点**：
- "选错没副作用就没关系" → 改为"无副作用只是不造成外部损失，但浪费预算、结果错误，靠仲裁拦；有副作用必须事前确认"
- 匹配表述要顺：不是"压进提示词 + 向量匹配"两个都算，是"向量召回出候选，LLM 从候选中选"。

## Q4：Skill 执行到中途某步失败，谁负责恢复？重试粒度？和亮点一的"失败分支局部恢复"什么关系？

**标准答案**（口播约 50 秒）：

> 恢复是分层分粒度的。Skill 内部管单步重试：瞬态失败——网络抖动、超时——就地重试，上限 3 次、指数退避，撞到限流就退避等待而不是硬撞；第 1 到 3 步已经成功的中间结果在步骤级快照里保留（Redis 热态、PG 落库），重跑只从失败步继续，不会回头重吃。工具调用结果按"工具 + 参数"带 TTL 缓存，同参数期内直接复用，天然幂等。
>
> 单步重试耗尽、或者参数错误这类确定性失败，Skill 执行器不做全局决策，只是上报，节点状态机置 failed——怎么善后由编排层按确定性策略判断：走局部重规划、替换检索路径，缺参就生成澄清问题问用户。这就是和亮点一的咬合点：Skill 内部管"单步"，节点和 DAG 管的"局部恢复"在 Skill 外面，两层靠节点状态机衔接。
>
> 节点之间也一样：上游失败没有有效产物，下游进入 blocked，不是干等——要么等上游恢复，要么编排层从失效节点做局部重规划；预算耗尽就返回部分结果。原则是一致的：谁的状态谁负责，执行器只上报，决策在编排层。

**要点**：
- 恢复分层：Skill 内 = 单步重试（上限 3 次、指数退避、429 退避）；Skill 外 = 节点/DAG 层，走亮点一的局部恢复
- 成功的中间结果步骤级快照（Redis 热态 + PG 持久化）→ 重跑从失败步继续
- 工具结果缓存复用条件：同工具 + 同参数 + TTL 内，且限查询类可复用 → 幂等
- 节点失败不全在 Skill 内解决：执行器上报 → 状态机置 failed → 编排层策略决策（重规划 / 换路径 / 澄清用户）
- 节点间：上游无产物 → 下游 blocked → 重规划或部分结果，不是干等

**易错点**：
- "参数错误重新执行整个 Skill" → 参数错是入口 schema 校验的职责，漏进来按确定性失败上报，不无脑重跑
- 缓存复用要限定条件（同参数 + TTL + 查询类），不能笼统说"不重复执行"
- "阻断下游"要接后半句：blocked 之后编排层有处置路径

## Q5：Skill 的粒度——跨 Agent 流程和单 Agent 流程什么关系？"10+ 工作流"具体指什么？举一个例子。

**标准答案**（口播约 50 秒）：

> 我们的 Skill 是分两个粒度层的，统一一套体系沉淀——元数据、流程定义、资源脚本管理方式都一样。
>
> 编排级 Skill：跨 Agent 的端到端 SOP，沉淀的是 DAG 骨架——哪些 Agent 节点、什么依赖、哪些跨节点必查项。LeadAgent 匹配到它之后只做实例化：填参数、补细节节点，再走四层校验，而不是即兴编计划。节点级 Skill：单 Agent 内部的步骤 SOP，由专家 Agent 匹配后执行。
>
> 举我们最核心的"新器件引入流程"：编排级骨架锁定四个节点——器件选型 → 国产替代验证 → 测试验证方案 → 项目管理归档，第四步是新人最容易漏的跨节点必查项，模板保证它一定出现在计划里。其中"器件选型"节点内部再挂一个节点级 Skill，六步固定：参数归一化（代码）→ 结构化库查询（MCP）→ 候选筛选（LLM 判断）→ 国产替代初筛（代码/MCP）→ 库存交期查询（MCP）→ 报告生成（LLM）。而且节点级 Skill 是可复用的——比如"国产替代验证"这个节点级 Skill，同时被"新器件引入"和"替代方案评估"两个编排级流程引用，一个 SOP 沉淀一次，多个流程复用。
>
> 对外一句话：编排级锁节点之间的骨架，节点级锁节点内部的步骤，LLM 只占语义判断。"10+" 是两层加起来的沉淀量。

**要点**：
- 定性：Skill 分层生态（编排级 = 跨 Agent DAG 骨架；节点级 = 单 Agent 内 SOP），统一机制管理
- 编排级：LeadAgent 匹配 → 实例化 → 四层校验（不是即兴编）
- 节点级：专家 Agent 匹配 → 执行器驱动步骤（呼应 Q2）
- 万能例子：新器件引入流程 = 4 节点骨架（第 4 步"项目归档"是常被漏的跨节点必查项）+ 节点内 6 步 SOP
- 嵌套复用：节点级 Skill 可被多个编排级引用（国产替代验证 → 两个流程复用），"沉淀一次、多处复用"才是含金量
- "10+" = 两层加总，每个端到端流程 = 1 编排级 + n 节点级

**易错点**：
- 别在两个名词（"模板"/"Skill"）间反复横跳——面试现场口径漂移比术语不纯危险得多，统一叫"两级 Skill"
- 问你"举一个 Skill 的例子"，就讲新器件引入流程，两层都展示，一个例子讲全

## Q6：MCP 接入怎么实现？传输协议、动态发现机制、调用权限、工具与 Skill 的复用关系？

**标准答案**（口播约 50 秒）：

> 传输层：所有 MCP Server 部署在公司服务器，走 Streamable HTTP——网络服务场景下最合适，stdio 只适合本地进程，SSE 已是淘汰候补。Server 侧强制服务间 token 鉴权，调用统一走平台入口。
>
> 动态发现：Agent 启动时，MCP 客户端向所有已注册 Server 发列表查询请求，取回工具的名称、描述、输入 schema，聚合成平台的工具注册表——上下文里只放这些轻量描述，不加载任何实现；LeadAgent 规划时从注册表里挑工具分配，真正执行到那一步才发起调用。新增系统 = 注册一个新 Server、刷新注册表，Agent 代码零改动。
>
> 权限三道闸：第一道 Server 鉴权（服务 token，证明调用方是合法客户端）；第二道平台授权——工具带权限标签，用户的可调工具集来自权限中心，LeadAgent 做能力权限校验时就有"工具是否允许"这一项，规划阶段提前拒掉、调用时兜底再查；第三道，写入类高影响操作要求事前用户确认，回调时再校验权限和幂等。
>
> 工具和 Skill 是多对多：一个工具被多个 Skill 的步骤按名字引用，这就是"三个子 Agent 共享同一套工具、不重复实现"的来源。并发上按性质分：只读查询可并行、结果缓存复用；写入操作串行化、加幂等保护。

**要点**：
- 传输：Streamable HTTP（理由：网络部署；对比 stdio 本地进程 / SSE 淘汰候选）+ Server 侧 token
- 动态发现 = 启动拉取工具 schema 描述 → 平台工具注册表（轻量、不加载实现）→ 规划时分配 → 执行时才 call
- 权限三道闸：① 查调用来源（Server 鉴权）② 查用户权限 vs 工具权限（平台授权，规划期拒掉+调用期兜底）③ 重要操作确认后执行
- 工具 ↔ Skill 多对多引用；读并发 + 缓存、写串行 + 幂等（两个独立维度，别混）

**易错点**：
- 权限别再说"不清楚"——三道闸和你 LeadAgent 的"能力权限校验"是同一件事，口径要统一
- 分清两个问题：工具被多个 Skill 引用是无条件允许的（共享资产）；并发才按读写性质区分

## Q7：Skill 固化死会不会牺牲 LLM 灵活性？SOP 没覆盖的新场景怎么办？

**标准答案**（口播约 50 秒）：

> 我们把它设计成"先跑起来、再逐渐锁死"的渐进式。Skill 是可选路由，不是必经之路：匹配不到时走自由规划——LeadAgent 正常做结构化规划，产物照样过四层校验、执行预算和仲裁层，只是少了 SOP 先验，稳定性靠校验和仲裁兜底、成本更高，这正是自由路径付出的代价。
>
> 而且灵活性并没有全被拿走：Skill 内部骨架是固定的，但判断节点是 LLM 语义判断——选哪个候选、参数怎么定，这部分依然是动态的。所以固化的是流程结构，不是每一个决策点。
>
> 自由路径和新 Skill 之间还有个闭环：系统记录自由执行的全轨迹，离线对同类请求聚类，按两个维度挑——出现频率高的，或者容易漏必查项的高风险场景，就提示人工把轨迹整理成一个新 Skill 上线。整个生态是滚动演进的：通用场景先自由跑，跑熟了、频率上来了，沉淀进 SOP。这也就是"10+"的来路。

**要点**：
- Skill 是可选路由：不匹配 → 自由规划（仍过四层校验 + 预算 + 仲裁，缺 SOP 先验、成本高是代价）
- 灵活性保留：骨架固定，judge 节点开放（候选、参数仍是 LLM 判断）
- 演进闭环：记录自由轨迹 → 聚类 → 按"频率 + 风险"挑 → 人工评审 → 沉淀新 Skill
- 承认代价 + 给出闭环 = 高可信度，这正是"10+"的生成机制

**易错点**：
- 别把"自由规划"说成裸 LLM——fallback 仍有校验/预算/仲裁，否则等于承认回到最初的不稳定
- 闭环只说"人工介入看看"太薄——"频率 + 风险两个维度"才有工程味

## Q8：怎么证明这套 Skill + MCP 真的有效？有没有量化效果？

**标准答案**（口播约 55 秒）：

> 效果从三个层面看。第一，离线评测集：来源三路——Skill 上线前收集的硬件工程师线上真实提问、我们手工补充的、以及 AI 数据增强的，大概 6:3:1，保证贴近真实分布。评测就是对照组设计：同一批请求分别走"自由规划模式"和"Skill 模式"，看四个维度——结果质量、平均耗时、工具调用次数、Token 消耗。整体都有提升，最明显的是耗时和工具调用，因为确定性步骤砍掉了大量 LLM 调用，步骤固定以后也没有重复试错；还有一个很关键的指标：必查项覆盖率，自由路径下不稳定，Skill 路径直接到 100%。
>
> 第二，防过拟合：离线评测集固定，流程调优可能对它过拟合，所以我们做了线上灰度对照——部分流量走 Skill 版本持续观察线上耗时和用户反馈，验证收益在真实流量下同样成立。
>
> 第三，MCP 侧的收益主要在开发效率：新增系统的接入成本，从"给 Agent 改代码、加提示词、重新部署"变成"写一个 MCP Server 注册进来"，Agent 代码零改动，三个子 Agent 直接共享，新工具即插即用。

**要点**：
- 评测三件套：来源 6:3:1（真实 / 手工 / 增强）+ 对照组（自由规划 vs Skill 同批请求）+ 四维度（质量 / 耗时 / 工具调用 / Token）
- 每个指标配机制解释：耗时与工具调用降得多 = 确定性步骤砍 LLM 调用 + 固定步骤消除试错
- 特色指标别漏：必查项覆盖率 → Skill 路径 100%（比耗时更能证明核心价值）
- 防过拟合：线上灰度 + 对照组观察（耗时、用户反馈）
- MCP 收益：接入成本从"改代码+提示词+重部署"→"写 Server+注册"，即插即用、三 Agent 共享

**易错点**：
- 只说"都提高了"没有"为什么"——面试官要听机制
- 灰度要说"对照组比较"，不是"上线看没出事"

## Q9：SOP 变了 Skill 怎么更新？版本管理、在途实例、执行进度可见性？

**标准答案**（口播约 55 秒）：

> 版本管理遵循"实例绑定版本、发布不替换"的原则：Skill 元数据带版本号，每次变更发布一个新版本，旧版本继续保留、但不再接收新请求——正在执行的实例锁定它启动时的版本，跑完不受影响，自然排空后旧版本才下线。
>
> 新请求默认路由到新版本，按灰度比例切换；新版本一旦出问题，因为旧版本还在，路由一键回退即可，不用等紧急修复——这就是版本化最大的价值。
>
> 用户侧是"版本可见 + 变更提示"：报告里注明本次执行的 Skill 版本；涉及必查项变化的重大版本，主动在回复里提示"本流程已按新版 SOP 执行"。不做"结果可能不准确"这类贬损式提醒。
>
> 执行到一半的旧版本实例，默认不打断，交付前自动做一次版本核对，按变更性质分三级：无关变更不打扰、照常交付；相关但非硬性的优化，照常交付并附注"本次按 vX 执行，新版已发布，可一键按新版重跑"；如果新版本改的是必查项这类硬规则——按旧版交出去会违反现行政策——就直接中断、自动切新版重跑，并告知用户原因。判定由编排层自动做。
>
> 可观测这边不需要另起炉灶：执行中每个节点的状态本来就在 Redis 热态、PG 落库（和编排层同一套状态机），天然就有完整执行轨迹。用户在飞书能实时看到当前跑到哪一步；运维侧发现节点超时、长时间 running 就告警，从轨迹直接定位到卡住的那一步。

**要点**：
- 实例绑定版本 + 发布不替换：新版本注册 → 新请求切新（灰度）→ 旧实例自然排空后旧版本下线
- 回滚 = 路由切回（旧版本还在，比紧急修复快）
- 用户侧：报告带版本号；必查项变更的大版本主动提示"已按新版 SOP 执行"
- 在途实例分级处理（交付前版本核对，编排层自动）：无关 → 不打扰；相关非硬性 → 附注 + 一键重跑；硬规则变更 → 中断 + 自动切新版 + 告知
- 可观测复用编排层设施：节点状态 Redis 热态 + PG 轨迹 → 进度实时可见、超时告警、轨迹定位到步

**易错点**：
- "等旧实例跑完再更新"→ 发布即注册新版本、实例绑定版本自然排空，发布不被存量阻塞
- "提示结果可能不正确"是坏设计 → 版本可见 + 分级变更提示
- 别漏回滚——版本管理的核心价值

## Q10：如果重做或继续演进这套体系，你会优先改进什么？当时有什么妥协？

**标准答案**（口播约 50 秒）：

> 最想重做的是 Skill 的适用边界判定。现在用户问题跟某个 SOP 很接近、但有细微差异时，偶尔会误调 Skill——这类边界靠写死的描述很难一次磨准。
>
> 改进分三步。第一，机制上先保守化：误用的代价和漏用不对称——误调可能走上错误的强制流程、甚至触发副作用写操作，漏用无非多花点资源走自由规划，所以边界模糊时宁可不用 Skill，走自由规划兜底。
>
> 第二，把边界 case 纳入评测闭环：收集线上误用样本，建一套"不应触发"的负样本评测集，和正样本一起回归；同时给 Skill 元数据加"排除场景"字段，匹配时正反两个条件都要过。
>
> 第三，把沉淀环节半自动化：现在从自由轨迹到新 Skill 有人工评审的瓶颈，未来按频率和风险聚类后先由 LLM 生成 Skill 草稿、人工只做把关。优先级上先做前两点，因为它们直接关系线上正确性。

**要点**：
- 最强的反思点 = 适用边界难磨准（近似请求被误调 Skill）
- 代价不对称原则（整段灵魂）：误用（错流程/副作用）≫ 漏用（多花资源）→ 边界模糊时宁漏不误、自由规划兜底
- 三个改进：① 匹配策略保守化 ② 负样本评测集 + 元数据"排除场景"字段 ③ 半自动沉淀（LLM 草稿 + 人工把关）
- 收尾一句优先级判断

**易错点**：
- 反思题切忌只抱怨不给改法——要说具体机制（负样本集、排除字段）
- 别选大而空的点（"扩展性不足"）；选自己真踩过的小坑
