# 并发资源治理

## 一句话定位

用户一个请求在系统内部扇出成多个异构资源调用，LLM、DB、下游服务瓶颈完全不同，必须分类独立治理。

---

## 问题现场

百余人同时在线，请求类型差异极大：

```
简单请求："TPS54331 工作温度范围"  → 文本检索，1~2 秒
复杂请求："选型 + 测试方案 + 查进度" → Multi-Agent DAG，30+ 秒
```

一个复杂请求在系统内部实际触发：

```
LeadAgent 规划       → 1次 LLM 调用
节点A 器件检索       → 1次 LLM + 2次 DB 查询
节点B 测试方案       → 1次 LLM + 1次 DB 查询
节点C 查项目进度     → 1次下游服务调用
────────────────────────────────────
合计：4次 LLM + 3次 DB + 1次下游服务
```

百人同时发复杂请求 → 400次 LLM、300次 DB 同时打出去。

---

## 三个核心问题

**① 复杂任务挤占简单请求**
全局 FIFO 队列下，复杂任务占满并发槽，简单请求排在后面等，P95 延迟 15 秒。

**② 单用户打爆资源池**
李工同时发 10 个复杂请求，把 LLM 并发槽全占了，其他用户进不来。

**③ 重试级联雪崩**
复杂请求失败重试，重试优先级和新请求一样，再次占满资源池，触发更多超时和重试，滚雪球。

---

## 三个解法

### 1. 分类并发上限

不同资源瓶颈不同，必须分类设上限独立计数：

| 资源 | 上限来源 | 典型值 |
|---|---|---|
| LLM 调用 | API 的 RPM ÷ 平均响应时间推算 | RPM=600、均耗4s → 上限~40 |
| DB 连接 | 连接池大小（受 PG max_connections 约束） | pool_size，通常20~50 |
| 下游服务 | 压测拐点的 70%~80%（留安全余量） | 按各服务单独设 |

**为什么不能混用一个计数器：**
DB 查询 10ms 跑完，LLM 调用 4s 跑完，混在一起限流——DB 被 LLM 的慢速拖累，LLM 也没被有效限制，快慢资源互相干扰。

### 2. 用户间公平轮转

按 user_id 分组，每用户每轮最多派发 N 个任务（通常 N=1~3），轮流拿槽：

```
全局 FIFO:   李工10个请求先全跑完 → 张工等
公平轮转:    李工1个 → 张工1个 → 王工1个 → 李工1个 ...
```

N 值的 tradeoff：N=1 最公平但调度开销大；N 稍大平衡公平与效率。

### 3. 重试降权 + 老化升权

```
正常新请求  → 正常队列（参与公平轮转）
重试请求    → 降权队列（排在正常请求后面）
```

**防饥饿（老化机制）：**
重试请求在队列等待 > 阈值（参考正常请求 P95 耗时的合理倍数，如 60 秒）→ 自动升权到正常优先级，不会永远饿死。

**完整优先级：**
```
1. 升权重试（等待超阈值，老化提升）
2. 正常新请求（公平轮转）
3. 降权重试（刚进来的重试）
```

---

## 超时三层嵌套

```
单次 LLM 调用超时:    30 秒   ← API 侧设置
单个 DAG 节点超时:    60 秒   ← 含重试次数
整个任务超时:         3 分钟  ← 用户等不了更长
```

从内到外逐层收口。只设全局超时不设内层超时的后果：一个卡死的 LLM 调用把整个任务槽占满 3 分钟。

---

## 被拷打数字时的通用答法

> 具体数值是根据约束推算或压测得出的——LLM 上限从 rate limit 推，DB 上限是连接池大小，下游服务是压测拐点的七八成。这些值随系统负载调整，重要的是推导方法，不是某个固定数字。

---

## 效果

- 简单请求 P95：15s → 5s（不被复杂任务挤占）
- 重试不级联（降权隔离 + 老化防饥饿）
- 单用户打爆资源池的情况消失（公平轮转）

---

## 口播版（约 45 秒）

> 并发治理解决三个问题。第一是复杂任务挤占简单请求——用户一个请求在系统内部会扇出成多次 LLM 调用、DB 查询、下游服务调用，这三类资源的瓶颈完全不同，我们按资源类型分类设并发上限独立计数，LLM 上限从 API 的 rate limit 推算，DB 上限是连接池大小，下游服务是压测出来的。
>
> 第二是单用户打爆资源池——改全局 FIFO 为按 user_id 公平轮转，每个用户每轮最多派发 N 个任务，轮流拿槽。
>
> 第三是重试级联雪崩——重试请求降权进低优先级队列，新请求可以插队；但为了防止重试永远饿死，等待超过阈值后自动老化升权。三层嵌套超时兜底，单次调用、单节点、整个任务从内到外逐层收口。最终简单请求 P95 从 15 秒降到 5 秒。
