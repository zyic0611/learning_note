## Q1：完整介绍一下"Agent 运行时治理"这个亮点——问题、解法、效果？

**标准答案**（口播约 55 秒）：

> 这个亮点解决的是"用户一个请求在系统内部扇出成多个异构资源调用"带来的并发治理问题。一个复杂请求内部会触发多次 LLM 调用、DB 查询、下游服务调用，三类资源瓶颈完全不同；百来人同时在线，扇出来就是几百个并发调用。
>
> 由此引出三个问题：第一，复杂任务占满并发槽，简单请求被挤到后面干等——原来全局 FIFO 下简单请求 P95 到 15 秒；我们改成按资源类型分类设并发上限、独立计数，LLM 上限从 API 的 rate limit 推算，DB 上限是连接池大小，下游服务是压测拐点的七八成。第二，单用户连发打爆资源池——把全局 FIFO 改成按用户公平轮转，每个用户每轮最多派发 N 个任务，轮流拿槽。第三，重试级联雪崩——重试请求降权进低优先级队列，新请求可以插队；同时设老化机制，等待超过阈值自动升权，不会饿死。
>
> 在这之上还有请求级执行预算兜底：最大轮次、累计 Token、端到端超时三层约束，超时从单次调用、单节点到整个任务由内向外逐层收口。最终简单请求 P95 从 15 秒降到 5 秒，降了 67%；单用户打爆的现象消失，重试也不再级联。

**要点**：
- 一句话洞察开篇：一个请求 → 内部扇出异构调用矩阵，这是全部机制的根
- 三问题 ↔ 三解法各配推导口径（RPM 推算 / 连接池 / 压测拐点）
- 第四块别漏：请求级执行预算（轮次 / Token / 超时）+ 三层嵌套超时——简历写了必须亮
- 效果收尾：P95 15s→5s（↓67%），这是这段话的句号

**易错点**：
- **"设置 FIFO"说反了**——FIFO 是旧方案，你们是"公平轮转取代 FIFO"
- 收尾没效果数字 = 没句号

## Q2：为什么不能用一个全局计数器统一限流？分类上限的数值怎么推出来的？

**术语注**：
- **RPM（Requests Per Minute）**：LLM API 供应商/网关给的限流配额，每分钟最多允许调用多少次，超过会被拒（429）。
- **压测拐点**：用压测工具（JMeter/Locust 等）逐步加大并发打某个下游服务，画出"并发量 vs 响应时间"曲线；曲线从平稳转为陡升的那个点就是拐点——之前服务有余力，之后服务饱和、响应时间骤增甚至崩溃。取拐点的 70%~80% 作为上限，是因为压测环境和生产有误差、生产流量有突发峰值，留 20%~30% 做缓冲垫。

**标准答案**（口播约 45 秒）：

> 用一把锁去管速度差几百倍的资源，必然顾此失彼。举个具体数字：DB 查询 10 毫秒跑完，LLM 调用 4 秒跑完，差 400 倍。如果共用一个计数器、上限 40：这 40 个槽可能被 40 个 LLM 调用全占满、每个占 4 秒——此刻 DB 池其实是空的，但"总槽"满了，快资源被慢资源堵在门外；反过来，如果为了迁就 LLM 的能力把小计数器设成 10，那 DB 这种本来能扛几百并发的也被压到 10，慢资源反过来误伤快资源。一个计数器没办法同时表达两种量级的上限——设大了慢资源打爆，设小了快资源被浪费。所以必须分类独立计数，各按各的能力配锁。
>
> 数值不是拍脑袋的：LLM 并发上限 40 是推导出来的——API 的 RPM 是 600，平均响应 4 秒，稳态并发 = 每秒请求数 × 平均耗时 = 10 × 4 = 40，这是排队论里 Little's Law 的简化用法，在不超 rate limit 的前提下把并发正好跑满。DB 上限就是连接池大小；下游服务取压测拐点的 70%~80%，留安全余量。这些数都是从现有约束推出来的，负载变了再调——推导方法比具体数值重要。

**要点**：
- 单计数器顾此失彼的双向量化场景：10ms vs 4s（400 倍）；上限设大 → LLM 打爆（DB 被空占），设小 → DB 被误伤
- 结论：一个计数器无法同时表达两种量级的上限，分类独立计数 = 各配各的锁
- LLM 上限推导：稳态并发 = RPM/60 × 平均耗时 = 10×4 = 40（Little's Law: L=λW）
- 其余：DB ← 连接池大小；下游 ← 压测拐点 70-80%
- 防拷打口径：数值随负载调整，推导方法才是重点

**易错点**：
- 只说"瓶颈不同所以分开"太浅——必须能即场报出"10ms vs 4s"的双向反例
- "40 是拍脑袋/压测出来的"要不得——是公式推导，卖点在推导法

## Q3：公平轮转具体怎么实现？空闲时会不会浪费资源？和 DAG 内部节点并行是什么关系？

**标准答案**（口播约 50 秒）：

> 公平轮转的实现是每用户一个独立队列 + round-robin 调度器：每个 user_id 的请求先进自己的队列，调度器按用户维度轮流出队——轮到你，从你的队列里最多取 N 个任务派发到资源池，然后轮到下一个用户，一圈转完再回到第一个用户。这个"轮"不是时间片，是调度器的一次遍历：只在有空闲资源槽时才发生下一次遍历，不是定时触发。
>
> 只有李工一个人在发请求时，公平轮转不会浪费资源——公平只在"有竞争"时起作用，调度器遍历发现其他用户队列是空的，直接把槽都分给李工，他能吃满整个资源池；等张工的请求一进来，下一轮才会在两人之间轮流分配。所以这不是预先按人头切资源，是竞争发生时才限速，空闲时不设限。
>
> 粒度上，公平轮转控制的是任务派发到资源池这一层，不是 DAG 节点内部。一个复杂请求的 DAG 展开后，无依赖节点本来就可以并行——但这些并行节点要抢的是同一批全局资源槛（LLM/DB/下游）。公平轮转决定的是"这一轮从谁的任务队列里往资源池派任务"，一旦某个节点被派发、拿到槛，它自己该并行跑还是串行跑，完全由 DAG 依赖决定。两层不冲突：DAG 依赖决定节点间能不能并行；公平轮转决定并行的节点该优先给谁的资源。

**要点**：
- 实现：每用户独立队列 + round-robin 调度器；"轮" = 调度器一次遍历，非定时时间片
- 关键澄清：公平只在竞争时限速，空闲时单用户可吃满全池（不是预先按人头切分）
- 粒度分层：公平轮转管"任务派发进资源池"这一层；DAG 依赖管"节点间能否并行"这一层，两者正交、不冲突
- 一句话总结：DAG 决定能不能并行，公平轮转决定并行时资源先给谁

**易错点**：
- 别说成"每人固定分到 1/n 资源"——这会在"只有一人在线"的追问下站不住，正确说法是"竞争时限速，空闲不设限"
- 别把"公平轮转"和"节点并行"混成一层——一个管派发入口，一个管 DAG 内部拓扑

## Q4：重试降权会不会被新请求一直插队饿死？老化阈值倍数怎么选？重试是不是新开节点？降权具体降什么？

**标准答案**（口播约 55 秒）：

> 不会永远饿死，这靠两套独立机制配合：一套是重试次数上限，比如单步重试到 3 次还失败，就直接标记节点失败、放弃重试，不是升到最高优先级；另一套是队列老化，跟重试了几次无关，纯粹按排队等待时长触发——等待超过阈值，自动把它从降权队列提到正常优先级，这样才不会被后面源源不断的新请求一直插队。
>
> 阈值倍数是有讲究的，取正常请求 P95 耗时的合理倍数：选太小，重试几乎一进降权队列就被拉回正常优先级，等于没有真正让新请求插队，降权失去意义；选太大，会接近整个任务的端到端超时上限，等它终于被老化提升，可能已经没剩多少预算把这次重试跑完，用户体验照样差，甚至直接触发端到端超时报错。所以倍数要卡在一个区间：明显大于正常 P95、又给端到端超时留出足够余量，保证升权后这次重试还有时间真正跑完，不是白升。
>
> 重试用的是同一个节点，不是新开节点——呼应节点内单步重试的机制，前面已成功步骤的中间结果有快照保留，重试只从失败步继续，节点身份不变，变的只是它在队列里的优先级。降权本身也只影响排队顺序，不动并发槽位分配，槽位还是按资源类型统一分配。

**要点**：
- 两套机制维度不同：重试次数上限（管"还试不试"，到了标记失败）vs 老化升权（管"等太久"，按时长触发，与重试次数无关）——绝不能合并成一句话
- 老化的意义在超时之前主动纠偏，不是"等到崩溃边缘才报错"
- 阈值权衡：太小 = 降权形同虚设；太大 = 升权也快没时间跑完、接近端到端超时；要卡在"明显大于 P95 + 给超时留余量"的区间
- 重试 = 同一节点续跑（呼应 Skill 单步重试的步骤级快照），非新开节点
- 降权只动排队优先级，不动并发槽分配

**易错点**：
- 别把"重试 3 次上限"和"老化升权"说成同一机制——次数维度 vs 时间维度必须分开讲
- "等太久直接报超时"不是老化的目的，是它的失败兜底，老化是提前干预避免走到那一步

## Q5：三层嵌套超时怎么互相制约？和请求级预算（Token/轮次）是什么关系？触发后具体怎么收口？

**标准答案**（口播约 55 秒）：

> 三层超时是嵌套硬顶：单次调用 30 秒、节点 60 秒、任务 3 分钟，从内到外收紧，外层永远是硬约束。冲突时外层说了算——比如一个节点内部重试，单次限时 30 秒，但节点总共只给 60 秒：即使某次重试还没撞到自己的 30 秒上限，只要节点累计耗时到了 60 秒，节点级超时直接把它掐断，重试预算被外层截断，不会出现"内层还没超时所以放任不管"的情况。这样保证无论内部怎么重试，节点绝不会拖爆上一层给它的时间片，任务也绝不会因为某个节点失控而拖爆整体 3 分钟。
>
> Token/轮次这两个预算和三层超时是并行的独立约束，不是嵌套关系——两边同时监控，谁先触发谁生效：可能时间还没到但 Token 先超了，也可能 Token 够但时间先到。
>
> 触发之后是优雅收口，不是硬腰斩：不再派发新节点，正在跑的节点让它自然结束或撞到自己的超时上限，然后把已经产出的节点结果直接聚合返回——这和重规划机制里"预算不够不重规划、直接返回部分结果"是同一个决策，是确定性策略触发，不是异常崩溃。这样既守住了预算上限，又不浪费已经跑出来的中间结果。

**要点**：
- 三层超时关系：内层收紧、外层是硬顶；冲突时外层截断内层（用重试撞节点超时这个具体例子讲清楚，不能只说"以外层为主"）
- Token/轮次预算与三层超时：并行独立约束，谁先触发谁生效，非嵌套
- 触发后的动作要交代"怎么收"：不再派发新节点 + 让在跑节点自然收尾（而非硬腰斩）+ 聚合已产出结果
- 关键连接点：这和"重规划机制"里"预算不够不重规划、返回部分结果"是同一策略，是确定性触发不是异常

**易错点**：
- "打架以外层为主"要配上具体场景讲透，不能只留一句结论
- "掐断"要说清是优雅收口（停止新派发+已跑节点自然结束），不是不分青红皂白的硬杀

## Q6：这套治理会不会拖累复杂任务、拉低整体吞吐？"P95 15s→5s"是怎么验证出来的？

**标准答案**（口播约 55 秒）：

> 不会拖累，反而是保护吞吐的。核心论证是：分类上限本身就是各资源的安全承载线——LLM 上限是从 rate limit 推的、DB 是连接池物理上限、下游是压测拐点。不设治理不代表能突破这条线，只会让请求硬撞上去：LLM 被打到 429 限流、DB 连接耗尽排队、下游过了拐点响应雪崩，这些失败还会触发重试，重试又占用更多资源、形成级联，真实吞吐反而更差。所以治理不是在压低系统容量，是在防止容量被击穿。
>
> 公平轮转也不是砍总资源，是重新分配"什么时候执行"，不是"总共给多少"——一个复杂任务如果当时没人竞争，还是能吃满整个资源池；只有多用户同时抢的时候，才从"李工独占、别人干等甚至可能超时失败"变成"大家轮流拿到资源、都能推进"。个别用户的绝对耗时可能因为排队多了几秒，但系统整体完成的请求数（吞吐）是上升的，因为没有请求被饿死到超时失败要重新来过。
>
> 效果验证不是纯理论推算：搭建了并发压测/回放环境，模拟真实混合流量——多用户同时发简单+复杂请求，总资源池上限保持一致，只切换调度策略——旧版全局 FIFO vs 新版分类限流+公平轮转+老化，对比两组的简单请求 P95 延迟和整体吞吐（单位时间完成请求数），确认新方案在两个指标上都更优，然后跟 Skill 效果验证一样，也做了灰度上线做线上对照，确认线上真实负载下同样成立。

**要点**：
- 吞吐论证核心：分类上限=安全承载线，不治理不代表能突破，只会撞线触发重试级联，真实吞吐更差——治理是"防止被击穿"不是"压低容量"
- 公平轮转重分配的是"时机"不是"总量"：无竞争时单用户仍吃满全池，有竞争时从"部分饿死"变"大家都能推进"→ 整体吞吐上升
- 验证方法要具体：并发压测/回放 + 固定总资源上限只切调度策略（FIFO vs 新方案）+ 对比 P95 和吞吐两个指标 + 线上灰度对照
- 呼应 Skill 效果验证用词一致：离线对照 + 灰度验证，两个亮点口径统一显得体系完整

**易错点**：
- "大部分是中等请求所以没事"不是有效论证，容易被追问"那如果都是复杂请求呢"打穿——用"安全上限本就存在、治理只是防击穿"才站得住
- 验证方法别停在"内部评测集对比 FIFO"一句话，要说清楚"固定总资源、只切调度策略"的对照设计
