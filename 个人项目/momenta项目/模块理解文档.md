# DDH Multi-Agent 模块理解文档

> 基于代码阅读的技术学习笔记，覆盖从用户消息进入系统到各子 Agent 执行的完整链路。

---

## 一、整体架构概览

```
用户消息（飞书 / Web）
    ↓
Handler 层（解析身份 open_id / union_id / chat_id）
    ↓
LeadAgent（意图路由中枢）
    ↓ 快速路由 or LLM 路由
Python 路由层 dispatch()（BFS 拓扑调度）
    ↓ asyncio.gather 并行
CHD Agent   HPD Agent   HTV Agent   General Agent
    ↓
汇总结果 → 返回用户
```

四个子 Agent：
- **CHD**：硬件器件专家（Datasheet 查询、五维评分）
- **HPD**：硬件项目交付专家（Delivery Center API + 飞书操作 + RAG 文档检索）
- **HTV**：测试验证专家（HTV 测试管理系统 + 飞书操作）
- **General**：通用兜底（联网搜索、群聊分析、闲聊）

## 二、Claude Agent SDK

### SDK 是什么

高层封装，自动管理完整的 ReAct（Reasoning + Acting）循环。开发者只需调 `query()`，SDK 处理：
- 向 Claude API 发送请求
- 解析模型输出，检测工具调用
- 执行工具并把结果返回给模型
- 循环直到模型输出最终答案

开发者迭代 SDK 返回的消息流：`SystemMessage` → `AssistantMessage` → `UserMessage` → `ResultMessage`。

### Session 管理

SDK 把每次对话历史存为本地 JSONL 文件，返回一个 `session_id`（文件路径指针）。下次调用传入 `resume=session_id`，SDK 从 JSONL 恢复上下文，实现多轮对话。

Redis 存的是 `session_key → sdk_session_id` 的映射：
- `session_key`：稳定的"门牌号"，格式如 `p2p:ou_abc123`，由用户 open_id + Agent 类型组成
- `sdk_session_id`：SDK 内部 JSONL 文件的指针，每次新对话会变

用户发多条消息 → 每次用同一个 `session_key` 查 Redis → 拿到最新 `sdk_session_id` → resume 继续对话。

### MCP（Model Context Protocol）

Anthropic 的工具通信协议，分两种传输方式：
- **本地 MCP**：`create_sdk_mcp_server()` 把 `@tool` 装饰的 Python 函数包装成进程内 stdio MCP Server
- **远程 MCP**：HTTP dict，SDK 自动连接、拉取工具列表、转发调用

两种方式对模型完全透明，工具名统一格式：`mcp__<servername>__<toolname>`。模型只输出 JSON 调用决策，SDK 是真正的网络客户端，模型没有网络能力。

## 三、LeadAgent — 意图路由中枢

### 职责

接收用户消息，判断意图，路由给对应子 Agent。LeadAgent **没有任何业务工具**，只做路由。

### 快速路由（fast-path）

`_fast_route(task)` 用 frozenset 关键词匹配，零 LLM 开销：

```python
_CHD_KEYWORDS = frozenset(["器件", "芯片", "评分", "datasheet", "s32k", ...])
_HPD_KEYWORDS = frozenset(["项目", "okr", "飞书", "云盘", "wiki", ...])
_HTV_KEYWORDS = frozenset(["测试设备", "测试用例", "流水线", "mphy", ...])
_GENERAL_OVERRIDE_KEYWORDS = frozenset(["天气", "群聊", "你好", "帮我给.*发消息", ...])
```

规则：
- 命中 GENERAL_OVERRIDE → 直接路由 general
- 只命中一个域 → 路由该域
- 命中多个域 / 都没命中 → 返回 None，走慢速路由

### 慢速路由（slow-path）

调 SDK `query()`，关键配置：
```python
ClaudeAgentOptions(
    allowed_tools=[],       # L1 防护：无工具可调，不会触发超轮
    resume=None,            # LeadAgent 无状态，每次独立调用
    max_turns=3,
    setting_sources=[],
    permission_mode="dontAsk",
)
```

`allowed_tools=[]` 是关键：防止 SDK 注入内置 Agent 工具，确保模型只能输出纯 JSON 路由指令。

模型按 `lead_agent/skill/SKILL.md` 的格式输出 JSON：
```json
{
  "tasks": [
    {"task_id": "task_0", "to_agent": "chd", "task": "...", "depends_on": []},
    {"task_id": "task_1", "to_agent": "hpd", "task": "...", "depends_on": []}
  ]
}
```

### JSON 解析

`_parse_routing_plan()` 用 `rfind('}')` 找最外层 JSON 对象（不用非贪婪正则，避免匹配到内层的 `"context": {}` 对象），再 `json.loads()` 解析为 `TaskSpec` 列表。

### BFS 拓扑调度（router.py dispatch()）

计算依赖波次，同一波次内并行执行：

```python
# 计算入度和邻接表
in_degree = {s.task_id: len(s.depends_on) for s in specs}
dependents = {s.task_id: [] for s in specs}
for s in specs:
    for dep in s.depends_on:
        dependents[dep].append(s.task_id)

# BFS 执行
ready = deque(s for s in specs if in_degree[s.task_id] == 0)
while ready:
    wave = [ready.popleft() for _ in range(len(ready))]
    results = await asyncio.gather(*[_run_one(s) for s in wave])
    # 更新入度，新就绪的加入队列
```

`depends_on=[]` 的 task 并行执行；有依赖的 task 等前置完成后才加入队列。前置 task 失败 → 下游直接标记 failed，不执行。

## 四、CHD Agent — 器件硬件设计专家

### 两个 MCP Server

- **本地 MCP**（`mcp__chd__*`）：`create_sdk_mcp_server()`，包含 `datasheet_search`、`datasheet_extract`、`get_skill_guide`
- **远程 HTTP MCP**（`mcp__ddh-chd-mcp-auth__*`）：CHD 器件评分系统 API，Header 注入用户 Keycloak token

### 核心工具

**`datasheet_search`**：用 Python `glob` 模块（非 bash，纯 Python 实现）按三种模式匹配本地 PDF 文件：
1. 精确匹配文件名
2. 基础型号匹配（`_normalize_part_number` 去掉封装后缀）
3. 通配符匹配

评分规则：完整型号在文件名中得 100 分，以该型号开头加 20 分；基础型号匹配得 50+10 分。返回 top 5。

**`datasheet_extract`**：`asyncio.create_subprocess_exec` 启动 `pdf_extractor.py` 子进程，90 秒超时。`mode=text` 返回 JSON 文本；`mode=images` 返回 base64 PNG 列表。

**为什么用子进程而不是直接 import？** PDF 解析库（PyMuPDF）有全局状态和内存管理问题，进程隔离防止崩溃影响主服务。

### 鉴权

进 LLM 前先检查 Keycloak token，没有直接返回 `__KEYCLOAK_AUTH_REQUIRED__{url}` 哨兵，不启动 LLM。

### Bash 沙箱（`_bash_guard`）

只允许 `lark-cli` 命令和 `date`，拒绝其他所有命令。CHD 的 bash 使用场景比 HPD 简单。

### Session 失效恢复

检测 stderr 里的关键词（"no such session"、"jsonl"、"resume"等），如果是 session 相关错误 → 清除 Redis 里的 `session_id` → 重试一次，建立全新 session。

## 五、HPD Agent — 硬件项目交付专家（最复杂）

### 两个 MCP Server

- **本地 MCP**（`hpd-tools`）：`get_skill_guide`、`rag_search`、`rag_sql_query`、飞书消息工具、提醒工具
- **远程 HTTP MCP**（`ddh-hpd-mcp-auth`）：Delivery Center 项目管理 API，Header 注入 Keycloak token

### 双层鉴权

**第一层：飞书 Device Flow**（按需）
```python
feishu_needed = await _needs_feishu_ops(task)  # 关键词判断
if feishu_needed:
    cfg_dir = await lark_user_cfg.get_cfg_dir(auth_key)
    if not cfg_dir:
        return "__FEISHU_AUTH_REQUIRED__", False
```
`feishu_missing = feishu_needed AND not cfg_dir`，只有需要飞书写操作且没有授权时才触发。

**第二层：Keycloak OAuth2**（必须）
```python
keycloak_missing = not keycloak_token  # 无条件检查
```
只要有 `auth_key` 就必须有 Keycloak token。调 Delivery Center API 必须有 JWT。

两道都缺 → 返回 `__FEISHU_AND_KEYCLOAK_AUTH_REQUIRED__{url}`；只缺其一 → 返回对应哨兵。

### ContextVar 身份隔离

```python
owner_token = current_owner_id.set(open_id)  # 注入
try:
    return await self._run_inner_body(...)
finally:
    current_owner_id.reset(owner_token)       # 必须 reset
```

`rag_search` 工具从 ContextVar 读 `open_id`，不在参数 Schema 里暴露——LLM 无法传这个参数，无法伪造其他用户身份。

**为什么必须在 finally 里 reset？** asyncio 协程可能被复用，不 reset 会让下一个请求继承上一个用户的 `open_id`，造成跨用户文档泄露。

### 审批网关（DeferredToolUse）

四步流程：

1. **Hook 拦截**：`_create_issue_guard` 匹配 `create_issue_delivery_v1_mass_production_tables`，首次触发返回 `defer`
2. **SDK 冻结**：返回 `ResultMessage.deferred_tool_use`，携带工具调用参数（项目名、问题描述等）
3. **发确认卡片**：Agent 格式化预览文本，保存 `sdk_session_id`，返回 `__APPROVAL_REQUIRED__{session_key}||||{preview}` 哨兵
4. **用户确认后 Resume**：Redis 写入 `approved` → 重新调用 Agent.run() → Hook 读到 `approved` → 返回 `allow` → 工具真正执行

**为什么用 defer 而不是 deny + 重新发起？** Resume 接续之前的 ReAct 步骤，已完成的工具调用不重跑。deny + 重发要从头执行所有步骤，既浪费 token 又慢。

**为什么 Hook 里不直接等用户点击？** Hook 在 ReAct 循环内同步执行，循环等 Hook 返回，Hook 等用户点按钮，卡片还没发出去——死锁。必须把控制权交出去再发卡片。

### Bash 沙箱（`_bash_guard`）

允许两类命令：
```bash
# 飞书操作
export LARKSUITE_CLI_CONFIG_DIR=/path && lark-cli doc create ...

# HSI 脚本
cd /mnt/data/lx-works/Agent/ADCU_WRI_hsi && python3 scripts/pipeline.py ...
```

检查流程：
1. 先检测注入字符（`;`、`|`、`$(` 等），有则拒绝
2. 按 `&&` 拆段，逐段验证
3. 前置段只能是 `cd <白名单目录>` 或 `export LARKSUITE_CLI_CONFIG_DIR=...`
4. 末段只能是 `lark-cli ...` 或 `python3 scripts/<白名单脚本>.py`

白名单脚本动态读取：`_HSI_SCRIPTS_DIR.glob("*.py")`，新增脚本不用改代码。

### max_turns=100

HPD 有 HSI 自动化流程（4 块芯片 × 多步操作），需要大量 ReAct 步骤，设为 100。CHD 和 HTV 是 15。

## 六、RAG 文档检索系统

### 阶段一：上传处理（异步后台）

**状态机**：`queued → parsing → indexing → ready`

每步用 CAS（compare_and_set_status）校验，防止"删除后复活"：如果用户在解析期间删除文档，CAS 失败，pipeline 立刻中止并清理产物，不把已删除文档写回 ready。

**ingest 子命令（Docling 解析）**：
- `asyncio.create_subprocess_exec` 启动子进程，300 秒超时
- Docling 识别版面结构（标题层级、正文、表格、图片）
- 表格 `export_to_html` 保留 `<tr><td>` 结构
- 图片可选调用 VLM 生成文字描述
- 每份用户上传文档使用独立 collection：`upload_{doc_id}`

**build-index 子命令**：
- BGE-M3（BAAI 开源，本地离线运行）向量化每个 chunk
- 写入 ChromaDB（本地向量数据库）
- chunks 序列化为 `chunks.pkl`（BM25 用）

### 文档切分策略（三条路）

**文本块：段落聚合 + 超长硬切**
同一章节下连续段落合并为一个 chunk，超过 1500 字符才切断。不用固定字符切，保证语义完整性。

**表格：整表优先，超长按行切，每块重复表头**
- token 数 ≤ 1200 → 整表一个 chunk
- 超长 → 按 `<tr>` 边界切，绝不截断一行
- 每个分块都带表头行（第 2、3 块开头也有 `<th>`）
- 保留 HTML 格式而非纯文本，行列对应关系不丢失

**图片：单独成块 + 补"出身信息"**
图片 chunk 的文本 = `[出处] 章节+文档主型号` + Caption + VLM 描述。防止不同文档的同类图片（如卷盘包装图）混淆。

**title_path 层级路径**：每个 chunk 携带 `title_path = "祖先标题 > 当前章节"`，解决同页多级标题导致上下文丢失的问题。翻页时 `page_title` 重置，不跨页污染。

### 阶段二：查询检索（在线）

**用户隔离**：从 `catalog.list_ready_by_owner(owner_id)` 取该用户 ready 且未过期的文档，其他用户文档物理上不在查询范围内。

**混合检索（BM25 + BGE-M3 Dense + RRF 融合）**：

BM25 关键词匹配：
```python
corpus = [section_title + " " + chunk_text for chunk in chunks]
bm25 = BM25Okapi([_tokenize(t) for t in corpus])
# 分词保留完整型号（如 lqg15hh6n8j02d）和中文字符
```

BGE-M3 语义向量检索：
```python
qv = model.encode([query], normalize_embeddings=True)
results = collection.query(query_embeddings=[qv], n_results=50)
```

RRF 融合（Reciprocal Rank Fusion）：
```python
_RRF_K = 60
for rank, i in enumerate(bm25_ranking):
    rrf[i] += 1.0 / (60 + rank + 1)
for rank, i in enumerate(dense_ranking):
    rrf[i] += 1.0 / (60 + rank + 1)
```
只看排名不看绝对分数，在两条路都有排名的 chunk 更可信。

**三个增强机制**：
- 型号加权：查询含完整型号（长度≥8，字母数字混合）时，含该型号的 chunk +1.0 分，前缀匹配 +0.3 分
- 表头块降权：只有 `<th>` 没有 `<td>`（< 3 个）的纯表头 chunk -0.5 分，避免空表头排到真实数据前面
- 同义词扩展：查"额定电流"自动扩展出 `["idc", "rated current", "允许电流"]`，提升中英文混合文档召回率

**no-answer 守护**：
- 规则A（强）：查询含具体型号/实体，但全库找不到 → `no_answer=True`
- 规则B（弱）：BM25 最高分 < 8.0 → `no_answer=True`

### Agentic RAG：决策逻辑在 SKILL.md

`rag_search` 返回 `top_rrf_score` 给 Agent，Agent 按 `datasheet-rag/SKILL.md` 的决策树自主判断：

```
> 0.02   → 结果可信，直接回答
0.01~0.02 → 偏低，回答标注"置信度较低"
< 0.01   → 改写查询重试（同义词/中英互换/拆分）
no_answer_guard=true + 已重试≥1次 → 如实告知未找到
rag_search 总调用 ≤ 5 次（硬性上限）
```

模型在 ReAct 循环的 thinking 里自主执行这棵决策树，不是代码 if-else。

## 七、HTV Agent — 测试验证专家

### 与 HPD 的关键区别

**`_needs_feishu_ops` 多了 LLM 降级路径**：
关键词没命中时，用单轮 LLM 调用（`max_tokens=10`，只回答 yes/no）做二分类兜底。原因：测试工程师描述更技术化，"把报告写到 Wiki"这句话没有"飞书"二字但显然需要飞书操作，关键词覆盖不到。

**Bash 沙箱更简单**：
只允许 `lark-cli` 命令和 `date`，没有 HSI 脚本白名单，没有 `cd` 路径校验——HTV 没有 HSI 自动化场景。

**没有 `_create_issue_guard`**：
测试管理系统的写操作（创建测试用例、更新测试结果）回滚成本低，不需要用户二次确认审批网关。

**独立 Bot 身份**：HTV Bot 用自己的 `HTV_FEISHU_APP_ID/APP_SECRET`，与 HPD 隔离，飞书后台可以分别配置权限。

**max_turns=15**（HPD 是 100），测试场景不需要 HSI 多步自动化。

## 八、SKILL.md 机制——懒加载的子系统提示词

### 架构分层

每个 Agent 的 System Prompt 只写通用框架，专项操作的详细规则写在独立 SKILL.md 文件里，通过 `get_skill_guide` 工具按需加载：

```
模型收到任务："这个 PDF 里 SPI 时钟频率是多少"
  → 调 get_skill_guide("datasheet-rag")
  → 返回 datasheet-rag/SKILL.md 全文
  → 模型按决策树执行：rag_search → 评估 → 改写 → 再查 → 回答
```

### 为什么不全放 System Prompt

System Prompt 每轮都发给模型，太长会：
1. 多消耗 token
2. 模型注意力被稀释，远处的规则被忽略

懒加载：用到哪个技能才把那份 SKILL.md 注入 context。

### 软约束 vs 硬约束分层

这是整套架构最核心的设计判断：**用代码保安全，用提示词保质量**。

| 约束类型 | 在哪里强制 | 失败后果 |
|---------|----------|---------|
| 未授权不能调 API | auth gate（Python if-else） | 安全漏洞 → 必须硬约束 |
| Bash 只能白名单命令 | `_bash_guard` Hook | 命令注入 → 必须硬约束 |
| 量产问题单需用户确认 | `_create_issue_guard` Hook + defer | 不可逆写操作 → 必须硬约束 |
| RAG 只查当前用户文档 | ContextVar + Schema 无 owner_id 参数 | 数据泄露 → 必须硬约束 |
| RAG 改写重试 ≤ 5 次 | `datasheet-rag/SKILL.md` | 多花 token → 质量问题，软约束够 |
| 回答必须带来源引用 | `datasheet-rag/SKILL.md` | 答案没来源 → 质量问题，软约束够 |
| lark-cli 命令格式 | `feishu-doc/SKILL.md` | 命令执行失败，模型重试 → 可接受 |

硬约束的特征：**模型就算想违反也做不到**，因为能力在代码层被截断了。软约束出问题影响的是答案质量，不是系统安全或数据完整性。

## 九、哨兵字符串机制

子 Agent 遇到特殊情况时返回哨兵字符串，Handler 层通过子串匹配检测并处理：

| 哨兵 | 含义 | Handler 处理 |
|------|------|-------------|
| `__FEISHU_AUTH_REQUIRED__` | 飞书未授权 | 发 Device Flow 授权卡片 |
| `__KEYCLOAK_AUTH_REQUIRED__{url}` | Keycloak 未授权 | 发 OAuth2 登录链接 |
| `__FEISHU_AND_KEYCLOAK_AUTH_REQUIRED__{url}` | 两者都缺 | 同时发两个链接 |
| `__APPROVAL_REQUIRED__{session}||||{preview}` | 等待用户确认 | 发带预览的确认卡片 |
| `__GENERAL_FALLBACK__` | 专家 Agent 无法处理 | router.py 转发给 General Agent 重试 |

哨兵不是异常，是正常返回值，Handler 层的 if-else 分支处理各种情况。

## 十、面试核心问答

**Q：LeadAgent 为什么不持有任何工具？**
A：LeadAgent 的职责是路由决策，不执行业务操作。给它工具会导致它尝试自己完成任务而不是分发，破坏多 Agent 架构的职责分离。`allowed_tools=[]` 是物理隔离，不是靠 System Prompt 约束。

**Q：ContextVar 为什么要在 finally 里 reset？**
A：asyncio 协程可能被复用，不 reset 会让下一个请求继承上一个用户的 open_id，造成跨用户文档泄露。reset 是唯一安全的做法，try/finally 保证无论成功失败都执行。

**Q：审批网关 defer/resume 比 deny + 重发有什么优势？**
A：resume 接续之前的 ReAct 步骤，已完成的工具调用（查项目列表、确认项目 ID 等）不重跑。deny + 重发要从头执行所有步骤，既浪费 token 又慢，且中间状态丢失。

**Q：为什么 rag_search 的参数 Schema 里没有 owner_id？**
A：不能让 LLM 传这个参数，否则模型可能被诱导传其他用户的 ID，造成数据泄露。从 ContextVar 读是唯一安全路径，物理上就不存在这个参数，模型无法伪造。

**Q：为什么同时用 BM25 和向量检索？**
A：两路互补。BM25 擅长精确型号匹配（LQG15HH6N8J02D 这种字符串），向量检索擅长跨语言语义理解（"工作温度" = "operating temperature"）。RRF 融合只看排名不看绝对分数，实现简单、效果稳健。

**Q：文档切分为什么不用固定字符滑窗？**
A：Datasheet 里表格是主要信息载体，固定字符切会断行或丢表头，导致模型拿到数据但不知道哪列是什么参数。按内容类型分三条路（文本段落聚合、表格整表优先按行切、图片单独成块）保留了文档的语义结构。

**Q：HTV 和 HPD 为什么不合并成一个 Agent？**
A：三个理由：① 工具集完全不同，合并后工具列表膨胀，模型选错工具概率上升；② 权限隔离，两套系统的 API 访问权限互不应可见；③ System Prompt 专注领域更精准，一个 prompt 很难同时成为"项目管理专家"和"测试验证专家"。

**Q：SKILL.md 是软约束，流程会不会出问题？**
A：分两类。安全关键的约束（鉴权、Bash 白名单、审批网关、用户隔离）全在代码里强制，模型就算想违反也做不到。质量相关的约束（RAG 改写策略、来源引用格式、命令格式）在 SKILL.md 里，模型不遵守的后果是答案质量差，不是安全漏洞或数据泄露。把两者混在一起才是问题——全靠提示词不安全，全靠代码无法表达复杂的语言策略。
