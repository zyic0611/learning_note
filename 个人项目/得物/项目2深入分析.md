

**Q：请介绍一下这个 Java 抢单项目。**

A：这个项目面向暴雨防汛、大型活动等突发场景。调度人员发布有固定名额的应急工单，符合条件的环卫人员进行抢单。

原链路需要在 MySQL 中完成资格、工单状态、重复抢单和剩余名额校验，再扣减名额并写入抢单记录。高并发时会产生数据库连接池压力和热点行锁竞争。

我主要负责抢单链路优化：使用 Redis Lua 原子完成资格校验、防重复和名额预扣；预扣成功后通过 RabbitMQ 异步落库；使用 MySQL 联合唯一索引、Publisher Confirm、手动 ACK、死信重试、Outbox 补发和库存对账保证可靠性。优化后核心接口 QPS 从 474 提升到 886，最终本机 200 并发下达到 1123 QPS，P99 为 375ms，压测中无超卖、5xx 和连接池超时。

**Q：为什么使用 Redis Lua？直接先查库存再 DECR 有什么问题？**

A：GET 和 DECR 单条命令虽然原子，但“校验资格、判断重复、检查库存、扣减库存”这一组操作并不原子，存在 Check-Then-Act 竞态，可能导致超卖。

Lua 把完整抢单判断放在 Redis 服务端一次执行，中间不会穿插其他请求。单独使用 DECR 后判断负数可以处理简单库存，但无法同时保证资格、状态和防重复校验的原子性。

**Q：Lua 脚本具体做什么？Redis 使用了哪些数据结构？**

A：脚本依次检查工人资格、工单状态、该用户是否抢过以及剩余名额是否大于 0。全部通过后扣减名额，并把抢单状态写为 `PROCESSING`。

`worker:{workerId}` 使用 Hash 保存工种、区域和资格状态；`task:{taskId}` 使用 Hash 保存工单状态、剩余名额和截止时间；`claim:{taskId}:{workerId}` 使用 String 保存 `PROCESSING`、`SUCCESS` 或 `FAILED`。这里的防重复含义是同一用户不能重复抢同一工单。

如果使用 Redis Cluster，Lua 不直接跨槽读取全局工人 Key，而是在工单发布时生成同槽的资格标记，例如 `eligible:{taskId}:{workerId}`，让资格标记、工单和抢单状态使用相同的工单 Hash Tag。


**Q：Redis 预扣成功，但 RabbitMQ 发送失败怎么办？**

A：Lua 预扣时会记录事件 ID 和 `PROCESSING` 状态，应用随后把同一事件写入 Outbox，初始状态为 `SENDING`。Confirm 超时或发送失败时，定时任务会扫描超时记录并补发；收到 Broker Confirm 后再更新为 `SENT`。

如果消息其实已经到达 Broker，只是 Confirm 丢失，补发会产生重复消息，所以消费端必须幂等。

**Q：Redis 预扣后，应用在写 Outbox 前宕机怎么办？**

A：Redis 和 MySQL 不能使用同一个本地事务，所以这里存在短暂的不一致窗口。对账任务会扫描 Redis 中长时间处于 `PROCESSING`、但 Outbox 和 MySQL 都没有对应事件的孤儿预扣，随后回滚名额和用户抢单标记。

这不是强一致方案，而是通过状态记录、补发和对账实现最终一致性。

**Q：RabbitMQ 为什么可能重复消费？如何保证消费幂等？**

A：消费者可能已经提交数据库事务，但在 ACK 前宕机或 ACK 丢失，Broker 会重新投递消息。

入口 Redis 防重解决用户重复提交；消费端可以用 `consume:{eventId}` 做快速过滤，但最终依靠 MySQL 的 `(task_id, worker_id)` 联合唯一索引和数据库事务兜底。

消费者先插入抢单记录，再扣减 MySQL 名额，两步必须处于同一个事务。重复消息插入时触发唯一键冲突，不再重复扣减名额。

**Q：加入 Redis 消费标记是否有用？**

A：有用，但它只是性能优化，不能代替数据库幂等。`claim:{taskId}:{workerId}=PROCESSING` 是入口抢单状态，不能代表消息已经消费；消费完成可以单独记录 `consume:{eventId}=DONE`。

`DONE` 必须在数据库事务提交后设置。如果提交后、写 Redis 前宕机，消息会再次投递，由 MySQL 唯一索引兜底。

**Q：为什么必须在数据库事务提交后再手动 ACK？**

A：如果先 ACK，RabbitMQ 会删除消息；随后数据库失败或应用宕机，就会出现消息已消费但业务未落库的假消费。

正确顺序是执行数据库事务、提交成功、再手动 ACK。提交后 ACK 前宕机可能造成重复投递，但可以通过消费幂等解决。相比消息丢失，我们允许重复，再通过幂等保证正确性。

**Q：Redis 预扣成功，但消费者发现 MySQL 名额已经为 0，怎么办？**

A：正常情况下不应该发生。Redis 先预扣、MySQL 后异步扣减，所以 Redis 剩余名额应该始终小于或等于 MySQL 剩余名额。

消费者仍会执行 `UPDATE ... SET stock = stock - 1 WHERE stock > 0` 并检查影响行数。如果为 0，说明初始化、重复扣减或其他写入口破坏了一致性。此时回滚当前事务，将事件转入异常补偿，标记抢单失败并触发对账，不能无限重试。

**Q：工单发布后，如何把状态和名额加载到 Redis？**

A：采用发布前预热。先在 MySQL 中创建待发布工单，再把资格条件、工单状态和初始名额加载到 Redis；初始化成功并校验后，最后把工单切换为可抢。Redis 初始化失败时不开放抢单，由任务重试。

**Q：为什么抢单库存不能完全使用普通旁路缓存？**

A：普通旁路缓存适合查询数据，但抢单库存还是实时并发控制状态。Redis 预扣后，MySQL 可能还有消息没有消费，二者会短暂不一致。

如果库存 Key 丢失后直接从 MySQL 懒加载，可能把尚未落库的预扣名额重新放出，导致超卖。因此库存采用发布时预热、统一 Lua 修改和对账恢复；普通工单详情等读数据才使用旁路缓存。

**Q：Redis 宕机或库存 Key 丢失怎么办？能否直接从 MySQL 恢复？**

A：Redis 通过主从和故障切换提高可用性，但异常时不会降级为直接访问 MySQL 抢单，而是失败关闭，暂时返回系统繁忙或不可抢，并触发告警和恢复任务。

不能直接用 MySQL 当前名额回填，因为队列中可能还有未落库消息。恢复时先暂停抢单，再结合初始名额、MySQL 已成功记录和 Outbox 中的待处理事件计算真实库存，或者等待消息消费完成后重建 Redis，校验通过再开放。

**Q：消费者一直失败，为什么不能无限立即重试？**

A：无限立即重试会形成消息热循环，持续占用消费者线程、CPU 和数据库连接；参数错误等永久性异常也不会因为重试而恢复，还可能影响正常消息。

失败消息进入带 TTL 的重试队列，TTL 到期后通过死信交换机重新路由到业务队列，并在 Header 中记录重试次数。超过三次后进入最终 DLQ，同时通过钉钉或企业微信告警，由人工检查。

**Q：失败消息转入重试队列时，原消息什么时候 ACK？**

A：先确认失败消息已经可靠投递到重试队列，再 ACK 原业务消息。如果先 ACK、后投递，而重试消息发送失败，就会丢失原消息。

**Q：Publisher Confirm 能保证什么？**

A：它只能确认生产者发送的消息是否到达并被 Broker 接收，不能说明消息已经被消费者处理，更不能说明数据库已经落库。

Publisher Confirm 保护生产者到 Broker；数据库事务提交才代表业务处理成功；消费者 ACK 只是通知 RabbitMQ 可以删除消息。

**Q：收到 Publisher Confirm ACK，是否一定说明消息进入了队列？**

A：不一定。如果交换机存在，但 Routing Key 没有匹配任何队列，Publisher Confirm 仍可能返回 ACK。需要开启 `mandatory` 并通过 Return Callback 感知无法路由的消息。

**Q：RabbitMQ 消息可能在哪些阶段丢失？**

A：生产者到 Broker 阶段使用 Publisher Confirm 和 Outbox 补发；路由失败使用 `mandatory` 和 Return Callback；Broker 存储阶段使用持久化交换机、持久化队列和持久化消息；消费阶段在数据库事务提交后手动 ACK，并通过唯一索引处理重复投递。

**Q：为什么 Redis 和 RabbitMQ 能提升 QPS？**

A：Redis Lua 把多次 MySQL 查询和热点行更新变成一次服务端原子操作，减少网络往返、数据库连接占用和行锁竞争。

RabbitMQ 把抢单受理与业务落库解耦，接口不再同步等待完整数据库事务。异步化没有消除数据库写入，而是把压力转移到了消费者和数据库异步写入链路。

**Q：优化后的性能瓶颈可能在哪里？**

A：可能转移到 Redis 热点 Key 和 Lua 执行能力、RabbitMQ Broker 吞吐、消费者 TPS、MySQL 最终写入能力以及消息积压。1123 QPS 表示接口受理能力，不代表数据库每秒完成 1123 条落库。

**Q：QPS 474、886、1123 和 P99 375ms 是如何压测的？**

A：使用 JMeter 设置 200 个并发线程，Ramp-up 为 20～30 秒，先预热约 30 秒，再稳定压测 3～5 分钟。提前准备库存充足的工单以及大量符合资格、不重复的 `workerId + taskId` 数据，保证请求经过完整受理链路，避免库存售罄后大量请求快速失败导致 QPS 虚高。

在相同环境、数据和并发下分别测试 MySQL 同步链路、Redis Lua 链路和 RabbitMQ 异步链路，并对比 QPS、平均 RT、P95、P99、5xx 和连接池状态。异步版本还要观察消费者 TPS、最大消息积压和最终清空时间。

**Q：200 人抢 10 个名额的测试能否用来证明 1123 QPS？**

A：不能。前 10 个请求成功后，其余请求会快速返回售罄，这个 QPS 主要反映拒绝能力。

该场景只用于验证并发正确性；性能测试必须准备足够库存或多批工单，让绝大部分请求经过完整抢单链路。

**Q：使用很多库存充足的工单，会不会避开真实热点竞争？**

A：会，所以要分场景测试。单热点工单使用充足库存，保留对同一 Redis Key 或 MySQL 行的竞争；多工单混合请求测试系统整体吞吐；200 人抢 10 个名额只验证超卖和防重复。三个版本的性能数据必须来自相同的热点程度和测试口径。

**Q：如何证明压测中没有超卖和重复记录？**

A：200 个不同用户同时抢 10 个名额，等待消息消费完成后核对：接口最终成功数为 10、Redis 名额为 0、MySQL 有效抢单记录为 10、按 `task_id + worker_id` 分组不存在重复记录、RabbitMQ 最终无积压。

性能测试还要核对接口受理总数、Outbox 记录数、MySQL 最终落库数和失败补偿数，确认性能提升没有牺牲正确性。

**Q：大量用户抢同一个工单，热点 Key 会不会成为瓶颈？**

A：会。首先保证 Lua 只执行 O(1) 的资格、防重复和库存操作，不遍历大集合；其次在网关或应用层限流，售罄后使用短期本地标记快速拒绝，避免继续访问 Redis。

流量确实超过单分片能力时，可以把总名额预分配到多个库存桶，并根据 workerId 稳定路由。各桶名额总和等于总名额，但分桶会增加防重复、库存利用和回收复杂度，因此不是首选方案。

**Q：Redis Cluster 能否自动解决单个热点 Key？**

A：不能。Redis Cluster 只能把不同 Key 分配到不同分片，单个 Key 仍然只属于一个分片。要分散单工单热点，必须在业务层做库存分桶，同时处理全局防重复和剩余名额回收。

**Q：Redis Cluster 中，Lua 同时操作多个 Key 有什么限制？**

A：同一个 Lua 脚本访问的多个 Key 必须位于同一个 Hash Slot，否则会出现 `CROSSSLOT` 错误。可以使用 Hash Tag，例如 `task:{123}`、`claim:{123}:456`，让同一工单相关 Key 落到同一槽位。

这样能够保证单工单 Lua 原子性，但也意味着同一工单的请求集中在一个分片，所以 Hash Tag 解决的是跨槽执行问题，不是热点问题。
