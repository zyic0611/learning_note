**Q：整条 NL2SQL 链路怎么走？**

A：用户问题先经过领域判断、槽位提取、指代消解和多轮条件补全，得到结构化查询；主图根据它完成 Schema Linking、Join Graph 补全和 QueryPlan 生成，然后生成 SQL。SQL 通过 AST 安全校验、QueryPlan 语义校验和 EXPLAIN 成本检查后才进入数据库，失败则分类修复，最后把结果整理后通过 SSE 返回。

**Q：LangGraph 中有哪些节点，State 保存什么？**

A：主图包括领域判断、域外回答、追问快路径、ReAct Agent、工具执行和结果整理；NL2SQL 子图包括 Schema Linking、QueryPlan、SQL 生成、安全与语义校验、EXPLAIN、SQL 执行和反思重试。

State 保存 Messages、结构化问题、Session Slot、候选 Schema、QueryPlan、SQL、错误类型、重试次数、Token 用量和结果引用。各节点读取共享 State，只返回自己更新的字段，便于条件路由、循环重试和 Checkpoint 恢复。

**Q：为什么选择 LangGraph，而不是普通 Python 工作流？**

A：普通 Python 也能实现，但项目存在多分支、循环重试、子图调用和会话恢复，LangGraph 可以把节点和条件边显式表达，并通过 State 统一管理上下文。Checkpoint 支持中断恢复，`astream_events` 也方便通过 SSE 展示进度。

它的代价是增加 State、Reducer、条件边和 Checkpoint 的学习及调试成本。它不会让路由本身更智能，核心价值是把复杂分支、循环和状态恢复工程化。

**Q：业务槽位是用 LLM 还是规则提取？**

A：我们采用 LLM **结构化抽取为主、规则和业务词典校验为辅**。LLM 负责识别指标、维度、时间、地域、企业以及多轮指代，再按照固定 JSON Schema 输出；规则负责把“去年”转成具体时间范围，把地区和企业名称映射成标准编码。

核心槽位缺失或口径存在歧义时，不直接生成 SQL，而是向用户澄清。

**Q：多轮对话的条件继承、覆盖和清空怎么实现？**

A：我们把时间、地域、指标、企业等条件保存在 Redis Session Slot 中。新一轮问题只更新明确提到的槽位，其他条件默认继承；“换成去年”属于覆盖，“不要地区限制”属于清空。规则负责明确表达，LLM 结合上下文处理指代和模糊追问，最后输出受约束的状态变更。

**Q：固定 Slot 会不会覆盖不了新的业务条件？**

A：Slot 固定的是指标、维度、时间、地域、企业等核心结构，具体值是动态的；**长尾条件通过通用 `filters` 表达。同时保留原始 Query** 参与 Schema Linking，避免结构化抽取遗漏后信息完全丢失。确实无法映射的新概念会触发澄清，再补充到语义层和回归集。

**Q：Checkpoint 和 Redis Session Slot 有什么区别？**

A：Session Slot 是业务状态，保存用户当前的时间、地域、指标、企业和历史结果引用，跟随会话并设置 TTL。Checkpoint 是工作流状态，保存 LangGraph 的 Messages、当前路由、QueryPlan、SQL、错误和重试次数，通过 `thread_id` 用于中断恢复和故障续跑。

一句话说，Session Slot 保存“用户想查什么”，Checkpoint 保存“工作流执行到哪里”。

**Q：追问快路径缓存的是什么？**

A：Redis 会缓存上一轮查询结果及字段元数据。用户继续做排序、筛选或趋势总结时，如果现有结果已经包含所需字段，就直接复用，不再重新生成和执行 SQL；所需字段不完整时再走完整的 NL2SQL 链路。

**Q：多轮任务完成率从 33% 提升到近 90% 是怎么评测的？**

A：我们维护了约 100 段固定的多轮回归用例，每段 3～8 轮，覆盖时间、地域、指标切换以及条件继承、覆盖和清空。每轮都标注预期槽位、SQL 条件和数据结果。

评测时从空 Session 完整执行，关键轮次全部正确才算整段任务完成。确定性结果用规则比较，趋势总结等开放内容以人工评测为主、LLM Judge 为辅。优化后任务完成率由约 33% 提升到接近 90%。

**Q：QueryPlan 和 Schema Linking 谁先执行？**

A：先做前置问题理解，再做 Schema Linking，最后生成完整 QueryPlan。前置层输出的是不包含物理字段的 `SemanticQuery`，例如指标是“中标金额”、维度是“区域”；Schema Linking 找到具体表字段并补齐 Join 路径后，才生成绑定物理字段的 QueryPlan。

完整顺序是：原始问题 → 问题理解和多轮条件补全 → SemanticQuery → Schema Linking → Join Graph → QueryPlan → SQL 生成和校验。

**Q：环卫业务语义层是怎么组织并注入 Prompt 的？**

A：我们在物理 Schema 之上维护四类元数据：表字段描述、业务术语与同义词、指标计算口径、表关联关系。这些元数据存储在 MySQL，并加工成 BM25 文本和 BGE 向量。

用户查询时只召回相关的字段、口径和 Join 路径，以结构化形式注入 Prompt，而不是把全量 DDL 都塞进去。语义层的作用就是把“流标”“保洁作业面积”等业务语言映射到明确的物理字段和计算口径。

**Q：Schema Linking 为什么使用 BM25 + Vector 双路召回？**

A：Vector 擅长处理语义相近但字面不同的表达，BM25 擅长企业名、字段缩写和业务关键词的精确匹配，两路能力互补。我们分别召回后用 RRF 融合，兼顾语义召回和关键词召回。

**Q：向量召回使用什么模型，为什么选择它？**

A：我们使用 BGE-M3 的 Dense Embedding 能力，把表名、字段名、字段描述和业务口径编码成 1024 维向量，再按余弦相似度检索。选择它主要是因为中英文支持都比较好，适合中文业务描述和英文物理字段混合的场景。

我们没有做领域微调，主要是高质量 Query-Schema 正负样本不足，而且通过补充同义词、字段描述和业务口径，回归效果已经能够满足需求。

**Q：BM25 的原理是什么？**

A：BM25 可以理解为对 TF-IDF 的改进，综合考虑词频、词的稀有程度和文档长度。它对词频做了饱和处理，避免某个词出现很多次就获得过高分数，同时做长度归一化，避免长文本天然占优。

**Q：BM25 的中文分词怎么处理？**

A：我们维护了环卫招投标领域的自定义词典，保护“保洁作业面积”“中标金额”“服务期”等完整业务词，同时保留必要的细粒度词和同义词。最小检索 Chunk 以字段为单位，但会携带表名、字段描述、业务别名和指标口径；BM25 漏掉的语义表达再由向量召回补充。

**Q：两路各取 Top 多少，RRF 后取 Top 多少？**

A：BM25 和向量召回分别取 Top 20，RRF 融合、去重后保留 Top 10，再通过 Join Graph 补齐必要的中间关联表。这个参数是在内部回归集上对比得出的，候选太少容易漏召回，太多又会增加 Token 并干扰模型选表。

**Q：为什么用 RRF，而不是直接把 BM25 和向量分数相加？**

A：BM25 分数和余弦相似度不在同一个数值空间，直接相加容易让某一路长期占优。虽然可以归一化后加权，但需要持续调参。RRF 只使用排名，不依赖原始分数范围，实现简单且更稳定。

RRF 的缺点是会丢失原始分数差距，也不理解业务语义，所以融合后还需要表级聚合、业务口径匹配和 QueryPlan 约束完成去歧义。

**Q：RRF 里的 k 有什么作用？**

A：RRF 的公式是各路 `1 / (k + rank)` 之和，k 用来平滑头部排名的优势，我们使用常见经验值 60。两路都靠前的候选通常得分最高，但只在一路靠前的候选也有机会保留。

**Q：Schema 召回是整表级还是字段级？同名字段怎么去歧义？**

A：我们采用“字段级召回、表级聚合、业务口径重排”。最小召回单元是字段，但字段的检索文本会携带表名、表描述、业务别名和指标口径。RRF 只负责融合排名，之后再结合所属表、指标口径和问题中的时间、维度进行重排。

例如“中标金额”可能同时召回预算金额和实际中标金额，但语义层会把它优先映射到 `bid_result.win_bid_amount`，再通过 Join Graph 补齐区域表等关联表。

**Q：Join Graph 是什么，怎么补全跨表路径？**

A：Join Graph 的节点是表，边是主外键或业务关联关系，边上保存关联字段、方向、Join 类型和权重。Schema Linking 命中多张表后，我们在图上查找最短路径，把中间表和 ON 条件补充进 Prompt，避免模型自己猜 Join 关系。

**Q：Join Graph 在内存中用什么数据结构？**

A：我们使用 Python 邻接表，Key 是表名，Value 是关联边列表。普通关系用 BFS 找最短路径；存在多条带权路径时优先选择主外键明确、路径更短的方案。Schema 规模不大，没有必要额外引入 NetworkX。

**Q：Schema 和知识库的文本、向量分别存在哪里？**

A：Schema 的完整文本和元数据存储在 MySQL，向量和 Schema ID 存在 FAISS。FAISS 是向量检索库，不是完整的向量数据库。Schema 只有几百到一千个检索单元、更新不频繁，所以使用 FAISS 做版本化全量替换更轻量。

知识库的文档量更大，还需要在线更新和元数据过滤，所以使用 Milvus 管理 Chunk 向量及检索元数据，原始文档和业务信息仍保存在 MySQL 或对象存储中。两类索引分开管理，避免不同 Chunk 粒度和检索参数相互影响。

**Q：为什么 Schema 使用 FAISS，知识库使用 Milvus？**

A：Schema 只有少量字段级检索单元，更新不频繁，而且我们采用全量重建、版本切换和快速回滚，FAISS 更简单。知识库文档量更大，需要频繁增删、元数据过滤和多实例访问，所以使用 Milvus 更合适。

两者即使使用同一个 BGE 模型，也会使用独立索引，因为 Schema 和文档的 Chunk 粒度、Top-K、过滤条件及更新频率都不同。

**Q：Schema 变化后，BM25 和 FAISS 索引怎么更新？**

A：我们采用版本化全量替换。表字段、同义词或指标口径发生变化后，后台基于最新元数据全量构建新版 BM25 和 FAISS 索引。校验通过后通过 Redis 通知各服务实例加载，并原子切换到新版本；旧版本会保留，出现问题可以快速回滚。

**Q：Schema Linking 从 71% 提升到 95%+ 是怎么评测的？**

A：内部回归集共有 800 多条问题，其中约 200 条是 Schema Linking 专项用例。数据来自测试人员整理、脱敏后的线上反馈，以及 AI 同义改写；AI 扩充内容会经过人工审核、去重和口径校验。

每条专项用例都会标注正确的核心表和字段。优化前后全量运行同一套回归集，在 Top 10 候选范围内，只有核心 Schema 全部覆盖才算完整命中，完整命中率从 71% 提升到了 95% 以上。这个数字是内部工程回归指标，不代表独立测试集上的泛化准确率。

**Q：Prompt Token 降低 17.3% 是怎么测的？**

A：我们在固定的 Schema Linking 回归集上做对照。基线方案不做 Schema Linking，把全量相关表 DDL 注入 SQL 生成 Prompt；优化后只注入召回的 Top 10 字段、所属表和必要 Join 关系。

两组使用相同模型和 Prompt 模板，通过接口 Usage 统计 SQL 生成节点的平均 `prompt_tokens`，最终降低 17.3%，同时保证 Schema 完整命中率达到 95% 以上。

**Q：QueryPlan 具体包含哪些内容？**

A：主要包含指标字段、聚合方式、查询维度、过滤条件、时间字段和范围、候选表、Join 路径、排序和 Limit。它先固定用户的业务意图，再约束 SQL 生成和后续语义校验。

例如“去年上海市各区中标金额总和”，QueryPlan 会明确中标金额对应的物理字段、聚合方式为 SUM、按区域分组、时间范围为去年，以及需要使用的表和 Join 条件。

**Q：QueryPlan 语义一致性校验具体检查什么？**

A：SQLGlot 解析成功只代表 SQL 结构基本合法，不代表业务语义正确。我们会从 AST 中提取表和字段、聚合函数、Group By、Where 时间条件以及 Join 条件，再与 QueryPlan 逐项比较。

例如要求 SUM 却生成 AVG、要求按区域分组却缺少 GROUP BY，或者使用了错误的时间字段，这些 SQL 虽然能执行，但结果是错的，会在执行前被拦截并定向修复。

**Q：SQL 失败后的自修复怎么做？**

A：我们先对错误分类：语法或字段错误、QueryPlan 语义不一致、安全和成本超限，以及用户信息不足。前三类会把具体错误、上一版 SQL 和候选 Schema 交给模型定向修复；缺少业务信息时不盲目重试，而是要求用户澄清。

自动修复最多三次，并记录错误类型和 SQL 指纹。如果连续生成相同 SQL 或重复相同错误，就提前终止。查询结果为空时保留用户原始条件，提示没有结果并给出放宽条件的建议，不擅自修改查询口径。

**Q：线上最常见的失败是什么？你排查过什么问题？**

A：常见问题主要是 Schema 或业务口径选错、多轮槽位混乱，以及 LLM 超时或慢 SQL。早期多轮追问中，经常出现时间、地域条件错误继承或互相覆盖。

我对比 Redis 中每轮 Slot 快照和 Trace 日志，发现原来每轮都让模型重新生成完整 Slot，系统又分不清空值表示继承还是清空。后来改成 `KEEP`、`SET`、`CLEAR` 三种增量操作，并用规则校验时间和地域，最终多轮任务完成率从约 33% 提升到接近 90%。

**Q：SQL 只读校验能覆盖子查询吗？**

A：可以。我们使用 SQLGlot 递归遍历 AST，只允许 SELECT，并检查所有子查询节点、表白名单和危险函数。即使应用层漏掉风险，数据库仍使用只读账号作为最后一道防线。

**Q：EXPLAIN 扫描行数阈值怎么确定？**

A：阈值是根据业务表规模和压测时的 P99 延迟反推的。单表百万级数据时，预估扫描超过 50 万行触发风险提示，超过 200 万行直接拦截。除了扫描行数，还会结合是否命中索引、Join 类型和是否出现笛卡尔积判断成本。

**Q：熔断机制怎么做？**

A：一层是故障熔断，LLM 连续超时或报错达到阈值后打开熔断器，冷却后进入半开状态探测恢复；另一层是成本守卫，单次请求 Token 或模型调用次数超限后，基于已有结果提前结束，避免继续消耗资源。

**Q：SSE 怎么推送执行进度？**

A：FastAPI 使用异步生成器消费 LangGraph 的 `astream_events`，把节点进入、退出和模型输出转换成 SSE 事件。前端可以实时看到“Schema Linking”“SQL 生成”“执行查询”等进度和最终 Token 用量。

**Q：SSE 断开后，后台任务怎么处理？**

A：当前没有实现基于 `Last-Event-ID` 的无缝续传。FastAPI 检测到连接断开后会取消图任务，停止后续 LLM 调用和重试；已经发出的请求只能尽力取消，SQL 还会通过超时和连接释放控制资源。

用户重新请求时，可以通过相同 `thread_id` 从最近的 Checkpoint 做有限恢复。完整重连方案需要把任务与 SSE 解耦，并增加 Redis 事件缓存和事件回放。

**Q：OpenTelemetry 怎么接入 LLM 调用？**

A：我们对 LLM 调用做了统一封装，在封装层创建 Span，把模型名、耗时、重试次数以及 `prompt_tokens`、`completion_tokens` 写入 Attributes，再上报到 OpenTelemetry Collector。这样可以通过 Trace ID 串联一次请求的模型、Redis、MySQL 和 LangGraph 节点。

**Q：Trace ID 如何串联 LLM、Redis、MySQL 和 LangGraph 节点？**

A：每次 HTTP 请求对应一个 Trace ID。FastAPI 创建根 Span，LangGraph 核心节点和 LLM 封装层创建子 Span，Redis 和 MySQL 通过自动埋点继承当前 Trace Context。结构化日志也注入 Trace ID 和 Span ID，因此可以还原整次请求的模型调用、缓存访问、SQL 执行和重试过程。

Trace ID 串联一次请求，Session ID 串联多轮对话，Thread ID 串联 LangGraph State 和 Checkpoint。

**Q：数据库有多少表和数据？**

A：业务库大约有四五十张表，但 Agent 只开放二十多张白名单核心表，包括项目、标段、公告、中标结果、企业和区域等。核心业务数据总量是千万级，单张事实表是百万级，最大的公告或标段表大约两三百万行。

Schema Linking 检索的是字段元数据，不是千万行业务数据，加工后只有几百到一千个字段级文档。

**Q：数据量扩大十倍，最先出现什么瓶颈？**

A：如果只是业务数据行数扩大十倍、表结构不变，最先出现瓶颈的是 MySQL 的跨表 Join、Group By 和趋势分析，不是 FAISS。我们会先优化联合索引、时间分区、只读副本、缓存和预聚合；达到近亿级并以分析查询为主时，再把统计链路迁移到 ClickHouse 或 Doris。

我不会一开始就分库分表，因为跨分片聚合会让 NL2SQL 更复杂。只有 OLTP 写入、存储或连接能力达到单机瓶颈，并且存在明确分片键时，才考虑分库分表。




**Q：这个项目最难的技术点是什么？**

A：最难的是前置问题理解和业务语义对齐。问题一旦理解错，后面的 Schema、QueryPlan 和 SQL 都会跟着错。我们通过结构化槽位、业务语义层、多轮回归集和线上失败案例回流，逐步降低这类级联错误。

**Q：如果重新做一次项目，你会改进什么？**

A：第一，更早建立并版本化回归集，同时额外冻结一套独立测试集，降低针对回归用例调优的风险；第二，为 Session Slot 增加版本栈，支持“回到刚才的查询”这类撤销操作；第三，随着 Schema 规模扩大，再评估独立向量数据库和增量索引方案。

**Q：被问到项目数据来源时怎么回答？**

A：准确率和任务完成率来自固定的内部回归环境；性能指标来自压测环境。线上规模和压测环境存在差异，所以这些数据主要用于同环境下比较优化前后的相对效果。
