## 工作记忆 

**原理对标：** 类似于后端架构中的 Session 缓存或 Redis 热点数据，或者是程序的 RAM。

**核心实现：** **AgentState.messages** + **LangGraph Checkpoint**

**运行机制：** 工作记忆保存的是**最近几轮的原始对话（Raw Messages）**，包括用户的提问、LLM 的回复以及 Tool（工具）的原始调用结果。在 LangGraph 中，状态（State）在图的节点（Nodes）之间流转，`messages` 列表会不断 append 新的消息。

**Checkpoint 的作用**：LangGraph 的 Checkpointer（如 `MemorySaver` 或基于数据库的 Saver）会在每个节点执行完毕后，拍下一个“快照”。这使得 Agent 能够在多轮对话中保持“当前正在做什么”的专注度，甚至支持**人机协作（Human-in-the-loop）**——中断执行等待用户确认后，再从 Checkpoint 恢复工作状态。

**工程意义**：这是 Agent 能够进行多步推理（ReAct）的基础，保证了短期交互的极致精确。但它的致命弱点是：随着对话增加，上下文会迅速膨胀，导致 Token 溢出或 API 成本飙升。

## 情节记忆

**原理对标**：类似于后端将海量原始日志（Log）定期进行 MapReduce 聚合分析，生成摘要后冷备。

**核心实现：** 是通过 LLM 生成的**业务背景摘要** (Summary)

**运行机制**：为了解决工作记忆无限膨胀的问题，我们需要设计一个“垃圾回收”或“压缩”机制。当 `messages` 列表的长度或 Token 数量达到阈值时，触发一个专门的 Summarize 节点。该节点会调用 LLM，让其阅读之前的对话记录，并提炼出核心的**业务背景、用户意图或已确认的条件**。

**状态更新**：生成摘要后，系统会将这个摘要写入 `AgentState` 中的 `summary` 字段，并**清空或截断**大部分的旧 `messages`，只保留最新的 1-2 轮对话。

**工程意义**：用极少的 Token 保留了长期的对话背景（例如：“用户正在排查一个工业环卫系统的并发问题”），防止 LLM 在后续任务中“失忆”或偏离业务主线。

## 产物记忆

**原理对标**：类似于业务系统中的 MySQL 数据库或结构化 SaaS 业务数据，强调数据的**确定性**与**可复用性**。

**核心实现**：**可复用的结构化结果**（如通过 Tool 查询出的行数据、生成的 JSON、提炼的 SQL 语句）。

**运行机制**：在执行特定任务（如 NL2SQL 查询、调用外部 API）时，Agent 会获取到精确的数据（如查询到的表格数据、用于渲染图表的图表配置）。这些数据**绝不能**仅仅以自然语言的形式混杂在对话列表中，因为 LLM 在长文本中容易发生“幻觉”，篡改或遗忘精确的数字。

**状态设计**：在 LangGraph 的 `AgentState` 中，除了 `messages` 和 `summary`，通常会定义专门的结构化字段，例如 `chart_data: dict` 或 `queried_rows: list`。当 Tool 节点执行完毕后，直接将清洗后的结构化数据赋值给这些字段。

**工程意义**：实现了**自然语言处理与业务数据的解耦**。前端 UI 或下游组件可以直接读取这些结构化的“产物记忆”进行图表渲染或系统入库，整个过程不需要 LLM 再进行二次解析，保证了业务侧100%的绝对可控。
