**工具消息压缩**与**对话摘要修剪**，正是业界解决长文本上下文的标准工程范式。 在 LangGraph 的状态流转中，如果不做干预，`AgentState.messages` 会像滚雪球一样无限膨胀。这两层压缩在架构上分属不同的生命周期：

## 工具消息压缩 Tool Message Compression

**压缩原理**：这是一种**无损语义替换**。当 Tool（例如数据库查询节点）返回了 500 行的 JSON 数据时，如果在 `tools → agent` 之间直接将这些数据塞入 `messages`，会瞬间榨干 Token 并干扰 LLM 的注意力。因此，我们在路由节点拦截这个返回，将其替换为**元信息 (Metadata)**（例如：“共 500 行，列名：date, revenue, user_id”）。

**架构协同**：此时，那 500 行真实的 JSON 数据必须被存入类似 `AgentState.queried_data` 的业务字段中（即**产物记忆**）。LLM 靠元信息知道“数据已就位”，而前端渲染组件则绕过 LLM，直接从产物记忆中读取数据绘图。

## 对话摘要修剪 (Summarization & Message Pruning)

**物理修剪 (Pruning)**：这是最暴力的数组截断操作。当 `messages` 列表长度超过设定阈值时，系统会直接**物理删除**最旧的 N 条消息，仅保留最近的（如最后 2 条）交互记录，确保短期工作记忆的高度聚焦。

**对话摘要 (Summarization)**：单纯的物理删除会导致 Agent 彻底“失忆”。因此，在删除前，必须触发一个 Summarize 节点，让 LLM 充当“书记员”，对即将被删除的对话进行**有损压缩 (Lossy Compression)**，提取出核心意图，并追加或合并到 `AgentState.summary` 摘要字段中。  也就是提取历史信息到 情节记忆中

## 风险与工程解法

### 风险一：摘要丢失列名/口径，导致多轮追问失效

**场景重现**：

用户第一轮问“各部门的营收”，Agent 查了 `department_name` 和 `total_revenue`。随后触发了摘要，生成的 summary 仅为“用户查询了部门营收”。第二轮用户追问“帮我算一下他们的占比”，此时旧的 tool_message 已被修剪，且 summary 中没有列名，Agent 瞬间抓瞎，不知道该用哪个字段计算占比。

**解决方法** ：

常规的摘要 Prompt（如“请总结以下对话”）在数据分析场景下是失效的。你必须针对 BI 场景重写 Summarization 节点的 System Prompt，**强制要求保留元数据约束**。 建议的 Prompt 结构需包含以下指令：

1. 提取用户当前的核心分析目标。
2. **必须保留（Do Not Omit）**：已确认的数据库表名、关键列名（如 `total_revenue`）、过滤条件（如 `时间范围: 2026年3月`）。
3. 忽略具体的数值结果，重点记录**逻辑映射关系**。

### 风险二 ：阈值 6 对 BI 场景偏紧

**场景重现**：

在 ReAct 范式下，一次完整的数据查询可能包含：1(User) → 2(Agent Thought) → 3(Tool Call SQL) → 4(Tool Response Error) → 5(Agent Fix SQL) → 6(Tool Response Success) → 7(Agent Final Answer)。

如果设置 `MAX_MESSAGES_BEFORE_SUMMARIZE = 6`，意味着在 Agent 还在修复 SQL 报错（执行到第 5 步）时，系统就触发了修剪，直接把用户最初的问题（第 1 步）给删除了，导致 Agent 彻底忘记自己为什么要查表。

**解决方法：**

在 LangGraph 架构中，不能简单粗暴地按 `len(messages)` 计数，应该采用**基于交互轮次 (Turns) 或动态窗口**的策略：

1. **区分 Message 与 Turn**：人类的一句话和一个最终回复算作一“轮”。内部的 Thought、Tool Call 不应该计入外部阈值。应该设置 `MAX_TURNS_BEFORE_SUMMARIZE`，只在完整服务完用户一次请求后，才评估是否需要压缩。
2. **状态机安全锁**：在代码逻辑中加入前置判断。如果当前 `AgentState` 处于正在执行工具循环（如未输出最终结果）的阶段，强制跳过修剪节点，直到拿到确定的图表产物或最终答案后，再进入 `(summarize)` 节点进行结算清理。
