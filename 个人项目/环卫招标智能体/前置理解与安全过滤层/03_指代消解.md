## 核心原理

指代消解的本质是判断当前文本中的指代表达，与上下文中的哪个实体或事件建立引用关系。

假设在工业环卫系统的派单场景中：

- **Turn 1（历史）**：“帮我查一下昨天静安区所有超时未处理的**清运工单**。”（触发数据库查询，提取出 50 条记录）。
- **Turn 2（当前）**：“把**这些**直接派给离得最近的**外包车队**。”

对于后端的派单 API 来说，它根本不认识“这些”。指代消解的任务，就是在 Turn 2 进入核心 Agent 思考循环之前，将其在内存中静默重写（Rewrite）为：

- **重写后意图 (Resolved Intent)**：`把 [2026-03-01 静安区 50条超时未处理清运工单] 直接派给离得最近的 [外包车队]。`

## 轻量级方案 上下文拼接

这种方案不改变现有的节点编排，主要通过将历史上下文、摘要和当前问题共同输入 LLM，让模型基于上下文语义完成隐式指代解析。

使用：最近对话 摘要信息 当前提问。 完成指代回复

在请求核心agent的时候 system prompt包含全局摘要 用户当前问题原封不动的传进去

**优点**：

- **架构极简**：不需要增加额外的流转节点。
- **延迟与成本低**：省去了一次专属的 LLM 判定调用。

**缺点 幻觉与对其丢失**

当系统处于 NL2SQL 这种强 Schema 依赖的场景时，LLM 很容易在长长的 `summary` 中迷失。比如 `summary` 里同时存在“A车队”和“B车队”，用户说“给他们发个通知”，轻量级方案极容易因为注意力漂移而发错对象。



## 重量级方案 独立重写节点


**运行机制**：拦截用户的真实输入，调用一次专门调优过的轻量大模型（如 GPT-4o-mini 或 Qwen-Turbo），强制输出一个**没有任何代词、条件绝对完备的独立陈述句**。

**输入结构**：

1. `history_context`：上一轮的输出或摘要（如“TOP10 环卫项目名单及中标金额”）。
2. `raw_query`：“以他们的金额生成饼图”。

**输出流转**：该节点将输出结果 `xin w新问题 = "以 [TOP10 环卫项目] 的 [中标金额] 生成饼图"` 写入 `AgentState`。后续所有的 Tool 调用和 SQL 生成，**只看 问题`，raw_query也得传进去 否则llm生成错误新问题 没有反思的基准 保留审计的链路**。

**优点**：
  
  **绝对可控**：将“语境理解”与“业务执行（查库/画图）”完全物理隔离。一旦发生查错数据的 Bug，你可以立刻通过日志定位是“重写节点”理解错了，还是“工具节点” SQL 写错了，极大地降低了 Debug 难度。
