DDL/DML 拦截、多语句拦截以及对 MySQL 5.7 的语法兼容，在底层依赖的是 **AST (Abstract Syntax Tree，抽象语法树)** 的静态分析技术

## 是什么 正则的区别

**正则表达式（Regex）**

是基于文本字符串的字面匹配。面对复杂的 SQL（如带有嵌套注释、嵌套子查询、`WITH` 表达式、或者故意利用特殊空白符绕过的 SQL 注入），正则会极易被**绕过** 或者产生**误报 。

**AST 机制**

`sqlglot` 或 `sqlparse`  这两个是现成的python库 会将大模型生成的 SQL 文本，通过词法分析和语法分析，转换成一棵结构化的树状数据结构（即 AST）。

## 防御机制

本质上对应了 编译原理和代码静态分析的两个阶段 词法分析和语法分析

### 剥离注释

在安全工程中，有一个经典的防御原则：**“永远不要在未清洗的脏数据上做安全校验”**。

注释剥离 (`_strip_sql_comments`) 的底层概念属于**数据规范化 (Data Normalization)**。它的目的是消除输入数据中的**语法噪音 (Syntactic Noise)**，让数据暴露出原本的执行语义。

**签名绕过问题：**

假设你的系统有一个简单的白名单校验规则（比如早期的 WAF 或正则匹配）：

> **规则：** `如果 SQL 字符串中包含 "_ALLOWED_TABLE"，则放行。`

攻击者深知这一点，于是他们构造了这样的恶意 SQL： `DROP TABLE users; -- 这是一个友军请求 _ALLOWED_TABLE`

- **数据库引擎的视角：** 看到 `--` 后面的内容全部忽略，坚决执行了 `DROP TABLE users;`（删库）。
- **正则/字面量校验的视角：** 扫描字符串，发现确实包含了 `_ALLOWED_TABLE` 字符，判定为安全，放行。

**这就是典型的“认知不对齐”漏洞。** 剥离注释，就是在词法层面（Lexical Level）把人类可读、但不被机器执行的噪音强行抹掉，强制让**安全校验程序的视角**与**底层数据库执行引擎的视角**保持绝对一致。

### 节点遍历

AST是二维或者多维的树状数据结构 它剥离了空格、换行、大小写等表象，只保留代码的**真实逻辑骨架**。

我们在进行安全校验时，就不再是“查找字符串”，而是变成了**数据结构中的图/树遍历问题**（通常使用**深度优先搜索 DFS** 或**广度优先搜索 BFS** 算法）。

**拦截 `exp.Drop`**：无论攻击者把 `DROP` 写成小写 `drop`，还是在里面加了换行和无数个空格 `D R OP`（假设某种数据库方言允许），或者把它藏在极深的子查询里，**只要这棵树上被解析出了一个类型为 `Drop` 的节点**，遍历算法就会立刻抓住它并触发硬拦截。

**拦截 `exp.Star` (`SELECT \*`)**：同理，程序不是去搜字符串里有没有 `*` 号（因为 `SELECT 8 * 9` 也是合法的），而是沿着树找到代表 `SELECT` 的子节点，检查里面有没有类型为 `Star` 的对象。

## SQL 谓词注入

强制注入 `DELETED = 0` 不能简单的在字符串末尾拼接 AND deleted = 0 必须利用 AST 遍历所有的 `exp.Join` 和 `exp.Select` 节点，识别出绑定了逻辑删除的表别名，动态地在这几个子节点的 `WHERE` 子句中插入 `exp.Eq(left=..., right=0)`。
