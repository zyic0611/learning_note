

**问题**

大模型如果在非索引字段上生成了高维聚合、或者多表笛卡尔积，会导致 MySQL CPU 飙升至 100% 导致整个平台雪崩

**底层技术**

1、设置查询时间：

是利用了数据库内核的**线程级定时器机制**。一旦该查询执行超过 15 秒，MySQL 内核会直接终止该线程并向客户端抛出 `ER_QUERY_INTERRUPTED (Error 3024)`。

2、Socket读超时

这是在 PyMySQL（客户端网络层）设置的 TCP 缓冲区读取超时。它是弱超时，无法精准控制 MySQL 内部的计算开销。

双层防线在分布式架构设计中是非常标准的 **Defense in Depth（纵深防御）** 思想。



## 游标级数据截断

**技术原理**

设置 `SQL_MAX_ROWS=500`。在执行查询时，不能使用 `fetchall()` 一口气把所有数据加载到 Python 内存中（防止 OOM）。

**正确做法**

使用 `fetchmany(500)`。意识是只能读500row 如果还有剩下的1000行 也就是如果发现游标中还有剩余数据，立刻触发 `truncated = True` 标志。这个标志一起发给大模型，大模型就会知道 哦 我不能这么查 需要重新写sql语句 用limit或者聚合函数

这在 Agent 领域被称为**反向压制 (Backpressure) 与上下文窗口保护**——防止大模型因为读入几十万行表格数据而导致 Token 爆掉或思维混乱。
