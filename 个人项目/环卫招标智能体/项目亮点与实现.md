## schema linking

首先用户的问题进来后  需要走三条路径 对问题进行精简 决定出要用哪些列 再走联表闭合 决定要用哪些表。 

**路径一 BM25粗排**
把用户的问题 用正则 提取出三类token。 
- 数字
- 连续的中文
- 英文标识符
然后仅对连续的中文 使用2/3-gram 滑动窗口的方式 拆分出token。

然后事先已经对数据库环卫招标表和省份等地狱表的一共32列字段 提前建立好文档。
建立文档的方式是：每一列用 表名、列名、字段描述，一些字段同义词建立文档。
这里是不做倒排索引 用的是比较轻量化的构建文档索引   对每一列先 使用2/3-gram 滑动窗口的方式 拆分出token。 然后统计出词频 也就是token在每一列出现的次数 再计算平均文档长度 然后持久化到本地文件 这个阶段是离线进行的。

然后对用户的query  对每一个token  用 TF + IDF + 文档长度归一化打分。 最后得到列的得分排名 

**路径二 向量精排**
直接对用户的query 做embedding 
同样事先也是对32列做embedding 得到32个embedding文档。这里的列用的是列名、字段描述，一些字段同义词建立文档再转向量 没有表名。
然后用query向量 与32列 每一个都做 余弦相似度计算 


**一二路径融合策略**
 先对各自 top-k 内的分数做 min-max（除以该路最高分），再融合
 只在 BM25 top-5、不在向量 top-5 的列：向量分按 0 算，反之亦然
 融合是按加权 再得到top5排名。 比如BM25 0.4 向量检索 0.6的 加权计算后 再取 top-5，

**路径三 子串匹配 强制命中列** 
先对用户的query 归一化处理一下  去掉空格、标点、下划线、转小写。
然后遍历32列的列名 列描述 同义词 看有没有出现在这些的子串。
如果子串命中 则强行把这些列加入

如果前置语义层检索 比如意图识别之类的 命中了某些yaml规则 则同样把对应的制定列加入

加入是在前面两个路径计算后的额外加入 

**联表闭合**
发生在列检索后（BM25/向量/tag） 决定要用哪些表。
这个项目里是一个主表+3个地域表 。主表直接和维表join ，所以不需要djkstra 星形结构即可。

A 看列命中：
	根据BM25/向量/tag 如果命中了 非主表上的列 就把那一列添加进来
B 看地域意图
	在语义层检索已经命中了 地域连接规则  或者 问题子串命中了列文档 


表集合确定好后 再按照护栏 追加主表上的必须列 比如deleted projectStatus

**完整链路：**

路径一 BM25 top-5 ─┐

路径二 向量 top-5 ─┼→ 归一化加权融合 top-5 + tag 强制列

路径三 子串/规则 ─┘

↓

联表闭合（星型：主表 + 需要的维表）

↓

自动补 DELETED / ProjectStatus / Provinces|City|County

↓

输出 compact_schema压缩列结构 + join_hints连接规则

**面试模版：**

用户问题进来后，列链接分三路并行：  
BM25：query 与 32 列文档同用「正则三类 token + 中文 2/3-gram」；离线建轻量内存 BM25 索引（列 token、df、avg_dl），在线 Okapi BM25 打分取 top-5。  
向量（hybrid 模式）：query 整句 embed，与 32 列预计算 embedding 做余弦，取 top-5。  
Tag 强制：query 归一化后与列名/描述/同义词做子串匹配；语义规则命中再 boost 指定列；命中列在融合时分数兜底为 1.0，且不受 top-5 截断。  
两路检索分数各自归一化后按 0.4/0.6 融合，再与 tag 列合并。  
之后做星型联表闭合（列命中维表 + 地域 tag → 补省/市/县表），并强制补 `DELETED`、`ProjectStatus` 及对应外键列。

##  YAML 结构化语义层

原本的是把所有业务规则全量注入 token浪费 难维护 改业务口径需要动代码。
拆分为YAML后 按照用户问题 检索对应片段 反思的时候按照错误类型追加

业务规则分为六类规则职责

### 全局策略 

**内容：** 
	`DELETED=0`、禁止 `SELECT *`、时间窗、中文字段展示等执行红线。

**技术用法：**
- 生成prompt 用字符串拼接的方式 把这个执行红线信息注入给llm
- 执行前注入 在sqlglot中改写
- 执行前校验 遍历sqlglot 看有没有注入完整这些红线
**总结：** 全局策略是双轨 一部分写进prompt约束llm 一部分用AST解析 在执行前程序化注入和校验。

### 表结构规则 

内容是联表路径 字段类型 状态口径 

检索方式是 归一化后的问题走 tag匹配到 省/市/区/招标/中标

### 维度规则 

**内容：** 
	品类的映射、 企业别名、 国企民企 
**技术用法：**

- 把相关规则正文注入进prompt 是用户问题归一化后 与规则进行 **子串tag匹配**
- 静态映射：YAML 里维护一张 简称 → 检索词 的对照表，问题命中简称时，当场生成一小段操作说明 塞进 prompt。主要是用于企业别名。
- 列链接 boost   提权某些列。
- 混合检索  主要是在关键词匹配的前提下 加入向量路径 引入同义词召回能力。 给两路加权打分。 这里额外加入一个关键设计 只要关键词命中的规则 不会被向量结果挤掉 向量只做增量补充。 这个就是防止排序截断需要的列

### 指标规则 
内容是金额档位 同比/环比/占比模版 检索方式也是tag命中对应关键词

还有版本规则 Mysql5.7版本的一些不支持函数的规则 主要是在生成sql语句的时候 报错 反思的时候 把错误信息和Mysql的版本规则做关键词匹配。动态给prompt里追加规则约束。

### 列元数据目录

内容是32列数据建文档 检索方式是 BM25+向量列检索

也就是schema-linking

### 金标SQL种子 

内容是30条问答对 主要是做做 few-shot（少样本示例）告诉模型sql语句的写法结构 做的是纯向量检索。只会在第一次生成的时候注入 后续反思的时候不需要 因为反思的时候已经有上一次生成的参考了。

做法是 

- 先把这30条问题+sql语句 离线 embedding 建立向量数据库。

- 然后用户问题进来后 向量化 做余弦相似度计算
- 检索出相关的top-k条 然后把拼接进prompt。

金标SQL种子  是一条独立的RAG路线 不和规则检索混在一起。

**反思错误映射**：
将Mysql错误信息映射到规则条目中 再生成片段基础上追加特定信息。 比如未知列名 继续看表结构规则中的联表路径

## Agent 前置治理链 

### 两层编排 架构

整条链分图外和图内两段：

- 图外（进 LangGraph 主图之前）：只做「话题关联判定」
- 图内（LangGraph 状态机）：业务域判定 → 追问快路径 → 口径澄清 → 工具路由 → 工具执行 → 更新上下文 → 可选摘要压缩

先话题关联判定 看是不是新话题 这一步只有第二轮对话只有第二轮才做 决定要不要重置记忆。 

然后信息进入智能体后 先做一个业务域判断 域外直接llm问答

域内域就做一个追问快路径检测  快路径并不会跳过下一步口径澄清 是给工具调用和口径澄清提供上下文信息。一般会从情节记忆里拿信息。

下一步做上下文感知口径澄清 如果业务信息不够 则返回澄清话术 。一般分为冷启动和热追问 热追问就会寻找情节记忆里的信息 填入该轮问题缺失的部分 冷启动就是纯粹的缺少业务信息。

如果通过 则走到工具路由 看要调用什么工具 。

### 话题关联判定

仅第二轮起，决定是否重置记忆

**触发条件**

- 用户每发一条新消息，在进入主智能体图之前先跑这一步
- 首轮跳过：从会话 checkpoint 里读不到「上一轮用户问题」就不做
- 重试跳过：重试的时候 不做话题关联判定

**输入来源：**

从该会话的 LangGraph checkpoint 快照里取：

- 上一轮用户问题（从消息列表倒序找最近两条 human 消息）
- 情节记忆摘要（压缩后的业务摘要字段，可选是否带入）
- 本轮新问题

**判断**

- 调一次大模型，给它专门的判定提示词
- 典型判「相关」：追问、改图表、改时间/地域/维度、引用上一轮结果（「改成饼图」「再看上海」）
- 典型判「无关」：全新独立统计需求、从查数切到写报告、业务主题明显切换
- 要求模型只输出 JSON：`related: true/false`
- 带重试调用，并记录 token 用量

**无关后操作**

一次性清掉：

- checkpoint 里全部对话消息
- 情节记忆摘要
- 结构化上下文字段（最近口径、最近查询意图、最近结果结构、快路径标记）
- 查询结果缓存栈（产物记忆）

并通过 SSE 给前端推一条 `memory_reset` 事件，提示用户上下文已切换。

**容错策略：**

JSON 解析失败 → 保守当作「相关」，宁可多留记忆，也不误清导致图表追问断链

### 业务域判断

主图第一个节点，每轮用户问题都会经过（域内路径）。

**判断操作：**

- 再调一次大模型做二分类：是否属于「环卫招标/中标数据库查询」服务范围
- 提示词里枚举了 in-domain / out-of-domain 的典型例子
- 可带入情节记忆摘要，帮助识别「对上一轮环卫数据的追问」仍算域内
- 输出 JSON：`in_domain: true/false`

**域外路由：**

- 条件路由到「直接回复」节点
- 用专门的系统提示词 + 当前对话消息调大模型
- 不绑定任何查数/图表/报告工具，纯文本问答
- 若有摘要，会拼进系统提示作为对话背景

**容错：**

- 解析失败 → 保守当作域内，避免把合法查数请求挡在外面

### 追问快路径

快路径不会绕过下一步口径澄清，只是在状态里打一个标记，供澄清豁免和后续工具路由使用。

**判定逻辑** 不调用LLM

两个条件同时满足才命中：

1. 查询缓存栈顶有数据行（上一轮查数成功写入的产物记忆）

2. 当前问题像「基于上一轮结果的展示变换」

   ，通过关键词规则识别：

   - 直接含图表类词（饼图、柱状图、折线图、占比图…）
   - 或同时含指代词（他们、这些、上面、刚才…）+ 展示类词（图、展示、可视化、占比）

**情节记忆的联系**

快路径本身主要看产物记忆（查询栈）；情节记忆主要在下一步澄清里用。但域判定、话题判定、工具路由阶段都会读摘要，所以快路径和情节记忆是协同而不是替代关系。

### 上下文感知口径

**位置**

快路径检测之后、工具路由（主 Agent 节点）之前。

**核心机制：**

- 澄清规则来自 YAML 配置目前是两条典型业务歧义：
  1. 招标+中标同时出现但没说明要分别统计还是只看一种
  2. 提到合同额/金额/成交额但没说明是招标预算还是中标合同额
- 规则用「必须含 / 任一含 / 必须不含」三类关键词触发
- 命中第一条规则就返回预设澄清话术，本轮不进 SQL、不调工具

**冷启动：**

- 用户第一句就像「合同额是多少」，当前句和上下文都没有招标/中标/预算等口径线索
- 规则命中 → 直接返回澄清话术，结束本轮

**热追问**：

- 上下文已能推断出口径，就对特定规则做豁免（skip）
  - 金额口径不清：若上下文已确立招标/中标口径（从摘要、上一轮问题、最近查询意图、结构化口径字段推断），跳过
  - 或者：有查询缓存 +（快路径标记 或 可视化追问意图）→ 也跳过
  - 招标中标歧义：有缓存 + 可视化追问 → 跳过
- 典型场景：用户说「以他们的金额生成饼图」，当前句只有「金额」，但上一轮查的是「中标合同额 TOP10」，结合缓存和摘要后放行给工具路由

**触发澄清后：**

- 走「澄清回复」节点：把话术作为 AI 消息返回，SSE 推文本
- 不进入工具循环
- 对话条数超阈值时仍会走摘要压缩（和工作记忆修剪一致）

**三层记忆：**

- 工作记忆
  - 存储 checkpoint 里最近几轮原始 human/ai/tool 消息
  - 使用：域判定、澄清读上一轮问题、Agent 多轮推理
- 情节记忆
  - 存储：超长对话压缩后的摘要字段
  - 使用：话题判定、域判定、澄清豁免、直接回复背景、Agent 系统提示
- 产物记忆
  - 存储：查询栈 + 结构化字段（口径/意图/schema）
  - 使用：快路径检测、澄清豁免、图表工具读 latest、话题重置时一并清空

## 执行前护栏栈

#### 设计动机

大模型生成的 SQL 不可信：可能写增删改、查非白名单表、漏掉删除标记、用 MySQL 8 窗口函数。护栏栈在**任何 SQL 执行前**统一拦截/修复，形成「提示词引导 + 执行强制」双保险。

#### 实现要点

**五层顺序**：

```markdown
原始 SQL
  → ① 策略注入（语法树改写 WHERE）
  → ② 策略校验（全列查询 / 行数限制 / 年月函数）
  → ③ 只读安全检测
  → ④ MySQL 5.7 兼容（禁 CTE/窗口函数）
  → ⑤ 表白名单
  → 可执行 SQL + 警告信息
```

双层策略 采用提示词注入和 强制执行
