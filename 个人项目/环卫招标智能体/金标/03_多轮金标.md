Multi-turn金标 不是测试SQL 而是测试Agent是否理解了上下文 所以是测试 **多轮对话和上下文管理能力**

在实际开发中 用户一般不会只问一个简单的固定问题 所以golden sql的测试局限性就产生了 一般都是多轮追问 。

本质上是一个YAML文件 记录的是一整段对话。

```YAML
id: province_amount_chain

conversation:

  - user: 广东省2025年合同额是多少？
    expect:

      topic: contract_amount

      slots:
        province: 广东
        year: 2025

  - user: 浙江呢？
    expect:

      topic: contract_amount

      slots:
        province: 浙江
        year: 2025

  - user: 今年呢？
    expect:

      topic: contract_amount

      slots:
        province: 浙江
        year: 2026
```

也就是主要记录多个用户提问 期望的主题是什么 期望的slot是什么 。

主要记录的是 用户输入和**当前应该保存的状态** 



## 企业标准测试内容

### 第一类：话题Topic

判断的是后面对话的话题是否保持。 

所以第一项断言是Topic是否正确

### 第二类：槽位Slot 也是核心

当第一轮提问为：广东2025合同额

则 AgentState应为：

```markdown
province = 广东

year = 2025

metric = 合同额
```

第二轮提问为：浙江呢

则provide 必须修改为浙江 其他不变

这里只有身份被覆盖 其他全部继承

当第三轮提问为：去年呢

则年份要被覆盖

因此断言为：

slots:

province是否等于浙江

year是否等于2024

### 第三类 Context 上下文继承

很多公司会把它单独测

第一轮： 广东 2025 合同额

第二轮提问浙江呢 系统必须自动补全 2025 合同额这两个信息

所以Golden会检查  哪些字段来自用户。 哪些字段要来自继承。

### 第四类 Clarity 澄清

当遇到歧义的时候 不能乱猜。 

第一轮提问为广东合同 第二轮提问排名呢 此时排名产生歧义 则Golden应该要求

**need_clarity=true** 



## 总结

关注的是agent的思考过程 ： Topic 主题 Slot槽位 Context上下文 

检查项：

Topic 是否保持正确： 验证 Topic Segmentation 没误判新话题

Slot 是否正确继承：验证 active_context（也就是schema linking中问题理解后的槽位提取） 是否正常更新和覆盖

是否触发 Clarify：验证 Business Guardrail 是否正确识别歧义并中断执行

最终 SQL 是否符合预期：验证上下文经过继承后生成的 SQL 没有偏离用户真实意图

## 面试话术

我们除了维护单轮 NL2SQL Golden Set 外，还维护了 Multi-turn Golden Set，用于验证 Agent 的上下文管理能力。每条金标由一整段对话组成，每轮都会断言 AgentState 是否符合预期，包括 Topic 是否发生切换、业务槽位（如省份、时间、指标）是否正确继承或覆盖、是否需要触发澄清，以及最终生成的 SQL 是否与用户真实意图一致。这类金标主要用于回归测试 Agent 的记忆管理和多轮推理能力，避免修改上下文管理逻辑后导致原本正确的多轮对话能力出现退化。
