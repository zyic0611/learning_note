
## 业务特点

- Schema 固定（32列）
- 领域固定（环卫招标）
- 有明确业务口径
- 但是用户表达方式复杂

## 为什么不纯规则YAML解析

规则设定：
```
垃圾量: metric: transport_weight 
中标状态: column: project_status
```
就会走正则匹配 问题里有垃圾量 就让metric=transport_weight

优点： 稳定 可控 延迟低
缺点： 用户的问题可能表达复杂 泛化能力很差 很多东西匹配不到

## 为什么不 纯LLM Json 

比如prompt设定：
```
请解析用户问题： 
输出： 
{ metric:"",
 dimension:"",
  time:"", 
  filter:"" 
}
```

优点：语义能力很强
缺点： 
1、可能会产生幻觉 把差不多但错误的文本填上去
2、口径不稳定 同一个问题 可能解析的不一样
3、企业场景能力差 不了解企业特定一些术语

## 混合设计

 第一层 规则快速解析：
	 比如时间 地域 业务关键词 指标 快速用yaml规则解析
第二层 llm补充语义理解
	当规则无法确定的时候 调用llm 进一步理解语义

最终融合二者的json输出 并且规则优先 因为业务规则权重更大。


## 总结业务技术

在 Schema Linking 前增加 Query Understanding 层，将自然语言问题解析为结构化业务语义，降低 Schema 检索空间，并通过规则+LLM混合方式保证领域准确性。
