
工具选择的参数生成和校验 核心就是把LLM生成的候选调用 变成可执行、正确、安全的调用 不能把模型输出就直接当成事实了。

**决策链：**
	用户意图
		要不要调用工具
		调用哪个工具
		参数从哪里来 如何生成
		四层校验
		修复/澄清/拒绝/执行

## 要不要调用工具

一般按照 **信息来源 和 行动后果** 判断

优先调用工具的情况：
- 实时数据 ： 容易变化 需要最新的
- 私有数据： 一般需要内部工具去获取
- 精确计算：调用计算工具
- 外部验证： 发邮件 退款 删除文件 
- 需要验证： 有些东西不能靠猜测 必须调用工具查询后才知道

**本质上调用工具 并不是由模型会不会决定 时候由答案是否依赖外部真实状态 是有信息 或副作用决定**


## 选哪个工具

意图匹配 并不等于 名称匹配。

llm主要根据 tool 的 name + description + 输出参数的语义 来选择工具。

选择原则
- 先满足用户目标 能否完成需求
- 最小能力原则 ： 能读就不要写 能查单个资源 就不全局搜索
- 最小权限原则： 优先选择天然呆用户/租户隔离的工具
- 避免重叠工具： 多个能力相似的工具 会显著提高误选率

所以description很重要 高质量的会写清楚：
**适用场景+不适用场景+权限范围+关键限制**

## 参数生成：

有三类来源 需要区分 模型不能接触可信字段

- 用户明确提供：可以直接提取
- 可安全推导出来：必须依赖当前真实数据 时间 时区
- runtime注入：userid 权限 token  llm不可生成
- 工具内部派生 ： 内部字段映射 不可暴露给模型

## 参数校验

schema通过校验 并不代表可以执行

- Json/Schema校验 主要是校验结构对不对 看是否缺字段 类型不对 非法枚举
- 业务校验 校验业务上是否成立 比如订单不存在、不可重复退款
- 权限校验
- 安全风险校验 看是否高危操作 或者被注入的风险

schema即哦啊样只能证明 看起来是合法请求 业务 权限 安全校验才决定能不能真正的执行

##  校验失败后处理

修复、澄清、拒绝

### 自动修复
是低风险、语义唯一

适合
- 隐式类型转换
- 去掉多余空格
- 日期格式可以无歧义转换
- 参数名打大小写

不适合：
- 金额推测
- 从多个同名对象中选一个
- 自动缩小 或者扩大删除范围

### 请求澄清

缺少关键意图 澄清问题需要一次手机关键缺失项 不要逐字段盘问

### 直接拒绝

越权 危险 违反规则的行为 就算llm可以生成参数 也应该被runtime直接拒绝


## 比较好的执行流程

1. 模型提出 tool call
2. Runtime 解析 JSON
3. Schema 校验
4. 注入可信上下文（user_id / tenant_id / permission）
5. 业务校验
6. 权限与安全校验
7. 必要时要求用户确认
8. 执行工具
