

tool calling是模型根据上下文生成的 **结构化调用意图** 用Agent runtime校验 并执行真实工具 再把执行结果交给llm继续执行决策的闭环机制。

所以 **通常llm并没有直接调用工具**

一般是生成执行工具的信息。

LLM本质上是根据当前上下文输出的模型 它本身通常无法直接调用工具、函数。 因此需要工具。

LLM： 负责理解用户意图和决定下一步

Tool：负责访问真实数据库或执行真实动作。

## 工具调用的四个参与者

一个完整的工具调用系统后通常包含4个参与者：
- user
- model
- agent runtime
- tool

### user

用户负责提出目标 通常不会明确的告诉agent 调用什么api 工具。

如何finish user task 通常由agent decide。

但是用户请求不是无条件可执行的。  仍然需要检查身份、权限、风险....


### model

模型负责理解和决策  
- 用户想完成什么
- 是否要用工具
- 选择哪个工具
- 需要什么参数
- tool result说明了什么
- 是否要继续用别的工具
- 什么时候生成最终回答

llm生成的是建议行动

因为模型输出时概率性的 不能把他当成可信的权限系统或者确定性程序 所以不负责真正执行工具 鉴权 等等

### agent runtime

是连接模型与工具的中间执行系统

理解为是agent的执行内核。

负责：
- 组装模型上下文
- 调用llm
- 接受tool call
- 解析参数
- 校验schema
- 校验业务规则
- 鉴权
- 执行tool
- 保存状态
- 处理错误
- 生成tool result

### tool

是被runtime调用的确定性能力接口

可能封装：
- 本地函数
- http api
- 数据库
- 搜索引擎
- 浏览器
- 文件系统
- 另一个agent
- mcp server


## tool calling的三层架构

不只有模型生成json这一层 可以分为三层

### 协议层

协议层负责解决：
- 模型如何表达 我要调用工具
- runtime 如何表达 工具执行结果
- tool call 和 tool result 如何关联

协议层关注：
- 工具定义
- 工具调用
- 工具结果
- 调用id
- 消息顺序
- 流式参数拼接
- 多个并行调用的关联

### 执行层

解决：如何把模型生成的调用意图变成真实操作

包括：
- 工具注册
- 调度器
- 参数解析
- schema校验
- 业务检验
- 工具执行
- 超时
- 重试
- 幂等性
- 状态保存
- 异常处理

### 治理层

解决 这个操作是否允许执行 以及执行后如何追踪

包括：
- 身份认证
- 权限控制
- 风险分级
- 用户确认
- 提示词注入防护
- 数据泄漏防护
- 审计日志
- 调用预算
- 人工审批
- 安全评测

## 完整生命周期

1. runtime准备上下文
	- 系统消息
	- 开发者消息
	- 用户消息
	- 历史消息
	- 可用工具定义
	- 当前时间等运行时消息
2. 模型判断语义 选择工具 输出Tool Call （json格式
	- 叫做 Tool Selection+ Argument Generation
3. runtime **校验** 调用
	- 工具是否存在
	- 参数是否为合法json
	- 字符串参数是否为合法字符串
	- 日期参数是否为合法日期格式
	- 用户是否被允许调用该工具
	- 调用次数是否过多
	- 如果不合法可以
		- 拒绝调用
		- 返回结构化错误
		- 让llm修复参数
		- 请求用户补充信息
4. runtime 执行 工具 ：真正调用工具服务
5. 工具返回结果 一般是json格式
6. tool result进入上下文 为 
	- assistant tool call：tool name
	- tool result ： ...
7. llm继续决策 如果需要tool call 继续生成第二个tool call json格式 如果不需要 则生成最终回答

## tool definition

也就是runtime在调用模型的时候 需要告诉模型 有哪些工具可用 

json格式

一般包含 ：
- name 
- description
- input schema

有些甚至还会提供
- 返回值描述
- 风险等级
- 权限要求
- 调用成本
- 超时时间

## 三种轮次

一次用户请求中需要区分：

- 对话轮次：用户发送一次消息，Assistant 最终回复一次。
- 模型调用轮次：一次任务可能多次调用 LLM。
- 工具调用轮次：一次模型输出可能包含零个、一个或多个 Tool Call。

所以：

```text
一次对话轮次
    ├── 可能包含多次模型调用
    └── 每次模型调用可能产生多个工具调用
```

## 生命周期中的五个核心对象

1. Tool Definition：告诉 LLM 有哪些工具可用。
2. Message History：模型当前可以看到的消息和历史调用。
3. Tool Call：模型生成的候选调用。
4. Tool Result：Runtime 执行工具后返回的结果。
5. Execution State：Runtime 在模型上下文之外维护的确定性任务状态。

Message History 主要用于模型推理，Execution State 主要用于程序可靠控制任务，二者不能混为一谈。

## Runtime 接收请求时还需要准备什么

Runtime 可能加载或创建：

- task id、conversation id、任务状态和当前步骤；
- 当前用户身份、权限、时间和时区；
- 会话历史、长期记忆和可用工具；
- Token 预算、调用预算和最大循环次数。

模型不会自动拥有这些信息。哪些信息和工具进入当前上下文，由 Runtime 负责选择和组装。

## Tool Result 标准化

第三方 API 的原始响应通常不适合直接进入模型上下文。工具适配层应该将其转换成稳定结构，以便：

- 屏蔽不同供应商的字段差异；
- 降低模型理解负担和 Token 成本；
- 区分成功、失败、空结果和部分成功；
- 支持自动测试和后续替换服务。

## 任务终止状态

模型不再生成 Tool Call，不一定表示任务成功。Runtime 应显式区分：

```text
completed
waiting_user_input
failed
denied
cancelled
budget_exhausted
unknown
```

例如模型可能正在请求用户补充信息，也可能错误地跳过了必需工具，因此不能只用“有没有 Tool Call”判断任务是否完成。


但是并非所有元数据都要给llm
比如
- 数据库密码
- 内部服务地址
- 管理员token

这些术语runtime 内部信息 不应暴露给模型

## tool definition 的双重身份

### 是给llm的prompt

模型通过名称和描述 来理解工具
- 用途
- 生命时候用
- 参数是什么意思
因为和业务相关 一般放在 developer prompt 有时放在system prompt里

因此tool schema 也属于 prompt engineering的一部分

### 是runtime的输入协议

runtime可以根据 schema来验证
- 参数是否确实
- 类型正确
- 字段是否多余
- 是否符合枚举

因此tool schema是模型语义提示+机器校验协议

但是schema并不能完成全部校验 

最后还需要runtime和业务系统检查 比如就算类型正确 字段合法 但是可能超出业务要求的范围

## llm如何 choose tool

内部通常不是if else程序

主要是根据上下文输出最可能的下一段输出

模型可能输出自然语言回答 也可能输出tool call结构

具体的api通常支持类似
- auto： 模型自行判断是否调用工具
- required：必须调用至少一个工具
- none：不允许调用
- specific tool:必须调用某个固定工具

但是即使 required
llm 依旧可能选错工具 参数错误 理解错用户意图

因此强制结构化输出 只能保证输出形式 不能保证业务语义错误。

## 普通function

普通function 调用者是 确定性的代码 参数由程序员构造。

tool-calling中 是
1. 用户自然语言 
2. 概率模型选择函数 
3. 概率模型生成参数
4. runtime 校验后执行

## 是提案 不是命令

这是整个tool calling安全模型的核心

当输出 tool calling的时候 runtime不应该理解为 llm已经决定 立即调用

应该理解为 llm提出了一个候选行动 需要验证 是否存在 合法 授权 安全

runtime可以
- 允许 
- 拒绝 
- 修改参数 
- 请求用户确认 
- 返回人工审批
- 返回权限错误。

所以关系为
- model提出动作建议
- runtime 执行策略
- 工具执行动作

## 工具分类

### 信息读取工具

比如单纯的查询网站 获取天气 获取订单状态 读文档

特点是：
- 一般没有副作用
- 需要权限校验 和数据范围控制
- 返回结果不一定可信
- 可能泄漏敏感信息。

所以只读不等于安全  某些读取操作虽然不update 但是仍然属于高敏感操作。

### 写入工具

比如 发送邮件 创建订单 更新订单 写文件

特点：
- 改变外部状态
- 通常需要 严格的 鉴权
- 可能需要用户确认
- 需要考虑是否重复执行 幂等校验
- 需要记录审计日志 可溯源

### 不可逆或高风险工具

比如 转账 删除文档数据 授权 

特点是：
- 影响范围大
- 难以撤销
- 可能产生 法律 财务 安全后果
- 不能只依赖llm判断
- 一般需要强确认 审批 人工介入

### 计算型工具

比如 计算器 代码执行器 数据分析器

它门不一定访问外部业务系统 但可以弥补模型在以下方面的不足：
- 精确计算
- 大规模数据处理
- 执行代码
- 文件格式转换
- 图标生成

代码执行工具尤其需要沙箱 因为可能间接访问文件 网络 系统资源

## tool result 并非绝对可信事实

tool result通常比 llm 猜测更可信 但是仍存在：
- api返回过期数据
- 数据库同步延迟
- 搜索结果包含错误信息
- 网页包含提示词注入
- 工具存在bug
- 只返回了部分数据
- 工具超时 但是操作成功

所以tool rusult最好包含
- 状态
- 返回的数据
- 数据源
- 召回时间
- 警告信息
- 是否是部分信息 partial

## 与相关概念的区别

### api calling

是程序application去调用某个接口  application -> api

tool calling是模型先决定是否调用什么 以及生成什么参数
Model-> tool calling -> runtime -> api

api是底层能力 tool是暴漏给agent的语义封装

一个tool 内部可能调用多个api


### structured output

主要是解决 让模型按规定结构输出 不一定会触发外部执行

toolcalling表示 模型生成了一个需要runtime 执行的调用意图

共同点是 都使用 **结构化生成** 区别是后者一般连接真实执行

### work flow

workflow通常由程序预先定义步骤 是写死的流程

而tool calling则允许模型动态选择下一步

一般混合组合使用：
**固定workflow控制主流程 模型在某些节点选择工具**


## 总结

什么是tool calling？

是一种与llm与外部能力交互的协议机制 。 llm根据上下文和工具定义 判断是否需要工具 然后生成包含工具名和结构化参数的 tool call。 runtime接收后 进行schema校验 业务规则 权限 风险校验 最后通过 则执行真实工具。 把结果以tool result的形式加入历史消息 然后再次调用模型 让模型选择继续调用模型还是输出最终回答。
模型通常不直接调用工具 因此toolcall只是候选行动 建议 不代表操作已经成功。 生产级实现还要处理 工具调用的超时 重试 幂等 副作用确认 提示词注入防御 状态管理 trace 。
