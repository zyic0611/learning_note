## 三大核心组件

Registry Dispatcher Agent Loop

架构为：
```
Tool Call
   ↓
Dispatcher ──查找──> Tool Registry
   ↓                  ↓
执行、捕获异常       工具实现 / 元数据
   ↓
统一 Tool Result
   ↓
Agent Loop 决定：继续 / 完成 / 澄清 / 失败
```

### Tool Registry

工具注册目录  
Registry 来保存 工具名->可执行实现的 映射 以及保存必要的元数据

解决的问题
- 模型提到的工具是否真的存在
- 实际该执行哪一个api或者代码
- 工具有哪些执行权限

原则为 **未注册工具绝不执行 模型输出的工具名不是授权**

### Dispatcher

是单次调用的执行器  负责接收已经校验通过的Tool Call

负责
1. 从Registry 找到实现
2. 注入可信运行时上下文
3. 调用工具
4. 捕获超时、网络异常、服务异常
5. 把不同的工具结果返回 统一为 Tool Result

### 最小Loop

继续执行循环 直到出现终态

生产环境下绝对不能无限循环 至少要限制
- 最多调用llm次数
- 最多执行多少个工具
- 时间预算
- Token 预算
- 单工具超时


## Grounding 

模型的回答最后 必须有结果依据

也就是模型的回答 必须基于工具实际返回的数据

Runtime/Prompt应该约束模型
- 工具没有返回的数据 不得编造
- success+`[]`  应表达未查询到数据 不能说系统出错 
- error 应如实说明限制 给用户下一步建议
- 工具成功也只总结结果中存在的字段

## llm处理

不能把整个数据库塞回模型上下文

工具可能返回几百条搜索结果、长文档或完整日志。直接塞回模型会导致：

- Token 成本高；
- 模型忽略关键数据；
- 上下文溢出；
- 私有信息暴露面扩大。

Runtime应该在进入模型前作确定性处理

原始结果
 → 权限字段过滤
 → 只保留必要字段
 → 分页 / Top-K
 → 聚合或摘要
 → Tool Result
