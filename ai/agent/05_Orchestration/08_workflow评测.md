
不能只看最终任务的完成率

```
完成率高，但人工转接率极高
→ 系统可能只是把困难任务交给人工

完成率高，但重试率和成本很高
→ 系统可用，但工程效率差

路由准确率低
→ 后续 Agent 或工具再强，也会在错误路径上浪费成本
```

评测顺序一般是：
1. 先看看任务是否完成
2. 没完成看失败的环节
3. 最后要看耗时、成本、人工介入

## 最小测试集

每个workflow至少覆盖以下场景：

1. 正常主路径成功
2. 每个条件分支
3. 路由未知
4. llm输出非法
5. 工具超时 临时失效
6. 工具永久不可用
7. 非关键分支失败后的降级
8. checkpoint后 服务的中断与恢复
9. 取消任务
10. 副作用节点的重复调用

测试不仅看跑通 还得看每个异常是否进入预期控制路径

## 总结：

我会把 Agent Workflow 当作一个可观测的业务流程，而不只是一次 LLM 调用。对不同失败类型，分别定义 Retry、Fallback、Skip、Escalate 或 Fail；其中 Retry 只用于可重试的临时错误，有副作用操作必须依赖幂等键。可观测性上，我会用 Trace ID 贯穿 Workflow、节点、工具和子 Agent，并记录状态变化、路由决策、耗时和异常路径。评测时优先看任务完成率，再结合路由准确率、失败率、人工转接率、恢复成功率、延迟和成本定位瓶颈。
