

推理与规划描述 Agent 如何理解任务、组织信息并决定下一步行动。

需要区分四个概念：

```text
Reasoning
    分析当前信息并作出决策，下一步要怎么做。 例如是否需要查数据库、调用工具

Planning
    为了完成目标、将目标拆成步骤、依赖和完成条件。

Execution
    当前这一步具体需要如何做 是调用工具、还是发送消息

Orchestration
    整个系统如何稳定的运行、如何编排。 比如状态管理、全新啊、人工审批等等。
```

推理比完整 Agent 架构更细，它描述某个**决策节点**如何工作；
规划定义整体怎么做
执行负责具体做事
编排保证系统可靠。

## 推理模式与Agent架构

ReAct、Reflection 等，描述的是 Agent 在某个决策点如何思考和选择行动，属于“推理/决策模式”。

而以下更偏系统架构：

- Workflow：固定或半固定流程
- Multi-Agent：多个角色协作
- Memory-Augmented：引入长期记忆或检索
- Runtime：工具调用、状态机、恢复、权限等运行环境

ReAct 解决的是“当前轮如何根据观察结果继续行动”；Multi-Agent 解决的是“任务由哪些角色协作”；Workflow 解决的是“流程如何组织与约束”。它们可以组合，不能简单视为同一层级的替代品。


## COT并非生产能力

CoT（Chain of Thought）不是要求模型把完整内心推理公开出来。

生产环境应优先保留“可审计、可执行、可验证”的结构化外显信息 。 

不能依赖存储 很长的自由文本推理。 因为
- 不稳定 同一个任务未必会得到一致的文字过程
- 不利于程序消费 难以校验和恢复
- 可能会泄漏不该泄漏的中间信息
- 真正可观测的应该是 ： 计划、工具参数、结果 、状态、错误。

**面试：我会把模型推理转成结构化决策轨迹，而不是依赖完整 CoT。这样方便审计、回放、评测与失败恢复。**

**CoT 是提升复杂推理表现的提示与中间表示思想**；在生产 Agent 中，我会将它落成结构化的任务分析、计划和决策轨迹，而不是依赖模型暴露完整思维链。ReAct、Plan-and-Execute 和 Reflection 则是在此基础上分别处理动态行动、长程控制和结果验证。

## 模型推理不能代替系统约束

llm负责提出候选决策 程序负责校验 授权 约束 执行。

所以 出现问题 分层排查
- Agent 选错工具 漏掉关键步骤： 推理/规划问题
- 参数错误、接口超时、重复扣款： Execution/Runtime问题
- 状态丢失 重试失控 并发冲突： Orchestration问题
- 越权调用、敏感操作没有审批： 安全和权限问题
