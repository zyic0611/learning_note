原则是 面对具体的任务 选择最小够用的模式 不能为了Agent化二Agent。

- 单步任务用direct 多步任务用Plan
- 业务流程固定用Workflow 不确定用ReAct
- 需要和外界环境交互 比如查数据 调用工具  用Agent loop 不需要用Direct
- 明显步骤有依赖关系 用Plan-and-Execute
- 高风险加入 Verifier 验证 审批

五种常用模式：

- Direct
- Workflow
- ReAct
- Plan-and-execute
- Reflection

一个常用决策树：

```
任务能否单步完成？
├─ 能：是否需要外部实时状态？
│  ├─ 否 → Direct Response
│  └─ 是 → 单次工具调用 + 验证
│
└─ 不能：业务路径是否基本固定？
   ├─ 是 → Fixed Workflow
   └─ 否：是否存在明确的全局步骤与依赖？
      ├─ 是 → Plan-and-Execute
      └─ 否 → ReAct

关键产物是否高风险或可确定性检查？
└─ 是 → 在对应节点加入 Verifier / 人工审批
```

## 混合架构
职责不能重叠

```
Workflow
├─ 收集用户输入与权限检查
├─ Plan-and-Execute：生成迁移方案
│  ├─ Planner：维护步骤与依赖
│  ├─ Executor：执行当前步骤
│  │  └─ ReAct：在信息收集时按 Observation 选择工具
│  └─ Controller：更新状态、局部重规划
├─ Verifier：检查方案是否满足硬性约束
└─ 人工确认后执行高风险动作
```

- workflow: 业务主流程和固定关卡
- Planner / Controller  全局计划和步骤状态
- ReAct 某一步内部的动态工具选择
- Verifier 结果是否通过标准
- Runtime 工具执行、状态、重试、权限等确定性保障

不能所有都决定下一步是什么 那样会导致状态冲突

## 高级模式

|                   |                 |             |
| ----------------- | --------------- | ----------- |
| Self-Consistency  | 多次生成候选，投票或评分选结果 | 调用次数与成本上升   |
| Tree of Thoughts  | 同时探索多个推理分支并筛选   | 搜索空间、延迟迅速增长 |
| Graph of Thoughts | 让不同分支的中间结果组合复用  | 实现、状态和评估更复杂 |

## 选型指标依据

- 看E2E 任务成功率
- 平均错误率
- 平均延迟和P95延迟
- 单任务token和工具调用成本
- 人工介入率
- 重试/重规划率

## 提问

如果被问“什么时候用 ReAct，什么时候用 Plan-and-Execute？”：

> 我先判断任务是否具有明确的全局步骤和依赖。若路径主要依赖工具返回结果、难以预先确定，例如故障诊断或开放式检索，我会选择带轮数和预算控制的 ReAct。若任务是多步骤且依赖清晰、需要维持全局目标，例如方案生成或复杂流程处理，我会选择 Plan-and-Execute，并在局部信息收集步骤中使用轻量 ReAct。对于高风险或可验证结果，再叠加确定性 Verifier；不会默认使用最复杂的架构。
