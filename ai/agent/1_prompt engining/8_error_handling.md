错误处理和降级策略

应该定义 失败的时候应该怎么做。

- 工具调用失败
- 结果为空
- 结果冲突
- 参数不合法
- 模型无法完成

有点类似于条件规则 但是主要是失败兜底。


例如

```
如果工具调用失败：
1. 检查参数是否正确；
2. 必要时修正参数后重试一次；
3. 如果仍然失败，停止调用并向用户说明原因。

如果查询结果为空：
- 不要猜测；
- 告知用户没有找到匹配数据；
- 必要时建议用户补充筛选条件。
```

主要属于 agent的可靠性设计

## 重试

重试的时候要注意  有的时候工具调用失败 是因为 **执行成功但响应失败** 。

对于读取操作可能适用 对于有副作用的操作存在风险

所以不能无脑重试。

必须加入

```
对于有副作用的工具 重试前必须确认
- 工具是否幂等
- 是否存在请求ID
- 是否可以查询操作状态
- 是否能安全判断第一次调用有没有成功
```

工具调用的幂等性。

## 错误分类和对应处理

**参数错误**： 参数缺失、类型错误、枚举非法值
处理： 修正参数或者向用户澄清。

**鉴权错误：** 用户权限不足
处理： 不能反复重试，需要停止或者升级。

**限流错误：** 服务器返回 rate limit
处理：按照 retry-after（应该等待多久后重试）等待、或降级。

**超时错误：** 无法确认操作是否完成
处理：查询状态后决定是否重试

**业务错误：** 业务不足、订单已取消、库存不足等
处理：给用户解决对应的 业务原因 不能当成系统故障

**系统错误：** 服务不可用、网络异常、内部错误
处理：有限重试、备用服务、人工升级或稍后重试

## 工具返回结构化错误

格式一般为：

```
{
	"success":false   # 代表是否成功
	"error_code":"TIMEOUT"  # 错误码 错误的类型
	"message":"请求超时" # 错误信息
	"retryable":false  # 是否可以重试
	"operation_status":"unknown"  # 
	"retry_alter":null  #等待多久后重试
	"user_action":"请稍后查询操作状态" # 对这个错误用户要做出的行为
}
```

关键字段为 retryable 、 error_code 
不要让llm根据一个自然语言错误描述 自行判断 是否需要重试

## 部分成功

复杂agent 执行5个步骤 可能部分成功、部分失败。
不能只简单的返回 任务失败。

需要定义

```
已完成:

未完成：

下一步要做什么：
```

## 错误信息分层

内部错误和用户错误不应该完全一样。

内部错误比较详细 需要记录 **数据库异常、堆栈、工具响应码**

用户通常只需要： **任务没有完成的原因、是否产生副作用、下一步需要做什么**

## agent runtime

这些规则的实际控制 还是通过agent runtime。

一般会在代码里明确控制为：

prompt:告诉模型错误发生后应该采取什么策略

runtime:真正控制 重试次数 超时 幂等 熔断 和 回滚
