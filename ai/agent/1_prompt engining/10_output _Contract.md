
输出契约 ：不止是要求模型输出JSON 而是定义模型输出的接口协议。

## 分类

### 自然语言约束：

比如请用markdown 表格回答 。 

优点：
- 灵活
- 适合面向用户的回答
缺点：
- 依赖模型遵循 指令
- 解析稳定性比较差
- 不适合关键业务的接口

### JSON Mode

一般保证输出可以是合法的 json格式

但不一定保证符合所需要的 字段格式的json
比如不保证
- 字段完整
- 字段类型正确
- 枚举值正确
- 业务逻辑正确

### structured Outputs

使用json schema约束 或者类似schema约束模型输出使结构符合制定格式 

适合：
- 信息抽取
- Agent内部状态流转所用
- 工作流节点通信
- 后端程序消费

但需要注意： 结构符合schema 并不代表  内容正确 业务安全 事实真实

### Function Calling

主要目的并不是让 模型回答json 

而是让模型请求应用 去执行某个函数 或者执行工具工具：

模型生成工具名和参数：
- 应用校验参数
- 应用执行工具
- 工具结果返回模型

函数的参数虽然结构化 但是属于 Agent 工具协议 不等同于普通回答格式。 工具调用本质上是模型和应用的一个 接口。

### Pydantic/Zod等数据模型

通常是应用侧的数据模型和校验工具。可以用于：
- 定义schema
- 解析模型输出
- 校验字段类型
- 发现非法值
- 生成接口文档

但是并不是模型本身的输出约束机制。 
做的主要是校验 不是约束。

## 输出契约内容

需要明确：

- 输出格式
	- JSON
	- MarkDown
	- 纯文本
	- 函数调用
- schema:
	- 字段名称
	- 字段类型
	- 必填、可选字段
	- 枚举值
	- 数组结构
	- 嵌套对象
- 语义：
	- null的含义
	- 每个字段代表什么
	- 空数组和缺失字段的区别
- 状态：
	- success 成功
	- need_clarification 需要澄清
	- error 错误
	- refused 拒绝
	- pending_approval 等待确认
- 错误：
	- 错误类型
	- 错误信息
	- 是否可以重试
	- 用户下一步做什么

## 原则

### 业务状态要和文本内容分开

不建议只返回 message:没有找到订单

建议:要同时返回
	status：not_found
	message:没有找到订单
	order:null

### 不要用自然语言表示状态

不建议 success: 也许成功了

建议： 
	success:false
	status:unknown

### 明确定义null 、空数组、缺失字段

null：当前没有值 或者无法确认
`[]`：已经确认为空集合
字段缺失：该字段没有被返回 或者 不使用

### 结构化输出后仍要做校验
因为结构化输出只能保证格式 不能保证业务等逻辑一定正确 仍要做 schema校验
- 类型校验
- 枚举校验
- 业务规则校验
- 权限校验
- 结果验证

## 总结

output contract 是模型与下游程序之间的接口协议 。
json只解决语法问题 schema只解决结构问题 最终的业务正确性 安全性 权限 仍然需要应用层校验
