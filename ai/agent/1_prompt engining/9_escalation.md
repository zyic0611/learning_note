升级和人工介入。

**agent 不应该默认 所有问题都是自己完成**

需要定义什么时候需要 （升级的主要类型）

- 澄清：信息不完整 需要用户补偿
- 请求用户确认：某些需要得到用户确认的操作
- 转人工处理：不适合让agent自主判断 需要人工接管
- 停止执行：某些操作即将违反安全或者权限边界 无法执行
- 请求更高权限
- 返回人工审核状态

比如
```
涉及以下操作时，必须先获得用户确认：

- 删除数据
- 发送外部邮件
- 修改订单
- 执行资金操作
- 发布公开内容
```

并且更高风险的操作 即使用户确认 也需要代码或者人工审批。

## 用户确认不等于授权

即使用户确认 授权还是由身份和权限系统决定

## 高风险操作需要知情确认

不能只是简单写prompt ：
	涉及危险操作 需要询问用户是否确认

应该详细告诉用户： 也就是知情确认
	将执行什么操作
	作用于什么对象：比如删除什么订单
	产生什么副作用：比如永久删除相关记录和订单数据
	是否可撤销：不如不可恢复
	是否会产生费用

## 升级策略 需要定义 触发条件

可以分成：

**风险触发：** 设计到付款、删除、发布、权限变更

**不确定性触发：** 关键事实无法确认

**可靠性触发：** 连续重试失败、工具状态未知、结果相互冲突

这些其实是可靠性触发器 reliability trigger 意思是**系统发现自己 不再确定当前状态是否可靠的信号** 也就是系统此时无法 可信的自主运行 就需要触发额外的可靠性机制 比如恢复 降级 人工介入 重新规划

**合规触发：** 某些操作 需要人工审查或法律判断

## 升级后需要定义状态

agent不能只是告诉用户 需要人工 还需要进入一种明确的状态

状态列表：
- PENDING_APPROVAL 等待系统批准
- WAITING_FOR_HUMAN  等待用户确认
- ESCALATED 升级策略 
- REJECTED 拒绝执行
- COMPLETED 已经完成

所以llm输出就变为

```
状态：
操作：
原因：这么做的原因
下一步：下一步做什么
```

## 审计和权限控制

当高风险升级的时候 需要记录
- 谁发起的
- agent提议了什么
- 用户是否确认
- 审批人是谁
- 实际执行了什么
- 执行结果是什么
但是这些内容已经超出了 纯system prompt

但是system prompt 应该告诉agent
设计高风险操作 不得绕开 确认与审批流程。



## 逻辑链路

conditional rules 指导模型在节点内进行各种判断 操作 判断下一步怎么做
uncertainty & clarification 当模型遇到不确定性情况的时候 具体告诉模型 应该如何处理 ：澄清 假设 调用tool 拒绝猜测
grounding 根据可靠性基于 让模型知道必须基于必须基于可信来源回答 ： tool rag cite
error handling：告诉llm 当出现错误、失败、冲突的时候 需要如何重试、修正、降级、停止
escalation：告诉模型 什么时候需要升级 确认、审批、转人工、拒绝
