
**存储选型取决于查询方式：精确查用 KV/关系库，语义查用向量库，关系遍历用图数据库。**

实际系统通常采用混合存储：

> **关系库存事实，向量索引找文本，图数据库查关系。**

数据库主要是解决 如何保存和查询。 
不能决定
- 什么值得记
- 新旧记忆如何处理
- 哪些记忆要提供给模型
这些需要由runtime 或者业务层来执行

## KV 

比如redis

适合：

- 已知唯一key的查询 比如某一id
- session 状态
- 缓存
- 简单用户配置
- 高频 低延迟读写

优点：
- 查询快
- 结构简单
- 容易水平扩展

局限：
- 不擅长复杂条件查询
- 不擅长实体关联
- 数据约束和统计能力差

## 关系数据库

比如mysql 数据按照表、字段、关系组织。

适合
- 用户画像
- 项目配置
- 结构化事实
- 任务状态
- 权限与租户隔离
- 精确查询、更新、事务

优点：
- 精确查询
- 支持事务和约束
- 更新、删除可靠
- 容易审计和权限管理
缺点：
- 不擅长理解自然语言语义
- 模糊文本召回能力差

## 向量数据库

按照语义相似度找内容

适合：

- 对话摘要；
- 历史案例；
- 非结构化经验、文档；
- 用户表达近义词的查询

基本流程：

```text
文本切分
→ Embedding
→ 向量存储
→ 相似度检索
```

切分可能破坏原始语境，可以保留会话、父文档、时间和来源等元数据。
也就是说向量记录不能只有向量。
最少需要：
- memory_id
- embedding 向量
- user_id
- text
- type
- time
元数据用于限定 用户、租户、类型、时间 

局限：
- 相似不等于相关
- 相似不等于正确
- 不适合精准事实判断
- 不擅长事务和复杂更新
- 文本修改后要重新嵌入
- 切分不当会破坏语境

## 图数据库

适合表达：

```text
实体—关系—实体
```

例如：

```text
用户 → 参与 → 项目
项目 → 使用 → 数据库
```

图结构适合
- 精确关系查询
- 多跳关联
- 关系本身就是核心信息
- 数据结构经常形成网络

优点：
- 关系表达好
- 多跳查询清晰
- 适合知识网络

只有当关系查询成为核心需求 才会用图数据库 比如知识图谱

局限性：
- 不擅长语义搜索
- 结构和维护成本高

## 混合架构

记忆写入 -> 使用memory_id标识

原文、状态、元数据 存入 关系数据库

同时向量化 存入向量数据库

一般都是：根据向量匹配后 拿到memory_id 去关系库拿到元数据。

总结：

关系库做事实源，向量库做语义索引；KV 管快速状态，图数据库解决多跳关系。
