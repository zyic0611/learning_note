领域分类 → 口径澄清 这套流程的本质，就是在用户请求真正触达核心业务逻辑（调用大模型和工具链）之前，设立的一个**领域守门员**。

也就是当用户通过了 话题关联判定 与上一轮对话有关或者无关  也通过了规则口径澄清 没有模糊的话语 没有风险的话术 需要再判定 该问题在不在 领域范围内 。

## classify_domain 意图识别 也叫领域分类

**核心作用**：判定用户的输入是否属于当前 Agent 的核心业务管辖范围

**运行机制**：

- 当系统（`START`）接收到用户输入后，第一个执行的就是这个节点。它通常是一个轻量级的 LLM 调用，或者基于文本相似度的分类器。
- 它的唯一任务是输出一个**布尔值或枚举类型**，并将其写入 `AgentState`（例如更新状态字典中的 `in_domain = True` 或 `False`）。
- **场景映射**：假设你正在开发的 Agent 是用于**工业环卫系统**的。
  - 如果用户输入：“帮我查一下今天静安区垃圾清运车的派单情况”或者“拉取最新的高并发抢单日志”。此时，分类器判定符合业务，设置 `in_domain = True`。
  - 如果用户输入：“帮我写一首关于春天的诗”或者“感冒了怎么用药”（医疗资源问题）。此时，分类器判定超纲，设置 `in_domain = False`。



## 条件路由

在这个环节，LangGraph 不会执行具体的节点操作，而是执行一个条件判断逻辑

- 路由器会读取 `AgentState` 中的 `in_domain` 标志位。
- 如果为 `True`：放行，将状态流转到核心的 `agent ↔ tools` 节点，开始复杂的思考和数据库查询。
- 如果为 `False`：拦截，将状态强制导向 `clarify_scope` 节点。


## 工程意义

- **防御大模型幻觉**：如果任由用户输入无关问题，主 Agent 可能会为了强行迎合用户，而在业务场景下“胡编乱造”。前置拦截切断了这种可能。
- **极致的成本控制与性能优化**：`agent ↔ tools` 循环是极其消耗 Token 和系统资源的（涉及到 ReAct 思考、调用外部 API 或数据库）。用一个最廉价的 `classify_domain` 节点在前置位挡住无效请求，能大幅节省 API 开销并降低系统并发压力。
- **状态机的高效管理**：这套流程将“意图识别”与“任务执行”解耦。在审查代码时，你只需要确保 意图识别的 Prompt 足够精准，就能保证整个后台业务链路（如 NL2SQL、抢单日志分析）不被脏数据污染。
