它的核心理念是：在向大语言模型发送 Prompt 之前，不再简单粗暴地将整个数据库的完整物理建表语句（全量 DDL）塞入上下文，而是通过检索与裁剪算法，**动态提取并重组仅与当前用户查询高度相关的表结构、字段和约束条件**，生成一份“迷你版”的 DDL 喂给模型。

## 原因

1、 **突破 Token 限制 (Context Window Limits)**：工业数据库通常包含成百上千张表，几万个字段。如果将完整的 `CREATE TABLE` 语句拼接，往往会产生几十万甚至上百万 Token，直接导致 API 请求失败或产生极其高昂的推理成本。

2、**注意力稀释与幻觉防范 (Attention Dilution)**：大量的评测表明，即便使用支持超长上下文的模型（如 Claude 3 或 Gemini 1.5 Pro），冗余的无关表结构也会触发 **“迷失在中间” (Lost in the Middle)** 效应。模型面对过载的信息容易发生张冠李戴，凭空捏造不存在的外键映射，导致生成的 SQL 出现基础语法错误。

## 核心工程链路

实现高准确率的 DDL Slice，本质上是将 **RAG (检索增强生成)** 的思想应用在了结构化数据库的元数据提取上。标准的工作流包含以下三个阶段：

1、离线元数据索引

系统启动或表结构变更时，后台脚本会将每一张表的 DDL、字段中文注释、甚至高频枚举值提取出来，转化为文本块。随后，通过嵌入模型计算向量，并存入向量数据库中；同时构建**倒排索引**以供后续的字面量召回。

2、在线混合召回

当接收到用户的自然语言请求时 系统会启动**混合检索 (Hybrid Search)**：

- 依靠 **BM25** 召回精确的表名和列名（如“工单”、“清运异常”）。
- 依靠**向量检索**泛化召回语义相关的列。 通过排序融合算法（如 RRF），确定当前问题最有可能涉及的 Top-K 目标表集合。

3、图算法补全与物理裁剪

这是最关键的一步。仅仅召回目标表是不够的，如果召回了 A 表和 C 表，但它们在物理上需要通过 B 表才能 JOIN 起来，此时就需要借助**连接图 (Join Graph)** 计算**最短 Join 路径**，将缺失的中间表 B 强制拉入上下文中。 最后，程序会对这些表的原生 DDL 字符串进行正则切割，剔除掉未被命中的边缘字段，最终拼装出一份极致精简的 DDL 字符串作为模型的 Schema 提示词。

## schema处理方案

### 全量注入

零切片，直接输入整个数据库的所有 `CREATE TABLE` 语句。

架构极其简单，不依赖任何外部检索组件或图算法。

### 表级切片

仅保留被召回及其关联链路上的完整表，剔除无关的整张表。

显著降低了 Token 数量，保留了被选中表的完整上下文。

### 列级切片

极其激进，不仅剔除无关表，连被选中表内部**未被使用的字段也会从 DDL 中抹除**。

Token 利用率达到极致，模型注意力高度集中，生成的 SQL 极难出错。
