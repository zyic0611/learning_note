## 产物引用与指针机制

在没有产物缓存的古典 Agent 中，LLM 会直接把数据库查出来的几百行 JSON 吞进肚子里，然后再吐出带有这些数据的图表配置。这不仅 Token 成本极高，还会导致严重的上下文溢出。

**产物引用的本质，是在大模型和实际数据之间建立了一个指针**

**运行机制** 当 `query_data` 工具成功从环卫数据库中拉取到“静安区 5 月份清运车派单明细”后，系统不把这些数据喂给 LLM。相反，系统将数据存入内存（如 Redis 或 `_session_query_cache`），并生成一个唯一的引用 ID（例如 `ref_id = "latest"` 或 `ref_id = "query_102"`）。

**LLM 视角**：LLM 看到的仅仅是元信息（**“数据已就绪，引用标识为 latest”**）。当用户要求“画个饼图”时，LLM 只需要输出 `generate_chart_config(data_ref="latest")`。

**渲染拦截**：前端或图表渲染节点在收到这句指令后，会通过指针去缓存里把真实的 JSON 数据捞出来，完成拼装与渲染。LLM 实现了对重度数据的“零接触”调度。

## 保留最后一次产物

只保留最后一次产物 在单线任务中非常完美。但只要遇到**多维交叉分析**，这个架构就会瞬间崩溃。

**场景还原（工业环卫数据分析）：**

1. **用户**：“帮我查一下 A 车队上个月的超时派单量。”（系统执行查询，缓存写入 `latest = [A车队数据]`）。
2. **用户**：“那 B 车队呢？”（系统执行查询，缓存被覆盖，此时 `latest = [B车队数据]`）。
3. **用户**：“**把他们俩的数据放在一个折线图里对比一下。**”
   - **灾难发生**：此时 LLM 想要执行对比图表，但你的缓存字典里 `latest` 只有 B 车队的数据，A 车队的数据已经被物理覆盖。系统只能报错，或者被迫重新去数据库里同时查 A 和 B。

## 多查询栈

为了解决上述问题，必须将标量缓存升级为**列表/栈结构** 内部是字典结构

在升级后的架构中，系统流转逻辑如下：

- **入栈与元数据注册**：每次查询成功后，数据作为一条独立记录追加到 List 中。关键在于，系统必须自动生成一个描述性 `intent`（如“A车队超时量”），并连同 `query_id` 一起发给 LLM。
- **大模型的“数据目录”**：此时，大模型的工作记忆（Messages）中不再只有 `latest`，而是拥有一份**数据目录（Data Catalog）**。比如：
  - `[数据存入] ID: q_001, 内容: A车队上个月超时派单量`
  - `[数据存入] ID: q_002, 内容: B车队上个月超时派单量`
- **精准调用**：当用户要求对比时，LLM 可以精准地输出：`generate_chart_config(data_ref=["q_001", "q_002"])`。底层代码遍历引用 ID，将两份数据合并后交给前端图表库。
