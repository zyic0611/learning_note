ThinCoder 的 `resume` 不是从暂停的代码行继续执行，而是用原来的 Agent 状态和对话历史，重新进入一次 `runAgent()`。 

恢复的是“任务语义”。

简单点说Resume就是保留已经落入 Agent 持久状态的信息，丢弃当前执行现场里的临时信息。



实现是在 agentloop外面 再包裹循环。循环的意义是内层agentloop可能主动被用户中断、插话、turn上限用户要求继续 外层需要能捕获这些信息并决定是否再次调用runAgent。



主要处理的就是取消、中断、预算上限的情况。

## 取消

取消（ ctrl c） 含义是不要继续当前工作。 agent就不保存不完整的模型输出 直接抛出abort错误。

外层循环接收到错误 就不再resume。退出循环。

需要处理： 生成一半的文字。

如果模型正在流式生成，终端可能已经显示了一部分文字，但这部分文字不会被正式写进 Agent 历史。这样模型下次不会把半截回答误认为完整历史。



## 插话



ctrl i 插话。 处理策略根据发生阶段的不同而不同。 

**如果是llm生成期间插话** 

​	也就是生成了部分文字  则保留部分assistant输出 注入用户的输入 然后抛出abort错误 重新运行llm。让下一轮模型知道用户的插话针对什么

**如果llm还没来得及生成token**

​	就把旧input和插话 作为新的上下文 重新给llm。

**如果llm刚生成tool call 还没执行**

​	视为半成品tool-call ，不会保留。

**如果是工具执行期间插话** 

​	处理更加保守。

- 不提交半截的工具结果。 
- 不把中断造成的工具失败 认为是真实失败
- 如果多个工具执行 只完成了部分工具结果 也不提交 因为llm看到的状态会模糊。

### 悬空的tool call

历史消息中 可能已经有 assistant 给出的tool call 但是 tool并没有执行。

有两层主动修复 在进入Agentloop后的 整理上下文步骤。 会删除 孤立的tool call（找不到所属assistant的）。 与缺失结果的tool call 补上说明。

在真正发送请求给llm前 会再次整理消息顺序。 对于没有结果的tool call 补充上说明。

让llm知道 这个工具曾经被请求，但结果不可用，需要重新判断，而不是假装工具成功或失败。

### 工具中断的问题

没有提交工具结果 但是工具的外部副作用可能已经产生了。 

thincode 没有把工具包装成数据库事务 所以中断不会自动回滚外部副作用。

所以工具设计最好具备

- 幂等性 重复执行没事
- 可检查性 后续可以check
- 可恢复性 可以撤销
- 明确结果 工具调用明确说明做了什么
