## 基本思想

ThinCoder 在工具调度 核心要做到的问题 就是LLM可能提出多个工具调用 要怎样安全的**审查 授权 排序 执行 并回传结果**。

**核心流程：**

就是 llm提出 tool call后 先逐个审查 但不执行 审查后 按照顺序执行 结果回传模型。 所以是一个两段式安全执行。

**如果不一次性检查完：** 

可能就会出现 工具执行一半 后面无法执行的混乱状态 把所有调用都检查一遍 形成执行计划 再统一执行。

这里的统一执行 并非事务 不能保证全部成功或者全部回滚 但是明确区分了 是否合法 和怎么执行。 关注合法。



## 阶段1 权限与合法性审计

该阶段不会运行工具 只是给每个工具调用做一个分类。

区分： 可以执行 参数错误 未知工具 模式禁止 用户拒绝 设计门禁禁止（禁止在评审前修改代码）  Hook阻止。

### 拒绝工具不抛异常

特别注意 **被拒绝的工具调用会变成普通 tool result**  然后交还给模型。这样模型可以自行修正。

工具失败通常是 Agent 可以处理的业务事件，不是整个主循环的系统故障

唯一的例外是 用户主动中断了工具调用 中断必须向上传播 不能伪装成普通的工具错误 回传给llm反思 否则Agent回无视用户中断 要求继续执行循环。

## 阶段2 保序执行

区分工具调用的并行和串行。

- 有依赖的连续工具调用只能串行 
- 有副作用的工具 要单独执行。 
- 连续的只读/可并行工具 可以并行

### 只读和并行是安全基础

工具对象会明确声明 

- 是否只读
- 是否允许并发

这两个元数据。

调度器会依赖元数据做出判断

- 是否需要授权
- 是否可以再Plan mode使用
- 是否并行。

如果一个写工具被错误标记为只读 

- 会绕过用户授权 
- 绕过PlanMode 
- 其他工具并行 
- 破坏调用顺序

### 副作用工具建立Undo快照

非只读工具真正执行前生成Undo快照 做到的是尽可能可以被撤销 

但不是在中断的时候 自动回滚

网络请求、数据库操作 未必可以恢复

不保证所有操作可以撤销 

所以并非严格的ACID事务

### 工具执行结果

只能是字符串 不管什么结果 统一协议接口 输出为字符串。

这样可以简化主循环。 

多模态工具是特殊情况：它返回结构化 JSON，后续再拆成文本和图像。

### 超大工具结果落盘

比如超过十几万字字符的

- 大文件内容；
- 测试日志；
- 全仓库搜索结果；
- 巨大的命令输出；

全部塞给模型会迅速消耗上下文。

ThinCode策略 以16K为界限

```
≤ 16K 字符
→ 直接返回模型

> 16K 字符
→ 全量写入 ~/.thincoder/tmp/
→ 模型只看前 2K 预览和文件位置
```

核心思想是完整数据保留在外部存储，模型上下文只放索引和摘要。

### 工具错误 区分

工具异常的时候 完整信息会写入本地的工具错误文件夹。

包括 

- 时间
- 工具名
- 完整参数
- 错误信息
- stacktrace

模型一般只收到错误信息+少量关键参数。

因为stacktrace很长 并且可能会泄漏本机信息。 所以完整信息会写入本地日志 供Agent决策恢复。
