
## 新任务和续跑

用一个resume参数 明确区分是新任务还是续跑。

新任务 resume=false 就需要重置本次任务的工作状态 比如是否修改过文件 是否运行过验证 等等信息。 一般保留会话事实就够了 比如会话开始时间 单纯的会话历史。

续跑 resume=true 就需要保留本次任务的工作状态。 特别是达到轮次turn或者预算上限了 用户确认要续跑 此时就需要保存任务状态。 状态一般是 任务事实、收敛预算。


## turn上限

根据可以续跑可以分析出来 turn上限并非失败 只是一个暂停点。  所以主循环使用的是有界for 超过上限后 只是抛出一个控制信号 意思是任务可能没完成 但是预算耗尽 询问用户是否继续。  要区分真正的异常 比如网络、工具错误。 

单次运行预算并不等驾驭整个任务， 

所以不能使用无限循环，也不能到达上限就强制中断任务。 for+resume 是一种折中。

## turn开始 先做compact检查。

每个turn开始时 先判断上下文是否需要压缩。 但是只在最后一条消息是 user 或者tool的时候 可以压缩。 因为工具调用在对话历史里有配对关系 

assistant 可以发出tool call
tool会响应tool result。 如果在assistant后截断 会丢失配对关系。

所以上下文压缩 并不只考虑token过多 还必须满足消息序列处于一个协议完整的边界。

### 压缩后还需要重置衍生状态

因为上下文压缩后 会改变一些状态。 比如Plan提醒的节流位置 、停滞检查的近期工具签名。
主要是因为压缩已经重建了历史 如果还是用压缩前的历史长度 或者操作窗口 判断会欧五。

### 压缩失败不能阻断主任务

压缩操作本身可能需要调用llm 也可能会失败。采取的操作是

1. 普通压缩失败 先计数
2. 没到上限就继续任务
3. 连续失败达到阈值后 用本地fallback压缩
4. 如果是用户取消压缩产生的错误 向上级传递。

所以压缩是一个保障机制 不能成为主任务的一个故障

## 模式约束需要重复注入

当压缩之后，或者对话变长以后，模型可能逐渐弱化早期约束。每轮调用模型前检查**模式状态。**

### Plan mode

只读模式  不能直接改代码。

它的提醒策略不是每轮完整重复，而是：

- 每 2 轮注入简短提醒；
- 每 5 轮注入完整提醒；
- 用户发送新消息时重新强调。

这是“约束强度”和“token 成本”之间的平衡。

真正的写操作限制还会在工具调度阶段硬拦截。因此这里形成两层防线：

prompt 软约束 提醒llm 尽量遵守
工具权限硬约束 即使llm没有遵守 也没有写权限。 只靠工具约束的话会浪费llm回合 两者配合

### Engineering mode

工程模式状态 也会持续注入 要让llm知道目前处于
- 设计阶段；
- 评审阶段；
- 还是允许编码的阶段。

## autothink

也就是任务的难度分类 只会在本次用户输入的第一个turn 也就是第0轮执行 后续不会动态改变。 原因：

- 避免每轮增加一次额外模型请求；
- 避免 reasoning effort 在同一任务中反复跳动；
- 工具返回通常只是任务进展，不代表任务类型变化。

而且分类失败会被静默忽略，继续使用原来的 reasoning 设置。

## chat()

也就是调用大模型 会传入 callbacks 比如
- 完整消息；
- 工具 schemas；
- token 流回调；
- 思考流回调；
- 等待状态回调；
- 取消信号；
- 流式规则。

主循环只负责产生事件 TUI或者其他前端决定怎么展示这些callbacks。 当替换前端时候 不用修改主循环 只要修改callbacks的接收者就好了

### response

llm 返回的response 的简单对象：

```js
response = {
  content: "模型输出的正文",
  reasoning: "模型的思考内容",
  toolCalls: [],
  usage: {
    prompt_tokens: 12000,
    completion_tokens: 800,
    total_tokens: 12800
  },
  finishReason: "stop", 描述的是停止原因 llm为什么到这里就结束了 可能是tool call 让客户端准备执行工具 可能是length 超出单词输出长度限制被截断 可能是content_filter 输出内容被安全系统截断等等 。  
  
  但是结束原因主要是 注入提醒 。 因为内容虽然不完整、或者触发安全红线等等 但是仍有意义 可以作为上下文加入历史。

  // 以下字段只在特殊情况下出现
  ruleTriggered: true, //是否触发规则
  _warnings: [], //规则命中的警告信息
  interrupted: true //用户主动终止
}
```

### LLM响应后的处理顺序

chat()后 主循环接收到response 按照固定顺序处理
- 用户是否在生成途中 插话
- 这次用了多少token
- 模型是为什么停止的
- 有无工具调用

### 流式规则 stream rule

流式生成过程中，检查目前已经生成的正文 是否匹配某个模式。

所以需要去建立规则 构建模式 供匹配。 匹配的是llm生成的content 不是tool result
规则内容主要是
```
pattern:"console\\.log"  要检测的文字模式 会被编译成正则表达式
message:"xx"   匹配之后告诉模型什么内容
action: abort  触发规则的时候 llm采取的行动 是立刻终止 还是只记录警告
repeat: once 运行中 匹配上 是只触发一次 还是每次匹配都触发

```

- `abort`：立刻停止本轮llm生成，但不是终止整个agent任务。 是截断这一次llm生成 带着纠正提醒 重新请求llm
- `warn`：允许本轮生成完成，不会中断llm，把warm放入response，所以警告实际上会传入下一轮上下文。 但是步强制创造上下文

### Usage 基线

收到 provider 返回的usage 也就是token用量统计。 内容一般是
```js
{
  prompt_tokens: 50000, 这次发送给llm的上下文 有多少token
  completion_tokens: 1200, llm生成了多少token
  total_tokens: 51200, 两者合计
  prompt_cache_hit_tokens: 40000 有多少token 命中了llm的前缀缓存
}
```

记录的作用 1是给界面显示 2是作为上下文压缩的真实基线。可以参与上下文管理
