主要是在Agentloop前 准备

- 运行参数： maxTurns、压缩阈值
- 能力边界：本次允许使用哪些工具
- 模型上下文：system prompt + history 注入

是环境构造器。



## 上下文注入的思路

llm并非一上来就看用户问题，它还需要知道当前现场。

知道的顺序大概是

- Git状态
- 工作目录快照
- 项目代码大纲
- 相关文档
- 历史记忆
- 当前时间
- 待办清单
- 用户真实输入

给它一份成本受控的开工摘要。



### Git快照

包括：

- 当前分支；
- 最近提交；
- 未提交改动。

解决的问题是：模型必须知道项目现在处于什么状态，避免覆盖用户已有修改，也避免把旧改动误认为自己产生的。

### 目录快照

不是读取所有文件内容，只给有限目录树。 

解决的问题是：模型先获得项目结构感，再决定具体读取哪些文件。

这可以减少盲目搜索，但目录数量有限制，避免大型仓库把上下文塞满。



### 代码大纲

提供项目中主要模块、符号和关系的摘要。 区别于目录树回答 有哪些文件 代码大纲回答 这些文件里大概有什么

### 文档和记忆检索

它们不是全量注入，而是根据用户当前输入做搜索，只取最相关的少数结果。

检索的是 文档和历史记忆

### 用户输入最后注入



前面的内容相当于背景材料，用户输入才是真正需要执行的任务。

把用户输入放在最后，可以让模型清楚地看到：以上是现场资料
现在这是用户真正要求你做的事。



### role：user

把这些信息全部伪装成 特殊格式的user-role。 主要原因是保护 system prompt 的稳定性。 

因为这些内容基本都是动态的 system prompt 每次都会变化，provider 很难命中前缀缓存。

ThinCoder选择：

稳定规则 → system prompt
每轮变化的现场信息 → user-role reminder。

也就是规则放system 状态放history。



## 信任边界

在 目录 文档 记忆 项目文件里可能会包含恶意文字。 提示词注入。

ThinCoder 会使用  

<untrusted_doc_chunk>
  文档内容
</untrusted_doc_chunk>

把文档内容 包裹起来 并进行XML转义， 向LLM 表达 这里面的文字是待分析的数据，不是新的系统指令。

不同的标签说明来源 是目录内容 还是项目的规则文件 还是检索出的文档 还是历史记忆。

XML转义是为了外部内容自己写包裹符号 提前逃出容器。

但这是一种 prompt 层的防御和语义隔离，不是绝对安全沙箱。 高危操作还是需要工具权限层阻止。

## transient

是true or false的一个tag。

代表 这条信息本次运行需要，但不应该作为永久对话事实保存。 

也就是临时需求的信息 比如当前目录树、git状态、时间、一次检索出来的文档片段。

如果永久保存 下次恢复会话时可能误导模型。

## 两条历史线

ThinCoder实际上维护两条历史线。

**agent.history：**

主要是给LLM 使用的上下文

包括 真实对话 系统提醒

可以被压缩 并且会不断变化

**agent.fullHistory**

是永久的 未被压缩的真实交互记录

- 用户输入
- assistant输出
- 工具结果
- 多模态消息



真实的消息会写入两条历史线 但是系统提醒一般直接写入history 

因为LLM运行需要大量的提醒 但是永久会话记录不应该被机器消息污染。 所以history可以被压缩 真实记录不行。



## system prompt 的字节稳定

所谓字节稳定，就是相同配置下，system prompt 每次请求应当完全一致，连时间戳变化都不能有。

这样 provider 可以缓存长前缀：





不过项目规则和技能列表目前会被拼入 system prompt。它们通常比较稳定；一旦项目规则或技能文件变化，缓存前缀自然会变化，这是合理失效。



## 提示词前缀缓存

LLM缓存的并非答案 而是模型“读懂前面这段输入”时产生的中间计算结果。

可以降低输入token的成本 首字输出的时间 长对话每轮重复读取历史的计算量。

模型保存的是KV Cache 也就是保存前缀得出的理解 作为KV



而ThinCoder 的主循环天然是追加式历史 就可以保证前缀不变 适合做前缀缓存。
