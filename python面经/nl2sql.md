Q：NL2SQL完整流程是什么？为什么不能直接让LLM生成SQL？

A：最好是先把用户的query 转化为结构化意图 然后根据结构化意图 做schemalinking 召回相关的表、列、字段。 再根据一些关键字和联表关系 强制召回某些表、字段。 然后生成queryPlan 。 然后将原始问题 <mark>结构化查询意图</mark> queryPlan 相关ddl交给llm 让llm生成sql语句 然后校验sql语句<mark>是否</mark>符合queryPlan 再用sqlglot解析sql的ast语法树 然后经过治理层 <mark>基于 AST 校验并按需改写 SQL，例如限制只读语句、允许访问的库表、最大返回行数和超时</mark> 然后<mark>使用只读、最小权限账号在受控环境中</mark>给数据库执行sql 成功<mark>后可根据权限上下文、查询参数和数据时效策略决定是否缓存</mark> 失败的话就根据失败类型决定要反思重试还是直接报错。<mark>不能直接让 LLM 生成后立即执行，因为语法正确不代表表列存在、业务语义正确，也不代表权限与查询成本安全。</mark>



Q：Schema Linking是什么？如何让模型知道用户问题对应哪些表？

A：就是根据用户的问题 召回对应sql语句需要的表、字段。 就是需要离线先对数据库的表、字段、字段描述、字段同义词、一些代表值构建文档。 对用户的问题 或者提取后的结构化意图 做RAG召回相关的信息。 然后<mark>对被业务词典、精确字段名或确定性规则命中的</mark>字段或者表 强制召回<mark>；代表值应经过脱敏和采样，不能把敏感数据直接写入检索文档</mark>。



Q：如果数据库有1000张表，怎么避免把所有schema塞给LLM？

A：构建一个路由 将表分组 根据用户的问题 先路由到组里 再组里做schema linking。



Q：SQL生成错误怎么优化？

A：区分错误 如果是<mark>业务口径不明确，应向用户澄清；如果是权限不足，应返回脱敏后的权限错误，不能把数据库内部信息直接暴露给用户</mark>。 如果是可修复的错误 比如字段错误、表错误、不止一句sql、<mark>方言或语法错误</mark> 可以把错误信息和sql语句 queryplan交给llm 重新生成sql语句 并且标明重试次数 设置重试阈值。<mark>慢 SQL、高成本 SQL 不能只根据文本判断，应结合数据库的 EXPLAIN/查询成本估算；超过阈值时再优化、降级或拒绝执行。</mark>



Q：如何验证LLM生成的SQL是否正确？

A：先用sqlglot<mark>按目标数据库 方言 解析 SQL、构建 AST，并检查可识别的语法问题；仅成功解析不能证明 SQL 在目标数据库中一定可执行，更不能证明业务语义正确</mark> 再校验sql是否满足queryplan <mark>并结合真实 schema 检查表、列、类型、聚合维度和 Join 条件</mark> 再经过治理层 判断权限、规则、<mark>成本</mark>等问题。 <mark>之后可用 EXPLAIN 或在只读、限时、限行的环境中试执行，并用测试集核对结果。高风险查询再人工审阅；不能仅凭“执行成功”判断 SQL 正确。</mark>



Q：Join Graph在NL2SQL中有什么作用？

A：根据<mark>Join Graph</mark> 联表图<mark>中预先维护的主外键、业务关联键及连接方向</mark>，找到合适的表连接<mark>路径</mark>，缺少<mark>的中间表和连接键</mark>都强制召回。<mark>它能减少笛卡尔积、错误 Join 和模型臆造关联条件的问题；如果存在多条路径，还需结合业务语义、路径代价选择。</mark>
