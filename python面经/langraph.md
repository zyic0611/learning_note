Q：langchain和langGraph的定位区别 选择：

A：
Langchain和Langraph都是用来开发大模型应用的，但定位不太一样。

Langchain偏向提供基础组件和快速开发能力，比如模型调用、Prompt、工具调用、RAG、Agent，以及各种数据源和模型的集成。它比较适合流程相对简单、执行链路比较固定的应用。

LangGraph 更偏向复杂 Agent 的流程编排。它用“图”的方式定义节点、状态和跳转关系，比较适合需要多轮循环、条件分支、失败重试、人工介入，或者多 Agent 协作的场景。它的状态管理和流程控制能力会更强。

实际项目中我不会把它们看成互斥关系，因为 LangGraph 本身也可以使用 LangChain 提供的模型、工具和检索组件。

我的选择标准是：如果只是简单的 RAG、模型调用或者固定Workflow，我一般优先使用 LangChain，开发更快；如果业务流程比较复杂，需要维护状态、动态决策或者让 Agent 循环执行，我会选择 LangGraph。

一句话概括就是：LangChain 更像大模型应用的组件库，LangGraph 更像复杂 Agent 的流程编排框架。


Q： LangGraph 和普通 LangChain Chain 有什么区别？为什么 Agent 更适合用 LangGraph 构建？

A：langchain chain **<mark>通常是预先编排好的流程，但不一定是线性的，也可以包含分支和并行</mark>** 而<mark>LangGraph</mark>**一般是有向图结构的状态机，可以描述更复杂的agent工作流、包括条件分支、循环、状态持久化** 。 Agent和chain最大的区别就是 <mark>Agent 会根据模型决策、工具结果和当前状态动态选择后续执行路径，而普通 Chain 的控制流通常由开发者预先定义</mark>。



Q：LangGraph 中 State 是如何设计的？如果 State 里面存储的信息越来越多，会有什么问题？如何优化？

A：状态<mark>先通过 schema 定义字段及类型，并可通过 reducer 定义各字段如何合并更新；字段内容</mark>一般就是 最近几轮对话 工具调用的信息 结果 历史摘要 澄清信息 执行的状态 一些指向外部缓存、文档的指针 等等 如果存储的信息越来越多会导致<mark>存储与序列化开销增加；如果这些信息又被传给 LLM，还会导致</mark>上下文爆炸 llm注意力漂移 超出上下文窗口请求失败、或者上下文过长导致模型注意力下降。 针对历史对话 可以采用滑动窗口截断、摘要。对于工具调用可以只保留结果的摘要 。有些可以复用的对话信息 并且现在用不到 可以提取到长期记忆中落盘 需要的时候再检索出来用。



Q：Node 和 Tool 有什么区别？为什么有些操作设计成 Node，有些设计成 Tool？

A：节点是图状态机里一个<mark>读取 State 并返回状态更新的执行单元</mark>，更关注工作流的控制。比如判断意图、生成回答、审核。

Tool<mark>是暴露给模型或程序调用的、具有明确输入输出 schema 的可调用能力，内部可以封装函数、外部 API、HTTP 或 RPC 请求</mark>。 一个节点可能调用工具 也可能不调用工具。调用的工具也不是确定的。 而且工具有可能特别多 如果每个工具都作为一个节点 那么图就很大 难以维护 。所以<mark>需要显式编排、负责状态更新或流程控制的步骤适合设计为 Node；需要由模型按需选择的外部能力适合设计为 Tool</mark>。



Q：LangGraph 如何实现条件路由？比如 Agent 判断是否需要调用工具，这个流程怎么设计？

A：就是在一个<mark>节点</mark>后加入条件路由边，<mark>路由函数读取当前 State，根据判断结果返回下一个节点名（或结束标记），从而决定后续路径</mark>。



Q：Checkpoint 在 LangGraph 中有什么作用？为什么需要持久化 State？

A：checkpoint可以用来保存状态 在agent遇到错误中断、宕机等情况的时候 就可以从上一个健康的checkpoint里恢复状态 重新运行。 <mark>不持久化 State 并不表示 Agent 在单次运行中没有状态，而是状态只存在于当前进程/调用中；进程退出、跨会话或中断恢复时无法继续。持久化还支持多轮记忆、人工审批、回放与调试。</mark>



Q：**如果 Agent 执行过程中调用工具失败，你如何设计异常恢复机制？**

A：工具调用失败。首先要做异常分类。 针对网络波动、服务器限流等可恢复的问题 可以<mark>采用指数退避并加入随机抖动</mark>重试  并且设置重试次数上限。 针对参数错误、参数不足的情况 可以将报错信息 一起返回给llm 重新生成toolcall 再次重试 这种情况也需要设置重试<mark>上限</mark>。如果返回给llm llm认为缺少信息 无法用默认值 则返回澄清消息给用户。 如果是权限不足、<mark>工具不存在或请求方式明确不合法等不可恢复错误</mark> 则直接返回错误 不再尝试调用llm。



Q：Agent 为什么会出现死循环？比如一直调用工具，你如何解决？

A：因为agent调用工具的核心是一个<mark>ReAct</mark>循环。 是输入llm信息 llm<mark>判断</mark>需不需要调用工具 <mark>生成</mark>调用工具的tool call 然后runtime真实调用工具 再把调用工具的结果 和本来的信息拼接 重新给llm 一直循环。 此时就可能出现调用工具失败或者工具执行结果为空的情况。 llm可能会再次尝试调用工具。 容易进入死循环。 解决方法就是 需要记录工具调用次数 设置全局最大工具调用次数 和单工具最大调用次数 。 每次调用工具看agentstate里 已完成的任务和未完成的任务有没有变化 也就是看<mark>任务是否取得进展；还可以检测相同参数的重复调用，并设置超时、终止条件和降级策略</mark>。 



Q：ReAct Agent 的思想是什么？Reasoning 和 Acting 分别是什么？

A：核心思想就是 先思考 再做出行为 然后根据<mark>行为得到的观察结果</mark> 重新思考。 reasoning就是<mark>模型根据输入与已有观察判断下一步；Acting 是模型选择动作/工具并生成参数，由 runtime 执行后把 Observation 返回给模型。Reasoning 不等同于必须向用户输出模型的内部思维过程</mark>。



Q：Prompt Engineering 常见优化手段有哪些？比如一个 Agent 输出不稳定，你怎么优化？

A：明确role llm需要作为的身份是什么。职责范围是什么

明确goal 该次任务的目标是什么 接受标准是什么 也就是做到什么程度算成功 明确不做什么 如果有很多目标冲突的时候 优先级是什么 该次任务什么时候需要停止。

同时 需要明确constraint。约束。主要是对llm的行为进行约束 可以做什么 不能做什么。  对输出的内容进行约束 比如不能编造事实 不能泄露隐私  对输出格式进行约束 比如要输出自然语言 比如要输出json格式 markdown格式 还有对资源进行约束 比如某个工具只能调用几次 llm只能重试几次 只能访问规定的文件夹

还需要明确能力边界、职责边界、权限边界。

并且要说清楚 conditional_rules 条件规则 主要是在一个llm节点内部 做出一些判断 遇到什么信息 应该如何思考

然后说明不确定性处理 遇到不确定的信息 需要用默认值、或者向用户澄清、什么时候可以假设 。

然后要说明llm可以利用的数据依据 必须源自于知识库之类的。

然后定义一些错误处理策略和降级方式，还有升级方式。

最后可以<mark>few-shot</mark> 适当注入一些正面案例、边界案例、反例。



Q：System Prompt、User Prompt、Tool Prompt 的优先级关系是什么？

A：<mark>“Tool Prompt”不是统一标准的消息层级。通常指令优先级是 System（若平台另有 Developer 层，则在 User 之前）> User；工具描述用于告诉模型如何调用工具，工具返回值通常应视为外部数据，不能覆盖上层指令。</mark>



Q:LLM 为什么会产生幻觉？在工程中有哪些解决方案？

A：源自于llm是一个<mark>按概率预测输出的</mark>语言模型 根据输入 和自己的训练数据 得到输出，<mark>目标是生成合理文本而不是天然验证事实</mark>。 所以没有办法保证llm的输出一定正确。 工程中 首先提示词软约束 第二 <mark>通过 RAG/工具提供可追溯来源；模型自报的置信度不能直接当作真实可靠度</mark> 第三<mark>对于高风险输出做规则过滤，并对关键事实进行外部校验或人工审核</mark>。



Q：Temperature、Top-p 分别有什么作用？生产环境为什么一般降低 temperature？

A：<mark>Temperature 调整概率分布的平坦程度，越高通常输出越多样；Top-p 只从累计概率达到 p 的候选集合中采样。</mark> 生产环境<mark>通常降低 temperature 以减少采样波动</mark> 让agent的表现更稳定<mark>，但结果仍不保证完全确定；一般不建议同时大幅调整 Temperature 和 Top-p</mark>。



Q：结构化输出（Structured Output）是怎么实现的？为什么比让模型直接输出 JSON 更可靠？

A：<mark>结构化输出不只是靠 Prompt：优先使用模型原生的 JSON Schema/Structured Output；不支持时可通过 Tool Calling 约束参数结构。</mark> 然后是可以给<mark>few-shot</mark> 输出后可以用Pydantic<mark>解析和校验，并在失败时重试或降级</mark>。 因为<mark>仅靠 Prompt 让</mark>模型<mark>输出 JSON 时可能出现</mark>编造字段<mark>、类型不符、缺少必填字段</mark> 并且输出的json前后可能<mark>夹杂</mark>markdown文本或者自然语言<mark>；基于 schema 的约束和校验因此更可靠</mark>。



Q：Function Calling 和普通 Prompt 让模型输出 JSON 有什么区别？

A：主要是要输出调用工具的 tool call。 需要满足字段名、字段类型、枚举值等都满足工具的schema。 不仅仅是单纯的输出json



Q： 上下文窗口有限，如果历史对话越来越长，你如何处理？

A：可以采用对话轮数截断或者token截断。 被截断的历史对话可以做一个动态摘要 存入state。 然后看对话里如果有错误、重复的消息 直接删除。



Q：**流式输出 SSE 是怎么实现的？为什么 Agent 场景需要流式响应？**

A：SSE首先是<mark>通过一个持续的 HTTP 响应建立服务器到客户端的单向事件流</mark>，服务器可以不断的给客户端推送消息。 流式就是<mark>服务端在完整结果生成前，逐步发送文本 token、节点状态或工具事件，并不等于输出模型的内部思考过程</mark>。 因为Agent是和用户交互 使用流式响应 首字响应快 用户交互感 体验更好 并且用户可以看到<mark>可公开的执行进度、工具状态和部分答案</mark>。
