
客户端负载均衡：是调用方自己主动选择目标实例。
服务端负载均衡：是调用方把请求 交给中间代理 油代理选择目标实例。

## 客户端负载均衡

比如订单服务自己要去调用支付服务的实例 订单服务需要知道
-支付服务有哪些实例
-哪些实例健康
-这次要选择哪一个
-服务实例变化后 如何更新本地列表

在spring cloud里 一般是：
注册中心：提供实例列表
spring cloud LoadBalancer 选择一个实例
Feign：向选中的实例发送http请求

请求并不会经过额外的 负载均衡代理 比如Nginx


## Nginx 服务端负载均衡

调用路径就变成 订单服务固定只请求 Nginx的固定地址
由nginx 做 负载均衡算法的选择 去选择一个固定的服务实例

此时订单服务就不用知道 有哪些支付服务实例 哪些健康 需要选择哪个 维护列表。 它只知道eginx是统一入口。

nginx对外隐藏了后端实例。

## 为什么常用客户端负载均衡

**微服务内部**的调用通常很多 如果每一次都经过nginx 就多了一次网络转发 并且让nginx承担了大量的内部流量 所以让调用方直接刀目标实例 路径更短 减轻了中间代理的压力。

并且服务注册中心 会把实例变更 通知调用方 调用方的本地实例列表随扩容更新

代价： 每个服务都需要集成服务发现 和负载均衡能力。 如果系统语言很多 客户端能力不一致 维护成本就很高。

## 外部请求走nginx or 网关

外部请求 不应该了解内部的服务架构 所以外部流量必须走同一入口 nginx或者api网关。

因为这层入口 除了负载均衡 一般还负责
https证书、TLS终止、登陆鉴权、限流、跨域、黑白名单、请求日志、静态资源、按路径路由刀不同服务

## 共存

一般可以共存
外部流量 走 nginx/网关转发 和负载均衡
内部服务调用 用Feign +服务发现+客户端负载均衡处理

## 二者的故障点

客户端负载均衡：可能某服务本地缓存里有一个下线的实例 但是被客户端选中了 就调用失败。
所以会比较依赖 注册中心变更同步、健康检查、超时、适度重试、

Nginx负载均衡：所有流量全部经过Nginx 单个Ngxin宕机或者过载 导致大范围请求受影响。
所以生产环境的Nginx也要部署多台 并且通过云负载均衡 等方式做高可用、
并且 Nginx的后端实例列表也必须及时更新。 传统的Nginx 一般靠配置文件维护。 容器和云原生环境中 一般靠服务发现 或动态配置机制同步后端地址。

## 总结

客户端负载均衡由服务消费者在本地完成。消费者从注册中心获取并缓存服务实例列表，再通过轮询、加权轮询等算法选择一个实例，并直接发起调用。Spring Cloud LoadBalancer 就属于这种模式。  
Nginx 属于服务端负载均衡，调用方只请求 Nginx 的固定地址，由 Nginx 从后端实例中选择目标并转发。调用方不感知具体实例，但请求会多经过一层代理。  
两者通常配合使用：外部请求通过 Nginx 或 API 网关进入系统，内部微服务之间通过服务发现和客户端负载均衡直接调用。
