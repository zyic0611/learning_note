
##  虚拟机栈
当 Java 方法被执行时，会创建一个**栈帧** 。 

栈帧中的局部变量表存放了编译器可知的各种基本数据类型和**对象引用**

只要该方法还在执行（栈帧未出栈），这些局部变量引用的堆中对象就绝对不能被回收。

## 静态变量
静态变量属于类级别的属性 并非实例级别。

在 JDK 8 及之后，方法区由**元空间 (Metaspace)** 实现。
类加载后，其静态变量信息存放在此处。

如果一个静态变量引用了一个实例化对象，那么这个实例化的对象在堆中，但是引用他的指针在元空间。

**重点：**

只要该类（拥有静态变量的类）的 **Class 对象**没有被卸载，其静态变量引用的堆对象就不会被回收。

由于类的卸载条件极为苛刻（需同时满足：该类所有实例已被回收、加载该类的 ClassLoader 已被回收、该类对应的 java.lang.Class 对象没有任何地方被引用），因此静态变量极易导致**内存泄漏 (Memory Leak)**，在长生命周期的后端 SaaS 系统中尤为常见。

## 常量池
主要是指运行时 常量池中的引用。
**深度解析：** 
这通常包括**字符串常量池 (String Table)** 中的引用，以及被 `final` 修饰的常量对象。 
比如代码中声明 `String s = "hello";`，这个字面量 `hello` 在堆中的字符串常量池中有一份，如果方法区中有指向这个常量的指针，它就是 GC Root。

**内存位置变迁：**
在 JDK 7 之后，字符串常量池已经被移至**Java 堆 (Java Heap)** 中。因此，这里的 GC Root 实际上是虚拟机内部维护的 StringTable（本质是一个哈希表）中持有的对字符串对象的强引用。

## 本地方法栈中的JNI引用
JNI 即 **Java Native Interface**，用于 Java 调用 C/C++ 代码。
**深度解析：**
当java程序通过JNI 调用底层 Native 方法时， Native 代码可能会在 C/C++ 层面持有 Java 对象的引用。 JVM 无法直接管理 C/C++ 层的指针，因此为了防止这些 Java 对象在 Native 代码运行期间被 GC 掉，必须将它们加入 GC Roots。
**重点：**
JNI 引用分为**局部引用**和全局引用。 
局部引用在 Native 方法返回时会自动释放；
全局引用必须由 Native 代码手动调用 `DeleteGlobalRef` 释放。如果 C/C++ 程序员忘记释放，会导致 Java 堆出现严重的内存泄漏，且使用常规的 Java 内存分析工具 (如 MAT) 排查起来非常困难。

## 隐藏的GCRoots对象

1. 所有被同步锁 (Synchronized) 持有的对象。
2. **Java 虚拟机内部的引用**：例如基本数据类型对应的 Class 对象，一些常驻的异常对象（如 `NullPointerException`、`OutOfMemoryError` 等），以及系统类加载器 (System ClassLoader)。
3. **反映 Java 虚拟机内部情况的 JMXBean**、JVMTI 中注册的回调、本地代码缓存等。
