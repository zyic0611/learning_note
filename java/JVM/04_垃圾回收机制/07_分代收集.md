## 三大核心假说

1. **弱分代假说**：绝大多数对象都是**朝生夕灭**的。
    
    - _工程映射_：这是划分出**新生代** 的根本原因。由于大部分对象（如局部变量、临时 DTO 对象）很快死亡，把它们集中在一起，每次 GC 只需要关注少数存活对象（用复制算法），回收收益极大。
        
2. **强分代假说**：熬过越多次垃圾收集过程的对象，就越难以消亡。
    
    - _工程映射_：这是划分出**老年代** 的根本原因。对于长生命周期的对象（如 Spring 容器中的 Bean、数据库连接池对象、缓存），把它们集中起来，虚拟机就可以以极低的频率对其进行扫描，从而避免高频率的内存复制和整理开销。
        
3. **跨代引用假说**：跨代引用相对于同代引用来说仅占极少数。
    
    - _工程映射_：如果新生代对象被老年代引用，它大概率也会活下来并晋升到老年代，从而消除跨代引用。这个假说引出了解决跨代扫描性能问题的核心数据结构——**卡表 (Card Table)**。

## GC类型
基于上述假说，JVM 将堆内存切分，并针对不同区域实施不同频次和量级的 GC 操作

### Minor GC/ Young GC
**目标回收区域：**
	新生代（包含 Eden 区和 Survivor 区）
	
**触发条件机制**
	当 **Eden 区**空间被填满，无法为新对象分配内存时。

**执行特点与性能：**
	**极度频繁**。由于存活率极低，采用复制算法，STW 停顿时间极短（通常在毫秒级）。

### Major GC/Old GC
**目标回收区域：**
	仅老年代（注意：目前只有 CMS 收集器会有单独收集老年代的行为）
	
**触发条件机制**
	老年代可用空间不足，或触发了空间分配担保失败时。

**执行特点与性能：**
	**频率极低**。通常伴随标记-清除或标记-整理算法，由于存活对象多且需更新引用，STW 停顿时间通常是 Minor GC 的 10 倍以上。
###  Full GC
**目标回收区域：**
	**整个 Java 堆**以及**方法区 (元空间)**
	
**触发条件机制**
	老年代空间不足、元空间空间不足、代码中显式调用 `System.gc()`。

**执行特点与性能：**
	**极其昂贵**的全局停顿。是大厂线上高并发服务发生 API 超时、系统假死的罪魁祸首，JVM 调优的核心目标就是减少甚至消除 Full GC。

## 跨代引用与卡表

在讨论新生代频繁 GC 时，大厂面试官通常会抛出一个极具杀伤力的问题： **“发生 Minor GC 时，仅仅扫描新生代的 GC Roots 够吗？如果老年代中的对象引用了新生代的对象，为了防止误杀新生代对象，难道要把庞大的老年代也全部扫描一遍作为 GC Roots 吗？”** 也就是必须找出这些新生代对象的老年代root

如果你回答“全表扫描老年代”，面试就结束了，因为这违背了分代收集“极短 STW”的初衷。

**解决：**

- **记忆集**：JVM 在**新生代**中建立了一个全局的数据结构，用来记录从非收集区（老年代）指向收集区（新生代）的指针集合。
    
- **卡表**：记忆集的具体工程实现。它是一个字节数组。JVM 将老年代内存空间划分为一系列 512 字节的**卡页**。
    
- **执行逻辑**：只要老年代某个卡页内部的对象存在对新生代对象的跨代引用，这个卡页对应的卡表元素的值就会被标记为 1，称为**脏卡**。
    
- **极速枚举**：当发生 Minor GC 时，垃圾收集器**绝对不会扫描整个老年代**，而是直接去查卡表。只要发现哪个卡表元素是脏的，就只把该元素对应的那 512 字节的老年代内存块加入到 GC Roots 中进行扫描。这极大降低了 Minor GC 的扫描开销。
