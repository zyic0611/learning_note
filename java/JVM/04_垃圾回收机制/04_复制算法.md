为了解决“标记-清除”的效率和碎片问题，复制算法将可用内存按容量划分为大小相等的两块，每次只使用其中一块。当这一块用完了，就将还存活着的对象复制到另一块上，然后再把已使用过的内存空间一次清理掉。

## 核心指标：
- 空间利用率: 比较低 需要留下一个s区
- 产生内存碎片：否 因为整个使用过的内存空间都一起清理
- 内存分配方式：使用指针碰撞  直接往空闲的空间分配内存 分配很高
- 执行开销： GC成本 与存活对象的数量成正比 由于是复制操作 对象移动快
- 适用场景： 新生代 存活率很低 大部分都会被清理 只有少部分存活 生命周期大部分比较短 这样复制的量比较少


## 深度理解： Appel 式空间分配 8:1:1比例
- **内存利用率的突破**：研究表明，新生代中j绝大多数对象都是朝生夕灭。因此，HotSpot 并没有采用 1:1 的比例划分内存，而是采用了 **Appel 式回收
    
- **Eden 与 Survivor 区**：新生代被划分为一块较大的 **Eden** 空间和两块较小的 **Survivor** 空间（S0 和 S1，或称 From 和 To），默认比例为 **8:1:1**。每次分配只使用 Eden 和其中一块 Survivor（如 S0）。发生 Minor GC 时，将 Eden 和 S0 中存活的对象一次性复制到另一块 Survivor (S1) 上，然后直接清空 Eden 和 S0。这种设计使得新生代的可用内存空间达到整个新生代容量的 **90%**，仅有 10% 会被“浪费”。
    
- **空间分配担保 (Handle Promotion)**：如果单次 Minor GC 后存活的对象大小超过了单块 Survivor 区的容量（10%），这些对象将直接通过分配担保机制进入老年代 。
- 面试常考的底层逻辑是：在发生 Minor GC 之前，JVM 必须检查老年代最大可用的连续空间是否大于新生代所有对象总空间（或历次晋升的平均大小），如果小于，则可能需要提前触发 Full GC 以腾出老年代空间。
