串行收集器  核心思想为：绝对的单线程、绝对的独占资源

当 Serial 触发垃圾回收时，必须暂停所有正在执行的**用户线程**，这个过程被称为 **(STW)**，直到垃圾收集彻底完成。

- **新生代实现**：采用**标记-复制算法**。由于是单线程，在进行从 Eden 到 Survivor 的内存复制时，不需要考虑多线程并发场景下的**CAS** 锁竞争问题，指针碰撞分配速度极快。
    
- **老年代实现**：采用**标记-整理算法** Lisp 2 滑动整理算法。老年代对象存活率高，单线程执行标记、计算转发地址、更新引用和物理移动，整个过程线性执行。

## GC STW的实现

核心是适用 **内存保护页、安全点与主动轮询**

**内存保护页 Polling Page**
JVM 并非瞬间“冻结”所有线程，是无法做到让所有下沉一瞬间停止下来。当 Serial 决定进行 GC 时，会在内存里设置一个标志位，标志位被放在**内存保护页  Polling Page**中。 就像一个广播一样。

**安全点 Safe Point**
线程在执行时，并不是每执行一条机器指令都去查一下 Polling Page（那样的性能开销太大了），而是只在特定的位置才会去检查。这些特定位置就是 **Safe Point**。

安全点通常位于**方法调用、循环跳转、异常跳转**等指令序列复用的地方 简单理解就是一般放在程序一定会经过 但是不会太久才经过的地方。

而且如果程序执行到一半 CPU刚读了一半一个对象的引用 就执行GC  那等程序继续执行 就报错了。 所以GC必须等 线程执行到 **可以知道线程状态的地方 也就是安全点**

- **方法调用**：调用一个方法时，CPU 本来就要完成保存现场、创建栈帧、跳转等操作，这时候线程状态非常稳定，而且 JVM 已经知道当前栈帧里哪些位置存放着对象引用（通过 OopMap）。因此顺便检查一下"要不要进入 GC"，成本几乎可以忽略，所以方法调用天然适合作为 Safepoint。
- **循环回边**：也就是循环准备开始下一轮的时候。HotSpot 就会在这个循环跳转之前插入一次 安全点检查。这样无论循环执行多久，每一轮都会检查一次 GC 请求。如果 GC 发起 STW，线程最多执行完当前这一轮循环，就能停下来，而不用等整个循环结束。这就是为什么长时间运行的循环或者死循环不会把 GC 卡死。
- **异常跳转**：当发生异常时，JVM 会进行异常处理，查找异常处理器、调整栈帧、修改程序计数器。这一刻线程的执行状态也是稳定的，因此也适合作为 Safepoint。

**安全点检查**：会主动去轮询这个内存保护页的状态。实际上当JVM想要GC的时候 就会把这块内存保护页设置为不可访问。 当程序执行到安全点的时候 想要访问这块内存 发现访问不了 就会产生缺页异常。 Hotspot就知道可以把线程挂起 让他去STW 执行GC了。

所以整套设计其实是在平衡两个目标：**既不能因为检查太频繁影响程序性能，也不能因为检查太少导致 GC 长时间等不到线程停下来。** 方法调用、循环回边、异常跳转正好都是线程状态稳定、控制流发生变化的位置，而且程序一定会经过，因此成为了 HotSpot 最理想的 Safepoint 插入点。

## STW停顿时间长的原因

1. **木桶效应-等待最慢的线程到达安全点**

	假设服务器有 4 个核心，跑着 4 个线程。交警拉响警报后，其中 3 个线程刚好经过循环跳转，立刻进安全点挂起了。但是，第 4 个线程正在执行一段极其庞大且没有条件跳转的运算（比如超长的非循环矩阵乘法），距离下一个安全点还有很长的时间。 

	此时，JVM 必须原地死等。**已经挂起的 3 个线程和 GC 线程都要等待这最慢的 1 个线程到达安全点**。这段漫长的“同步等待时间”是直接计入应用程序对外不可用的 STW 时间的。
2. **一核有难，多核围观（单线程执行的致命伤）**
	所有线程都到达安全点挂起了，真正的 GC 终于开始了。由于使用的是 **Serial收集器**，它只会启动**一条单独的 GC 线程**去清扫垃圾。 如果你用的是一台现代的 32 核服务器，那么在漫长的 GC 清理期间，**有 1 个核心在满负荷跑 GC 线程，而剩下的 31 个核心全部处于 Idle（空闲）状态**。它们既不能跑用户业务，也不能帮忙做 GC。堆内存几十个 G 的垃圾全靠这一个核心吭哧吭哧清理，自然会导致系统不可用的时间呈线性暴增。


## 现在 serial收集器的意义

如果面试官问：“现在服务器动辄 32 核 64G，Serial 收集器是不是毫无用处了？” **标准答案：绝对不是。在现代微服务与云原生架构中，Serial 迎来了“第二春”。**

Serial 收集器拥有其他所有现代收集器（如 G1、ZGC）都无法比拟的两个绝对优势：

1. **极低的额外内存消耗 **：
    
    - 现代收集器为了实现并发回收和增量处理，需要维护极其庞大的后台数据结构。例如，G1 的**记忆集**可能会消耗高达堆总容量 10%~20% 的额外内存。
        
    - Serial 收集器没有任何复杂的跨区引用记录表，其**额外内存消耗**在所有收集器中是**最小的**。
        
2. **单核环境下的极高吞吐量：
    
    - 没有多线程环境下的锁同步开销（如无竞争的对象头锁、无自旋锁）。
        
    - 没有操作系统层面的**线程上下文切换  开销。
        
    - 在单 CPU 核心环境下，它把所有资源都用于“纯粹的垃圾收集”。
        

**现代适用场景 (Serverless / 云原生微服务)**： 在 K8s、Docker 以及 FaaS（函数即服务）场景下，企业为了极限压缩成本，经常会部署大量规格仅为 **1 核 CPU、256MB 或 512MB 内存** 的微型容器。
在这种资源极度受限的环境下，如果使用 G1，单是维护 G1 的内部结构就会导致 OOM；如果使用 Parallel，多线程上下文切换会榨干 1 核 CPU 的算力。
因此，在这种微容器场景下，显式开启 Serial 收集器，反而能获得最高的吞吐量和最稳定的表现
