CMS和G1有一个严重的问题  **只要垃圾收集器需要把存活的对象从一个地方移动到另一个地方（为了消除内存碎片），就必须全局暂停用户线程（STW）**因为如果一边移动对象，用户一边访问，极容易拿到旧的、已经失效的内存地址，导致系统直接崩溃（。因此，堆内存越大，移动的对象越多，停顿就越久。

## 染色指针

是ZGC的底层原理。 

在 CMS 和 G1 中，如果想知道一个对象有没有被标记过，或者被移动过，这些信息都记录在对象头。

但 ZGC 认为，在对象移动的过程中，去读取对象头是非常不安全的。

**ZGC 的颠覆性操作：把对象的状态信息，直接记录在“引用这个对象的指针”本身上。**

在 64 位操作系统中，指针长度是 64 个比特位（bit）。实际上，目前的硬件根本用不完 64 位，Linux x86-64 架构实际上只使用了低 48 位来寻址（最大支持 256TB 内存）。 ZGC 极其聪明地“强行征用”了 64 位指针里的几个高位比特，作为颜色标志位：

**Marked0 / Marked1 (标记位)**：用于标记对象是否存活。有两个，是双缓冲思想 。

比如Mark =1 GC并不知道这个是上一轮存活还是这一轮标记出来的 则每次GC不需要先清空所有上一轮标记 再重新Mark 只需要使用两个缓冲区交替标记即可。

**Remapped (重定向位)**：核心位。用于标识这个对象是否刚刚被 GC 移动过，且指针还没有来得及更新。

比如一个对象的地址 被很多东西引用。 但这个对象的地址移动了 但是这些东西对该对象的引用还没有更新。 如果用户线程池是直接通过这些东西 来访问对象 则访问到旧的地址 肯定不行。 

传统GC是采用STW 但是ZGC不停止 所以当CPU看到Remapped=1 就不会直接访问 会进入LoadBarrier

LoadBarrier： 看对象的地址是否变动 如果没有 直接返回 如果变动了 找到Forwarding Table转发表里的变动后的地址 然后把该东西对该对象的引用地址修改为新的。 则理解为延迟更新的意思。

**Finalizable (终结位)**：标识对象只能通过 `finalize()` 方法访问。

如果一个类重写了 finalize方法 则当GC发现没人引用该类的时候 无法直接删除该对象  因为还有finalize() 需要先放入Finalizer queue 再执行finalize方法 还有机会复活。

**底层硬件问题：**

CPU 硬件是不认识这些“颜色位”的，它只会把这 64 位当成一个纯粹的内存地址去访问。为了让 CPU 不报错，ZGC 在操作系统底层利用了 **多重映射** 技术。它将带有不同颜色位的多个虚拟内存地址，映射到了同一块真实的物理内存上。

这也就是为什么 **ZGC 绝对不支持 32 位系统**，且极度依赖 64 位操作系统的底层能力。

## 读屏障与自愈机制

CMS 和 G1 为了解决并发标记的漏标问题，使用的是**写屏障（Write Barrier）**（在对象赋值时触发）。

而 ZGC 的灵魂，在于它高频使用了**读屏障（Load Barrier）**（在程序读取对象引用时触发）。

ZGC实现 并发移动对象不报错 就是 Self-Healing 指针自愈过程。

1. **并发转移发生**：GC 线程正在把对象 A 从旧地址复制到新地址。同时，在这个阶段，GC 线程会维护一个极其重要的 **转发表（Forwarding Table）**，记录“对象 A 的旧地址 -> 新地址”。
2. **用户线程读取（触发读屏障）**：就在这个时候，用户线程刚好执行了 `Object obj = A;` 试图去读取 A。
3. **读屏障拦截与颜色校验**：JVM 底层的读屏障瞬间介入。它会检查指针 A 的高位颜色。如果发现 `Remapped` 标志位不对，说明这个对象已经被移动过了，但当前这个指针还是旧的！
4. **查表与指针自愈**：读屏障立刻去查转发表，拿到对象 A 的新地址。然后，读屏障做了一件极其伟大的事：**它不仅返回了新地址的对象给用户线程，顺手还把用户线程里的那个旧指针直接修改为了新地址，并更新了颜色位！**
5. **后续极速访问**：下一次，别的业务逻辑再来访问这个指针时，由于颜色位已经是正确的，读屏障直接放行，几乎没有任何性能损耗。

## 独立自愈

这个自愈过程 比如一个对象 a的地址 p1->a p2->a a的地址被修改了 则这个两个引用的指针都会被修改对吧 然后当访p1->a的时候 就会延迟去自愈这里面的正确地址 但是p2->A的地址还是旧的。

重点就是：

颜色是记录在指针里的 

## 四大并发周期

ZGC 的执行过程几乎全程都是并发的，只有极其短暂的 STW：

1. **并发标记**：遍历对象图，利用 Marked0/Marked1 染色指针标记存活对象。初始标记和最终标记有极短的 STW。
2. **并发预备重分配**：扫描整个堆，统计哪些内存区域（ZGC 中称为 Page）里垃圾最多，把它们选出来组成重分配集（RSet）。
3. **并发重分配**：**这是 ZGC 最硬核的阶段。** GC 线程把重分配集里的存活对象复制到新的空白 Page 中，并更新转发表。此时如果用户线程访问旧对象，会触发**读屏障自愈**。
4. **并发重映射**：GC 线程去遍历堆里剩下的所有旧指针，把它们都更新成新地址。由于有读屏障的“自愈”兜底，这个阶段并不紧急，ZGC 甚至直接把这一步合并到了**下一次 GC 循环的并发标记阶段**去顺手完成，省去了一次完整的对象图遍历！
