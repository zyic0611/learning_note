## 工作流程

实际上是5个步骤。
前面三个阶段和CMS的基本一样。

1.初始标记 短暂stw 标记gc roots

2.并发标记 采用三色标记法 此时不stw 用户线程继续运行  gc继续标记gc roots连接的对象。此时就涉及到STAB技术。当工作线程对 对象的引用发生修改时  通过写屏障 记录下来修改的引用。 **GC本来可达的对象 即使引用没了 stab还认为对象应该存活 那么这部分垃圾就会等到下次GC再回收 。所以本来应该通过gc 可达的对象本来应该需要被标记 也就是白色对象本来要被标灰 此时被工作线程把这个链断开了 就会把这个白色对象放在 stab buffer里 在remark阶段补标存活 形成浮动垃圾 等待下一轮GC** 。

3.再次标记 remark阶段 短暂stw 这个阶段就是去stab buffer里把对象拿出来 重新执行三色标记。

4.cleanup阶段  统计每个 Region：存活对象大小 垃圾大小 回收成本

5.与CMS不同  这个阶段不会采用标记清除算法。由于划分region 采用标记复制算法 。 复制存活对象 这个阶段必须STW 因为要修改指向移动对象的引用。 这个阶段就要采用多次Mixed GC 对cleanup后的cset里 的region进行复制存活对象 回收垃圾。
## 内存架构

设计目标：在保证高吞吐量的同时，解决 CMS 的内存碎片问题，并建立可预测的停顿时间模型

**Region机制：**

G1 不再将堆内存划分成连续且固定大小的 Eden、Survivor 和 Old 区。相反，它把整个 Java 堆切分成了数千个大小相同的、独立的内存块，称为 **Region**（通常为 1MB~32MB）。

**逻辑分代**

每个 Region 都可以动态地扮演 Eden、Survivor 或 Old 的角色。内存的分配变成了“按需分配物理上不连续的块”，但逻辑上它们依然遵循分代体系。但是物理内存不连续。 所以Region的大小永远不会变 变得只是他的逻辑角色。

**Humongous 区 (H 区)**

这是 G1 首创的设计。对于大小超过半个 Region 容量的**大对象 (Large Object)**，G1 不会让它进入 Eden 区，而是专门分配在连续的 **Humongous Region** 中。如果一个对象极大，会横跨多个 H 区。

旧的方法 如果一个大对象 出生在eden区 经历GC的存活 又被复制到 survivor区 最后又被复制到old区 多次复制 消耗大 如果直接诞生在H区 则省去两次复制开销。

为什么要有 H 区？因为 G1 回收内存时大量采用**复制算法**，如果让超大对象在 Region 之间来回复制，CPU 开销会极其可怕。H 区本质上归属于老年代，但在新生代 GC 时也会顺带检查 如果有用 就不动 继续存活 如果没用 就直接清除。

核心就是 **从来不参与复制**

## 第四阶段 cleanup阶段

主要是适用。Cset G1启发式算法找出收益最大region。

**收益率计算**

在后台，G1 会跟踪每个 Region 里的垃圾堆积价值（即该区域内垃圾对象所占的比例除以以及回收所需的时间）。 也就是 **单位停顿时间能够回收多少垃圾。**

**CSet：** Collection Set，回收集

当需要进行垃圾回收时，G1 会根据用户设定的期望停顿时间，运用启发式算法，**优先挑选那些垃圾最多、回收收益最大的 Region 组成一个集合**，这就是 CSet。

**核心理解：**

不再强求一次把所有的垃圾收完  而是在有限的时间内 去清楚最有价值的区域

**原因：**
由于CMS 的回收是只要老年代满了，就得把整个老年代扫描并清理一遍，耗时完全不可控。而 G1 的核心设计目标是**建立可预测的停顿时间模型** 就结合cleanup 引入**最大停顿时间**
就是 G1 允许用户指定一个期望的垃圾回收停顿时间（默认 200 毫秒）。

## RSet

CMS中 只需要一张**卡表**记录老年代指向新生代的引用

G1中 整个堆被分为了几千个Region 任意两个Region之间都可能有引用

则使用Remembered Set 记录。 G1 给**每一个 Region 都配备了一个专属的 RSet**。它本质上也还是一个卡表 记录的是 谁指向自身的区域地址 也就是入边。 所以young GC 不需要扫描整个old区  因为如果不记录入边 在young gc的时候 可能也会有old对象指向young对象 如果 young gc只清理young对象 那么old对象就会 指向空 所以就需要扫描整个old区。但是如果有了 Rset，只需要扫描eden里regionRset就行。 也就是解决 **跨代引用问题**

**与CMS的内存比较**

CMS只有一个全局卡表，额外内存占用极低 而 G1 的每个 Region 都有 RSet，在复杂的微服务架构中，对象引用错综复杂，G1 的 RSet 会吃掉堆内存总容量的 **5% 到 20%**！这被称为**极高的内存屏障占用**  所以在 4GB 以下的小堆内存中，G1 的表现往往不如 CMS。

## SATB 原始快照

为了解决三色标记的“漏标”，CMS 采用了**增量更新**  会导致在Remark阶段 对变动的引用链 进行漫长的深度重扫

**核心动作：**

**当灰色对象要删除指向白色对象的引用时**，G1 会通过写屏障，把这个**即将被删除的旧引用记录下来**。记录进stab buffer

则并发扫描期间，G1 假装整个对象图是处于刚开始 GC 时的“冻结快照”状态。即使你把引用删了，G1 根据stab buffer 依然认为它是活的。

**优势和折中**：

在 Remark 阶段，只需要处理SATB buffer，也就是快照后产生的变化，以及少量的变更记录。因此 G1 的 Remark 阶段 STW 时间极短且稳定。代价是，那些本来已经成了垃圾的对象，会在本次 GC 中被当做存活对象放过，沦为**浮动垃圾**，只能等下一轮 GC 再回收。

## 第五阶段 Mixed GC

Mixed GC 的意思就是**混合回收**，因为它一次 GC 同时回收两部分区域：**整个年轻代（Eden + Survivor）**，以及**一部分老年代 Region**。

**这里为什么叫 Mixed，而不是 Full GC？**

因为它**不会扫描整个老年代**，而是根据 Cleanup 阶段统计出来的结果 开始复制清理垃圾。


然后进入 **Evacuation（对象撤离）** 阶段，这个阶段必须 **STW**。

**为什么必须 STW？**

因为 G1 使用的是**复制算法**。它不会把垃圾对象一个个删除，而是把 **CSet 中所有存活对象复制到新的空闲 Region**，复制完成以后，整个旧 Region 直接释放。
另外，还有一个非常重要的点：**Mixed GC 通常不是一次完成的，而是一系列 GC。**

假设并发标记完成以后，有 200 个老年代 Region 都值得回收。如果一次全部回收，停顿时间可能达到几秒，这违背了 G1 的设计目标。

因此 G1 会连续执行多次 Mixed GC：
每一次都根据目标停顿时间控制 CSet 的大小，直到高收益的老年代 Region 基本都回收完成，这一轮 Mixed GC 才结束。
