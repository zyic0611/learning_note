CMS 的终极目标只有一个：  获取最短回收停顿时间 为了把漫长的 **STW**  停顿打散 它将**老年代的回收**过程精细地拆分成了四个阶段。 新生代的回收用的是ParNew收集器。

## 工作流程

**1 初始阶段**

STW 

仅标记GC Roots能直接关联到的对象 

**速度极快**。因为不需要顺着引用链遍历整个堆，STW 停顿时间极其短暂。

**2 并发标记**

不STW

从 GC Roots 的直接关联对象开始，遍历整个对象图。

**耗时极长**，但与用户线程并发。采用**三色标记法** 

此时CMS的 **增量更新**就开始生效 在此期间  其他工作线程对 card的修改 会把card标记为dirty card 并且加入脏卡队列 。底层利用**写屏障** 和**增量更新** 算法记录变动。

**3 重新标记**

STW

修正并发标记期间，因用户程序继续运作而导致标记产生变动的那一部分对象的标记记录

耗时比初始标记长，但远比并发标记短。 也就是去处理脏卡队列。 拿出每一个脏卡的对象 重新执行三色标记



**4 并发清除**

不STW

清理删除掉标记阶段判断的已经死亡的对象。

耗时较长，与用户线程并发。由于不需要移动存活对象（标记-清除算法），所以可以与用户线程并发执行。

## 三大缺陷

### 三色标记法的漏标和增量更新

见三色标记法文件。

### 浮动垃圾与CMF

由于在**并发标记**和**并发清除**阶段，用户线程还在运行，程序自然会伴随产生新的垃圾。这些在标记过程之后才产生的垃圾，CMS 在本次收集中无法处理，只能留到下一次 GC，这就是**浮动垃圾**。

**CMSGC阈值**正因为垃圾收集期间还要留一部分内存给正在运行的用户线程使用，CMS 不能像其他收集器那样等到老年代几乎全满才触发。默认情况下，当老年代使用了 **92%** 时就会触发 CMS GC。

**CMF**Concurrent Mode Failure  如果在 CMS 并发清理期间，用户线程持续产生大对象，导致预留的那 8% 的内存被瞬间撑爆，此时 CMS 就会宣告失败。

**降级STW**发生 CMF 后，JVM 别无选择，只能启动终极后备预案——**全面暂停用户线程 (STW)**，临时启用Serial Old 收集器来清理老年代。由于现代服务器堆内存动辄十几 G，单线程清理会导致系统假死数秒甚至数十秒，这就是大厂监控面板上最可怕的 P0 级报警。

### 空间碎片与晋升失败

CMS 基于**标记-清除**算法实现，这意味着每次 GC 后都会产生大量不连续的**内存碎片**。

 本质是因为CMS是非压缩性GC 所以无法移动对象 整理内存 消除碎片 所以并非内存不够 而是因为内存是碎片的 无法满足连续分配需求。

**问题**
即使老年代总剩余空间还非常充裕，但因为找不到足够大的连续内存块，当新生代发生 Minor GC 时，无法容纳通过**空间分配担保**晋升上来的大对象，这被称为 **Promotion Failed 晋升失败**

**缓解策略**
CMS提供了一个开关 开启后 在 CMS 不得不进行 Full GC 时，使用标记整理算法 整理空间碎片。。但由于**标记-整理算法**需要移动大量对象并更新引用，这个整理过程必须全程 STW，导致停顿时间进一步变长。

### 统一问题

CMS的根本设计缺陷： CMS 是 Mark-Sweep + 并发化补丁，而不是为并发设计的完整GC系统

所以天然引出三大问题：

CMF 本质是分配失败 无压缩

碎片 本质因为无整理能力

remark操作 作为一致性补丁
