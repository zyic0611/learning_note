

## 一、JVM 运行时数据区

### 1. JVM 运行时数据区包含哪些部分？哪些线程私有、哪些线程共享？

线程私有的区域：程序计数器、虚拟机栈、本地方法栈。

线程共享的区域：堆、方法区。

直接内存常在面试中一并提及，但不属于 JVM 规范定义的运行时数据区。方法区是 JVM 规范概念；HotSpot 在 JDK 8 后使用元空间（Metaspace）实现。

### 2. 一个虚拟机栈栈帧包含哪些主要部分？

每次 Java 方法调用都会创建一个栈帧，主要包含：

- 局部变量表：按 Slot 存放方法参数和局部变量；`long`、`double` 各占两个 Slot。
- 操作数栈：用于字节码计算、参数传递和结果暂存。
- 动态链接：将运行时常量池中的符号引用关联到所需的直接引用。
- 方法返回地址：记录方法正常结束后应回到调用方的哪条指令。
- 附加信息。

返回值通常交给调用方栈帧的操作数栈；异常退出时由异常处理机制逐帧寻找处理器。

### 3. 程序计数器的作用是什么？为什么不会发生 OOM？

程序计数器是线程私有的，记录当前线程下一条将要执行的 JVM 字节码指令地址。线程切换后，可据此恢复自己的执行位置。

如果线程正在执行 `native` 方法，程序计数器的值为未定义。它所需内存极小且固定，JVM 规范没有为它定义 `OutOfMemoryError` 场景。

### 4. 虚拟机栈何时抛出 `StackOverflowError` 和 `OutOfMemoryError`？

无限递归会让栈帧不断入栈，超过单线程允许的栈深度时抛出 `StackOverflowError`。

若 JVM 支持动态扩展栈，扩容时无法申请到足够内存，可能抛出 `OutOfMemoryError`。创建大量线程、每个线程分配栈空间，也可能耗尽进程内存。

局部变量长期持有对象引用通常造成的是堆内存泄漏，而不是虚拟机栈 OOM。

### 5. 堆主要存放什么？对象一定连续分配吗？

堆主要存放对象实例和数组。字符串常量池从 JDK 7 起位于堆中；静态字段的具体物理放置与 JVM 实现和版本有关。

堆在虚拟地址和物理内存层面都不要求整体连续。对象能否连续分配取决于收集器和当前区域是否存在碎片：

- Serial、ParNew 等复制/整理型收集器，在连续空闲区中常用指针碰撞分配。
- CMS 基于标记-清除，容易产生碎片，常通过空闲列表分配。
- G1 将堆划分为多个 Region；它会在 Region 或 TLAB 内快速分配，并通过对象转移整理被回收的 Region。

### 6. 什么是 TLAB？它解决什么并发问题？

TLAB（Thread Local Allocation Buffer）是从新生代 Eden 区预先划给一个线程的小块私有分配缓冲区。

线程优先在自己的 TLAB 中分配对象，只需移动私有分配指针，避免多个线程频繁竞争 Eden 的共享分配指针。TLAB 不足时才进入慢路径，申请新 TLAB 或进行其他分配。

### 7. 执行 `new` 创建对象时，大致经历哪些步骤？

1. 解析 `new` 指令中的类符号引用，确保目标类已加载、连接；`new` 还会确保类完成初始化。
2. 在堆中分配对象内存，常见快速路径是在 TLAB 内用指针碰撞分配。
3. 将实例字段设置为零值。
4. 设置对象头中的 Mark Word、类型指针；数组对象还会设置数组长度。
5. 执行构造器 `<init>`，完成显式字段赋值和构造代码。
6. 获得对象引用并继续后续字节码执行。

### 8. Mark Word 存储什么？为什么锁状态会影响它？

对象可概括为：`对象头 + 实例数据 + 对齐填充`。对象头通常包含 Mark Word 和类型指针；数组对象额外包含数组长度。

Mark Word 是会随对象状态复用的管理信息区，通常可保存：锁状态、身份哈希码（`System.identityHashCode`）、GC 年龄、指向锁记录或 `ObjectMonitor` 的指针。

| 对象状态 | Mark Word 主要内容 |
| --- | --- |
| 无锁 | 哈希码、GC 年龄、无锁标记等 |
| 轻量级锁 | 指向当前线程栈中 Lock Record 的指针 |
| 重量级锁 | 指向 `ObjectMonitor` 的指针 |
| 偏向锁（旧机制） | 偏向线程 ID、时间戳等 |

Mark Word 被不同状态复用，是为了使无锁对象足够小、加锁尽量快。偏向锁属于较旧 HotSpot 机制，较新的 JDK 已不再使用。

### 9. 为什么 `synchronized` 不应锁字符串字面量？

字符串字面量会进入字符串常量池并被复用。不同模块中相同的字面量，例如 `"lock"`，可能实际指向同一个对象；无关代码会意外竞争同一把锁。

```java
private final Object lock = new Object();

public void work() {
    synchronized (lock) {
        // critical section
    }
}
```

推荐使用 `private final Object` 作为专用锁对象。`new String("lock")` 虽可避免池化共享，但语义和性能都不如专用 `Object`。

### 10. `synchronized` 修饰实例方法和静态方法时，锁对象分别是什么？

- 实例同步方法锁的是当前实例 `this`。同一对象上的实例同步方法互斥，不同对象之间通常可以并发。
- 静态同步方法锁的是当前类的 `Class` 对象。该类的所有实例共享这把锁。

因此，一个线程执行实例同步方法、另一个线程执行静态同步方法时，通常不会阻塞：`this` 和 `当前类.class` 是两把不同的锁。

### 11. 什么是 `synchronized` 的可重入性？

可重入性指同一线程已经获得某个对象的 monitor 后，可以再次进入以同一对象为锁的同步代码，而不会把自己阻塞。

例如同步方法 A 调用同一对象的同步方法 B：线程已持有 `this` 的锁，进入 B 时重入计数加一；退出 B 和 A 时再逐层释放。

### 12. 方法区主要存放什么？JDK 8 为什么用元空间替代永久代？

方法区是规范概念，主要存放类元数据、运行时常量池、字段和方法信息、方法字节码等；类变量也属于它管理的内容。

JDK 8 后，HotSpot 用本地内存中的元空间替代永久代。它不再受固定永久代大小的直接限制，更适合动态生成、卸载大量类的场景。

元空间仍可能耗尽，典型报错为 `OutOfMemoryError: Metaspace`。字符串常量池在 JDK 7 起已移到堆中。

### 13. 运行时常量池和字符串常量池有什么区别？

运行时常量池是每个类加载后，由 class 文件常量池转换而来的运行时结构。它包含字面量常量，以及类、字段、方法、接口的符号引用；需要时可解析为直接引用。

字符串常量池是全局复用 `String` 对象的池。字符串字面量和调用 `intern()` 后的字符串可以进入其中；现代 HotSpot 中它位于堆。

```java
String s1 = "abc";             // 使用字符串常量池对象
String s2 = new String("abc");  // 在堆中新建对象
String s3 = s2.intern();        // 返回池中的 "abc"
```

### 14. 直接内存属于 JVM 运行时数据区吗？如何使用，可能有什么问题？

直接内存不属于 JVM 规范定义的运行时数据区，但属于 JVM 进程占用的内存。NIO 的 `ByteBuffer.allocateDirect()` 常使用它，以减少 Java 堆与操作系统缓冲区之间的额外复制。

它可能抛出 `OutOfMemoryError: Direct buffer memory`。常见原因是超过直接内存上限，或 `DirectByteBuffer` 对象仍被引用、尚未发生 GC，关联的 Cleaner 未释放堆外内存。通常可通过 `-XX:MaxDirectMemorySize` 设置上限。

### 15. 本地方法栈和虚拟机栈分别服务什么代码？异常有什么异同？

虚拟机栈服务 Java 方法的执行，每次 Java 方法调用创建栈帧。本地方法栈服务 `native` 方法，例如经 JNI 调用 C/C++ 等本地代码。

具体 JVM 实现可将二者合并。二者都可能因栈深度或容量不足抛出 `StackOverflowError`；支持动态扩展时，扩容失败也都可能抛出 `OutOfMemoryError`。

### 16. 常见的 GC Roots 有哪些？

- 虚拟机栈栈帧局部变量表中引用的对象。
- 本地方法栈中 JNI 引用的对象。
- 方法区/元空间中，类静态字段所引用的对象。
- 被 `synchronized` 持有的对象。
- JVM 内部引用，例如活动线程、系统类加载器、JNI 全局引用等。

字符串常量池中的字符串、异常对象都不是天然 GC Root；只有从某条 Root 引用链可达时才会存活。

### 17. 一个类被卸载通常需要满足哪些条件？

通常需要同时满足：

1. 该类及其子类没有任何存活实例。
2. 加载该类的 `ClassLoader` 已不可达、可被回收。
3. 该类对应的 `java.lang.Class` 对象没有被任何地方引用。

因此，自定义类加载器加载的类更可能卸载；动态加载类却不释放类加载器，容易造成元空间泄漏。

### 18. 遇到三类常见 OOM 时优先排查什么？

| 错误 | 优先排查 |
| --- | --- |
| `Java heap space` | 对象数量或大小持续增长、缓存未清理、集合持有、静态集合、`ThreadLocal`、监听器等堆泄漏；结合堆转储分析引用链。 |
| `Metaspace` | 动态生成类、热部署/插件卸载后 `ClassLoader` 仍被引用、字节码增强框架生成的类未释放。 |
| `Direct buffer memory` | NIO 直接缓冲区分配量、缓冲区是否长期被引用、GC 是否不及时、`MaxDirectMemorySize` 是否过小。 |

## 二、JVM 类加载机制

### 19. 类从被加载到可使用，经历哪些阶段？

经典生命周期可概括为：加载、链接、初始化、使用和卸载。其中链接包括验证、准备和解析。

- 加载：读取 class 二进制流，在方法区/元空间创建类元数据，并在堆中创建对应的 `Class` 对象。
- 验证：校验字节码格式、语义和安全性，确保符合 JVM 规范。
- 准备：为类变量分配内存并设置零值；编译期可确定的 `static final` 常量可在此阶段直接赋值。
- 解析：将运行时常量池中的符号引用转换为直接引用；JVM 可以把部分解析延后到实际使用时。
- 初始化：执行编译器生成的 `<clinit>`，包括静态变量显式赋值和静态代码块。

### 20. 哪些情况会触发类初始化？

- 执行 `new` 创建该类实例。
- 读取或修改该类的非编译期常量静态字段（`getstatic`、`putstatic`）。
- 调用该类的静态方法（`invokestatic`）。
- 通过反射主动初始化，例如 `Class.forName("com.example.User")`。
- 初始化子类之前，先初始化父类。
- JVM 启动时，先初始化包含 `main` 方法的主类。

常见不触发目标类初始化的情况：访问编译期常量、创建类数组、`ClassLoader.loadClass()`、`Class.forName(name, false, loader)`。

### 21. 什么是双亲委派模型？基本流程是什么？

默认情况下，类加载器收到加载请求后不立即自行加载，而是优先委托父加载器；父加载器再逐级向上委托。只有父加载器无法加载时，当前加载器才尝试自行查找和定义该类。

1. 调用 `findLoadedClass()` 检查类是否已经加载，避免重复加载。
2. 委托父加载器的 `loadClass()`；父为空时由启动类加载器尝试。
3. 父加载器无法加载后，当前加载器调用 `findClass()`。

价值在于：保证类的唯一性，并保护核心类。用户自定义 `java.lang.String` 也无法替换由启动类加载器加载的 JDK `String`。

### 22. JDK 常见三层类加载器是什么？

| 类加载器 | 主要加载内容 |
| --- | --- |
| Bootstrap ClassLoader | 最核心的 Java 类库，例如 `java.base` 模块中的 `java.lang.*`。由 JVM 本地代码实现，不是普通 Java `ClassLoader` 对象。 |
| Platform ClassLoader | JDK 平台相关、但不属于最核心类库的模块。 |
| AppClassLoader | 应用自身的类和 classpath 上的第三方依赖。 |

`String.class.getClassLoader()` 返回 `null`，表示它由启动类加载器加载。JDK 8 的旧说法中，第二层是 Extension ClassLoader，主要加载 `jre/lib/ext`。

### 23. JVM 如何判断两个 `Class` 对象是否代表同一个类？

类身份由“类的全限定名 + 定义它的类加载器”共同决定，单看全限定名不够。

两个不同的类加载器都定义了 `com.example.User` 时，它们是 JVM 中两个不同的类型；跨加载器强制转换可能发生 `ClassCastException`。若子加载器委托父加载器成功加载了某类，子加载器拿到的是父加载器定义的同一个 `Class` 对象。

### 24. 自定义类加载器时，`loadClass`、`findClass` 和 `defineClass` 的职责分别是什么？

- `loadClass`：加载入口，负责检查已加载类、执行双亲委派，并在必要时触发当前加载器查找。
- `findClass`：真正获取 class 字节码的位置，例如从目录、数据库、网络或加密 jar 读取。自定义类加载器通常重写它。
- `defineClass`：将读到的 `byte[]` 交给 JVM，定义为 `Class<?>` 对象，通常由 `findClass` 调用。

```java
class MyClassLoader extends ClassLoader {
    @Override
    protected Class<?> findClass(String name)
            throws ClassNotFoundException {
        byte[] bytes = readClassBytes(name);
        return defineClass(name, bytes, 0, bytes.length);
    }
}
```

除非明确实现子优先等策略，否则一般只重写 `findClass`，不随意重写 `loadClass`。

### 25. 面试中所谓“双亲委派机制失效”有哪些典型场景？

更严谨地说，这不是 JVM 故障，而是为了类隔离、插件扩展等需求，有意不遵循默认的父加载器优先策略。核心矛盾是：父加载器通常看不见子加载器加载的实现类。

- **JDBC / SPI**：JDK 核心类需要使用应用 classpath 中的驱动或服务实现，常通过线程上下文类加载器（TCCL）实现逆向委派。
- **Tomcat**：多个 Web 应用可能依赖同一库的不同版本。WebAppClassLoader 为实现隔离，通常优先从本应用的 `WEB-INF/classes` 和 `WEB-INF/lib` 查找，再委托父加载器。
- **OSGi**：每个 Bundle 通常拥有自己的类加载器，按模块导入/导出依赖关系在模块间查找，更像依赖图而非单一父子树。

面试总结：双亲委派保障类唯一性和核心类安全；JDBC/SPI、Tomcat、OSGi 是对默认策略的有意扩展。
