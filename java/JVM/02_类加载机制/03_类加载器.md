## 启动类加载器

Bootstrap ClassLoader

**核心指责** 专门负责加载 **Java 运行所需的最基础、最核心的 API 类库**。例如都在用的 `java.lang.String`、`java.lang.Object`、`java.util.List`

**加载范围** 实际上这些加载器 也是要去加载固定目录下的文件内容

**底层实现**  在 **HotSpot 虚拟机**中，它是用 **C++** 语言实现的，直接嵌套在 JVM 内核中。由于它不是一个 Java 对象，因此在 Java 代码中尝试获取核心类的类加载器时，返回的结果始终是 **`null`**。

**安全机制**  即使恶意开发者将自定义的类打包放到其管辖目录下，只要文件名不符合官方规定，启动类加载器也会拒绝加载，从而保障核心 API 的绝对安全。

## 扩展类加载器

Extension ClassLoader 

**核心指责** 负责加载 **Java 平台提供的一些安全扩展或者非核心的官方类库**（例如 `javax.*` 开头的包，或是 XML 解析、加密解密相关的标准实现）。

**底层实现**  由 Java 语言实现 在 Java 代码中可以直接获取并使用它。

**版本演进**  在 JDK 9 引入模块化系统（JPMS）后，扩展目录的机制被废除，这个加载器被重命名为 **Platform ClassLoader（平台类加载器）**，主要负责加载那些不属于核心 `java.base` 模块，但依然由 **Java 平台**提供的运行时模块。

## 应用程序类加载器 

Application ClassLoader

**核心指责** 负责加载开发者自己编写的**业务代码**，以及项目中通过 Maven/Gradle 引入的各种**第三方开源框架（jar包）**（如 Spring、MyBatis、Guava 等）

**底层实现**  由 Java 语言实现，具体类是 `sun.misc.Launcher$AppClassLoader`。如果没有特殊指定，开发者创建的任何自定义类，以及通过 `Thread.currentThread().getContextClassLoader()` 获取到的**线程上下文类加载器（TCCL）**，默认都是这个加载器。

## 自定义类加载器

Custom ClassLoader

自定义类加载器则是架构师用来解决复杂业务场景的。它由开发者通过继承 `java.lang.ClassLoader` 类自行编写。

**核心指责和实战场景：**

1. **字节码加密与解密**：为了防止核心商业代码被反编译，可以在编译后对 `.class` 文件进行 AES 加密。在运行期，通过自定义类加载器读取加密文件，在内存中解密后再调用 `defineClass()` 生成 `Class` 对象，防止源码泄露。
2. **非标路径加载**：突破本地磁盘的限制，从远程服务器网络（如 HTTP 下载字节流）、数据库或特定的内存块中动态加载类。
3. **组件/租户隔离**：如前文提到的 Tomcat 的 `WebAppClassLoader`，通过为每个 Web 应用分配独立的自定义类加载器，实现同名但不同版本的类库隔离运行，防止内存污染。
4. **代码热部署（Hot Swap）**：类似 JRebel 或阿里 Arthas 的底层原理。当类被修改时，废弃原有的自定义类加载器并创建一个新的实例去重新加载修改后的类文件，实现在不重启 JVM 的前提下更新业务逻辑。
