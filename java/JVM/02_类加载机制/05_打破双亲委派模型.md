子类有事找父类”的线性思维，而“破坏”往往意味着**逆向调用**或**拦截委派**。

以把这个抽象问题拆解为两个最经典的工业级实战场景：**基础组件调用业务代码（SPI）**，以及**SaaS/容器环境的依赖隔离（Tomcat）**。

## SPI机制和 逆向委派（基础调用业务）

核心问题在于  **高层级的类加载器，无法访问低层级类加载器的管辖范围**。

SPI ：Service Provider Interface

是 Java 提供的一种服务发现机制，最典型的代表就是 JDBC 数据库驱动。

- **规则定义者**：Java 官方在 JDK 中定义了 `java.sql.DriverManager` 接口，它位于 `rt.jar` 中。根据双亲委派模型，它必须由处于最顶层的 **Bootstrap ClassLoader** 加载。
- **具体实现者**：各个数据库厂商（如 MySQL）编写了具体的实现类 `com.mysql.cj.jdbc.Driver`。这些第三方 Jar 包存在于业务工程的 ClassPath 下，必须由底层的 **Application ClassLoader** 加载。

**问题：**

当我们在代码中调用 **驱动管理对象DriverManager** 的**建立连接函数**的时候。 **驱动管理对象**需要去实例化Mysql的Driver类。 但是 **DriverManager**类 是被顶层的Bootstrap 启动器加载类加载的  所以他找不到ClassPath下的Mysql驱动。 因为双亲委派模型只支持向上查找 不允许向下查找。

**解决方法： 使用TCCL**

Thread Context ClassLoader  线程上下文类加载器

- 在 JVM 启动时，主线程的上下文类加载器会被默认设置为 Application ClassLoader。
- 当 `DriverManager` 需要加载 MySQL 驱动时，它不再使用自己的 Bootstrap ClassLoader，而是执行 `Thread.currentThread().getContextClassLoader()`，强行获取到当前线程绑定的 Application ClassLoader。
- 然后，拿着这个底层的加载器去“逆向”加载 ClassPath 中的 MySQL 驱动实现类。

彻底破坏了双亲委派模型自下而上的规则，实现了**父加载器委托子加载器**的逆向操作。

## 应用拦截委派  容器环境的依赖隔离

就比如Tomcat中 部署了两个 Web 应用

- WebApp A 依赖了 `Spring Boot 2.x`。
- WebApp B 依赖了 `Spring Boot 3.3`。

如果 Tomcat 遵守严格的双亲委派模型，那么当这两个应用启动时，类的加载请求都会一路向上委派给 Application ClassLoader。

关键在于： Application ClassLoader 发现自己只要加载过其中一个版本的 Spring 核心类，就不会再去加载另一个版本。

最终结果就是，必然有一个 Web 应用因为版本不兼容而全面崩溃。

**解决方法 WebAppClassLoader 优先加载**

Tomcat为了实现应用之间的绝对隔离，自定义了 `WebAppClassLoader`，并**重写了 `loadClass()` 方法**（注意：重写 `loadClass` 是破坏双亲委派的核心，只重写 `findClass` 依然是遵守双亲委派）。

Tomcat 的加载逻辑变成了“**优先拦截，自己先上**”：



- 当 `WebAppClassLoader` 收到类加载请求时，它**不再优先委派给父类加载器**。
- 它会优先去当前 Web 应用的 `/WEB-INF/classes` 和 `/WEB-INF/lib` 目录下自己寻找并加载类。
- 只有当当前应用目录下确实找不到该类时（比如 `java.lang.String` 这种基础 API），它才会无可奈何地向上委派给父类加载器。

这种机制确保了 WebApp A 和 WebApp B 拥有各自独立的类加载空间，即使类全限定名完全一样，只要是由不同的 `WebAppClassLoader` 加载的，在 JVM 内存中就是两个互相隔离的 `Class` 对象
