## 逻辑本质和Klass存储模型

在Hotspot虚拟机的底层C++实现中 java的类并不是以.class字节流的形式存在于内存中 而是被解析为Klass模型

**InstanceKlass**：当类加载器将类加载到方法区后，HotSpot 会在方法区内创建一个 `InstanceKlass` 对象。它包含了类的全部元数据，包括常量池、字段信息、方法信息、虚方法表（vtable）、接口方法表（itable）等。

**内存镜像：** 同时，JVM 会在 Java 堆（内存中）生成一个对应的 `java.lang.Class` 对象，作为开发者在 Java 代码中访问方法区内 `InstanceKlass` 数据的对外接口（这就是反射的底层支撑）。



## 物理架构演进

由于方法区是逻辑概念 所以每个JDK版本的物理实现和位置不同的。

JDK6以及之前 实现为永久代 ParmGen 属于JVM堆内的连续内存 此时字符串常量池和静态变量 都在ParmGen中 是早期设计 将所有类相关数据全部耦合在连续的永久代内存中

JDK7 实现为永久代 但区别是把 字符串常量池和静态变量移动到java堆中。 原因是字符串的创建极为频繁 留在永久代中很容易引发OOM 。移入堆中 可以复用GC机制。

JDK8 实现为元空间 属于宿主机**本地物理内存** 字符串常量池和静态变量 仍然在java堆中。 彻底打破了永久代的物理空间上线瓶颈。 随着动态代理的大量使用 比如Spring CGLib 的大量使用 类的动态生成很容易撑爆永久代 改用受系统物理内存限制的元空间。




## 元空间的底层内存分配机制

元空间并不归JVM GC管理。 使用的是OS的本地内存。

**chunk内存池**：底层采用组chunk分配机制 JVM从操作系统申请一块较大的连续内存块Chunk 然后把Chunk分配给各个类加载器。

**卸载条件严苛：** 元空间里面的类信息很难被回收。 一个类要被卸载 必须满足三个条件 

- 该类的所有实例都被回收
- 加载该类的`ClassLoader`已经被回收
- 该类的`Class`对象没有在任何地方被引用

因此 频繁创建自定义类加载器的场景 比如Tomcat动态热部署 依然需要监控 metaspace OOM的问题。 因为类是很难被回收的 容易OOM
