## 7个参数

核心线程数 ：就是常驻在线程池的线程数量 
最大线程数 ：最多可以扩充到多少个线程数量
最大空闲时间：临时线程最大的空闲时间 超过该时间就要被销毁
空闲时间单位 
线程工厂：给线程起有意义的名字 方便排查问题 还可以设置线程的优先级 还可以设置为守护线程 或者用户线程 甚至可以绑定特定的异常处理器
拒绝策略 ：队列满了 的拒绝任务策略
工作队列：也就是阻塞队列 排队的队列




### 实例理解

当核心线程数为2 最大线程数为5 阻塞队列 为10 此时进来1-15个线程

1，2个线程先工作 3-12的线程进入阻塞队列 13-15的线程 发现核心线程正在工作 阻塞队列也满了 触发了最大线程机制 创建了三个临时线程去处理 13 14 15 

这就是  **后来的先执行的问题**



## 拒绝策略

`AbortPolicy` 默认 直接抛出拒绝执行异常 数据丢失风险低 有异常抛出 可以进行捕获处理 一般适用于核心业务流程 必须明确感知任务提交失败的场景。

`CallerRunsPolicy` 谁提交的业务 让谁执行 一般就是主线程执行 数据丢失风险特别低 只要主线程没挂 任务一定会执行 适用于对业务完整性要求高 并且允许牺牲整体系统吞吐量的场景

`DiscardPolicy `静默丢弃任务 并且不抛出任何异常 数据丢失风险很高  适用于无关紧要的旁路任务 比如 普通日志打印或不重要的数据上传

`DiscardOldestPolicy `丢弃阻塞队列最老的一个任务 然后重新尝试提交该任务 数据丢失风险高  适合具有时效性的任务 比如最新的实时数据刷新 旧数据失去价值



## 阻塞队列

`ArrayBlockingQueue` 基于数组的阻塞队列 必须指定大小

`LinkedBlockingQueue` 基于链表的队列 默认大小为 `Integer.MAX_VALUE` 很容易导致OOM 建议手动指定大小

`SynchronousQueue` 不存储元素的阻塞队列 每一个插入操作必须等待另一个线程调用移除操作

`DelayedWorkQueue` 支持延迟获取元素的 无界 阻塞队列。 一般用于定时任务线程池

`可以自定义阻塞队列`


## 生命周期
把线程池的生命周期，想象成火锅店从营业到彻底关门倒闭的 5 个阶段：

1. **`RUNNING`（正常营业）**：
   - **状态**：大门敞开，来客就接，后厨疯狂切肉。
   - **对应**：能接受新任务，也能处理队列里的任务。一被 new 出来就是这个状态。
2. **`SHUTDOWN`（温和打烊）**：
   - **状态**：晚上10点，门口挂牌“停止接客”，但店里的客人得伺候完。
   - **对应**：**不接受新任务**，但会**继续处理**队列中排队的任务。
   - 对应方法shutdown() 
3. **`STOP`（紧急清场）**：
   - **状态**：店里着火了！不接客了，等位的赶走，正在吃的掀桌子。
   - **对应**：**不接受新任务**，**不处理**队列里的任务，并且尝试**中断**正在执行的任务。
   - 对应方法shutdownNow()
4. **`TIDYING`（关门打扫）**：
   - **状态**：客人都走光了（不管是吃完走的还是被赶走的），店里空无一人。员工开始打扫卫生，盘点今天的账目。
   - **对应**：所有的任务都已终止，工作线程数量（workerCount）等于 0。此时会执行一个钩子方法 `terminated()`。
5. **`TERMINATED`（彻底倒闭/下班）**：
   - **状态**：卫生打扫完了，锁门，拔钥匙，彻底下班。
   - **对应**：`terminated()` 方法执行完毕，线程池彻底凉凉。



## 进阶

### 核心线程的“空闲销毁”特性

按照常规理解，核心线程是“常驻”的，即便空闲也不会被销毁。但在实际 API 中，可以通过调用 `allowCoreThreadTimeOut(true)` 方法，让核心线程在空闲时间超过 `KeepAliveTime` 后也被销毁。这在资源极其紧张、且业务存在明显波峰波谷的服务器环境中非常实用。
