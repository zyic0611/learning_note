

排查工具一般有三种

## JDK原生CLI jstack

适用于 快速定位线上无APM介入的基础java进程异常

`jps -l` 查PID 查出进程id

`jstack pid > thread.log `导出堆栈信息



## Alibaba Arthas

适用于 现代微服务架构下的复杂线上问题实时诊断

`thread -b` 看阻塞源

`thread -n 1` 看最忙的线程 一般是CPU型问题

`thread id` 看具体栈

`trace/watch` 用于判断 

- 是否卡在DB
- 是否卡在RPC
- 是否锁竞争

真实流程： `thread-b 找阻塞源 再trace  看调用链条`

## 死锁本质识别能力

一般会问 `你怎么确认这个是死锁 而不是假死 阻塞 io卡住`

1. 真死锁：

   - 互相持有对方锁

   - jstack明确输出 `Found one Java-level deadlock`

2. 线程阻塞

   - 一个锁被占用
   -  其他线程排队 
   - **并且不会形成环**

3. 假死 (Hang/假死锁)

   - RPC卡住
   - DB慢查询
   - MQ阻塞
   - GC停顿 STW

## jstack 实战解读方法

1. 找到BLOCKED线程
   - `java.lang.Thread.State:BLOCK(on object monitor)`
2. 找到持有锁的线程
   - `waiting to lock <0x00000007>`
   - `locked `<0x00000007>
3. 判断环路
   - 死锁结构 形成环路等待条件 
   - Thread A : waiting lock X ,holds lock Y
   - Thread B : waiting lock Y ,holds lock X

jstack 本质上是构建锁依赖图

## 死锁预防和解决策略

架构设计中 **事后排查** 不如 **事前规避**

**固定锁的获取顺序：**破坏循环等待条件 确保所有线程 按照某种全局唯一排序 比如主键id、字典序来决定加锁顺序。 确保所有线程 按照相同的顺序获取资源。

**带有超时的并发锁：** 破坏 持有并等待条件。 抛弃底层的`synchronized` 改用 ReentrantLock 调用tryLock(long timeout)方法 尝试获取锁超时后 主动放弃 并且释放当前已持有的锁 随后进行重试或抛出异常

**最小化锁的粒度和作用域：** 严格遵循 锁内部 只包含必要的共享变量操作逻辑。 禁止在持有锁期间 执行RPC远程调用 发送消息队列 执行慢sql。 容易引起死锁 并且降低系统的并发吞吐量

## 常见死锁类型

1. synchronized 嵌套锁死锁 也就是内部还有锁
2. ReentrantLock顺序错误 多锁+不同模块调用链 顺序不一致
3. 数据库死锁： Mysql 行锁 gap lock 两个事务的更新顺序不同 类似于环路等待

## 线上真实处理流程

1. 发现
   - CPU不高 但是请求卡死
   - RT飙升
   - thread pool full
2. 定位
   - jstack/arthas thread -b
3. 隔离 
   - kill -3 dump 触发JVM输出程序栈  也就是拍快照 防止重启后证据消失
     - 所有线程状态
     - BLOCKED/WAITING
     - 死锁信息 如果有
   - or 重启实例 兜底
     - 清空所有线程状态
     - 打破死锁
     - 释放所有锁资源
     - 恢复服务可用性
   - 隔离在生产排查中是指在不解决根因的情况下，通过线程转储或重启实例等手段，先控制故障影响范围，防止线程堆积或死锁进一步扩大，同时保留现场用于后续分析。
4. 分析原因
   - jsatck分析死锁 trace调用链
   - 锁顺序问题
   - 外部依赖阻塞
   - DB锁
5. 修复
   - 改锁顺序
   - 超时机制
   - 降级/熔断
