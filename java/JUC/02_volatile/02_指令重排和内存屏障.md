
## 指令重排：

- 编译器：指令调度 优化
- CPU：缓存 乱序执行
- JVM：JIT优化

简单理解为 为了加快速度 会打乱代码执行顺序 单线程没问题 但是**多线程会引发问题**。

## 四种屏障

对单个变量的操作 可以抽象为：

- load:从内存读到寄存器 缓存  一般是 `if(flag==ture)`这种读取操作
- Store:从寄存器/缓存写到内存。 比如a=1就是一个store操作  一般是`a=1`这种写、赋值操作

四种屏障 按照 前操作类型x后操作

LoadLoad、LoadStore、StoreLoad、StoreStore

不能重排=屏障前的该类操作 不能越过屏障到屏障后。

### storestore

**指令规则**：写-写屏障 指令规则 `Store1;StoreStore;Store2`

核心作用：保证在Store2之前 Store1的数据一定刷新到主内存 对所有内存可见

不加的后果：**对象半初始化问题**

```java
//线程a
config=new Config();//Store1:给config赋值 写操作
// 发生了指令重排 没有storestore屏障
isReady=true //store2:修改标识位 用标识位代表赋值完毕
```

如果CPU把Store2调度到Store1前面。 此时标志位的赋值生效 config还没有赋值。 此时进来一个线程B 看到标志位生效 直接去拿config 会引入空指针或者拿到错误数据。

**屏障的作用：**在中间插入 StoreStore 强制要求先写数据 再修改标识位

### LoadLoad

不加的后果：**读到过期数据**

```java
//线程B
if(isReady==true){ //Load1 读取标志位
  use(config)//Load2 读取config数据
}
```

现代CPU支持 **推测执行**.CPU可能在判断 isReady之前 就提前把`config`的值读到缓存里。 此时线程A刚好更新了`config`和`isReady `  。依旧是多线程情况 此时虽然Load1 判断通过 但是CPU提前读进来旧数据。

**屏障的作用**： 中间插入LoadLoad 强制要求先读完标志位 再去读数据 拒绝CPU的 **推测执行**



### StoreLoad

作用: 保证store1写入的数据 对所有线程可见 才能进行load2的读取

不加的后果： **缓存未刷新的致命逻辑错误**

```java
//线程a
a=1; //Store 1
x=b; //Load2
  
同时：
//线程B
b=1;//Store1
y=a;//Load2
```

现代CPU有 **写缓存**`Write Buffer` 写操作先放在缓存里 还没同步到主内存 就执行下一条读命令

不加屏障，a=1 A线程只会写在自己的私有缓存修改 然后直接去主内存读取b。 此时b还是旧值。

同理 b线程的y读取的也是主内存的旧值。

这就是经典的 **可见性延迟**导致逻辑全盘崩溃。

屏障的作用： 这是 **最昂贵 也是最全能的屏障** 会强制清空写缓存 等待数据写入主内存后 才允许后续的读取。 由于它具备其他三种屏障的部分效果 绝大多数底层硬件架构中 volatile的底层核心就是靠处罚类似StoreLoad的指令实现。

### LoadStore

主要为了防止 读操作还没结束 cpu就把那块内存覆盖写的极端情况。





## JMM如何操作屏障

为了告诉CPU 这个变量不需要改变前后顺序落地 JMM采取保守策略 编译时 在`volatile`变量的操作前后 自动插入这些屏障

- 写操作前  加入storestore 保证所有普通写操作都刷新进内存 不排到后面 防止 volatile写后 被普通操作覆盖
- 写操作后 加入storeload 保证 volatile写完 立刻刷新主内存 防止后面的读操作读到错误数据
- 读操作后 加入loadload 保证volatile读完后 所有普通读顺序排队 不能提前推测执行 避免读到旧数据
- 读操作后 加入loadstore 保证volatile读完后 后面的普通写操作不能提前执行 覆盖内存 提前读到新数据
