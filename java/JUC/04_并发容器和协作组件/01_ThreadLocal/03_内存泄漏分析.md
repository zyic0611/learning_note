核心内存引链条

Thread实例 -> ThreadLocalMap ->Entry -> key弱引用ThreadLocal,Value:强引用 Object

## 为什么设计为弱引用：

防御性设计，如果是强引用 只要线程存活 哪怕业务代码中没有再使用ThreadLocal对象 也永远无法被回收 因为被Map强引用

把Key设计为弱引用 当业务代码丢弃了ThreadLocal实例 下一次GC 就会回收Key 此时Entry.key就变成null 。 就形成了一个脏数据 结合启发式清理的知识 下次就会清理这个。

​	

## 线程池复用的问题

Tomcat处理请求 Dubbo异步线程池中 线程几乎都是由线程池管理 。 并且线程的生命周期等同于应用的生命周期。

当entry.key被gc回收变成null 由于value是强引用 引用链还存在。

所以只要引用链的最上层 线程 不被销毁 value对象永远不会被垃圾回收

如果是大型对象 比如巨型报表 大型上下文context 内存很容易被打满 最后OOM



## 强制remove

虽然ThreadLocalMap底层有启发式清理 但是是被动并且不可靠的机制。 如果业务后续不再对该线程的ThreadLocal进行读写操作 value就会永远沉睡。

生产规范：必须在代码边界 比如finally代码块里 显式调用remove方法  是切断value强引用的唯一手段 还防止线程池复用导致的上下文污染。
