# 设计模式 面试复盘

## 总览：三大分类

| 分类 | 解决什么问题 | 本文涉及模式 |
|------|-------------|-------------|
| 创建型 | 怎么 new 对象更灵活 | 单例、工厂 |
| 结构型 | 类和对象怎么组合 | 代理、装饰器 |
| 行为型 | 对象之间怎么协作 | 观察者、策略 |

## 一、单例模式（Singleton）

### 核心思想
一个类全局只有一个实例。

### 三种写法（从烂到好）

**① 饿汉式**：简单，但类加载就创建，不管用不用都占内存。
```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

**② 懒汉式 + 双重校验锁（DCL）**：用时才创建，线程安全。
```java
public class Singleton {
    private static volatile Singleton instance; // volatile 防指令重排
    private Singleton() {}
    public static Singleton getInstance() {
        if (instance == null) {                 // 第一次检查，避免每次加锁
            synchronized (Singleton.class) {
                if (instance == null) {         // 第二次检查，真正创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

**③ 枚举（最推荐）**：代码最少，防反射，防反序列化。
```java
public enum Singleton {
    INSTANCE;
    public void doSomething() {}
}
// 使用
Singleton.INSTANCE.doSomething();
```

### 关键考点

**为什么 DCL 需要 volatile？**
`new Singleton()` 不是原子操作，分三步：分配内存 → 初始化对象 → 赋值引用。
JVM 指令重排可能让另一个线程拿到「还没初始化完」的对象，volatile 禁止这种重排。

**反射为什么能破坏单例？**
反射通过 `getDeclaredConstructor().setAccessible(true)` 强行打开 private 限制，
绕过 `getInstance()`，直接 new 出第二个实例。
注意：反射**走了构造方法**，只是绕过了访问控制。

**反序列化为什么能破坏单例？**
`ObjectInputStream.readObject()` 不走构造器，直接在内存分配新对象并填充字段，
同样绕过了 `getInstance()`，产生新实例。

**枚举为什么能防住两者？**
- 防反射：JVM 在 `Constructor.newInstance()` 内部硬编码了检查，枚举类直接抛 `IllegalArgumentException`，是 JVM 层强制拦截，不是软约束。
- 防反序列化：Java 序列化规范对枚举有专属处理，反序列化时调用 `Enum.valueOf()` 查找已有实例，不会创建新对象。

**本质理解**：单例的核心是「控制创建实例的入口，只允许通过 `getInstance()` 拿到实例」。任何绕过这个入口的方式（反射、反序列化）都会破坏单例。

### 面试话术
> "我用双重校验锁，关键是 volatile 防指令重排。更推荐枚举单例，因为它的防护是 JVM 层强制的，不依赖程序员记得加防护代码。"

## 二、工厂模式（Factory）

### 开闭原则（前置知识）
> 对**扩展开放**，对**修改关闭**。加新功能时，加新代码，不改旧代码。

判断标准：你发现自己在**改现有方法**来支持新需求 → 可能违背了开闭原则。

### 三种工厂

**① 简单工厂**：一个工厂类，传参决定造什么。
```java
public class AnimalFactory {
    public static Animal create(String type) {
        if (type.equals("dog")) return new Dog();
        if (type.equals("cat")) return new Cat();
        throw new IllegalArgumentException("不支持：" + type);
    }
}
```
优点：简单。缺点：加新产品必须改工厂类，违背开闭原则。

**② 工厂方法**：每个产品对应一个工厂类，符合开闭原则。
```java
interface AnimalFactory { Animal create(); }

class DogFactory implements AnimalFactory {
    public Animal create() { return new Dog(); }
}
class CatFactory implements AnimalFactory {
    public Animal create() { return new Cat(); }
}
// 加新动物：只加 Bird + BirdFactory，旧代码不动
```
优点：符合开闭原则。缺点：类数量翻倍，类爆炸。

**③ 抽象工厂**：造「一族配套产品」，换就整套换。
```java
interface UIFactory {
    Button createButton();
    Input  createInput();
}
class LightThemeFactory implements UIFactory {
    public Button createButton() { return new LightButton(); }
    public Input  createInput()  { return new LightInput(); }
}
class DarkThemeFactory implements UIFactory {
    public Button createButton() { return new DarkButton(); }
    public Input  createInput()  { return new DarkInput(); }
}
// 切换主题只换工厂，保证组件永远配套
UIFactory factory = new DarkThemeFactory();
```
缺点：给「一族」加新产品类型，必须改所有工厂类。

### 三种对比

| | 简单工厂 | 工厂方法 | 抽象工厂 |
|---|---|---|---|
| 造几种产品 | 一种 | 一种 | 一族（多种配套） |
| 开闭原则 | 否 | 是 | 部分 |
| 类的数量 | 少 | 中 | 多 |
| 适用场景 | 业务代码 | 框架/SDK | UI主题、跨平台 |

### 什么时候用工厂？

核心判断：**调用方需不需要知道「造的是哪个具体类」？不需要就用工厂。**

典型场景：
- 创建逻辑复杂，不想让调用方关心（数据库连接、缓存选用）
- 根据配置/环境动态决定用哪个实现（测试用内存存储，生产用 Redis）
- 同一套接口有多种实现，将来可能扩展（支付方式）

**实际项目里用简单工厂最多**，工厂方法用于框架设计，抽象工厂用于产品必须成套的场景。

### 面试话术
> "实际业务里我用简单工厂最多，足够解决大部分问题。工厂方法是需要对外提供扩展点时才用，抽象工厂是产品必须成套出现时才用。不会为了用设计模式而用。"

## 三、代理模式（Proxy）

### 核心思想
不直接访问目标对象，通过代理对象控制访问，在前后插入逻辑，调用方无感知。

```
调用方  →  代理对象（加逻辑）  →  真实对象
```

### JDK 动态代理

**限制**：目标类必须有接口。

```java
UserService target = new UserServiceImpl();

UserService proxy = (UserService) Proxy.newProxyInstance(
    target.getClass().getClassLoader(),
    target.getClass().getInterfaces(),
    new InvocationHandler() {
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            System.out.println("前置：" + method.getName());
            Object result = method.invoke(target, args);
            System.out.println("后置：" + method.getName());
            return result;
        }
    }
);
proxy.save("张三");
```

**原理**：运行时在内存里动态生成一个新类，实现同一个接口，每个方法都转发给 `InvocationHandler.invoke()`。必须有接口，因为代理类通过实现同一接口来「伪装」成目标类。

### CGLIB 代理

**解决问题**：目标类没有接口时使用。

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(OrderService.class);
enhancer.setCallback(new MethodInterceptor() {
    public Object intercept(Object obj, Method method, Object[] args,
                            MethodProxy proxy) throws Throwable {
        System.out.println("前置：" + method.getName());
        Object result = proxy.invokeSuper(obj, args);
        System.out.println("后置：" + method.getName());
        return result;
    }
});
OrderService proxy = (OrderService) enhancer.create();
```

**原理**：生成目标类的子类，通过重写方法插入逻辑，最终用 `invokeSuper` 调用父类真实方法。

**限制**：`final` 类和 `final` 方法无法代理（子类不能重写）。

### 两者对比

| | JDK 动态代理 | CGLIB |
|---|---|---|
| 原理 | 实现同一个接口 | 继承目标类生成子类 |
| 要求 | 目标类必须有接口 | 不能是 final 类/方法 |
| Spring 默认 | 有接口时（旧版本） | Spring Boot 2.x 后默认全用 |

### Spring AOP 就是代理模式

Spring 扫描到 `@Transactional`、`@Aspect` 等注解，背后的逻辑：
1. 判断目标类有无接口，选 JDK 代理或 CGLIB
2. 生成代理对象，在方法前后插入事务/日志等逻辑
3. Spring 容器里存的是代理对象，不是你写的原始类

**为什么 AOP 基于代理模式？**
AOP 要「在方法执行前后插入逻辑，且不改原始代码」，代理模式天然就是干这个的——拦截方法调用，前后加逻辑，调用方无感知。两者目标一致，所以自然选代理模式实现。

### 装饰器 vs 代理（对比）

| | 装饰器 | 代理 |
|---|---|---|
| 目的 | 叠加功能，增强能力 | 控制访问 |
| 谁来组合 | 调用方决定套几层 | 代理自己决定，调用方不知情 |
| 层数 | 可无限叠加（套娃） | 通常一对一 |
| 例子 | IO 流叠加能力 | Spring AOP 事务、权限 |

## 四、装饰器模式（Decorator）

### 核心思想
不改变原有类，通过「包裹」的方式动态叠加功能。可以无限套娃，每层只负责自己的增强逻辑。

### 代码示例（奶茶配料）

```java
interface Milk {
    String describe();
    int price();
}

// 基础对象
class BaseMilk implements Milk {
    public String describe() { return "原味奶茶"; }
    public int price() { return 10; }
}

// 装饰器基类：实现同一接口，持有被包裹对象
abstract class MilkDecorator implements Milk {
    protected Milk milk;
    public MilkDecorator(Milk milk) { this.milk = milk; }
}

// 具体装饰器
class PearlDecorator extends MilkDecorator {
    public PearlDecorator(Milk milk) { super(milk); }
    public String describe() { return milk.describe() + " + 珍珠"; }
    public int price() { return milk.price() + 3; } // 问里层价格再加自己的
}

class PuddingDecorator extends MilkDecorator {
    public PuddingDecorator(Milk milk) { super(milk); }
    public String describe() { return milk.describe() + " + 布丁"; }
    public int price() { return milk.price() + 4; }
}

// 使用：随意叠加
Milk order = new PuddingDecorator(new PearlDecorator(new BaseMilk()));
System.out.println(order.describe()); // 原味奶茶 + 珍珠 + 布丁
System.out.println(order.price());    // 17
```

调用链：`PuddingDecorator → PearlDecorator → BaseMilk`，一层层往里问，一层层往外加。

### Java IO 就是装饰器模式

```java
InputStream in = new FileInputStream("a.txt");  // 基础：读文件
in = new BufferedInputStream(in);               // 套一层：加缓冲
in = new DataInputStream(in);                   // 再套一层：加读基本类型
```

想要什么能力就套什么，随意组合，互不干扰。

### 为什么不用继承？

假设有 3 种基础流、4 种增强功能，继承需要 3×4=12 个子类，功能再多就爆炸。
装饰器只需要 3+4=7 个类，随意组合。

## 五、观察者模式（Observer）

### 核心思想
一对多依赖关系。一个对象（Subject）状态变化，所有依赖它的对象（Observer）自动收到通知。

### 代码示例

```java
interface Observer {
    void update(String msg);
}

class Subject {
    private List<Observer> observers = new ArrayList<>();

    public void addObserver(Observer o) { observers.add(o); }
    public void removeObserver(Observer o) { observers.remove(o); }

    public void notifyObservers(String msg) {
        for (Observer o : observers) o.update(msg);
    }
}

// 使用
Subject subject = new Subject();
subject.addObserver(msg -> System.out.println("观察者A收到：" + msg));
subject.addObserver(msg -> System.out.println("观察者B收到：" + msg));
subject.notifyObservers("状态变了");
```

### 典型应用场景
- 消息队列的发布订阅
- Spring 的 `ApplicationListener` 事件监听
- 前端的事件绑定（`addEventListener`）
- GUI 的按钮点击监听

### 观察者 vs 发布订阅

| | 观察者模式 | 发布订阅模式 |
|---|---|---|
| 耦合程度 | Subject 直接持有 Observer | 多一个消息中心解耦 |
| 通知方式 | 通常同步 | 通常异步 |
| 例子 | Spring 事件 | MQ（Kafka、RabbitMQ） |

## 六、策略模式（Strategy）

### 核心思想
定义一组算法，各自封装，可互相替换。**用组合代替大量 if-else**，运行时动态切换算法。

### 代码示例（支付方式）

```java
// 策略接口
interface PayStrategy {
    void pay(int amount);
}

// 具体策略
class WechatPay implements PayStrategy {
    public void pay(int amount) { System.out.println("微信支付：" + amount); }
}
class AliPay implements PayStrategy {
    public void pay(int amount) { System.out.println("支付宝支付：" + amount); }
}

// 消灭 if-else：用 Map 注册所有策略
Map<String, PayStrategy> strategies = new HashMap<>();
strategies.put("wechat", new WechatPay());
strategies.put("alipay", new AliPay());

// 使用：传什么 key 就用什么策略，新增策略只加新类
strategies.get("wechat").pay(100);
```

**对比没有策略模式的写法**：
```java
// 每加一种支付方式，就得改这个方法 ← 违背开闭原则
public void pay(String type, int amount) {
    if (type.equals("wechat")) { ... }
    else if (type.equals("alipay")) { ... }
    else if (type.equals("card")) { ... }  // 越来越长
}
```

### 策略模式 vs 多态

两者底层都是「接口 + 不同实现」，区别在于意图：
- **多态**：对象类型决定行为，对象创建后行为固定
- **策略模式**：同一个对象，运行时可以**动态替换**算法

策略模式的核心价值不是多态本身，而是**把 if-else 变成 Map 查找，新增策略不改旧代码（开闭原则）**。

### 典型应用场景
- 支付方式切换
- 排序算法切换
- 不同促销规则
- Spring 的 `ResourceLoader`

## 七、高频对比题（面试拉开差距）

| 对比 | 结论 |
|------|------|
| 简单工厂 vs 工厂方法 | 简单工厂造一种产品但违背开闭原则；工厂方法每种产品一个工厂，符合开闭原则 |
| 工厂方法 vs 抽象工厂 | 工厂方法造「一个」产品，抽象工厂造「一族配套」产品 |
| 装饰器 vs 代理 | 装饰器是功能叠加（调用方套娃），代理是访问控制（调用方无感知） |
| 装饰器 vs 继承 | 继承是静态的（编译时确定），装饰器是动态的（运行时叠加），且避免类爆炸 |
| 策略 vs 多态 | 多态对象类型决定行为，策略模式同一对象运行时可换算法，核心是消灭 if-else |
| 观察者 vs 发布订阅 | 观察者同步、耦合较紧；发布订阅多了消息中心解耦，通常异步 |
| JDK代理 vs CGLIB | JDK 基于接口，CGLIB 基于继承生成子类；Spring Boot 2.x 后默认全用 CGLIB |

> **目的** → **写法/结构** → **关键细节** → **项目落地/框架体现**
