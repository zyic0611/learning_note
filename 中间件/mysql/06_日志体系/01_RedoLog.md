重做日志 主要是为了保证 Crash-Safe能力 也就是崩溃恢复 主要是确保事务的持久性。  

一般是 预防断电情况 只要事务提交了 就算数据库断电了 数据也不会丢。



## 为什么出现

修改的数据为什么不直接写到磁盘里 还要先去写日志。

核心矛盾 **磁盘的随机IO太慢了** ：

- buffer pool ：mysql为了提高性能 所有的数据增删改查都是在内存进行的。

- 脏页 :内存的数据修改后 和disk里的数据不一致。 叫做脏页 如果每次修改后就把脏页刷回disk 由于真实data可能分布在disk的各个角落 属于随机IO
- WAL:日志先行技术 :innoDB 先在内存中修改数据 然后把修改了什么记录到redolog里 。 写redolog属于顺序I/O  末尾追加 速度快
- 异步脏刷：redolog只要写入成功 mysql就会告诉客户端提交成功。 至于脏页 后台可以打开专门的异步线程 慢慢刷入磁盘。

**所以本质上就是由轻量级的顺序写 替换了笨重的随机写。并且认为只要把数据成功写入redolog 就视为落盘成功** 

## 物理日志

redolog记录格式非常底层  类似于将 表空间id为10 数据页号为20 偏移量为100的位置更新为123

- 为什么设计成物理日志：

因为物理日志恢复速度快 比sql语句快（解析语法树 检查权限 并且需要挨条执行 ) 只需要覆盖对应物理页数据就行， 所以宕机恢复很快的原因。



## 数据结构

空间是固定大小 类比圆环，所以是**环形数组**和双指针。

- 写指针：记录写到哪里

- 检查点 记录有多少数据成功刷盘 刷盘成功 该指针就会移动 腾出redolog空间 。  断电恢复的时候就可以对比检查点 然后顺序往后恢复数据。 该检查点对应物理磁盘的状态。

因为是环形数组 所以采用**循环覆盖写**   旧的数据会丢失



## Os Cache

OS会拿一部分内存 当作磁盘缓存 这就是OS Cache。
任何程序 不管是mysql java python 都没有权限直接操控磁盘硬件。 所以写文件操作 默认都是写到os cache内存里 就立马返回成功。把刷入磁盘的操作丢给操作系统 可以直接返回成功 所以效率很高

### 数据写入

mysql自己在内存里有一个很大的 buffer pool来管理数据页，如果数据刷盘的时候还要经过一次os cache  那就会导致 **双重缓存**、**内存污染** 两个问题。同一份数据在RAM存两次 浪费宝贵的RAM空间。

mysql默认开启 **直接io**  告诉操作系统 数据文件不需要你管 我自己刷盘。

### 日志写入

但是对于redolog binlog两个日志 必须走os cache。

- write() 只是写入os cache

- fsync() 强制操作系统 把oscache里的数据 落盘到disk

这两个api是操作系统提供给上层应用使用的 比如mysql.

推出： 写binlog redolog 也是写入os cache 不可以直接去操纵disk。

### os cache的优点

**为什么日志写入必须走oscache？**

- 因为日志文件是存顺序写。
- 操作系统针对顺序写有极强的优化（比如合并写请求、Page Cache 批量刷脏）。MySQL 把日志 `write()` 到 OS Cache 后可以立刻返回，相当于把耗时的物理写盘动作“外包”给了操作系统。
- 所以，不是 MySQL “无法”直接操作 disk 写日志，而是对于高频的日志追加来说，**借用操作系统的 OS Cache 做缓冲和批量合并，才是性能最高的最优解**。
- 对于mysql写数据来说 都是随机io 就没必要用到 os cache。 





## 刷盘策略

0 :事务提交 不做任何操作。
后台线程每1s 把binlog日志写进oscache 并且同时调用fsync()刷入disk。

1:事务提交马上 写入oscache 并且fsync()。 双1策略 最安全 一个事务对应一次落盘

2: 每次提交事务 马上写入oscache 后台线程每秒执行一次fsync()把oscache里的数据刷入磁盘。


## 必要性
redolog 搭配binlog
如果只有binlog 没有redolog

- binlog的缺点 不知道结果
     - 断电重启后 内存里有很多脏页 去询问binlog binlog 只知道逻辑上修改了什么 
     - 但是不知道脏页写进了硬盘里没有 
     - binlog无法记录物理页的状态 innodb没办法进行精确的崩溃恢复
     - 也就是分不清断电重启后 哪些脏页需要重新刷进去
   - redolog
     - 是循环写的 有个核心概念叫做 checkpoint 
     - checkpoint之前的数据 代表刷入了 这部分的redolog空间就可以被覆盖 
     - 断电重启后 innodb会寻找最新的checkpoint 然后顺序往后执行
