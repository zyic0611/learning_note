# Redis 底层数据结构复习题参考答案（面试版）

## 一、必会题答案

### 1) SDS 解决了 C 字符串哪些问题？
- **长度获取低效**：C 字符串依赖 `\0` 扫描，`strlen` O(N)；SDS 维护 `len`，读长度 O(1)。
- **越界与溢出风险**：C 不记录容量；SDS 维护 `alloc`，修改前检查并自动扩容。
- **二进制不安全**：C 字符串遇 `\0` 提前终止；SDS 按 `len` 处理，可存任意二进制数据。
- **工程结论**：Redis 作为通用内存数据库，必须保证高频字符串操作可预测且安全。

### 2) SDS 字段含义与 `\0` 保留原因
- `len`：已用字节数（真实长度）。
- `alloc`：已分配总容量（不含头部）。
- `flags`：SDS 头类型标记（不同位宽，节省空间）。
- `buf[]`：数据区。
- **保留 `\0` 的原因**：兼容部分 C 函数生态；Redis 内部逻辑仍以 `len` 为准，不依赖 `\0` 判长。

### 3) 预分配与惰性释放
- **空间预分配**：扩容时不只补齐当前需求，还预留额外空间（小于 1MB 倾向翻倍，大于等于 1MB 额外加固定量），减少频繁 `malloc/realloc`。
- **惰性释放**：缩短字符串后不立即归还系统，避免“删一点加一点”的抖动成本。
- **收益**：降低分配器调用次数、降低延迟抖动。
- **代价**：可能短期持有更多内存。

### 4) ziplist 布局与 `prevlen`
- **布局**：`zlbytes | zltail | zllen | entry... | zlend`。
- **`prevlen` 作用**：记录前一节点长度，支持从尾到头回退遍历。

### 5) ziplist 连锁更新
- **触发点**：节点头部里 `prevlen` 编码从 1 字节膨胀到 5 字节（典型阈值是前一节点长度跨过边界）。
- **过程**：某节点变长 -> 后继节点 `prevlen` 也需膨胀 -> 连续传播。
- **成本**：连续内存搬移与重分配，最坏可退化到 O(N^2) 级别，导致明显抖动。

### 6) listpack 为何避免连锁更新
- **关键变化**：节点不再存“前一节点长度”，而是存“当前节点总长度（放尾部）”。
- **结果**：前面节点变大，不会迫使后面节点改头信息，避免级联扩散。
- **副作用权衡**：编码与遍历逻辑稍复杂，但换来更稳定的修改成本。

### 7) quicklist 的平衡思路
- **结构**：外层双向链表，内层每个节点是一个紧凑连续块（早期 ziplist，后续 listpack）。
- **平衡点**：
  - 不做“整条 list 一个大连续块”，避免大块内存申请失败。
  - 不做“每元素一个链表节点”，减少指针开销与碎片。
- **本质**：分段连续 + 链式连接。

### 8) quicklist 两端操作为何仍接近 O(1)
- 外层保留头尾指针，`LPUSH/RPUSH` 主要命中头尾块。
- 只有头尾块满时才新挂一个块节点，属于摊销常数成本。

### 9) dict 的冲突、索引、插入策略
- **冲突解决**：拉链法（同桶链表）。
- **索引计算**：`hash & (size - 1)`，位运算快于取模。
- **为何 size 取 2 的幂**：保证 `hash % size == hash & (size - 1)` 成立。
- **插入策略**：头插，常数时间完成入桶。

### 10) MurmurHash2 -> SipHash 的原因
- MurmurHash2 性能高但抗碰撞攻击弱，可能被构造大量同桶 key，触发 HashDoS。
- SipHash 更抗恶意碰撞，牺牲少量性能换稳定性与安全性。
- **面试表达**：从“纯性能优先”升级为“性能 + 对抗性输入鲁棒性”。

### 11) 渐进式 rehash 完整流程
1. 分配新表（`ht[1]`）。
2. 打开 rehash 状态（`rehashidx` 从 `-1` 变非负）。
3. 每次普通 CRUD 顺带迁移一部分桶（按 `rehashidx` 推进）。
4. 若业务空闲，后台任务补迁移，避免长期停滞。
5. 迁移完成后释放旧表，`ht[1]` 变主表，`rehashidx` 复位。

### 12) rehash 期间读写路由
- **新增**：直接写新表，避免回流旧表。
- **查/删/改**：先旧后新（或双表查），确保迁移中不漏数据。
- **遍历类命令**：需覆盖双表。
- **设计目标**：不停服完成迁移，同时保证一致可见。

### 13) 后台持久化时扩容阈值提高原因
- `BGSAVE/BGREWRITEAOF` 依赖 `fork + COW`。
- 若此时大规模 rehash，会改写大量页，触发更多物理页复制，内存瞬时放大。
- 提高阈值是为了延后 rehash，降低 COW 放大风险。

### 14) intset 适用条件与权衡
- 适用：set 元素全是整数且规模较小（你笔记中提到默认阈值 512）。
- 权衡：用有序整数数组减少哈希节点/指针开销（省内存），但插入可能搬移（多 CPU）。

### 15) intset 为什么有序
- 有序后可二分查找，查询 O(logN)。
- 插入需定位 + 可能搬移，均摊不如哈希插入稳定。
- 适合“小而纯整数”的集合场景。

### 16) intset 升级与不降级
- **升级触发**：新元素超出现有编码范围（16->32->64 位）。
- **升级步骤**：扩容 -> 从后向前搬迁并重编码 -> 把新值放首或尾 -> 更新头信息。
- **只升不降**：避免频繁抖动重分配；历史上出现过大值，未来大概率还会出现。

### 17) 跳表 O(logN) 的依据
- 每层按概率抽样保留节点，层数期望是对数级。
- 查找过程“高层快速跳 + 逐层下沉”，总比较次数期望 O(logN)。
- 随机化用于近似平衡，避免复杂旋转维护。

### 18) zset 选跳表而非红黑树/B+树
- **范围查询友好**：定位起点后，底层链可顺扫区间。
- **实现复杂度低**：不需要严格平衡旋转逻辑。
- **内存场景差异**：Redis 在内存中，B+树“为磁盘 I/O 降树高”优势不明显。

### 19) Redis 跳表工程化改造
- 底层带后退指针，支持反向遍历。
- 分数相同再按成员字典序，保证稳定有序。
- 最大层数和晋升概率做工程参数化控制。

### 20) 何时紧凑编码，何时升级通用结构
- **共性原则**：小数据、规则数据优先紧凑编码（省内存、cache 友好）。
- **触发升级**：规模上升、元素类型变复杂、写入模式导致紧凑结构代价上升。
- **示例**：
  - set：纯整数小集合倾向 intset，复杂后转哈希表。
  - list：紧凑块由 quicklist 管理，避免单块过大。
  - zset/hash：小对象倾向紧凑表示，越界后转通用结构。

## 二、进阶题答案

### 21) 如何定位抖动是否来自连锁更新/rehash
- 看慢查询与命令分布：是否集中在中间插入/大对象改写/hash 扩缩容窗口。
- 看内存与 fork 时段：抖动是否与 `BGSAVE/BGREWRITEAOF` 同期放大。
- 看数据形态：是否存在大量临界长度对象（容易触发编码膨胀）。
- 通过“现象-时段-数据分布”三维交叉验证，而不是只看单点指标。

### 22) Redis 中“CPU 换内存”与“内存换 CPU”
- **CPU 换内存**：intset 用二分和搬移，减少哈希节点与指针。
- **内存换 CPU**：SDS 预留空间与元数据，换取更低修改成本和 O(1) 长度读取。
- **核心**：不是固定策略，而是按场景动态选最优点。

### 23) 单线程不等于耗时只来自命令逻辑
- 命令执行外还有内存分配、页复制（COW）、rehash 迁移、数据搬移等成本。
- 单线程只是执行模型；延迟是“数据结构成本 + 系统行为”共同结果。

### 24) 排行榜场景如何解释 zset 性能边界
- 写入：插入/更新需维护有序结构，期望 O(logN)。
- 查区间：先定位后顺扫，范围查询效率高。
- 边界：高并发频繁改分 + 大范围拉取时，核心瓶颈转为排序维护与返回数据量。

### 25) set 从整数到混合类型的影响
- 纯整数小集合可走 intset；混入字符串后需转通用哈希结构。
- 影响：内存占用上升、对象封装与哈希开销上升，但通用性更强、操作复杂度更稳定。

### 26) 从局部性比较三种结构
- linkedlist：节点离散，cache 命中较差。
- ziplist/listpack：连续内存，局部性好，但修改时搬移成本敏感。
- quicklist：分段连续，兼顾局部性与可扩展性。

### 27) 证明你真懂 rehash 的回答框架
- 先讲**为什么不能一次性搬**（单线程阻塞风险）。
- 再讲**怎么分摊**（CRUD 带迁移 + 后台兜底）。
- 再讲**一致性策略**（双表查、写新表、遍历双表）。
- 最后讲**与持久化/COW关系**（阈值调优）。

### 28) 底层结构演进主线
- 主线一句话：**围绕延迟稳定性和内存效率，在“紧凑编码”与“通用结构”间按数据规模动态切换**。
- SDS：先解决字符串安全与效率基本盘。
- ziplist->listpack：修复连锁更新导致的尾延迟风险。
- quicklist：用分段方式折中连续内存与链式扩展。
- dict/rehash：用渐进迁移保障在线可用。
- intset/skiplist：分别针对“纯整数集合”和“范围有序访问”做特化。

## 三、模拟追问答案

### 29) “ziplist 有问题，为何早期还用？”
- 在“小数据 + 少中间改写”场景下，ziplist 的紧凑性和局部性收益非常高。
- 工程实践先追求主要矛盾：先把内存占用压下来，再在规模增长后迭代缺陷。
- listpack 是后续版本对真实线上问题的演进，而不是否定早期设计。

### 30) “rehash 不阻塞，为何仍会抖动？”
- 渐进式只是避免“一次性大阻塞”，不等于零成本。
- 迁移本身有摊销开销；叠加 COW、分配器行为、大 key 访问，仍会出现尾延迟抖动。
- 正确表述应是：**显著降低阻塞风险，而非完全消除抖动**。

### 31) “intset 查找快，为何不统一替代 dict set？”
- intset 适合纯整数 + 小规模；一旦类型混杂或规模变大，插入搬移成本和泛化能力都不如哈希表。
- dict set 在通用场景下复杂度更稳定，且支持更丰富键类型。

### 32) “跳表随机性会不会不稳定？”
- 理论上存在最坏情况，但概率极低；实践中通过固定概率、层高上限等参数控制风险。
- Redis 追求的是实现简单、范围查询友好和工程可维护，不是教科书最坏界的绝对极致。

## 面试作答模板（可复用）

当你回答任一底层结构题时，尽量按这 5 句走：

1. **先定义**：这结构解决什么问题。  
2. **讲结构**：核心字段/组织方式。  
3. **讲复杂度**：读写查改大概成本。  
4. **讲权衡**：它牺牲了什么、换来了什么。  
5. **讲演进**：在什么条件下会被替代或升级。  

只要这 5 句稳定，你的回答会非常像“真正做过高并发系统的人”。
