字符串遇到`\0`就会停下来 无法读二进制流。 动态扩容麻烦 需要预先分配好内存 。查询长度需要on的时间复杂度便利。

因为：

**订正：**
- <mark>还漏了「缓冲区溢出/越界」：C 字符串不记录已分配容量，拼接时容易越界写；SDS 用 `alloc - len` 检查并自动扩容。</mark>
- <mark>「动态扩容麻烦」应改为：C 字符串扩容需开发者自己 `realloc` 且容易算错；SDS API 内部自动处理。</mark>
- <mark>SDS 用 `len` 字段读长度是 **O(1)**，不是 O(n)。</mark>
- <mark>「因为」应补全：Redis 要存二进制数据（RDB/AOF/图片等）、高频改字符串、且要可预测的延迟，C `char*` 无法满足安全性和性能要求。</mark>

### 2) SDS 的 `len`、`alloc`、`flags`、`buf` 各自含义是什么？`buf` 末尾为何还保留 `\0`？
答题区：

len代表长度
alloc:分配的内存长度
flags:
buf:

因为方便

**订正：**
- <mark>`len`：当前字符串**实际已使用**的字节数（真实长度）。</mark>
- <mark>`alloc`：当前 SDS **总共分配**的容量（不含头部元数据），`alloc - len` 即剩余可用空间。</mark>
- <mark>`flags`：SDS 类型标记（`sdshdr5/8/16/32/64`），短串用更小的头省内存。</mark>
- <mark>`buf[]`：真正存数据的字节数组。</mark>
- <mark>保留 `\0` 是为了**兼容部分 C 库函数**（如 `printf`、`strcmp`）；但 Redis 内部以 `len` 为准判长，不依赖 `\0`。</mark>

### 3) SDS 的空间预分配与惰性释放策略分别是什么？这样设计的收益与代价是什么？
答题区：

就是每次申请空间 不足1mb 分配1mb 超过mb 按需分配 如果长度减少 不会释放空间
收益就是避免了动态的扩容 代价是可能会产生内存碎片

**订正：**
- <mark>**空间预分配**（你写反了）：修改后 `len < 1MB` → 扩容到 **2 倍**；`len >= 1MB` → 在所需空间上**再多分配 1MB**。</mark>
- <mark>**惰性释放**：缩短字符串后**不立即 `free` 还给 OS**，保留 `alloc` 容量，方便后续追加。</mark>
- <mark>收益：减少 `malloc/realloc/free` 次数，降低延迟抖动。</mark>
- <mark>代价：可能**短期多占内存**（不是「内存碎片」——碎片是分配器层面的空洞，这里主要是预留空间未释放）。</mark>

### 4) ziplist 的整体布局是什么？`prevlen` 字段的作用是什么？
答题区：

整体布局就是 总字节数目 尾节点偏移量 节点数 entry..
prevlen字段就是可以记录前一个元素的长度

**订正：**
- <mark>整体布局：`[zlbytes 总字节数] [zltail 尾节点偏移] [zllen 节点数] [entry1] [entry2] ... [zlend 255 结尾标志]`。</mark>
- <mark>每个 entry：`[prevlen 前节点长度] [encoding 类型+长度] [data 数据]`。</mark>
- <mark>`prevlen` 不仅「记录长度」，更是为了**从尾部反向遍历**——指针退到前一 entry 起点。</mark>

### 5) 解释 ziplist 连锁更新（cascade update）触发条件、过程与最坏复杂度。
答题区：

由于prevlen字段 前一个元素长度0-254之间 分配1字节 否则5字节 如果每一个元素刚好都在253 252之类的 则prevlen都是1字节。 如果在第一个元素前插入1个大元素 则第一个元素的prevlen需要修改为5字节 则第一个元素的总长度就超过254 就会导致下一个元素的prevlen需要修改为5字节 以此类推 导致了连锁更新的问题
最坏复杂度是0n

**订正：**
- <mark>过程描述基本正确 ✓</mark>
- <mark>补充触发条件：当前节点因插入/变长导致自身变大 → 后继节点的 `prevlen` 从 1 字节膨胀到 5 字节 → 后继节点也变长 → 级联传播。</mark>
- <mark>最坏复杂度应写 **O(N²)**，不是 O(N)。每次连锁都可能触发内存重分配和数据拷贝，N 个节点连环膨胀时总代价可达平方级。</mark>

### 6) listpack 相比 ziplist 的关键结构变化是什么？它为什么能避免连锁更新？
答题区：

关键结构变化是不再记录前一个元素的长度prevlen 而是在元素结尾加一个字段 记录该元素的长度。 由于不记录前一个元素的长度 不管前面加入多大的元素 本元素的长度都不会变。

**订正：**
- <mark>基本正确 ✓</mark>
- <mark>补充字段名：`element-tot-len`（节点总长度），放在 entry **尾部**。</mark>
- <mark>反向遍历：指针在节点末尾，读 `element-tot-len` 往前跳即可找到上一节点，无需知道前驱长度。</mark>

### 7) quicklist 的结构是什么？它如何平衡“链表碎片化”和“压缩列表大块连续内存”这两个矛盾？
答题区：

结构是 外层双向链表 双向链表的结点是 ziplist。 
把大部分数据都存储在ziplist连续内存里 只有少量的指针链接 缓解了链表碎片花的问题
并且每一段ziplist只有部分数据 把连锁更新的问题限定在了小ziplist中。

**订正：**
- <mark>基本正确 ✓</mark>
- <mark>补充：Redis 7.0 后内部节点已从 ziplist **升级为 listpack**（消除连锁更新）。</mark>
- <mark>平衡本质：**分段连续**——既避免整条 list 一块巨型连续内存（申请困难），又避免每个元素一个链表节点（指针开销大、碎片多）。</mark>

### 8) 为什么说 quicklist 的两端操作仍然接近 O(1)？
答题区：

因为外部是双向链表 双向链表头尾的操作为o1 并且头尾的ziplist是一块连续的内存 符合cpu cache机制 读取速度很快 所以接近o1

**订正：**
- <mark>「双向链表头尾 O(1)」这点正确 ✓</mark>
- <mark>但核心原因不是 cache，而是：`LPUSH/RPUSH` 只需操作**头/尾那个 listpack 节点**，在节点内追加即可；只有该节点满了才新建一个 listpack 挂到链上，属于**摊销 O(1)**。</mark>
- <mark>cache 友好是额外收益，不是 O(1) 的主因。</mark>

### 9) dict 的冲突解决、索引计算、插入策略分别是什么？为什么哈希表大小常取 2 的幂？
答题区：

冲突采取拉链法解决
索引计算 用二进制的&计算 value&(size-1)
插入策略：
size取2的幂 能保证 索引计算 value%size=value&(size-1)


**订正：**
- <mark>冲突解决、索引计算正确 ✓</mark>
- <mark>**插入策略你漏了**：同桶内采用**头插法**（新节点插到链表头部），入桶 O(1)，无需遍历。</mark>
- <mark>索引应写 `hash & (size - 1)`，不是 `value`（value 是存的值，索引用的是 key 的哈希值）。</mark>
- <mark>size 取 2 的幂：让 `%` 等价于 `&`，位运算比除法快；且保证均匀分布。</mark>

### 11) 什么是渐进式 rehash？请给出完整流程（触发、迁移、结束）。
答题区：

触发条件： 哈希表需要扩容
迁移： 是两个数组实现迁移。 采用的懒迁移 每次对旧数组上的数据访问的时候 才吧对应的数据迁移到新数组
如果都迁移完毕 就修改rehash标记 标记为迁移完毕 并且 新旧数组对换

**订正：**
- <mark>**触发条件不完整**：扩容（负载因子 ≥ 1，BGSAVE 期间 ≥ 5）+ **缩容**（负载因子 < 0.1）。</mark>
- <mark>结构是 `ht[0]`（旧表）和 `ht[1]`（新表），不是泛泛的「两个数组」。</mark>
- <mark>迁移机制：每次 CRUD 时顺带迁移 `ht[0]` 在 `rehashidx` 位置的**整个桶链表**到 `ht[1]`，然后 `rehashidx++`。</mark>
- <mark>补充：若服务器空闲无 CRUD，**后台定时任务**会批量迁移，防止 rehash 长期停滞。</mark>
- <mark>完成后：释放 `ht[0]`，`ht[1]` 指针赋给 `ht[0]`，`rehashidx` 重置为 -1。</mark>

### 12) rehash 期间，新增、查询、删除、修改分别怎么路由？为什么要这么做？
答题区：

新增：直接去新表
查询：查新的 查不到再去旧的
删除：删除新的和旧的
修改：修改新的 并把旧的清空
保证了数据一致性

**订正：**
- <mark>新增 → 直接写 `ht[1]` ✓ 正确</mark>
- <mark>查询 → 应**先 `ht[0]` 再 `ht[1]`**（你写反了）。数据可能还在旧表未迁出。</mark>
- <mark>删除 → 也是**先 `ht[0]` 找，找不到再去 `ht[1]` 删**，不是两个都删。</mark>
- <mark>修改 → 先定位（旧→新），找到后在**所在表**上改；不是「改新的清空旧的」。</mark>
- <mark>全量遍历命令（如 `HGETALL`）需**同时遍历两表**，防遗漏。</mark>
- <mark>设计目的：新增只进新表避免回流；读写先旧后新保证迁移中的数据不丢。</mark>

### 13) 为什么在 `BGSAVE/BGREWRITEAOF` 期间，扩容阈值会从 1 提高到 5？
答题区：

底层是fork()出一个子线程 本质上是COW机制。当写入的时候 就会复制出一块内存 如果写入频繁 则对内存消耗大 如果在此期间 又触发扩容 会导致内存占用进一步提升 可能OOM

**订正：**
- <mark>核心逻辑正确 ✓</mark>
- <mark>「子线程」→ 应为 **子进程**（`fork()` 创建的是子进程，不是线程）。</mark>
- <mark>补充：rehash 会大量修改内存页 → 触发 COW 页复制 → 父进程内存占用暴增；提高阈值是为了**推迟 rehash**，降低 COW 放大风险。</mark>

### 14) intset 的适用条件是什么？它与 dict 版 set 的权衡点是什么？
答题区：

使用条件是创建一个set 里面全都是整数。
权衡点是内存连续 只能存整数  数据有序存储 内存占用小
dict版 查询速度快  o1 可以存储所有数据类型 

**订正：**
- <mark>适用条件不完整：全是整数 **且元素数量 < 512**（`set-max-intset-entries` 默认值）。</mark>
- <mark>intset 查询是 **O(log N) 二分查找**，不是 O(1)；但省了哈希表节点和指针，**更省内存**。</mark>
- <mark>intset 插入需要搬移数组，最坏 **O(N)**；dict 插入均摊 **O(1)**。</mark>
- <mark>权衡总结：intset = **用 CPU（二分+搬移）换内存**；dict = **用内存换 O(1) 操作**。</mark>

### 15) intset 为什么要求有序？插入与查询复杂度分别是什么？
答题区：

因为有序方便二分查找。 插入的时间复杂度为on 查询ologn

**订正：**
- <mark>核心正确 ✓：有序是二分查找的前提，否则无法 O(log N) 定位。</mark>
- <mark>插入 O(N)：先二分找插入位置，再把后面元素整体后移（数组搬移）。</mark>
- <mark>查询 O(log N)：有序数组上二分查找。</mark>
- <mark>补充：intset 用**有序数组**替代哈希桶，本质是**用 CPU 换内存**——牺牲插入搬移，换取无指针、高紧凑度。</mark>

### 16) intset 的升级机制是怎样的？为什么“只升级不降级”？
答题区：

当插入一个新的数据的时候 并且该数据 目前intset的数据类型无法满足的时候 就会发生升级。


**订正：**
- <mark>触发条件正确 ✓：新元素超出当前 encoding 范围（INT16 → INT32 → INT64）。</mark>
- <mark>**升级步骤你漏了**：</mark>
  - <mark>1. 按新 encoding 重新分配更大内存</mark>
  - <mark>2. **从后往前**搬迁旧元素并重编码（防覆盖）</mark>
  - <mark>3. 新元素因触发升级，一定在数组**最前或最后**，直接安置</mark>
  - <mark>4. 更新 `encoding` 和 `length`</mark>
- <mark>**只升不降的原因**：</mark>
  - <mark>防止临界值元素反复进出导致频繁重分配（抖动）</mark>
  - <mark>曾经出现过大整数，说明业务可能需要，维持高位 encoding 更划算</mark>

### 18) Redis 的 zset 为什么使用跳表而不是红黑树或 B+ 树？
答题区：
红黑树或者b➕树虽然查找单个节点快 但是在插入或者删除元素的时候 维护树的平衡开销大。 并且只支持查找单个节点速度快 zset通常需要范围查找 跳表最底层采用双向链表连接 范围查找友好 红黑树b+树范围查找需要中序遍历。 并且zset可能需要对两个字段进行排序 跳表可以实现。


**订正：**
- <mark>范围查询、底层链表顺扫、红黑树中序遍历——这几点很好 ✓</mark>
- <mark>补充 **B+ 树 vs 跳表**：B+ 树为**磁盘 I/O** 优化（降低树高、减少随机读）；Redis 数据在**内存**中，读速快，不必为降树高刻意用 B+ 树。</mark>
- <mark>补充 **实现成本**：跳表插入只改相邻指针 + 随机层高，无需红黑树左旋/右旋，代码简单、维护成本低。</mark>
- <mark>补充 **内存**：跳表通过晋升概率（1/4）控制索引密度；红黑树每个节点都要存左右子指针 + 颜色位。</mark>
- <mark>「两个字段排序」更准确的说法：节点先按 `score` 升序，`score` 相同再按 `member` **字典序**排序，保证唯一有序——这是 Redis 跳表的工程规则。</mark>

### 19) Redis 跳表有哪些“非教科书式”的工程化改造？
答题区：
每插入一个新的节点 采用抛硬币的方式决定 要不要构建上层指针


**订正：**
- <mark>「抛硬币决定层高」是**标准跳表机制**，不是 Redis 特有改造，面试里别当答案重点。</mark>
- <mark>Redis 真正的工程化改造：</mark>
  - <mark>**第 0 层加后退指针**：标准跳表是单向的，Redis 在最底层加了 `backward`，支持 `ZREVRANGE` 等反向范围遍历。</mark>
  - <mark>**双重排序**：`score` 相同按 `member` 字典序排，保证节点唯一、顺序稳定。</mark>
  - <mark>**层高上限参数化**：默认晋升概率 1/4，最大层数 Redis 5.0 前 32 层、之后 64 层，控制索引开销。</mark>
