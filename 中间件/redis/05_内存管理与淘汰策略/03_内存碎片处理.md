## 内因

redis默认使用内存分配器为 jemallloc 不是要多少字节就给多少字节 而是按照固定的刻度进行分配。 所以会产生内部碎片。

## 外因

**频繁的对redis进行del set 修改值长度  zrem移除集合元素**

​	假设内存中原本连续存着 A、B、C 三个对象。

​	业务逻辑删除了 B。此时 A 和 C 中间就空出了一个“坑”。

​	接着，新来了一个对象 D。如果 D 的体积大于 B 留下的坑，D 就塞不进去，只能去内存末尾申请一块全新的空间。

​	久而久之，内存里到处都是塞不进新数据的小坑。**虽然这些坑的总体积很大，但因为不连续，导致操作系统不得不给 Redis 分配更多的物理内存。** 这就是**外部碎片**



## 内存碎片率

ratio= used_memory_rss/used_memory

​	used_memory_rss： 是操作系统实际上分配给redis进程的物理内存大小

​	used_memoru：redis 逻辑分配出去的内存 也就是实际存放数据占了多少内存

ratio:

1.03~1.30 ：健康 少量内存碎片

\>1.50：碎片率超过50 警报

<1.0 说明物理内存不够redis用 redis数据往硬盘塞 redis性能严重下降



## 自动活跃碎片清理

**redis4.0以前 延迟高** 

遇到内存碎片 只能重启redis redis会重新用rdb/aof文件来加载数据到内存 顺序写入 碎片就消失了。 但是会导致主从切换和短暂服务不可用



**redis 4.0 以后：active defrag**   

defrag是磁盘碎片整理的意思

是一种无缝迁移的技术。 

redis用后台定时defrag线程 持续扫描内存中的各种对象 比如dict、skiplist、quicklist 判断是否值得整理。 
发现对象所在的内存块碎片比较多 就重新就向os申请一块刚好合适的新连续内存 把旧数据拷贝过期 然后释放内存碎片率高的旧内存。也就是迁移数据过去


**阻塞主线程**

后台线程可以负责申请新内存 复制数据。

但是真正修改对象引用、更新指针等涉及数据一致性的操作，需要在主线程完成，因此整理过程中仍然会产生一定延迟。 



**Active Defrag 为什么默认不开？**

原因就是整理碎片需要申请内存 复制对象 修改引用 释放旧内存 CPU消耗高。所以碎片不高 没必要整理
