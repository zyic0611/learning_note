rdb解决了数据恢复速度 和冷备的问题。

但是由于其定时快照的机制 注定了无法满足高可用架构 对数据安全性的极致要求。

索引引入了aof机制。 append only file。

aof记录的是Redis协议命令日志 基本上就是redis指令 恢复的时候就重新执行这些命令。

所以AOF恢复等于命令重放 RDB恢复等于数据恢复



## 写后日志

mysql的redo log 采用的是wal 写前日志 即先写日志 再修改内存。

redis的aof相反 先修改内存 再写日志。

原因：

1.省去语法检查开销

​	 redis执行命令之前不会做严格的预编译和语法分析 

​	如果先写日志 可能会把错误的命令记录下来 恢复时出错

​	确保了只有执行成功的命令才会被记录

2.不阻塞当前操作

​	命令执行成功后才写日志 不会因为写日志的写磁盘延迟而阻塞当前命令的执行 日志是在磁盘里 

3.Redis是内存数据库

如果采用WAL  那么：整个Redis请求都会等待日志。则丢失了内存访问的优势。

Redis期望是修改内存后直接返回 后台慢慢写日志 优先保证响应速度 而不是零数据丢失

问题：

1.极小概率丢失数据

​	如果命令再内存中生效，还没来得及写aof redis进程崩溃 数据就丢失了

2.可能阻塞下一条命令

​	写后日志虽然不因为fsync阻塞当前命令 。因为命令写入aof_buf后 只要成功write进内核缓冲区 就直接返回客户端。不会真正等待磁盘io

但是aof写入是在主线程中执行的(写入内核缓冲区 用fsync()刷盘) 如果磁盘io压力大 还是可能阻塞后续命令



## 刷盘策略

aof不是直接写入磁盘的 类比redolog binlog 都是在linux os层面经历两个阶段

1.主线程write() 把命令追加到os的内核缓冲区 page cache 这一步很快

2.后台/主线程fsync() 将内核缓冲区数据真正的刷盘到物理disk 这一步涉及缓慢的磁盘io

- always(同步写回) 每次执行完wirte命令 立刻同步写回磁盘 绝不丢失数据 但是效率极差 
- Everysec 每秒写回 先把命令写到 系统内核缓冲区  每隔一秒由后台刷入磁盘。 【默认配置  推荐 只会丢失一秒的数据
- No redis只写入内核缓冲区 什么时候刷入磁盘 由os决定 性能最好 但是不安全

### everysec还是有可能会阻塞主线程：

因为如果磁盘io压力大 比如其他进程在疯狂写disk。后台的fsync超过2s（redis固定的）都没执行完。

此时主线程如果继续处理写请求并且试图调用write()写入aof缓冲区。

为了防止数据丢失过多 主线程会主动阻塞等待。直到上一轮的fsync执行完毕 

称为。**aof阻塞问题** 是排查redis p99延迟毛刺的一个方向。



## aof重写机制

### 为什么不能直接修改旧AOF

因为旧的AOF 比如100GB 如果边删除 边压缩 此时 Redis还在写数据 此时整个文件 

**Offset物理偏移量全部都在发生变化** 很难维护  Redis的做法是直接生成新的aof文件 然后直接覆盖 。

也就是**Copy then rename 思想**

并且旧的AOF里面 可能有非常多命令 但是redis里数据不断变化 此时的数据可能远少于aof里的命令数据 所以扫描内存可能更快。

### 重写生成的内容

就是对于redis里所有集合 比如Hash List Set ZSet 生成对应的 **数据恢复命令**

数据恢复那肯定是 添加数据命令 所以是 HMSET RPUSH SADD ZADD

所以AOF Rewrite生成的是 **能够恢复当前状态的最少集合命令**

### 重写

重点： aof重写不是定时任务 是基于文件增长比例触发的低频操作。

Redis 提供了两个核心配置：

- AOF 文件至少达到 64MB 才允许重写
- AOF 文件大小比上一次重写后增加了 100% 才触发

redis引入了 BGREWRITEAOF重写机制

### 重写不是 改写

重写并不会去读取旧的aof文件 并且精简里面的命令 把对一个key 1000次incr操作 合并成set操作

而是一个全新的过程，核心依旧是 fork产生子进程 依然依赖于cow机制 子进程直接扫描当前内存中的全量数据状态 然后用最简洁的命令组合 生成一个全新的aof文件

### 双重缓冲区的并发控制

子进程缓慢生成aof文件时 主线程依旧在接受客户端的写请求。

redis在aof重写期间 主线程会把新来的 写命令 放入本来的 **aof缓冲区** (用来继续写旧aof文件的) 还会放入一个专门的 **aof重写缓冲区**（用来处理增量命令）

#### 为什么必须同时存在

因为rewrite通常需要几十秒 但是旧的AOF不能停 否则redis崩溃的话 就丢失了rewrite期间的几十秒数据 

所以aof_buf是用于写入旧的aof文件 保证正常持久化

同时rewrite_buf 记录重写期间的增量命令

#### 工作流程

1.触发与fork： 

​	主线程触发重写 fork()出子进程 这个子进程是只读的 此时主线程短暂阻塞复制页表 与rdb快照过程fork是一样的

2.子进程写盘

​	cow的核心是 写时复制 不写就共用。此时子进程任务把redis里所有数据 写入新的aof临时文件 只读公共内存 也是cow机制。

3.主线程双写

​	此期间 主线程处理的新写请求 就不像rdb快照那样用cow写入复制的页面。 而是既写入aof_buf 保证原有的aof机制正常运转 又写入aof_rewrite_buf

4.子线程完成

​	向主线程发送信号

5.主线程**合并阻塞**

​	主线程收到信号后 短暂阻塞。将aor_rewrite_buf中累积的新命令 追加到子进程生成的新aof文件末尾。 **不阻塞就会又会丢失新的增量命令**

6.原子替换

​	将新aof文件重命名 原子替换旧文件。Rename 必须是原子的 保证系统里要么是新的 要么是旧的 不能一半新一半旧

总结：

​	虽然aof重写是在后台 仍然两次阻塞 第一次是fork 第二次是合并aof重写缓冲区。。





## aof落盘的深入理解

### 写入aof_buf 用户态

aof_buf 是 Redis 在自己进程的内存中申请的一块空间（可以理解为一个 C 语言的字符串数组或链表）。它完全属于**用户态**。

当 Redis 主线程成功执行完一条命令后，会把这个命令转成 RESP 协议格式的字符串，然后**仅仅是在内存中把它追加到 aof_buf 里面**。

这是纯内存的字符串拼接操作，速度极快，开销极小。**此时根本没有发生任何系统调用（System Call）。**

### 调用 write() 写入 Page Cache 内核态

内核缓冲区（Page Cache）。它属于操作系统的**内核态**。

Redis 是单线程 Reactor 模型，在每一次事件循环（Event Loop）即将结束，准备再次睡眠等待新请求到来之前，**主线程**会发起一次 write() 系统调用。

把刚才攒在 aof_buf 里的所有数据，一次性拷贝到操作系统的内核缓冲区（Page Cache）中。完成后，清空 aof_buf。

### 调用 fsync() 写入物理磁盘（硬件层面

数据从操作系统的内存真正固化到磁盘介质上。

这就完全取决于你配置的 appendfsync 策略了。如果是 everysec，就是后台那个专门的 bio (Background I/O) 线程，每秒钟去调用一次 fsync()，把 Page Cache 里的数据刷进磁盘。



### 为什么要aof_buf

既然最终都要通过 write() 写入内核的 Page Cache，Redis 为什么不每执行完一条命令，就直接调一次 write() 呢？为什么要在进程里搞个 aof_buf 先存着？

**答案是：为了抵御“系统调用（System Call）”带来的巨大性能灾难。**

1. **上下文切换极其昂贵：** 从“用户态”进入“内核态”（调用 write()）是一次非常重的操作，操作系统需要保存当前进程的上下文、切换 CPU 运行级别、执行内核代码、再切换回来。这期间会有几微秒的 CPU 消耗。
2. **批处理（Batching）的艺术：** 假设在这个极短的时间片段（一次事件循环）内，Redis 处理了 1000 条客户端的并发命令。
   - **如果没有 aof_buf**：Redis 会对每一条命令都调用一次 write()，也就是引发 **1000 次**昂贵的用户态到内核态的上下文切换。Redis 的 CPU 直接就被系统调用吃光了。
   - **有了 aof_buf**：Redis 先把这 1000 条命令在内存中拼接到 aof_buf 里。然后在事件循环的末尾，**只调用 1 次** write()，把一大块数据一把梭哈给内核 Page Cache。

> **大厂高频术语归纳**：aof_buf 的本质，就是一个应用层面的 **“写合并（Write Batching）”** 缓冲区。它的存在是为了减少 write() 系统调用的频率，压榨出单线程 CPU 的极限性能。
