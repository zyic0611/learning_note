主从复制和哨兵机制是为了解决单机故障问题:单机故障转移与故障自动转移。

切片集群 是为了解决 单机内存和性能瓶颈 问题。横向扩展、水平扩容。

单机内存：通常不超过10-20GB 否则bgsave导致严重的fork阻塞。

情景：

- 当公司业务数据大到几百GB甚至上TB 一台服务器内存装不下。 
- 并发写操作极高 一台机器的cpu扛不住 
- 就必须用切片集群分担压力到其他物理机。

## hashSlot

集群不采用传统的哈希取摸 因为节点增减的时候会数据大洗牌。

也不采用一致性哈希 容易发生数据倾斜。

固定哈希槽位位16384 

1. 路由算法

   - redis存入一个键值对的时候 redis会拿键名去做 CRC16算法运算 得出一个16bit的数字
- 数字对16384取模 得出key对应的哈希槽编号
   - hash_slot=crc16(key)mod 16385

2. 节点分配算法 比如有三个物理机
   - 平均分配 16384/3 一台拿5461
   - 手动分配 比如两台老机器 一台新的 希望新机器多干活 可以给新的多分点位置

3. 这是一个逻辑概念 并没有实际的槽位 只是把一个键值对映射到到槽位 --> 节点 

4. 为什么是16384 不是crc的最大值 65536
   - redis集群之前通过gossip协议交换心跳信息(ping/pong) 心跳包中包括一个bitmap 宣告该节点负责那些槽位
     - 65536 bitmap 8kb 浪费网络带宽
     - 16384 2kb 比较刚好
   - 集群规模的物理限制： redis cluster的设计不是为了支持很多节点 集群规模一般不会超过1k个节点。 对于1k个节点 16384槽位足够保证数据均匀分布

## 转向重定向 Redirect

为了解决客户端走错门。

java后端开发 面对的是去中心化的集群 客户端理论上可以对集群中的任意一个节点发送命令 如果客户端请求的key所在的槽位 刚好是这个节点管 就直接处理 如果不在：

就需要 MOVED与ASK重定向机制。

### MOVED redirect

适用于槽位已固定的情况。

场景： 客户端拿着一个key找node A 、nodeA计算了一下槽位 发现归Node B管。

动作： Node A拒绝处理 返回错误 `MOVED <slot> <node b 的ip port>`

客户端响应： 客户端收到moved后 知道了 要去node请求 并且更新本地的槽位-节点缓存映射 下次就直接去找b。



### ASK redirect

适用于槽位正在迁移中。

场景：集群正在扩容 比如新增了node c 、node a的一部分槽要迁移给c。客户端找a 要数据 、key正在迁移 并且已经被搬到了c。

动作： node a 返回`ASK <slot> <node c 的ip port>`

客户端响应： 客户端收到后 先给c发一个asking打招呼命令 紧接着发送真正的数据请求。

核心区别： 收到ask 客户端不会更新本地的槽位映射 因为迁移还没结束 槽的映射还在node a里。



## gossip协议

redis cluster 不需要单独的 sentinel集群实现自动的故障转移 自己就可以实现高可用。

- **去中心通信 gossip**: 节点之间通过meet ping pong等消息交换彼此的状态和槽位信息

- **故障转移**: 半数以上的节点ping某个master 超时 就会标记为fail 客观下线。 该master的replica就会发起选举 类似于哨兵 基于延迟和偏移量。 胜出的节点成为master。
- **平滑扩缩容**： 增加新节点 直接加入集群 其他节点的槽位平滑迁移给新节点 ask redirect。 全程不需要停机。



## 一些概念

### 物理机

一个物理机是一个承载节点的容器， 会有很多节点 ，可能是主node 也可能是从node 。所有物理机的node共同组成集群。

为了防止一台物理机断电导致数据丢失，主节点和从节点不会放在一台物理机上。所以物理机上的node是集群 但是没有对应的主从关系。

###  分片

每一个分片采用主从模式 也就是一个主节点对应一个/多个从节点。 抛弃哨兵模式。因为集群自己可以实现故障转移 不需要哨兵模式了。

集群中的每个主节点 既承担数据读写的工作 又兼职类似于哨兵的监控和投票。

### slot

slot是分配给redis node 是一个在特定端口运行的redis进程，不是直接分配给物理机的。

## 优缺点分析
### 优点
1. HA：横向拓展内存 自带哨兵机制。
2. 高性能：以前是所有客户端对一台机器读写 现在是几台 几十台同时处理请求 QPS成倍增加
3. 扩展性好 ：当需要提升的时候，直接加几台机器进集群，然后把旧机器的一部份哈希槽包括数据迁移到新机器 。不需要的 也可以下线结点 很方便
### 缺点
1. 部署和维护复杂 需要监控几十个节点的所有问题 运维难度大
2. 数据同步延迟 节点越多 网络通信越复杂 如果某个结点挂了 引发主从切换 或者进行槽位迁移 都会占用大量的网络带宽和磁盘IO 这个此前可能会出现短暂的读写延迟和 报错
3. 某些操作不能跨节点实现。比如一行指令同时涉及到node a & node b redis集群默认不支持跨多node进行事务操作或者多键操作 则会报错
