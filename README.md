## 三条主线

### 1. Java 与运行时

不是背 API，而是沿着「字节码 → 内存布局 → 并发语义 → 回收」一路往下。

- 语言层：值传递、泛型擦除、`String` 不可变、异常与设计模式
- 并发层：JMM 可见性 → 指令重排与内存屏障 → MESI → `CAS`/`AQS` → 锁升级 → `ThreadLocal` → 线程池
- 运行时层：类加载与双亲委派 → 对象内存模型 → 可达性分析 → 分代收集 → CMS/G1/ZGC

入口：[Java 宏观认识](java/basic/宏观认识.md)、[JMM 内存模型和可见性](java/JUC/02_volatile/01_JMM内存模型和可见性.md)、[JVM 整体架构](java/JVM/01_基础结构/01_JVM整体架构.md)

### 2. 存储与分布式

先看单机存储怎么撑住读写，再看多机怎么保持一致与可用。

- **MySQL**：数据页与行格式 → B+ 树与索引 → 最左匹配/索引失效 → MVCC 与锁 → redo/undo/binlog → 主从延迟/分库分表
- **Redis**：SDS/ZipList/QuickList/SkipList → Reactor 与 IO 多路复用 → RDB/AOF → 哨兵/分片 → 分布式锁 → 穿透/击穿/雪崩/双写一致
- **RabbitMQ**：AMQP 模型 → Exchange 路由 → 生产/Broker/消费三段防丢 → TTL/死信/延迟队列 → 幂等消费
- **微服务**：DNS → LVS → Nginx → API 网关 → RPC（南北流量），以及 RPC 内部的服务发现、负载均衡、超时/重试/熔断/限流（东西流量）

入口：[用户请求全链路](微服务/用户请求全链路/定义.md)、[MySQL 整体架构](mysql/00_基础与架构层/01_MySQL整体架构.md)、[Redis 线程模型](redis/03_线程模型和执行原理/03_线程模型.md)

### 3. AI 应用工程

核心判断：**不确定的语义决策交给 Model，确定的状态、权限、执行与终止交给 Runtime。**

- Agent 基础：从 L0 确定性代码逐级长到 L5 Multi-Agent，只为真实问题增加结构
- 上下文：消息结构、指令与事实的冲突、Prompt、Context Engineering、结构化输出
- 工具：Tool Call 闭环、工具定义、协议、Runtime 校验、多工具协作
- 记忆与编排：写入/召回/存储架构，Workflow/Subflow/Checkpoint/失败处理
- 工程化真问题：长任务跑偏、多步任务失败、工具调用不可靠、记忆污染、上下文取舍
- 评测与观测：三层观测对象（Model/Tool/Runtime）、四层观测层级、各类 Span、metric 与故障归因
- RAG：PDF/代码/表格解析 → chunk 策略 → 索引与向量检索 → 召回后处理 → 评估与调优

入口：[Agent 系统心智模型](agent/基础/0_Agent系统心智模型.md)、[上下文管理策略](agent/PiAgent/上下文管理策略.md)、[RAG 流程](python面经/RAG流程.md)

## 每篇笔记的写法

1. **问题从哪来**：先说明这个机制要解决什么现实约束，不解决会怎样。
2. **机制怎么走**：用链路、状态机或数据结构图讲清执行顺序。
3. **边界在哪**：什么情况下会失效、退化、放大，例如索引失效、锁退化、缓存击穿。
4. **横向对比**：同类方案的取舍，例如 `CAS` vs 锁、`CopyOnWrite` vs `ConcurrentHashMap`、G1 vs ZGC。
5. **落到排查**：把机制映射回可观测指标和命令。

目录和文件普遍用 `01_`、`02_` 前缀编号，**编号就是建议的阅读顺序**；同一主题内先基础、再底层、最后架构与实战。
