## 度量桶

时间格子内装的真正对象是 `MetricBucket` 度量桶。

一个请求过来 不只是记录通过 他会记录5种维度的数据

- 通过数量
- 被限流/拒绝的数量
- 业务异常的数量
- 业务正常执行的数量
- RT 总响应时间

源码中 内部维护一个数组 装着5个计数器

```java
private final LongAdder[] counters = new LongAdder[5];
```



## 为什么不用AtomicInteger

既然都是原子类 高并发情况下如果用`AtomicInteger` 它的底层原理是 CAS  。 

如果使用CAS的逻辑进行+1 a拿到当前值为0 准备改成1 这一瞬间被人改成1 则a进行自旋 重新去拿1 准备改成2.

当并发数很高的时候 在同一瞬间 可能其他所有线程都发生a的情况 可能只有一个线程修改成功 其他所有线程都在死循环竞争重试 锁竞争激烈 CPU可能飙升到卡死。

**大白话比喻：** `AtomicInteger` 就像超市里**只有一个收银台**。人少的时候很快；一旦来了 5000 个人同时结账，所有人挤在一个通道里，互相推搡，最后谁也结不了账。



## LongAdder

底层使用空间换时间 把热点数据打散

内部：

- base 基础值
- Cell[]

1.低并发的时候： 直接用CAS修改base 速度和`AtomicInteger`一样

2.高并发的时候 ：`LongAdder`发现CAS失败 意味着出现激烈竞争 直接启用Cell数组

3.分流：比如5000个线程进来 LongAdder根据每个线程的hash值 路由到不同cell里去做+1操作

4.当FlowSlot 也就是限流裁决者 需要知道这1s的请求量 对Base和Cell做一个求和



## 伪共享

Cell既然是一个数组 在内存里 是紧挨着的。 现代CPU是通过缓存行读取内存 一次读64字节。 

如果Cell0和Cell1挤在同一个缓存行里   就算线程a修改0 b修改1 cpu硬件底层还会导致缓存一致性锁 

为了压缩性能 ：

​	JDK 的开发者在 `Cell` 类上加了一个神奇的注解：**`@sun.misc.Contended`**。 这个注解的作用是：**在每个 `Cell` 的前后强行塞入空白字节进行占位（Padding）**，确保每一个 `Cell` 都独占一个完整的 CPU 缓存行。这样，线程之间在硬件层面也实现了绝对的物理隔离，真真正正做到了“无锁并发”！
