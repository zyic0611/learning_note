
“排查 CPU 飙升，我的经验主要分四步：

第一步，`top` 找 PID。  
第二步，`top -Hp <PID>` 找具体线程 TID，然后 `printf "%x\n" <TID>` 转成十六进制。  
第三步，`jstack <PID>` 导出堆栈，搜索这个十六进制 nid，打印前后 20 行。  
第四步，看堆栈里线程到底在干什么。

根据我的经验，通常分两种情况：

一种是**业务线程飙升**，比如 `while` 死循环、正则回溯陷阱，这时候就去 review 业务代码。

另一种极其高频，就是**GC 线程（VM Thread）飙升**。这时候 CPU 高其实不是业务在算，而是内存快爆了，JVM 在拼命 Full GC。这时候我会用 `jstat -gcutil` 看老年代使用率和 FGC 频率，再 `jmap -dump` 导出堆快照，用 MAT 分析大对象和 GC Roots 引用链，定位到底是哪里泄漏了。”

“当然，如果公司允许引入第三方诊断工具，在真实的线上救火场景中，我首选阿里开源的 **Arthas**。遇到 CPU 飙升，直接连上 Arthas，敲一行命令 **`thread -n 3`**，它就能一键直接把当前 CPU 占用率最高的前 3 个线程的堆栈信息打印出来。






“如果系统没 OOM，CPU 也没飙升，但是有些接口就是卡死一直不返回，可能是什么情况？”

-通常是发生了**线程死锁**。排查极其简单，不用去猜，直接用 `jstack` 打印堆栈，拉到文件最后，如果发生了死锁，JVM 会极其明确地打印出一句 `Found one Java-level deadlock` 并把互相死锁的线程列出来。
