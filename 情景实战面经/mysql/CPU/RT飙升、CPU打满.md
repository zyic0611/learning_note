业务现象：线上某订单库，白天业务高峰期，简单的订单状态查询 SQL，where 条件是普通索引，explain 显示也走到索引了，但大量请求 RT 突然飙升，数据库 CPU 打满，没有慢查询告警。请分析可能原因，以及怎么定位处理。

首先我先从现象分析 走索引 没有慢查询。 说明确实命中索引了。 并且sql执行的也快。

如果 短时间有大量查询 也就是高峰期QPS很高 就算单条sql执行很快 比如就15ms 慢查询阈值100ms 不禁慢日志slow log。如果单条sql只需要回表1000次 因为扫描1000行 做内存页访问 耗费CPU。  QPS如果=4000 就会大量的回表 并发放大回表数 CPU消耗很大。
关键看的指标： show status like `Innodb_rows_read`实际每秒扫描的行。

确实命中索引了 但是索引区分度不高 可以理解为在二级索引树上命中了大量节点 比如是range 在索引树上范围访问 产生巨量回表。 虽然sql执行很快 但是回表量大 cpu消耗大

如果sql查询的热点数据并不在buffer pool里  Mysql持续扫描LRU 淘汰页面 消耗大量CPU

在内存里读B+树 虽然读锁可以共享 但是是依赖于CAS加锁 。同时间并发请求很大，就会产生同时间大量CAS，会导致不断自旋 空耗CPU 并且大量请求加内存锁不成功 则RT会相对上升。 可以用performance_schema （PFS）细粒度二点内部事件采集器 来看 B+树页的 rwlock等待
