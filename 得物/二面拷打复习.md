# 得物二面项目拷打复习

## 项目一：智慧环卫招标分析平台（NL2SQL Agent）

---

### Q1：Schema Linking 为什么要 BM25 + Vector 双路召回？

**答：**
- Vector 召回擅长语义层面匹配，但压缩过程中会丢失关键词信息，精确字符匹配能力弱
- BM25 擅长关键词精确召回，两者互补
- 合并使用 **RRF（倒数排名融合）**，公式 `1 / (k + rank)`，只考虑排名不考虑原始分数，类似归一化

**追问：RRF 里 k 的作用？**
- k 用于平滑高排名的权重优势，经验值通常取 60
- 两路都靠前的字段得分最高；只在一路排第一的字段也有竞争力，并非"只有两路都靠前才能排上"

---

### Q2：Join Graph 是什么？怎么补全跨表关联路径？

**答：**
- Join Graph 是离线维护的一张图，**节点是表，边是外键或业务关联关系**
- 当 Schema Linking 识别出查询涉及多张表时，在图上做 **BFS 找最短关联路径**
- 把路径上的 JOIN 条件自动注入到 SQL 生成的 Prompt 里，减少 LLM 幻觉，也是 Prompt Token 降低的原因之一

**示例：**
```
企业表(company) --[company_id]--> 标段表(bid_section)
标段表(bid_section) --[bid_id]--> 中标结果表(bid_result)
```
用户问"某企业的中标金额" → BFS 找到路径 → 自动补全 JOIN 条件

---

### Q3：QueryPlan 语义一致性校验具体检查什么？

**答：**
- 用 AST 解析生成的 SQL，提取 WHERE 条件里的时间节点、表名、字段名
- 与 QueryPlan 里约束的指标、维度、时间范围、关联表逐一比对
- SQL 语法正确可以执行，但业务口径错误（用错时间范围、用错表）才是最危险的情况
- 校验不通过 → 分类反思 → 定向重试，而不是让错误结果返回给用户

**示例：** QueryPlan 定义时间范围为本月，LLM 生成的 SQL 用了上月的日期 → AST 解析出日期值 → 比对失败 → 触发重试

---

### Q4：多轮对话条件继承和覆盖怎么实现的？

**答：三级降级策略**

1. **规则层**：维护槽位关键词表（时间槽位/地区槽位/企业槽位），命中哪个槽位就只更新那个槽位，其余继承上一轮 Session Slot
2. **相似度层**：新问题与上一轮余弦相似度 > 阈值（如 0.85）认为是追问走继承；低于阈值认为新话题走清空
3. **LLM 层**：给 LLM 结构化选择题，只能在继承/覆盖/清空三选一，约束在有限空间决策，不做开放生成

---

### Q5：SQL 只读校验能覆盖子查询吗？

**答：**
- 用 SQLGlot AST **递归遍历所有节点**，只允许 SELECT 操作
- 子查询会出现在 AST 的子节点里，递归遍历可以覆盖到
- CTE（WITH 语句）因为数据库是 MySQL 5.7 不支持，直接排除

---

### Q6：EXPLAIN 扫描行数阈值怎么定的？

**答：**
- EXPLAIN 只让优化器估算执行计划，不真正扫描数据，成本毫秒级，可接受
- 阈值根据业务表数据量和压测结果反推：单表百万级数据，rows 超 50 万触发风险警告，超 200 万直接拦截
- 不是拍脑袋，是压测后结合 P99 延迟定的

---

### Q7：整条 NL2SQL 链路怎么走的？

**答：**

```
用户输入
  → 前置语义理解层
      三级漏斗（话题关联判断）
      槽位提取
      指代消解
      追问快路径判断
      → 结构化问题
  → 主图（LangGraph）
      域内/域外判断（域外路由小模型直接回答）
      追问快路径命中 → 填入缓存结果
      → LLM 主循环（ReAct）
          工具调用 → NL2SQL 子图
              Schema Linking
              生成 QueryPlan
              ReAct 循环：生成 SQL → 执行 → 反思/重试
              返回查询结果
      → 主图润色
  → 返回用户
```

---

### Q8：追问快路径缓存的是什么？

**答：**
- 缓存的是上一轮 SQL 查询结果的**指针** + 查询结果的**元数据描述**（有哪些字段）
- 真实数据还在 Redis 里
- 如果用户追问的问题所需字段在缓存结果里有覆盖，走快路径直接使用；否则重新走 NL2SQL 子图

---

### Q9：反思触发条件是什么？

**答：两层触发**

1. **执行前**：语义一致性校验发现 SQL 与 QueryPlan 不符，直接触发反思，不执行 SQL
2. **执行后**：检测结果异常
   - 空结果（条件太严）
   - 数值越界（金额负数、未来时间）
   - JOIN 爆炸（行数异常大）
   
SQL 执行成功且结果正常时，信任 QueryPlan 校验已保证语义正确性，不做额外 LLM 自评，控制成本

---

### Q10：SSE 怎么推执行进度的？

**答：**
- LangGraph 提供 `astream_events` 接口，图执行过程中每个节点进入/退出、LLM 每个 token 输出都触发事件
- FastAPI 用异步生成器消费事件，按 SSE 格式推给前端
- 前端实时看到"Schema Linking 中"、"SQL 生成中"、"执行查询"等进度和最终 Token 用量

---

### Q11：OpenTelemetry 怎么接 LLM 调用的？

**话术备用：**
> "对 LLM 调用做统一封装，在封装层创建 Span，从 LLM response 的 usage 字段拿到 prompt_tokens 和 completion_tokens，连同模型名、耗时一起写入 Span 的 attributes，上报到 OpenTelemetry Collector。"

---

### Q12：熔断机制是怎么做的？

**答：两层保护，注意区分**

1. **故障熔断**：LLM 接口连续超时或报错达到阈值 → 熔断器打开 → 后续请求直接降级返回兜底提示，不再打到 LLM → 冷却后进入半开状态探测恢复
2. **成本守卫（预算保护）**：单次请求 Token 消耗超上限，或图内 LLM 调用次数超限 → 收集已有结果整理后提前返回，告知用户触发限制

> 注意：这是两个不同维度的保护，面试时要说清楚区别

### Q13：这个项目最难的技术点是什么？

**答：**
> "最难的是前置问题理解层。问题理解错了后面所有步骤都白谈，错误会被级联放大。槽位提取、指代消解、追问判断每一步都会影响最终的查询质量，而且这层很难有清晰的量化指标，早期全靠人工观察。"

---

### Q14：重做这个项目会改什么？

**答：**

1. **更早建离线评估集**：早期改动没有量化依据，Schema Linking 准确率 71% → 95% 说明早期有大量线上错误，一开始就应该有金标集驱动迭代
2. **QueryPlan 加入聚合方式约束**：AVG/SUM 混淆目前靠 LLM 自己判断，语义校验捞不到，加进 QueryPlan 后可以直接拦截
3. **Session Slot 加版本栈**：现在槽位直接覆盖，不支持"回到刚才的查询"这类 undo 操作
