Rate Limit

比如 agent 是1000QPS LLM服务器 比如open AI 只能100QPS

那个QPS无法匹配 如果不对agent进行限流 就会导致

- 大量 请求过多提示 llm返回请求过多错误
- 大量请求等待
- 线程池耗尽
- 甚至导致和openai服务端的连接断开 服务雪崩。

## 限流算法

### 固定窗口：

 限定一分钟内最多100次请求 但是在两个分钟的交界处 其实进来了200次请求 称为 **临界突发问题**

一般用redis设置一个 值 每次incr自增 并且设置 60s ttl 即可实现

### 滑动窗口： 

**缺点：存储成本高**

固定窗口的问题是 时间边界会导致突刺 滑动窗口就不按固定时间段 一直动态的看最近60s 

限定最近60s最多100请求  需要记录每个请求的时间戳 。

所以带来缺点 要记录大量请求的时间戳 成本高

**滑动窗口计数器优化 一般用hash 没那么精确：** 把60s拆成小格子 比如10s一个格子 每个格子只记录 10s内的请求数量 。

**使用ZSET实现精确滑动窗口**：

使用zset保存每一次请求时间 也就是score作为时间戳 zset会按照score排序 并且每次进来新的时间戳 可以删除窗口外的时间戳记录 然后统计zset大小就是窗口内的流量

### 令牌桶算法

不限制请求速度 提前发放通行证。

结构是提前生成一批通行证token 请求来了就消耗一个token 

参数：

- 桶容量Capacity：最多允许瞬间有多少个请求。
- 生成速度Rate：平均每秒产生10个token

为什么令牌桶比漏桶更适合 Agent

因为LLM调用有特点 平时稳定的很少 突然会用户集中。

令牌桶： 系统有能力的情况下 会允许capacity数量的请求一次性通过。

漏桶：是请求进入桶以后 以固定的速度出去  限制系统处理速度。



## 总结

对于LLM API的调用 适合采用令牌桶控制整体QPS

对于用户侧接口 适合采用 redis滑动窗口 统计用户最近时间 窗口请求次数 防止单用户调用过多

滑动窗口的实现上 可以使用redis zset 以请求时间戳作为score  每次请求删除窗口外数据 再统计窗口内请求数量

漏桶只能保证消费速度控制为固定速率 保证流量平滑 但是不支持突发流量 所以一般情况用于消息队列

令牌桶按照固定速率生成令牌 允许一定情况突发 目前网管和agent调用llm比较常用
