## 生产端为什么会丢消息

消息从生产者 到 rabbitMQ队列的时候 有两个风险点。

1.网络闪断 或者Broker宕机 ：此时消息完全没到 Broker。  rabbitMQ采用 **Publisher Confirm** 发布确认机制解决。

2.路由失败： 消息发送到了 Broker的 Exchange 但是由于RoutingKey写错了 或者Queue没绑定上BandingKey 消息无处发送 被Exchange丢弃。 RMQ采用 **Return Callback**  路由失败回调解决




## Publisher Confirm

发布确认机制

主要是确定 消息有没有送到Exchange上。 深层： 是用于确认消息是否已经被 RabbitMQ Broker 接收并处理完毕。 也就是消息成功给broker了 但是路由成功还是路由失败不确定 这个由return确定 但是确实处理完了。

### 原理

开启 Confirm模式后 生产者发出的每一条消息 

- 如果消息成功到达 broker broker会回传一个ACK
- 如果 broker内部发生异常 比如磁盘满了 导致拒收message  会会回传一个 NACK

### 同步和异步

- 同步确认：生产者发一条消息 必须死等broker返回ACK 再发送下一条 **生产环境下一般不使用 除非再要求强一致性的场景下 比如支付等 可以牺牲吞吐。** 一般会导致 吞吐量严重下降 失去了引入 MQ异步解耦的初衷
- 异步确认 ：生产者只管发送 message 、broker在后台慢慢回复ACK。   为了提高网络效率 broker会进行批量确认。

### 落地难点 oom风险

异步模式 生产者本地必须维护一个 **未确认消息的集合** 一般是 ConcurrentSkipListMap。 支持按照ID排序  并且 线程安全。

- 发送消息 存入Map
- 收到ACK 从Map里剔除。

极端情况： Broker负载很高 迟迟不回复ACK 则Map疯涨 导致java OOM。因为 Map是放在内存里的。

解决： 必须为Map设置容量限制和过期清理机制 对于超时未确认的消息 写入补偿表或者打入日志 然后从内存中清楚。 并且还要发送限流 对于未确认的消息超过某个阈值 生产者应该暂停发送信息  不能让 发送速度>confirm速度。

所以完整的策略： padding map+ 最大容量限制+超时检测+发送限流+失败补偿


## Return Callback

路由失败回调。  解决的是 消息成功到了 exchange 但是没找到queue怎么办

### 机制

默认情况下 exchange如果找不到合适的queue 会悄悄地把消息丢掉 生产者不知道。   

为了防止这种情况 需要

1. 在发送消息时 设置 `mandatory=true`  打开强制路由
2. 开启 Return Callbak

消息无法被路由的时候 broker就会触发 Return Callbak 把消息 归还给 producer 并且回调里附带 失败原因。

### 注意

return callback 只有在路由失败的时候 被触发 成功的时候是没有任何回调 。 就像一个差评机制 没有消息就是好消息。



java中要设置 CorrelationData 相关数据 一般设置为订单ID或者业务流水号  因为 回调是异步的 当回调的时候 只知道有一条消息失败了 但是不知道是哪一条 必须放入相关数据 回调的时候才知道是哪个业务消息没有发送成功。 回调的时候靠 `correlationData` 精准对账

## confirm失败的做法：

不能仅仅只记录日志  生产一般： confirm nack后  放入失败消息表 定时扫描 重新投递

所以总结：
Confirm失败的消息不能简单丢弃，需要结合本地消息表、重试机制或人工补偿保证最终一致性。



## 总结

confirm 发布确认机制 解决 producer-> broker
return 路由失败回调 解决 exchange->queue

二者经常配合使用 构成 **生产端可靠性投递**
